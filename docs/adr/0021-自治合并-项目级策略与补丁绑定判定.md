# ADR 0021 · 自治合并：项目级策略 + 补丁绑定判定 + 保护路径

> 状态：**已裁决**（2026-10-20，用户在会话中确认 `docs/spec/28-自举闭环-自写自合.md` §3 的 D1–D7 推荐裁决；本 ADR 收其中关于产品的 D1–D6，D7 是施工流程约定，留在 spec 28）。票 #1401。修订 ADR 0018「合并动作留人」与 #1256 的适用范围：两者在 `mergePolicy = human` 下原样有效。施工票 #1403（P2）、#1404（P3）、#1405（P4）、#1406（P5）、#1408（P7）。

## Problem Statement

pacman 的合并动作只由人触发。ADR 0018 把它写进名册（「合并动作留人，不在名册内」），#1256 在两个机器入口硬挡：chief `merge_builds` 与 MCP `merge_builds` 被调用即返回 `MERGE_HUMAN_ONLY_COPY`。

用户要 pacman 在 `xiechimon/pacman` 上自己写 PR、自己合并，用户角色变成事后看 main 上落了什么、抽查、回滚、把纠正升格成闸。参照形态：poteto 2026-09-21 演讲与 pstack 的合并流——写代码的 agent 不批自己的合并；独立验证者按确切的补丁出判定；CI 在最新基线上绿；合并后人抽样复查。

问题拆成四个子题：

1. 合并权怎么下放，同时不改掉对外的默认（README：「Gated by design」）？
2. 谁执行合并，凭什么证明「判定对应的就是被合并的那份代码」？
3. 哪些改动无论判定如何都必须留人？
4. 自动进料怎么防公开仓里的 issue 注入？合并之后实例怎么更新自己？

## Decision

| ID | 裁决 |
|---|---|
| **D1** | 合并权按项目下放：`project.mergePolicy = human \| shadow \| autonomous`，**默认 `human`**。`human` 下 ADR 0018「合并动作留人」与 #1256 的两个硬挡原样有效。`shadow` 计算合并就绪闸、写结果，不合并。`autonomous` 由 server 在合并就绪闸全绿时合并。团队级 `autonomyPaused` 急停开关凌驾于所有项目策略 |
| **D2** | 合并由 **server** 执行：经 `lib/github.ts`（唯一 github.com 出口）调 REST merge，带 `sha` 参数，head 不等于该值即被 GitHub 拒绝。方式为 squash，message 由 server 拼：标题取 PR 标题，正文末行固定写 `closes #<sourceRef 的 issue 号>`。合并权不下发到 agent 机器上的 `gh` 登录 |
| **D3** | 判定绑定**补丁摘要** `patchDigest`：对 `compare/{base}...{headSha}` 的文件列表排除 `docs/verify/**` 后，按 `status filename blobSha` 排序取 sha256。review、verify、chief go/no-go 三种判定都记 `headSha` 与 `patchDigest`，由 server 按判定里的 `headSha` 现算。合并时重算，摘要不等即判定过期、自动重验。update-branch 只合入 main 时摘要不变，判定不重跑；verifier 只向证据目录提交时摘要不变；任何改代码的推送都让摘要变 |
| **D4** | 保护路径命中即强制 `human`，不论策略与判定：`.github/**`、`biome.json`、`scripts/*gate*`、`scripts/*baseline*.json`、`.husky/**`、`CLAUDE.md`、`AGENTS.md`、`docs/adr/**`、合并就绪闸自身的源码、`apps/server/drizzle/**`、`package.json`、`pnpm-lock.yaml`。另外：删除测试文件、补丁超过 800 行或 40 个文件、compare 文件列表被截断、当日自治合并数达上限（默认 10），均强制 `human` |
| **D5** | 自动进料只领带 `ready-for-agent` 标签、且该标签由仓库 owner 或 collaborator 打上的 open issue（events API 核对打标人；读不到打标人即不领）。issue 正文一律按数据处理，不进入 system 层 |
| **D6** | 合并后的实例自更新走独立部署环：挑 main 上必需检查全绿的最新 SHA → 备份库 → 排空在飞步 → 重启 → 健康检查 → 失败回滚到最后已知良好 SHA。回滚由部署脚本完成，不依赖 pacman 自身。npm 发布永远留人 |

### 合并就绪闸（D1–D4 的执行面）

`mergeReadiness(build) → {ready, blockers[]}` 为纯函数，结果写成 head SHA 上的 commit status `pacman/merge-gate`，并在任务详情页与 chief 工具 `merge_readiness` 同源展示。blocker 至少覆盖：

- 策略为 `human`，或自治已暂停；
- PR 非 open 或为 draft；`mergeable_state` 不是 `clean`；
- 必需检查在当前 head 未全绿；`pr-evidence` 未绿；
- 验证判定缺失、未通过或摘要过期；
- 任一审核判定含 blocking 或摘要过期；chief 未出 go 或摘要过期；
- 命中 D4；
- todo 的 `sourceRef` 解不出 issue 号；
- PR body 的 raw 证据链不指向本分支 `docs/verify/<票号>/`。

`pacman/merge-gate` **不加进**分支保护的必需检查：加了会把 Claude Code 车道与人工合并一起锁住。

## 与既有裁决的关系

- **ADR 0018**：「合并动作留人」修订为「合并动作按项目策略归属，默认留人」。名册与「personas do not invoke other personas」不变；chief 小合并步（三报告 + diff 出 go/no-go）由 P3（#1404）实现，其输出是合并就绪闸的一个输入，不是合并动作本身。
- **#1256**：`human` 策略下两个机器入口照旧硬挡。`autonomous` 下 chief 只能「请求合并」，请求仍过合并就绪闸，不存在绕过闸的入口。
- **ADR 0007**：仓库级 auto-merge 与分支保护不变，继续服务 Claude Code 车道与人工合并。产品内的自治合并不依赖 auto-merge，直接调用 REST merge 并带 `sha`。
- **ADR 0014 D3**（review 关口永不跳过）：不变。`autonomous` 下 review 关口由自动审核与验证填充，而不是被跳过。

## Premortem（假设已失败，三种最可能死因 + 护栏）

| 死因 | 护栏 |
|---|---|
| agent 改测试或改闸，让自己过闸 | D4 保护路径与「删测试即 `human`」；棘轮基线以 PR base 为准 |
| 判定对的是旧代码，合并的是新代码 | D3 补丁摘要 + D2 的 `sha` 参数，平台层与产品层双重绑定 |
| 合并把运行中的实例砸坏，它再也修不了自己 | D6 回滚不依赖 pacman；迁移属 D4 留人 |

## 双向门

D1 的默认值 `human` 使本 ADR 对未开启的项目零影响。开启后回退 = 把项目策略改回 `human`，下一轮生效；已合并的提交按普通回滚处理。
