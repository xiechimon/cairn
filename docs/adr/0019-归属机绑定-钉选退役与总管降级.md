# ADR 0019 · 归属机绑定：钉选退役与总管降级

> 状态：**已裁决**（2026-10-12，#1259 + #1260 定案）。取代 ADR 0018 决策 4（协调模型：agent 不绑机 + 能力闸）与决策 0 中总管的特殊派发位；0018 其余决策（名册、票内流水线、拆票、并行闸）不动。施工票 #1259（worker 绑定 + UI 闭环）、#1260（总管降级）。

## Problem Statement

ADR 0018 决策 4 同日定稿「agent 不绑死机器 + 能力声明/能力闸」，方向复核时被用户推翻：「我还是想对齐 multica，就是不同的机器不同编排」「还是稳定一点好」「学到底」。推翻的依据是池化模型下三个结构性问题：

1. **模型不匹配洞**：能力闸只校验「机器装了哪个 runtime」，不校验「这台机器的 claude-code 实配了哪个模型」——agent 配模型 X，步被派到装了 claude-code 但没配 X 的机器，跑到模型解析才炸。闸要补到模型粒度，等于把「哪台机跑得动这个 agent」重新算一遍——那不如直接把它存成一个属性。
2. **钉选散点**：todo.machineId / build.pinnedMachineId / chiefThread.pinnedMachineId / schedule.machineId 四处钉选位各自为政，与能力闸叠加后「这条步到底去哪台机」没有单源答案，pending/失败文案也指不清原因。
3. **总管是特例**：chief 游离于 agent 名册外（亲和持锁、不占并发槽、无机器归属），跨机拓扑下「chief 在哪台机跑」没有答案； Multica 里 leader 就是 squad 名册里一个绑了 runtime 的普通 agent（squad.leader_id → agent → agent_runtime）。

## Decision

### 1 · 归属机单源

`agent.machineId` = 该 agent 的步投向的唯一答案（词表：归属机）。创建 agent 必选归属机；worker 步只被归属机领（claim 循环里 `agentRow.machineId !== machineId` 即跳过）；chief 步投 chief 的归属机。四处卡片钉选（todo.machineId / build.pinnedMachineId / chiefThread.pinnedMachineId / schedule.machineId）全部退役——「我要它在哪跑」从每张卡各自的散点收敛为 agent 的一个属性。

### 2 · 校验单源 homeMachineRejectReason

创建 / 换绑 / 整机迁移三入口共用 dispatch-eligibility.ts 里一条校验：目标机该 runtime 已开 +（claude-code 系）模型 ∈ 该机自报模型清单；pi 档免模型查（pi 是 server 侧配置，机器无关）。校验不过 = 创建 400 / 换绑 400 / 迁移留原机，文案指名缺什么。

### 3 · 存量迁移：直接回填 mea，无横幅

0036 迁移把存量 agent 全部回填到 mea 机（同团队内 name LIKE 'mea%' 的机器），0037 删四个钉选列。用户定：「不用置顶横幅，你直接先全部弄到 mea 中」——迁移提示横幅形态否决。

### 4 · 机器生命周期出口

- **删机保护**：有绑定 agent 的机器 DELETE → 409 点名占用清单。
- **整机迁移**（词表：整机迁移）：POST /api/machines/:id/evacuate 把绑定 agent 逐个过决策 2 的校验迁到目标机；过不了的留原机、响应列明各自原因——部分迁移是正常出口。
- **UI 闭环**：/app/resources/machines/:id 详情页（fact 条 + 归属本机的 agent 网格 + 预选归属机的创建槽 + 迁移/删除出口），网格复用 /app/team 的卡网格（用户定：「这个路由里面的内容正好可以复用：/app/team」）；machines 列表行机器名 = 详情页链接；agent 卡带归属机行。

### 5 · 总管降级为普通 agent（#1260）

chief 从派发层的特例降级为名册里一个绑了归属机的普通 agent：亲和持锁（chiefAffinityHeldByOther）、不占并发槽、线程钉选机位全部退役；chief 步与同机普通步同闸同队列。0018 决策 0 的名册语义（1 编排者 + 6 persona）不动——动的是机制面：chief 的机器归属从「无答案」变成「它的归属机（主力机）」。

## Premortem（假设本裁决错了，三个最可能的死因）

1. **归属机离线 = 该机全部 agent 停摆**——绑定把「机器挂 = 局部损失」放大成「该机名册全停」，chief 归属机挂则编排停摆 → 护栏（**2026-10-13 并入 #1257 挂起语义后的现行口径**，见下方「与 #1257 的撞车与收口」）：步挂起不判死，板面 waitingOn「等机器」chip 透出，机器回来自动续跑；换绑与整机迁移是一等公民操作（决策 4），chief 同样可换绑。
2. **换绑/迁移后目标机模型漂移**（卸模型、改配置）→ 步卡在归属机拿不到运行时，比池化时代更显眼 → 护栏（现行口径同上）：闸挡形挂起 + chip，机器模型清单走 30s 心跳自报（F3），校验看最新快照，装上即自动解锁。
3. **并发热点**：好机器被绑满、别的机器闲置——绑定放弃了池化的溢出弹性 → 这是刻意取舍（「还是稳定一点好」）；护栏：机器级 maxConcurrent 让步排队而非错派，step-queue 的 waitingFor 把「在等哪台机」摆上 UI，人看见热点后用整机迁移疏散。

## 与 ADR 0018 的关系

0018 决策 4 的机制面（requiredCapabilities 声明 + 能力闸 + 离线/缺能力 reason code 族）作废，未开工的 #1251 随之改向；能力上报中已施工的「模型清单自报」（F3）保留，降级为归属机校验的输入。决策 0 名册、决策 1 票内流水线、决策 2 拆票、决策 3 并行闸均不动。0018 与 0017 的正交关系（选源先于选派）在绑定模型下简化为：机器由归属机唯一确定，选源判定（githubRepo vs localPath，0017）在该机内部照常进行。
