# ADR 0021 · Autonomous merge: project-level policy + patch-binding verdict + protection paths

> Status: **Decided** (2026-10-20; the user confirmed in-session the recommended rulings D1–D7 of §3 of `docs/spec/28-bootstrap-closed-loop-self-authored-self-merged.md`; this ADR incorporates the product-related D1–D6 of them; D7 is a construction-process convention and stays in spec 28). Ticket #1401. Amends the applicability of ADR 0018's "merge action stays with humans" and of #1256: both remain in effect verbatim when `mergePolicy = human`. Construction tickets #1403 (P2), #1404 (P3), #1405 (P4), #1406 (P5), #1408 (P7). The wording of D2–D4 was changed during #1410's construction per the pr-gate review rounds' findings: D4 went from a file list to protection categories, then to default-deny, and gained a security-sensitive-surface category; D3's `patchSha` comes from pr-gate round three of #1420. Most changes are tightening; the one loosening is the `mergeable_state` condition of the merge-readiness gate (#1410's 1517363: `has_hooks` is treated as `clean`; `unstable` passes only when the only failing visible check is the gate's own status, otherwise the gate would wedge on its own status). This ADR was merged by the user with #1410; the text at merge time governs. A second loosening of D4 comes from ian's ruling on 2026-10-24 (#1621): Markdown under `docs/` enters the auto-mergeable set, and a pure-docs PR may merge without a human once all checks pass; other files under `docs/` (scripts, HTML, JSON in research material) stay outside the set, `docs/adr/**` and `docs/pr-review.md` still belong to protection category ①, and `docs/spec/**` is a design decision, explicitly listed in ① as well rather than relying on default-deny.

## Problem Statement

pacman's merge action is triggered only by humans. ADR 0018 wrote it into the roster ("the merge action stays with humans, not in the roster"), and #1256 hard-blocks it at both machine entries: calling chief `merge_builds` or MCP `merge_builds` returns `MERGE_HUMAN_ONLY_COPY`.

The user wants pacman to write PRs and merge them by itself on `xiechimon/pacman`, with the user's role becoming: look at what landed on main afterwards, spot-check, roll back, and promote corrections into gates. Reference form: poteto's 2026-09-21 talk and pstack's merge flow — the agent that wrote the code does not approve its own merge; an independent verifier judges against the exact patch; CI is green on the latest baseline; after the merge, a human samples and re-checks.

The problem splits into four sub-questions:

1. How is merge authority delegated without changing the external default (README: "Gated by design")?
2. Who performs the merge, and by what proof does "the verdict corresponds to exactly the code being merged" hold?
3. Which changes must keep a human in the loop regardless of verdicts?
4. How does automatic intake defend against issue injection in a public repo? And how does an instance update itself after merging?

## Decision

| ID | Decision |
|---|---|
| **D1** | Merge authority is delegated per project: `project.mergePolicy = human \| shadow \| autonomous`, **default `human`**. Under `human`, ADR 0018's "merge action stays with humans" and #1256's two hard-blocks remain in effect verbatim. `shadow` computes the merge-readiness gate and writes the result without merging. `autonomous` merges via the server when the merge-readiness gate is fully green. A team-level `autonomyPaused` emergency stop overrides every project policy |
| **D2** | On the autonomous path, the merge is executed by the **server**: it calls REST merge through `lib/github.ts` with the `sha` parameter; GitHub rejects if the head does not equal that value. The method is squash; the server composes the message: the title takes the PR title, and the last line of the body is fixed as `closes #<the issue number of sourceRef>`. Merge authority is not delegated to a `gh` login on agent machines. A human clicking merge inside pacman likewise merges via REST with the same message passed; when a human merges on the GitHub web UI or CLI, follow AGENTS.md's squash-taking rule |
| **D3** | Verdicts bind the **patch digest** `patchDigest`: over the file list of `compare/{base}...{headSha}` with `docs/verify/**` excluded, take each file's `[status, filename, previous_filename, blobSha, patchSha]` JSON tuple, sort, and sha256 (a rename binds both ends; a rename is excluded only when both ends are inside `docs/verify/`). `patchSha` is the sha256 of the `patch` text compare gives for that file, null when there is no patch (such files outside the evidence directory go to a human per D4): binding only the head blob is not enough — when the PR merges into main and conflict resolution keeps its own version, the head blob is unchanged while the patch silently changes from "A changes B" to "C changes back to B", quietly reverting main's change (pr-gate round three of #1420). The review, verify, and chief go/no-go verdicts each record `headSha` and `patchDigest`, computed live by the server per the `headSha` in the verdict. At merge time it is recomputed; a digest mismatch means the verdict is stale and auto re-verification follows. When the verifier commits only into the evidence directory, the digest is unchanged. When update-branch merges main in, as long as main's new commits do not touch the files this PR changes, the digest is unchanged and verdicts do not re-run; when they do touch them, the patch of those files relative to the merge base changes (conflict resolution keeping this PR's version still leaves the head blob unchanged while the patch text changes anyway), the digest changes accordingly and verdicts re-run (the conservative direction). Any push that changes code changes the digest |
| **D4** | Hitting a protection path forces `human`, regardless of policy and verdicts. The adjudication is **default-deny**: only paths in the "auto-mergeable set" — product source and tests (`apps/*/src/**`, `apps/*/test/**`, `apps/*/e2e/**`, `packages/*/src/**`, `packages/*/test/**`, `integration/test/**`), evidence (`docs/verify/**`), and Markdown under `docs/` (`docs/**/*.md`) — that do not fall into the following protection categories may skip the human; everything outside the set goes to a human. Enumerating "what must keep a human" by file name always misses (pr-gate rounds three, four, and five each found a new batch: scripts called by CI, nested biome configs and `.gitignore`, `AGENTS.override.md`, `.pi/skills`, nested `.claude/`), so instead we enumerate "what may skip the human". Protection categories ①②③ count at any directory level (`**/` includes the repo root); ④⑤ match from the repo root without `**/`. All matching is case-insensitive (macOS's default file system is not), and the folding applied depends on the direction: matches that widen protection (protection categories, the deleted-test adjudication) fold per Unicode (`ſ` and `K` count as `s` and `k` respectively), while matches that grant auto-merge (the auto-mergeable set and `docs/verify/**`) fold only ASCII case, so a path that looks like product source or evidence only under Unicode folding (e.g. `apps/web/ſrc/x.ts`) falls outside the set and goes to a human by default-deny. The protection categories are: ① files of CI, hooks, and the agent hosts on the left and right: `.github/**`, `**/.husky/**`, `**/.claude/**` (skills, settings, hooks, workflows), `**/.pi/**`, `**/.cursor/**`, `**/.mcp.json`, `**/.ckignore`, `**/CLAUDE*.md`, `**/AGENTS*.md` (including `AGENTS.override.md`, which pi reads in preference to `AGENTS.md`), `docs/pr-review.md`, `docs/adr/**`, `docs/spec/**` (design decisions); ② gate scripts and config that decides check criteria: `**/scripts/**`, `**/*.config.*` (vite / vitest / playwright / drizzle etc.), `**/biome.json`, `**/biome.jsonc`, `**/tsconfig*.json`, `**/.gitignore` (biome skips files by it), `**/.gitattributes` (attributes like `-diff` make numstat record text as binary with line count 0, and leave reviewers seeing only "Binary files differ"; pr-gate round six); ③ one-way doors: `**/drizzle/**` (migrations), `**/package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `**/.npmrc`; ④ the merge-readiness gate's own source, kept only in `apps/server/src/services/merge-gate/**`, `packages/shared/src/records/merge-gate.ts`, and `apps/daemon/src/merge-decision.ts` (the gate's new source must not be placed anywhere else, or this category cannot catch it by name); ⑤ security-sensitive surfaces and the DB startup file that runs migrations: the files listed in AGENTS.md's "when touching security-sensitive surfaces, also run `/security-review`" section (`apps/server/src/lib/{secret-box,keys,token-auth,attachments-token}.ts`, `apps/server/src/services/{secrets,credentials,api-keys,webhook-tokens,oauth}.ts`, `apps/server/src/routes-machine.ts`, `apps/server/src/services/machine*.ts`, `apps/daemon/src/{credentials,secret-channel,shell-channel,machine-client}.ts`, `apps/daemon/src/backend/command-gate.ts`, `apps/server/src/services/{mcp-face,mcp-servers}.ts`, `apps/server/src/routes-webhook.ts`), plus `apps/server/src/db/client.ts`, which runs migrations at startup and decides the migrations directory; this category follows that list in AGENTS.md, and both places change together. Additionally, all of the following force `human`: deleting a test file (directories and suffixes case-insensitive); files outside the evidence directory where compare gives no patch (binary, diff too large, pure rename: the product gate cannot distinguish these three, and they are the same batch as the `patchSha`-is-null ones in D3; pr-gate reads from local git and judges the binary files that numstat records as `- -`: no line counts, and reviewers see no diff either; a single NUL byte in the source makes git treat the whole file as binary, and empty-tree attributes cannot change that); patches over 800 lines (line counts follow empty-tree attributes; in-repo `.gitattributes` cannot change it) or 40 files (both counted over the whole patch including evidence inside `docs/verify/`; the product gate reads from compare, a rename counts as two files, line counts take compare's additions/deletions, a pure rename is 0; pr-gate uses `--no-renames`, recording renames as whole-file delete+add, stricter on line counts, and a pure rename still has a readable diff there); a truncated compare file list; and the daily autonomous-merge cap (default 10) being reached |
| **D5** | Automatic intake only picks up open issues that carry the `ready-for-agent` label, where that label was applied by a repo owner or collaborator (the events API verifies the labeler; if the labeler cannot be read, the issue is not picked up). Issue bodies are always treated as data and never enter the system layer |
| **D6** | Post-merge instance self-update runs as an independent deployment ring: pick the latest SHA on main with all required checks green → back up the database → drain in-flight steps → restart → health check → on failure roll back to the last known-good SHA. The rollback is performed by the deployment script and does not depend on pacman itself. npm publishing always keeps a human in the loop |

### Merge-readiness gate (the execution surface of D1–D4)

`mergeReadiness(build) → {ready, blockers[]}` is a pure function; its result is written as the commit status `pacman/merge-gate` on the head SHA, and displayed with the same source on the task detail page and in the chief tool `merge_readiness`. The blockers cover at least:

- the policy is `human`, or autonomy is paused;
- the PR is not open or is a draft; `mergeable_state` is not `clean` (`has_hooks` is treated as `clean`; `unstable` passes only when the only failing visible checks are the gate's own `pacman/merge-gate`, otherwise the gate would wedge on itself), or any non-required check is failing (GitHub computes `mergeable_state` asynchronously, and the check list the gate reads updates);
- the required checks are not all green on the current head; `pr-evidence` is not green;
- the verify verdict is missing, failing, or digest-stale;
- any review verdict contains blocking or is digest-stale; chief has not produced a go or is digest-stale;
- D4 is hit;
- the todo's `sourceRef` does not resolve to an issue number;
- the PR body's raw evidence links do not point at this branch's `docs/verify/<ticket>/`.

`pacman/merge-gate` is **not** added to branch protection's required checks: adding it would lock out both the Claude Code lanes and human merges.

## Relationship to existing rulings

- **ADR 0018**: "merge action stays with humans" is amended to "merge action belongs per project policy, defaulting to humans". The roster and "personas do not invoke other personas" are unchanged; the chief small-merge step (three reports + diff producing go/no-go) is implemented by P3 (#1404), and its output is one input of the merge-readiness gate, not the merge action itself.
- **#1256**: under the `human` policy, both machine entries keep their hard-blocks verbatim. Under `autonomous`, chief can only "request a merge"; the request still goes through the merge-readiness gate, and no entry that bypasses the gate exists.
- **ADR 0007**: repo-level auto-merge and branch protection are unchanged and keep serving the Claude Code lanes and human merges. The in-product autonomous merge does not depend on auto-merge; it calls REST merge directly with `sha`. The bootstrap construction session's own PR has separate premises (spec 28 D7 and §7.5): pr-gate produces a go on the current head before auto-merge is enabled, and that head is pinned; merges hitting D4 stay with the human.
- **ADR 0014 D3** (the review gate is never skipped): unchanged. Under `autonomous`, the review gate is filled by automatic review and verification, not skipped.

## Premortem (assuming it failed: the three most likely failure modes + guardrails)

| Failure mode | Guardrail |
|---|---|
| An agent changes the tests or the gate to pass itself | D4's protection paths and "deleting a test forces `human`"; the ratchet baseline is per PR base |
| The verdict is for old code while the merge is for new code | D3's patch digest + D2's `sha` parameter — double binding at the platform layer and the product layer |
| A merge breaks the running instance so it can never fix itself | D6's rollback does not depend on pacman; migrations belong to D4's human-kept set |

## Two-way gate

D1's default value `human` gives this ADR zero impact on projects that have not opted in. After opting in, rollback = change the project policy back to `human`, effective next round; already-merged commits are handled as ordinary rollbacks.
