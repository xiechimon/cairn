# ADR 0014 · chief dispatch verdict (plan first / fix directly): the authority rests with chief — decide, explain, overridable

> Status: **Decided** (2026-10-08; the user's ruling overturned the first round's core conclusion). Landing ticket: #903 rework round (PR #1016).
> Predecessor: this ticket's first round delivered the ADR "0013-chief-dispatch-mode-choice-belongs-to-humans-server-enforced" — it existed only on the PR branch, never merged to main, and was deleted with the rework, wholly succeeded by this file (the per-entry disposition of the old decisions is in "Disposition of the old decisions"; nothing is silently deleted). The 0013 number on main belongs to "chief-panel-form-floating-window" (#1047) and is unrelated to this ticket.
> Basis = `docs/research/892-gate-usage-measurement.md` (measured gate usage; fact numbering follows it).

## Problem Statement

The real problem is unchanged (#892 measured): on the main dispatch path the confirm gate is unilaterally revoked by the orchestrator — the `run_builds` tool defaults to `withPlan:false`, and the system-prompt working convention explicitly orders "withPlan:false means execute directly"; the two hardcodings reinforce each other, chief dispatched 8/8 with direct execution, and the user has neither an entry to express intent nor any way to learn why each dispatch went direct.

What the rework round fixes is **the problem definition**. The first-round ADR 0013 defined the disease as "chief has the power" and therefore confiscated the decision: a global setting slot `chief.dispatchWithPlan` + a server-side clamp (withPlan parameter removed from the tool surface). The user's 2026-10-08 ruling states: **the past problem was not "chief has the power", but that the power was hardcoded in two places — the tool default and the prompt — with no explanation to the user; what must be cured is opacity, not authority**. That sentence is the sole legitimate ground for this overturn.

The confiscation-style fix fails at two points: ① a global switch asks the user, outside any task context, to pre-judge whether all future tasks need a plan — while the party who can actually make that judgment is the chief looking at the task itself; ② the setting slot did not eliminate opacity — after the user sets "plan first", the chief still owes not one word of explanation for why each concrete ticket goes that mode. The form of transparency is **decide, explain, overridable**: the decision authority rests with chief (decide), every dispatch states its reason (explain), and the user can override with one local sentence (overridable).

## Decision

| ID | Decision | Reasoning |
|---|---|---|
| **D1** | **The decision authority rests with chief; the setting slot is deleted.** `withPlan` returns to the `run_builds` tool surface as chief's per-dispatch decision parameter; the `chief.dispatchWithPlan` setting slot exits wholesale — DB column, PATCH slot, envelope projection, settings UI row, fixture scenario, and i18n keys are all deleted cleanly, leaving no dumb controls. The only mechanical guarantee kept server-side = the default value when absent (D2); zero decision rules | See Problem Statement: cure opacity, not authority. The migration never merged to main (the first round's 0027 collided on numbering; the rework renumbered to 0029 and was deleted with the slot), so no existing-database burden |
| **D2** | **When unsure → plan first by default.** `run_builds`'s `withPlan` defaults to true (`bool(params,'withPlan',true)`); the prompt's decision section states the same in prose: "when unsure → plan first" and "the withPlan default is plan-first" | The fail-safe direction must be "ask one more time", not "silently skip the gate". **The original ADR 0013 D2's argument stands as-is**: ① the two hard gates are the product claim (spec 18); the default surface should not unilaterally revoke the confirm gate — the #892 8/8 disease was exactly "the default revokes the gate" (F1/F3); ② user data: 94% chose with-plan (F2). Only the carrier changes: column DEFAULT true → tool-parameter default true; the semantics are isomorphic and the surface is smaller |
| **D3** | **"Fix directly" skips only the confirm gate; the review gate is forever.** `withPlan=false` only decides the first step's kind (build, not plan); the review gate sits on the merge path and is unrelated to this parameter | The two hard gates are the product claim (`docs/spec/18-positioning-and-differentiation.md`); skipping review = nobody checks before release. Multica can dismantle gates because it never had any (F4); pacman dismantling them would dismantle its own selling point. Structurally the review gate never reads withPlan either — this is "cannot be skipped by this mechanism", not "agreed not to skip" |
| **D4** | **Decide + explain + overridable.** Decide: chief sets `withPlan` per dispatch. Explain: the decision reason is written into `run_builds`'s `dispatchReason` parameter (lands in the transcript/chief_message with the tool call, auditable, the F1 channel), and the prompt orders the acknowledgment to state "I decided fix-directly / plan-first, because X"; the response echoes `dispatchReason` for the LLM's self-check. Overridable: the user overrides with one local sentence, **affecting only that dispatch** (cancel_builds the running one, then re-dispatch in the opposite mode); it is not extrapolated into a standing preference. The acknowledgment carrier = chief's acknowledgment text in the conversation (a dispatch instance of the working-convention "acknowledgment" line); the structured-card surface (in-UI Q&A card, verdict and override slots on the card) belongs to #1049 — this ticket invents no UI of its own | A non-auditable decision = a different black box, i.e. no change. Explain (transcript record + acknowledgment prose) and overridable (one local sentence) are the entire difference between "chief decides" and "chief dictates"; "affects only this dispatch" prevents a single override from quietly becoming the new default — that would resurrect setting-slot semantics without the slot's audit surface |
| **D5** | **The criteria are written as charter prose, not as a rule table in code.** The system prompt's dispatch-decision section gives three **decidable signals** (not hard rules): a defect with reproducible steps or a failing test → fix directly; introducing a new capability, or changing across packages → ask first (until #1049's structured Q&A is in place, the carrier of "ask" = plan first — the plan doc is the question and the confirm gate is the blocking surface; the prompt's decision section states this carrier in the same sentence, no silent substitution); when unsure → plan first. From the factory there is only one **judgment discipline** (not a workflow), copied verbatim from multica's built-in Chief of Staff (Mika) instructions (F5): "ask only when the information would materially change the outcome, the execution approach, permissions, or safety; otherwise decide yourself, and say what you decided." The decision section is static text, not composed from any setting | A rule table would sooner or later become a second `withPlan:false` — any decision logic written into code hardens into unauditable behavior just like the original tool default (F3 is the precedent). "Defect or new capability" is itself a semantic judgment needing task context, and the LLM is exactly the judge; the server keeps only the fail-safe default (D2), zero rules. The original D4's requirement ("the prompt must match actual behavior") is inherited: the static decision section describes the real tool surface — the parameter is in the vocabulary, and the default semantics match the parameter description |
| **D6** | **The product provides only the mechanism, not the policy.** Writing the form of some skill (e.g. `grill-with-docs`) into chief's default behavior = welding the user's personal workflow into the product. **The trigger right belongs to the user**: that flow runs only when the user names it | The multica mirror (F4): building in no workflow at all is exactly its adaptation surface — behavior is decided by free text, with no code branches. pacman's mechanism counterparts are all in place: the charter (user-writable) + full skill visibility (F6) + the advisory routing section (F7). Any factory-shipped policy beyond the mechanism is overreach |

## Alternatives considered and rejection reasons

| Alternative | Rejection reason |
|---|---|
| Global setting slot (first-round plan, old D1/D3/D5) | See the old-D1 row of the disposition table: confiscation treats "authority", not "opacity"; a decision problem is misplaced as a configuration problem |
| Keep the setting slot as a "default preference" that chief can override per call | Dual-source decision = neither transparent nor auditable: the user thinks the semantics are locked while chief can still change them, and the change owes no explanation. Deletion is cleaner — the default semantics are carried by the tool-parameter default (D2), and the explanation obligation by D4 |
| A code rule table (decide withPlan by task attributes: defect tag → fix directly, cross-package diff → plan first) | A rule table would sooner or later become a second `withPlan:false` (D5's first sentence); and "defect / new capability / cross-package" is a semantic judgment that task attributes cannot be structured enough to support |
| Factory-default policy (e.g. "new features must grill the user first") | Welds a personal workflow into the product (D6); the multica counter-proof: it does not even build in plan mode (F4) |
| Wait for #1049 structured Q&A before returning the decision authority | Decide + explain + override runs over existing channels (tool parameters, transcript, conversation messages) and does not depend on blocking Q&A; it is not worth tying transparency to another ticket's schedule. Once #1049 lands, the "ask first" signal upgrades to a first-class form (see Dependencies) |

## Premortem (assuming it failed: the most likely failure modes + guardrails)

| Failure mode | Guardrail |
|---|---|
| chief's decision is abused: back to 8/8 direct execution, re-enacting #892 | dispatchReason lands in the transcript (F1 channel); #892's statistics script can be re-run at any time to audit decision quality; the acknowledgment reason is visible to the user, so abuse is exposed on the conversation surface at the first occurrence; the user's local override costs one sentence |
| chief's decision turns conservative: everything plans first, confirm dwell re-enacted for days (#892 §5 confirm dwell) | The fail-safe direction tolerates this bias by design (D2: asking once more > silently skipping the gate); the Mika discipline sentence states verbatim "otherwise decide yourself" — asking is the exception, not the default; gate wake notifications continue during dwell |
| dispatchReason becomes boilerplate ("for quality"), audit surface voided | A known limit of transparency mechanisms; the guardrail = the reason is echoed in a user-visible acknowledgment, and the cost of boilerplate being seen by a human is far lower than being buried in logs. No length/content validation — that would be another rule table (D5) |
| Override semantics drift: the user's one-sentence override is understood by chief as a standing preference | D4 states verbatim "affects only this dispatch, not extrapolated"; the prompt's decision section and the acknowledgment obligation share one source, and drift would surface directly in the acknowledgment text |
| The multi-machine skill-verification split (F10) taints the decision section's credibility | The decision section is self-sufficient (three signals + the discipline sentence) and does not depend on the skills tool; the split surface is registered as F10 awaiting a separate ticket |
