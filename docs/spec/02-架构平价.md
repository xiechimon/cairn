## 1. 进程模型与部署拓扑（A1）

### 1.1 三段组成

```
浏览器 (React SPA, 同源)  ──HTTP + SSE──┐
                                        ├─ pacman-server（编排 API + DB + git 托管 + cron + 通知）
executor daemon (独立进程) ──HTTP + SSE─┘   ↑ 经 serverUrl 连接（本机或异机，LAN/云皆可）
```

- **锁定**：三段形状与 todos.dev 同构（r3 §1/§8 实测其即此形状）；默认部署文档按"本机一把跑齐"教（server + daemon 同机），但**协议面不折叠**——daemon 永远经 HTTP URL 连 server，"机器"可注册局域网/云服务器上另一台，兑现 BYOC 形状与免费 BYOC 档的功能平价。
- **沿用 D1/D3**：编排 durable 语义（step 队列、会话持久化索引、重试记录）全部 server 自持；pi 引擎只活在 daemon 进程内（r3 §1.5 executor=pi 构建的同构事实）。
- **沿用 D5**：web 前端 = 普通 SPA，不假设与 server 同进程；macOS 桌面壳（Electron/Tauri 类）与 PWA 包同一前端，架构不需改动（#34 Notes 桌面兼容前提兑现）。

### 1.2 实时通道（**锁定**，r3 §8.1 实测"全 SSE 无 WebSocket"）

| 通道 | 端点 | 事件（观测） |
|---|---|---|
| 团队流（浏览器） | `GET /api/teams/{id}/stream` | `{"type":"ping","seq":n}` ~15s 心跳；`{"type":"machine_presence","machineId","online"}`；**r5 实测扩充**：`{"type":"todo"\|"build",seq,v,doc}` 全文档推送与 `{"type":"notification",…}`（r5 §7.2） |
| 会话流（浏览器） | `GET /api/conversations/{id}/stream` | transcript 实时流（r3 §3.5 抓包） |
| 机器 wake（daemon） | `GET /api/machine/stream` | 低延迟派发唤醒（r3 §1.5） |

看板非 presence 类更新：r3 窗口未见任务事件入流，原判 **[推断]** 走查询失效重取；**r5 §7.2 部分改判**——team stream 实测承载 `todo`/`build` 全文档事件（带 `seq`/`v` 版本）与 `notification` 事件，看板可据文档事件直更；是否并存失效重取未分离观测 **[推断保留]**。复刻采双保险：SSE 文档事件直更 + 重取兜底。

| 持有方 | 数据 |

## 2. 租户与简化边界（A2/A3）

1. **用户**：seed 单本地用户；启动即自动登录，`GET /api/auth/session`、`/api/user/me` 端点保形返回该用户。无注册、无邀请、无登录页复刻（#35 只盘公开页；登录后 workspace 才是平价对象）。
2. **团队**：`team` 表与全部 `teamId` 路径段形状保留，数据恒 seed 一行。多租户 SaaS 运维本就 Out of scope（地图）。
3. **成员**：团队页真人成员区只渲染自己一行 + Agent 计数（r3 §4 观察"成员计数把 Agent 计入"）。invite/join 流不实现。
4. **付费触点（锁定，Q15 裁决）**：r2 §7 全部 Pro 墙与升级弹窗**不复刻**——机器位数不限（r2 §7.1 `1/4` 门、r3 §1.2 限额弹窗均为对照物非复刻目标）、providers"新建"按钮恒在（r3 §2 门控观察为 todos.dev 行为，不采）、托管 repo 无墙、无 `升级到 Pro` 按钮。`plan` 字段保留于 team 记录形状但不参与任何门控。"槽位"概念（r1 §9.6 chief 对话不占槽的口径冲突）随付费面一并落空，不裁。
5. ~~`maxConcurrent 3`~~（r3 §1.5 机器日志、§4 机器页文案"并发上限 3"）不是付费件，但**并发上限概念已随 #503 整体摘除**——该上限无用户旋钮、daemon 串行执行又从未真正触顶，server 闸随之拆除；以后要做限流由机器自己那侧决定。

## 3. repo 托管双形态（A4）

| 形态 | 落地 | 平价出处 |
|---|---|---|
| 托管 repo | server 按团队/项目 init **本地 bare repo**；对 executor 呈现 `http-backend` 远端 URL，形状对应 r3 §1.4 `https://git.todos.dev/<teamId>/<repoName>`（域名段进命名常量表 → #44） | r3 §1.4 全链实测（clone/push/merge/main 读回 83 号验证） |
| GitHub 接入 | 连号授权 → 用户自有 repo：executor push `conv-*` 分支、建 PR、读 PR/issues/CI workflow runs；看板"分支与 PR"区出现 PR 卡 | r3 §3.9 [推断: PR 语义仅 GitHub-backed 项目]；r1 docs 六能力组（Read the repo）；r2 §7 GitHub 路径 free 可用 |

- **锁定**：git 服务端组件用 git 自带 `git http-backend`（CGI），不引第三方 git host。凭证纪律同 r3 §1.4：托管 repo 的 git 凭证**仅 per-step 注入**（r3 实测手动 fetch 无凭证失败），daemon 不落常驻。
- 文件浏览面（`/api/projects/{id}/tree?ref=`、`/file?path=&ref=`，r3 §8.2 实测）服务项目页 `Tasks | Files` 分段开关（r1 §461 changelog）：读裸库 ref 树与单文件，server 端实现，无检出要求。
- 项目创建流两分支（导入 GitHub / 托管新建）UI 按 r2 §9 D 组截图为靶。

## 4. 编排状态机与时序（A5–A8）

### 4.1 phase 九值权威（A5，**锁定**）

一 todo 恒恰处一个 phase（`[docs_concepts]`、`[docs_todos]` 两表一致，r1 §7.4）。内部名取 docs 序：

| 内部值 | 语义（docs 原文） | 看板列（6 列，r2 §4.1） | 证据 |
|---|---|---|---|
| `todo` | 已建档未开始 | 待开始 | API 实测（r3 §3.0） |
| `queued` | 已启动，等空闲机器 | 执行中 | docs 表；列位 = 参考站 changelog 2026-09-12「a queued todo sits on the step its build will run」（#1447 取代原 `待开始（折叠）` [推断]） |
| `planning` | 读仓库写计划 | 规划中 | docs 表（r3 "planning 未采到 [推断同族]"由此补实） |
| `confirm` | 计划就绪等你 | 待确认 | docs 表 + UI"确认方案"按钮实测（r3 §3.4） |
| `building` | 在改 | 执行中 | docs 表；r3 `exec` 猜测作废，正名 `building` |
| `review` | 改动就绪等你 | 待验收 | API 实测；`待验收≡审核` 同 phase（CONTEXT.md 裁决沿用） |
| `done` | 已接受，若选了则已合并 | 已完成（近 7 天） | API 实测 + changelog "Done (last 7 days)" |
| `failed` | run 停在错误上 | 钉执行中列顶 | docs 表 + changelog 原文（r1 §7.4） |
| `closed` | 未完成即搁置 | 不占列 **[推断]**（6 列无 closed 列；右键 Close 菜单项实测 r1 §443） |

字段其余形状照抄 r3 §3.0（`phaseAt/seqNum/orderIndex/tagIds/spec/assignment/agent/latestBuildId/lastRunAt/hasChanges/hasPlan/buildHistory/sourceTodo/v`）。

**列映射细粒度（r5 §8 观察加注）**：gate 态卡片的列位还看 `hasChanges`——confirm/review 且**无代码改动**的卡片留在 `执行中` 列（主按钮分别 `方案`/`回复`），**有改动**的 review 卡才进 `待验收`（主按钮 `完成`）。复刻看板按此双键（phase × hasChanges）渲染。

### 4.2 build 与 step 模型（A6，**锁定**：r3 §1.5/§3 实测语义 1:1 收录）

- **实体等式**：一次运行 = 一个 build = 一个 conversation = 一个 worktree + 一条 `conv-<conversationId>` 分支；`buildId ≡ conversationId`（r3 §3.0 实测）。Conversation/Plan/Transcript 为 facet 非实体（CONTEXT.md 沿用）。
- **step 队列 server 持有，机器 claim**：三类步 = 规划步、执行步、合并步（r3 §1.5 观测）；机器页文案 canon：「领取构建、规划与审核任务并运行 Agent。并发上限 3」（r3 §4）。
- **主时序**（全链 r3 §3 实测）：

```
创建 todo(POST /api/projects/{id}/todos {title,spec}) → phase=todo
点「开始」→ 开始任务 dialog（Agent 可空 / 「规划与执行分用不同 Agent」开关 / 先做规划 | 立即执行）
→ POST /api/projects/{id}/builds → server 入队规划步
→ 机器 tasks/claim → workspace 准备(准备工作区...) → 规划步(new session) → plan 卡(v1) → push 分支
→ phase=confirm →（人工）确认方案 → 执行步 → transcript 流(text_delta/toolcall/edit/bash 行) → push
→ phase=review →（人工）完成 → 确认弹层「将改动合并到默认分支」→ POST /api/builds/{id}/merge
→ 202 {delegated:true} → 机器领合并步(continue session 复用执行轮会话) → git merge --no-edit → 时间线「发起了合并」+ 结果行 + 🎉 → phase=done（停掉本 build 没人领的 verify / review 步）
```

- **收尾与人手动作（#1403）**：合并步成与下文 PR 对账走同一条 done 收尾（`finishTodoDone`），收尾时停掉本 build 没人领（排队中或等额度）的 verify / review 步，PR 对账打成 failed 时同样停掉。`POST /api/builds/{id}/merge` 与 AI 审核动作在 await（PR 探测、读变更）之后重读相位：卡在这期间已被收尾 → 409，不入队合并步 / 审核步。

- **GitHub 形态的 PR 对账（#1403，[设计]）**：done 的第二条路。卡停在 review、当前 build 带 PR 时，server 每分钟条件读一次 `pulls/{n}`（未连接 GitHub 时每个 PR 每 5 分钟一次，最久没读的先读；最近一小时里对账自己的匿名请求到 20 个、或对账与磨绿合计到 50 个时，对账停读，磨绿只计数、不受这两个上限拦）：PR 在 GitHub 上合并进默认分支、合并时的 head 包含本 build 最后的 checkpoint → 时间线「PR #n 已在 GitHub 合并」行 + 与合并步成同一条 done 收尾（同一条完成行）；合并进别的分支或漏了之后的提交 → 提示一行，卡留在 review；关闭未合并、紧接着的下一次读（隔一轮）仍关闭（为重跑 CI 关掉又重开 PR 不算；两次读之间有步在飞没读、或有一次读不到，就从下一次读重新数）→ 时间线关闭行 + `build.errorMessage` + `failed`。每个结局每一轮只报告一次（轮界 = 本 build 最近一个 build / plan 步，#931 返工复用同一 build 时从新一轮算起）：本轮已有完成行（合并步或对账写的）就不再按已合并收，已有对账的关闭行就不再按已关闭收；人在报告之后把卡拖回 review 是人的决定。不看时钟，CI 一绿就合并时卡在合并之后才进 review 照样收尾。收尾时停掉没人领（排队中或等额度）的 verify / review 步。写之前核对 PR 是本 build 的：PR 号是 daemon 按分支名查到的（`gh pr list --head` 只比分支名，公开仓里 fork 的同名分支 PR 也会被查到），head 仓与 base 仓是同一个仓（同一份响应里按仓库 id 比：仓库改名或转移后照样对得上，fork 对不上）、head 分支是本 build 的 `conv-<conversationId>` 分支才收尾或打回；对不上（含 fork 已删、head 仓为空）→ 每轮提示一行、卡留在 review；响应缺 head 分支或 base 仓 id → 按读不到。时间线行里引用的 GitHub 文本（分支名、合并者、合并提交）去掉控制字符、截到 100 个字符。

- **确认回路（r5 §4 实走改判）**：驳回 = `POST /api/builds/{id}/steps` body `{"action":"revision","side":"plan","feedback":<文本>,"clientMessageId":<uuid>}` → server 入队重规划步（同 conv `continue session`）→ plan 文档版本 v2；确认 = 同端点 `{"action":"confirm"}`。版本呈现 canon：文档头版本 chip `v1→v2` + 下拉（`vN · 相对时间` + 恢复图标）+ `与其他版本对比…`（二级：目标版本/`上一版本`）→ **plan.md 文件级 unified diff**（`1 个文件改动`/`+n −m`/hunk `@@ … @@`/双侧行号，即 `GET /api/documents/{id}/diff` 的 UI 触点）；时间线插用户驳回消息行 + agent 调整摘要行。plan 即文件（plan.md），版本 = 文件版本。
- **plan 交接物校验与 spec 兜底**（#113，**[设计]**——官方此边界行为未采；M6 实跑暴露：规划轮可跳过写 plan.md 直接交付，执行轮仅收到 confirm 关口措辞而拿不到任务内容）：① 规划步成功收尾但未产 plan.md → 不算成——留 `planning` + 自动入队补写步（指令 = 补写 plan.md 四段）；有界，仅首轮规划步触发，补写/驳回重规划等续轮指令步仍无产物 → 放行 `confirm`（关口决策交还人）。② 确认时 plan.md 仍缺席 → 执行步以 **new session** 派发（daemon 以 todo 原始 title+spec 开工），agent 必拿任务内容；plan.md 在 → 续轮 `continue session` 不变。
- **失败与重跑**（r3 §3.7 实测）：PR 在 GitHub 关闭未合并 → `failed`（#1403，见上文 PR 对账）；机器离线 → `failed` + canon 文案「运行该任务的机器已离线 / 请将其重新上线，或重新运行任务以改派其他机器。」+ 按钮 `重新运行`（新 conv/新分支/新 build，重开开始 dialog）与 `复用方案→直接执行`（跳过规划，时间线首行「复用了上一次运行的方案。」）。**步级失败无自动重跑**；自动重试仅 pi provider 流级（`auto_retry_start/end` 事件，r3 §1.5，pi 自带）。幂等停止（重跑时 agent 判定内容已在 main → 停 `review` 不重复改）为涌现行为，不硬编码。
- **failed→review 恢复（#702，[设计]**——#519 B-C17 实测豁口：build 步已真实交付（分支/PR 在）而审核步失败时，failed 相位把「本轮 step 失败」等同成「整个 build 失败」，merge 面的路（review→done）在 failed 不可达——UI「完成」钮消失、`POST /api/builds/{id}/merge` → 409，已交付产物在产品内无出路，合并被迫发生在产品外（维护者 gh CLI））：**条件边**——仅对「本 build 执行步 done 且产物在（执行步回传的 conv 分支 HEAD `checkpointCommit`，或 PR 记录 `prUrl`/`prNumber`，任一在场）」的 failed 任务合法。合法性数据依赖，静态边表不可表达：边表（`services/phase.ts`）只记「这条流转在相位机上合法」，**数据闸进服务端判定**（`builds.ts` restoreFailedReview = 唯一放行点；REST merge / steps action review / chief merge_builds 三生产者共用），手动 PATCH 改相面拒收（review 不在手动落点集，raw 改相无数据闸）。两出口：**合并已交付产物**（恢复回 review 关口 → 202 委派合并步 → done）或**只重跑审核**（恢复 → 审核步入队）。**审核步失败 ≠ 审核通过**：恢复落 review 等人工决策、`failed→done` 保持非法（完成经合并步落地，或经上文 GitHub 形态的 PR 对账从 review 落地）；恢复后的合并 = **人工接受未完成 AI 审核的交付物，合并责任在人**。`failed→queued` 重跑语义不动（r3 §3.7）。参考产品对该形态的流转未观测 [推断]——按「最小不孤儿」原则自裁，非照抄**）**。
- **恢复到此处**：每步行 hover 按钮（r3 §3.5 实测 UI），后端 = worktree checkpoint `git reset --hard + clean -fd`（r3 §1.4），语义细节 **[推断]**（未实走回退）。
- **[设计] 扩展方向（ADR 0018，施工 #1250）**：步种扩 `verify`（Verifier 跑 docs/verify/<票号>/ 证据包）、assignment 双槽扩四步种槽位、review 步 fan-out 三视角（meta header 承载不变，槽位管默认挂接）——详见 `docs/adr/0018-多agent团队三层与机器能力闸.md`。

### 5.5 worktree 契约（r3 §1.4 实测全套照抄）

|---|---|

### 5.6 事件与工具面（r3 §1.5）

- pi 流事件词表：`text_delta` / `thinking` / `thinking_delta` / `toolcall_end` / `message_update` / `message_end` / `message_stop` / `compaction` / `compaction_start` / `compaction_end` / `auto_retry_start` / `auto_retry_end` / `steer` / `done` / `error` / `wake` / `shutdown`；配置 kind：`api_key` / `oauth` / `http` / `stdio`。
- 流超时护栏：`streamFirstEvent 300000 / streamIdle 480000 / streamBodyTimeout 540000` ms（r3 bundle 原文）。**重置语义（#699，pacman 侧 [设计]）**：参考产品的 body 超时语义（per-step 还是 per-call）未观测 [推断]，不照抄——按在树参考实现 pi 自身 watchdog 的 first/idle「事件重置」语义对齐：三臂全部**事件到达即重置**（#654 先把 body 粒度从「步」推进到「轮」，#699 推进到「事件」），活跃长步不死于固定 540s 墙；真死流（事件流静默，如挂死的工具执行）由 idle 臂收；步级**绝对上界** = `PACMAN_STREAM_DURATION_CAP_MS`（缺省 3600000，不随事件重置——兜住完全无上界的日志/费用失控步）；超时收尾文案指名触发臂与数值（`arm=<first|idle|body|duration>`），`build.errorMessage` 携带。

## 9. 支撑机制（A12）

### 9.1 通知

- **todos.dev 实测投递架构（r5 §7 改判）**：**Web Push 真存在**——页 bundle 内嵌 VAPID 公钥，`registerForPush()` = permission granted → `pushManager.subscribe({userVisibleOnly, applicationServerKey})` → `POST /api/push` 上传订阅；SW（`sw.js`）消费声明式载荷 `{web_push:8030, notification:{title,body,navigate,tag}}`（Safari 18.4+ 原生；Chrome/Firefox 走 `push` handler 回退），**前台抑制 = 存在 visible+focused 的 app 窗口**；`notificationclick` 经 CacheStorage `/__pending-nav` + postMessage 深度链接。**页层零 `new Notification(`/`showNotification(` 调用**（bundle 静态证实）——页内体验 = SSE team stream `{"type":"notification",…}` 事件 → toast/未读徽标/侧栏红点。引导条文案 canon「标签页切换到后台时，通过桌面通知提醒你」对应 push+前台抑制语义。桌面壳（`isDesktopShell()`）另走原生路径。
