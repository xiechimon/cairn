## 问题

**用户诉求（#861 原话，2026-10-05）**：「我还想加一个编排功能：一台机器只有一个 agent，用来编排所有的 agent。如果我使用这台机器，也是一样的。在这台机器上弄一个 A，然后它编排下面所有的 Agent。」配套诉求：「我这个电脑关掉了，它还可以继续，对面机器还可以继续跑。」

R14 已把这个诉求翻译成 pacman 语义：**复用 chief，落实为机器亲和**——不新增 per-machine 编排者，而是让 chief 回合钉在一台主力机上。#687 接好了显式钉选的全部管路；缺的是**没有显式钉选时的默认策略**。现状四个缺口（码位以 main = `b16e6e2c` 为准）：

1. **未钉的 chief 线程没有任何策略。** 抽屉新主题（`POST /api/teams/:id/chief/threads`，`apps/server/src/routes.ts:828`）不带机器语义，`sendChiefMessage` 落 `pinnedMachineId: body.pinnedMachineId ?? null`（`apps/server/src/services/chief.ts:360`）；claim 侧 `or(isNull(chiefThread.pinnedMachineId), …)`（`apps/server/src/services/machines.ts:656`）——未钉 = 任何在线机器 FIFO 抢。chief 会话文件（pi sessionDir）是执行机本地资产（machine-execution-plane §4-7），**每次换机认领 = 一次会话降级**（T1 的 `RESUME_FRESH_SESSION_NOTE` 会显式标记，但对话上下文实际丢了）。多机部署下「自动」的真实语义是「每轮可能换机」，正确性缺口与 worker 步完全同源——而 worker 面已由 T2 会话亲和闸修掉（`machines.ts:921-930`），chief 面没有对应物。**同一正确性问题，两个步族一个修了一个没修。**
2. **「主力机」没有单源。** pin 的数据层（`build.pinnedMachineId` / `todo.machineId` / `chief_thread.pinnedMachineId`）、claim 过滤、服务参数全部在位，但「缺省时钉哪台」没有答案：没有用户设置面，没有回退规则。调度器以外唯一写线程 pin 的路径是 orchestrate 入口对 `todo.machineId` 的透传（`routes.ts:621`）。
3. **machines 页零编排信息。** 机器行只有 online 点、shell 闸、runtime 品牌 mark（`apps/web/src/resources/machines-page.tsx:110-169`）。哪台机器承载总管、总管回合是否正在某机执行、是否有回合在等某台机器上线、谁是默认主力——一概不可见。用户「关电脑前确认编排已落在常开机器上」没有观测面。
4. **存量线程的迁移语义未定。** `chief.ts:355-359` 注释钉死「既有线程不回写：会话在哪台机器续跑由线程创建时刻决定，中途换机丢上下文」。主力机概念落地后，「换主力机时存量线程跟不跟」必须有明确答案，否则首日就产生不可解释的行为。

## 三问速答

- **哪台是主力机？** 用户在 chief 设置里钉的那台（`chief.machineId`，本 spec 新增）。没钉就没有主力机——只有会话亲和（见 A4）兜住正确性。
- **谁来定？** 用户。系统不猜：猜错一台主力机的代价是**每个总管回合 10 分钟超时失败**（T3 闸），而钉选语义的既定裁决是「约束由人设定、由人解除」（T3 结论原文：The user lifts the constraint; the system never does）。设定入口一次、成本一击（见 A6），系统替用户拍板没有任何对称收益。
- **machines 页编排状态怎么表达？** 三态读标注：「总管主机」徽标（谁是默认）、「总管回合进行中」（该机正在执行 chief 步）、「总管等待机器」（被钉的 pending chief 步存在且该机当前不可执行）。数据走 GET /chief 封套新 `orchestration` 块（见 A5）。
- **与 `chief_thread.pinnedMachineId` 的关系？** pin 的缺省来源链变长：`todo.machineId`（orchestrate 入口，现状）→ `chief.machineId`（新）→ null。既有线程不回写（现状语义保持）；未钉线程补上 T2 同款会话亲和闸，把「自动」从「每轮可能换机」修成「粘住会话机、机器消失才换」。

### 机制总图

```text
sendChiefMessage 建线程（chief.ts）
  thread.pinnedMachineId = body.pinnedMachineId（orchestrate 的 todo 钉选，现状）
                        ?? chiefRow.machineId（主力机，新）
                        ?? null
  既有线程：不回写（现状语义保持，chief.ts:355-359 注释不动）

tryClaim 的 chief 候选循环（machines.ts，A4）
  thread 钉了机器（pinnedMachineId 非空）
    → SQL 过滤：唯钉选机可见（现状，不动；亲和不参与——T2 同律）
  thread 未钉 + 会话已开（thread.sessionId !== ''）
    → 会话亲和闸（新，与 worker T2 同型）：
        会话机（该线程链尾 session 步的 machineId，查询与 T2 的
          prior 查询同源，machines.ts:891-894 同型）在线且 runtime 闸开
          → 本机跳过该候选，步留 pending 等会话机领
        会话机离线 / 机器行被删 / runtime 闸关 / machineId 空
          → 本机领；换机 = daemon SessionNotResumable 回退新会话 +
            RESUME_FRESH_SESSION_NOTE（T1 显式降级，#862 契约不预判）
  thread 未钉 + 会话未开（首轮）
    → 现状 FIFO（先到先得；单机部署 = 唯一机器，与钉选无差异）

GET /chief 封套（A5，orchestration 块）
  defaultMachineId = chief.machineId
  activity[] = per 机 { machineId, running, waiting }
    running  = 该机上 status='claimed' 的 chief 步数（回合进行中）
    waiting  = 被钉到该机且 status='pending' 的 chief 步数 × 该机当前
               不可执行（离线或 runtime 闸关）——T3 已知缝隙（在线但
               闸关 = 无界等待）借此获得可见性

machines 页（A8，全部读态）
  「总管主机」徽标      → defaultMachineId 命中行
  「总管回合进行中」    → activity[].running > 0 行
  「总管等待机器」      → activity[].waiting > 0 行
```

亲和闸三处细节与 T2 保持同律：钉选线程不亲和（钉选 SQL 过滤下唯一可见者不能再被挡死；钉选 = 用户显式选择，盖过软偏好）；跳过只作用于当前候选，不挡同机领其它线程的步（每机可见性语义，无队头阻塞）；亲和判定的 runtime 闸用 chief 绑定 Agent 的 provider（与 `buildChiefClaim` 内闸同源，`machines.ts:777`）。

### 与 T3 的关系（等待上界不恶化）

亲和在会话机**消失时即刻放行**（离线/被删/闸关任一成立），不等宽限——所以未钉线程不会因亲和产生新的无界等待。T3 的 10 分钟宽限 + 显式失败只作用于**钉选**路径（`chief.ts:847-858`），而主力机缺省链恰好把「显式钉选」的语义原样继承：设了主力机 = 每个新线程都钉它 = 主力机离线时回合在 10 分钟宽限后失败并点名机器（`dispatch-timeouts.ts:41`）。这条失败路径从「只有 todo 钉选才可达」变成「设了主力机即默认可达」，因此 A7 同时把 `CHIEF_PIN_OFFLINE_HINT`（`dispatch-timeouts.ts:49`）的出口文案从「把任务的机器改为其它在线机器」扩成「改 chief 设置的主力机，或清回自动」——失败信息必须指向真实存在的出口（T6 律：报机器 + 报修法）。

## 被否掉的替代方案

| 方案 | 为何否 |
|---|---|
| **N1 另起 per-machine 编排者 A** | R14 已否：与 chief 职责重叠、状态双轨（drift 失败类）。用户要的「一机一编排者」由机器亲和承接，不新增编排实体。 |
| **N2 系统猜主力机（缺省预填 `kind='local'` 行，或首台自选）** | 四条独立理由：① 替用户拍板了钉选——与「约束由人设定」的既定裁决正面冲突；② 猜错失败面 = 每个回合 10 分钟超时（T3），不是降级是停摆；③ server 宿主机无 daemon 的部署形态（server 在 VPS、daemon 在各笔记本）下 local 行永远离线，chief 直接全灭；④ 「local 在线才钉」的条件缺省 = 同一线程不同时刻创建拿到不同语义，破坏确定性。用户自用拓扑里 mea 恰为 server 宿主——**设一次即完全等价**，预填收益只有省一次点击，代价是替所有部署猜一次。 |
| **N3 主力机跟随用户所在机器** | web 客户端对 server 不携带机器身份（浏览器 → server，无主机概念）；用户 ≠ 机器（手机开面板时无主机可指）。无可靠信号，否。 |
| **N4 亲和回写 pin（把会话机写进 `thread.pinnedMachineId` 定型）** | 与 T2 的 claim 期软语义分叉（worker 无回写）；回写后机器消失走 T3 硬失败而不是放行换机——亲和的正确性收益被砍半；且 pin 的写入方混入第三来源（claim 循环），「这个 pin 谁写的」排障面变糊。 |
| **N5 默认把 worker 步也钉到主力机（「chief 回合与 worker 步钉同一台」的字面解）** | 集中全部工作到一台 = 多机利用率归零，与派发骨架（未钉 = FIFO + T2 亲和）的设计相悖；worker 的关机续跑不依赖钉选——T1 释放闭环已建（claim 持有者失联 → 步回 pending → 他机续跑）。chief 要集中工作时走**章程**（常设指示，r5 §2）与 `run_builds` machineId（既有参数），那是语义正确的通道。 |
| **N6 machines 页行内「设为主力机」动作** | machines 页行内活控件纪律（XMON-113 起唯一 = shell 闸，`machines-page.tsx:12-15` 注释）；主力机是 chief 的执行配置，决策面住 chief 设置与绑定 Agent / 模型 / 思考强度同层。徽标是读态，不破纪律。 |
| **N7 换主力机时存量线程重钉到新机** | 中途换机丢 chief 会话上下文（creation-time 语义，`chief.ts:355-359`）；未钉存量线程已由 A4 亲和粘在当前会话机，重钉是纯损失。留重开条件（见下）。 |
| **N8 orchestration 聚合走 machines 列表响应（machine record 加字段）** | machine record 是 shared schema + 快照钉面，且 per 机 chief 状态是 chief 域数据；住 GET /chief 封套（chief 域自己的响应）语义归属正确、schema 面最小，machines 页客户端 join。 |
| **N9 chief 步跨机释放（T1 对称扩展到 chief）** | chief 回合副作用非幂等：回合中途已落的 `create_todo` / `run_builds` 派工没有事务回滚面，释放重跑 = 重复派工风险。worker 的释放闭环吃的是 git checkpoint 回退（rewind 到步起点），chief 无对应物。在飞回合死亡维持「显式失败 + 重发」（`failAbandonedChiefSteps` claimed 分支），主力机钉选本来就把这条路径的触发概率压到「机器死」本身。 |

## 已知边界与重开条件

- **换主力机后存量线程不跟**（N7 的代价面）：未钉存量线程由亲和粘在当前会话机。重开条件：用户明确提出「把总管挪到 X」——届时做线程级 pin 编辑（PATCH thread machine + UI），不做批量迁移。
- **多用户团队**：`chief.machineId` per 用户（chief 记录粒度），machines 页徽标对每个请求者显示自己的主力机。自托管单用户是运行现实；多用户徽标语义显形再议。
- **亲和楔住**（会话机在线但迟迟不领）：与 T2 同型已知边界，无超时——记录在案，不新增机制。
- **在飞 chief 回合随主力机死亡**：维持显式失败 + 重发（N9 理由）；重开条件 = 主力机频繁重启的真实痛点出现时，再做「释放重跑 + 派工去重」的完整设计。
