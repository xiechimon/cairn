# 17 · 双运行时执行面（claude-code 第二引擎）

> 范围：daemon 执行面引入 claude-code 第二运行时——`agent.provider='claude-code'` 的步从「claim 后第一步必炸」变为真实可执行。回答三问：Multica 怎么做双运行时（机制核验稿）；pacman 缺什么（逐项清单）；claim/dispatch/reclaim 能否共享（能，分叉点唯一）。本票只出设计 + 执行票草稿，**不改产品代码**（仓规：先调研真实实现再造机制）。
>
> 参照：r10（Multica runtime 调研，docs/research/r10-multica-runtime.md）、r11（pacman↔Multica 差距清单 G1-G25，docs/research/r11-runtime-gap.md）、r13（r10 的 fresh-clone 核验稿，HEAD `2ea01ae`，2026-10-02，docs/research/r13-multica-runtime-verify.md，行号以该 clone 为准）、Agent SDK 文档研究稿（code.claude.com/docs/en/agent-sdk/*，2026-10-02 抓取）。

## Problem Statement

1. **claude-code 模型可选中、执行必死。** 5 跳故障链（各跳均有现行码位）：
   - web 两级选择器（PR #617，分支态）把 model-sources 的 claude-code 段投喂进 picker，用户可选 `claude-code/<model>`（`apps/web/src/api/mappers.ts:812` RUNTIME_LABELS 已含 claude-code）；
   - agent 落库 `provider='claude-code'`，无 custom provider 行；
   - server `stepToken` 的 `toProviderConfig` 回退：`return agentProviderId ? { kind: 'api_key', providerId: agentProviderId } : null`（`apps/server/src/services/machines.ts:1405`）——凭空造一个 `api_key` 形的 provider 配置；
   - runner 同样回退：`creds.provider ?? (agent?.provider ? { kind: 'api_key', providerId: agent.provider } : null)`（`apps/daemon/src/runner.ts:261-262`）；
   - daemon 唯一后端是 PiBackend：`runtime.getModel('claude-code', modelId)` 抛 `model claude-code/<x> not found`（`apps/daemon/src/backend/pi.ts:562-564`），步失败。
   即「claude-code」在 pacman 里只有词汇面（MODEL_SOURCE_RUNTIMES、MACHINE_RUNTIMES、RUNTIME_LABELS、providers 页 tab），没有执行面。
2. **缝早已为此预留。** `AgentBackend` 缝就是给第二引擎的（spec 00/D1：缝保持 engine-agnostic；「Claude Agent SDK 只能作第二引擎补位，不能作唯一引擎」——`docs/spec/00-地基决议.md:27`）；`MachineLoopOpts.backend?: AgentBackend` 本就是注入面（`apps/daemon/src/machine-loop.ts:41`）。缺的是第二个实现和按步选后端的解析点。
3. **机器面词汇是装饰。** `machine.enabledRuntimes` 已入库可写（spec 11 A9），但 claim/执行链从不消费（r11 G7）——「本机可跑 claude-code」既不真也不假，是无人读取的位。
4. **模型来源方向已歪。** providers 页 claude-code 段 = server 进程 fs 直读 `~/.claude/settings.json`（`apps/server/src/services/providers.ts:131-161`）——控制面与执行面分离后读的是 server 宿主的配置，不是执行机器的（r11 G22）。

## 上游机制：Multica 两层模型（核验稿摘要）

以下全部经 fresh clone 核验（HEAD `2ea01ae`，核验稿 = r13）；与 r10 的两处出入已修正（BuiltinRuntime 12 字段非 9；不消费 `opts.McpConfig` 的家族是 6 个非 4 个）。

**身份层（identity）= 注册表描述符。** 运行时身份是 daemon 注册的 provider key，**不是**协议家族（不出现在 `SupportedTypes` 与 `protocol_family` CHECK 约束里）。`BuiltinRuntime` 描述符 12 字段（`builtin_runtimes.go:18-70`）：ID（身份键）、ProtocolFamily（派发目标）、DefaultCommand（PATH 探测）、EnvPrefix（`MULTICA_<ID>_*` 覆盖）、DisplayName、SkillsDir/UserSkillsDir、LaunchHeader、DefaultExecutable/ProviderLabel（家族后端的身份覆写）、ModelDiscovery（替换整族发现的策略函数）。注册表现只有一条：`omp`（family=pi）。结构论点在 struct doc 里说尽：「Adding a new compatible fork of an existing runtime is a descriptor entry, not a cross-stack change」。

**家族层（family）= 执行后端。** 25 个协议家族（`agent.go:364-390`），每个家族后端实现**同一个单方法接口**：

```go
type Backend interface {
    Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
```

（`agent.go:17-23`）。差异全在各 `*Backend` 私有实现里；丰富能力面（Supplement、ToolActivity、InterruptBackgroundTools 等）经返回的 `Session` 结构可选暴露（nil = 不提供）。`New(agentType, cfg)` 是纯家族 switch（`agent.go:432-498`）。

**解析入口唯一。** `ResolveBackend(provider, cfg)`（`builtin_runtimes.go:147-158`）：身份键 → `NewRuntime`（建家族后端 + 应用描述符覆写，家族后端不支持身份承载时**fail-closed** 报错，`builtin_runtimes.go:160-186`）；否则 → `New`。daemon 永不直呼 New/NewRuntime。后端实例**每任务一建**：`runTask` 内 resolve 一次、局部变量用完即弃（`daemon.go:8588-8599`），无进程级缓存。

**claude 家族协议**（`claude.go`）：`claude -p --output-format stream-json --input-format stream-json --verbose --permission-mode bypassPermissions --disallowedTools AskUserQuestion` + 条件 `--model`/`--effort`/`--resume`/`--max-turns`（`claude.go:1078-1136`）；prompt 以单条 stream-json `user` 帧写 stdin 且**保持打开**（中途 `control_request`/`control_response` 走同一管道）；stdout 逐行解析；`session_id` 从 system/result 帧刮出回传；transcript 留在 CLI 自己的 `~/.claude/projects/<slug>/<id>.jsonl`（`claude.go:936-972`）。模型发现无 CLI flag——专门起一个 discovery-only 会话发 `list_models` control_request，20s 超时，失败落静态目录（`claude_models.go:215-240,274-295`）。systemPrompt **不走** `--append-system-prompt`，而是把 per-task CLAUDE.md 写进 workdir（`claude.go:1112-1115`）。

**pi 家族协议**（`pi.go`）：`pi -p --mode json --session <path> --model <selector> --thinking <level>`，prompt 写 stdin 后 EOF；事件流 = stdout JSONL。会话 ID = 本地会话文件路径本身（`pi.go:376-386`）。发现两段式：`--mode rpc` JSON-RPC 优先，`--list-models` 表格兜底。

**claim/dispatch/reclaim 全族共享。** claim = WS-RPC `tasks.claim`，**只按 runtime ids 键**（`daemon.go:5457`）；heartbeat 每 runtime id 一个 goroutine（`daemon.go:4435-4476`）；reclaim（RecoverOrphans）per runtime id；dispatch（handleTask）到 runtimeIndex 查表为止 provider-盲（`daemon.go:5721-5745`）。**家族分叉全部发生在 claim 之后**：runTask 里的 execenv/skills 注入、MCP 合并、`ResolveBackend`，以及 backend 包内部。skills 与 MCP 都在**后端解析之前**进管道（execenv Prepare/Reuse + `skillsDirPath` 按身份写进各家原生目录，`execenv/context.go:328+`）。

**凭据本地自持。** daemon 从不读取/上传各 CLI 的登录 token——claude 的订阅登录、pi 的自有配置都留在各机器本地（r10 §8.2）。daemon 侧无凭据面。

## Solution

| ID | 决策 | 落地形态 |
|---|---|---|
| **A1** | 采 Multica 的**分形**，不采其**机构** | 分形 = 「身份（词汇/记录层）与家族（执行后端）分离 + 分叉唯一化 + 凭据本地」。机构 = 12 字段描述符注册表、26 CLI 探测矩阵、EnvPrefix/LaunchHeader 机器——pacman 只有 2 个 runtime、pi 是库内消费非 CLI spawn，这些机构没有对应问题要解。身份层在 pacman = 既有词汇常量 + model-source 记录（MODEL_SOURCE_RUNTIMES / MACHINE_RUNTIMES / agent.provider 值），零新注册表 |
| **A2** | claude-code 后端桥形 = `@anthropic-ai/claude-agent-sdk` | 新增 `apps/daemon/src/backend/claude-code.ts`，biome noRestrictedImports 增条目锁缝（与 `@earendil-works/*` → `backend/pi.ts` 同律）。理由见下「取舍清单」 |
| **A3** | per-step 后端解析，唯一分叉点 | `MachineLoopOpts.backend`（现为单后端注入面）扩为注册/解析：`agent.provider` 命中 runtime 身份词表 → 对应后端，**其余（custom provider id / null）恒走 pi**——默认支不变即零回归。对齐 Multica「分叉只在 runTask 内、claim 全族共享」的拓扑 |
| **A4** | claude-code 凭据语义 = 机器本地、零 provider | server `toProviderConfig` 对 runtime 身份返回 null（堵 `machines.ts:1405` 回退）；runner 对 runtime 身份步不因 provider null failStep（堵 `runner.ts:261-266` 回退+拦截）；daemon 永不读/传 claude 登录态（认证 = 机器上既有 claude 登录或 ANTHROPIC_API_KEY，Multica §8.2 同律）。pi 的 per-step 密钥通道不动 |

| **A9** | ~~skills 注入 = catalog 追加 systemPrompt（与 pi 同律）~~ **superseded by spec 24** | 原文保留：复用 buildSkillsCatalog → append 通道，SDK systemPrompt append 形承载。**不采** Multica 的 workdir CLAUDE.md 写入法（会污染 worktree git status，pacman worktree 纪律不容）。原生 `.claude/skills` 发现归后续票。<br>**推翻依据见 `docs/spec/24-运行简报落-worktree-文件.md`**：本行两条前提均已失效——两个后端**本来就原生读** worktree 的上下文文件（含用户仓库自带的 CLAUDE.md），而 git 洁净在 pacman 的镜像 clone 布局下有解（Multica 那套 exclude 之所以不可用，是因为它的 common dir 是用户仓库）。改动落 `#958` |

| **A13** | 权限面 = bypassPermissions + readOnly 映射 | daemon 非交互语义 + worktree 隔离已由宿主 git 护栏承担（Multica 硬钉同对齐，`claude.go:1079-1092`）。readOnly（审核步）→ SDK `disallowedTools` 收 Edit/Write；thinkingLevel → SDK `effort`（域内透传，`off`/`minimal` 缺省不发）。域外值 fail-closed 不猜 |

### 对 Multica 的取舍清单

**采（有理由）：**

| 机制 | Multica 证据 | pacman 落点 | 为何采 |
|---|---|---|---|
| 身份/家族分离的分形 | builtin_runtimes.go:8-17 struct doc | 词汇常量 + AgentBackend 实现 | 分叉唯一化是可维护性的核心——「加一个 runtime 是描述符/实现条目，不是全栈改动」的论点直接成立 |
| claim/heartbeat/reclaim 全族共享，分叉只在执行入口 | daemon.go:5457/4435/5721/8588 | machine-loop/runner 机制零改动，分叉 = backendFor | pacman 机器机制（journal/recover/steer/stop/presence）全部工作在 SessionOpts/handle 之上，本就 runtime 无关——验证了这个共享不是巧合是结构 |
| 凭据本地自持 | r10 §8.2 | A4 零 provider | 与 pacman「密钥 per-step 内存态、永不落盘」哲学同向，且免掉跨机传 token 的整类问题 |
| 会话指针走 server 侧记录 | daemon.go:5940/:6265 + types.go:297 | 既有 step.sessionId 通道 | pacman 已有同构通道（sessionRefSchema），零新契约 |
| model verbatim 透传 | claude.go:1099-1101 | SDK `model` 直传 | 不引入模型翻译层，发现/解析归 CLI |

**不采（有理由）：**

| 机制 | 为何不采 |
|---|---|
| 12 字段 BuiltinRuntime 注册表 | pacman 的身份层数据已散落在既有单源（MODEL_SOURCE_RUNTIMES/MACHINE_RUNTIMES/model-source 记录）；再立注册表 = 第二个词表单源，违仓内单源纪律。等 runtime ≥3 或出现「同族多身份」（omp 形态）再评估 |
| raw CLI spawn 协议适配 | Multica 25 家族引擎无关，每家族一个 argv/stream 适配器优于每引擎一个 SDK 依赖——那是它的正确解。pacman 仅 2 runtime 且 pi 已是**库内消费**（AgentBackend 缝的存在理由），SDK 是 pi 消费方式的同构延展；且 SDK 是 CLI 的严格超集（研究稿能力表 a-k 全覆盖 + 类型化事件 + in-process 工具回调），版本钉进 lockfile（spec 01 D6 同律）而非依赖机器上的 CLI 版本 |
| ~~workdir 写 CLAUDE.md 的 systemPrompt 通道~~ **已由 spec 24 翻回「采」** | 原文理由：污染任务 worktree 的 git status；pi 后端用 systemPromptOverride 已验证该通道成立，SDK append 形同构。**该理由的前提是「无解」——spec 24 给出了解**（标记块 + 提交前擦除 + 按内容而非按文件名的提交闸），且换过去能拿到 CLI 原生记忆机制与逐字节稳定的缓存前缀（后者恰恰是留在 systemPrompt 里做不到的：它每轮重算） |
| EnvPrefix/LaunchHeader/探测矩阵 | 无 26 CLI 的管理问题；probe 换成 daemon 启动时一条 SDK 探活（T3 的模型源上报顺带） |
| `mat_` task token / 重连宽限 / GC | pacman 有自己的 per-step token/journal/recover（r11 列为 pacman 自有增量，spec 02/08 锁定） |

**SDK 形态的边界条件（明示）：** ① SDK 自带平台二进制（optional deps，`npm ci --omit=optional` 会缺——CI/install 面注意）；② ToS 边界——Anthropic 不允许第三方转售 claude.ai 登录/限额，pacman 是自用单用户自托管（定位裁决「自用第一」），不触此界，但若未来走向多租户需重估；③ 闭源依赖面扩大一处（spec 00 §S3.2 当时否的是「唯一引擎」，第二引擎补位正是 D1 预留位）。

## User Stories

1. 作为用户，我在模型选择器选 Claude Code 的模型（如 opus 槽），任务步真实执行并产出 transcript、token 计数与会话 ID——不再第一步炸 `model claude-code/<x> not found`。
2. 作为用户，我的 claude 认证（机器上的登录或 API key）留在机器本地；pacman 的 server/daemon 都不读、不传、不存它。
3. 作为用户，同一台机器上 pi agent 与 claude-code agent 的任务混跑：claim、心跳、恢复、steer/stop 的机器行为完全一致，差别只在谁执行。
4. 作为用户，续轮任务接续上一会话（claude resume），会话断点由 server 记录的 sessionId 承载，行为与 pi 会话续接一致。
5. 作为审核者，我看到 claude-code 审核步拿不到写文件工具（readOnly 生效），worker 步全量工具——两后端能力面在缝上可读。
6. 作为回归测试者，我看到 pi 侧全部既有 probe 在引入第二后端后全绿（零回归是被证明的，不是被声称的）。

## Implementation Decisions

### 数据契约

- ClaimedStep / machineTokenResponse **零新增字段**：claude-code 步的 `provider` 槽 = null（A4），`agent.provider` 字符串本身承载身份（'claude-code' ∈ BACKEND_RUNTIME_IDS）

| SDK 面 | StepEvent | 备注 |

**票名**：`daemon(claude-code): 第二运行时最小闭环——SDK 桥、per-step 解析、零凭据通道`

**可验证闭环目标**：verify 栈上，一个 `provider='claude-code'` 的 agent 跑通一个 worker 步：claim → claude 后端执行 → transcript 出 text/toolcall 行 → done 携 usage → 步 completed、sessionId 回传；第二步以该 sessionId 续会话（resume 生效）。同一栈上 pi 既有 probe 全绿（零回归）。

**先列失败方式，再写实现**（仓规测试 3）：
1. SDK 平台二进制缺失（`--omit=optional` 安装 / 平台不匹配）→ 后端构造即报「Native CLI binary not found」→ probe 前置断言后端可构造
2. claude 认证缺失（verify 栈合成 HOME 切走了登录态）→ 首个 query 失败 → probe 环境契约：claude-code 面在真实 HOME（或 ANTHROPIC_API_KEY）下跑，脚本明示（t-0024 实测坑）
3. resolver 默认支改坏 → pi agent 步走错后端 → 分支测试钉「非 runtime 身份恒 pi」+ pi probe 回归
4. server/runner 凭据回退改漏一侧 → claude-code 步仍炸 `no agent/model` → 两处分支同票落地 + 失败信息含 runtime 字样

## 影响面（blast radius）

**改动是什么**：设计票——产品代码零改动；T1 落地时 daemon 增第二后端 + 两处凭据分支 + 一条缝 lint。

**全案安全所依赖的一个事实**：**后端解析的默认支不变**——`agent.provider` 不命中 `BACKEND_RUNTIME_IDS`（即全部既有 pi agent：custom provider id 或 null）时，走的后端、拿的 provider 配置、进的 failStep 判定与今日逐字节相同。设计阶段证明到第 3 级（走代码步进）：runner 的凭据分支只对 runtime 身份短路（`runner.ts:261-266` 现行为对 pi agent 是 `creds.provider ?? {kind:'api_key', providerId}`，改动后非 runtime 身份的这条表达式原样）；server `machines.ts:1405` 回退只排除 runtime 身份值；machine-loop `:84-101` pi 后端构造不动。第 4/5 级证明（跑真代码）= T1 的 pi 回归 probe——这正是票面把它列为验收的原因。

**风险**（确认保留）：
- **fail-open 而非 fail-closed**：后端对不支持的 opts（remoteTools/MCP）静默丢弃会让 chief 链路悄悄降级。缓解：A10 首票即 fail-closed 报错。可能性低（新代码新分支）、代价中（静默行为漂移）。
- **SDK 依赖面**：平台二进制 optional deps + 闭源 + 版本随 CLI 走（SDK 版本号钉 bundle 的 CLI 版本）。缓解：lockfile 钉版（D6 同律）+ 升级窗口纪律沿用 pi 的经验。可能性中、代价低（缺二进制 = 启动即报，不静默）。
- **steer 语义分叉**（A8）：pi 中途注入 vs claude 排队下轮，用户在 UI 上看不到差别说明。缓解：T2 收口 + 文档明示。可能性高（必然存在）、代价低（行为仍正确，只是时点不同）。
- **verify 栈认证坑**：合成 HOME 切走 claude 登录 → probe 假红。缓解：T1 失败方式 2 的环境契约。可能性高（t-0024 实测过同类）、代价低（probe 期暴露，不进产品）。

**已核查清除**：
- claim/journal/recover/steer/stop/heartbeat/transcript/git 收尾——全部消费 SessionOpts/AgentSessionHandle/StepEvent，后端实现替换不影响（缝的存在理由，`agent-backend.ts:220-227`）；machine-loop `:41` 本就是注入面
- Multica 侧对照（claim 全族共享、分叉唯一）经 fresh clone 核验，非 r10 转述
- 词汇面不新增第二单源：BACKEND_RUNTIME_IDS 只收 backend 身份（'claude-code'），与 MODEL_SOURCE_RUNTIMES（含 pi）语义分立、各自单源

**合入前最便宜的捕捉**：T1 的两条 probe——claude-code 步闭环（红则新后端坏）+ pi 既有 probe（红则默认支坏）。
