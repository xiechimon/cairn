# 26 · pi session runtime and trust surfaces (trust / telemetry / settings / cost / cache)

> Scope: the daemon's pi session (`apps/daemon/src/backend/pi.ts`, in-process SDK) previously had three "silent defaults" and one "cost bit that was always 0". This volume lands five decisions explicitly in code: what project trust rules on, how far telemetry/version check is turned off, what file-backed settings bypass, where cost comes from and goes, and how the cache retention tier is set.
>
> References: issues #925, #927, #1808; pi 1.0.4 docs (`docs/security.md` §Understand project trust, `docs/settings.md`, `docs/models.md`, `docs/custom-provider.md`, `docs/environment-variables.md`) and dist sources (cited line by line below). At ticket-writing time pi was 0.86.0 and the upgrade has since happened — D1–D6 were re-verified against **1.0.4**. D7 was checked against pi **1.4.0**.

## Problem Statement

1. **Project trust had zero handling, and the direction was opposite to the ticket's guess.** pi CLI in non-interactive scenarios defaults to `"ask"` → skips protected resources; but the daemon goes through the SDK + `SettingsManager.inMemory`, whose `projectTrusted` defaults to **true** (`settings-manager.js:187/214`). Consequence: a task worktree's `.pi/SYSTEM.md` / `.pi/APPEND_SYSTEM.md` **silently becomes part of the session system prompt** (`resource-loader.js:941-956` lets it through per `isProjectTrusted()` → `agent-session.js:1272` consumes `loader.getSystemPrompt()`). The task repo's content can thereby rewrite the agent's responsibility surface — bypassing every pacman-owned authorization seam (brief = the AGENTS.md written by runner, skills = catalog+allowlist+read gate (spec 14/#917), MCP = server authorization bridge, commands = #866 gate). `.pi/mcp.json` / `.pi/extensions` not taking effect today is only because the SDK surface has no builtin extension injection (`resource-loader.js:247`, the builtin set comes from `extensionFactories`, which the daemon does not pass) — a coincidence, not a decision.
2. **Telemetry is on by default.** pi's `enableInstallTelemetry` defaults to **true** (`settings-manager.js:777`), and the SDK request surface consumes it: `sdk.js:194`, on every stream request, goes through `mergeProviderAttributionHeaders` to add attribution headers for OpenRouter/NVIDIA/Cloudflare hosts (`provider-attribution.js:28`). Install telemetry and the pi.dev version check proper live on the CLI entry paths (`interactive-mode.js:1010`, `package-manager-cli.js:577`); SDK sessions do not trigger them, but the subprocess inheritance surface is unpinned.
3. **File-backed settings are bypassed wholesale, without any declaration.** `SettingsManager.inMemory` makes pi's user-level/project-level `settings.json` (retry, modelOverrides, httpProxy, cacheWarming, packages…) entirely inert for daemon sessions. The bypass itself can be the right trade, but the list was never declared.
4. **Cost is always 0.** pi-ai's per-message `Usage.cost` (five USD terms, `types.d.ts:291-311`, computed by `models.js:657 calculateCost` from model prices) is dropped in the daemon's projection (`PiMessageLike.usage` has only four dimensions); custom endpoints materialize into `models.json` with always-zero prices (`CUSTOM_MODEL_DEFAULTS.cost`), and there is no price source anywhere in the chain.
5. **Cache retention tier unset.** `PI_CACHE_RETENTION` (consumed by pi-ai's five adapters: anthropic-messages → `cache_control.ttl:"1h"`; openai-completions → `prompt_cache_retention:"24h"`; openai-responses/bedrock/pi-messages same family) and cache warming (`cache-warmer.js`; the settings `cacheWarming` defaults to `"streaming"`, i.e. it will spontaneously send background refresh requests) both sit on pi's silent defaults.

## Solution

| ID | Decision | Landing form (single source) |
|---|---|---|
| **D1** | project trust = **deny**: protected resources under the task worktree's `.pi/` are never loaded | `daemonSettingsManager()` = `SettingsManager.inMemory(PI_DAEMON_SETTINGS, { projectTrusted: false })` (backend/pi.ts; open() and tests share the same construction, so declaration and behavior cannot fork) |
| **D1a** | deny **leaves a trace**, not silent | `detectTrustProtectedResources(cwd)` (an eight-entry vocabulary = pi security.md, `TRUST_PROTECTED_ENTRIES`) non-empty → `[trust] denied: <…> present in worktree …` canon line (the tenth family of DAEMON_LOG_PREFIXES; empty worktree stays silent) |
| **D2** | telemetry / version check = **off**, pinned at three layers | ① `PI_DAEMON_SETTINGS.enableInstallTelemetry: false` (flips pi's default true → attribution headers not sent); ② env pins `PI_TELEMETRY=0` (`telemetry.js:6`, env takes precedence over settings — double insurance + the subprocess inheritance surface); ③ env pins `PI_SKIP_VERSION_CHECK=1` (`version-check.js:66`; the existing `PI_OFFLINE=1` pin already short-circuits `getLatestPiRelease`, `version-check.js:37`) |
| **D3** | file-backed settings = **explicitly declared bypass** | `PI_SETTINGS_BYPASS` (a nine-family list, each entry with "who is responsible after the bypass") is the config-surface canonical copy, this section the doc surface; `PI_DAEMON_SETTINGS` = all session settings (compaction on / telemetry off / cacheWarming off); at startup the sequence lands a `[machine] pi policy: trust=deny telemetry=off version-check=off cache-retention=<tier> settings=in-memory …` proclamation line — the runtime surface is readable from daemon.log, no reverse-engineering from code |
| **D4** | cost = **record whatever pi reports**, host computes nothing | Per message: the `message_end` line carries `usage` (including cost) passed through verbatim (messageRecordSchema loose bits, the event-stream traceability surface); runner lands a `[step] message usage: <model> input=… output=… cacheRead=… cacheWrite=… cost=<total>` line per assistant message (daemon.log runtime reconciliation surface — "which stored cost was computed by which request" is checkable line by line); aggregation: `mapPiSessionEvent` accumulates `ModelUsage.cost` per `<provider>/<modelId>` (optional bit) → `done` → machine wire (`modelUsageSchema`; an old daemon not carrying it = defaults) → server `token_usage` five columns (real, migration 0027) → `GET /api/builds/:id/usage` |
| **D5** | price source = **administrator declares, pi computes** (no self-made price table) | `providerModelSchema.cost` (optional, USD / 1M tokens, pi catalog-price semantics, same shape as ModelCostRates) goes through provider config → `materializeProvider` overrides the zero default of `models.json` entries → pi's `calculateCost` computes per-message cost from it. Undeclared = zero price = cost always 0 (honestly reflecting "no price source"); preset providers use pi's built-in catalog prices. API surface configurable; the UI form is out of scope for this volume |
| **D6** | cache retention = **explicit tier, default short** | `PACMAN_PI_CACHE_RETENTION` (ENV_VARS.piCacheRetention): only `long` means long retention; unset or garbage values all mean `short`; `PI_CACHE_RETENTION` is always explicitly set (short included — the policy is readable from the process environment). Cache warming explicitly **off** (`PI_DAEMON_SETTINGS.cacheWarming`): unattended sessions send no background LLM requests at all; spend comes only from the agent steps themselves; the model-side `promptCache` lifetime is **not declared** — its only consumer is warming eligibility (`cache-warmer.js:26-30`), and with warming off, the declaration is meaningless |
| **D7** | compaction reserve = **upstream default, not set** | `buildPiSessionSettings().compaction` is `{ enabled: true }` only. pi 1.4.0 `SETTINGS_DEFAULTS.compaction.reserveTokens` is 16384 (`settings-defaults.js`). `getCompactionSettings()` fills that default when the field is unset. `shouldCompact` is `contextTokens > contextWindow - reserveTokens`. From 1.4.0, `generateSummary` ignores `reserveTokens`; the summary request uses the model output limit. |

### Why the compaction reserve stays at 16384 (#1808)

pi 1.4.0 uses `compaction.reserveTokens` only to decide when compaction starts. Cairn does not set the field, so a session runs on 16384. That default fits the context window Cairn materializes when a model declares nothing: `CUSTOM_MODEL_DEFAULTS` is a 128000 token window and a 16384 token output cap (`apps/daemon/src/backend/pi.ts`). After the reserve, 111616 tokens remain, which is enough for one full default output. The #1744 relay window was 320000 tokens; 16384 still leaves a positive headroom there (303616). The ceiling failure was the summary request itself: on 1.0.4 a prompt the provider counted as 319873 input tokens was sent with 128 output tokens, and 319873 + 128 exceeds 320000. 1.4.0 stops capping that summary at a fraction of `reserveTokens`. When the local token estimate is within the clamp's 4096-token margin of the provider's count, that same request succeeds. A provider that counts the prompt higher than the local estimate, or a prompt the provider counts past the window, still returns 400. Setting another reserve would start compaction earlier on every model. The provider schema allows a declared `maxTokens` with no upper bound (a 1000000 window may declare 32768), so no single explicit reserve covers every model. A turn that jumps past 16384 still hits pi's overflow recovery. The field stays unset.

### When the summary request itself is rejected (#1744)

`compactionCeilingFetch` wraps the pi session fetch. It retries only a summarization request, recognized by the pi summarization system prompt. When the provider reports an input count that still leaves room, the retry lowers `max_tokens` to that room. When the input itself leaves no room, the retry drops the oldest conversation text and asks again, up to four attempts. Each retry is a daemon step log line. If the prompt still does not fit, the log line is `compaction summary hit the context ceiling` plus the provider error, and a failed `compaction_end` is logged as `compaction failed: ...`. The step then fails with that provider error. A non-summarization request, and a summarization request rejected for another reason, are returned unchanged, so pi's own overflow recovery still runs.

### Why deny rather than approve

The task worktree is the agent's own workspace: part of its files come from the model's pen. Approve would mean "a `.pi/SYSTEM.md` written by the model may rewrite the next step's system prompt" — a self-privilege-escalation channel that bypasses every pacman authorization seam listed in D1. The only project-level input pacman needs is one thing: the brief context file written by runner (the AGENTS.md family), and it is **not gated by project trust** (pi security.md: context files load regardless of project trust; `noContextFiles` unset) — deny does not harm the brief channel, and the integration surface has zero-regression assertions. The agentDir-level (`PACMAN_HOME/agent-runtime`) `SYSTEM.md` still loads: that is the daemon's self-managed directory, not task input.

The detection point = each step session's `open()` (pi sessions are created per step and dropped per step): a protected resource appearing mid-step is named at the **next step's open**; the deny decision itself does not depend on detection — `projectTrusted:false` is a construction-time constant, and detection only provides the trace of "what deny actually intercepted".

### Why retention defaults to short rather than long

Long sends new fields to the gateway (`prompt_cache_retention` / `cache_control.ttl`). Some gateway channels deterministically reject unknown fields — the same family of lessons as #654's `store` / `max_completion_tokens`, unfixable on the relay side (corporate gateways). Short = pi's default tier; the request surface stays byte-identical to the past, zero exposure; long is the opt-in for operators who "know their gateway accepts this field". Warming follows the same tightening: its expected-savings rule (≥$0.05, `cache-warmer.js:7`) depends on catalog prices — a custom endpoint with no price never triggers it, but preset models would genuinely send background requests — explicit-off turns "will it spend" from an inference into a declaration.

## Compatibility surface

- **mixed-version**: old daemon → new server: `modelUsage.cost` absent, upsert records 0; new daemon → old server: zod objects strip unknown keys by default, the cost bit is ignored, the four dimensions continue as before.
- **claude-code backend**: usage mapping produces no cost (its SDK surface has no same-shape bit); `ModelUsage.cost` as an optional bit stays absent — the four-dimension convention is uniform across both backends; the cost dimension is a pi-backend capability bit.
- **chief accounting** (`services/chief.ts` four-dimension aggregation) untouched: the chief-surface reading convention for the cost dimension is out of scope for this volume.
