## 1. Process model and deployment topology (A1)

### 1.1 Three segments

```
browser (React SPA, same origin)  ──HTTP + SSE──┐
                                                 ├─ pacman-server (orchestration API + DB + git hosting + cron + notifications)
executor daemon (standalone process) ──HTTP + SSE─┘   ↑ connects via serverUrl (same machine or another, LAN/cloud both fine)
```

- **Locked**: the three-segment shape is same-shape with todos.dev (r3 §1/§8 measured it to be exactly this shape); the default deployment documentation teaches the "everything on one machine" form (server + daemon on the same machine), but **the protocol surface does not fold** — the daemon always connects to the server via an HTTP URL, and a "machine" can register another machine on a LAN/cloud server, honoring the BYOC shape and the free-BYOC tier's functional parity.
- **Inherited D1/D3**: durable orchestration semantics (step queue, session-persistence index, retry records) are all self-held by the server; the pi engine only lives inside the daemon process (the same-shape fact of r3 §1.5 executor=pi build).
- **Inherited D5**: the web frontend = an ordinary SPA, with no assumption of sharing a process with the server; a macOS desktop shell (Electron/Tauri-class) and the PWA wrap the same frontend, and the architecture needs no change (honoring the #34 Notes desktop-compatibility premise).

### 1.2 Realtime channels (**locked**; r3 §8.1 measured "all SSE, no WebSocket")

| Channel | Endpoint | Events (observed) |
|---|---|---|
| team stream (browser) | `GET /api/teams/{id}/stream` | `{"type":"ping","seq":n}` ~15s heartbeat; `{"type":"machine_presence","machineId","online"}`; **r5 measured extension**: `{"type":"todo"\|"build",seq,v,doc}` full-document pushes and `{"type":"notification",…}` (r5 §7.2) |
| conversation stream (browser) | `GET /api/conversations/{id}/stream` | the transcript realtime stream (r3 §3.5 capture); **pacman-side event-vocabulary extension [designed]**: message / step / text_delta / thinking_delta / activity / agent_todo (vocabulary single source = `packages/shared/src/protocol/sse.ts`; activity (#905) and agent_todo (#1524) are transient events, not persisted, the hub keeps the latest copy in a single slot for late-joiner replay, cleared at the step's terminal state) |
| machine wake (daemon) | `GET /api/machine/stream` | low-latency dispatch wake (r3 §1.5) |

Board updates that are not presence-class: no task events were seen entering the stream in the r3 window, originally judged **[inferred]** to go through query-invalidation re-fetch; **partially re-adjudicated per r5 §7.2** — the team stream measurably carries `todo`/`build` full-document events (with `seq`/`v` versions) and `notification` events, and the board can update directly from document events; whether invalidation re-fetch coexists was not separately observed **[inference kept]**. The replication adopts a double safety net: direct update from SSE document events + re-fetch fallback.

## 2. Tenants and simplification boundaries (A2/A3)

1. **User**: a single local user is seeded; auto-login at startup, with `GET /api/auth/session` and `/api/user/me` returning that user in the preserved shape. No registration, no invites, no login-page replication (#35 inventoried public pages only; the workspace after login is the parity object).
2. **Team**: the `team` table and all `teamId` path segments keep their shape, with the data permanently seeded as one row. Multi-tenant SaaS operations are out of scope to begin with (the map).
3. **Members**: the team page's real-member area renders only one row for yourself + the Agent count (r3 §4 observes "member count includes Agents"). The invite/join flow is not implemented.
4. **Paid touchpoints (locked, Q15 ruling)**: all Pro walls and upgrade popups of r2 §7 are **not replicated** — no machine-count limit (the r2 §7.1 `1/4` gate and the r3 §1.2 limit popup are comparison objects, not replication targets), the providers "new" button is always present (the r3 §2 gating observation is todos.dev behavior, not adopted), hosted repos have no wall, and there is no `upgrade to Pro` button. The `plan` field stays in the team-record shape but participates in no gating. The "slot" concept (the wording conflict of r1 §9.6 that chief conversations do not occupy slots) falls away with the paid surface and is not ruled on.
5. ~~`maxConcurrent 3`~~ (r3 §1.5 machine logs, §4 machine-page copy "concurrency cap 3") is not a paid item, but **the concurrency-cap concept has been removed wholesale with #503** — that cap has no user knob, the daemon executes serially and never actually hit it, so the server gate is removed with it; if rate limiting is ever wanted, the machine's own side decides.

## 4. Orchestration state machine and timeline (A5–A8)

### 4.1 The nine-value phase authority (A5, **locked**)

A todo is always in exactly one phase (the `[docs_concepts]` and `[docs_todos]` tables agree, r1 §7.4). Internal names take the docs ordering:

| Internal value | Semantics (docs original) | Board column (6 columns, r2 §4.1) | Evidence |
|---|---|---|---|
| `todo` | filed, not started | `待开始` | API measured (r3 §3.0) |
| `queued` | started, waiting for a free machine | `执行中` | docs table; column position = reference-site changelog 2026-09-12 "a queued todo sits on the step its build will run" (#1447 replaces the original `待开始 (folded)` [inference]) |
| `planning` | reading the repo, writing the plan | `规划中` | docs table (this also substantiates r3's "planning not captured [same-family inference]") |
| `confirm` | the plan is ready, waiting for you | `待确认` | docs table + the UI "confirm plan" button measured (r3 §3.4) |
| `building` | making changes | `执行中` | docs table; r3's `exec` guess is voided, the correct name is `building` |
| `review` | changes ready, waiting for you | `待验收` | API measured; `待验收 ≡ 审核` are the same phase (CONTEXT.md ruling inherited) |
| `done` | accepted, merged if you chose so | `已完成` (last 7 days) | API measured + changelog "Done (last 7 days)" |
| `failed` | the run stopped on an error | pinned to the top of the `执行中` column | docs table + changelog original text (r1 §7.4) |
| `closed` | shelved without completion | occupies no column **[inferred]** (the 6 columns have no closed column; the right-click Close menu item measured r1 §443) |

Other field shapes copy r3 §3.0 (`phaseAt/seqNum/orderIndex/tagIds/spec/assignment/agent/latestBuildId/lastRunAt/hasChanges/hasPlan/buildHistory/sourceTodo/v`).

**Column-mapping granularity (annotated per r5 §8 observation)**: a gate-state card's column also depends on `hasChanges` — a card in confirm/review **with no code changes** stays in the `执行中` column (its primary buttons being `方案`/`回复` respectively), and only a review card **with changes** enters `待验收` (primary button `完成`). The replication board renders by this dual key (phase × hasChanges).

### 4.2 The build and step model (A6, **locked**: r3 §1.5/§3 measured semantics collected 1:1)

- **Entity equation**: one run = one build = one conversation = one worktree + one `conv-<conversationId>` branch; `buildId ≡ conversationId` (r3 §3.0 measured). Conversation/Plan/Transcript are facets, not entities (CONTEXT.md inherited).
- **The step queue is held by the server; machines claim**: three step kinds = planning step, execution step, merge step (r3 §1.5 observation); the machine-page copy canon: "claims build, planning, and review tasks and runs Agents. Concurrency cap 3" (r3 §4).
- **Main timeline** (full chain measured r3 §3):

```
create todo (POST /api/projects/{id}/todos {title,spec}) → phase=todo
click "start" → the start-task dialog (Agent optional / the "use different Agents for planning and execution" switch / plan first | execute now)
→ POST /api/projects/{id}/builds → the server enqueues a planning step
→ machine tasks/claim → workspace preparation (preparing workspace…) → planning step (new session) → plan card (v1) → push branch
→ phase=confirm → (human) confirm plan → execution step → transcript stream (text_delta/toolcall/edit/bash lines) → push
→ phase=review → (human) complete → the confirm popover "merge the changes into the default branch" → POST /api/builds/{id}/merge
→ 202 {delegated:true} → the machine claims the merge step (continue session reusing the execution turn's session) → git merge --no-edit → the timeline "started the merge" + result line + 🎉 → phase=done (stops the build's unclaimed verify / review steps)
  (github shape, build records a PR: → the server merges the PR via GitHub REST → the timeline "started the merge" + merge line + 🎉 → phase=done → 202 {delegated:true}, see "merge via the GitHub API" below)
```

- **Wrap-up and human actions (#1403)**: a merge-step success, a successful merge via the GitHub API below, and PR reconciliation all go through the same done wrap-up (`finishTodoDone`); at wrap-up, the build's unclaimed (queued or quota-waiting) verify / review steps are stopped, and when PR reconciliation comes out failed the same stopping applies. `POST /api/builds/{id}/merge` and the AI-review action re-read the phase after awaiting (PR probing, reading changes): if the card was wrapped up in the meantime → 409, and neither a merge step nor a review step is enqueued.

- **The github shape's CI grind-to-green, BEHIND and DIRTY (#1150, #1403 segment 3, [designed])**: a card whose execution step delivered a PR stays on building, and the server grinds one round per minute. First it conditionally reads `pulls/{n}` for the PR's head SHA and `mergeable_state`; when the recorded PR is the one this build opened (same repo, head is this build's working branch, target is the default branch), check runs are read by that head SHA (`commits/{sha}/check-runs`), not by branch name; when it is not (a same-named branch in a fork, another branch, target not the default branch, already closed) → read by working-branch name, and conflicts are not processed. Only the default branch's required-check list is honored: the union of classic branch protection (`protection.required_status_checks`' `contexts` and `checks[].context` from `branches/{default branch}`) and ruleset (`required_status_checks` from `rules/branches/{default branch}`) (when classic's `enforcement_level` is `off`, its list does not count), cached 10 minutes per repo and default branch; a rules response of 404, or 403 with a message saying the plan lacks the feature ("Upgrade to GitHub Pro … enable this feature"), not rate limiting, not SAML SSO denial (`x-github-sso`) → no rules (the plan has no ruleset); a 403 from insufficient permissions cannot be read — anything else unreadable means no movement this round (other cards of the same repo are not read again within this round; re-read next round). When check runs return 304, re-judge the previously read runs against the list at that time. Same-named runs fold into one name: one `success` passes (a same-named failure no longer spawns a fix round). When pacman just pushed (a step wrapped up within the empty-check grace period reported its commits, review steps excepted) and the PR's head is not yet it → no judgment this round (GitHub has not caught up with the push; both head and `mergeable_state` are stale); past the grace, judge by the PR's head (a human may have pushed more commits); DIRTY / BEHIND on review behave the same. When the list is non-empty: required checks not finished → wait; `failure` / `timed_out` → a `[ci-fix]` fix round (3-round cap); `action_required` (waiting for human approval, an agent cannot fix) does not count as pass; a required check absent → wait, and still absent past the empty-check grace → does not count as pass (it may report on commit status, or beyond the first page of 100 check runs: neither is read), and "the repo has no CI" does not grant passage; all `success` → advance to review; any other conclusion (`cancelled`, `neutral`, `skipped`, `stale`) does not count as pass: no advance, no fix step, one prompt per round. When the list is empty: look at all checks; zero → after the grace hand to a human as green; a name without `success` but with `cancelled` or `action_required` → does not count as pass; `neutral` and `skipped` do not block. When the open PR's `mergeable_state` is `dirty` (conflicting with the default branch) → dispatch one `[merge-conflict]` execution step on the same build (merge the default branch into the same branch, resolve conflicts, commit and push; the instruction quotes the default-branch name in shell single quotes; no rebase, no force-push, no new branch or PR, spec 23's same-branch continuation), first stop the build's unclaimed verify / review steps (same on building), a card on review returns to queued (entering building when claimed, the grind-to-green takes over), if the build already has a verify step (an unclaimed one is stopped, or a finished one; the same for a conflict-resolution round on building) one line is logged, and when the grind returns to review a new verify is re-queued for the merged head (the `[ci-fix]` rounds in between do not affect it; verify steps stopped for other reasons are not re-queued, one per build as usual); a stopped unclaimed AI-review step is also logged as one line, and review does not re-queue automatically (how many reviewers and who reviews are decided when a human initiates). Two rounds still conflicting on the same build → no more dispatch: on building it turns failed (same as the fix-round cap), on review one prompt per round. `behind` is handled only on review, only on the build's own open PR: the merge strategy is human-merge (human, currently the only strategy), pacman does not issue update-branch for a human; one prompt per round (click Update branch on GitHub, i.e. `PUT pulls/{n}/update-branch` with `expected_head_sha`). Other `mergeable_state` values are left alone. When a step is written done / failed / stopped, `step.finishedAt` is set (migration 0047), "the last pushed commit" is ordered by it, and rows from before the migration fall back to the last report.

- **Merging via the GitHub API on the github shape (#1403 segment 2b, design D, user ruling 2026-10-22, [designed]; ADR 0021 D2)**: when the project is github-shape and the current build records a PR, `POST /api/builds/{id}/merge` does not dispatch a merge step; the server merges this PR with the team's GitHub connection instead, and merge authority is not delegated to machines. First do the checks that write nothing: the phase is review, or failed and recoverable (the #702 criterion below; other phases 409 or illegal phase transition), this run is the todo's current run, this build has no in-flight steps (claimed steps, or non-review steps queued or waiting quota: they still push when they wrap up; unclaimed verify / review steps do not block and are stopped at wrap-up); re-read after the #1217 second-PR guard; the XMON-77 permission gate; the GitHub connection (none → 409 please connect, unresolvable → 409 please reconnect, the server has no secret box → 409 naming the server's key configuration; a review card can also be merged directly on GitHub and wrapped up after reconciliation — without a connection the reconciliation reads anonymously and cannot read private repos); no merge in progress on the same build (in-process registration; if present → 409). Then read `pulls/{n}` with the token, and after the read the gate re-adjudicates once more (the phase must still be the one at the gate at the start): closed-unmerged, not this build's PR (same reconciliation criterion: same repo, this build's working branch), the author lacking write permission on the repo (`author_association` not OWNER / MEMBER / COLLABORATOR: what the daemon records is the open PR with the highest number on the branch, regardless of who opened it), target not the default branch, unreadable (404, rate-limited, 5xx, timeout, network error, a response body that is not a JSON object) or missing fields (including the title) → 409, no merge issued, no line logged; passing these and already merged → 409 for the review card (reconciliation will verify and wrap up), a failed card restores to review, logs one line, returns 202, and is handed to reconciliation for the wrap-up (a failed card is not read by reconciliation; dragging the card to done on the board also goes through the merge popover back to here, so the rejection copy for failed cards says "merge on GitHub, then click merge again"); then take the build's last-pushed commit (the commit reported by the step that wrapped up last, taken the same way as the PR reconciliation below, but merge-step commits also count: it merges the default branch into the working branch and pushes, so the PR's head is exactly it; missing or not a 40-hex SHA → 409), a head that is not it → 409 naming both short SHAs. Then issue `PUT pulls/{n}/merge`: `sha` = the last-pushed commit, `merge_method: squash`, `commit_title` = `<PR title> (#n)`; when the PR title itself (verifying the title only, not the string after appending ` (#n)`) carries a ticket-closing shape (GitHub's closing keywords close / fix / resolve in all forms, case-insensitive, optionally with a colon, followed by a numbered token: #N, GH-N, owner/repo#N, an issue link) switch to `Merge pull request #n` — the PR title is decided by the PR author, and the author criterion includes read-only members, so letting a title with a closing shape into the default branch would close arbitrary issues; when the todo comes from this repo's issue N (GitHub issue import or self-created issue) `commit_message` = `closes #N`, and for other repos' issues, orchestration sources, or no source it is `Merged by pacman.` (always passed: when not passed, GitHub takes the PR body or each commit's message per repo settings, and closing keywords would enter from there). Three outcomes: merged → the timeline "started the merge" + "PR #n was merged by pacman via GitHub (squash, merge commit …)" + the done wrap-up (failed first restores to review; if the phase was changed by a human during the request only a line is logged), 202 `{delegated:true}`; GitHub explicitly refuses (4xx and not rate-limited, or 200 with `merged: false`) → 409 with GitHub's `message` (same cleaning as reconciliation, truncated to 100 characters; 401 please reconnect GitHub), no line, no phase change, clicking again re-issues; rate-limited (429, or a 403 with `x-ratelimit-remaining: 0`, `retry-after`, or a secondary-rate-limit message: GitHub did not process the request) → 409 with GitHub's `message` and the unblocking moment (when known), no line, no phase change (user ruling 2026-10-22, amending design D's original "rate limiting counts as no clear answer" clause, [record](https://github.com/xiechimon/pacman/issues/1403#issuecomment-6344983763)); no clear answer (timeout, network error, 5xx, an unreadable 200) → "started the merge" + one explanatory line, failed restores to review (reconciliation reads review cards only), 202, and the later PR reconciliation closes the loop once it reads the merge (`sha` bound the last-pushed commit, so containment holds naturally). While the request is in flight, reconciliation treats this build as having a step in flight (it does not touch it before or after the read). A merge step completing on such a build (dispatched before the upgrade, or recording the PR only at its report time) → no wrap-up (a phase that cannot reach done is rejected as before), one line naming the PR, and after the PR merges on GitHub the reconciliation wraps up. A github shape without a PR, an invalid githubRepo, and hosted-vs-local repos go through the merge step as before. Cost: this path does not merge the default branch into the PR branch at merge time; in repos that require up-to-date branches, a stale PR receives GitHub's refusal copy, and after clicking Update branch on GitHub the head is no longer the last-pushed commit, so a human merges on GitHub and the reconciliation wraps up (the update-branch discussion of segment 3 is separate).

- **PR reconciliation on the github shape (#1403, [designed])**: the second road to done. A card stuck on review with the current build carrying a PR: the server conditionally reads `pulls/{n}` once per minute (when GitHub is not connected, once per PR per 5 minutes, least-recently-read first; when the reconciliation's own anonymous requests reach 20 in the last hour, or reconciliation plus grind-to-green together reach 50, reconciliation pauses reading — the grind only counts, and is not blocked by these two caps): the PR merged into the default branch on GitHub, with the merge-time head containing the checkpoint of the step that wrapped up last on this build (review steps and merge steps do not count: a merge step's commit merges the default branch into the working branch, not a delivery; and it must be the most recently created step: a verify step created in the previous round may finish and push only after this round's build step — ordered by the step's wrap-up moment `step.finishedAt`, rows before migration 0047 fall back to the last report) → the timeline line "PR #n merged on GitHub" + the same done wrap-up as a merge-step success (the same completion line); merged into another branch or missing later commits → one prompt line, the card stays on review; closed unmerged, and still closed on the immediately next read (one round apart; closing and reopening a PR to rerun CI does not count; if a step was in flight between the two reads so no read happened, or one read failed, restart the count from the next read), and the target is the default branch → the timeline close line + `build.errorMessage` + `failed`; the target is another branch (another PR from the working branch to another branch, e.g. a collaborator's backport: the daemon probe records the open PR with the highest number on the build, and the build's real PR may still be open) → after confirmation one prompt line, the card stays on review, no close line, no bounce-back, no step stopping. Each outcome is reported at most once per round (round boundary = the build's most recent build / plan step; when #931's rework reuses the same build, a new round starts from then): if this round already has a completion line (written by the merge step or reconciliation) do not wrap up again as merged; if it already has a reconciliation close line do not wrap up again as closed; a human dragging the card back to review after the report is the human's decision. No clock is watched: when CI goes green and the merge happens, a card entering review only after the merge still wraps up. At wrap-up, stop the unclaimed (queued or quota-waiting) verify / review steps. Before writing, verify the PR is this build's: the PR number was found by the daemon via branch name (`gh pr list --head` matches branch names only, so a fork's same-named-branch PR is also found), the head repo and base repo are the same repo (compared by repo id within the same response: still matches after a repo rename or transfer, a fork does not), and the head branch is this build's `conv-<conversationId>` branch — only then wrap up or bounce back; a mismatch (including a deleted fork, an empty head repo) → one prompt line per round, the card stays on review; a response missing the head branch, base branch, default branch, or base-repo id → treated as unreadable. The PR number recorded on the build is refreshed by the daemon's probe only when a non-review step wraps up; when a human closes it during review and opens another from the same working branch, it goes stale (#1403 segment 2): after confirming the close, before bouncing back, and before the first read of someone else's PR each round and before prompting, list the PRs from this build's working branch to the default branch once (`pulls?state=all&head=<owner>:<branch>&base=<default branch>`); the owner in the list's head takes the response's current target-repo owner (the stored name goes stale after a repo rename or transfer). If the build has another PR of its own (same repo, this build's working branch, target the default branch, author with write permission on the repo: `author_association` is OWNER / MEMBER / COLLABORATOR, #1403 segment 2b — a human closing this build's PR means discarding this change, and a same-branch PR opened later by someone without write permission does not count; prefer open, otherwise the highest-numbered merged one, and it must be newer than the build's own most recent closed-unmerged PR (for that one the author's write permission does not matter, #1509 pr-gate round 2: the list response carries no closer, so a maintainer's close and the author's own close are indistinguishable — taking either side without changing the record means a misjudgment only bounces the card to failed for a human), and on the close path it must at least be newer than the recorded one: an earlier merge is old business, and a human closing the new one means discarding this change) → re-record it (number and link, only when the build still records the original one), one timeline line per round, no bounce, no prompt, read it next round; if the recorded one is open or merged again in the list (reopened or merged between the two reads) → no write, re-read it next round. A list that cannot be produced on the close path → no write, the close still counts as seen, list again on the next read, and a second consecutive failure to list → bounce back as above; a recorded PR that is not this build's (including an open one) → listed at most once per 10 minutes (per hour when GitHub is not connected), the count restarts when the recorded PR changes, and with none or an unproducible list → one prompt per round as usual. GitHub texts referenced in timeline lines (branch names, merger, merge commit) have control and formatting characters stripped (bidirectional overrides, zero-width characters) and are truncated to 100 characters.

## 8. Key-security model (A11, three-layer boundary)

| Layer | Contract | Source/nature |
|---|---|---|
| at-rest | credential-class data uniformly encrypted in server-side storage; the key source = a local keyfile (generated on first start; no external KMS / no passphrase-derivation scheme → detailed plan handed off to #43) | locked (Q5); copy parity: `密钥将加密存储，保存后无法再次查看。` (r3 measured form note) |
| runtime | provider keys and git credentials are **delivered per step**, held in executor memory, never resident on disk; team Secrets are **authorized per Agent and narrowed per step** (write-only; the version-gate shape "requires tds CLI 0.1.28 or later on the machine" kept), with plaintext **never spread into the agent process environment** | the provider/git shapes inherit r3 §1.6/§4; not-on-disk is **[inferred]** (inheriting r3's annotation as-is). The delivery form of Secrets = a **replication-side deliberate divergence** (#508): the official writes long-lived plaintext into the task shell environment variables, while the agent's very job is to execute the code in the repo — dependency postinstalls, MCP servers, and any CLI it spawns all inherit the process environment and can read it without a trace. The replication changes to: the daemon holds the true values + a per-step local retrieval channel (explicit retrieval within the step, retrieval leaves an audit line, invalid at step wrap-up), the same discipline as the per-step lifecycle of the git half |
| API surface | all key-class fields are **write-only masked** (`apiKey`, provider keys, team secret values never returned by GET); apiKey/machine tokens are **stored as hashes server-side, not reversible values** (login verification only needs matching; unrelated to todos.dev's internal implementation — the user sees the same masking either way) | the former measured; hash storage marked **[designed]** |

- One-time display: the apiKey creation response carries the plaintext once + `请立即复制密钥，它仅显示一次。`; thereafter list rows are masked (r3 §6 measured).
- Threat-model statement: the self-host scenario = local-disk static protection + minimal runtime exposure; no promise of todos.dev's cloud multi-tenant isolation semantics (out of scope).
- Recovery wording: a lost keyfile = all existing provider keys are void and must be re-entered — the documentation must state this (guardrail against the "encryption = recoverable" misreading).

### 9.1 Notifications

- **todos.dev's measured delivery architecture (r5 §7 re-adjudication)**: **Web Push really exists** — the page bundle embeds a VAPID public key; `registerForPush()` = permission granted → `pushManager.subscribe({userVisibleOnly, applicationServerKey})` → `POST /api/push` uploads the subscription; the SW (`sw.js`) consumes declarative payloads `{web_push:8030, notification:{title,body,navigate,tag}}` (Safari 18.4+ natively; Chrome/Firefox fall back through the `push` handler); **foreground suppression = an app window exists that is visible+focused**; `notificationclick` deep-links via CacheStorage `/__pending-nav` + postMessage. **The page layer has zero `new Notification(`/`showNotification(` calls** (statically proven from the bundle) — the in-page experience = the SSE team stream's `{"type":"notification",…}` events → toast / unread badge / sidebar red dot. - **Replication delivery (Q6 final ruling, #45 2026-09-22)**: the replication honors the "background reminder" user semantics via SSE notification events + in-page `new Notification()` (fired when `document.hidden`); Web Push/VAPID does not enter the spec, ruled a **deliberate divergence** (not a parity obligation). The sw.js push handler keeps its file shape, and the server does not push; the desktop shell's native path keeps its shape. Acceptance criterion = volume 04 §5.
