## 0. 目标与终态

**「它」= pacman 产品本身**，不是 Claude Code 车道。车道今天已经在自合：ADR 0007 让车道开 PR 即挂 `gh pr merge --squash --auto`，CI 一绿 GitHub 自己合。本计划要的是另一条环——mea 上跑着的 pacman 实例，对 `xiechimon/pacman` 这个仓，自己领票、自己写、自己开 PR、自己验证、自己合并。

**毕业判据（终态，机器可核）**：

1. mea 实例上的 pacman，对 `xiechimon/pacman`，**用户零点击**连续落地 5 张 `ready-for-agent` 票：领票 → 派发 → plan → build → 开 PR → CI 磨绿 → 三视角审核 + 独立验证（判定绑定确切补丁）→ 合并就绪闸全绿 → squash 合并 → issue 关闭 → todo `done`。
2. 这 5 次合并之后 main 的 `check` / `pack-smoke` / `e2e-gate` 全绿，24 小时内无回滚。
3. 每张 PR 的 body 过 `pr-evidence` 闸，证据在 `docs/verify/<票号>/`，raw 链钉 SHA。
4. 五条负对照全部按预期拦下（§4 P8）。

用户角色随之变成视频里那句：事后看 main 上落了什么，抽查、回滚、把纠正升格成闸。这也是 spec 18 §5 诚实清单第 1 条（「更好」依赖无人值守成真）欠着的账。

## 1. 视频讲了什么，pacman 已经站在哪一级

视频的主线不是「怎么让 agent 合并」，而是**信任**：合并权是信任攒够之后的副产品。她给的路径和 pacman 现状逐条对照：

| 视频主张（时间戳） | pacman 现状 | 差距 |
|---|---|---|
| 信任曲线（05:20）：1–5 个 agent 的阶段靠盯每个会话；没有信任就扩并行 = 一堆 slop PR 与回归 | 多车道并行 + chief 派发 + #1153 双机持续派发实测已过 | 信任没有落成**机器可判的合并资格**——判定散在消息行里，不进任何闸 |
| 验证技能 = feature map（给上下文）+ CLI（给控制），「THE AGENT CAN VERIFY ITS OWN WORK」（08:28） | `verify-pacman` 已是 pstack 六节形（Launch / Doctor / Drive / Evidence / Cleanup / Helpers），`features/` 36 份地图 | `scripts/` 下 101 个脚本，大半是一票一个 `drive-<票号>.mjs`——正是她点名要消灭的形态（每个会话各写各的脚本）；证据归档靠人手拷 |
| 纠错阶梯（15:40）：codebase > static analysis（lint/compiler/ci）> rules/bugbot > skills > style guide，越靠前越好 | 闸很多：ui-debt / registry / consumer-shape / lane-file / spec-parse / drizzle drift / pr-evidence / pr-tasks | 没有「一次纠正 → 升一级」的机制化回路；`docs/pr-review.md` 评分卡仍落在第 5 级（靠人读） |
| 园丁（24:28）：删债 → 单一铺装路 → lint 反模式；「Each copy makes the next copy likelier」 | 棘轮基线（只降不升）已有 | 没有定期的园丁任务 |
| 外环自动化（31:57）：Slack/Sentry 事件自动拉 cloud agent，自动复现、自动开 PR | webhook 只吃 `issues/labeled`，且 server 在 tailnet 内 GitHub 打不进来；`ci-loop.ts` 60s 轮询 check-runs | 无 issue 轮询；chief 的 `issues` / `pull_requests` / `workflow_runs` 工具是空桩 |
| agent 自合 PR（2026-08 推文；pstack：独立验证者按确切 head 出判定，root 合并，CI 须在最新基线上绿） | 合并留人（ADR 0018「合并动作留人」、#1256 机器入口硬挡）；GitHub 形态的 merge 步 server 侧不落地 | 本计划主体 |

结论：pacman 的仓规与闸已经爬到阶梯中上段（这也是车道能挂 auto-merge 的前提）。缺的是**产品里**的三样：判定绑补丁、合并权按策略下放、外环进料。

## 2. 现状盘点（af161e3，三路调研 + 抽查）

### 2.1 可复用

- **进料**：webhook `issues/labeled`（标 `pacman`）→ `importGithubIssue` → `orchestrateTodo`；手动导入 `POST /api/projects/{id}/github/issues/import`，`sourceRef` 409 防重。
- **派发**：chief `run_builds`（`withPlan` 判定，ADR 0014）；`split_todo` 依赖边 + 波次自动派（`advanceSplitWaves`）；confirm 闸 chief 自动确认（#1254）。
- **执行**：7 员 persona 名册（ADR 0018）；按机 worktree；daemon push；agent 用机器上的 `gh` 开 PR；`github-probe.ts` 回填 `prUrl/prNumber`；换机续跑（#1153 leg-8）。
- **CI**：`ci-loop.ts` 红 → `[ci-fix]` 同分支修复步（3 轮上限）→ 绿 → `review` + verify 步。
- **审核 / 验证**：三视角 review fan-out（CodeReviewer / SecurityAuditor / TestEngineer），`blocking` 发现自动返工；verify 步结构化判定 `{passed, conclusion, evidence[]}`。
- **护栏**：第二张 PR 守卫（#1217）；合并/推送权限开关（`AGENT_TOOL_SWITCHES`）；分支保护 `strict: true` + 必需检查 `check` / `pack-smoke` / `e2e-gate`；`allow_auto_merge` / `allow_update_branch` 已开。
- **仓规**：`pr-pacman`（六节 body）、`verify-pacman`、`docs/pr-review.md`、`issue-label-gate` 的标签词表（`ready-for-agent` 现成就是领票队列）、chief-dispatch hillclimb 评测（36–64 例，回归闸）。

## 3. 开跑前裁决（用户拍板）

每条给推荐项。goal 会话只按这里写定的裁决施工，遇到未裁决项即停。

| ID | 问题 | 推荐裁决 | 理由 |
|---|---|---|---|
| **D1** | 合并权怎么下放 | 新 ADR 0021 修订 ADR 0018「合并动作留人」：项目级 `mergePolicy = human \| shadow \| autonomous`，**默认 `human`**。`human` 下 #1256 硬挡原样保留；`shadow` 只算闸、不合并；`autonomous` 由 server 在合并就绪闸全绿时合并 | README 的卖点是「Gated by design」，对外默认不变；pacman 自用项目单独开。`shadow` 就是 pstack 的 autopilot-stack：同一条环、什么都不发，攒对照数据再放权 |
| **D2** | 谁执行合并 | 自治路径由 **server** 经 `lib/github.ts` 调 REST merge，带 `sha` 参数（head 必须等于该值 GitHub 才合），squash。squash 的 message 由 server 拼：标题取 PR 标题按仓规形态，正文末行固定写 `closes #<sourceRef 的 issue 号>` | 合并权不下发到 agent 机器的 `gh` 登录；`sha` 参数让「判定对应确切 head」在平台层兜底；「关票关键字写进 commit message」这条仓规由代码保证，不靠 agent 记得（视频阶梯第 1 级）；凭证沿用团队 `github_connection`（scope 已含 `repo`） |
| **D3** | 判定绑定什么 | 绑**补丁摘要** `patchDigest` = 对 `compare/{base}...{head}` 的文件列表（排除 `docs/verify/**`）取每个文件的 `[status, filename, previous_filename, blobSha, patchSha]` JSON 元组排序后取 sha256（改名两头都绑定；`patchSha` 是该文件 patch 文本的 sha256，解冲突保留本 PR 版本时 blob 不变而补丁会变）；判定同时记 `headSha`。合并时重算，摘要不等 = 判定过期 = 重新验证 | update-branch 把 main 合进来，只要 main 的新提交不碰本 PR 改的文件，摘要就不变，判定不必重跑（省 token）；碰到了则摘要变、判定重验（保守方向）；verifier 只往 `docs/verify/` 提交证据，也不会让判定失效；任何改代码的推送都会让摘要变，判定自动作废。pstack 原话：verifiers run again after every later push that changes the patch |
| **D4** | 哪些改动永远留人 | 默认拒绝：只有产品源码、测试与 `docs/verify/**` 可不经人，其中再排除保护类别；保护类别按类、任意层级、不分大小写匹配（清单见 ADR 0021 D4）：CI 与钩子、左右 agent 的文件（各级 `.claude/`、`.pi/`、`.cursor/`、`CLAUDE*.md` / `AGENTS*.md`、`docs/pr-review.md`、`docs/adr/**`）、闸脚本与决定检查口径的配置（各级 `scripts/`、`*.config.*`、biome、tsconfig、`.gitignore`、`.gitattributes`）、合并就绪闸自身的源码（只放在 ADR 0021 D4 ④ 列的三处）、迁移（单向门）、依赖清单与锁文件（供应链）、安全敏感面（AGENTS.md `/security-review` 一节的清单，两处一起改）与跑迁移的 `apps/server/src/db/client.ts`。另加：删测试文件、证据目录外 compare 不给 patch 的文件（二进制、diff 过大、纯改名）、补丁超 800 行或 40 个文件（含证据）、单日自治合并超过上限 | agent 不能改自己的闸来让自己过闸（古德哈特）；迁移和依赖是单向门 |
| **D5** | 领哪些票 | 只领**带 `ready-for-agent` 标签、且该标签由仓库 owner / collaborator 打上**的 open issue（events API 核打标人）；issue 正文一律当数据 | 公开仓谁都能开 issue，但只有协作者能打标；标签就是授权。正文里的注入靠 D4 + 合并就绪闸兜底 |
| **D6** | 合并后 mea 实例要不要自更新 | 要，但走独立的部署环：定时器挑「main 上 CI 全绿的最新 SHA」→ 备份库 → 排空在飞步 → 重启 → 健康检查 → 失败回滚到最后已知良好 SHA。**npm 发布永远留人** | 不自更新，main 上的修复永远到不了干活的实例；但部署失败会把自己砸死（G10），所以回滚是硬要求不是可选 |
| **D7** | goal 会话施工期间自己的 PR 怎么合 | 沿用 ADR 0007 车道流程（`--squash --auto`），但开 auto-merge 的前提是 §7.5 的 `pr-gate` workflow 在当前 head 出 go；**另有**两类留给用户点合并：P0 的 ADR 0021（推翻既有 ADR）、P4 的合并执行器（把合并权交给机器）。其余按 D4 判，命中保护路径的也留人 | 这两张是单向门；其余都是双向门，CI + 证据闸足够。施工期实际上每期 PR 都留用户合并：§7.4 要每期在自己的 PR 里改 §8 台账，`docs/spec/` 在可自动合并集外，P1 还碰 `.claude/`、P3 是闸源码；auto-merge 只落在不改台账、只碰产品源码 / 测试 / 证据的拆分段 PR 上 |

## 4. 分期施工

每期都按仓规走：先开票（标签过 `issue-label-gate`）→ 需要时先跑 §7.5 的 `understand` / `design-panel` → **先列失败方式、先写失败测试** → 实现 → `pnpm lint` / `pnpm typecheck` / `pnpm spec:parse` / `pnpm exec vitest run --changed` / `pnpm --filter @pacman/web e2e:affected` → `verify-pacman` 取实物证据进 `docs/verify/<票号>/` → `/code-review` 自审（开 PR 前跑，PR 期间推送修复后、合并前各再跑一次；确认的发现先修）→ `pr-pacman` 六节 body → CI 绿后跑 §7.5 的 `pr-gate` → 按 D7 合并 → 回写 §8 台账。commit message 结尾 `closes #N`。

依赖关系：P0 → {P1, P2, P5a} 可并行 → P3（依赖 P2）→ P4（依赖 P0 + P3）→ {P5b, P6, P7} → P8。粗估 15–20 张 PR。

### P1 · 验证 CLI 收敛（视频里的 Control Glass）

- 把 `verify-pacman/scripts/` 下的 launch / doctor / drive / capture / cleanup 收成一个入口：`node .claude/skills/verify-pacman/scripts/vp.mjs <launch|doctor|list|drive <feature> [case]|capture|archive <票号>|links <票号>|cleanup>`。
- `features/*.md` 每份补「用户怎么到达」（路由、快捷键、点哪个元素）与对应 `drive` 子命令名——这是视频说的 feature map 的另一半。
- `archive <票号> --from <证据目录>` 把 `.claude/verify-evidence/` 下点名的目录拷进 `docs/verify/<票号>/`（只拷贝，目标已存在即拒绝，ADR 0015）；提交并推送之后，`links <票号>` 打印钉 SHA 的 raw 链（原先这一步靠人手，§2.2 未列但是证据链的断点）。raw 链要等提交推上去才能解析，所以拷贝与打印链分成两个子命令。
- 加一道静态闸：新增匹配 `drive-\d+` 的脚本即红（把「每票一个脚本」从第 5 级升到第 2 级）。**存量 drive 脚本不删**——删「看起来是有意写的」代码前先问用户（CLAUDE.md）。
- **失败方式**：子命令与老脚本行为漂移；feature 地图引用的选择子过期（已有 `feature-map-staleness-gate` 兜）；端口撞别的车道（沿用 8791/5273 与 `VERIFY_*` 覆写）。
- **验收**：一个只拿到 `vp.mjs --help` 与 feature map 的新会话，端到端验证 3 个既有功能并归档证据；负对照：人为植入一个回归，CLI 驱动能抓住。

### P2 · GitHub PR 面 + 合并对账

- `lib/github.ts` 增：读 PR（`state` / `merged` / `draft` / `mergeable_state` / `head.sha`）、`update-branch`（带 `expected_head_sha`）、merge（带 `sha`）、commit status、`compare` 文件列表、PR 评审与评论读取。端点与参数施工前按 CLAUDE.md 外部 API 纪律核实，不凭记忆。
- **对账环**：`ci-loop` 的候选集从 `building` 扩到 `building | review`（有 `prNumber` 的 GitHub 形态 build）：
  - PR 已合并（不管谁合的）→ todo `done`，落 system 行写明合并 SHA，推进 split 波次；
  - PR 关闭未合并 → todo `failed` + 原因；
  - BEHIND → `update-branch`（`human` 策略下只提示不动手）；
  - DIRTY → 同分支追加 `[merge-conflict]` build 步（把 main 合进来解冲突，禁 force-push，同 spec 23 的同分支续轮）。
- check-runs 改按 **head SHA** 读，不按分支 ref；neutral / skipped / cancelled 不再一律算绿（只认必需检查名单）。
- **人工合并路也修好**：GitHub 形态的「完成 + 合并」改为 server 经 API 合并（带 `sha`），不再依赖 LLM 服从 `请把本会话分支的改动合并到默认分支` 那句 prompt。这条对所有用户都是缺陷修复，与自治无关。
- 修 G9：先写失败测试复现，再改 review 关口的 wake 文案。
- **失败方式**：GitHub 429 / 404 / 网络错 → fail-open 不动、下轮重试（沿用 ci-loop 纪律）；人工在网络窗口里推进了 phase → 写前重读；同一 PR 被两个 build 指向（#1217 守卫）；merge 返回 405（不可合）→ 下轮重评，不重试轰炸。
- **验收**：集成测试用假 GitHub 覆盖四态；mea 上实测「在 GitHub 网页手动合并 → 1 分钟内卡变 done」。

### P3 · 合并就绪闸（补丁绑定判定 + 自动审核 / 验证 + chief go/no-go）

- 判定 schema（review / verify / go-no-go 三种）加 `headSha` 与 `patchDigest`；server 收到判定时按 D3 现算摘要并落库。
- verifier 改为**对代码只读**：只允许向 `docs/verify/<票号>/` 提交证据；收尾校验「判定 head 之后的提交只碰证据目录」，否则判定作废。
- `mergePolicy ≠ human` 时，进 `review` 自动派三视角审核 + verify（verify 槽缺省落 Verifier persona），不再等人手点。
- 实现 ADR 0018 的 chief 小合并步：三份审核 + 验证判定齐了、且摘要一致，chief 持全上下文（三报告 + diff + 验证证据）出 `{go, reasons, headSha, patchDigest}`。
- blocking 发现改走**同分支修复轮** `[review-fix]`（同 `[ci-fix]` 形，2 轮上限），不再一律回 `planning`（G8）；需要改方案的由 chief 判定后才回重规划。
- 闸的源码只放在 `apps/server/src/services/merge-gate/**`、`packages/shared/src/records/merge-gate.ts` 与 `apps/daemon/src/merge-decision.ts`：ADR 0021 D4 ④ 与 pr-gate 的保护清单按这三处判，放到别处的闸代码会被当成普通产品源码自动合并。
- 纯函数 `mergeReadiness(build) → {ready, blockers[]}`，blockers 至少覆盖：策略为 `human`；自治暂停中；PR 非 open 或是 draft；`mergeable_state ≠ clean`（`has_hooks` 视同 `clean`；`unstable` 只在未通过的全是闸自己的 status 时放行）或有非必需检查未通过；必需检查在当前 head 未全绿；`pr-evidence` 未绿；验证判定缺失 / 未通过 / 摘要过期；任一审核有 blocking 或摘要过期；chief 未出 go 或摘要过期；命中 D4 保护路径或体量上限；删了测试；todo 的 `sourceRef` 解不出 issue 号（D2 拼不出 `closes #N`）；body 的 raw 证据链不指向本分支 `docs/verify/<票号>/`（AGENTS.md 合并前核验规则）。
- 结果写成 head SHA 上的 commit status `pacman/merge-gate`（描述带首个 blocker），任务详情页与 chief 新工具 `merge_readiness` 同源展示。**不加进分支保护的必需检查**——加了会把车道与人工合并一起锁住。
- **失败方式**：判定在推送之后才落库（竞态）→ 以判定里的 `headSha` 现算摘要，不以收到时的 head 为准；compare 文件列表被截断（超过 API 单次上限）→ 直接判 `human`；三视角之一超时 → 不合成 go；chief 的 go 与某条 blocking 冲突 → blocking 优先。
- **验收**：单元测试覆盖每个 blocker 的真假两腿；集成测试演示「update-branch 后摘要不变、判定仍有效」与「改一行代码后判定作废、自动重验」。

### P4 · 自治合并（策略 + 执行器 + 刹车）

- 迁移：`project.mergePolicy`（默认 `human`）、团队级 `autonomyPaused`、`maxAutonomousMergesPerDay`（默认 10）。
- 合并执行器（scheduler 家族，60s）：`autonomous` 且 `mergeReadiness.ready` → REST merge 带 `sha`；一仓一轮最多合一个（`strict: true` 下其余 PR 会转 BEHIND，交给 P2 的 update-branch，补丁摘要不变则判定不重跑）。`shadow` 只写 status 与「本应在 <sha> 合并」的 system 行。
- 合并后：P2 对账把 todo 推 `done`；commit message 的 `closes #N` 关 issue；`scripts/cleanup-merged-branches.sh` 清分支。
- **刹车**：
  - 急停：UI 开关 + REST + `pacman autonomy pause`，下一轮即生效；
  - 熔断：自治合并产生的 main 提交 CI 转红 → 自动暂停自治 + 开回滚 PR（回滚 PR 自身走 `human`）+ 通知；
  - 日上限；
  - `human` 策略下 chief `merge_builds` 继续硬挡；`autonomous` 下 chief 也只能「请求合并」，最终仍过 `mergeReadiness`，没有绕过闸的入口。
- **失败方式**：merge 成功但响应丢失 → 下轮对账看到 merged 收尾，不重复合并；两个执行器实例并发（server 重启重叠）→ 以 `sha` 参数 + 库内合并锁去重；急停与合并同一秒落下 → 合并前最后一次读开关。
- **验收**：用户合并本期 PR（D7）。演练仓上 `shadow` / `autonomous` 各跑通一次；急停与熔断各演一次，证据入档。

### P5 · 自主进料 + 仓规内化

- **P5a 进料**：issue 轮询（5 分钟，scheduler 家族；opt-in，`PACMAN_ISSUE_INTAKE` 为 `1` / `true` / `yes` 才开，默认关），按 D5 过滤（该标签最新一条 labeled 之后没有 unlabeled，打标人在仓库上是 triage 及以上；这条 labeled 事件带 `performed_via_github_app`，即经 GitHub App 打的标，不领。这一条只认得出 GitHub App：用 OAuth App 令牌或 PAT 打的标，事件上与该账号本人亲手打的一样，拦不住。OAuth App 令牌包括 `gh auth login` 自己拿到的令牌，也包括团队的 GitHub 连接令牌（自注册的 GitHub OAuth App 换来的）——pacman 把它随步下发给 git（git 自己的钩子也在这个环境里跑），也交给仓库里的 `.agents/setup` / `.agents/resume` 钩子，能改这些钩子的 agent 步就拿得到它；pacman 的 agent 步还能直接用机器上已登录的 `gh`。两条路都能以对应账号的身份打标、给进料喂票），导入（`sourceRef` 409 防重）→ `orchestrateTodo`；项目级在飞上限（默认 3）。webhook 的 `pacman` 触发（#1459，进料开没开都生效）守同一 D5 与同一上限：打标人取事件的 `sender`，在仓库上 triage 及以上才导入（与轮询器同一权限读、同一缓存），在飞现数含还在等 GitHub 读的导入；没有 sender、sender 不是 GitHub 账号名、sender 不到 triage、权限读不到或遇限流、项目已满、团队没有可用 token、项目存的 githubRepo 不是 owner/repo、GitHub 上找不到该 issue，都不导入，记一行日志写明原因码，一律答 202（拒收不喂 GitHub 重投；打标人权限类的三种拒收只答同一句，不说是哪种、哪个账号。这只去掉作答里的权限结论，之后导入是否继续仍会显出打标人够不够格，URL token 泄漏的补救仍是吊销）。webhook 载荷里没有 `performed_via_github_app`，经 GitHub App 打的 `pacman` 标仍会导入，留给后续段。chief 的 `issues` / `pull_requests` / `workflow_runs` 改成真读。
- **P5b PR 反馈回灌**：`autonomous` 下，PR 上的人类或 bot 评审评论进同分支修复轮（同 `[ci-fix]` 形）；回复与 resolve 由修复轮的 agent 用 `gh` 完成。
- **仓规内化**：在 daemon worktree 里实测一次——`AGENTS.md` / `CLAUDE.md` 被引擎原生读到（spec 24）、`.claude/skills/pr-pacman` 与 `verify-pacman` 可用、`pnpm lint` / `typecheck` / `spec:parse` 能跑、body 过 `pr-evidence`。哪条不成立就补到 run brief（spec 24）或 Implementer persona 文案里。daemon `commitAll` 的分支内提交形态是 `<kind>: <title>`，与仓规 `<scope>(<票号>): <subject>` 不同。squash 进 main 的 message 取决于谁发起合并：自治路径取 D2 由 server 拼的 message；在 pacman 里点合并也由 server 经 REST 合并（#1403），未传 message 时 GitHub 按仓库设置取（单提交取该提交 message，多提交取 PR 标题加各提交 message），单提交 PR 会把 `<kind>: <title>` 带进 main。故对齐放在 server 侧：REST 合并统一传 `commit_title`（PR 标题）与 D2 的正文末行，分支内提交不改；PR 标题本身由 P5 对齐仓规。
- **失败方式**：同一 issue 被 webhook 与轮询各导一次（409 兜住，落测试）；轮询打满 GitHub 速率 → 轮询器自己的读（候选列表、events、permission、issue 状态）遇限流（429，或带限流信号的 403），该团队本轮其余的读全停（读到一半的对账与列表留到下一轮），下一轮照常再读，日志记一行（GitHub 给了重置时刻就带上）；导入时 `importGithubIssue` 自己的读遇限流只算这一次导入失败（记一行），本轮接着判下一条候选；issue 在派发后被摘标 → 不中途撤，但不再领新票；被领的 issue 在 GitHub 上关了 → 只对账轮询器领的卡：导入时 createdBy 记为本队 chief 绑定的 Agent，对账只认 createdBy 等于本队 chief 当前绑定 Agent 的 github-issue 卡（手工导入与 webhook 导入的卡 createdBy 是 seed 用户，不碰；chief 没绑 Agent 的团队不对账；换绑后，换绑前领的卡不再对账）；本进程看到它从 open 变成 closed、且最新一条 closed 事件的关闭人在仓库上是 triage 及以上，才对账收尾为 `closed`（首见即 closed、外部作者自己关的都不动）；review 卡与 build 交付过 PR 的卡不归进料关，合并带关闭引用关掉 issue 时不以 `closed` 收尾：review 期交付过 PR 的由 P2 的 PR 对账收尾（段 1 #1414 已合并），其余相位的由 ci-loop 推进或等人处理；拆卡父卡还有子卡不在 done / closed 时不碰（子卡全 done 时父卡自动收口落 done）。
- **验收**：演练仓上打标 → 无人介入出 PR，body 一次过 `pr-evidence`。

### P6 · 纠错回路 + 园丁

- 新增仓内 skill `.claude/skills/correct/`：输入一次纠正（自治合并被回滚、人在 review 关口打回、`shadow` 期的误放），按视频阶梯定级（codebase > lint/CI > rules > skills > 评审卡），优先最高可行级，产出一张带 `correction` 标签的票；新闸必须拿那次真实失误做负对照验证（pstack 同律）。
- 触发：回滚、打回、同一类 blocking 发现第二次出现 → chief 开纠错票，票照常走自治环（但改闸属 D4 保护路径，合并留人）。
- 园丁：每周一次的定时任务——压低棘轮基线（ui-debt、lint-warning-cap、feature-map 陈旧基线）、清死类（dead-class-gate）、刷新 feature map；每项都是普通票，走同一条环。
- **验收**：拿 `shadow` 期一次真实误判跑通「纠正 → 新闸 → 负对照红 → 修复后绿」。

### P7 · mea 自部署与回滚

- `scripts/ops/deploy-mea.sh`：入参是 main 上的 SHA；校验该 SHA 的必需检查全绿 → `pnpm install --frozen-lockfile` → 构建 web → 按 `docs/ops-db-backup.md` 备份库 → 排空（停领新步，等在飞步收尾，有上限）→ 重启 systemd 三件套 → 健康检查（server API、daemon 心跳、演练项目上一张冒烟卡）→ 失败则回滚到最后已知良好 SHA 并重启 → 落一行部署记录。
- systemd 定时器每 30 分钟挑「main 上必需检查全绿的最新 SHA」，与合并执行器解耦。
- 含迁移的版本：迁移本身是 D4 保护路径（人合），部署前强制备份。
- **失败方式**：部署把 daemon 砸坏、它再也修不了自己 → 回滚由部署脚本自己做，不依赖 pacman；排空等不完 → 超时后放弃本轮部署而不是硬杀；回滚目标本身也坏 → 停在原版本并通知。
- **验收**：在 mea 上演一次故意失败的部署（健康检查必挂的 SHA），自动回滚，证据入档。

### P8 · 毕业（干跑 → 演练仓 → 本仓）

1. **shadow**：`xiechimon/pacman` 开 `shadow`，至少 10 张 PR，逐张记录「闸的判定 vs 用户的判定」。过线：**零误放**（闸说 go、用户找到了 blocking 问题）；每次误拦写明原因并进 P6。
2. **演练仓 autonomous**：`xiechimon/pacman-1150-dogfood` 跑 5 张票，加五条负对照：
   - 植入缺陷的 PR → 验证不过 → 不合并；
   - 改保护路径的 PR → 转 `human`；
   - 验证之后又改了一行代码 → 判定作废 → 自动重验；
   - 急停 → 一轮内不再合并；
   - 合并后 main 转红 → 熔断暂停 + 回滚 PR。
3. **本仓 autonomous**：`xiechimon/pacman` 开 `autonomous`，按 §0 毕业判据收口。

## 5. Premortem（假设已失败，最可能的死因与护栏）

| 死因 | 护栏 |
|---|---|
| agent 改测试或改闸让自己过闸 | D4 保护路径；删测试即 `human`；棘轮基线以 PR base 为准（ui-debt-gate 既有 D3） |
| 判定对的是旧代码 | D3 补丁摘要 + merge 带 `sha`；摘要变即重验 |
| 两张各自绿的 PR 合在一起把 main 弄红（10-16 事故同形） | `strict: true` 已在；熔断 + 回滚 PR；一仓一轮最多合一个 |
| 合并把 mea 上的自己砸死 | P7 回滚不依赖 pacman；迁移留人 |
| 公开仓 issue 注入 | D5 只认协作者打标；正文当数据；D4 + 合并就绪闸 |
| 证据是编的或钉错 SHA | 合并就绪闸核 raw 链指向本分支 `docs/verify/<票号>/`；verifier 自己重新生成证据，不信 PR 描述（pstack：distrust the PR description） |
| token 失控 | 修复轮上限（ci-fix 3 / review-fix 2）；项目在飞上限；日合并上限；各期在 §6 记每张合并 PR 的花费 |
| 环悄悄死了没人知道 | 轮询器与执行器都在 server 进程内（不靠模型醒）；自治暂停、熔断、部署回滚都发通知 |
| `shadow` 数据不够就放权 | P8 第 1 步的硬线：至少 10 张、零误放 |

## 6. 度量（P4 起持续记录）

- 自治合并数 / 天；开 PR 到合并的中位时长。
- 误放率（合并后被回滚或被用户判为不该合）——过线前要求 0。
- 误拦率（闸拦了、用户原样合并）——只记录、进 P6，不设硬线。
- 每张合并 PR 的 token 花费；main 红灯分钟数；用户点击次数 / 张。

## 7. goal 模式运行手册

### 7.1 `/goal` 是什么

Claude Code 内建命令，`/goal <条件>`：设置会话级完成条件，每轮结束由一个小模型对照对话记录判「未达成 / 达成 / 不可能」，未达成就继续下一轮。判定模型**不跑命令、不读文件，只看对话里出现过的东西**，所以条件必须能从输出里证明；连续几轮没有工具调用会自动停；条件上限 4000 字符。文档：https://code.claude.com/docs/en/goal 。它不改权限模式——要无人值守，得同时开 auto mode（https://code.claude.com/docs/en/permission-modes ）。

### 7.2 在哪跑、怎么跑

- **推荐在本机（Mac）跑**：需要 `gh` 登录（车道合并、update-branch）和 ssh 到 mea（P2 实测、P7、P8）。云端会话没有 `gh`、也到不了 tailnet 里的 mea，只能做到 P6 的代码面，P7 / P8 的实测要回到本机。
- 按仓规建绝对路径 worktree：`git fetch origin main && git worktree add --detach /Users/xmon/Code/AgentProjects/pacman/.claude/worktrees/bootstrap origin/main`，在里面起 `claude`，确认状态栏是 auto mode，再贴 §7.3 的提示词。
- 无头跑法：`claude -p "<§7.3 全文>" --permission-mode auto --max-budget-usd <上限> --output-format stream-json --verbose`。人在外面时用 Remote Control 从手机看进度；D7 留给用户的那几次合并在 GitHub 手机端点。
- 一个 goal 跑全程会经历多次上下文压缩；跨压缩的进度靠 §8 台账（提交在仓里）而不是对话记忆。想分段跑，就把 §7.3 里的「全部完成」换成「P<n> 完成」，一期一个 goal。

### 7.3 goal 提示词（贴进会话即视为对 D1–D7 的显式确认）

```text

每轮结束打印一行台账摘要：当前期、在飞 PR 及其 CI 状态、等我合并的 PR 清单。
完成条件：§8 台账 P0–P7 每一行已勾选且带已合并 PR 链接与 docs/verify 证据链接，并已在对话中贴出 `gh pr list --repo xiechimon/pacman --state merged --search "<各期票号>"` 的输出核对；P8 第 1 步 shadow 报告已提交。若连续两轮只剩等我合并或等我裁决的事项，打印清单后停下。最多 400 轮。
```

### 7.4 云端会话变体（2026-10-20 用户选定：先在当前 Claude Code 云端会话跑，不另备宿主）

2026-10-20 在云端容器实测：server（scratch `PACMAN_HOME`）起得来，daemon `start --foreground` 注册成功，机器在线、认到本机 `claude` 二进制——施工与验证都能在容器里完成。容器的边界决定了范围：

| 约束 | 后果 | 处理 |
|---|---|---|
| 容器闲置即回收，数据目录随之消失 | 不能当长期 pacman 实例 | 只做施工现场；P7、P8 与各期「宿主实测」腿记为**待宿主** |
| pacman 的 agent 需要模型凭证，本会话的 Claude 凭证不外借 | pacman 自己的 agent 在本容器不干活 | 各期验收用集成测试（假 GitHub、假引擎）+ verify-pacman 隔离栈取实物 |
| 会话默认只许推 `claude/nice-faraday-o329b3` | 多期并行要多分支 | 提示词里显式授权 `claude/bootstrap-*` |

### 7.5 workflow 编排（2026-10-20 用户授权：「用 workflow 加入 plan」）

workflow = Workflow 工具执行的编排脚本（JavaScript）：按脚本确定性地调度一批子代理（并行、流水线、结构化输出），后台运行，跑完通知主会话；中途中断可凭 runId 续跑，已完成的代理直接取缓存。分工：整期施工（写码、跑闸、开 PR、等 CI）仍由主会话串行推进；workflow 只承担一次范围明确的铺开，跑完主会话读结果再决定下一步。

容量事实：同时在跑的代理上限 = min(16, CPU 数 − 2)，本容器 4 核即 2 个，其余排队；本会话规模指引为单个 workflow 不超过 10 个代理（`/config` 的 Dynamic workflow size 可调）。故云端变体期与期按序施工，不并行开工。

| workflow | 何时跑 | 形状 | 代理数 | 产出与用途 |
|---|---|---|---|---|
| `pr-gate`（核心） | 每张 PR 的 CI 全绿之后、开 auto-merge 或请用户合并之前；补丁每变一次重跑 | 五个维度并行找问题 → blocking 发现按审查者交卷先后各派 2 个反驳者，全程至多 4 个（即至多两条发现能被反驳；第三条起不派、原样保留，go 为假）（默认判「不成立」；两位都作答且都判不成立才撤销，任一缺席即保留）→ 汇总。反驳者也报自己读到的 headSha，读到别的 head 不算作答。D4 由脚本机械判（默认拒绝）：可自动合并集之外的路径与保护路径按调用方传入的 `changedFiles` 匹配，再并上审查者报的；删测试文件、证据目录外的二进制文件、补丁超 800 行或 40 个文件也转 `user`。安全维度另跑一遍文件列表，调用方漏传的路径（如没加 `--no-renames` 时重命名的原路径）使 go 为假并同样参与匹配。五维度：正确性与回归；仓规与缝纪律（`docs/pr-review.md`、biome 缝、尾标）；测试与失败方式覆盖；安全与 D4；证据真实性（在独立 worktree 里 detach 到 headSha，复跑 PR Verified 节引用的至多三条最窄命令，核对 raw 永久链，不信 PR 描述） | 5 + 反驳者至多 4，共至多 9 | `{pr, ticket, headSha, go, blocking[], suggestions[], protectedPaths[], mergedBy, humanReasons[], missing[], shaMismatch[], unlistedFiles[], skepticsMissing, checked}`。**只有 go 且 headSha 等于 PR 当前 head，主会话才开 auto-merge 或请用户合并**；no-go 的 blocking 在同分支修复后重跑。这是 P3 产品内合并就绪闸在施工期的手工等价物：写代码的主会话不批自己的合并 |
| `understand` | P2、P3、P4、P5 开工时 | 3–4 个只读代理各读一个子系统（server 服务层、daemon runner、shared 记录、相关测试）→ 结构化地图 + 失败方式候选 | 3–4 | 喂给「先列失败方式」，摘要写进票面 |
| `design-panel` | P3（补丁摘要与就绪闸）、P4（执行器与刹车）落码前 | 3 个独立方案（最小改动优先 / 风险优先 / 可测性优先）→ 2 个评审打分 → 主会话综合 | 5 | 选定方案写进票面与 PR 的 Upstream / Risk 节 |
| `drive-inventory` | P1 开工时 | 流水线：`verify-pacman/scripts/` 下的脚本逐个归类（属于哪个 feature、并入哪个子命令、是否已过期），低推理档 | 分批，单次不超过 10 | 收敛映射表进 P1 票面；**只归类不删改**，删存量脚本仍按 CLAUDE.md 先问 |

规则：

- 脚本里不用 `Date.now()` / `Math.random()`（会破坏续跑），时间戳经 `args` 传入。
- `pr-gate` 存为仓内 workflow `.claude/workflows/pr-gate.js`，随 P0 的 PR（#1410）提交，参数 `{pr, headSha, ticket, changedFiles, deletedFiles, linesChanged, binaryFiles}`：`changedFiles` 取 `git -c core.quotePath=false diff --no-renames --name-only origin/main...<headSha>`，`deletedFiles` 是同一命令加 `--diff-filter=D`，`linesChanged` 是 `git -c core.quotePath=false --attr-source=4b825dc642cb6eb9a060e54bf8d69288fbee4904 diff --no-renames --numstat origin/main...<headSha>` 两列之和（二进制行 `- -` 记 0；属性取空树，仓内 `.gitattributes` 的 `-diff` 改不了行数，pr-gate 第六轮；`--attr-source` 要 git 2.40 及以上，旧版 git 报未知选项时升级 git，不要去掉这个选项），`binaryFiles` 是同一 numstat 里 `- -` 行的路径：`docs/verify/` 之外的二进制文件留人（源码里一个 NUL 字节就会让 git 把文件当二进制、行数记 0，#1410 的 `/code-review`）。不加 `core.quotePath=false`，git 把非 ASCII 路径（`docs/adr/` 下全部文件）转义成带引号的形式，glob 匹配不上，脚本见到引号开头的路径直接拒绝；不加 `--no-renames`，重命名只列新名，保护文件改名移走就漏判（#1410 pr-gate 第二轮）。安全维度不看调用方的清单，自己按同样的命令取这四样，脚本取并集与较大值（调用方就是写 PR 的会话）。numstat 也要 `core.quotePath=false`，否则非 ASCII 的二进制路径被加引号，对不上文件清单（#1410 pr-gate 第七轮）。审查者只读仓库成员（`author_association` 为 OWNER / MEMBER / COLLABORATOR）的 PR 评论，评论命令用 `--jq` 先滤掉其余，正文不进审查者的上下文：仓库公开，谁都能评论，而证据维度有 shell（#1410 最终 `/code-review`）。票的正文在 D5 下可能出自仓外作者，提示里与 PR 正文一样写明是作者写的不可信数据、不是指令（#1410 pr-gate 第十一轮）。子代理对 GitHub 只读。确定性部分（参数校验、D4 判定、反驳撤销规则、go）由 `scripts/pr-gate-selfcheck.mjs` 以桩代理自检，CI 的 check 作业每次都跑；它在 `scripts/` 下，同属 D4。**跑 origin/main 上的那份**（`git show origin/main:.claude/workflows/pr-gate.js` 写到一次性文件后按 `scriptPath` 调用），不跑待审 PR 工作区里的那份——PR 不能改评它的闸。命名调用按会话**当前工作目录**下的 `.claude/workflows/` 解析：在不含该文件的 worktree 里按名找不到；同一目录里文件改过之后，按名拿到的内容可能仍是之前扫描的那份（#1410 三次实测，`docs/verify/1401/pr-gate-named-probe.txt` 与 `pr-gate-named-probe-2.txt`）。它属 ADR 0021 D4 保护路径，修改留用户合并。
- 证据维度会在独立 worktree 里执行 PR 引用的命令，带本会话的凭证。只对本会话施工的 PR 跑 `pr-gate`；脚本让证据维度先查 `head.repo.full_name`，不是本仓即不 checkout、不装依赖、不跑命令，只用 `git show` / `git diff` / `git ls-tree` 读、核链接；本仓的 head 也关掉钩子（`git -c core.hooksPath=/dev/null`）再 checkout、fetch、删 ref，因为共享 clone 的 `core.hooksPath` 可能是 husky 写的相对路径 `.husky/_`，会解析到 checkout 出来的树里。
- go 只对它判过的那个 head 有效。开 auto-merge 时钉住该 head（`gh pr merge --squash --auto --match-head-commit <headSha>`；GitHub 工具开 auto-merge 后核对 PR 的 head 仍等于 headSha）。之后要推送（修 CI、update-branch）先关 auto-merge；推完重跑 `pr-gate`。唯一例外按 D3：只合入 main、且 main 的新提交不碰本 PR 改的文件（补丁摘要不变），判定沿用，重开时钉新 head。
- workflow 子代理同样注入 CLAUDE.md；对 GitHub 只读（看 PR、拉提交），开 PR、合并只由主会话做。
- 每次 workflow 的结论在当轮台账摘要里转述一行（谁拦了什么、为什么）。
