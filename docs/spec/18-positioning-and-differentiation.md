## 1. Thesis (owner decision, 2026-11-28; supersedes the 2026-11-14 text)

> <!-- ruling:positioning.thesis -->Cairn makes your agents better at your work over time, on your own machines and with your own subscriptions: what you correct becomes memory, a mistake that repeats becomes a check in your repo, and a change to how an agent works will be kept only after it beats the current harness on an exam the agent cannot edit.<!-- /ruling --> The keep rule is being built; memory, the check proposal and retry lessons are what ship today. You tell one Coordinator what you want; it opens a thread for each piece of work, and agents do that work on your machines. Anything that cannot be undone, such as merging, sending a mail or submitting an application, waits for your yes.

One product, two kinds of project, one loop. A code project has a repository and lands through review plus the merge gate when you ask (or when your rules allow it). A personal project has no repository and holds the owner's own affairs, such as mail, calendar and job search; agents read, sort and draft there, and outward actions go through the one approval mechanism (the confirm-once class in `docs/design/ai-native-actions.md`). Both use the same Coordinator, the same memory, threads and decision cards; there is no second inbox or second approval system.

Who it is for: one person who writes code or works alongside code, has a machine that can stay on, already pays for Claude Code, Codex or Gemini or holds an API key, and wants code, mail and credentials to stay on their own machines. It is for one person, not a team: someone else who wants it runs their own copy. Not for: teams that share channels, roles and billing (Amp Spaces, Multica); people who only want a better interface for driving one coding agent themselves (T3 Code); an assistant whose home is a chat app (OpenClaw, Hermes Agent) — chat apps are entry points here, not the residence; people who want a hosted service with nothing to install. README's "Who it's for" section carries the same lists.

The review and merge machinery is one capability among others and is not the product's pitch. <!-- ruling:positioning.eval-scope -->Evaluation and harness self-improvement are the centre: `eval/**` (task set, scorers, run configuration) is a protected path read from the merge base, and a change to prompts, skills, routing or tool use will be kept only after it beats the current harness on that exam, with delivery and interruption guards; the keep rule is being built under `docs/design/harness-self-improve.md`, the exam and its grader are never editable by the agent being measured, and adoption of arbitrary application changes stays out.<!-- /ruling --> Evaluation applies to a personal assistant as much as to coding work (owner, 2026-11-12). What is specific to coding is the exam's content, not the ruler. <!-- ruling:positioning.roadmap-board -->Remaining direction work is tracked on the owner's roadmap board as the single checklist entry; no in-repo plan tracker.<!-- /ruling --> That board is outside the repository (owner decision, 2026-11-17; the in-repo tracker `docs/design/home-redesign-backend-todo.md` was deleted and its items migrated).

### 1.1 Capabilities carried over from the 2026-11-01 thesis

The 2026-11-01 thesis read "cairn is a self-hosted agent team whose output is trusted because of how it lands, not because of who routed it". Its three pillars survive as capabilities, not as the pitch; the second one is also the base the 2026-11-28 thesis builds on:

> As of 2026-11-01 neither DeepSeek Harness's super-agent nor sig has any of them (walk: `docs/research/dsh-sig-walk-2026-11.md`, #2489, PR #2490):
>
> 1. **An evidence-bound merge gate, model-checked.** The gate rule counts a verdict only for the patch it judged: verdicts bind to `patchDigest` (`apps/server/src/services/merge-gate/digest.ts`), the independent review additionally to `headSha`, and a later passing verdict cannot clear a blocking one on the same digest (ADR 0021, 0026, 0028). TLA+ models (`MergeGate`, `LocalLanding`, `RepeatedVerdict`, `ReviewHeadCausality`, plus `StepClaim` for who may run a step) are checked by TLC with negative controls (`.claude/skills/verify-merge-gate/`, `.claude/skills/verify-step-claim/`). Open gap, recorded there as F1: the manual REST merge (`mergeThroughGithub`) pins the merge to the checkpoint commit but does not yet re-read verdicts or re-derive the digest; closing it belongs to this capability.
> 2. **An eval ruler the agents cannot edit.** The system-level eval suite (`docs/design/eval-gate.md`, `eval/**`) keeps its task set, scorers and run configuration in `humanQueue.evalConfig`, and reads the exam from the merge-base checkout at run time, so a change cannot rewrite what judges it (`eval/README.md`). It runs daily on a dedicated host (`scripts/ops/eval-daily.mjs`). Its earlier form — trajectory packs exported by `apps/server/src/trajectory-export.ts` under spec-29 protection — was deleted on 2026-11-21 together with the exporter and the pack schema (owner decision). The harness-regression merge gate, the in-repo eval benches and the paired-trial adoption judge were removed on 2026-11-16 (owner decision). The keep rule that retains a harness change only after it beats the current harness on this exam is being built (`docs/design/harness-self-improve.md`); adoption of arbitrary application changes is not built and stays out.
> 3. **Per-task isolation that separates work, not privileges.** Each build edits and verifies in its own git worktree and branch on the user's host, so parallel work does not collide (`~/.cairn/workspaces`). The agent still runs as the operator's OS user: the orb executor and its nspawn provider were removed; no container or VM boundary ships today.
>
> The router (chief / coordinator), the daemon and machine pairing are necessary plumbing: cairn matches the best existing designs there (thread-subscription fast path #2487, watchdog #2488, quiet by default #1784) rather than claiming them as differentiators.

Why the thesis changed on 2026-11-28: the owner ruled that the product's centre is agents getting better at the user's work — memory, a repeat mistake turned into a repo check, and retry lessons today, with a change kept only after it beats a protected exam — and that the merge gate, review and this repository's own landing process (push-queue, green-main) are how code lands here, not the product's pitch. An outside comparison that read those as Cairn's core read the wrong layer. Why the thesis changed on 2026-11-14: the owner wants cairn to write code and run his personal affairs in one product, and to be used by other people; he ruled out team features for now and set no order among mail, calendar and job search. "General assistant" did not say who the product is for, so it is replaced by a named audience. Why the thesis changed on 2026-11-11: the owner decided cairn is a general assistant whose planned work reaches past code (mail, job applications, a daily brief), so a pitch built on the merge gate describes one capability and not the product. Why it changed on 2026-11-01: the earlier thesis (#516, 2026-10-01: "two hard gates + AI review with teeth + versioned plan documents", scarcity against Multica and todos) predates ADR 0026 / 0028, which replaced the human merge gate with machine trust, and the 2026-11-01 walk showed two shipped products (DSH super-agent, sig) with cairn's routing shape: a resident router over isolated workers on the user's own machines is table stakes. The earlier text is in git history and in `docs/adr/0008`.

In-volume terms (do not enter `CONTEXT.md` — that only manages product-domain entities):

- **Hard gate**: a fixed stopping point in the phase machine, two in total — Confirm (before any code is touched, review the plan) and Review (before release, review the diff). The server-side edge table enforces the transition; gates are not status labels. Confirm can be passed by plan auto-confirm per project policy (`sweepPlanAutoConfirm`); for merging, since ADR 0026 the default is the autonomous gate, and ADR 0028's phase-1 routes send protected paths and ADRs to the owner.
- **AI review with teeth**: the reviewer's blocking verdict directly drives the `review→planning` auto-reflow (#330 loop) — it can block a merge, not just leave a comment.
- **Versioned plan documents**: Plan / Changes class documents, comparable version by version, the object "looked at" on the gate.
- **Evidence-bound**: a verdict counts only for the patch digest it judged (ADR 0021 D3); the independent review is additionally bound to the current head (ADR 0026).
- **The exam**: the task set, scorers and run configuration under `eval/**`, read from the merge base. **The keep rule**: a candidate harness change is retained only after it beats the retained harness on paired trials of the exam, with delivery and interruption guards; it is being built.
- **Semantic axis / runtime axis**: the semantic axis = what makes the agents better (memory, checks, retry lessons, the exam and its keep rule); the runtime axis = where a task runs (runtime, daemon, worktree, self-hosted deployment).
- **Second-person criterion**: see §2.

**Maintenance trigger**: this thesis's scarcity has a clock. Any of these expires it the same day: a competitor ships learning from real corrections plus an un-editable exam and a keep rule for harness changes; todos goes open-source or self-hosted; DSH or sig ships a measured harness-improvement loop. On trigger, rewrite this section and README's lead sentence, leaving no hung thesis.

## 2. Criterion: A Second Person Can Run It (owner decision, 2026-11-14)

<!-- ruling:positioning.second-person -->Every trade-off first asks whether a second person can run it, then whether it differentiates; replaces self-use first.<!-- /ruling --> "Can a second person run it" means: someone other than the owner, without the owner's help, installs cairn (packaged desktop app, or `npx @xiechimon/cairn`), connects their own machine and their own subscription or API key, and gets a first result, such as a thread that merges a pull request.

This replaces "self-use first" (#515, 2026-09-30), which asked "do I really use it myself" first. That question ranked last everything only a newcomer hits and the owner never does: unclear first-run guidance, errors only the owner can read, documents that assume the history, and settings that exist only on the owner's machine. The second person is still one person with their own copy; the criterion does not bring in team features (§4).

Supporting discipline (#515 hard constraint): **reference implementation first, do not fabricate out of nothing** — any new mechanism first researches down to a running real implementation (Multica's open-source repo, todos official docs, Craft Agents, pi SDK), and if none found, mark `[inferred]` and degrade. Landing on the two axes: the semantic axis's mechanisms do not take Multica as reference (it has none); the runtime axis's mechanisms are not self-invented (it has an open-source implementation to read).

## 3. Two Axes

### 3.1 Semantic axis: measured capability on an exam the agent cannot edit

> <!-- ruling:positioning.capability-axis -->The semantic axis is measured capability: the same harness gets better at the user's real work, judged by an exam the agent cannot edit; memory, check proposals and retry lessons are shipped, and the keep-only-if-better rule is being built.<!-- /ruling --> This replaces D55's 2026-11-01 axis (the machine-verified, evidence-bound merge gate). The merge gate remains the enforcement point for code output — ADR 0026 / 0028, with owner approval wherever ADR 0028 routes the PR to the owner (protected paths, ADRs, lockfile changes, unsplittable oversized PRs, paths outside the auto-merge set) — but it is one capability, not the product's axis. The table below is kept as the record of the 2026-09/10 todos alignment; in it, Confirm can be passed by plan auto-confirm per project policy, and ADR 0028's phase-1 routes send protected paths and ADRs to the owner.

| Core piece | pacman landing spot | Comparison |
|---|---|---|
| two hard gates | Confirm / Review two phases; transitions only through the server-side edge table (`apps/server/src/services/phase.ts:17` `PHASE_TRANSITIONS`, REST / MCP / chief tool write surfaces all through `assertPhaseTransition`), the agent has zero state-self-writing channel | Multica: issue status explicitly written by the agent through the CLI, `in_review` is a status not a gate; todos: the two gates are the phases themselves |
| AI review with teeth | blocking verdict → `review→planning` auto-reflow (#330); review material = plan + change diff + read-only checkout, the same computation path a human looks at (#511 fixed the material link break) | todos: built-in AI review but explicitly states the reviewer has no veto ("The review does not decide anything"); Multica: no built-in (the official tutorial self-builds @Reviewer, the conclusion is just a normal comment) |
| versioned plan documents | the plan cards into the confirm gate, "review the plan before passing" has something to look at and compare version by version | Multica: no counterpart (plan goes through issue description and comments) |

### 3.2 Runtime axis: aligned with the Multica runtime model

<!-- ruling:positioning.runtime-axis -->The runtime axis follows the Multica runtime model: runtime = one computer x one CLI tool, daemon as runtime, self-hosted single data root.<!-- /ruling --> The model also has board + agent as handler. Multi-machine execution, runtime detection, liveness judgment, task-level identity read from Multica's open-source implementation (r10 full explanation, r11 gap inventory), not self-invented.

### 3.3 Not aligned with Multica's philosophy (three tenets)

no hard gates / status-first / daemon not a sandbox boundary ("Treat every run as unsandboxed"). Choosing them equals deleting one's own differentiation, becoming "a weaker Multica".

Added by D55 (2026-11-01, `docs/research/dsh-sig-walk-2026-11.md`): **workers as the operator's OS user** (DSH super-agent presets run `danger-full-access`; sig runs Claude Code with permission checks skipped) and **merge rules as prompt text** (DSH leaves merge conditions to the agent's instructions and GitHub branch protection). cairn takes the merge-rule item as its target: merges pass the evidence-bound gate (with the F1 gap in §1 still open). On worker isolation cairn currently matches DSH and sig rather than beating them — agents run as the operator's OS user in a per-task worktree, with no container or VM boundary shipped — so that is not a differentiation claim.

### 3.4 Coordinator: the single entry

Chief withdraws from the differentiation pillar (#516 ruling, 2026-10-01; the earlier #515 two-axes wording includes Chief, #521 still writes "differentiation four pieces", this item wins over both, corrected in the same batch). It exists as the **single entry** that carries every task and the harness's lessons — who dispatches work, collects results and keeps the memory and checks; **survival ruled by real closed-loop measurement**. In a single-person self-use scenario the user is the orchestrator themselves, Multica's "human assignment + squad leader routing" covers the same need; Chief cannot self-wake, the actual shape is a delegation panel + watchdog. The criterion is same-sourced with §5 honesty-list item 2: count the withPlan distribution and Chief's actual usage rate in the real closed-loop measurement. Once the thread-subscription fast path (#2487) lands, the measurement also counts the slow-path share: the fraction of events on existing work that still needs a chief turn (D55).

### 3.5 Shape principle: one Coordinator, capability first (2026-11-28 ruling; origin 2026-10-24)

Origin: after comparing EverMind Raven (the chief draws a task-dependency graph in memory, self-checks and runs directly, upstream output handed directly to downstream, chat entry), the user asked "should local users who need no PR switch to the Raven shape — with a board use the board, without a board use Raven". The 2026-11-28 ruling replaces the 2026-10-24 shape. <!-- ruling:positioning.shape -->One Coordinator; the entry is the user's choice; every task feeds the same harness — memory, the check proposal, retry lessons — and the same safety boundary; how code lands, a PR or a local merge, is only the landing route.<!-- /ruling --> The shape splits into three choices:

| Choice | Decided by | Values |
|---|---|---|
| entry and viewing surface | user | the Coordinator chat at home; IM (Telegram and WeChat iLink first slice, `docs/design/im-connections.md`; further platforms stay C class, see §4); command line (future). All share the same Coordinator and the same harness |
| output type | Coordinator judges per task | `code`: a repository change, reviewed before landing; `info` (research, report): does not touch the repo, results handed directly to the downstream card (#1626) |
| code landing mode | project shape | `githubRepo`: opens a PR, merges per ADR 0021; `localPath`: no PR, the same judgment merges locally (#1625) |

Constraints:

- The shape does not decide who learns or what is safe: every task feeds memory, and the irreversible-action boundary holds on every entry. Removing review or approvals for a subset of users would be a weaker product, not adopted.
- The gate is a phase-machine stopping point; the passer can be a human or a deterministic checker per project policy (ADR 0021's merge-readiness gate, #1623's decomposition checker); since ADR 0026 the default policy is autonomous, with protected paths requiring an independent review; in this repository ADR 0028's phase-1 routes send protected paths and ADRs to the owner. (Superseded wording, 2026-10-24: "the default is always a human, same caliber as ADR 0021 D1".)
- <!-- ruling:positioning.action-bound-approvals -->Approvals bind the irreversible-action boundary, not a mandatory lifecycle stage: merge/send/submit-class actions gate at the moment of effect via the action registry; the phase machine stays as the work-lifecycle spine for code output.<!-- /ruling --> (Owner decision, 2026-11-17.) The action registry's confirm-once/owner-only classes and standing grants decide each such gate, and the confirm/review phase gates remain the enforcement point until each action class re-derives its check (tracked on the owner's roadmap board).
- Same-kind comparison (historical, 2026-10-24): Vibe Kanban, Conductor's local worktree shapes all ultimately land through PRs, Raven's coding specialist has no repo-level merge gate. At that date "local repo, no PR, gate before merge" had no existing implementation; cairn's own gated local landing has since landed (#2050: `apps/daemon/src/local-merge.ts` calls `decideLocalMerge`).

Construction tickets (2026-10-24; #1625 has since landed through #2050): #1623 (decomposition checker passes → auto-run) → #1625 (local-shape auto-merge) → #1626 (info-class fast lane); #1624 (sub-card injection pre-delivery summary) parallel with #1623. The IM entry no longer waits: #1607 concluded, and the first slice (Telegram + WeChat iLink: pair → receive → text reply) landed per `docs/design/im-connections.md`; decision-card buttons and further adapters remain open. External-agent onboarding follows the ACP conclusion.

## 5. Honesty List

#516 five items and the 2026-11-28 addition (the parts the thesis cannot falsify):

1. **"Better" is only measured if the exam matches the work** — the fixed suite is small (50 coding-centric cases, 106 trials) and can go green while real work still fails; the keep rule's delivery and interruption guards stop a local gain from becoming a product regression, but they cannot prove the exam covers a given user's work. The public eval measures coding delivery, not a general "better at your work" claim.
2. **withPlan already measured — bypass dominates (2026-10-05 #892 measured)** — direct-execute skipping confirm is a built-in ability (`withPlan=false`), a manual phase change can also bypass the funnel; measured (local 28 builds / 17 done cards): direct-execute 39% (chief dispatch 8/8 all direct), the confirm gate entered 13 times only 3 confirmed, the review main door passed only 1, 15/17 done cards landed through manual phase changes (both gates skipped), versioned plan documents 0 rows. The "rubber stamp" did not appear (the only 4 human gate dwells were all substantive), but "bypass" holds — the degraded shape is really "two gates + a side door everyone walks", not "one gate + a ritual". Data and improvement-ticket suggestions: `docs/research/892-gate-usage-measurement.md`.
3. **The runtime surface is currently in debt** — #518 inventoried 25 gaps (no runtime object / no capability advertisement / no liveness judgment / no task-level identity), of which 6 block #519. (Historical, 2026-10-02; the D55 thesis added per-task container isolation on the runtime axis — that executor has since been removed, and the runtime axis now carries worktree separation only, not a privilege boundary. A dormant container branch survives in the ops smoke helper (`scripts/ops/real-smoke.mjs`): it is not a product path, and removing it is debt.)
4. **single-person repo vs a live project** — Multica v0.6.0 (2026-09-28) is live; the security-fix and protocol-follow long-run risk cannot be refuted, only absorbed through daily use of cairn on real work.
5. **Coordinator** — in a single-person self-use scenario the user is the orchestrator themselves; per the 2026-10-01 ruling it withdraws from the pillar, demoted to "the single entry", survival awaits real closed-loop measurement.
6. **The keep rule is not shipped** — memory (`apps/server/src/services/memory-documents.ts`), the repeat-mistake check proposal (`apps/server/src/services/memory-corrections.ts`, offered through the coordination prompt in `apps/server/src/services/chief.ts`) and retry lessons (`apps/server/src/services/retry-lessons.ts`) are real, and the exam with its protected scorers is real (`eval/**`), but retaining a prompt, skill, routing or tool-use change only after it beats the current harness is a plan (`docs/design/harness-self-improve.md`), not a shipped behaviour. Until it ships, the product's learning is memory, check proposals and retries, and saying otherwise would be an overclaim.
