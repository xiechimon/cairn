## 0. Goal and end state

**"It" = the pacman product itself**, not the Claude Code lanes. The lanes already self-merge today: ADR 0007 has lanes arm `gh pr merge --squash --auto` when opening PRs, and GitHub merges once CI is green. This plan wants the other loop — the pacman instance running on mea, against the `xiechimon/pacman` repo, claiming tickets itself, writing them itself, opening PRs itself, verifying itself, merging itself.

**Graduation criteria (end state, machine-checkable)**:

1. The pacman instance on mea, against `xiechimon/pacman`, lands 5 consecutive `ready-for-agent` tickets with **zero user clicks**: claim → dispatch → plan → build → open PR → grind CI green → three-perspective review + independent verification (verdict bound to the exact patch) → merge-readiness gate all green → squash merge → issue closed → todo `done`.
2. After those 5 merges, main's `check` / `pack-smoke` / `e2e-gate` all green, no rollback within 24 hours.
3. Every PR body passes the `pr-evidence` gate, evidence in `docs/verify/<ticket>/`, raw links pinned to SHAs.
4. The five negative controls all intercepted as expected (§4 P8).

The user's role becomes the line from the video: afterwards, look at what landed on main, spot-check, roll back, promote corrections into gates. This also settles the debt of spec 18 §5 honest-list item 1 ("better" depends on unattended operation coming true).

## 3. Pre-launch rulings (user decisions)

Each entry has a recommendation. The goal session builds only on the rulings fixed here, and stops on any unruled item.

| ID | Question | Recommended ruling | Reason |
|---|---|---|---|
| **D1** | How merge authority is delegated | New ADR 0021 amends ADR 0018's "the merge action stays with humans": project-level `mergePolicy = human \| shadow \| autonomous`, **default `human`**. Under `human` the #1256 hard block stays as is; `shadow` only computes the gate and never merges; `autonomous` has the server merge when the merge-readiness gate is all green | README's selling point is "Gated by design"; the external default is unchanged; pacman's own-use project opts in separately. `shadow` is exactly pstack's autopilot-stack: the same loop, nothing fires, accumulate comparison data before delegating |
| **D2** | Who executes the merge | On the autonomous path the **server** calls the REST merge through `lib/github.ts`, with the `sha` parameter (the head must equal that value for GitHub to merge), squash. The squash message is assembled by the server: the subject takes the PR title in repo-rule form, and the body's last line is fixed as `closes #<the issue number of sourceRef>` | Merge authority is not handed down to the agent machine's `gh` login; the `sha` parameter makes "the verdict corresponds to the exact head" backstopped at the platform layer; the repo rule "the closing keyword goes in the commit message" is guaranteed by code, not by the agent remembering (ladder rung 1 in the video); credentials reuse the team `github_connection` (scope already includes `repo`) |
| **D3** | What the verdict binds to | Bind the **patch digest** `patchDigest` = over the file list of `compare/{base}...{head}` (excluding `docs/verify/**`), take for each file `[status, filename, previous_filename, blobSha, patchSha]`, JSON-encode the tuples, sort, and sha256 them (both ends bound on renames; `patchSha` is the sha256 of that file's patch text — on a conflict resolved keeping this PR's version, the blob is unchanged while the patch changes); the verdict also records `headSha`. Recomputed at merge; a digest mismatch = verdict expired = re-verify | update-branch merges main in; as long as main's new commits do not touch the files this PR changes, the digest is unchanged and the verdict need not rerun (saves tokens); if touched, the digest changes and the verdict is re-verified (the conservative direction); the verifier commits only into `docs/verify/`, which also does not invalidate the verdict; any push that changes code changes the digest and auto-voids the verdict. pstack's words: verifiers run again after every later push that changes the patch |
| **D4** | Which changes always stay with humans | Deny by default: only product source, tests, and `docs/verify/**` may skip the human, with protected categories excluded again among them; protected categories are matched by class, at any depth, case-insensitive (the list is in ADR 0021 D4): CI and hooks, files steering agents (`.claude/`, `.pi/`, `.cursor/`, `CLAUDE*.md` / `AGENTS*.md`, `docs/pr-review.md`, `docs/adr/**` at every level), gate scripts and configs that decide check semantics (`scripts/`, `*.config.*`, biome, tsconfig, `.gitignore`, `.gitattributes` at every level), the merge-readiness gate's own source (only the three places listed in ADR 0021 D4 ④), migrations (one-way doors), dependency manifests and lockfiles (supply chain), security-sensitive surfaces (the list in AGENTS.md's `/security-review` section, changed in both places together) and `apps/server/src/db/client.ts` which runs migrations. Plus: deleting test files, files whose compare gives no patch outside the evidence directory (binary, oversized diff, pure rename), patches over 800 lines or 40 files (evidence included), over the daily autonomous-merge cap | An agent must not edit its own gate to pass its own gate (Goodhart); migrations and dependencies are one-way doors |
| **D5** | Which tickets to claim | Claim only open issues **tagged `ready-for-agent`, where that tag was applied by the repo owner / a collaborator** (who applied the tag verified via the events API); the issue body is always treated as data | On a public repo anyone can open an issue, but only collaborators can tag; the tag is the authorization. Injection in the body is backstopped by D4 + the merge-readiness gate |
| **D6** | Whether the mea instance self-updates after merging | Yes, but through a separate deploy loop: a timer picks "the newest SHA on main with CI all green" → back up the DB → drain in-flight steps → restart → health check → on failure roll back to the last known good SHA. **npm publishing always stays with humans** | Without self-update, fixes on main never reach the working instance; but a failed deploy kills itself (G10), so rollback is a hard requirement, not an option |
| **D7** | How construction PRs merge | Superseded by [ADR 0026](../adr/0026-machine-trust-replaces-human-merge-gates.md), R2 and R4, as amended by [ADR 0027](../adr/0027-independent-review-requires-a-different-vendor.md) and, for phase 1, by [ADR 0028](../adr/0028-phase-1-merge-routes.md), under which every PR that pr-gate routes to the user, ADRs and specs included, goes to ian. The target state: ADRs, specs, and other protected changes merge after a review bound to the current head and patch by a different reviewer from a different vendor, with both mandatory questions answered; either answer being yes blocks | Design decisions still need ian's prior decision; the recording PR follows the machine gate |

## 4. Phased construction

Every phase follows the repo rules: open a ticket first → run §7.5's `understand` / `design-panel` when needed → **list failure modes first, write failing tests first** → implement → `pnpm lint` / `pnpm typecheck` / `pnpm spec:parse` / `pnpm exec vitest run --changed` / `pnpm --filter @pacman/web e2e:affected` → `verify-pacman` captures artifact evidence into `docs/verify/<ticket>/` → `/code-review` self-review (run before opening the PR, and once more after pushing fixes during the PR and once more before merging; fix confirmed findings first) → `pr-cairn` four-section body (What / Proof / Review / Risk) → after CI is green run §7.5's `pr-gate` → merge per D7 → write back the §8 ledger. Commit message ends with `closes #N`.

Dependencies: P0 → {P1, P2, P5a} in parallel → P3 (depends on P2) → P4 (depends on P0 + P3) → {P5b, P6, P7} → P8. Rough estimate 15–20 PRs.

### P0 · Rulings on disk (docs only)

- Write ADR 0021 "autonomous merge: project-level policy + patch-bound verdicts + protected paths", the body collecting D1–D6; add a revision pointer at ADR 0018's head (the ADR body is not edited; per repo rules a new ADR overturns).
- Open one issue each for P1–P8, the ticket body listing failure modes and acceptance items, backfilling the ticket numbers into the §8 ledger.
- **Acceptance**: ADR 0021 merged by the user (D7).

### P1 · Verification CLI convergence (the video's Control Glass)

- Converge the launch / doctor / drive / capture / cleanup scripts under `verify-pacman/scripts/` into one entry: `node .claude/skills/verify-pacman/scripts/vp.mjs <launch|doctor|list|drive <feature> [case]|capture|archive <ticket>|links <ticket>|cleanup>`.
- Each `features/*.md` gains "how the user gets there" (route, shortcut, which element to click) and the corresponding `drive` subcommand name — the other half of the video's feature map.
- `archive <ticket> --from <evidence-dir>` copies the named directory under `.claude/verify-evidence/` into `docs/verify/<ticket>/` (copy only; refuse if the destination exists, ADR 0015); after commit and push, `links <ticket>` prints raw links pinned to SHAs (previously this step was done by hand; not listed in §2.2 but it was a break point in the evidence chain). Raw links only resolve after the commit is pushed, so copy and link-printing are two subcommands.
- Add a static gate: any new script matching `drive-\d+` goes red (lifting "one script per ticket" from rung 5 to rung 2). **The existing drive scripts are not deleted** — ask the user before deleting code that "looks intentional" (CLAUDE.md).
- **Failure modes**: subcommand behavior drifts from the old scripts; feature-map selectors go stale (check selectors against the running app); port collision with another lane (keep 8791/5273 and `VERIFY_*` overrides).
- **Acceptance**: a fresh session given only `vp.mjs --help` and the feature map end-to-end verifies 3 existing features and archives evidence; negative control: deliberately plant a regression and the CLI drive catches it.

### P2 · GitHub PR surface + merge reconciliation

- `lib/github.ts` gains: read PR (`state` / `merged` / `draft` / `mergeable_state` / `head.sha`), `update-branch` (with `expected_head_sha`), merge (with `sha`), commit status, `compare` file list, PR review and comment reads. Endpoints and parameters verified per CLAUDE.md's external-API discipline before construction, not from memory.
- **Reconciliation loop**: `ci-loop`'s candidate set widens from `building` to `building | review` (github-shape builds with a `prNumber`):
  - PR already merged (whoever merged it) → todo `done`, a system line lands naming the merge SHA, split waves advance;
  - PR closed without merge → todo `failed` + reason;
  - BEHIND → `update-branch` (under the `human` policy, only prompt, do not act);
  - DIRTY → append a `[merge-conflict]` build step on the same branch (merge main in and resolve, force-push forbidden, same-branch continuation rounds per spec 23).
- check-runs are now read by **head SHA**, not branch ref; neutral / skipped / cancelled no longer all count as green (only the required-check list counts).
- **The manual merge path is also fixed**: the github-shape "finish + merge" becomes the server merging via API (with `sha`), no longer relying on the LLM obeying the prompt line `请把本会话分支的改动合并到默认分支`. This is a defect fix for all users, independent of autonomy.
- Fix G9: first write a failing test that reproduces it, then change the review gate's wake copy.
- **Failure modes**: GitHub 429 / 404 / network error → fail-open, retry next round (ci-loop discipline); a human advances the phase within the network window → re-read before writing; the same PR pointed at by two builds (#1217 guard); merge returns 405 (not mergeable) → re-evaluate next round, no retry bombing.
- **Acceptance**: integration tests with a fake GitHub cover the four states; measured on mea: "manual merge on the GitHub web page → the card turns done within 1 minute".

### P3 · Merge-readiness gate (patch-bound verdicts + automated review / verification + chief go/no-go)

- Verdict schemas (the review / verify / go-no-go three kinds) gain `headSha` and `patchDigest`; when the server receives a verdict it computes the digest per D3 and stores it.
- The verifier becomes **read-only on code**: it may commit evidence only into `docs/verify/<ticket>/`; at finish it validates "commits after the verdict's head touched only the evidence directory", else the verdict is void.
- When `mergePolicy ≠ human`, entering `review` automatically dispatches the three-perspective review + verify (the verify slot defaults to the Verifier persona), no longer waiting for a manual click.
- Implement ADR 0018's chief mini-merge step: with the three reviews + the verification verdict in and digests matching, chief holds the full context (three reports + diff + verification evidence) and issues `{go, reasons, headSha, patchDigest}`.
- Blocking findings now go through a **same-branch repair round** `[review-fix]` (same form as `[ci-fix]`, 2-round cap), no longer always back to `planning` (G8); cases needing a plan change still go back to replanning, but only after chief judges so.
- The gate's source lives only in `apps/server/src/services/merge-gate/**`, `packages/shared/src/records/merge-gate.ts`, and `apps/daemon/src/merge-decision.ts`: ADR 0021 D4 ④ and pr-gate's protected list judge by these three places; gate code placed elsewhere would be auto-merged as ordinary product source.
- The pure function `mergeReadiness(build) → {ready, blockers[]}`, whose blockers cover at least: policy is `human`; autonomy paused; the PR is not open or is a draft; `mergeable_state ≠ clean` (`has_hooks` counts as `clean`; `unstable` is passed only when everything unpassed is the gate's own statuses) or a non-required check failed; the required checks not all green at the current head; `pr-evidence` not green; a verification verdict missing / failed / digest stale; any review with a blocking or a stale digest; chief has not gone or its digest is stale; a D4 protected path or size cap hit; tests deleted; the todo's `sourceRef` resolves to no issue number (D2 cannot assemble `closes #N`); the body's raw evidence links do not point at this branch's `docs/verify/<ticket>/` (the AGENTS.md pre-merge verification rule).
- The result is written as a commit status `pacman/merge-gate` on the head SHA (the description carries the first blocker), displayed same-source in the task detail page and chief's new tool `merge_readiness`. **Not added to branch protection's required checks** — adding it would lock the lanes and manual merges too.
- **Failure modes**: a verdict lands after the push (race) → compute the digest from the verdict's own `headSha`, not from the head at receipt; the compare file list truncated (over the API's per-call cap) → rule `human` directly; one of the three perspectives times out → no go is composed; chief's go conflicts with a blocking → blocking wins.
- **Acceptance**: unit tests cover both legs (true/false) of every blocker; integration tests demonstrate "after update-branch the digest is unchanged and the verdict stays valid" and "after changing one line of code the verdict is void and re-verified automatically".

### P4 · Autonomous merge (policy + executor + brakes)

- Migration: `project.mergePolicy` (default `human`), team-level `autonomyPaused`, `maxAutonomousMergesPerDay` (default 10).
- Merge executor (scheduler family, 60s): `autonomous` and `mergeReadiness.ready` → REST merge with `sha`; at most one merge per repo per round (under `strict: true` the other PRs turn BEHIND, handled by P2's update-branch; if the patch digest is unchanged the verdict does not rerun). `shadow` only writes the status and a "should have merged at <sha>" system line.
- After merge: P2 reconciliation pushes the todo to `done`; the commit message's `closes #N` closes the issue; `scripts/cleanup-merged-branches.sh` cleans the branch.
- **Brakes**:
  - Emergency stop: UI switch + REST + `pacman autonomy pause`, effective from the next round;
  - Circuit breaker: a main commit produced by an autonomous merge turns CI red → autonomy auto-paused + a rollback PR opened (the rollback PR itself goes `human`) + notification;
  - Daily cap;
  - Under the `human` policy chief's `merge_builds` stays hard-blocked; under `autonomous` chief too can only "request merge", still passing `mergeReadiness` in the end — there is no entrance that bypasses the gate.
- **Failure modes**: the merge succeeds but the response is lost → next round's reconciliation sees merged and finishes, no re-merge; two executor instances concurrent (overlapping server restarts) → deduped by the `sha` parameter + an in-DB merge lock; the emergency stop and the merge land in the same second → read the switch one last time before merging.
- **Acceptance**: the user merges this phase's PR (D7). On the rehearsal repo, `shadow` / `autonomous` each run through once; the emergency stop and the circuit breaker each rehearsed once, evidence archived.

### P5 · Autonomous intake + internalizing the repo rules

- **P5a intake**: issue polling (5 minutes, scheduler family; opt-in, only enabled with `CAIRN_ISSUE_INTAKE` as `1` / `true` / `yes`, default off), filtered per D5 (the tag has no unlabeled after its newest labeled event, and the tagger is triage or above on the repo; a labeled event carrying `performed_via_github_app` — tagged via a GitHub App — is not claimed. This can only recognize GitHub Apps: tags applied with an OAuth App token or a PAT look on the event exactly like that account tagging by hand, and cannot be intercepted. OAuth App tokens include the token `gh auth login` obtains for itself and the team's GitHub connection token (exchanged from a self-registered GitHub OAuth App) — pacman hands it to git with the step (git's own hooks also run in this environment), and to the repo's `.agents/setup` / `.agents/resume` hooks; any agent step that can change those hooks can get it; pacman's agent steps can also directly use the machine's logged-in `gh`. Both paths can tag as the corresponding account and feed the intake), import (`sourceRef` 409 dedupe) → `orchestrateTodo`; a project-level in-flight cap (default 3). After labeler validation and the cap check, the poller reads linked pulls (issue timeline + GraphQL closing references): open same-repo links skip with the PR number logged; when link evidence shows exactly one same-repository GraphQL closing reference and that pull request is merged, the poller closes the GitHub issue on GitHub and does not import it (this GitHub write is separate from transitioning an already-imported Cairn task to `closed` during reconcile); other merged or ambiguous link combinations defer without import; unverifiable link evidence skips the candidate; those link-read failures stay candidate-local and do not stop the team. The webhook's `pacman` trigger (#1459, effective whether or not intake is on) follows the same D5 and the same cap: the tagger is taken from the event's `sender`, imported only if triage or above on the repo (same permission read and same cache as the poller), and the current in-flight count includes imports still waiting on the GitHub read; no sender, the sender is not a GitHub account name, the sender is below triage, the permission read fails or rate-limits, the project is full, the team has no usable token, the project's stored githubRepo is not owner/repo, or the issue is not found on GitHub — none of these import; a log line records the reason code, and all reply 202 (a rejection does not feed GitHub retries; the three tagger-permission-class rejections all reply the same one line, never saying which kind or which account. This only removes the permission conclusion from the reply; whether the import proceeds afterwards still reveals whether the tagger qualifies; remediation of a leaked URL token is still revocation). The webhook payload has no `performed_via_github_app`, so a `pacman` tag applied via a GitHub App still imports; left to a later phase. chief's `issues` / `pull_requests` / `workflow_runs` become real reads.
- **P5b PR feedback backflow**: under `autonomous`, human or bot review comments on the PR enter a same-branch repair round (same form as `[ci-fix]`); replies and resolution are done by the repair round's agent with `gh`.
- **Internalizing the repo rules**: measure once in a daemon worktree — `AGENTS.md` / `CLAUDE.md` natively read by the engine (spec 24), `.claude/skills/pr-pacman` and `verify-pacman` usable, `pnpm lint` / `typecheck` / `spec:parse` runnable, the body passes `pr-evidence`. Whatever does not hold is patched into the run brief (spec 24) or the Implementer persona copy. The daemon `commitAll`'s in-branch commit form is `<kind>: <title>`, different from the repo rule `<scope>(<ticket>): <subject>`. The message squashed into main depends on who initiates the merge: the autonomous path takes the D2 server-assembled message; clicking merge inside pacman also merges via server REST (#1403); when no message is passed, GitHub follows the repo settings (single commit: that commit's message; multiple: the PR title plus each commit's message), so a single-commit PR carries `<kind>: <title>` into main. Hence the alignment is server-side: the REST merge uniformly passes `commit_title` (the PR title) plus D2's body last line; in-branch commits are unchanged; the PR title itself is aligned to the repo rules by P5.
- **Failure modes**: the same issue imported once each by webhook and poller (409 backstops, landed as a test); an open same-repository linked pull request (timeline or GraphQL closing references) → skip that candidate, log the PR number, re-check on later sweeps; a merged linked pull with complete evidence of exactly one merged closing reference → close the unclaimed GitHub issue with `state_reason: completed` without importing (failures stay on that candidate and retry on later sweeps); other merged or conflicting link shapes → defer without a GitHub close write; incomplete, conflicting, or unreadable link evidence → skip that candidate only; a rate limit on timeline or closing-pull GraphQL for one candidate skips that candidate and continues with later candidates and projects; polling saturates GitHub rate limits → the poller's own reads (candidate list, events, permission, issue state) hitting a limit (429, or a 403 carrying rate-limit signals) stop all of that team's remaining reads this round (half-read reconciliations and lists wait for the next round), the next round reads as usual, one log line (with the reset time if GitHub gave one); `importGithubIssue`'s own reads hitting a limit during import count only as that one import failing (one line logged), and the round continues judging the next candidate; an issue untagged after dispatch → do not withdraw mid-flight, but claim no new tickets; a claimed issue closed on GitHub → reconcile only the cards the poller claimed: at import the createdBy records the Agent bound to this team's chief, and reconciliation only recognizes github-issue cards whose createdBy equals the Agent currently bound to this team's chief (manually imported and webhook-imported cards have the seed user as createdBy, untouched; teams with no bound Agent to chief do not reconcile; after rebinding, cards claimed before the rebinding are no longer reconciled); only when this process sees it go from open to closed, and the closer of the newest closed event is triage or above on the repo, does reconciliation finish it as `closed` (seen-first-as-closed and self-closed by the external author stay untouched); review cards and cards whose build delivered a PR are not closed by intake, and when a merge carries a closing reference and closes the issue, the finish is not `closed`: cards that delivered a PR during review are finished by P2's PR reconciliation (segment 1 #1414 merged), the rest are advanced by ci-loop or wait for a human; a split card's parent is untouched while any child card is not done / closed (when all children are done the parent auto-closes as done).
- **Acceptance**: on the rehearsal repo, tag → PR out with no human intervention, the body passes `pr-evidence` first try.

### P6 · Correction loop + gardening

- New in-repo skill `.claude/skills/correct/`: input one correction (an autonomous merge rolled back, a human rejecting at the review gate, a mis-release during `shadow`), grade it per the video's ladder (codebase > lint/CI > rules > skills > review scorecard), prefer the highest feasible rung, and output a ticket tagged `correction`; a new gate must use that real mistake as its negative control (pstack same rule).
- Triggers: rollback, rejection, the same class of blocking finding appearing a second time, a build that went through ci-fix and finally turned green → open a correction ticket (the ci-fix turn-green is recorded by the poller as a pending-attribution event; a `correction` ticket is created after dedupe by failed-check category; ticket-opening failures retry without blocking review), and the ticket runs the autonomous loop as usual (but gate edits are a D4 protected path, merged by humans).
- Gardening: a weekly scheduled task — lower the ratchet baselines (ui-debt, lint-warning-cap, feature-map staleness baselines), clean dead classes (dead-class-gate), refresh the feature map; each item is an ordinary ticket on the same loop.
- **Acceptance**: run one real misjudgment from the `shadow` period through "correction → new gate → negative control red → green after the fix".

### P7 · mea self-deploy and rollback

- `scripts/ops/deploy-mea.sh`: the input is a SHA on main; verify that SHA's required checks all green → `pnpm install --frozen-lockfile` → build web → back up the DB per `docs/ops-db-backup.md` → drain (stop claiming new steps, wait for in-flight steps to finish, with a cap) → restart the systemd trio → health check (server API, daemon heartbeat, one smoke card on the rehearsal project) → on failure roll back to the last known good SHA and restart → land one deploy record line.
- A systemd timer every 30 minutes picks "the newest SHA on main with required checks all green", decoupled from the merge executor.
- Versions with migrations: the migration itself is a D4 protected path (human-merged); a backup is forced before deploy.
- **Failure modes**: the deploy breaks the daemon and it can never fix itself → the rollback is done by the deploy script itself, not by pacman; the drain never finishes → after a timeout, give up this round's deploy rather than hard-kill; the rollback target itself is broken → stay on the current version and notify.
- **Acceptance**: on mea rehearse one deliberately failed deploy (a SHA whose health check must fail), auto-rollback, evidence archived.

### P8 · Graduation (dry run → rehearsal repo → this repo)

1. **shadow**: `xiechimon/pacman` switches on `shadow`, at least 10 PRs, recording "the gate's verdict vs the user's verdict" for each. Passing the bar: **zero mis-releases** (the gate says go, the user finds a blocking problem); every over-block records its reason and enters P6.
2. **rehearsal-repo autonomous**: `xiechimon/pacman-1150-dogfood` runs 5 tickets, plus five negative controls:
   - a defect-planted PR → verification fails → no merge;
   - a PR touching a protected path → switched to `human`;
   - one line of code changed after verification → verdict void → auto re-verify;
   - emergency stop → no more merges within one round;
   - main turns red after a merge → circuit-breaker pause + rollback PR.
3. **this-repo autonomous**: `xiechimon/pacman` switches on `autonomous`, closing out per §0's graduation criteria.

## 7. Goal-mode operations manual

### 7.1 What `/goal` is

A Claude Code built-in command, `/goal <condition>`: sets a session-level completion condition; at each round's end a small model checks the conversation log against it ("not achieved / achieved / impossible") and continues to the next round while unachieved. The judging model **runs no commands and reads no files, seeing only what appeared in the conversation**, so the condition must be provable from the output; with no tool calls for several consecutive rounds it stops automatically; the condition caps at 4000 characters. Docs: https://code.claude.com/docs/en/goal . It does not change the permission mode — for unattended operation you must also turn on auto mode (https://code.claude.com/docs/en/permission-modes ).

### 7.2 Where to run, how to run

- **Recommended on the local machine (Mac)**: it needs `gh` login (lane merges, update-branch) and ssh to mea (P2 field test, P7, P8). A cloud session has no `gh` and cannot reach mea inside the tailnet; it can only do P6's code surface, and P7 / P8's field tests return to the local machine.
- Create an absolute-path worktree per repo rules: `git fetch origin main && git worktree add --detach "$(git rev-parse --show-toplevel)/.claude/worktrees/bootstrap" origin/main`, start `claude` inside it, confirm the status bar shows auto mode, then paste the prompt from §7.3.
- Headless form: `claude -p "<full text of §7.3>" --permission-mode auto --max-budget-usd <cap> --output-format stream-json --verbose`. While out, watch progress from the phone via Remote Control; the merges D7 leaves for the user are clicked on GitHub mobile.
- One goal run goes through many context compactions; progress across compactions relies on the §8 ledger (committed in the repo), not conversation memory. To run in segments, replace "all complete" in §7.3 with "P<n> complete" — one goal per phase.

### 7.5 Workflow orchestration (authorized by the user 2026-10-20: "use workflow to join the plan")

A workflow = an orchestration script (JavaScript) executed by the Workflow tool: it deterministically schedules a batch of subagents per the script (parallel, pipelines, structured outputs), runs in the background, and notifies the main session when done; interrupted runs resume by runId, and finished agents come straight from cache. Division of labor: whole-phase construction (writing code, running gates, opening PRs, waiting on CI) still proceeds serially in the main session; the workflow only takes over well-scoped spreads, and the main session reads the result and decides the next step.

Capacity facts: the cap on concurrently running agents = min(16, CPU count − 2), which on this 4-core container is 2, the rest queue; this session's sizing guidance is at most 10 agents per workflow (`/config`'s Dynamic workflow size can adjust). Hence the cloud variant constructs phase by phase in order, no parallel starts.

| Workflow | When it runs | Shape | Agent count | Output and use |
|---|---|---|---|---|
| `pr-gate` (core) | After each PR's CI is all green, before arming auto-merge or asking the user to merge; rerun on every patch change | Five dimensions find problems in parallel → blocking findings each get 2 rebutters dispatched in reviewer-submission order, at most 4 for the whole run (i.e. at most two findings can be rebutted; from the third on none are dispatched, kept as is, go is false) (default judged "does not stand"; withdrawn only if both answer and both judge it does not stand; any absence keeps it) → summary. Rebutters also report the headSha they read; reading a different head does not count as an answer. D4 is judged mechanically by the script (deny by default): paths outside the auto-mergeable set and protected paths are matched against the caller-passed `changedFiles`, unioned with what the reviewers report; deleted test files, binary files outside the evidence directory, and patches over 800 lines or 40 files also switch to `user`. The security dimension additionally runs the file list itself; paths the caller failed to pass (e.g. rename sources when `--no-renames` is missing) make go false and join the matching the same way. Five dimensions: correctness and regressions; repo rules and seam discipline (`docs/pr-review.md`, biome seams, trailing marks); tests and failure-mode coverage; security and D4; evidence authenticity (in an independent worktree detached at headSha, rerun the at-most-three narrowest commands referenced by the PR Proof section, verify the raw permanent links, distrust the PR description) | 5 + at most 4 rebutters, at most 9 total | `{pr, ticket, headSha, go, blocking[], suggestions[], protectedPaths[], mergedBy, humanReasons[], missing[], shaMismatch[], unlistedFiles[], skepticsMissing, checked}`. **Only with go and headSha equal to the PR's current head does the main session arm auto-merge or ask the user to merge**; a no-go's blocking is repaired on the same branch and rerun. This is the manual equivalent, during construction, of P3's in-product merge-readiness gate: the code-writing main session does not approve its own merge |
| `understand` | At the start of P2, P3, P4, P5 | 3–4 read-only agents each read one subsystem (server services, daemon runner, shared records, related tests) → structured map + failure-mode candidates | 3–4 | Feeds "list failure modes first"; the summary goes into the ticket body |
| `design-panel` | Before P3 (patch digest and readiness gate) and P4 (executor and brakes) are coded | 3 independent designs (minimal-change-first / risk-first / testability-first) → 2 reviewers score → main session synthesizes | 5 | The chosen design goes into the ticket body and the PR's Risk section, plus Upstream when it adds a mechanism |
| `drive-inventory` | At the start of P1 | Pipeline: each script under `verify-pacman/scripts/` is classified (which feature it belongs to, which subcommand it folds into, whether stale), low-reasoning tier | In batches, at most 10 at a time | The convergence map goes into P1's ticket body; **classify only, delete nothing**, deleting existing scripts still asks first per CLAUDE.md |

Rules:

- No `Date.now()` / `Math.random()` in scripts (they break resumption); timestamps pass in through `args`.
- The pr-gate verdict also carries `scriptSha256`, the sha256 of the `.claude/workflows/pr-gate.js` copy that produced it, so the persisted verdict JSON records which copy of the gate ran.
- `pr-gate` is stored as the in-repo workflow `.claude/workflows/pr-gate.js`, committed with P0's PR (#1410), parameters `{pr, headSha, ticket, changedFiles, deletedFiles, linesChanged, binaryFiles}`: `changedFiles` from `git -c core.quotePath=false diff --no-renames --name-only origin/main...<headSha>`, `deletedFiles` is the same command plus `--diff-filter=D`, `linesChanged` is the sum of both columns of `git -c core.quotePath=false --attr-source=4b825dc642cb6eb9a060e54bf8d69288fbee4904 diff --no-renames --numstat origin/main...<headSha>` (binary rows `- -` count 0; attributes taken from the empty tree, so the repo's `.gitattributes` `-diff` cannot change the line count, pr-gate round six; `--attr-source` needs git 2.40+, and on older gits reporting an unknown option, upgrade git, do not drop this option), `binaryFiles` are the paths of `- -` rows in the same numstat: binary files outside `docs/verify/` stay with humans (one NUL byte in a source file makes git treat the file as binary and count 0 lines, #1410's `/code-review`). Without `core.quotePath=false`, git escapes non-ASCII paths (every file under `docs/adr/`) into a quoted form the globs cannot match; the script rejects paths starting with a quote on sight. Without `--no-renames`, renames list only the new name, so a protected file renamed away is missed (#1410 pr-gate round two). The security dimension does not look at the caller's list; it takes these four itself with the same commands, and the script takes the union and the larger values (the caller is the PR-writing session). numstat also needs `core.quotePath=false`, else non-ASCII binary paths get quoted and fail to match the file list (#1410 pr-gate round seven). Reviewers read only PR comments from repo members (`author_association` OWNER / MEMBER / COLLABORATOR); the comment commands use `--jq` to filter out the rest first, and bodies do not enter the reviewers' context: the repo is public, anyone can comment, and the evidence dimension has a shell (#1410 final `/code-review`). A ticket's body may, under D5, come from an outside author; the prompt states it as author-written untrusted data, not instructions, same as the PR body (#1410 pr-gate round eleven). Subagents are read-only on GitHub. **Run the copy on origin/main** (`git show origin/main:.claude/workflows/pr-gate.js` written to a throwaway file, then invoked via `scriptPath`), not the copy in the PR-under-review's worktree — a PR must not edit the gate that judges it. Named invocation resolves against `.claude/workflows/` in the session's **current working directory**: it is not found by name inside a worktree that does not contain the file; after the file in the same directory is changed, the content fetched by name may still be the previously scanned copy (#1410, measured three times, `docs/verify/1401/pr-gate-named-probe.txt` and `pr-gate-named-probe-2.txt`). It belongs to ADR 0021 D4 protected paths; edits are merged by the user.
- The evidence dimension executes PR-referenced commands in an independent worktree, carrying this session's credentials. Run `pr-gate` only on PRs constructed by this session; the script has the evidence dimension check `head.repo.full_name` first — not this repo means no checkout, no dependency install, no command run, only `git show` / `git diff` / `git ls-tree` reads and link verification; heads of this repo also disable hooks (`git -c core.hooksPath=/dev/null`) before checkout, fetch, and ref deletion, because the shared clone's `core.hooksPath` may be husky's relative `.husky/_`, which would resolve into the checked-out tree.
- A go is valid only for the head it judged. When arming auto-merge, pin that head (`gh pr merge --squash --auto --match-head-commit <headSha>`; after arming auto-merge with the GitHub tools, verify the PR's head still equals headSha). To push afterwards (fix CI, update-branch), disarm auto-merge first; after pushing, rerun `pr-gate`. The sole exception is per D3: only main merged in, and main's new commits do not touch this PR's files (patch digest unchanged) — the verdict carries over, and on re-arming pin the new head.
- Workflow subagents get CLAUDE.md injected the same way; read-only on GitHub (view PRs, pull commits); opening PRs and merging are done only by the main session.
- Each workflow's conclusion is paraphrased as one line in that round's ledger summary (who blocked what, and why).
