## 1. 主张（#516 判决终稿，逐字）

> **开源可自托管的世界里，todos 的语义核心（两道硬闸 + 有牙齿的 AI 审核 + 版本化方案文档）只有 pacman 在做——Multica 有源码没这套语义，todos 有这套语义没源码。**常驻编排者（Chief）作为闸的既定消费者存在，存废由真闭环实测裁决。

册内术语（不进 `CONTEXT.md`——那里只管产品域实体）：

- **硬闸**：人强制在场的固定停留点，共两道——Confirm（任何代码被碰之前，看方案）与 Review（发布之前，看 diff）。闸是 phase 机的一部分（服务端边表强制流转），不是状态标签。
- **有牙齿的 AI 审核**：审核者的 blocking verdict 直接驱动 `review→planning` 自动回流（#330 回路）——能挡住合并，不只是一条评论。
- **版本化方案文档**：Plan / Changes 类文档，可逐版对比，是闸上「看」的对象。
- **语义轴 / 运行轴**：语义轴 = 任务怎么流转（闸、审核、文档、状态机）；运行轴 = 任务在哪跑（runtime、daemon、自托管部署）。
- **自用第一**：见 §2。

**维护触发**：本主张的稀缺性有时效——source-available 阵营（Multica 等）加闸、或 todos 走向开源/自托管，主张当天过期。触发即重写本节与 README Why 的主张句（README 为去点名短版，过期时维护成本低），不留挂死主张。

## 2. 判据：自用第一

所有取舍先问「我自己真用得到吗」，再问「是否差异化」（#515，2026-09-30 裁）。单人自用场景里市场验证权重低——51k star 证明「无闸有市场」，不构成「闸无价值」的证据。

配套纪律（#515 硬约束）：**参考实现优先，不凭空造**——任何新机制先调研到跑得通的真实实现（Multica 开源仓、todos 官方文档、Craft Agents、pi SDK），找不到就标 `[推断]` 并降级。落到两轴上：语义轴的机制不拿 Multica 当参考（它没有）；运行轴的机制不自己发明（它有开源实现可读）。

## 3. 两轴

### 3.1 语义轴：对齐 todos 三点核心

| 核心件 | pacman 落点 | 对照 |
|---|---|---|
| 两道硬闸 | Confirm / Review 两个 phase；流转只走服务端边表（`apps/server/src/services/phase.ts:17` `PHASE_TRANSITIONS`，REST / MCP / chief 工具写面全过 `assertPhaseTransition`），agent 零状态自写通道 | Multica：issue 状态由 agent 经 CLI 显式写，`in_review` 是状态不是闸门；todos：两道闸即 phase 本身 |
| 有牙齿的 AI 审核 | blocking verdict → `review→planning` 自动回流（#330）；审核材料 = 方案 + 变更 diff + 只读检出，与人看同一条计算路径（#511 修掉材料断链） | todos：内置 AI 审核但明说评审者无否决权（「The review does not decide anything」）；Multica：无内置（官方教程自建 @Reviewer，结论只是普通评论） |
| 版本化方案文档 | plan 卡进 confirm 闸，「看方案再放行」有物可看、可逐版比 | Multica：无对应物（plan 走 issue 描述与评论） |

### 3.2 运行轴：对齐 Multica runtime 模型

runtime = 一台电脑 × 一个 CLI 工具；看板 + agent 当经办人 + daemon 当 runtime + 自托管单数据根。多机执行、runtime 侦测、活性判定、任务级身份照 Multica 的开源实现读（r10 全解、r11 差距盘点），不自造。

### 3.3 不对齐 Multica 哲学（三条）

无硬闸 / status-first / daemon 不当沙箱边界（「Treat every run as unsandboxed」）。选了等于删掉自己的差异化，做成「更弱的 Multica」。

### 3.4 Chief：闸的既定消费者

Chief 撤出差异化支柱（#516 判决，2026-10-01；早于它的 #515 两轴表述含 Chief、#521 仍写「差异化四件」，均以本条为准，同批更正）。它作为两道闸的**既定消费者**存在——谁替你盯闸、派活、收结果；**存废由真闭环实测裁决**。单人自用场景里用户自己就是编排者，Multica 的「人指派 + squad leader 路由」覆盖同一需求；Chief 不能自醒，实际形态是委托面板 + 看门狗。判据与 §5 诚实清单第 2 条同源：真闭环实测里数 withPlan 分布与 Chief 实际使用率。

### 3.5 形态原则：一个总管，代码必过闸（2026-10-24 用户裁决）

起因：对照 EverMind Raven（总指挥在内存里画任务依赖图、自检后直接开跑、上游产出直接递给下游、聊天入口）后，用户问「不需要 PR 的本地用户要不要换成 Raven 形态，有看板走看板、没看板走 Raven」。裁决：不按「有没有看板」切形态，把形态拆成三件互不相干的选择：

| 选择 | 谁定 | 取值 |
|---|---|---|
| 入口与观看面 | 用户 | 看板；IM / 命令行（将来，见 §4 C 类）。全部共用同一个 Chief、同一套闸，看板是任务图的显示面，不是形态开关 |
| 产出类型 | Chief 按任务判 | `code`：过两道硬闸、AI 审核、验证；`info`（调研、报告、评测输出）：不碰仓库，成果直接递给下游卡（#1626） |
| 代码落地方式 | 项目形态 | `githubRepo`：开 PR，按 ADR 0021 合并；`localPath`：不开 PR，同一套判定在本机合并（#1625） |

约束：

- 产出是代码就过闸，与入口、是否开 PR 无关。「没看板就不过闸」等于把 §1 主张的三件核心件对一部分用户拿掉，做成更弱的 Raven，不采纳。
- 闸是 phase 机的停留点，放行者按项目策略可以是人，也可以是确定性检查器（ADR 0021 的合并就绪闸、#1623 的拆解检查器）；默认值一律是人，与 ADR 0021 D1 同口径。
- 同类对照（2026-10-24）：Vibe Kanban、Conductor 的本地 worktree 形态最终都靠 PR 落地，Raven 的编码专员无仓库级合并闸。「本地仓库、不开 PR、合并前有闸」无现成实现。

施工票：#1623（拆解检查器放行即自动开跑）→ #1625（local 形态自动合并）→ #1626（信息类快车道）；#1624（子卡注入前置交付摘要）与 #1623 并行。IM 入口与外部 agent 接入等 #1607 调研结论。

## 4. 不做什么（#515 Out of scope 固化）

- 付费三件套（built-in models 网关 / cloud sandbox / 订阅计费）——02 册排除项，继承。
- Squad 对象——Chief 的子集，且明说「不提高并发、不合并 agent」；只抄它的唤醒规则表，不引进对象。
- Chief 自主派活——先要「关机不掉链子」，不要「关机还在自己决定」。
- Gantt 视图 / 多 workspace / 第三方 Git（Forgejo / Gitea / GitLab）——自用场景无意义，直接杀。
- 直追 Multica 的集成面广度（IM 五件、desktop app、iOS）——记为「将来可能的 C 类」。
- todos.dev 基线重拍与像素对拍——06 册 D1 已解除对拍义务。

（Multica 哲学三条见 §3.3，不入本节。）

## 5. 诚实清单

#516 五条（主张证伪不了的部分）：

1. **「更好」依赖无人值守成真**——闸的价值命题（排队走人、回来只看两个点）与运行轴（常开机器夜跑）互为前提；真闭环实测不通、人在场盯着跑时，闸就只是啰嗦。
2. **withPlan 已量——绕过主导（2026-10-05 #892 实测）**——直执行跳 confirm 是内建能力（`withPlan=false`），看板拖拽也能绕过漏斗；实测（本机 28 build / 17 done 卡）：直执行 39%（chief 派发 8/8 全直执行）、confirm 闸 13 次进闸仅 3 次按确认、review 正门放行仅 1 次、15/17 done 卡经看板手动改相落地（两闸全跳）、版本化方案文档 0 行。「橡皮图章」未出现（仅有的 4 次人按闸 dwell 都实质），但「绕过」成立——退化形态实为「两道闸 + 一条人人走的侧门」而非「一道闸 + 一个仪式」。数据与改进票建议：`docs/research/892-gate-usage-measurement.md`。
3. **运行面目前是欠账**——#518 盘出 25 条差距（无 runtime 对象 / 无能力广告 / 无活性判定 / 无任务级身份），其中 6 条阻塞 #519。差异化主张目前只在语义面成立。
4. **单人仓 vs 活项目**——Multica v0.6.0（2026-09-28）是活的；安全修复与协议跟进的长跑风险反驳不了，只能以自用第一消化。
5. **Chief**——单人自用场景里用户自己就是编排者；按 2026-10-01 裁定撤出支柱，降格为「闸的既定消费者」，存废等真闭环实测。

#519 真闭环实测欠账（2026-10-02 实测，2026-10-03 修票合入后三条全销；修票逐条销账时更新本节）：

- **AI 审核五连败**（B-C9 `streamBodyTimeout` 540s 步级硬顶 / B-C13 审核判定提取被尾部工具调用击穿）——实测时审核闸由人肉审 PR diff 代替。已销：B-C9（#711 body 臂事件重置 + 超时文案指名真凶）、B-C13（#713 判定提取从尾向头跳过纯工具调用消息）。
- **产品内合并路锁死**（B-C17 failed 相位死锁，merge API 409）——实测时合并动作由 gh CLI 手动执行。已销：B-C17（#716 failed→review 条件边 + merge / 只重跑审核两出口共用恢复闸）。
- **确认闸方案文档为空**（B-C10）——实测时 confirm 实点，但闸上无物可看。已销：B-C10 / B-C11 / B-C14（#719 产物闸：plan 步无 plan 行不进 confirm，build 步零改动不进 review）。
