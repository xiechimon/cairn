# 20 · Attachment Reclaim Strategy (issue #759)

> Strategy-first document: this ticket rules the semantics first, then lands the code. Numbers each carry their reason; an implementation deviation must revise this doc back.

## 1. Facts (measured, not inferred)

- `apps/server/src/services/attachments.ts` has no GC / prune / unlink /
  retention / orphan in the whole file (grep zero hits) — the storage root
  `<dataDir>/attachments/<teamId>/<id>.<ext>` only grows.
- The token `![name](attachment:<key>)` is persisted in task bodies: `todo.spec`
  (text), `message.content` / `chief_message.content` (json), `steer_pending.content`,
  `plan.content`. The token is referenced by already-stored content ⇒ the
  attachment is data, not cache — must not be moved to /tmp (a restart breaks
  the whole chain into dead links, and silently).
- The web write-side token is constructed only after the upload 201
  (`apps/web/src/api/attachments.ts` `attachFile` three steps' end) — the grant
  only lands a `pending` row and produces no reference. The grant token carries a
  5min TTL (`ATTACHMENT_GRANT_TTL_MS`): after expiry that row can never reach
  `ready`.
- The daemon-side `<PACMAN_HOME>/step-attachments/<stepId>/` (#736) is a
  materialized copy: regenerated by downloading the original attachment from the
  server (`resolveStepImages`), the regeneration premise = the source row still
  exists + the step text still contains the token + the machine is online.
- The daemon already has an isomorphic precedent: orphan worktree reclaim (run
  once at startup + a daily cadence, TTL 7d, `machine-loop.ts` `sweepOrphans`) —
  the step side copies that cadence, no new mechanism.

## 2. Product Rulings (the three this ticket must rule first)

- **R1: deleting a task does not cascade-delete attachments.** The key scatters
  as a bare string across multiple reference surfaces (incl. copy, forward,
  chief threads); cascade deletion would wrongly delete files still referenced
  elsewhere. Deleting a task only removes one reference source, zero-reference
  files are swept by the tail — growth is bounded, false deletion is 0.
- **R2: three-state disposition.**
  - `pending` and over-age → reclaimable (no file, no reference, grant already
    dead all three hold).
  - `ready` and zero-reference and over grace → reclaimable (attached-but-never
    sent / send failed / draft abandoned / orphan whose owning task was deleted,
    all the same class).
  - any reference at all → **always kept** (it is part of the task record; the
    attachment cannot be regenerated, no "cache deletable" semantics).
- **R3: `step-attachments/` is scratch semantics.** Deletable (deleted when TTL
  reached), regeneration goes through the normal download path; the source
  attachment is not in the reclaim scope (goes to R2).
- **R4: the total cap goes through admission, not deletion.** Deleting
  referenced files cannot keep "false deletion = 0", so the quota only gates at
  grant time (over limit 400), the reclaim only collects zero-reference files,
  no rate limiting.

## 3. Mechanism: scheduler tick piggyback (server) + startup/daily sweep (daemon)

- server: reuse the existing `scheduler.tick` (15s), in-memory `lastSweep`, at
  most one sweep per hour. The rejected alternatives: an independent cron = a
  new moving part (timer, start/stop, test surface tripled); a pure startup
  sweep = a long-lived server has zero reclaim between two restarts. The tick
  shape is naturally testable (`tick(now)` injected), and startup back-sweeps
  (tick first runs inside `start()`).
- daemon: copy `sweepOrphans` (startup once + 24h interval, the same log
  channel).
- Reference scan surface (global cross-team scan — a cross-team false-keep only
  costs extra bytes, not a false deletion; under team isolation another team
  cannot see your key anyway):
  `todo.spec` + `message.content` + `chief_message.content` +
  `steer_pending.content` + `plan.content` (json columns go through stringify).
  Matching uses the key-syntax substring regex (a superset of whole-line tokens
  — an inline token also counts as a reference, only over-keep, never over-delete).
- Deletion order: first delete the DB row, then unlink the file (within the same
  sync block, no await interleaving). The crash landing point can only be
  "rowless file" (invisible waste), never "row-without-file" (a user-visible
  404). The server is a single instance holding SQLite exclusively, the premise
  holds.

## 4. Numbers (each with its reason)

| Constant | Value | Reason |
|---|---|---|
| `PENDING_TTL` | 24h | after the 5min grant that row can never reach ready; 24h = dead-and-buried + clock-drift slack; pending has no file, no reference, the false-deletion surface is zero |
| `ORPHAN_GRACE` | 7d | weekly rhythm — an abandoned draft within a week can still be recovered on regret; the total is anyway capped by quota, grace only decides "keep a few more days" |
| `TEAM_QUOTA` | 1GiB/team | a single item 10MiB ⇒ about 100 full-size files; normal task images (screenshots/docs) come nowhere near, malicious image-pasting filling the disk stops here; at grant time `sum(sizeBytes)+new > quota → 400` |
| `SWEEP_INTERVAL` | 1h | a full-table scan is O(row count); gated inside the 15s tick, at most once per hour — cost negligible, reclaim delay acceptable |
| `STEP_TTL` | 72h | a step's life is in minutes/hours; 72h = the step long dead + a machine offline for a weekend still reusable after return; the regeneration premise sees §1 |
| `SESSION_JSONL_MAX_BYTES` | 10MiB | the same value as the single-attachment cap (team 1GiB ≈ 100 full-size items); a step's pi / claude-code session JSONL is usually tens of KB to a few MB, 10MiB covers multi-round steps with tool output. Larger is treated as runaway: the daemon skips the upload and logs, the server PUT returns 413 without storing. No truncation — a half JSONL is worse than absent |

## 5. Observability

- Each sweep lands one info line: `attachment gc: pending <n> (<bytes>), orphan <n>
  (<bytes>)` (zero work also lands — proving the sweeper is alive; per-file goes
  through debug).
- The daemon same rule: `step-attachments recycled: <n> (<names>)`, lands only
  when there is work (same shape as sweepOrphans).

## 6. Failure-Mode List (tests fixed first)

1. Unreferenced ready item → reclaimed (file + row both gone).
2. spec/message either references a ready item → untouched (file + row both there).
3. After task deletion its attachment zero-reference and over grace → reclaimed (R1: deleting the task itself does not touch the attachment).
4. Task deleted but the attachment still referenced elsewhere → untouched.
5. pending over 24h → row reclaimed; pending not over-age → kept.
6. grant at quota-full → 400, old items unaffected.
7. the reference scan includes inline tokens (not whole-line) → still counted as reference (over-keep).
8. daemon: a step directory over 72h reclaimed; a step's internal new directory untouched; the source-attachment regeneration premise holds.
9. session.jsonl readable → uploaded with the transcript, fetched verbatim by stepId.
10. over `SESSION_JSONL_MAX_BYTES` → daemon skips, server PUT 413, not stored.
11. session file absent / read failed / upload failed → the step still success, log visible.
12. step alive → the session attachment kept; step deleted and over `ORPHAN_GRACE` → reclaimed.

## 7. Session Attachment (#1512)

At step wrap-up the engine's raw session JSONL (fixed name `session.jsonl`) is uploaded with the transcript through the existing upload-urls, stored at `<attachmentsDir>/step-sessions/<stepId>.jsonl`, fetched by stepId (`GET /api/machine/session/{stepId}` / `readStepSession`).

- **Not a user attachment.** No `attachment:<key>` token, not in the team quota, no grant. It is the step's diagnostic original (eval / replay), the transcript row remains the session source of truth.
- **R5: step alive means kept.** The step row still exists = the session attachment kept (when deleting a task does not cascade-delete a step, same as R1: over-keep, no false deletion).
- **Reclaim.** The step no longer exists and the file mtime over `ORPHAN_GRACE` (7d) → reclaimed. Same scheduler tick as §3 / at most once per hour. The daemon-side scratch (`step-attachments/`) still goes through `STEP_TTL` 72h, unrelated to this attachment.
- **Failure visible, step not failed.** Session file absent, read failed, over the cap, upload failed only log, do not block transcript / done.
