# 20-附件回收策略（issue #759）

> 策略先行文档：本票先裁语义、再落代码。数字逐条给理由；实现偏离须回改本文。

## 1. 事实（实测，非推断）

- `apps/server/src/services/attachments.ts` 全文无 GC / prune / unlink /
  retention / orphan（grep 零命中）——存储根
  `<dataDir>/attachments/<teamId>/<id>.<ext>` 只增不减。
- token `![name](attachment:<key>)` 持久化在任务正文里：`todo.spec`（text）、
  `message.content` / `chief_message.content`（json）、`steer_pending.content`、
  `plan.content`。token 被已落库内容引用 ⇒ 附件是数据，不是缓存——
  不许挪 /tmp（重启即全链死链，且静默）。
- web 写侧 token 只在 upload 201 之后构造
  （`apps/web/src/api/attachments.ts` `attachFile` 三步末尾）——grant 只落
  `pending` 行、不产生任何引用。grant token 自带 5min TTL
 （`ATTACHMENT_GRANT_TTL_MS`）：过期后该行永远到不了 `ready`。
- daemon 侧 `<PACMAN_HOME>/step-attachments/<stepId>/`（#736）是素材化副本：
  由 server 原附件下载再生（`resolveStepImages`），再生前提 = 源行仍在 +
  步文本仍含 token + 机器在线。
- daemon 已有同构先例：孤儿 worktree 回收（上线一次 + 每日节奏，TTL 7d，
  `machine-loop.ts` `sweepOrphans`）——step 侧照抄该节奏，不立新机制。

## 2. 产品裁定（本票最该先裁的三条）

- **R1：删任务不连带删附件。** key 以裸字符串散落在多个引用面（含复制、
  转发、chief 线程）；级联删会误删仍被别处引用的文件。删任务只去掉一个
  引用源，零引用件由回收扫尾——增长有界，误删为 0。
- **R2：三态处置。**
  - `pending` 且超龄 → 可收（无文件、无引用、grant 已死三重成立）。
  - `ready` 且零引用超 grace → 可收（粘了没发 / 发送失败 / 草稿废弃 /
    所属任务已删的孤儿，同属此类）。
  - 有任意一处引用 → **一律保留**（它是任务记录的一部分；附件不可再生，
    无「缓存可删」语义）。
- **R3：`step-attachments/` 是 scratch 语义。** 可删（TTL 到即删），再生走
  正常下载路径；源附件不在回收范围内（归 R2）。
- **R4：总量上界走准入，不走删除。** 删有引用文件保不住「误删为 0」，
  所以配额只在 grant 时卡（超限 400），回收只收零引用件、不限速。

## 3. 机制：scheduler tick  piggyback（server）+ 上线/每日扫（daemon）

- server：复用既有 `scheduler.tick`（15s），内存记 `lastSweep`、每小时最多
  扫一次。备选否决：独立 cron = 新 moving part（定时器、启停、测试面三倍）；
  纯启动扫 = 长驻 server 两次重启之间零回收。tick 形态天然可测
  （`tick(now)` 注入），启动即补扫（tick 在 `start()` 内首跑）。
- daemon：照抄 `sweepOrphans`（启动一次 + 24h 间隔，同一日志通道）。
- 引用扫描面（跨 team 全局扫——跨 team 误留只是多占字节，不构成误删；
  team 隔离下他 team 本来也看不见你的 key）：
  `todo.spec` + `message.content` + `chief_message.content` +
  `steer_pending.content` + `plan.content`（json 列走 stringify）。
  匹配用 key 语法子串正则（整行 token 的超集——行内 token 同样算引用，
  只多留、不多删）。
- 删除顺序：先删 DB 行、再 unlink 文件（同 sync 块内，无 await 交错）。
  崩溃落点只可能是「无行有文件」（隐形浪费），不可能是「有行无文件」
  （用户可见 404）。server 单实例独占 SQLite，前提成立。

## 4. 数字（逐条理由）

| 常量 | 值 | 理由 |
|---|---|---|
| `PENDING_TTL` | 24h | grant 5min 后该行永不可达 ready；24h = 死透 + 时钟漂移 slack；pending 无文件、无引用，误删面为零 |
| `ORPHAN_GRACE` | 7d | 周节奏——废弃草稿一周内反悔仍可找回；总量反正有配额封顶，grace 只决定「多留几天」 |
| `TEAM_QUOTA` | 1GiB/team | 单件 10MiB ⇒ 约 100 件满额文件；正常任务配图（截图/文档）远到不了，恶意粘图写满盘到此为止；grant 时 `sum(sizeBytes)+new > quota → 400` |
| `SWEEP_INTERVAL` | 1h | 全表扫描 O(行数)；15s tick 里设卡，每小时最多一次——成本可忽略，回收延迟可接受 |
| `STEP_TTL` | 72h | 步的生命以分钟/小时计；72h = 步早死透 + 机器离线一个周末回来仍可复用；再生前提见 §1 |
| `SESSION_JSONL_MAX_BYTES` | 10MiB | 与单件附件上限同值（team 1GiB ≈ 100 件满额）；一步 pi / claude-code 会话 JSONL 通常数十 KB 到数 MB，10MiB 覆盖多轮带工具输出的步。再大视为 runaway：daemon 跳过上传并落日志，server PUT 回 413 不落盘。不截断——半截 JSONL 比缺席更糟 |

## 5. 可观测

- 每次 sweep 落一行 info：`attachment gc: pending <n> (<bytes>), orphan <n>
  (<bytes>)`（零活也落——证明 sweeper 活着；逐文件走 debug）。
- daemon 同律：`step-attachments recycled: <n> (<names>)`，有活才落
  （sweepOrphans 同形）。

## 6. 失败方式清单（测试先固化）

1. 未引用 ready 件 → 被收（文件 + 行皆无）。
2. spec/message 任一引用 ready 件 → 不动（文件 + 行皆在）。
3. task 删除后其附件零引用超 grace → 被收（R1：删任务本身不动附件）。
4. task 删除但附件仍被他处引用 → 不动。
5. pending 超 24h → 行被收；pending 未超龄 → 留。
6. 配额满时 grant → 400，旧件不受影响。
7. 引用扫描含行内 token（非整行）→ 仍算引用（多留）。
8. daemon：超 72h 的 step 目录被收；步内新目录不动；源附件再生前提成立。
9. session.jsonl 可读 → 随 transcript 上传，按 stepId 取回原文。
10. 超 `SESSION_JSONL_MAX_BYTES` → daemon 跳过、server PUT 413，不落盘。
11. 会话文件缺席 / 读取失败 / 上传失败 → 步仍 success，日志可见。
12. 步行在则会话附件留；步删且超 `ORPHAN_GRACE` 才收。

## 7. 会话附件（#1512）

步收尾把引擎原始会话 JSONL（固定名 `session.jsonl`）经既有 upload-urls 随 transcript 上传，落盘 `<attachmentsDir>/step-sessions/<stepId>.jsonl`，按 stepId 取回（`GET /api/machine/session/{stepId}` / `readStepSession`）。

- **不是用户附件。** 无 `attachment:<key>` token、不进 team 配额、不走 grant。它是步的诊断原件（eval / 回放），transcript 行仍是会话正本。
- **R5：步行在则留。** 步行还在 = 会话附件保留（删任务不级联删步时同 R1：多留、不误删）。
- **回收。** 步行已不在且文件 mtime 超 `ORPHAN_GRACE`（7d）→ 收。与 §3 同一 scheduler tick / 每小时最多一次。daemon 侧 scratch（`step-attachments/`）仍走 `STEP_TTL` 72h，与本附件无关。
- **失败可见、步不失败。** 会话文件缺席、读取失败、超上限、上传失败只落日志，不挡 transcript / done。
