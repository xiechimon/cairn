# Run records for tasks and Coordinator turns — plan, 2026-11-27

## User scenario

Someone who installed Cairn today sends the Coordinator a message, and the turn fails: the chat shows the existing notice `未完成` (or `已停止，没有建任务。`). Today they can read only that one line and its `详情`; what the Coordinator thought, which tools it called with which arguments, and which call broke is stored but shown nowhere. A task run is the same: the thread shows a folded transcript, but no page shows one run end to end, links to it, or exports it.

After this change:

- The failed or stopped turn's notice (and the failure card above the composer) ends with `运行记录`. It opens a page for that one turn: the failure first, then what the user sent, the thinking (collapsed), each tool call with arguments and output, errors, the reply, the model and token use.
- The Coordinator's status mark at the top of the chat becomes a button. It opens a list of turns, newest first, grouped `今天` / `昨天` / `更早`, twenty at a time with more on scroll, filtered by default to turns that went wrong; a switch shows all turns.
- The first time a failed or stopped turn is in their chat, a small one-time hint beside the status mark says `点这里看每一轮做了什么`. Pressing it, its ×, any `运行记录` link or the mark itself retires it for good in that browser.
- A task's `⋯` menu gets `运行记录` (shortcut T), opening the task's latest run.
- Every run page has an export button that downloads the run as JSON.

They need no account, key or setting. Everything is read from the server's own database; nothing leaves the machine.

Why: owner's words, 2026-11-27 (translated): "build direction 2 [a separate run page] … and what about the Coordinator's trace?", on the entry point: "take 3 as the base, add 2's list, opened by clicking its avatar, with user guidance so people know the feature exists", and "the Coordinator's trace will get really long". Data from the owner's production machine on 2026-11-27: 486 Coordinator turns in 11 days (86 in the last day), 76 failed or stopped; the longest turn has 13 tool calls. `chief_message` already holds every turn's prompt, replies and tool calls with arguments and results; computer-run turns also hold their thinking as `msg-<stepId>-<n>` rows, while turns run inside the server (`coordinator/runtime`, used for API-key providers) drop thinking in `runtime/mirror.ts`. So the work is a reader and a page, plus one mirror change so both runtimes store the same rows.

| Situation | What the user sees | What the system does | Wait and cost |
|---|---|---|---|
| A Coordinator turn fails or is stopped | Notice line or failure card with `运行记录` | Link to `/app/runs/<stepId>` | none |
| Normal turn | Nothing new under the reply | — | none |
| Press the status mark | Turn list popover, problem filter on | `GET /api/teams/:id/chief/threads/:tid/turns?problems=1` | one request |
| Scroll to the list end | Next 20 turns | Same request with `before=<stepId>` | one request |
| Open a run | Run page, failure line on top | `GET /api/teams/:id/runs/:runId` | one request |
| Press export | A `cairn-run-<id>.json` file downloads | `GET /api/teams/:id/runs/:runId?download=1` | one request |
| Old in-server turn without thinking rows | Page shows prompt, tools, reply, error, usage; no thinking rows | Reader finds no thinking rows | none |

## Scope

1. One storage for both Coordinator runtimes. `entryRowSources` in `coordinator/runtime/mirror.ts` also emits, for each committed assistant entry with non-blank thinking, a row `[{type:'thinking', thinking}]` with id `coordinatorThinkingSourceId(stepId, entryId, storeId)` = `native-<storeId>:<stepId>-t<entryId>` (helper beside `coordinatorTextSourceId` in `packages/shared/src/coordinator-identity.ts`), before that entry's text row. Aborted entries emit none, except the entry the user stopped, whose thinking so far is kept. This is the row shape computer-run turns already write; the chat renders it as a collapsed thinking row, so in-server chats now show thinking like computer-run chats do (a visible chat change, named here on purpose). No new table, no migration.
2. Partial-write safety. Each emitted row carries `lastOfEntry`; `transcriptRow` advances the thread's `lastMirroredEntryId` only on the entry's last row. If a write fails after the thinking row but before the text or tool row, the watermark stays behind and the existing reconcile (`reseeded-ahead`) rewrites the entry; rows are deduplicated by id, so nothing doubles. This also closes the same gap that already existed between a text row and a tool row of one entry.
3. Seed budget. `readThreadRows` in `coordinator/seed.ts` skips rows whose first block is `thinking`, so stored thinking never uses up the 100-row seed budget and pushes real messages out of the model's context. This also applies to computer-run thinking rows, which already used up budget before this change.
4. One run reader, `services/run-trace.ts`, team-scoped: `GET /api/teams/:id/runs/:runId`. `runId` is a chief step id (a Coordinator turn), a build id or a build step id (a task run). A thread id, todo id, another team's id or an unknown id is 404, so a link always pins one run. Response (`packages/shared/src/run-trace.ts`, zod): kind, id, title, threadId, todoId, status, startedAt, finishedAt, models, usage (`input`, `output`, `cacheRead`, `cacheWrite`), `previousId`/`nextId` (Coordinator), `failure`, and ordered items `user | prompt | thinking | reply | tool | error | stopped | note | step`.
   - Coordinator turn: `chief_message` rows of the thread that belong to the step by id (`user-<stepId>`, `msg-<stepId>-*`, `native-*:<stepId>-e*|-t*`, `chief-err-<stepId>`, `chief-stop-<stepId>`), plus tool rows (no step in their id) whose `createdAt` lies in the window (this turn's `claimedAt`, the next turn's `claimedAt`], or (claimedAt, ∞) for the newest turn. A turn never claimed has an empty window. Neighbours are ordered by (`createdAt`, `id`).
   - Why time attribution is exact, not a guess: the server accepts a transcript row only from the step that currently owns its claim (`ownedStepRow` in `coordinator/server-api.ts`, the same check for computer-run and in-server turns), and a thread's next chief turn is claimed only after the previous one has finished (`hasEarlierLiveChiefStep` in `services/chief-turns.ts` blocks the claim while an earlier turn is live). So every stored tool row was written inside exactly one turn's window, for rows written before this change as well. The one shared instant is the next turn's `claimedAt` itself: the earlier turn can write its last row in that millisecond (its finish and the next claim may share it), while the next turn cannot, since its first tool call needs a model reply after the claim; so a row stamped exactly at the next claim belongs to the earlier turn, and the window excludes its own start. Decision, with its limit stated: a next-turn tool row in the claim's own millisecond would need a model round trip of under one millisecond, which no provider delivers (replies take tens of milliseconds at least), so the plan accepts that case instead of adding a turn id to every tool row and a migration; if it ever happened, the row would show in the earlier turn, nothing is lost or doubled, and its own turn's page would only miss that one row. No row is marked uncertain.
   - A turn still running reads as far as it has got: status `running`, `finishedAt` null, the items stored so far; the page shows them and nothing claims the turn ended.
   - Task run: the build's conversation `message` rows and its steps, in order; usage from the build's `token_usage` rows.
   - `failure` = `{text, itemId}`, one rule for both kinds: `text` is the last error item's text — for a Coordinator turn the `chief-err-<stepId>` row, for a task run the failed step's reason or, after it, the build's `errorMessage`; `itemId` is the id of the last errored tool call before that error (null when none). `failure` is null when the run has no error item; a failed status without any error item shows the status in the meta line only. A tool error that the run went on from is not the failure; the page marks that tool `之后已继续`.
   - Retry is not on the run page: the chat's failure card keeps `重试` (and a stopped turn is resent from the composer), so the page answers "where and why", and the place that already retries stays the one place.
5. Payload size and privacy. The page response caps each tool argument and result string at `RUN_TRACE_VALUE_CAP` (4,000 characters) and marks the item `truncated: true`; the export (`?download=1`, `content-disposition: attachment`, file `cairn-run-<id>.json`) is full. Both responses pass through `redactSecrets`, so an API key or token in a prompt, argument or output reaches neither the browser nor the file, and both send `cache-control: no-store`. Both need the signed-in team session; another team's id is 404. Once downloaded, the file is the user's, like any export: it holds the run's prompts and tool output (redacted), which is what the button says it exports.
6. Turn list: `GET /api/teams/:id/chief/threads/:tid/turns?limit=20&before=<stepId>&problems=0|1` → `{turns, nextCursor}`, newest first. A row is `{stepId, at, problem: failed | stopped | quota | null, firstLine, woke, toolCount, durationMs}`. `firstLine` is the first line of the owner's message for the turn; `woke` is true when the turn started without an owner message (a schedule, a task report or another wake), and the row then reads `自动唤醒`. `problems=1` keeps failed, stopped and quota-held turns. Team- and thread-checked; an unknown cursor is 404. Cost per page is bounded by the page, not the thread's history: one indexed query for `limit + 1` chief steps of the thread, then for each of the 20 rows its owner message, its error row, its next turn and a count of tool rows in its window — four point or range lookups per row, about 80 small queries, independent of how many turns the thread has. The run page reads one turn's rows; folding is visual, and the cap in row 5 bounds the transfer.
7. Run page (web), route `/app/runs/:runId`, a `RouteDialog size="page"` like the usage page. Head: title; actions previous / next turn (Coordinator only, disabled at the ends, replacing history so close returns to the chat) and export (icon buttons with tooltips, C27). Meta line: status · start time · duration · models · tool count · tokens. Then the failure as a danger notice with `看出错的那一步`, which opens and scrolls to that tool. Items via the Trace components: the prompt and thinking collapsed to one line; three or more consecutive successful tool calls fold into `N 次工具调用 · names`; each tool row is one line (name, arguments on one line, duration) that expands inline to its arguments and output, with `内容过长已截断，导出的文件里是全文` when truncated; an errored tool is never folded and, when the run went on after it, says `之后已继续`. `只看报错` shows only when the run has errors and keeps only error rows. Loading shows a skeleton; 404 says `找不到这条运行记录`; another failure says `未能加载运行记录` with `重试`.
8. Entries (web): `运行记录` on the Coordinator `未完成` notice, the failure card, and both stopped rows (with and without started tasks), each only when the row id names a step; `运行记录` (T) in the task `⋯` menu when the task has a run. Normal replies get nothing. The handoff row `已转给任务` keeps leading to the task, whose menu has the entry.
9. Status mark: the glyph is a `<button>` in both the desktop and the narrow variant, accessible name `Coordinator 运行记录`, the mark state as its description, tooltip `<state> · 点击查看运行记录`; it opens the turn list popover. ↑/↓ move between rows, Enter opens, Esc closes and returns focus to the mark; rows are at least 44px tall on touch. The popover groups `今天` / `昨天` / `更早` by local date, loads the next page when its end scrolls into view, keeps loaded rows and offers `重试` when a later page fails, and says `暂无出问题的轮次` with `看全部` (filter on) or `暂无轮次` (filter off) when empty. A thread with no id (before the first message) keeps the old non-interactive mark.
10. One-time hint, web state owned by the browser: localStorage `cairn:run-trace-hint-seen`, with an in-memory fallback when storage is unavailable (that session only). Shown when the chat has a failed or stopped turn row with a step id and the key is unset: a bubble right of the mark on desktop, under it in the narrow layout, overlaying the chat, never over the composer, no focus steal. Opening the list, pressing the hint, ×, or any `运行记录` link sets the key.
11. Unchanged: task transcripts, `inspect_run` output (it moves to the shared run-target helper with identical output), the existing `详情` detail, `coordinator_turn_snapshot`.

Why each proving test is red on the parent: `run-trace.test.ts` calls `/api/teams/:id/runs/*` and `/chief/threads/:tid/turns`, which do not exist on the parent (404 for every positive call); `run-trace.spec.ts` clicks `运行记录` links, the mark button and `/app/runs/*`, none of which exist on the parent; the mirror test expects the `-t<entry>` row and `lastOfEntry` only on the last row, which the parent never emits; the seed test fills the budget with thinking rows and expects the old message to survive, which the parent drops; the narrow-shell spec expects the mark as a named button, which on the parent is an image. Every not-found assertion sits in the same test as a positive call to the same endpoint for the same team, so it cannot pass on a parent where the endpoint is missing; the "normal reply has no link" case is asserted next to the failed row's link in the same chat.

States and transitions: hint unset → seen (terminal per browser; per session when storage is unavailable). Mirror watermark: advances per entry only after that entry's last row is written. Writers of thinking rows: `entryRowSources` through `transcriptRow` (live mirror and input replay), deduplicated by row id; `mapEntry` maps the thinking row to its entry like the text row, so a rewind deletes both together. Readers: chat (renders thinking collapsed), `run-trace.ts`; the seed skips them.
Web state: the turn list and the run trace are React Query caches keyed by (team, thread, filter) and (team, run id); switching the filter or the thread reads a different key, so a late response of the old key never shows in the new list. Pages accumulate in that cache while the popover is open and refetch on reopen. There is no selection state: rows are links, and the open run is the URL. The hint key is the only browser-stored value. Failure paths: a failed `transcriptRow` leaves the watermark behind and reconcile rewrites the entry; a run whose rows were deleted with its task or project is 404; the page's fetch failure shows `重试`; a failed export shows a toast.

## Out of scope

- Recovering thinking of in-server turns finished before this change.
- Changing `inspect_run`'s output or its 24 KB cap.
- Search inside a run (the browser's find works on the page).
- Server-side storage of the hint state (there is no user preference store).
- A timing strip or side pane on the run page; tool details open inline.
