# Saved browser passwords without chat credentials

Status: Coordinator approved the ordinary-flow contract on 2026-11-16. A read-only Claude Opus 5.5 assessment found no P0 and three P1 design defects; the explicit delivery type, browser-output redaction and strict origin-first injection below address them before implementation. Research: [primary-source comparison](../research/browser-secret-fill-2026-11-16.md). Extends M2b in [login handoff](computer-login-handoff.md); takeover and its 15-minute timeout remain.

## Contract and boundary

The owner saves a password and its exact origin in the existing Secrets settings: HTTPS, or HTTP restricted to `127.0.0.1`, `[::1]` and `localhost` with an exact port. The Coordinator sees only the name and origin and requests a fill by reference. The ordinary save, resolve, fill, result, conversation and OTel paths contain no plaintext password outside the encrypted store, trusted server/daemon memory, protected transport and receiving page. Saving authorizes subsequent fills on that origin without another confirmation. CAPTCHA, one-time codes, QR, passkeys and device approvals still use `request_takeover`.

This does not promise that a malicious authorized website cannot disclose a password it receives, or that arbitrary transformations of a password can always be redacted. The same-user shell and local CDP access can read a filled password under prompt injection; screenshots can disclose a password a site reveals. The Coordinator explicitly accepted these residual risks for this milestone. Browser isolation, persistent cross-tool secret redaction and hostile-site containment are out of scope. No claim of prompt-injection-proof secrecy is made.

## Owner binding and reference

Add `browser` to `SECRET_DELIVERIES` and a nullable `browserOrigin` to encrypted `secret` rows. A database CHECK makes browser delivery equivalent to a non-null browser origin, null HTTP columns and null project scope. Plaintext and HTTP rows require a null browser origin. Grant readers decrypt only explicitly plaintext rows; an unfamiliar delivery never falls through to plaintext. Existing rows retain their policy and ciphertext. The owner chooses browser-only use and enters the origin in the existing settings dialog; it shows the ASCII/punycode origin and warns against shared-hosting and user-generated-content origins. Match exact scheme, host and effective port; reject wildcard, path, query, fragment, userinfo and Cairn's own origins. HTTP is allowed only for the three literal loopback hosts above, never other HTTP hosts or loopback lookalikes; the serialized origin pins the effective port. The incident's preceding browser navigations confirmed loopback HTTP without publishing the private address. The Coordinator approved this exception on 2026-11-16; no new Langfuse HTTPS endpoint is needed.

Browser-only values are excluded from task grants, plaintext vaults, environment generation, mail credentials, HTTP gateway grants, withheld grants and `get_secret`. Mail linking requires plaintext delivery. Coordinator CRUD cannot create browser credentials, change their policy, retarget them or downgrade them to plaintext; `set_secret` and `delete_secrets` refuse names protected at either workspace or project scope. Owner conversion in either direction or retargeting requires a replacement value. Initially the Coordinator can reference only workspace-scoped browser credentials, not project-scoped credentials. Lists return metadata only.

For any of the three loopback hosts, regardless of HTTP or HTTPS, saving automatically binds `browserMachineId` to the machine of the authenticated owner's currently running private Coordinator browser, using the existing computer ownership check. HTTPS rejects other IP literals and `*.localhost`. There is no client-supplied machine binding and no machine selector. Refuse saving when that browser is not running or its machine is unavailable, with a plain instruction to open the Coordinator browser first. The dialog shows the bound machine name as one help line. At dispatch require the same machine; never silently rebind or widen the binding when a machine is deleted. A database CHECK requires a machine id exactly for loopback origins; the column has no deleting or nulling foreign key. Non-loopback HTTPS credentials have no machine binding. A changed binding requires a replacement value. Browser secrets share existing team-secret access: every team member's Coordinator can use them on the authorized origin and machine, not only the saving user; the dialog states this. Short passwords can over-redact browser output; that is accepted rather than weakening redaction.

Extend `browser_act` with `fill_secret {ref, secret}`. A dedicated action makes the credential intent explicit and avoids interpolation into arbitrary strings, URLs or shell commands. Keep literal `fill`/`type` refusal for password and OTP fields. Password references fill only a visible, editable `input[type=password]`; missing, stale, readonly, OTP, new-password, cross-origin-frame and non-password targets fail closed. The top-level page and receiving frame must both match the saved origin at fill time using trusted browser metadata; a previous navigation result is insufficient.

## Delivery, state and failure paths

| Path | Read/write and expected behavior | Failure behavior and required regression |
| --- | --- | --- |
| Settings create/update/delete | Encrypt value, bind explicit browser delivery and origin, automatically bind HTTP or HTTPS loopback to the owner's running browser machine, increment existing policy revision; API/list responses omit value | HTTP and HTTPS loopback without a running browser fail to save; invalid policy, mail linking and either conversion direction without new value rejected; DB CHECK rejects mismatched delivery/origin/machine; old records unchanged |
| Model secret tools and every credential grant reader | Metadata only for browser delivery; decrypt only explicit plaintext delivery; no model route can change its authority | A task granted a browser secret id receives nothing in values, HTTP or withheld grants; direct access, name collision, project override and policy conversion cannot disclose browser values |
| Relay authorization and replay | Require claimed Coordinator step, correct owner/workspace/computer, loopback machine binding, capability, free user-control lease and current policy revision | Wrong or missing bound machine, disconnected or old daemon refuses without plaintext fallback; unsafe fills are never replayed automatically |
| Server dispatch | Persist reference, origin, revision and outcome in call params; resolve only after authorization, free control lease, call insert and explicit daemon capability, into a separate typed non-logged transport envelope | No value in `computer_call.params`, stream events, errors or OTel; rejected, cancelled or unsupported-daemon calls do not resolve |
| Daemon injection | Receive credential outside params; focus fresh ref, run secret-free strict origin probe, then send strict origin-first synchronous fill script through stdin, not argv/env/disk | Iframes, redirects, OTP, new-password, cross-origin form actions, timeout, cancel, takeover or failed checks refuse; hostile wrong-origin prototype hooks capture nothing; all raw injection output/errors are discarded; partial delivery reports unknown, not retry |
| Browser observations | For every browser call, read current team browser secret values from the encrypted store into call-local memory and redact complete output/results/errors and URI, form-plus and JSON encodings before persistence or publication | A later reveal snapshot is redacted while the stored credential is current; discard values after each call, with no historical store or cache; shell remains outside this browser-only backstop |
| Screenshots and attachments | Normal password inputs remain masked; no screenshots are returned by the fill | A site's reveal control or subsequent shell/CDP readback is not a secrecy boundary in this milestone |
| Login detection and handoff | Password/username alone no longer forces human takeover; challenge/OTP detection and explicit takeover retain pending/held/returned/expired states | Owner-held control still blocks agent actions and observations; failed login cannot be reported as authenticated |
| Finish, crash and recovery | Plaintext is transient, outside durable call params; unsafe calls are not replayed; rotation and deletion affect new dispatches; drop call-local redaction values on finish or failure; fresh calls reload current values | Already-dispatched fills may complete with the old value; cancellation does not prove nothing ran; historical values are not retained after the call; retained browser state shares the accepted same-user risk |

Execution mechanism: a thin bridge uses the pinned agent-browser `focus` and `eval --stdin` commands. Both eval scripts are strict IIFEs whose first executable statement is `if (window.top !== window || location.origin !== "<serialized origin>") return false;`. No page-hookable API runs before this gate. A secret-free probe must pass before sending the fill script; the fill script repeats the gate synchronously, with the value literal only after it. It then checks the focused element's owning top-level document, visibility, editable password type and autocomplete, and refuses foreign-origin form actions or submit-button overrides before assigning. It never awaits between the gate and assignment and returns only a boolean. Host and scoped providers pass stdin through; no plaintext credentials are written to disk. Unset `AGENT_BROWSER_DEBUG`, require a private socket directory, verify stdin is not logged, and disable Chromium credential saving in the shared profile for both browsers. Agent-browser's maintained `auth login` requires a username and submits the form, so it cannot implement this password-only action or multi-page login without changing its contract; its vault also creates an unnecessary second secret store. A separate URL check alone is not the authority check.

Browser-output backstop: for every `browser_*` call, read the team's current browser-delivery values from the existing encrypted store into trusted server memory inside the common frame-receiving path. Pass those values, `encodeURIComponent` variants, form-plus encodings and JSON-escaped forms to the existing `redactSecrets` function before any complete output or error is persisted or published; discard them after processing the frames. This same path handles recovery, with no per-call secret state. Do not add an encrypted snapshot column, historical credential store or cross-call redaction cache. The Coordinator approved this scope on 2026-11-16 without narrowing the ordinary-flow promise. Old values no longer in the store are not protected in later output; an invalidated old value appearing later is an accepted residual risk. Deleting or replacing the Cairn record alone does not revoke the website's password. For loopback, another local process can bind the authorized port while the intended service is stopped; service identity beyond the bound machine and exact origin is a documented residual limit.

Negative controls cover the failure paths in each row, especially redirected origins, iframes, changed field type, injection errors, rotation/deletion, restart, cancellation and owner takeover.
