# Saved passwords: approve the website in chat

Owner revision, 2026-11-16: restore the existing secrets form without browser controls or website fields. Supersedes the settings-binding design. Prior art and the original incident are in [research](../research/browser-secret-fill-2026-11-16.md); CAPTCHA and second-factor [takeover](computer-login-handoff.md) remain unchanged.

## Contract

Save an ordinary workspace secret using the existing name, value and secret checkbox. On login the Coordinator reads the current page and calls `browser_act` with `fill_secret {ref, secret, origin}`. The origin must be an exact HTTPS origin, or literal loopback HTTP/HTTPS including its port. The server creates an existing conversation approval card naming the secret, ASCII website origin and execution machine. A pending fill does not open or deliver the value; server-local observation redaction can still open adopted secrets to suppress them from browser output. The question explicitly authorizes future fills for that website on that machine. Only the instance owner can decide the card; paired-device bearer tokens and browser sessions cannot. The agent cannot approve its own card.

Reuse immutable `action_proposal` records rather than adding secret columns or a migration. An executed, owner-decided `browser.secret.authorize` proposal is the grant, bound to team, secret ID, existing policy revision, exact origin and machine ID. The fill reloads the secret and grant on every dispatch. Rotation invalidates the revision; deletion, a different website or a different machine requires approval again. A fresh browser reference is required after approval. Refusal, expiry and supersession do not grant access. Approval records contain metadata only, never ciphertext or plaintext.

From the first proposal onward, that secret is excluded from task/plaintext/HTTP grants and model mutation/deletion, including same-name project overrides. This protection remains after refusal or expiry: a rejected browser request must not become a plaintext fallback. The owner can still rotate or delete it through the unchanged settings form. Environment variables, mail-linked credentials, daemon-reserved names, HTTP-delivery secrets and project secrets cannot be adopted as browser passwords. Owner APIs cannot turn an adopted password into HTTP or env delivery. Ordinary secrets not used for browser filling keep their existing behavior.

## State and failure paths

- **Stored → pending:** validate a workspace secret and capable machine, normalize the requested origin, then create/deduplicate a trusted approval card. Publish it through the existing question event. Return a pending result without a computer call, execution lease or decryption. Changing the proposed target supersedes the old pending card.
- **Pending → allowed/refused/expired:** the existing authenticated answer route, instance-owner decision check and intact-card digest enforce the decision. Approval rechecks the secret revision, eligibility and machine; a stale card fails closed. Reuse rechecks the deciding identity against the instance owner, so historical device-approved proposals cannot grant access. Existing subscription wakes resume the Coordinator, which takes a new snapshot and retries.
- **Allowed → fill:** reload authorization before opening the value into the existing separate, non-logged transport envelope. Keep reference/origin/revision only in durable call params. The daemon's secret-free probe and synchronous origin-first fill independently check the actual page, visible editable password input, receiving document and form target. Wrong websites, stale refs, new-password/OTP fields, cross-origin forms and frames refuse without literal-password fallback.
- **Observation, failure and recovery:** redact current adopted-secret values and encoding variants from every browser result/error before persistence or publication. No historical secret cache. Unsafe fills never replay automatically; already-dispatched operations may finish after cancellation or rotation. Existing user-control leases and explicit takeover remain authoritative.

Residual limits are unchanged: the authorized website receives the password; same-user shell/CDP access, reveal screenshots, historical rotated values and replacement services at an approved loopback port are not contained by this milestone. Do not claim prompt-injection-proof secrecy.
