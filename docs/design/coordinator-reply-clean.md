# Coordinator replies: output, completion, and changes — 2026-11-28

## User scenario

On their first day, a user asks Coordinator chat for command output, opens a completed task, or reads a draft delivered as an attachment. Put the result first; show evidence in its own place, not as a second layer of answer. This takes no new setting, key, storage, wait or cost. With no tasks there is no new UI; a missing task opens the existing unavailable-task panel. Prior art and the before/after proposal: the stage 1 reference walkthrough (Claude.ai, Claude Code and Amp), screenshots 333/335/336. The following 11-28 pick overrides the original prototype.

## Scope

1. Owner pick, 11-28 (paraphrased): the code component should keep the left column, and the file name with its extension belongs at the top-left. Split the background, not the message: `ChiefStreamRow` (`apps/web/src/chief/chief-message-rows.tsx`) and `ChatMarkdown`/`ReplyGroup` (`apps/web/src/detail/chat-markdown.tsx`) place top-level code in its own surface, in order. Keep one source/selection/copy owner and retain the existing `CodeBlock` header and actions. `apps/web/src/lib/markdown.ts` preserves an explicit fence filename, e.g. `ts title="name.ts"`. Left header shows that filename, else language, else localized Code. Render as escaped, single-line truncated text (not a link); nested and indented markup follows existing parse and nesting rules. Tables, checklists, attachments and rules stay inside the grey reply surface, and a run of replies keeps its tight touching corners on the painted surface. Text-only, tables, owners' bubbles, reports and non-Coordinator surfaces keep their layout.
2. Owner pick, 11-28 (paraphrased): say it through the bubble the way a person speaks, and when a task finishes give the result first. `wakeFactText` case `settle` and `settleWakePrompt` (`apps/server/src/services/chief.ts`) tell the Coordinator to write one or two colloquial sentences in the user's language, result first, confirmed availability only if relevant, action only if needed. Unknown/conflicting evidence stays uncertain; task completion is not merge or deployment. Raw evidence stays in the existing task transcript, not in prose. Generation and brevity are model instructions, not a schema or lossy regex filter; existing claim grounding still applies. Production must show an actual notice, not just seeded text. `notify_user` in `apps/server/src/services/chief-tools.ts` stays the existing writer; its tool description carries the same result-first, no-internal-detail rule so the model hears one instruction. `collectChiefStream` (`apps/web/src/api/mappers.ts`) maps a matching `[wake:settle]` echo and `watch:` provenance to an optional task id; `ChiefStreamRow` uses existing `ThreadLink` to offer Details beside, not inside, the normal bubble. No matched echo/provenance, no new link; older prose, failed/review wakes, ordinary notices and runtime-update notices are not rewritten. A click opens the ordinary task panel, without forcing Changes. An arrival neither opens a panel nor changes focus.
3. Owner pick, 11-28 (paraphrased): a code change is always attached below, and it is in the way. The literal Changed row is `ChangesCard` in the **task side chat** (`ThreadBody` result slot, `apps/web/src/board/side-chat.tsx`), not the main Coordinator timeline. Make the automatic slot a formal review affordance only: no auto card in a normal completed thread, and no auto card when delivering an attachment in the task's reply, even with a real file diff. Do not guess identity from a displayed file label. Provide explicit Changes through the task's existing more menu (`apps/web/src/board/thread-actions.tsx`), reusing `SideChat`'s per-task open state and the same card/scroll behavior as the PR Changes action and deep link. This intentionally preserves retry, undo, full diff and PR review when requested; a plain-folder task whose changes still offer undo, or that reports a conflict or load error, keeps the card in place because that action has no other home. The card's chevron closes it again. Separately `CHIEF_CORE` in `apps/server/src/services/chief.ts` steers `show_diff` (implementation `apps/server/src/services/chief-show.ts`, dispatch `chief-tools.ts`, `SHOW_DIFF_TOOL` in `packages/shared/src/protocol/chief-tools.ts`) only for a request to see code differences, not an attachment delivery; model intent stays there, while removal of the automatic footer is deterministic. Charts and manual task review are unaffected.
