# Keep-awake modes — plan, 2026-11-27

Owner decision: option 4, the recommendation that modes live in the menu-bar menu, the default keeps the machine awake while a task runs but lets the screen sleep, lid-closed running appears only on AC power, and nothing blocks sleep without a task. Research: `docs/research/keep-awake-modes-2026-11-27.md`.

## User scenario

A first-time Mac user installs Cairn, starts a task, closes the laptop lid or walks away. They do not know what caffeinate, pmset or power assertions are. Opening the Cairn menu-bar menu shows plain choices for how the computer stays awake while Cairn is working. The default needs no setup: after the runner claims a step, the computer does not idle-sleep while that step is in flight, but its screen may turn off. When nothing is in flight, Cairn holds no power assertion. Choices survive restart. Battery-powered lid-closed running is unavailable because macOS offers no no-password API for it; the menu hides that choice while unplugged rather than promising something Cairn cannot keep. Even on AC, a successful `PreventSystemSleep` assertion is only a request to macOS, not a guarantee that a physically closed laptop lid will keep running; Apple reserves override such as thermal or power emergencies, and the Mac mini evidence in this lane cannot exercise a lid at all.

Protection starts when the runner claims work, not when the user presses submit. If the machine sleeps before the runner can claim the step, the task waits; that is the direct consequence of the approved “nothing blocks sleep when no task runs” rule. After the step's compute finishes, `awaiting-upload` still counts as in flight because the result is not safely delivered. If the runner is stopped or failed, stale journal rows do not keep the desktop awake; recovery restarts protection when the runner starts again.

## Scope

1. Replace the desktop's persisted boolean keep-awake choice with one mode, `screen-on`, `system` or `lid-closed`, stored as one line in `userData/keep-awake`. `system` is the default. Legacy `on` migrates to `screen-on`; legacy `off`, missing, unknown or truncated content migrates to `system`. Writes go through a temporary file plus rename. A selection becomes effective only after that write succeeds, so the desktop menu and the daemon never diverge; if the write fails the previous effective row stays checked, and pressing the same row again retries the write. Startup migration failure keeps the mode the existing file bytes imply (legacy `on` reads as `screen-on`; invalid/missing bytes read as `system`) and retries on the next selection.
2. On macOS the daemon is the single owner of power assertions, for both embedded and standalone runners. The embedded runner receives `--keep-awake-file <userData/keep-awake>`; a standalone runner has no file and uses `system`. When the daemon claims a step it synchronously applies the current mode before starting execution: `screen-on` runs `caffeinate -d -i -w <pid>`, `system` runs `caffeinate -i -w <pid>`, and `lid-closed` runs `caffeinate -s -i -w <pid>`. While work is pending it re-reads the mode file and journal, replaces the child when the mode or file rewrite changes, retries after child failure, and releases it when no pending work remains. `-s` is constrained by macOS to AC power; on battery the `-i` assertion is the effective fallback and the stored choice is not rewritten.
3. On Windows and Linux, where caffeinate is unavailable, the desktop main process is the power owner and uses Electron `prevent-display-sleep` or `prevent-app-suspension` while the runner is `on`/`starting` and its journal has in-flight steps. `lid-closed` is never offered there. This platform split is explicit rather than two simultaneous owners on macOS.
4. The menu-bar menu shows the three mutually exclusive choices under a while-tasks-run heading. `lid-closed` appears only on macOS while `powerMonitor` reports AC power. The same checked state appears in the native menu, fallback Electron menu and web popover. When a stored `lid-closed` choice is temporarily unavailable, `system` is shown checked as the effective fallback without rewriting the stored choice; pressing `system` in that state is a real selection and discards `lid-closed`. Pressing the already effective row is a no-op unless the last persistence write failed, in which case it retries. Power changes publish a fresh menu; stale lid-closed clicks are revalidated and ignored on battery or non-Mac.
5. Remove the manual always-on override and schedule wake-ahead override in this change. Scheduled work is not specially kept awake before it starts; once a step is claimed, ordinary in-flight protection applies. Update retired tests, smoke assertions, `apps/desktop/README.md` and the wake-ahead section of `docs/design/routines-event-triggers.md` in the same change.
6. Register the persisted setting semantics in `scripts/product-surface-registry.json`. Standalone runners now also sleep when idle; consequently a task submitted while such a machine is asleep waits until the machine wakes for another reason. That product-wide trade-off follows the owner's approved rule and is called out in the report.

## State, readers and writers

Persisted selected state is the desktop `userData/keep-awake` file containing `screen-on`, `system` or `lid-closed`. The desktop main process is the only writer, at startup migration and after validated tray/popover choices. Readers are the desktop main process and, on macOS, the embedded daemon through the explicit `--keep-awake-file` handoff. Both readers use the same persisted-value parser: legacy `on` means `screen-on`, legacy `off` or invalid content means `system`. Writes are temporary-file-plus-rename. A failed write does not change the effective in-memory mode, is logged, and is retried by the next selection, including the same selection; the menu therefore cannot show a mode the daemon cannot read.

Journal state remains owned by the existing daemon step pipeline: the claim path creates `claimed`, execution writes `running`, delivery writes `awaiting-upload`, and terminal delivery/failure removes the row or leaves a non-pending state. The power loop only reads `StepJournal.pending()`; it never writes journal rows. Desktop non-Mac activity combines that journal fact with the runner lifecycle writer already in `main.ts` (`on`/`starting` versus `off`/`failed`), so stale rows cannot hold power after the runner is stopped.

Daemon power runtime state is `(pending journal count, selected mode content+mtime, current child, desired mode)`. Writers are the claim path, mode-file poller, child `error`/`exit` handlers and shutdown. A replacement is spawned only after the old child has been sent `kill`; the old child's late exit is keyed by object identity and cannot clear the replacement. Missing mode files mean `system`; unreadable files keep the last valid mode for the current task and revert to `system` on restart. Missing caffeinate or child failure retries on the next sync while work remains.

Tray bridge state changes from `keepAwake: boolean` to `keepAwake: KeepAwakeMode` plus `lidClosedAvailable: boolean`. Desktop main is the authority for the checked row in all three presentations: the native menu is rebuilt through `withHostState` from main's mode whenever published and again after helper restart, the Electron fallback is rebuilt after a selection or power transition, and the web popover renders only the latest published `desktop-tray:state`. Invalid IPC modes and stale battery lid-closed clicks are rejected without changing main state, so the next publish/native menu update reasserts the previously effective checked row rather than displaying a false protected selection. The web popover, preload bridge, schema and native helper move together in the packaged app; mixed-version web/desktop combinations are unsupported and fail schema validation rather than partially applying a mode. Native helper failure falls back to the Electron menu only and never stops the daemon's power loop.

## Out of scope

- Battery-powered lid-closed operation, `sudo pmset -a disablesleep`, a sudoers/Power Protect installer, private IOKit APIs, and thermal-policy changes.
- Physical lid-close verification on a laptop in this lane. The owner-requested production evidence is the packaged menu plus `pmset -g assertions` on the Mac mini; a Mac mini has no lid. The implementation requests the strongest no-password AC assertion macOS exposes, and the report labels this boundary explicitly.
- Waking an already sleeping Mac to claim or start future work. Protection begins after claim; a machine asleep before claim stays asleep.
- Changing scheduling, missed-run policy, task claiming or upload retry rules; this change only consumes their existing states.
