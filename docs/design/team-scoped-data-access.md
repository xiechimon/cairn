# Team-scoped data access

A new Cairn user opens a task, follows a design link, or pairs a runner in their team. They use the usual account or pairing flow; there is no new setting, payment, or key to enter. Existing data and credentials stay on the installation when their original ownership can be proved. History, edit receipts, and other content a legacy job could overwrite or copy also need proof of who produced the version that would be shown and where its contents came from.

| When | What the user sees and what Cairn does | Wait and cost |
| --- | --- | --- |
| Opening or changing an owned item | The usual result; Cairn checks the exact ownership chain. | No extra network round trip or fee. |
| Following a missing, foreign, or retired link | The usual missing response; no change, publication, or dispatch. | No retry or fee. |
| Importing or refreshing a skill | Choose an authorized source. A missing, foreign, or retired source cannot be previewed or copied; a failed refresh leaves the existing skill intact. | Local sources need no network call; remote sources use the existing provider access. |
| Attaching or using a project repository | Only the installation owner can bind or browse an approved local checkout. For GitHub, choose a repository granted through the team's existing connection. A runner receives access only to what its operation needs. If access is lost, the project remains but its repository is unavailable until explicitly rebound. | Local verification needs no network call; GitHub may require authorization and token minting. No new fee. |
| Running a step that needs a connector | The runner uses the team's existing connection for the granted operation. If the provider cannot issue narrow access, Cairn performs only the authorized operation on the runner's behalf or reports it unavailable. | Minting or brokering can add a network hop; no new credentials or Cairn fee. |
| Viewing a runner screen | The usual screen opens for an admitted viewer and runner. If either loses access, the stream ends and a new open is required. | The existing two upgrades; no new sign-in or fee. |
| Upgrading or restoring an installation | Work pauses. Unprovable durable records stay in a restricted local recovery archive, outside the UI and job queue. Unprovable access must be reissued or paired again. | One maintenance window, measured in rehearsal; no service fee. |

## Threat model

The boundary is between teams reached through Cairn's own interfaces: HTTP and WebSocket routes, paired devices, connectors, runner protocol messages, and data a job copies between rows. A process that runs on the server host as the installation owner's OS user (the desktop app's own runner, a host shell step) can already read the owner's files, including the database, and is outside this design. A team that must not share the owner's data runs its steps on a machine it registers, never on the owner's host.

## The team scope is the boundary

**A verified team scope object is the only way to obtain any protected handle.** A resource is protected if Cairn must establish team or narrower authority to access it or act on it, whether it is held by Cairn or by a provider. This applies by default to new resource types and sinks; the sections below are instances, not an allowlist of kinds.

The scope module owns issuance and raw access. The opaque scope binds the admitted installation, team, principal or job authority, operation, and current generation. It issues non-forgeable handles for the exact target, owner, permitted operation, and generation. The sink checks that binding at use, including after an await that can change authority. A handle cannot be unwrapped, widened, or rebound; IDs, locators, returned data, and a successful scoped lookup are not handles for a subsequent effect. Operations combining handles must use the same scope identity, not just equal team IDs; the module checks identity at runtime. An explicitly shared source is opened with a narrow grant within the consuming scope, not by borrowing another team's handle.

- **Request admission:** only a registered surface adapter can verify its credential and obtain the bound scope. Verify the trusted listener/installation binding where applicable; caller or receiving-app team values are not proof. A resource grant yields only its admitted operation, never a team-wide opener.
- **Jobs:** only registered job entrypoints can enumerate eligible opaque roots, then reopen the corresponding scope for the exact job kind, root and generation. One job invocation holds exactly one root scope: every read that can influence its control flow or output and every write it makes go through that scope, so a foreign row can neither supply content nor decide a branch. A job that must touch two roots is split into one invocation per root joined by a committed delivery edge. The gate rejects a job module that opens a second scope, keeps a scope across invocations, or imports raw access; the watchdog's gate-verdict and repeated-failure branches ([worker-watchdog.ts:45–118](../../apps/server/src/services/worker-watchdog.ts#L45)) are the negative control. No opener takes a team or payload ID as authority; request and job openers are not interchangeable.
- **Services and transactions:** receive the scope, an operation-specific view of it, or its same-scope transaction, never ambient authority. Derive owners and foreign keys from verified parents. A move resolves both parents in the same scope and updates its dependent edges atomically or rejects. Keep private-owner restrictions and remove the old access path at cutover.
- **Caller-chosen identifiers:** an ID supplied by a runner, device or client is never a global key. The server mints the row's primary key; the caller's ID is stored as a client key unique per (team scope, parent, client key), so an insert or upsert can conflict only with a row in its own scope and its outcome reveals nothing about other teams. The schema manifest lists every table that accepts a caller-chosen ID, and the gate rejects a scoped insert whose conflict target is not scope-qualified; the runner transcript insert ([machines.ts:852–886](../../apps/server/src/services/machines.ts#L852), `message.id` in [schema.ts:349–365](../../apps/server/src/db/schema.ts#L349)) is the negative control.
- **Copied content:** every value read through a scope handle carries that scope as a type brand that survives string derivation inside the scope module's helpers (snippet, summary, redaction). A writer accepts protected content only as a branded value of its own scope, or as a literal produced by the code itself; passing a plain string read elsewhere into a protected write is rejected by the same AST gate. The watchdog's `build.errorMessage` snippet into a notification ([worker-watchdog.ts:74–117](../../apps/server/src/services/worker-watchdog.ts#L74)) is the negative control: with both scopes live, content read in team A and written to a team B notification fails to compile.
- **Boundary-only operations:** pre-admission credential verification, due-root enumeration and installation control use fixed entrypoints inside the module with minimal outputs, never caller-built queries, raw handles, or protected content. Offline maintenance is a separate named executable over an explicit offline dataset, unreachable from the request/job graph; it returns reports or sealed artifacts, not handles. Raw fixture access is limited to fixture-owned data.

### One release-blocking AST/import gate

The same dependency/AST gate checks scope issuance, handle construction and consumption, and every route to a raw protected operation. Its checked manifest names exact entrypoints, files, and symbols for boundary internals, admitted adapters, and isolated offline/fixture paths. A boundary file is not a blanket exemption. Outside approved scope-module internals, forbid bare SQL, drivers and raw schema, raw filesystem and path operations on Cairn data directories, raw credential reads and decryption, raw repository access, and hub publication without a scope-issued handle. Raw authority cannot leak through an export, returned path or credential, injected dependency, or an API accepting arbitrary predicates, owners, targets or event bodies in place of handles. Only an enforceably narrowed credential may cross the boundary as bearer material.

Scan the executable dependency graph and invocation sites repo-wide, including shell, Python, helpers, SDKs and subprocess wrappers. Resolve aliases, re-exports, forwarding, loaders and command invocations to their underlying operations. Require raw effect dependencies to be classified as scope-module internals or proved unrelated to protected resources before consumers can use them. For filesystem/path use outside the scope module, prove the target is outside protected roots; a constructed, injected, or unresolved path is not evidence of that. Fail on unresolved access paths or unclassified sinks, not just known API spellings. Check every protected sink's contract for an opaque handle, even inside an admitted adapter. Require a manifest entry and acceptance case for each adapter and sink; enforce the gate in the required CI code checks ([ci.yml:174–179](../../.github/workflows/ci.yml#L174)). Route deploy lease, drain status and snapshots through named boundary commands rather than direct SQLite ([deploy-self.sh:350–367](../../scripts/ops/deploy-self.sh#L350), [backup-server-db.sh:149–150](../../scripts/ops/backup-server-db.sh#L149), [restore-drill.py:39](../../scripts/ops/restore-drill.py#L39)).

Use the same gate's negative controls for known raw call sites even when relocated into an otherwise admitted consumer. Include a deploy SQL write, indirect raw opener, aliased or forwarded raw dependency, caller-supplied owner, and a service opening another scope through a job or request entrypoint. Require scoped replacements and isolated fixtures to pass. Type checks and two-team behavior fixtures complement this one gate; compiler visibility alone does not enforce it.

### Scope is required to build a query

A protected query takes opaque `ScopedTable<S, Table>` handles minted by the scope for every table occurrence, including aliases, join operands, subqueries and mutation targets. A transaction mints handles usable only within that transaction. The private SQL emitter consumes only the closed typed query representation. It applies `team_id = boundTeam` to reads, updates and deletes without changing outer-join semantics, stamps insert ownership, and applies the bound team and exact-owner tuple to conflict resolution and the update target. No foreign conflict is updated, returned, or published. Deferred schema constraints complement, not replace, scoped query execution.

Compile-negative cases cover raw/unbound tables, cross-scope joins and owner overrides. The AST controls reject the current bare step lookup and message upsert even in a store method and accept their scoped replacements ([machine-deps.ts:70–79](../../apps/server/src/services/machine-deps.ts#L70), [machine-deps.ts:106–127](../../apps/server/src/services/machine-deps.ts#L106)). Two-team fixtures cover outer joins, subqueries, inserts, updates, deletes and conflict updates.

## Exact-parent key manifest

Use globally unique, non-reusable conversation IDs and a registry of `(team, kind, id)`; resolve kind from storage, never prefixes. SQLite enforces the listed relationships with foreign keys to matching `PRIMARY KEY`/`UNIQUE` tuples and checked owner variants. Enable and assert FK enforcement on every writer connection. Required tuple components are non-null. Optional links are explicitly absent or complete; partial-null tuples cannot bypass checking. Storage constrains reads, joins, deletes and conflict targets in addition to the constraints on writes. A public ID is a locator within a scope, never an authorization source.

## Import source boundary

Check the source and destination independently **before** previewing, listing or opening source content. An import receives a scoped destination and a read-only source handle, never authority from `localPath`, a URL, or `sid`. Team-managed sources carry their exact owner and source generation. Explicitly shared local sources come from a trusted installation registry with a read-only grant for the admitted team and principal; a shared handle cannot become a write destination or expose another team's managed root. An external source handle binds the exact repository, ref and path to the connection and authorization generation that may read them, or to a verified public source without a private credential. File names and remote locators select only within that handle.

All Cairn data-directory file effects, including opens for reading or writing, listing, moving and cleanup, go through opaque file handles bound to the exact owner, root and generation. A scoped attachment lookup yields a handle or scoped stream, never a path a route can reopen. The scope module confines resolution and use with stable root-relative opens or sealed snapshots, rejects traversal and unverifiable aliases, and never reaches another team's root or the recovery archive through a shared parent. Candidate discovery uses the same read handles; invalid sources appear absent. The AST gate rejects the existing attachment path handoff even after a scoped lookup ([attachments.ts:310–346](../../apps/server/src/services/attachments.ts#L310), [routes-uploads.ts:75–90](../../apps/server/src/routes-uploads.ts#L75)); accept its scoped replacement. Pause thumbnail capture, retire the attachment, then resume and assert no write or publication; keep the current-generation path working ([page-thumbnails.ts:72–99](../../apps/server/src/services/page-thumbnails.ts#L72)).

For refresh, resolve the skill by `(team, skillId, skillGeneration)` and the exact source record for that skill generation in the same store. Resolve that record's current read handle again; a saved path or prior import is not permission. The managed files and source record share the skill owner and generation. Stage bytes privately and publish both as one visible generation after the scope rechecks both bindings, or retain the old generation without a partial write. Today refresh resolves the skill and its source by `sid` in installation-wide paths ([routes-resources.ts:222–229](../../apps/server/src/routes-resources.ts#L222), [routes-resources.ts:490–494](../../apps/server/src/routes-resources.ts#L490), [skill-import.ts:544–579](../../apps/server/src/services/skill-import.ts#L544), [skill-source-store.ts:51–61](../../apps/server/src/services/skill-source-store.ts#L51)). Installed skills are instance-scoped: all teams share one managed skills directory, and a source record's team tag is refresh provenance, not a filesystem boundary.

### Project repository bindings

A project row authorizes access to project metadata, not its repository. Treat a repository as a separately authorized source. On create, attach, conversion, or retarget, verify both the project operation and a live grant for the exact source before its first probe, listing, or read. In the scoped write transaction, recheck the grant after any await and atomically save the binding, keyed to the project incarnation and a new binding generation. A failed change keeps the previous binding without publishing a new locator. Locators remain selectors, not authority. Hosted repositories use the exact team-owned provisioned repository identity and generation; a project without a repository remains valid.

- **Local checkout:** only the admitted installation owner, in their bound team, can bind a checkout in a trusted owner-approved root registry or use it directly. The grant pins the host, owner/team, exact checkout identity, and root generation. Apply the import file boundary before any filesystem probe or Git operation, including repository metadata and dependent paths. Reject root substitution or escapes into foreign or recovery storage. A runner or job may act only on the owner's live, operation-specific delegation for that project, repository generation, and designated host/runner; ordinary team membership, a paired device, and a stored path give no local-path access. Directory discovery is owner-only and scoped to the same roots.
- **GitHub:** require a grant for the exact provider repository identity and operation, through a verified connection belonging to the requesting team. Bind the connection identity, authorization generation, repository identity, and grant generation. Installation membership alone cannot issue a team grant. Do not use another connection or an anonymous fallback when a grant is missing or denied.

Apply the claim-bound handoff below. For GitHub, the scope mints through the [installation access token API](https://docs.github.com/en/rest/apps/apps?apiVersion=2022-11-28#create-an-installation-access-token-for-an-app) with the exact repository (`repository_ids` preferred) and explicit minimum `permissions`. Verify both returned restrictions, accounting for required baseline permissions. Broker any grant the provider cannot represent, such as finer ref restrictions, or deny it. For owner-local delegation, hand off only an enforceably confined capability or snapshot; links, worktree metadata and shared Git objects must not expose sibling or owner data. Otherwise use the owner-side broker or deny.

Each consumer obtains the current repository handle from the scope, not the project row, before browsing, importing, running tools, opening caches, handing off checkouts or accepting snapshots. Revocation, disconnection, root replacement or retarget retires the old generation; discard late work. Missing and foreign sources have the same result without revealing locators or metadata.

## Replay, dispatch, and delivery

Work is unclaimed → claimed for an exact runner and generation → terminal. Delivery is pending → committed/replayed or cancelled. Scope and current state must be checked at the effect boundary, not only at handler entry. After an awaited body or provider call and before settlement, reauthorize in the same-scope transaction; record state changes and required stop/outbox intent together. Before emitting already committed work, recheck the current binding and destination at the last server-controlled handoff. No unchecked await may intervene; if a writer waits for capacity, check again when it can hand off. An invalidated generation cannot settle, publish, or obtain credentials. Bytes or remote effects already handed off cannot be recalled. Do not hold a DB transaction across network I/O.

### Worker cache authorization

Use a typed cache namespace opened only from a verified team connection and exact external resource handle. Key cached payloads, ETags, derived results, and in-flight requests/waiters by team, connection identity and authorization generation, exact provider repository identity and mapping generation, and the requested resource and representation (for example PR number, or compare commit pair). A repo name and PR number are locators, not keys on their own. Any permitted public/anonymous read uses a separate team-bound public authorization namespace and never replays private results or validators. There is no global fallback, including on upstream denial.

Connection revoke, disconnect, replacement or permission changes retire the old authorization generation and invalidate its whole namespace, including validators, derived entries and in-flight work. Repo remapping retires the matching resource namespace. Fence reuse at the generation change, not when eviction eventually completes; discard late completions and do not let them refill a retired namespace. Check current connection and resource authorization at cache lookup, after any wait, before a cache fill, and again before settlement. A warm hit is usable only with current evidence of resource access; if local state cannot establish access, confirm through the same authorized connection before use. A `304` replays only the exact entry whose validator was sent under that same live binding; an absent entry, denial or stale binding yields no result and no state change.

The denied team must not get a warm hit, send the other team's validator, replay a conditional response, join the other team's in-flight work, or advance a task. Test same-binding hits and `304` replay, revocation/replacement or remap during a paused request, and denial after a previously authorized fill; assert that late results neither refill the cache nor settle work.

For **every concrete entry** use two-team fixtures with real parents. Prove own-team behavior and indistinguishable missing/foreign resource results where applicable, and no foreign row, file, frame, dispatch or settlement. Exercise recovery and job dispatch independently of HTTP with paused external work, deletion/replacement and restart. Include pre-change failing invariant tests or compatibility controls for paths already scoped.

## Executable migration provenance and accounting

Stage from an immutable legacy snapshot. Every source table and side-store class has an executable, versioned classifier with explicit evidence inputs, exact-owner checks, conflict rules and disposition codes. Start from proven teams/principals and typed root chains, not guessed context. Run the classifiers against the frozen input in dependency order and persist their decisions before consuming them as a rewrite plan. Retain uncontested IDs **after proof**. For a collided conversation ID, reserve the old ID as retired, then allocate replacement IDs for its proven typed roots in stable source-key order from a deterministic mapping of snapshot identity and typed root key. Reserve all kept and retired IDs before allocation and resolve allocation conflicts deterministically. Rewrite only proved edges and rebuild derived indices from those decisions. Retired IDs never resolve. Never use rewritten rows or a migration-created owner field as proof of their own origin.

Missing or conflicting evidence must produce an explicit reason code, not a fallback inference.

### Current-revision authorship and content lineage

Apply this rule to every retained row or file whose payload or metadata a legacy job, callback, importer, or recovery path could overwrite, copy, or derive from another team's content. This includes insert-only records and copied summaries, not just mutable transcripts. An exact destination FK proves neither the producing operation nor the source of the content. The phase-1 provenance manifest inventories writers and readers (including historical SQL, side-store writers, backfills, mirrors, and replay) per persisted field or payload group: record the destination, all producing operations, source identities/revisions, historical scope enforcement and evidence, propagation paths, and a retention or rebuild disposition. Classify a path outside this rule only with recorded proof it could not import foreign content, or because it is retired without reuse. An unclassified write or copy path blocks release.

Accepted evidence binds the frozen source table/file and key, original owner/incarnation, authorized producing operation and scope, exact input identities and revisions (including independent authorization for any permitted shared source), and actual committed output. Verify a trusted attestation against a versioned digest of all persisted fields used by reads, recovery or replay, including mutable metadata. A complete authenticated history is equivalent only if it proves the same final revision, including the lineage of inherited fields and copied or derived inputs, with no gaps or conflicting writes. Evidence must be independent of the legacy target and prove the actual producing write, not merely match bytes previously supplied by an authorized writer. Foreign, stale, missing, or conflicting evidence yields an explicit authorship/lineage reason and quarantines the unproved source row or artifact intact. Do not attribute it to either team or launder its payload through mirrors, seeding, indexes, or downstream copies. Rebuild replaceable projections only from independently proved inputs.

For each table, enumerate a stable identity for every source row (legacy primary key or snapshot row identity). A restricted ledger assigns **exactly one** of `kept`, `rekeyed`, `quarantined`, or `explicitly invalidated` to each source key, with classifier version, evidence reference/reason code, and appropriate destination key, archive reference, or invalidation record. Track invalidated links separately from kept owner rows. Same accounting for affected files, including digests and generation paths. Check `source count = kept + rekeyed + quarantined + explicitly invalidated` per table, no duplicate/unaccounted source keys, unique and existing active/archive destinations, and no unexplained new rows; reconcile new registry/derived rows in a separate generated-row ledger. Restrict the full ledger/archive to offline recovery; release evidence reports only aggregated counts and reason codes.

Commit the staged DB rewrite, ID map, ledger and completion marker in the **same transaction**; bind the staged file manifest/digests to that generation and publish it as ready only after file staging is durable. Key completion to the immutable input identity and migration version. On restart, an incomplete stage is not eligible; resume the same plan or restage from the immutable input. A matching completed stage is reusable only after verification. This must not use the current post-migration check for only new FK violations or the separately recorded one-shot helper ([db/client.ts:26–50](../../apps/server/src/db/client.ts#L26), [data-migrations.ts:6–15](../../apps/server/src/services/data-migrations.ts#L6)). Require a clean full `foreign_key_check`, executable zero-violation ownership/variant queries, the SQLite trigger gate, file manifest reconciliation and exact ledger reconciliation before activation.

Migration fixtures pair an independently attested legacy row with an otherwise identical bare-ID row lacking proof; only the former is active. Include a formerly different owner with one surviving parent, a colliding ID, stale credentials, conflicting evidence, wrong parents inside a team, unprovable receipts and file orphans. For each transcript writer, include a valid owner attestation followed by a foreign ID-conflict overwrite that leaves the original parent unchanged. The ownership-only control would keep it; the classifier must quarantine it, including when the row has a valid typed FK or retains original origin metadata. Also reject a stale revision attestation and a history with a missing write; keep a transcript with independently attested current authorship, preserving its payload. For memory receipts, start with a valid Team B edit and FK but a Team A producing turn and source document; an ownership-only classifier would retain the receipt. Require quarantine and absence from edit reads, retry summaries, tool-result replay and settlement. Pair it with a fully attested same-scope receipt, and reject a same-team wrong attempt or source revision and a stale or tampered payload attestation. For each copied-content family, exercise a valid destination with an unproved or foreign source, including a downstream copy of a quarantined revision; keep or rebuild an independently proved control. Assert source-row dispositions and destination keys, not just total counts, and no active projection, file, replay or dispatch from quarantined payloads. A crash before DB commit, after DB commit but before files are durable, and after readiness but before activation all leave production closed. Restart and repeat-upgrade of identical input must produce identical mappings, dispositions, counts and file digests without duplicate rows or a skipped rewrite.

## Phases and activation fence

1. **Inventory and red tests.** Freeze the concrete edges, admission and consumer manifest, including all protected effects, raw access, triggers and content lineage. Pin the authorized cases and require the gate's negative controls and two-team regressions to fail on the old paths before changing behavior. Replace parentless runner fixtures with real chains.
2. **Implement dependency groups, not production modes.** Move each group together with its readers, writers, publishers and jobs. No deployment permits old and scoped consumers to read or write shared data together; no group flags, shadow writes, or dual-path fallback. Exit only when the unified AST/import gate and manifest-wide exact-parent, admission, async and job tests pass. Do not ship the existing incremental route patch as the isolation boundary.
3. **Fence, snapshot and stage offline.** Close mutation admission first (including callbacks, upload grants, runner claims and connections); drain or cancel in-flight work and invalidate old generation/lease authority. Stop and fence the old binary and independently launched writers/resumers. The fence is durable and enforced at the launcher and operational commands as well as at server admission; it survives a restart and does not rely on the old binary knowing the new schema. Prove no live writer remains. Take a consistent immutable backup of the old binary/version, DB and matching affected files, including Coordinator stores, step sessions, attachments and other manifest-listed assets. Rehearse from a copy with dispatch disabled and stage a complete new DB/file generation, never in-place on the old dataset. Failure leaves the writer fence closed; incomplete generations are not selectable.
   Every credential delivered outside the server before the fence is treated as compromised by the cutover: revoke outstanding step tokens and runner leases, and rotate each team's connector secrets that a runner could have received as raw values (for example a saved Composio API key returned by the legacy step-token route, [routes-machine.ts:648–651](../../apps/server/src/routes-machine.ts#L648)). Activation is refused until the rotation ledger lists every such credential as rotated or revoked; afterwards runners receive only claim-narrowed credentials or broker handles. A credential that cannot be rotated by Cairn is reported to the owner with its connector, not silently kept.
4. **Prove the no-writes state.** `staged` means validated and sealed, not selected for normal startup. The verifier opens both generations read-only; no protected DB or file mutations are allowed from ready staging until activation. Enforce the startup interlock **before** writable config/bootstrap, opening a migrating DB, skills/key preparation, seeds/backfills, listener admission, Coordinator initialization, scheduler, mail or IM resume, or external dispatch. These paths currently run during startup ([index.ts:103–163](../../apps/server/src/index.ts#L103), [index.ts:316–355](../../apps/server/src/index.ts#L316)). Rehearse restoring the old binary **and its matching DB/files** while still fenced; validate that set via offline checks without normal startup, then return to the validated staged set. Exercise a normal launch, operational command, delayed callback and attempted job resume against a sealed stage; inject failed checks and crashes around selection. Assert protected DB/file digests unchanged, no new seed rows or due events, and zero connector resumes or dispatches. Control metadata and logs are outside the protected generation.
5. **Activate once.** Require exact-head independent security review, green CI, isolated two-team product/worker evidence, reconciled data/file ledgers, and a measured backup/restore window. Under the same exclusive writer fence, a durable explicit activation record selects one sealed generation by binary/schema version, DB milestone, and file manifest identity. No independent DB/file switches. Normal startup validates that selection before any write-capable initialization; only the selected generation may release writers or dispatch. A crash before the record stays fenced; a crash after it resumes the recorded generation or fails closed, never falls back or mixes files. Before activation, rollback selects the old matching set while still fenced; only an explicit rollback decision reopens the old generation. After activation, repair forward; restoring the old generation requires owner approval to lose writes since the backup.

Owner approval is required before production cutover if rehearsal finds stranded durable work, invalidated user access or an unacceptable outage window. Report the affected counts explicitly: a legacy installation with no independent attestations may strand otherwise visible conversation history or work. No such decision is needed to implement and rehearse this design. WeChat start coalescing and any future supported graph import are out of scope for this release.
