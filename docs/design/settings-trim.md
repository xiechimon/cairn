# Settings Trim: Single Page Headings & Automatic Runner Token Rotation — plan, 2026-11-28

Prior art: `docs/research/runner-token-rotation-2026-11-27.md`.

## User scenario

A newcomer who installed Cairn today opens **Settings** (`apps/web/src/settings/settings-page.tsx`).
1. When they open **Settings → Chat apps** (`聊天应用`, `apps/web/src/routes/im-page.tsx`), they see one heading `聊天应用` with its `(i)` `InfoTip` beside it, rather than seeing `聊天应用` repeated as both the page heading and the sole section heading below it. Every Settings page follows the same rule (no sole section repeating its page title). No new accounts, keys, or storage are used.
2. When they open **Settings → Runners** (`执行机`, `apps/web/src/resources/machine-row.tsx`) and click the `...` row menu, they see only two actions (`设为默认执行机` / `已是默认执行机` and `删除执行机`). Per owner decision (2026-11-28: users never see token rotation; remove the menu item and its copy, keep the in-place rotation mechanism and run it automatically on a fixed interval and whenever a runner re-registers with no UI), `更换令牌` / `确认更换令牌` and rotation reconnect banners/drawers are removed. In-place runner token rotation runs automatically in the background every 7 days for online runners (and resets on every runner re-registration) via the existing `dueEvent` schedule table and SSE `token.rotate` → `claim` → `ack` handoff. If a runner is offline or fails to acknowledge during an automatic rotation, its current token stays valid and the server retries silently later (and rotates 5 s after the runner next connects) so automatic rotation never locks out a runner or interrupts the user.
3. For any pre-upgrade row that already had `tokenReauthRequired = true` (or if the retained owner-authenticated programmatic API `POST /api/machines/:id/rotate-token` is called offline), the row displays as standard `离线` with no rotation UI; local desktop runners re-enroll on restart (`verifyStoredMachine` `401` → `enrollLocalMachine`), remote CLI runners log the `cairn logout && cairn start` recovery guidance on `401` in `apps/daemon/src/machine-loop.ts`, and reconnecting clears `tokenReauthRequired = false`.

4. Automatic in-place runner token rotation (`apps/server/src/services/due-events.ts`, `machine-rotate-token.ts`, `machines.ts`, `machine-revoke.ts`, `routes-machine.ts`, `routes-resources.ts`, `scheduler.ts`):
   - Extend `due-events.ts` with atomic reservation compare-and-set (`reservedDueAt` returned by `reserve`, with `finishSuccess`, `recordFailure`, and `settleDetached` filtering `.where(and(eq(dueEvent.id, event.id), eq(dueEvent.dueAt, reservedDueAt)))`), and optional `intervalMs?: number | null` on `DueHandlerResult`. Any concurrent modification to `dueAt` (or deletion) while an async handler is in flight or settling causes the handler's stale writeback to no-op cleanly instead of clobbering `enrollMachine`, `armOverdueTokenRotationOnConnect`, or `cancelMachineTokenRotation`.
   - Persist per-machine rotation schedules in the existing `dueEvent` SQLite table (`id = "token-rotate:${machineId}"`, `kind = "machine-token-rotate"`), using `7 days` (`MACHINE_TOKEN_ROTATION_INTERVAL_MS`), `1 hour` retry (`MACHINE_TOKEN_ROTATION_RETRY_MS`), `5 s` post-connect grace (`MACHINE_TOKEN_ROTATION_CONNECT_GRACE_MS`), and `MAX_CONCURRENT_AUTO_ROTATIONS = 4`.
   - Distinguish schedule mode via `dueEvent`: normal 7-day schedules store `intervalMs: null, attempts: 0`; retry schedules (`'offline'`, `'deferred'`, `'skipped'`, or exception backoff) store `intervalMs: retryMs` (or `attempts > 0`).
   - Re-registration (`enrollMachine`, `authorizeEnrollmentMachine`) mints a fresh token, calls `scheduleMachineTokenRotation(db, machineId, now + 7d)` (setting `intervalMs: null`, waking the clock listener), and cancels retired duplicates' `dueEvent` rows. `DELETE /api/machines/:id` and `revokeMachineToken` call `cancelMachineTokenRotation(db, machineId)` (and wake clock).
   - `scheduler.ts` (`syncDueSources`) seeds missing `token-rotate:${machineId}` rows for active enrolled machines (`retiredAt IS NULL AND tokenHash IS NOT NULL`) spread deterministically by `machineId` across `[now + intervalMs * 0.5, now + intervalMs]` (`intervalMs: null`) to prevent thundering-herd expiry after upgrade, and prunes rows for deleted/retired/unenrolled machines; handles `machine-token-rotate` via `processMachineTokenRotationDue`.
   - `GET /api/machine/stream` (`routes-machine.ts`) calls `armOverdueTokenRotationOnConnect(ctx.db, row.id)` AFTER writing `{ type: 'hello', connectionId }`: if missing, inserts `dueAt = now + intervalMs, intervalMs: null`; ONLY if `existing.dueAt <= now || existing.intervalMs !== null || existing.attempts > 0` (overdue, in retry, or post-error backoff — never a normal 7-day countdown) and `(existing.dueAt <= now || existing.dueAt > now + graceMs)`, updates `dueAt = now + graceMs, intervalMs: retryMs, attempts: 0, lastError: null` and notifies the registered clock listener (`dueRunner.arm()`).
   - Automatic rotation (`rotateMachineTokenAuto`, sharing the SSE `token.rotate` → `claim` → `ack` handoff core) NEVER calls `commitOfflineFallback`, NEVER invalidates `oldTokenHash` on offline/timeout/disconnect/push failure, and NEVER sets `tokenReauthRequired = true`. Offline runners return `'offline'` synchronously with zero 5 s wait, and concurrent in-flight auto rotations beyond `MAX_CONCURRENT_AUTO_ROTATIONS` return `'deferred'` immediately, preventing scheduler head-of-line blocking or burst load.
   - `ackMachineTokenRotation`: reschedules `token-rotate:${machineId}` to `now + 7d` (`intervalMs: null`) ONLY when `tokenHash` actually transitions (`pending` or `stagedRow` branch), never on an idempotent replay of an already-committed token; in the `stagedRow` branch, rejects with `401` if `hubMap.has(stagedRow.id)` (a newer rotation round is already active).
   - Race-safe `processMachineTokenRotationDue`: wraps `rotateMachineTokenAuto` in `try/catch` (logging non-secret `{ machineId, err }` on failure so `recordFailure` never clobbers concurrent writes), snapshots `startedAt` and `initialTokenHash` before `await`, logs structured non-secret outcome on `'deferred'`/`'offline'`/`'skipped'`, and re-reads `machine` and `dueEvent` right before returning `{ rescheduleAt, intervalMs }` to `finishSuccess` (paired with `due-events.ts` `reservedDueAt` CAS):
     - If `!after || after.retiredAt !== null || after.tokenHash === null` → returns `{ rescheduleAt: null }` (`finishSuccess` deletes `dueEvent` if `dueAt === reservedDueAt`).
     - If `after.tokenHash !== initialTokenHash` (rotated by us, late `ack`, or concurrent re-enroll) → returns `{ rescheduleAt: Math.max(finishNow + intervalMs, existingDue?.dueAt ?? 0), intervalMs: null }`.
     - Otherwise (`'offline' | 'deferred' | 'skipped'` or caught error): if `existingDue` was already armed by `armOverdueTokenRotationOnConnect` during flight (`existingDue.intervalMs === retryMs && existingDue.dueAt > startedAt && existingDue.dueAt <= finishNow + graceMs`), returns `{ rescheduleAt: existingDue.dueAt, intervalMs: retryMs }`; else returns `{ rescheduleAt: finishNow + retryMs, intervalMs: retryMs }`.
5. Keep unchanged: `POST /api/machines/:id/rotate-token` manual API, daemon `token.rotate` handler, `POST /api/machines/:id/revoke`, `machine.id`, `team.defaultMachineId`, `routingRule`, `step`, `phone`, `computer`, and all other Settings pages' layouts and controls.

## State, Readers, Writers & Failure Paths

- **`dueEvent` (`id = "token-rotate:${machineId}"`, `kind = "machine-token-rotate"`)**:
  - Readers: `createDueRunner` (`due-events.ts`), `armOverdueTokenRotationOnConnect` (`machine-rotate-token.ts`), `processMachineTokenRotationDue` (`machine-rotate-token.ts`), `scheduler.ts` (`syncDueSources`).
  - Writers & clock wakeups: `createDueRunner` (`reserve` records `reservedDueAt` and sets `dueAt = reservedDueAt`; `finishSuccess` updates `dueAt`/`intervalMs`/`attempts`/`lastError` or deletes on `rescheduleAt: null` guarded by `eq(dueEvent.dueAt, reservedDueAt)`; `recordFailure` increments `attempts` and sets exponential backoff guarded by `eq(dueEvent.dueAt, reservedDueAt)`), `scheduleMachineTokenRotation` (called by `enrollMachine`, `authorizeEnrollmentMachine`, and `ackMachineTokenRotation` on transition; sets `intervalMs: null` and invokes `notifyTokenRotationClock`), `cancelMachineTokenRotation` (called by `revokeMachineToken` and `DELETE /api/machines/:id`; deletes row and invokes `notifyTokenRotationClock`), `armOverdueTokenRotationOnConnect` (called in `routes-machine.ts` after `hello`; sets `intervalMs: retryMs` and invokes `notifyTokenRotationClock`), `scheduler.ts` (`syncDueSources` seeds/prunes; `start()` registers `setMachineTokenRotationClockListener(deps.db, () => dueRunner.arm())`, `stop()` clears it), and `processMachineTokenRotationDue` (returns `{ rescheduleAt, intervalMs }` to `finishSuccess`).
- **`machine.tokenHash`, `machine.pendingTokenHash`, and daemon `machine.json` / `pending-token-rotation.json` convergence**:
  - `staged` (`pendingByHub` holds `newTokenPlain`) → `claimed` (`claim` sets `pendingTokenHash = H(new)`, keeps `tokenHash = old`) → `pushed` (`ack` atomically promotes `tokenHash = H(new), pendingTokenHash = null, tokenReauthRequired = false`, calls `handoffConnection`, schedules `dueEvent` `+7d`).
  - Convergence across failures:
    - Offline or SSE `pushTokenRotate` failure on due tick: returns `'offline'`/`'deferred'` immediately; `oldTokenHash` untouched; `dueEvent` marked `intervalMs: retryMs`, `dueAt: now + 1h`; reconnect arms `now + 5s` after `hello`.
    - Caught error inside `processMachineTokenRotationDue`: handled within `try/catch` (logs non-secret `{ machineId, err }` and runs the exact same post-await `machine`/`dueEvent` reconciliation before returning `{ rescheduleAt }` to `finishSuccess`, so `recordFailure` is never triggered to clobber concurrent `enrollMachine`/`armOverdueTokenRotationOnConnect` writes); surviving `dueEvent` resumes automatically across server restart via `syncDueSources` + `dueRunner.arm()`.
    - Claim response lost / `savePendingTokenRotation` disk-write failure: daemon skips `ack` and keeps `T_old`; server auto-mode times out without touching `tokenHash` and retries `+1h`.
    - Claimed-then-timeout before `ack`: server keeps `tokenHash = H(T_old)` and `pendingTokenHash = H(T_new)`; late `ack` promotes `T_new` and schedules `+7d` unless a newer round already started (`hubMap.has(id)` → `401`, or newer round claimed and overwrote `pendingTokenHash`).
    - `ack` response lost / `finalizeRotatedToken` disk failure after `ack` `200`: `pending-token-rotation.json` was written before `ack`; daemon retries or runs `replayPendingTokenRotation` on reconnect, hitting idempotent `200` on `committed` without resetting any newer rotation schedule.
    - Handoff 45s grace expires without reconnect: `markOffline` runs; `T_new` is already persisted on daemon, so next connect authenticates cleanly.
    - Concurrent `enrollMachine` / `DELETE` / `revokeMachineToken` / `armOverdueTokenRotationOnConnect` during in-flight `rotateMachineTokenAuto`: post-await synchronous check in `processMachineTokenRotationDue` deletes `dueEvent` on retirement/deletion, preserves `enrollMachine`'s `+7d` schedule when `tokenHash` changed, and preserves `armOverdueTokenRotationOnConnect`'s `+5s` arming.
- **Capacity & diagnostics**:
  - `syncDueSources` staggers initial seeds across `[intervalMs * 0.5, intervalMs]`; offline machines return synchronously with zero wait; active concurrent auto-rotations cap at `MAX_CONCURRENT_AUTO_ROTATIONS = 4`; deferred/offline/error outcomes log structured `{ machineId, outcome }` diagnostics (no secrets) so persistently unresponsive old-version runners are observable without stalling the shared scheduler.

## Out of scope

- Deleting `POST /api/machines/:id/rotate-token` or dropping `machine.pendingTokenHash` / `machine.tokenReauthRequired` SQLite columns.
- Exposing token rotation interval settings or rotation history in the UI.
- Changing layout or headings of Settings pages that do not repeat their page title.
