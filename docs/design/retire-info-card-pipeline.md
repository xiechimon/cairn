# Retire the info-card pipeline and fire schedules in the Coordinator thread — plan, 2026-11-27

## User scenario

Someone who installs Cairn today connects their Coordinator model and pairs one plain Mac Runner (with no Linux container or VM). In Coordinator chat they type a recurring request such as "Every morning at 9 AM, summarize the new features released yesterday by competitors (Amp, Cursor, Claude Code, Codex, Devin)".

- **Where they meet it and why it is there**: They ask in the Coordinator conversation and inspect or manage the created schedule under Tasks → Scheduled. Before this change, Coordinator created an `output: 'info'` task routed into a separate info-card pipeline that required a VM computer and custom `submit_report` tools, so it stalled or never replied on a plain Mac Runner. Now the schedule runs directly in the Coordinator thread using the user's own words, normal Runner web access (`web_search`, `browser_*`, shell), and replies in that thread.
- **What they must know, accounts/keys/storage**: They need to know nothing about info cards, VMs, or special report tools. Only their already configured Coordinator model/subscription and an online Runner (or in-server Coordinator runtime) are used. Schedules are stored in the SQLite `schedule` table referencing either `chiefThreadId` (Coordinator-thread schedule) or `todoId` (task schedule), with nullable `projectId`.
- **When it fails**: If the target Coordinator thread or project is archived, the schedule pauses (`'Thread archived'` / `'Task archived'`) and shows a localized pause reason in Tasks → Scheduled. If a scheduled turn fails transiently (network/capacity/quota/outage), `lastRunStatus` records `'failed'` and retries after 5 minutes (also re-arming `nextRunAt` for one-shot schedules so they are not dropped); permanent failures pause the schedule and surface `lastRunError` and a thread turn error card.

| Situation | What the user sees | What the system does | Wait and cost |
|---|---|---|---|
| Create recurring schedule via Coordinator chat | Coordinator confirms the daily 09:00 schedule; row appears in Tasks → Scheduled under the thread title | `schedule_todo` (omitting `todoId`, passing `prompt` + optional `tz`) inserts a `schedule` row on the current `chiefThreadId` (`todoId = NULL`) | Instant; zero extra model calls beyond the turn |
| Click Run-now in Tasks → Scheduled | Toast confirms queued run; promptly the scheduled prompt appears as a user turn in Coordinator chat and Coordinator replies with a researched summary | `runScheduleNow` (in `IMMEDIATE` tx) checks target ownership/busy state, sets `nextRunAt = now`, clears `due_event`, wakes scheduler clock; `fireSchedule` inserts user `chiefMessage` and enqueues a `chief` step | Single-timer wake; single Coordinator turn cost |
| Scheduled due time arrives | At 09:00 in the schedule's timezone, Coordinator posts the summary in the same thread and advances `nextRunAt` to tomorrow | `scheduler` atomically acquires thread turn in `IMMEDIATE` tx, CAS-updates `schedule`, inserts user `chiefMessage`, calls `enqueueChiefStep` (`trigger: 'user'`), notifies via `finishScheduledStep` | Exact timer wake; single Coordinator turn cost |
| Target thread busy or archived | Busy: recurring `nextRunAt` skips to next slot; `once`/`webhook` wait out the active turn (`nextRunAt` kept `<= now`) and fire once free without being dropped. Archived: schedule pauses cleanly | `scheduleChiefThreadTurn` checks active `chief` step on `chiefThreadId` and `archivedAt` inside `IMMEDIATE` tx; `runScheduleNow` returns 409 | Zero wait; zero model cost |
| Upgrade from existing DB with info-card rows | Non-`event` info-card schedules linked to a same-team unarchived Coordinator thread move onto that `chiefThreadId` preserving prompt; `event`/orphaned/cross-team schedules keep `todoId` as `output = 'code'` | Migration `0263` links via `todo.sourceKind = 'orchestration'` (`'chief-' || substr(sourceRef, 7)`); unfinished active info todos become `code`; `done`/`closed` historical info todos stay `info` | One-time startup migration; zero model cost |
