# Change Cairn settings in chat — plan, 2026-11-28

## User scenario

After installing Cairn, a newcomer can ask in the same chat where they start work: “Run a read-only task with Doubao Auto on my Mac mini” or “Switch to dark appearance.” They need an enabled model source and a runner capable of using it, but no additional account, payment or key for settings chat. A one-time model pick does not change their defaults or favorites. A successful settings edit shows what changed and **Undo** in the conversation, even after reload. A protected request shows **Open Settings** for the corresponding page. Nothing sensitive is handled in chat. Invalid input leaves Settings unchanged and says what to correct.

> An agent cannot control its own settings… I think my Coordinator should have full access to its own settings. We are AI-native, with very few exceptions.

Owner decision (November 28; translated from the original chat): broaden control over Settings, with narrowly defined exceptions. [Inventory and root cause](../research/coordinator-settings-2026-11-28.md): task creation currently mistakes a shortlist for authorization, and the tool contract repeats that mistake.

## Scope

1. **Model selection slice:** resolve explicit task models from the same list as `models`, keyed by `source.provider ?? source.runtime`. Deduplicate by qualified key, match exact qualified IDs before bare IDs (which can themselves contain slashes), and preserve a matching favorite's effort. Custom providers count as configured when registered (there is no enabled field); dispatch still requires the appropriate credentials. For subscription-only runtimes require an active subscription, or the existing supported local route if one is already available, not simply a favorite or a stale machine report. Doubao sources already require an enabled account and can exist before that account signs in on the target runner. Do not make login/liveness a catalog requirement; preserve the distinct dispatch block and fallback rules. Do not change favorites implicitly.
2. A generic `settings` tool exposes typed operations for eligible settings in the inventory: models/favorites/routing; provider metadata and model lists; computers' names/defaults; skills; apps/MCP; schedules; projects; appearance/language; notifications; memory. A server-owned registry maps `(section, operation)` to strict, narrow schemas, a shared mutation called by the UI route and tool, a public read projection, a journal adapter, and cache invalidation. Never expose arbitrary routes, headers, URLs, SQL, or the raw owner HTTP capability; the UI route retains existing HTTP auth and same-origin requirements. For settings already exposed as narrow tools, migrate them to the same policy and writer or retire them where replaced.
3. Next slice: persist a server-authored nullable owner actor ID on chat messages, only from the same-origin owner-session send endpoint, never MCP/API-key/connector/worker ingestion or `sentByAgent`. Reject legacy unmarked, non-user trigger, external-provenance and mixed turns even if an owner later joins them. For writes require cited `messageIds` and verbatim `quotes` resolving to current, marked owner messages in the same thread, via the existing task-request citation validator. This is provenance, not semantic proof of intent; only typed allowlisted fields can change. Use a deferred write tool on both runtimes, outside mail/report/memory and subagent catalogs; do not add it to generic read allowlists. Missing server step or stable `toolCallId` fails closed; unique `(stepId, toolCallId)` returns the prior result only for the same validated input. Undo is a same-origin owner action, scoped to the actor/team/thread. Unknown fields fail closed. Existing approvals for unrelated actions are unchanged.
4. **Dispatcher exceptions:** entering or reading any secret value, passwords, API keys, vault contents, provider sign-in (QR, device code, OAuth), remote-access tokens; money (billing, plan upgrade); deletion of the account, a project's data or history; editing the Coordinator's own permission rules. The next slice replaces the Coordinator aliases for secret create/update/delete and project deletion with safe page links, leaving the manual owner routes intact. Block credential fields, auth headers, unsafe endpoint changes on credentialed provider/connector records, connector tool-grant expansion, autonomy unpause/merge limits, and work-policy tools/secrets or equivalent authority changes. Map links from fixed enums, using the existing model/account/remote/API-key/project pages and the applicable existing controls for permissions (no invented permissions page). OS/browser consent and identity actions require a real user gesture.
5. Next slice allowlist only the signed-in account's theme/locale, team favorite list and runner display name (reversible setting fields). Store account preferences by user ID with nullable theme/locale and field revisions; after account hydration the saved value wins, and device-local values are initialization only. Both manual UI and chat use the same writer and validation. Emit a sanitized receipt containing only safe section/status and opaque change ID; private value details are fetched from the owner-bound endpoint. Do not change the existing generic action journal response. Register new settings keys in `scripts/product-surface-registry.json`. Later adapters cover the remaining inventory; no delegation of raw connector URLs, schedule prompts that grant new Coordinator authority, or skill/memory installation as an authority change.

### State and UI draft

The model selection slice introduces no persisted schema; `todo.request.model` remains the route's existing per-task override. For the next slice, use a separate private `setting_change` table with actor/team/thread, section/target, typed safe before/after, applied revision, state and unique call identity. The relay writes `applied` with the setting and receipt in one transaction; manual UI writes update the same section revision without creating a chat receipt. Owner Undo is the only transition to `undone` and only if the field revision matches; mismatch returns conflict without writing, repeat of `undone` returns the stored result. The owner receipt-detail endpoint is the only client reader of before/after. Keep owner/same-origin checks in HTTP and provenance in the relay; writers validate input and the target in both paths. Commit cache and routing release effects after persistence. No filesystem/network effects inside SQLite and no such adapter before a tested reversible effect plan. Rollout does not rewrite history.

In the existing Coordinator transcript, reuse its action-card treatment (plain label and a text action): `外观 · 跟随系统 → 深色    撤销`, `外观 · 已撤销`, or `API 密钥需由你本人管理    打开设置`. No changes to sidebar, composer, existing approvals, or message spacing. No empty card; initial arrival follows transcript growth and reduced motion; pending/duplicate clicks stay in the same action slot. Seed conflict, offline and 400 ms latency; check long names, a pending question, light/dark and 390/1440 px. Keep errors in the card without inserting layout above visible content. Validate focus, wrapping and pending/recovery with `apps/web/e2e/coordinator-settings.spec.ts`, then capture live pixels. The draft is not production evidence.

## Out of scope

- Changes to default task model policy, provider credential storage, payment, pairing, or deletion beyond removing Coordinator settings access to protected operations.
- Production verification outside the designated sandbox, changes to the owner's primary thread, or deleting any verification messages.
