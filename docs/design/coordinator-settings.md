# Coordinator settings — 2026-11-28

## User scenario

Someone new to Cairn asks the Coordinator to run a task with Doubao Auto on a particular computer. The provider must already be enabled; this does not sign in, buy a plan, or require a new key. Auto is not in the team's Frequently Used Models yet. Because the owner's own message names it, the Coordinator adds it with one settings call, says it added that model to the frequently used models in one plain sentence, and starts the task. The owner removes the entry in Settings whenever they want. If the Coordinator itself wants a model the owner did not name, the existing decision card asks first; a refusal leaves the list untouched and starts nothing. Unavailable, ambiguous or unqualified names come back as one plain sentence instead of a silent pick.

November 28 direction, translated: “Ideally the Coordinator can only pick from frequently used models, and it can add a model to that list, which may need the user's permission.” This replaces the behavior from `3f648e19b`, where an explicit task model bypassed the list. ## Scope

1. **Tasks pick from Frequently Used Models only.** `create_todo` resolves an explicit `model` against the enabled catalog (unchanged: unique qualified match first, bare id second, its configured thinking level preserved) and then requires the same provider/model pair to be in the team's frequent list. A configured-but-not-frequent model is refused with a sentence telling the Coordinator to add it first and naming that path; nothing is created. Omitting `model` keeps today's default routing. The `models` tool keeps marking `frequent: true` and its description says task picks are limited to those rows.
2. **One narrow settings operation adds a model.** A new server-executed `settings` tool supports exactly `addFavoriteModel` with `{provider?, model, messageId?, quote?}`. It resolves the name to one canonical catalog row (qualified `provider/modelId`, then bare id, then display name; several matches require `provider`), so “Auto” alone asks which provider instead of guessing, and a disabled or unknown model is refused. The write appends that one row, keeps order, effort and unrelated entries, and is a no-op when the row is already present. It never replaces the list, removes, reorders or touches any other setting.
3. **The owner's own words are the permission.** A direct append needs `messageId` plus `quote`: the message must be one of this turn's owner messages in this thread, `role: user`, not synthetic or a task prompt, and the quote must be an exact substring sitting in an affirmative clause that names the canonical model. ASCII ids match on word boundaries (Auto does not match automation); the clause must also carry a request verb (use, run, pick, switch, try, or the equivalent in the owner's language); a negation or hypothetical word before or after the quote (not, never, don't, unless, if, suppose, what if, and the equivalent Chinese words) is not permission, and a switch word after the quote ("switch away from it") is not permission, while a switch word before it ("switch to it") is. Abbreviations that never match the canonical name, opinions and plain remarks go to the card instead. The new server-written marker `chief_message.ownerComposedAt` is stamped only when an owner cookie session page submits the text without an Authorization header — the two same-origin composer routes. Messages inserted by tests, agents, MCP, reports, wakes, mail, IM bridges or a Bearer API client stay null. The tool is not replay-safe: an append already present is a no-op, but a replay after the owner removed the row adds it again.
4. **The Coordinator's own suggestion asks first.** Without a cited owner message the tool routes to the new `settings.favorite-model.add` action (class `confirm-once`, coordinator surface only). Its input is the canonical `{provider, modelId}` pair; its existing approval card asks whether to add that model to the frequently used models, with approve and decline options, and only an authenticated same-origin page click on that card appends, so the generic `/api/actions/proposals/:id/answer` route, an API caller or a remote bridge cannot approve it. Refusal, expiry or a failed handler appends nothing, starts nothing and wakes the thread with the outcome; an approved wake names the added model and tells the Coordinator to continue the original request. No standing grant.
5. **Everyone reads one state.** The Settings page keeps reading the same `team_top_models` row and its manual add, remove and reorder keep working. A chat append publishes the team reconcile event, so an open Settings page refetches; the Settings save carries the `updatedAt` it loaded and a newer append makes it return 409 instead of overwriting the chat row, after which the page refetches. Settings copy states the new rule. Dispatcher exceptions stay out of this slice: secret values, passwords, API keys, vault contents, provider QR/device/OAuth sign-in, remote-access tokens, billing and plan upgrades, account/project data or history deletion, and the Coordinator's own permission rules — none is delegated here, and wider settings parity stays follow-up scope.

## Out of scope

- Wider settings parity, receipts and one-click undo — the follow-up slice named above.
- Removing or reordering frequent models from chat, changing default routing, provider credentials, authentication, payment, account or project deletion.
- No new visual primitive: the existing approval card, the existing Settings list and its remove action carry this slice.
