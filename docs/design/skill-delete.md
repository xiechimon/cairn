# Skill delete — plan, 2026-11-28

## User scenario

Someone who installed Cairn today opens Settings → Skills and finds skills there: one they imported from another agent tool, one they wrote in the app. Until now the list had no way out. To remove one they had to leave Cairn and hunt the filesystem: the dogfood run that tried it moved three separate copies by hand on the Mac mini — the server copy under the Cairn home, a view under `~/.cairn/team-skills/views/<hash>/`, and a leftover view that no longer matched any manifest. Nothing on screen had ever told them those copies existed. The owner asked for a delete action instead (11-28, "add one"), including that the copies Cairn made on every computer go with it, to the system Trash, so the same manual hunt is never needed again.

Now each row ends with its more menu holding Delete. Pressing it opens one confirm whose title names the skill (Delete skill "deploy"?), one plain line under it saying the skill leaves Cairn and its files go to the Trash while your own folder stays, one destructive Delete and one Cancel. Nobody needs an account, key or payment for this, and nothing waits on another computer. Who it touches: the team's skill list (every member's Settings stops showing it) and every runner that already holds a synced copy. Where the bytes live: the skill directory under the Cairn home (`<cairn home>/skills/<dir>/`), the runner's content cache (`<runner home>/team-skills/views/*` and `.../plugins/*`), and an import-source record. The skill's original folder on a computer (for example `~/.agents/skills/deploy`) is never written by Cairn and is never touched by delete. Only the instance owner may delete, exactly like import and refresh, because a skill is one shared directory on the owner's machine; another member of the team gets 403.

Failure is visible in place: the row comes back where it was and a toast says the delete failed, in the server's own words. Two exceptions are deliberate: a 404 means the skill is already gone, so the row stays gone and no toast claims a failure; and a computer that is off cleans its copy the next time it runs a task, not while it is off.

## Scope

1. Settings → Skills: every row gains the existing row-menu pattern (dropdown-menu + `DeleteConfirm`, no new component) with a Delete item; the confirm names the skill, says the skill leaves Cairn with its files going to the Trash while the user's own folder stays, and offers exactly one destructive primary.
2. `DELETE /api/teams/:id/skills/:sid` (owner session required, `requireOwnerSession`, 403 otherwise) deletes one skill: it moves `<skillsDir>/<dirName>` into the system Trash (macOS `~/.Trash`, Linux Freedesktop Trash with a `.trashinfo` restore record) or, where no Trash can take it (a macOS refusal such as TCC, a read-only home, or a platform without a Trash), into `~/.cairn/trash/<ts>-<name>` so the delete still succeeds recoverably, removes that skill's import-source record, appends a `delete` row to `skill_audit` and answers 204; 404 when the skill is not there, 409 when the entry lives inside a shared agent skills root (`~/.agents/skills` or `~/.claude/skills`) that Cairn only reads. The list shows real directories whose real path stays inside the Cairn skills directory (`scanLocalSkills` with its `within` bound, S11/R14): a link pointing out of it is not a skill here and answers 404, a link pointing at another directory inside it collapses to the folder it resolves to, and delete prefers the directory named like the id (`resolveLocalSkill`) so a delete reaches the folder and leaves a link dangling instead of mistaking the link for the skill. The Trash helper moves a link as a link rather than following it.
3. The list drops the row before the server answers and restores it plus a toast when the delete fails (404 excepted as above; 409 shows the toast).
4. Runner copies: when a runner receives a complete manifest (`selection: 'all'`, the team's full skill set), a view directory that still carries a name the manifest no longer lists is removed whole, and a plugin directory goes the same way when it holds such a name and the view it was built from is gone. A narrower view holding only names the manifest still lists is a whitelist step's legitimate cache and stays until its own LRU turn. The runner copy is a rebuildable cache, not user data, so it is deleted rather than moved to the Trash: a hash-named folder in a person's Trash is junk they cannot use, the next task rebuilds whatever it needs from the blob cache, and a platform without a Trash would accumulate a directory Cairn never empties. The one copy a person can want back — the skill's own folder under the Cairn home — is the one that goes to the system Trash (Scope 2). Contents are never edited in place, so a view named for a manifest hash is either that manifest or absent, and a restored skill rebuilds its view instead of hitting a half-empty one. A view a running step holds (`holdTeamSkillsCache` from `prepareStepTooling` until the step's cleanups) is left alone until that step ends. A whitelist manifest purges nothing, and an empty complete manifest (the last skill deleted) removes every view and plugin.
5. Tasks already running keep working: their held view is untouched, so every skill they already had stays loadable, including the deleted one until the step ends; the delete applies from the next task on.
6. Everything else stays as today: listing, create, edit, import, refresh, manifest distribution to runners, agent skill allowlists, and the existing LRU prune of the content cache.

## Out of scope

- Deleting skills from a relay/agent tool call, and any bulk delete: this change adds the Settings action and one HTTP route only.
- Reworking the runner cache format (content-addressed views and hardlinked blobs stay as they are).
- Purging content-addressed blobs under `team-skills/blobs/`: they hold file bytes shared with other skills and carry no skill path; the existing LRU prune already bounds them.
