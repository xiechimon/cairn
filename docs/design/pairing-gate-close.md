# Confirm the browser session before closing the pairing gate

A newcomer opening a pairing link or entering a code sees the existing pairing form until the server confirms that the browser can use its session. The code or link comes from Remote Access settings on the host. The link fragment is removed before any request, and the expected environment is checked before redemption. There is no new account, payment, stored credential, or setting. If a cookie is blocked or has expired, the form stays available for another code.

## Authority and transitions

`GET /api/auth/session` and `POST /api/remote/pair` share a guard before authorization or body processing. Both require the Cairn browser-auth header. A supplied `Origin` must equal the server origin, and supplied `Sec-Fetch-Site` must be `same-origin`. Missing or conflicting proof gets an empty, non-cacheable `403` without writing a cookie or consuming a pairing code. Accepted requests use the existing authorization middleware and return `204` when the browser can proceed (including when auth is off) or `401` when credentials are absent or expired. All responses are `no-store`, with no user data or cookie writes. The browser calls it directly with same-origin credentials, bypasses cache, and refuses redirects. Only an unredirected `204` confirms and closes the gate; only an unredirected `401` is a signed-out verdict. A network failure, redirect, timeout, or unexpected status is not a verdict. The operation retries with a delay of 250 ms, doubling up to four seconds, until it receives a definitive response or pairing cancels background recovery.

| Situation | What the user sees and what the browser does |
|---|---|
| Ordinary API call succeeds or fails with a status other than `401` | It settles independently without changing the gate. In particular, both arrival orders of an older `200` and newer `401` give the same session decision. |
| A same-origin protected API call returns an unredirected `401` | All callers join one recovery operation. It checks the current session first; off loopback, if signed out and Access accepts an exchange, it probes the resulting cookie again. The probe verdict controls the gate. Callers retry once if authenticated or return their original error otherwise. A retry that also gets `401` awaits a probe but is never sent a third time. |
| A pairing POST lacks same-origin proof or is not JSON | An unproven request gets an empty `403` even if oversized. A proven request still needs to satisfy the body limit and use JSON before the code can be consumed or a cookie issued. |
| A code or link is being redeemed | The form shows the pairing state, keeps the input editable, and prevents duplicate submissions during redemption. A manual code posts directly; only a link reads the descriptor to check its environment. Redemption cancels any prior recovery and starts its own probe after the attempt, even when the attempt fails or the descriptor does not match. |
| A probe is pending after redemption or unavailable during recovery | The form shows `Connecting…` and accepts another code while the probe is in flight or between retries. A replacement cancels the old probe and owns the result for both existing and new `401` callers. A definitive `204` closes the form; a definitive `401` ends the retry and either shows the pairing error or follows ordinary signed-out or Access recovery. |
| A probe or Access exchange hangs | Each request has a five-second deadline and is aborted on timeout. A timed-out probe is retried; a timed-out exchange fails and leaves the preceding signed-out verdict in effect. A superseded request cannot publish a result or start another exchange, even if it subsequently settles. |
| An exempt, cross-origin, or redirected response arrives | It does not start or join recovery or decide session state. Machine enrollment confirmation remains protected; enrollment polling is exempt. |
| Pairing restores access after requests already failed | Active queries refetch when the gate closes; failed mutations are not replayed. The existing UI cache and stream scope still advances at gate boundaries and on a confirmed Access replacement, but is never used to order requests or decide authentication. |

No ordinary API response, Access response, or pairing response changes session state directly. One operation owns recovery at a time. Pairing moves from redemption to confirmation without releasing waiting callers. A new code may take over during confirmation, but not while the previous code is being redeemed. Only the current operation may publish a verdict. Cancellation is local to the browser; it does not roll back work already performed by the server. The gate is presentation, not an authorization boundary; the server still authorizes each request.

## Proof and scope

Tests control response timing for the pairing link, expired session, concurrent `401`s, both orders of older `200` versus newer `401`, failed redemption with and without a usable cookie, and redirected `401`. They also check that the status route returns no data or cookie, works for owner, Access, and paired browser sessions, and allows auth-off mode. Fake timers and deferred responses cover probe deadlines, bounded backoff, cancellation during an active request or retry delay, and the transition from the existing connecting label to the authenticated or signed-out view. Browser cookie policy, proxy behavior, live Access, and visual and assistive-technology checks are outside the local tests. The gate keeps its existing controls, copy vocabulary, focus behavior, and test IDs.
