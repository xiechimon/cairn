# Personal relay: installation, pairing and account budgets

Status: design-only proposal; review disposition is recorded separately against the exact file hash. Recommend a single-owner relay in the owner's **Workers Free account**, installed by a local authenticated wizard, with existing Cairn device authorization enforced on the host. Do not deploy the synthetic experiment as this feature. [Research](../research/connect-do-enrollment-2026-11-15.md) distinguishes documentation reads from assumptions; [the experiment](connect-do-prototype.md) proves local transport only. No resources, accounts, secrets or deployments are authorized by this document.

## Scope and trust decision

One personal Cairn server, one Worker origin, one SQLite Durable Object and up to four simultaneous phone/browser connections. The one DO owns all relay metadata and budgets; callers cannot select an object ID, account, environment or upstream. No D1, tunnel, custom domain, GitHub account, paid plan or Cairn cloud account is required. Existing Tailscale and the separate Tunnel proposal remain unchanged. Multiple relay installations in the same account are unsupported in the first trial.

The phone loads a small relay client from that Worker's `workers.dev` HTTPS origin; the host opens an outbound authenticated WebSocket. Phone traffic passes through the relay, unlike the Tunnel proposal. The adapter invokes an explicit Cairn operation subset in-process, **never** the private HTTP listener, generic fetch, arbitrary method/path or loopback owner bootstrap. Model requests and credentials stay in Cairn's existing server/executor machinery. A phone is a paired controller, not a newly enrolled execution machine.

**Trust accepted for this proposed trial:** Cloudflare, the account owner, deployed Worker code and its supply chain can see/modify traffic, steal the host transport credential and browser device session, impersonate either endpoint, and inject/drop/replay requests or results. Relay-served JavaScript can steal pairing grants and act as a paired controller, including submitting agent work with the owner's local execution authority. Restricted operations do not make hostile prompts harmless. Descriptor checks detect accidental misrouting, not a malicious relay. This is not E2EE or proof of an honest result. An independently trusted client and authenticated E2EE would be a different project; the confirmation screen must disclose this before installation and before first pairing.

## From zero: six installation stages, then four first-result steps

These are proposed wizard stages, not a claim that six clicks work today. All wizard/adapter work below is unimplemented. Initial supported host: native unprivileged Linux x86-64 desktop, Node 24.x, same-user browser/local-owner proof. Unsupported/headless platforms keep local/Tailscale access; do not weaken bootstrap or ask users to disable auth. Mobile clients target current Safari and Chrome; actual-device support is unverified.

| Stage | Person's action and actor | Wizard/system work and visible exit condition |
| --- | --- | --- |
| 1. Run Cairn locally | Owner installs/starts Cairn and opens the local UI on their computer. | Reuse local owner session and existing setup. Reject auth-off, unsupported host and a non-owner browser. Keep the private service private. Show precise prerequisite repair links, not an empty QR. |
| 2. Obtain a local result | Owner enrolls their own executor, completes local CLI login/API-key setup, chooses a writable project and confirms a tiny model request. | Existing daemon/provider paths execute the task. Show actual response and machine/runtime identity; missing daemon, expired login, inaccessible directory and provider quota are distinct failures. This stage may involve several existing setup actions; installing a relay does not fix them. No model credential goes to the relay. |
| 3. Create the Free account | Owner follows the official Cloudflare link, registers/verifies email, enables MFA and activates a `workers.dev` subdomain in that account. | Instructions show expected dashboard pages. No domain purchase or payment upgrade. Prefer a dedicated empty account; inventory checks must show no other Workers/DO usage before offering the initial conservative budget. A shared/paid account stops with an explanation, not a guessed allowance. Account verification/eligibility is an external prerequisite and can block installation. |
| 4. Authorize installation | Owner chooses Connect in local Cairn, reads the trust/Free-plan warning, selects that account and authorizes the official pinned Wrangler login in their browser. | The local installer uses Wrangler OAuth, not a token pasted into Cairn/chat. State explicitly that Wrangler's account-level permissions can be broader than this Worker. Verify selected account/plan and exact permitted resource changes before proceeding. Cancel makes no deployment. No GitHub fork/CI setup is needed. |
| 5. Install this relay | Owner confirms the displayed Worker name, account, release version and one DO binding. This is the explicit cloud-resource/secret/deployment consent point. | A future installer pins/verifies the package, journals public IDs plus fresh host-only transport capability locally (0700 directory, 0600 files), deploys fail-closed code/assets, configures that capability via official Wrangler secret stdin, and probes the exact no-redirect HTTPS origin. The initial deployment accepts no sockets until configured. Secrets never enter argv, generated commands, repository, analytics or logs. Preserve journal on ambiguous failure and reconcile the same named resource, never create another relay automatically. |
| 6. Verify and finish | Owner sees Connection ready and Execution ready separately, then chooses Pair phone. | Persist origin/install identity in existing Connect state, connect the host and verify identity/round-trip. Check no deployment/build loop remains; explain and offer Wrangler logout after successful setup (re-authentication required for updates/repair). A canceled/failed setup leaves explicit installed-but-off/cleanup-pending status, with retry/remove instructions. Never say removed while resources are uncertain. |

Once installed, first pairing through first remote result takes **four person actions**: (1) owner clicks Pair phone in the local owner UI; (2) phone scans and opens the QR on mobile data with VPN off; (3) phone user names the device, reads the host/project/trust summary and confirms Pair; (4) phone user submits a fresh tiny task and sees the selected local executor's new result. Cloudflare login is not needed on the phone. Pairing alone is not first-result acceptance. Returning devices open a bookmarked secret-free origin; expired sessions require another QR.

This chooses local Wrangler installation over Deploy Button because the latter adds a source-host account/repository/build authorization and does not solve owner bootstrap. It trades one terminal-capable local installer for fewer cloud identity handoffs. A browser-only one-click installer is not promised. The release guide must count the actual sub-actions and show screenshots during approved unaided acceptance, rather than advertise the stage count as a measured click count.

## Three authorities, no public claim-first enrollment

| Authority | Holder and storage | Allowed power; specifically excluded |
| --- | --- | --- |
| Cloud deployment | Owner's Cloudflare session and local Wrangler OAuth cache, managed by Wrangler | Install/update/delete the named resources. Not supplied to the running Cairn host adapter, Worker or phone. Installer invokes a short-lived subprocess with redacted output; installation is not an unattended auto-updater. |
| Host transport | Independent random 32-byte capability, journaled owner-only locally; Worker secret binding, compared before upgrade | Admit the single configured host for the configured install identity. Never reuse Cairn owner/device/machine/model credentials. No public first-host claim or recovery by public hostname. Runtime stores only connection role/ID/epoch, not the bearer, in attachments/SQL. |
| Application device | Existing Cairn pairing/device/browser-session records on host; browser has a host-only HttpOnly cookie | Run only the remote controller subset as that device. The cloud holds digest + bounded admission metadata, not an independent owner account. It cannot make a forged session valid on the host. A compromised relay can nevertheless steal an actually presented session. |

Installer prerequisite: a working supported OS keyring. Set `CLOUDFLARE_AUTH_USE_KEYRING=true` on every Wrangler invocation so unavailable storage fails closed, never silently falls back to plaintext OAuth files. Detect and reject unexpected Cloudflare API-token/key or credential-source environment overrides before login/deployment; do not select an existing unrelated credential implicitly. Show a local keyring test/repair step before authorization, and stop without cloud writes if it fails. Existing Wrangler credentials are deployment authority retained on the computer until revoked/logout; explain this and obtain explicit consent before logging out an existing shared session. Do not erase or migrate another tool's credentials automatically. Minimum sufficient OAuth scopes and keyring availability still require approved platform acceptance; do not claim one-Worker scope from account selection.

Reuse/evolve `connect-store.ts` and `connect-lifecycle.ts` with a discriminated relay allocation, credential/configuration version and cleanup journal, rather than create a second Connect controller. Reuse `paired-devices.ts` transactional grants/device creation and `browser-session.ts`; add relay installation scope to those existing records, not a parallel device database. Current records do **not** carry this scope today. A cookie resolver alone is insufficient: host authorization must also check device existence/revocation, scope and session expiry for every operation and active subscription.

### Pairing exchange and browser-compatible admission

1. Local owner creates an existing 192-bit, five-minute one-use pairing grant scoped to the relay installation/current enable generation. The authenticated host registers only its digest, expiry and random correlation ID in the DO. Cap pending grants at the existing 20. A local/cloud partial failure revokes the local grant and shows Retry; QR is shown only after both sides agree. No owner credential crosses the host socket.
2. QR is `<exact-origin>/app#pair=<one-use-code>&env=<environment-id>`; never put credentials in query, subprotocol or referrer. The client immediately removes the fragment, validates the descriptor against the QR and makes a same-origin POST with code and bounded device name. Serve no third-party scripts/telemetry; use no-store for pairing/API, no-referrer and a restrictive CSP. Do not retain the grant in browser persistent storage.
3. The DO applies the shared attempt budget, checks the pending digest/expiry and reserves one bounded pending redemption. It forwards only a typed pairing operation to the current host epoch. Host redeems transactionally using the existing service, adding relay scope; host rechecks intent generation and grant eligibility at the committing transaction. The existing function's permanent device token is not exposed to the browser; issue only its browser session. Neither endpoint can choose a team/role/owner flag from client input. DO never reports pairing success without the correlated host result.
4. On success, the Worker sets `__Host-cairn_relay` with Secure, HttpOnly, Path=/, SameSite=Strict, no Domain, fixed expiry at most the existing 30 days, no sliding extension. DO stores its digest, device ID, installation scope and expiry for transport admission. The host owns the actual session. Response loss may leave an orphan device; never replay a consumed code or return its old secret. Owner can revoke it and create a new grant. Pending exchange times out after 15 seconds and is never silently retried.
5. Browser opens same-origin `/connect/client` with that cookie. Require exact HTTPS Origin, no conflicting Fetch Metadata, no query auth, no bearer/subprotocol override and no duplicate session-cookie names. Validate digest/expiry and ask the host to validate the actual session before committing the upgrade; if the host is unavailable or rejects it, reject without dispatch. Host uses a header-only capability on `/connect/host` and rejects Origin. Fresh upgrades replace connection IDs; cookies/device IDs are not routing IDs.

On this bounded admission exchange only, forward the raw session cookie transiently to the host. The host binds the validated **existing browser-session record**, installation identity, host epoch and newly allocated relay connection ID in its own connection registry. DO attachments/SQL retain only non-bearer connection metadata and session digests, never the raw cookie. Subsequent operations and subscription emissions resolve this host-owned binding and recheck the underlying session record and device revocation/expiry; client/relay claims cannot replace it. DO hibernation preserves connection IDs/epoch while this host-side registry remains live. Missing/uncertain binding, host process loss or a replacement epoch requires a fresh authenticated upgrade with the browser cookie, not restoration from claimed device IDs. Bound pending admissions by the same four-operation/15-second limits; a lost/late admission response cannot authorize a different socket.

Worker-to-host operations derive connection/role context from admitted socket state, not payload fields; raw cookies are used only in admission, and later dispatch looks up the host-owned binding. The host authorizes only its bound scoped **device** session; owner sessions/tokens, machine/API credentials and claimed identity fields never satisfy this interface. Transport control replies require host role; application payloads cannot become enrollment/budget/rotation commands. Keep the experiment's exact role grammar, UTF-8 complete-message cap, both-endpoint expiry, host epochs and late-callback isolation as baseline obligations. The new control-operation and browser wire schemas need their own exact versioned contract review before code; this design is not clearance to improvise them.

Initial client operations are named, schema-checked adapters for: list permitted existing projects/executor summaries; read that project's task/messages; submit one task/message; subscribe to its result; stop that task; answer/cancel its pending question. Use existing authorization and task execution services; scope object IDs to the personal team/project, validate payloads and enforce the operation allowlist again on the host. No arbitrary HTTP forwarding, URL fetch, provider/secret administration, machine enrollment, filesystem/git/computer control, uploads or owner settings. Serve a deliberately limited remote UI; do not expose unsupported full-SPA controls. HTTP endpoints are only built assets/app, public minimal descriptor/health, same-origin pairing POST and the two role-specific WebSocket routes; all other paths/methods are denied. Assets never proxy from private Cairn.

## Revocation, reconnect and recovery

| State path | Persistent owner and transition | Failure behavior |
| --- | --- | --- |
| Install/retry | Existing local Connect controller journals identity, credential and provision checkpoints before mutation | Reconcile exact account/name/version after lost responses. Unknown or foreign resource ownership stops for manual dashboard inspection; no adoption by hostname alone. |
| Enable/disable/remove | Reuse persisted intent generation, serialized commits and stale-callback fencing | Disable immediately closes host transport/subscriptions, invalidates pending grants, preserves scoped devices and resources; local/private access stays available. Remove invalidates installation-scoped sessions and records cleanup intent before cloud calls. Off/removing startup never reconnects. |
| Pair/redeem | Host grant transaction plus DO's bounded pending correlation, scoped to current host epoch/generation | Expired/revoked/replayed grants and late old-host results fail; second contender cannot obtain the session. Lost outcomes require a new grant, not credential recovery. |
| Device revoke/logout/expiry | Host is authoritative; DO receives transport invalidation when connected | Host denies immediately even if cloud notification is lost, closes subscriptions and instructs cloud to remove digests/sockets. On every subsequent operation/event emission, host rechecks authorization; a silent revoked recipient receives no new task data. Logout revokes that relay browser session without deleting private sessions. |
| Host loss/replacement | Epoch retires all its clients; no data forwarding while host is absent | Half-open sockets may block replacement until close/fixed expiry. Fresh host must validate surviving cloud device admissions against local records before clients can resume. Late callbacks never affect a new epoch. No replay, task retry or exactly-once promise; after ambiguous submission, inspect existing tasks before resubmitting. |
| Socket/session lifetime | Fixed socket lifetime at most one hour and never later than device-session expiry, enforced on both endpoints | Fresh upgrade required; it does not renew the browser session. Application output limits and expiry include silent/non-reading recipients. Preserve epoch/expiry/rate/output state over actual hibernation. |
| Lost local state/host capability compromise | Owner uses Cloudflare dashboard authority, not a phone or public setup link | Disable locally if possible; retire the old Worker/DO and its origin/session authority, then install fresh with new capability/install identity and re-pair. Revoke affected Cairn device sessions separately. No first-claim takeover, secret recovery by hostname, hot rotation or copied-controller support in the initial trial. |
| Uninstall/account loss | Local removal journals cloud cleanup; dashboard can disable/delete Worker, bindings and retained DO storage using the official procedure | Ordinary package uninstall is not cloud cleanup. Keep the journal until confirmed; account loss means stop the host and recover with Cloudflare, not Cairn support impersonation. Never instruct namespace deletion as an incidental retry. |

Do not log cookie/grant/bearer/payload, store chat payloads in the DO, or send them to analytics. Store only bounded digests, IDs, expiries, counters and protocol versions. Expired metadata is lazily swept with bounded work; no per-IP unbounded map, per-event history or recurring alarm/cron. Short-lived plaintext host results/session issuance exist only in memory while forwarding; reconnect never retrieves old secret material. Keep accepted socket attachments minimal; persist counters before send/mutation. No sensitive data in error responses.

## Account budget: fail closed, do not promise a quota firewall

One fixed DO is the only admission/counter owner for **all** grants, hosts, devices, HTTP/control calls and messages of this installation. No sharding by user-supplied environment/device ID, per-device allowance reset, second budget namespace or fallback when storage fails. Other Workers/DO namespaces in the Cloudflare account are outside this ledger. Therefore the initial supported configuration is a dedicated Free account with this one installation; it is not an accurate account-wide meter on an arbitrary shared account. Provider account quotas remain the actual account-wide outer boundary.

Proposed conservative trial defaults, not measured capacity: one host, four live clients, existing 50 stored-device cap, 20 pending grants; 64 admitted upgrades/day, 400 pairing attempts/day, 2,000 dynamic HTTP/control requests/day, 10,000 inbound application frames/day, and 32MiB/day total forwarded serialized UTF-8 output. Keep 64KiB complete inbound-message and 60KiB payload limits. Limit each socket to 8MiB lifetime output without refunds, host ingress to 1,200 frames/minute and each client to 60/minute; coalesce model events on the host and fail visibly if a result cannot fit. Maximum four in-flight operations account-wide; at most one pending pair redemption per grant. These are finite pilot limits, not appropriate production defaults or task/model spending limits.

Reserve before the corresponding admission/forward/send in one synchronous SQL transaction for the account row; attachment state retains socket counters/identity across eviction. Output reservation includes welcomes, control/error replies, framing and any duplicate delivery; never refund on failure/reconnect. Denials send at most one bounded response then close, rather than an unmetered error loop. Account counters survive host/client reconnect, DO eviction, restart and code deployment; midnight UTC changes the dated daily row, not per-socket lifetime output. Retain only current/previous date rows. Unexpected backward clock or missing/corrupt persisted budget state fails closed until locally authorized repair; never interpret loss as a fresh allowance. Initial row creation is permitted only for a new installation identity.

Budget exhaustion rejects admissions with 429 and a reset indication; active senders/recipients close 1013 and stop automatic reconnect until the stated reset. Send failure closes 1011 without refund/retry. A UTC reset allows new admissions, not replay of abandoned tasks. Connection recovery otherwise uses bounded jittered backoff with a finite attempt count and a visible manual Retry. A new connection never grants a fresh daily budget. Local diagnostics distinguish application budget, provider 1027/quota, host offline, auth expiry and unknown network error; cloud quota outages can prevent even the status page, so local repair help must remain available offline.

**Unavoidable limitation:** every request that reaches the Worker can already consume a Worker invocation before authentication or this ledger. DO-dispatched denials, invalid messages, WebSocket reconnects and storage counter writes also consume provider allowances. The Worker rejects invalid routes/oversized requests and missing host auth before DO dispatch where possible, but attackers can still exhaust the account's public ingress or DO allowance. Application counters cannot account for all edge/platform work or bound wall-clock duration. Rate limiting/Turnstile may mitigate abuse later, but are not a Free-tier availability guarantee. Do not automatically restart/redeploy/reset counters/switch to Paid when attacked.

Official Free limits include separate 100,000/day Worker and DO request allowances, 13,000 DO GB-s/day, and SQLite read/write/storage limits; incoming DO WebSocket messages use 20:1 metering, not one free invocation per message. Reserve headroom rather than equating application counts to billed counts. Our caps do not prove SQL row-operation/active-duration/CPU headroom: measure those during approved cloud acceptance. Free over-limit operations fail until reset; no paid subscription is enabled by the installer. If the account is already Paid or changes to Paid, refuse initial setup/re-enable and show that this design's zero-overage assumption no longer applies. A plan change while running cannot be detected reliably without fresh account authority; the operator must stop the relay before changing plan. No dollar ceiling is claimed for that case.

The local UI displays application counters and the official account-usage dashboard link, explicitly labeled different measurements. No runtime Cloudflare analytics/API token is introduced merely to poll usage. Cloudflare's separate Workers/DO account spending limits require positive-dollar thresholds, have enforcement delays/exclusions, and **do not block messages on already-open DO WebSockets**. They are not a zero-dollar policy or complete relay kill switch, and installing this relay must not change them silently. Any failed budget/session storage read or reservation write stops forwarding and closes affected sockets without requiring another successful SQL write; never continue on a cached allowance after quota/spend-pause errors. A 100-user population here means 100 independently owned accounts/relays, not 100 users sharing one free relay. Model costs remain the owner's existing subscription/key costs.

## Acceptance and decision gate

Before protocol implementation, independently review this scope and then the exact versioned enrollment/control/RPC schemas and failure/state contract. The local experiment's security PASS does not cover this proposal. Keep the Worker package isolated, reuse Cairn service owners named above, and do not expose a generic adapter for SPA compatibility.

Before asking to enable a real trial, obtain explicit approval for the selected account, resource/secret setup and deployment. Future proof must include: an unaided novice's fresh Free-account installation and actual action count; real Safari/Chrome pairing on mobile data without VPN; a fresh local-executor result; an offline/missing-provider path; expired/replayed/racing pairing and response loss; cookie/Origin/role forgery; revoked silent recipients; disable/remove during every pending callback; lost cloud/local state; single ledger across all clients/failed attempts and actual live-socket eviction; multibyte boundaries, stalled peers, send failure and nonrefundable output; UTC/reset/reconnect churn; measured Worker/DO/SQL/duration usage under normal use and abuse. Use serial tests/shared heavy admission. None of these cloud/real-device results are claimed here.

Recommendation to the owner after design review: decide whether the disclosed trusted-relay model and dedicated-Free-account install are worth a bounded cloud trial. Approval would authorize only the separately enumerated trial work, not E2EE claims, production rollout, Paid upgrade, full remote administration or changes to the self-deployed private service.
