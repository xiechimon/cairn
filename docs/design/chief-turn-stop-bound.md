# Bounding a Coordinator turn whose executor ignores stop

Issue #2556. `sweepOverlongChiefTurns` (30-minute cap) asks a claimed chief step to stop by writing `stop_pending` and pushing a `stopSignal`. That request is advisory: a daemon that keeps heartbeating but never picks the stop up — or picks it up and ignores it — holds the step `claimed` forever and blocks the whole Coordinator thread, because `ownedStep` accepted any step whose `machineId` matched, whatever its status. The fix has two halves that only work together: machine-dispatch surfaces refuse steps that are no longer running, and the same server-side settle that already exists for a stale heartbeat also fires when a stop request outlives a grace period.

## State

- `step.status`: `pending` → `claimed` → `done` / `failed` / `stopped` / `waiting_quota`. `claimed` is the only running state; ownership is `step.machineId` (`null` for an in-server Coordinator turn).
- `stop_pending(conversationId, stepId, discard, createdAt)`: one row per conversation, "a stop for `stepId` is awaiting executor pickup". For a chief step, `conversationId` is the `chief_thread.id`. `createdAt` is the time the stop was requested; a row rewritten for a different `stepId` restarts the clock. The grace clock therefore assumes the existing invariant of at most one `claimed` chief step per conversation (`hasEarlierLiveChiefStep`); if that is ever relaxed, the request timestamp must move onto the step or a per-step row.
- `chiefThread.activeRun`: cleared by `settleChiefActiveRun` once no live chief step remains; this is what unblocks the thread's next turn.
- Daemon side (unchanged): `deliverStop` fetches `GET /api/machine/stop` and hands the request to the run's `RunStop` slot; the run may honour or ignore it.

## Transitions and the paths that write the turn state

- **Stop request** (`stopClaimedChiefStep`, reached from `stopChiefTurn` and the overlong sweep): while the heartbeat is fresh and no same-step stop row is older than `CHIEF_TURN_STOP_GRACE_MS` (120 s), upsert `stop_pending` — preserving `createdAt` when the row already names this step — and emit `stopSignal`. Returns `{ delegated: true }`.
- **Force stop** (`stopClaimedChiefStep`): the heartbeat is stale beyond `CHIEF_ABANDONED_STEP_MS` (existing), **or** a `stop_pending` row naming this step is older than the grace (new). Set `status 'stopped'`, `finishedAt`, clear `archiveStop`, delete the `stop_pending` row, `releaseUnconsumedSteer`, `settleMemoryEditTurn(..., 'stopped', 'executor lost')`, emit `machineHub.stopSignal` for the step (its `onStop` listeners cancel any open computer call and release its execution lease; a `dispatched`/`running` row with no live listener expires at its own deadline), `settleChiefActiveRun`, publish the step row, then write the `chief-stop-<step>` marker via `recordChiefStop` so the marker never precedes the `stopped` row. Returns `{ delegated: false }`. A second user stop click past the grace lands here too.
- **Machine write surfaces** (`ownedStep`, machine-deps): existence + `machineId` + now also `status === 'claimed'`, else `NotFoundError` → HTTP 404. This covers heartbeat, tool / transcript-delta / transcript-row / thinking / activity / agent-todo reports, attachment download, skills manifest and file, `machineAsk`, transcript / session uploads, `getStepSession`, `finishStep`, and the daemon `transcriptRow` report.
- **`ownedStepRow`** keeps the old contract (exists + `machineId`, any status) for the paths that legitimately see a settled step and refuse or annotate it themselves: `localMergeRecheckAuthorization` answers `{ authorized: false, reason: 'step-released' }`, `reportBackgroundTask` marks a still-running background task `orphaned`, `machineAsk` throws 409 for a chief step after its provenance checks, upload-URL creation still grants a pending slot (the receive side enforces the real policy), `receivePlanUpload` keeps its own `status !== 'claimed'` → 409, `stepToken` keeps its designed degrade (subscription tokens, git credentials, connector fields and gateway http secrets are only issued while `claimed`; plain secrets and the provider key still answer), the in-server `transcriptRow` mirror still repairs `chiefMessage` rows on a settled step (restart mirror-debt restore) but silently drops a `NotFoundError` (gone or foreign step), and the relay entry points (`machineAsk`, `relayComputerTool`, `executeRelayToolCall`, `forwardComputerCall`) keep their existing `status !== 'claimed'` → 409 checks — extended to the non-self-guarding worker tools inside `executeWorkerMemoryToolCall` (attach_file, set_task_meta, memory and skill tools), so memory / skill / task-meta tools on a settled worker step are refused too.
- **Finish report** (`finishStep`): unchanged — `status !== 'claimed'` already returns early without writing. The in-server `done` gains the same gate (`server-api.ts`): it still records `body.usage` (tail token accounting only writes `token_usage` rows), then a no-longer-claimed step stops its computer calls and returns, so a late report can never resurrect a forced-stopped step. The in-server `transcriptDelta` drops a `NotFoundError` silently — mirroring a dead step is best-effort and must not fault the runtime callback.
- **In-server stop poll** (`server-api.ts` `stop`): returns `false` when the step row is gone or no longer `claimed`, whatever its owner, so the runtime aborts the turn promptly after a force-stop instead of polling forever.
- **Queued next turn**: the stopped head leaves `liveChiefSteps`, so `hasEarlierLiveChiefStep` no longer blocks the next pending chief step; the daemon's `tasks/claim` or the in-server claim takes it.

## Behaviour on each failure

- **Daemon heartbeats but ignores stop**: the sweep delegates once; fresh heartbeats keep `lastHeartbeatAt` young but cannot renew the `stop_pending` clock (the upsert preserves `createdAt` for the same step). Past the grace the sweep force-stops on the server. Total bound: `CHIEF_TURN_MAX_MS` + `CHIEF_TURN_STOP_GRACE_MS` + one tick.
- **Daemon honours the stop**: `fetchStop` hands it the row, the run reports `stopped`, `finishStep` applies it. No force path is reached.
- **Daemon is silent**: stale heartbeat → the existing abandoned branch stops the step at once, no grace wait.
- **Daemon comes back late** (partition or restart after force-stop): `recoverSteps` returns nothing `claimed`, so nothing resumes. A still-running executor's next heartbeat or any write gets 404; the stock runner self-stops on that heartbeat error (`runner.ts`). A late `done` is a no-op (`finishStep` early return; in-server `done` likewise). A machine `client.stop` fetch answers `{ discard: null }` — the request is already settled and the row is gone. The in-server `stop` poll answers `false` and aborts promptly.
- **Daemon ignores everything, including the 404**: server state is still bounded — every owned write surface refuses, the thread is freed, and the marker stands.
- **Stale `stop_pending` for another step**: a row naming a different `stepId` is overwritten with a fresh request; the grace for the new head starts then. `fetchStop` already deletes rows whose target is no longer active.
- **`stop_pending` delivered but report is `success`/`failed`**: finish applies normally and deletes the row; the turn ends as a normal turn, not a forced stop.
- **In-server Coordinator turn** (`machineId` null): `stop_pending` is what its stop poll reads, and the same grace applies. After a force-stop the `stop` poll returns `false` so the runtime aborts; a still-late `transcriptDelta` is dropped (a `transcriptRow` mirror may still land as transcript history, same as on any settled step) and `done` is refused, so the step stays `stopped` and the drain continues to the next head.
- **Pending question**: `holdForQuestion` keeps its hold deadline; the next ask / relay / heartbeat after the force-stop is refused, and a cooperative executor self-stops on the heartbeat refusal. A `pending` ask_user card stays pending — the same as on every other daemon chief-turn ending today (only the in-server finish cancels them).

## What the user sees

No new surface. The thread shows the same `chief-stop-<step>` system marker any stopped turn writes today ("turn stopped"), `activeRun` clears so the composer is usable, and the next queued message starts a new turn. The grace and cap constants are internal.
