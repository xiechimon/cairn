## User scenario

When a newcomer installs Cairn today and creates a task in plain words, clear fixes and well-specified requests (even across multiple files) proceed directly after listing 3–5 concrete edge cases and settle `done` (or `review` for info/report tasks) only after running real acceptance matching the task kind: live app run + visual check + `attach_file` screenshot for UI changes, real HTTP/handler request-response for API/server changes, real command execution for CLI/script changes, or opening and checking the generated deliverable artifact (`report.md`, exported HTML/PPTX/PDF/image/data file; genuinely unreachable external/paywalled sources may be marked as gaps rather than blocking). Large tasks with genuine architectural/product trade-offs or unclear scope pause once before the first edit on a single batched `QuestionCard` (1–3 guiding questions with a `recommended` default; or a pushed draft PR paired with `ask_user` confirmation), saving answers in `todo.decisions` and resuming on the existing `continue` path. In Slice 2, if a model ignores real acceptance, attaches only fixture/pending/failed/stale shots, leaves generated deliverables unchecked, or leaves GitHub commits unpushed (or unpushed state unknown), `completeStep` never enters `done`: it sends at most one bounded continue-session nudge, and if still unverified or explicitly blocked opens a per-step `needs_input` `QuestionCard` explaining what ran and what is missing — with zero new board columns, labels, or phases.

## For a Newcomer

- **Where you meet it:** Inside your first task thread and on the task card in Cairn.
- **What you must already know:** Nothing about Cairn internals — describe the task in plain language.
- **Accounts, payments, keys, and settings:** None. Reuses your configured model and runner; adds zero `CAIRN_*` env vars, zero settings toggles, zero new database tables, and zero new UI badges or status columns.
- **Where data is stored:** Answers to guiding questions and acceptance-blocked clarifications are stored in `todo.decisions` and conversation `message` rows; acceptance screenshots, reports, and deliverables are stored in `attachment`.
- **Where you get stuck / failure view:** Ambiguous or trade-off-heavy tasks pause once on a batched `QuestionCard` (1–3 guiding questions with `recommended` defaults; if unanswered, the thread stays cleanly in `needs_input`). If Slice 2 detects missing acceptance or unpushed commits, the system sends the agent back once (`building`); if still missing or explicitly blocked (sandbox, missing runtime, missing credentials, or git push-state unknown), or if the user replies without unblocking the underlying blocker, each affected step opens a fresh `needs_input` `QuestionCard` explaining what ran, what is missing, and how to unblock — never settling as `done`.

## Scope

1. **Slice 1 (prompt guidance & legacy backfill):** Tiered task planning, clear multi-file proceed rule, 3–5 edge cases before first edit, draft-PR + `ask_user` confirmation checkpoint, per-kind real acceptance criteria, and generated-artifact check (permitting gap-marked external sources) in `packages/shared/src/records/prompts.ts` (`SESSION_BRIEF`, `SESSION_REWORK_BRIEF`, `LEGACY_SESSION_BRIEFS`, `LEGACY_SESSION_REWORK_BRIEFS`), `packages/shared/src/protocol/chief-tools.ts` (`WORKER_ASK_USER_TOOL`), `packages/shared/src/protocol/info-card-tools.ts` (`infoCardHostBrief`, `infoCardBrief`), `apps/daemon/src/step-prompt.ts` (`composeWorkerSystemPrompt`), and `apps/server/src/services/transcript-origin-backfill.ts`.
2. **Slice 2 (daemon & wire unpushed-commit detection for `#53`/`#54`):** Extend `packages/shared/src/git-ops.ts` (`WorktreeOps.unpushedCommitCount?`), `apps/daemon/src/workspace.ts`, `apps/daemon/src/step-closing-git.ts`, `apps/daemon/src/step-settle-git.ts`, `apps/daemon/src/step-deliver.ts`, `apps/daemon/src/step-done-body.ts`, `packages/shared/src/protocol/machine-wire.ts` (`machineDoneBodySchema.unpushedCommits: z.number().int().nonnegative().nullable().optional()`), and `apps/server/src/services/machine-finish-step.ts` to inspect both `HEAD` and scanned `artifactBranches` (`branchesWithNewCommits`) on GitHub observe-only repos, returning exact unpushed commit count (`>= 1`), `0` only when confirmed pushed/landed, `null` when git check fails or remote ref cannot be verified (never collapsing unknown to `0`), and leaving `undefined` for legacy daemons that do not report the field.
3. **Slice 2 (deterministic acceptance evaluator):** Implement `evaluateStepAcceptance` and `extractEditedPathsFromMessages` in `packages/shared/src/records/acceptance.ts` (re-exported via `packages/shared/src/records/index.ts`). Evidence comes strictly from persisted tool-call/result blocks in `message`, step-scoped `ready`/`received` `attachment` rows, and daemon git telemetry (`unpushedCommits`) — never trusting assistant prose alone. Enforces: post-edit check freshness (an edit occurring after the last screenshot or command invalidates prior evidence), non-zero failed command exits, fixture-only or unready/failed UI screenshot rejection, generated info/doc artifact verification, explicit blocker detection (`blocked`), unpushed commits (`unpushed`, `unpushed-blocked`, `unpushed-unknown`), and read-only / no-change verification acceptance.
4. **Slice 2 (server completion, bounded retry, and per-step blocker recovery loop):** Wire `evaluateStepAcceptance` into `apps/server/src/services/build-step-complete.ts`, `apps/server/src/services/build-undelivered.ts` (`askAcceptanceBlockedOnce`), and `apps/server/src/services/transcript-origin-backfill.ts` (`isAcceptanceNudgePrompt`). Use per-step idempotency key `acceptance-blocked-${stepRow.id}` so if a user answers via `thread-message.ts` -> `worker-questions.ts` without unblocking the underlying issue, the subsequent step opens a fresh pending `QuestionCard` rather than deduping to silence and settling `done`.

## States, transitions, readers, writers, and failure behavior

- **Phases touched (zero new phases):** `building`, `needs_input`, `review`, `done` (`apps/server/src/services/phase.ts`).
- **Preconditions & precedence in `completeStepSettled` (`apps/server/src/services/build-step-complete.ts`):**
  - Only runs on `status: 'success'` reports that reach `completeStep` (steps already reporting `status: 'failed'` or `status: 'stopped'` never pass through `completeStep` per `apps/server/src/services/machine-finish-step.ts`; stopped/archived/stale-build/left-execution steps return early at lines 141–187 before acceptance evaluation).
  - Bypass `evaluateStepAcceptance` for non-build steps (`merge`, `review`, `verify`), when `pendingWorkerQuestions(deps.db, buildRow.id).length > 0` (already waiting for human answer), when `receivesAnswers(stepRow.kind) && undeliveredAnswers(deps.db, stepRow.buildId).length > 0` (user just answered — immediately enqueue `continue` with `ANSWERS_CONTINUE_PROMPT` so the agent acts on the answer; the continued step will re-run acceptance on completion), or when `messages` has zero assistant tool-free messages only in synthetic unit harnesses without assistant rows (`machine-finish-step.ts` rejects real silent runs via `zeroUsage` before `completeStep`).
  - Precedence before `askUndeliveredOnce`: run `evaluateStepAcceptance` first; if non-retryable `blocked`, `unpushed-blocked`, or `unpushed-unknown`, open per-step `askAcceptanceBlockedOnce` and skip `askUndeliveredOnce`. Else if `undeliveredEnd(...) !== null`, run `askUndeliveredOnce`. Else if `!acceptance.ok`: if prior `isAcceptanceNudgePrompt` steps on `buildRow.id` `< ACCEPTANCE_NUDGE_MAX` (1), mark current step `done` and enqueue 1 `continue` step inside an atomic DB transaction; otherwise open per-step `askAcceptanceBlockedOnce` (`needs_input`).
- **Readers and writers:**
  - *Daemon & wire:* `step-closing-git.ts` reads `ws`, `headAtStart`, `headCommit`, `headAhead`, `scanned` branches, and calls optional `git.unpushedCommitCount?.(cwd)` (covering `HEAD` and scanned branches, returning `null` on error) -> writes `ClosingGitOutcome.unpushedCommits` -> `step-settle-git.ts` -> `step-deliver.ts` -> `step-done-body.ts` -> `machineDoneBodySchema` -> `machine-finish-step.ts` reads `outcome.unpushedCommits` and `outcome.status` (calling `completeStep` only on `status: 'success'`).
  - *Journal & idempotent replay:* `apps/daemon/src/step-final-upload.ts` (`resumePendingUpload`) replays `putFinalArtifacts` + `client.done` on restart; `prepareStepReport` in `machine-finish-step.ts` sees `step.status !== 'claimed'` and skips re-running `completeStep`, preventing duplicate `continue` steps or `QuestionCard`s.
  - *Attachments & deliverables:* `agent-attachments.ts` writes step attachments with `createdBy: 'step:' + stepId`, `status: 'ready'`; deliverables write `grantId: 'deliverable:' + stepId + ':' + gen`. `build-step-complete.ts` queries only attachments scoped to `buildRow.id`'s steps with `status IN ('ready', 'received')`.
  - *Acceptance & recovery loop:* `build-step-complete.ts` reads `build.changes` (or `extractEditedPathsFromMessages(messages)` when `changes` is null on `hosted` / `> 512 KiB`), `message` (`buildId`), `step` (`buildId`), scoped `attachment` rows, `project.repoKind`, and `outcome.unpushedCommits` -> transactionally marks `step` `done` + either enqueues 1 `continue` step (`builds.ts:enqueueStep`), writes `acceptance-blocked-${stepRow.id}` (`build-undelivered.ts:askAcceptanceBlockedOnce`) -> `setTodoPhase(..., 'needs_input')`, or finishes `review` (info) / `done` (code). When the user answers, `thread-message.ts` -> `worker-questions.ts:settleQuestionAnswers` writes `todo.decisions` and `message` and enqueues `continue` via `sendBuildSteer`; when that resumed step completes, `build-step-complete.ts` re-evaluates acceptance cleanly.
