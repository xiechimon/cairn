# User-owned Cloudflare control plane

Status: architecture boundary with offline storage gate verified, 2026-11-15; cloud product and deployment remain unimplemented. The owner selected three modes: local-only, a local server reached over Tailscale, and a user-deployed Cloudflare control plane with multiple registered runners. This replaces the single-host relay as the third-mode target; it does not remove local or Tailscale support. Research: [platform and cost feasibility](../research/cf-control-plane-feasibility-2026-11-15.md), [prior enrollment/security research](../research/connect-do-enrollment-2026-11-15.md). Platform feasibility is established by documentation and bounded local workerd checks, not by a deployed Cairn trial.

## Architecture and ownership

- Local and Tailscale keep the current Node server, local database, Coordinator and daemon. Neither requires a Cloudflare account. Cloud mode is a separate server entrypoint, not a switch that changes an existing local database in place.
- One installation belongs to one owner in that owner's Cloudflare account. A Worker serves static web assets and authenticated API entrypoints; one SQLite Durable Object owns the installation's product state and event coordination. Multiple runners do not each need a separate DO. No Cairn-operated relay, Clerk account, D1 database, tunnel or always-on privileged home server is required.
- Runners initiate outbound HTTPS/WebSocket connections. A phone/browser controls tasks; a supported computer runs the daemon. Browser code never receives machine enrollment authority or a runner's model credentials. Runner enrollment does not itself grant desktop-control, shell or project-directory consent beyond the existing daemon policy.
- The cloud owns task/conversation records, ownership, routing decisions, claim generations, bounded product transcript/events and result acceptance. Runners own checkouts, tools, machine-local sessions, model-driven Coordinator turns and provider calls. Cloud mode does not start the existing in-server model loop. A Coordinator turn is assigned to a named eligible runner, not executed in the Worker.
- Reuse the existing shared schema, machine identity, task/step vocabulary and routing semantics. Port services at their real dependencies; do not add a second generic job queue beside `todo`/`build`/`step`. The existing Hono application cannot be bundled unchanged: its imports include filesystem serving, native SQLite, schedulers and local harness stores.

The cloud receives prompts, transcripts and results. Keeping API keys and subscription logins on runners is not end-to-end encryption. The owner trusts their Cloudflare account and deployment source. E2EE, public multi-tenant hosting, arbitrary browser runners, cloud CLI execution and transparent session migration are outside this design.

## First install and pairing

1. The supported installer presents the three modes with their prerequisites. Cloud selection explains that work stops when all runners are offline, that Cloudflare handles conversation data, and that Free quotas can interrupt service. A deployment preview names resources, account, plan and potential charges before the user confirms. Deploying or changing cloud resources is a separate authorized operation.
2. Owner bootstrap is not first-public-visitor-wins. The installer generates a high-entropy, short-lived, one-use bootstrap credential, binds it to the installation and exact HTTPS origin, and opens that origin with the credential in the URL fragment. It is exchanged in a bounded POST, removed from browser history, never placed in logs/query strings, and atomically consumed when owner authentication is established. An expired or interrupted bootstrap is recovered through the authenticated deployment tool, not a public reset endpoint.
3. A browser owner session is Secure, HttpOnly, SameSite=Strict and host-only. New browsers require explicit approval from an existing owner session or an installer-held recovery credential. Recovery has the same installation/origin binding and one-use semantics. The setup screen provides a local recovery export before setup is considered complete; secrets never enter task transcripts.
4. On each computer, the runner generates its own machine credential locally and requests enrollment using only a verifier. It displays a short-lived pairing code and opens the installation's approval page. The authenticated owner sees the computer's name, platform and requested capabilities and approves that exact request. The code is a locator, not execution authority. Polling requires a separate high-entropy enrollment secret. Approval/consumption is atomic and expires; denied, expired or replayed requests never create a machine session.
5. The cloud stores a verifier, not the recoverable machine secret. The approved runner proves possession and becomes online. The first runner becomes the default using the existing default-runner semantics; adding another does not change the default. Setup runs a credential-free connectivity check, then offers the first task on a selected runner. Missing local CLI/login/model configuration produces local setup instructions, not a cloud credential form.
6. Owner revocation invalidates the runner's credential generation and live sockets before accepting more claims/events/results. A stolen machine credential cannot enroll another machine, approve a browser or become owner. Revocation cannot undo a command already executing offline; the UI states that limitation.

Exact authentication schemas, token lengths/TTLs, retry budgets, endpoint admission and recovery ceremonies must be specified and tested in their implementation slices before exposing a public endpoint. Reuse reviewed ingress techniques, not the superseded single-host authority model. No unauthenticated deployment is a usable intermediate release.

## State, transitions and failure behavior

Product states remain the existing schema's states. Connection liveness and dispatch delivery are separate facts, not new meanings for `step.status`. Cloud-specific claim generation, acknowledgement and event sequence metadata must be durable and versioned alongside existing rows; adding fields requires a reviewed schema/protocol change.

| Path | Reads/writes and transition | Failure contract |
| --- | --- | --- |
| Install / restore | Installation identity, schema version, bootstrap/recovery verifier; absent → unclaimed → owner established | No public owner election. A failed migration fails readiness without admitting work. Restore changes installation authority and invalidates old sessions/claims before accepting traffic. |
| Enrollment / approval | Pending request, owner approval, verifier and credential generation; pending → approved → consumed, or denied/expired | Single atomic consumption. Concurrent approvals/replays cannot create extra authority. Owner check precedes approval; a code alone cannot approve or poll. |
| Connect / reconnect | Credential verifier/generation, socket attachment and durable connection generation | Revoked/stale credentials fail. A newer connection fences the older socket; its delayed close/message cannot mutate current liveness. Hibernation reconstructs from storage/attachments, not an in-memory registry. |
| Create / assign | Existing task, build, step and machine routing records; idempotent client request → pending step on a named runner | Preserve default/platform routing and hard session/local-path/explicit affinity. Offline or ineligible target waits with a reason; no silent handoff or model fallback. Duplicate request returns the same operation or rejects a mismatched payload. |
| Claim / start | Machine ownership, generation, current eligibility and pending step; atomic claim → durable dispatch identity → runner acknowledgement | Persist before sending. Claim/ack binds installation, machine, step and generation. Never hold a SQL transaction across network/model I/O. An unacknowledged delivery is not proof execution never started. |
| Runner receipt | Local durable dispatch journal, scoped project consent, local runtime/model credential | Journal the dispatch before starting the process. Duplicate delivery reconnects to the recorded attempt and never starts another process. Missing capability/login is a visible unavailable state, not an upload of credentials. |
| Events / finish | Current claim generation, monotonic event sequence, bounded transcript, outcome and usage; claimed → existing terminal state | Old-generation events/results cannot mutate the step. Same sequence/payload is idempotent; conflicting duplicates fail. Acknowledged events survive runtime restart. Finish is committed before acknowledging; duplicate finish returns the committed outcome. |
| Loss / deadline / cancel | Durable claim state, runner journal, stop intent and next alarm deadline | A disconnected or expired claim is uncertain, not automatically replayable. Reconcile on the same runner. Explicit retry creates a new attempt only after stop acknowledgement or owner acceptance of duplicate-side-effect risk. A fencing token protects cloud writes, not an offline process. |
| Revoke | Credential generation, current connections and affected claims | Reject further authenticated actions immediately; best-effort stop/close does not prove local process death. Tasks remain blocked/uncertain until reconciled, never silently moved. |
| Hibernation / retention | Durable cursors, socket attachments, bounded histories and earliest deadline | Use Hibernation API and one alarm for earliest durable deadline; no periodic DO timers. Expired/revoked sessions are rechecked on every wake. Bound cleanup work and resume it durably. Retention cannot remove an unresolved attempt's reconciliation identity. |

The cloud must remain useful with all runners offline: read existing history, enroll a computer and queue requests. It cannot generate an AI diagnosis without a runner. Offline notices and recovery instructions are deterministic; a model diagnosis waits for a runner. Coordinator harness files remain on their named runner with product transcript mirrored to CF. Losing that disk does not silently reconstruct or migrate a live session; an explicit fresh session can seed from the product transcript with the loss disclosed.

## Storage and service port

The first implementation gate is an offline workerd test of the installed Drizzle `durable-sqlite` driver against the real shared schema and the query/transaction shapes used by machine claim. A matching SQLite dialect does not prove the native `Db` interface is portable: `.run()` metadata, native `$client`, transactions, migration setup, FTS and filesystem data migrations need separate examination. Do not force-cast one driver to the other.

That gate passed four local workerd tests: current empty-schema loading and shared mappings, competing conditional claims with held-step boundaries and restart persistence, whole/nested rollback, and actual mutation metadata. The DO driver's `.run()` returns `undefined`; returning rows provide a tested alternative for conditional winner detection. These are representative SQL shapes, not the production claim service or full migration replay. The local fixture uses a version table because workerd rejects `PRAGMA user_version`.

After that gate, extract only platform-neutral service contracts that both drivers actually implement. Local startup/backup/migration remains native. Cloud migrations are bundled SQL, versioned and transactional where supported, with no filesystem or native-addon imports. Existing local data is not automatically uploaded. Migration of an existing installation, attachments/large artifacts, exports and destructive restore require explicit designs; the first cloud pilot uses a fresh database and bounded text-only tasks.

The first runnable vertical slice must use real task/step routing and the daemon execution seam with two isolated runner homes. A transport simulator alone is insufficient. It must prove named-runner selection, duplicate dispatch suppression, restart/reconnect reconciliation, stale-generation rejection, revocation, all-runners-offline behavior and absence of provider credential transport. A credential-free deterministic backend proves plumbing only; a real-model run requires separately approved local credentials and is reported separately.

## Cost and limits

Published prices checked 2026-11-15 are in the research note. SQLite DO can use Free. Workers Paid includes DO under one $5/account/month minimum; it is not $5 plus another DO subscription. An otherwise-unused account with one personal DO, up to five runner sockets, bounded text history and modest request/SQL/CPU usage can fit Free or the Paid included allowances. Even one continuously awake DO for 30 days is 331,776 GB-s under the vendor's example units, below Paid's 400,000 included. Five separate continuously awake DOs can instead cost about $30 including rounded duration overage.

Use hibernating inbound sockets, bounded frames/body sizes, sequence acknowledgements, batched transcript delivery, indexed queries and bounded retention. Admit work against durable per-installation limits before expensive storage/fanout; byte/event/connection/enrollment limits and rejection behavior belong in the protocol slice. Free exhaustion is a visible availability failure. Spending controls have lag and existing-WebSocket exceptions, so neither application limits nor CF controls promise a maximum bill. Existing applications share account allowances. Models, optional storage/logs/builds, taxes and other services are outside the estimate; 100 separately deployed users do not share one $5 account.

## Delivery gates

1. Design and storage portability proof, no public endpoints or deployment. Measure actual compatibility instead of cloning a scheduler.
2. Shared storage/service boundary plus real task/claim/finish behavior in local workerd. Preserve local and Tailscale checks. Add durable fencing/idempotency only through reviewed schema and wire changes.
3. Local-only model credentials and runner-hosted Coordinator; two-runner offline/recovery/stop/revoke acceptance. Missing unsupported cloud APIs fail explicitly rather than falling back to a privileged home server.
4. Owner/bootstrap/recovery/enrollment, static web integration and guided setup, with security tests and rendered browser/phone states. Update the feature map when those surfaces exist.
5. After separate authorization, a user-owned cloud pilot: deploy, measure Free CPU/SQL/duration, test actual hibernation, export/recovery and first-result setup without assistance. Only then advertise cloud mode as available. CI passing on a library slice is not completion of these gates.
