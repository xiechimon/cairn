## Attachments and file preview

Slices S4 (file preview panel) and S5 (composer and sent attachments) of the second recording audit were built web-only against reference recording B (drag a file into the composer, send it, open it in the right-hand panel). The web reads only what the server serves today. Fixtures `chief-files`, `chief-files-image`, `chief-files-long`, `chief-files-unsupported`, `chief-files-composer`, `chief-files-uploading` and `chief-files-failed` cover every state; their file bodies come from a fixture-only `FixtureSet.attachments` map, so no fixture needs a server.

What exists today, for reference:

- Storage: one row per attachment in the `attachment` table and the bytes on disk at `<attachmentsDir>/<teamId>/<id>.<ext>` (`apps/server/src/services/attachments.ts`, `grantUpload`, `uploadFile`). The draft and the sent message carry only the markdown token `![<name>](attachment:<teamId>/<id>.<ext>)`.
- Upload: `POST /api/uploads/grant` returns a signed grant (HMAC payload with id, key, size, mime and scope, five-minute expiry, `apps/server/src/lib/attachments-token.ts`), then `POST /api/uploads/upload` stores the bytes and re-checks size, mime and quota.
- Limits: 10 MB per file (`ATTACHMENT_MAX_BYTES` in `packages/shared`), a per-team byte quota (`TEAM_ATTACHMENTS_QUOTA_BYTES`), a mime allow list (`text/*`, `image/*`, JSON, PDF, XML) and an extension allow list (text and code formats, common images, `pdf`, `log`, `diff`, `patch`). The web pre-checks size and mime with the same rules (`apps/web/src/api/attachments.ts`), so the web and the server reject the same files.
- Read: `GET /api/attachments/:id` (`apps/server/src/routes-uploads.ts`), team-scoped by the session, with `content-type` from the stored row, `x-content-type-options: nosniff`, `content-security-policy: sandbox; default-src 'none'`, and `content-disposition: inline` for PNG, JPEG, GIF, WebP and PDF, `attachment` without a file name for everything else.
- Agent side: a machine fetches attachments through `GET /api/machine/attachment/:stepId/:attachmentId` (`apps/server/src/routes-machine.ts`); the daemon writes each token line of a step's input as a file under the step's materialize folder and passes inline images to the model (`apps/daemon/src/step-attachments.ts`). Agent tools read them through `readAttachmentMeta` in `services/attachments.ts` (used by `services/machines.ts` and `services/mcp-face.ts`), which returns text as UTF-8 and everything else as base64.
