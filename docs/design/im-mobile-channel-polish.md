# IM-first mobile channel polish (text-reply cards, restart cursor recovery, and reconnect UX) — plan, 2026-11-27

## User scenario

Someone who installed Cairn today opens **Settings -> Chat apps** (`/app/settings/im`) to talk to the Coordinator from their phone via **Telegram**, **Slack**, or **WeChat** (or **iMessage** on macOS). They already hold a Bot Token (Telegram), Slack App + Bot Tokens, or a personal WeChat account to scan the QR code; credentials are sealed at rest with `secretbox.key` inside SQLite `im_connection.secretCipher` (and cleared on portable export or account deletion). Before this change, live host diagnostics showed four concrete mobile reliability gaps:

1. **WeChat and other text-only replies cannot answer approval or question cards**: WeChat iLink renders no inline tap buttons (`buttons` are omitted when sending), yet `im/core.ts` only accepts structured `onAction` button callbacks (`imcb:<requestId>:<index>`). Replying `"1"` or `"发送"` starts a separate Coordinator message instead of resolving the waiting card.
2. **Server restarts lose polling cursors and WeChat reply tokens**: Telegram persisted `pollOffset` only before `update_id` advanced inside the loop (losing the last update's `+1` until a subsequent update arrived) and `telegram.ts` initialized `offset = null` instead of resuming from `fields.pollOffset`. WeChat stored `cursor` (`get_updates_buf`) and `contextTokens` purely in memory (`pollOffset: null` in DB), losing both across restarts and risking missed updates or refused `sendmessage` replies until the owner messages again.
3. **Raw `lastSendError` leaks into visible Settings copy (Rule C5)**: When `statusDetail` is `null` and a permanent or retry-exhausted `lastSendError` is recorded, `im-page.tsx` renders raw internal error text directly in the connection row instead of mapped user-facing copy with raw text in a tooltip, while `deliverOnce()` lacks a live-session guard so an already stopped/replaced session could race during reconnect and stamp an error onto the replacement session. (Intentional quiet `'drop'`-class errors remain unrecorded per `im-core.test.ts`.)
4. **Healthy (`ready`) connections lack an explicit Reconnect action**: In Settings -> Chat apps, `重连` only appears when status is `degraded`, `expired`, or `error`; recovering a stale socket without deleting paired senders forces deleting and re-pairing the connection.

When any recovery or card answer fails, the UI shows mapped copy (`最近一次回复发送失败` / `Last reply failed to send` with raw detail only in tooltip; `重连失败，请重试。` toast) and preserves paired senders and encrypted credentials.

## Scope

1. **Text-reply card resolution (`apps/server/src/services/im/core.ts`)**:
   - In `onMessage`, after `persistPollOffset`, `rememberInbound`, and `paired` checks pass, when `msg.images.length === 0 && msg.files.length === 0 && msg.text.trim() !== ''`, inspect up to 5 most recent `delivered` `external_effect` rows (`kind = 'im-send'`, matching `connId`, `chatKey`, non-null `requestId`, ordered by `desc(externalEffect.createdAt), sql\`rowid desc\``).
   - Pick the newest matching `chiefMessage` (`askQuestionContentOf`) where `status === 'pending'`, `questions.length === 1`, and `options.length > 0`.
   - Normalize trimmed `msg.text` by converting full-width digits `０-９` to ASCII `0-9`. Check 1-based numeric choice first (`/^([1-9]\d?)[.。、]?$/`, rejecting `0`/`00`, requiring `index < options.length`), and only if not matched check exact case-insensitive equality against `option.label.trim()`.
   - If matched, call `answerCard(connId, row, { chat: msg.chat, sender: msg.sender, value: \`imcb:${requestId}:${optionIndex}\`, messageId: msg.messageId })` and `return` so no user `chiefMessage` or extra `chief` step is created and `imTurnOrigin` attaches to the resumed/wake step; otherwise fall through to normal `enqueueChiefStep`. Keep `questionCard().text` format unchanged.
2. **Race-free cursor & encrypted WeChat `context_token` persistence (`apps/server/src/services/im/{types,core,telegram,wechat}.ts`)**:
   - Extend `ImConnectionHandlers` with optional `onOffset?(offset: string | number): void` and `onSecretField?(key: string, value: string): void`, and widen optional `session.offset?()` return type to `string | number | null`.
   - In `core.ts`, accept `string | number | null` from `sessionOffset`, extract `savePollOffset(connId, offset)` (no-op if row vanished or unchanged) used by both `persistPollOffset` and `handlers.onOffset`, and add `saveSecretField(connId, key, value)` used by `handlers.onSecretField` to update `secretCipher` via `deps.box.seal` only when the value actually changed (no-op if row vanished or `secretCipher` cannot be opened).
   - In `telegram.ts`, seed `offset` from `fields.pollOffset` when positive safe integer (`null` otherwise). In `poll()`, run `await normalizeMessage(...)` first, bail if `stopped`, and only then advance `offset = update.update_id + 1` and invoke `handlers.onOffset?.(offset)` right before `handlers.onMessage` / `handlers.onAction` (also invoking `onOffset` when a message update normalizes to `null` or is a `callback_query`).
   - In `wechat.ts`, seed `cursor` from `fields.pollOffset` (`''` if absent/empty) and expose `offset: () => (cursor === '' ? null : cursor)`. Hydrate `contextTokens` (`Map<string, string>`, max 50 non-empty string entries FIFO/LRU) safely from `fields.contextTokensJson` (fallback empty map on missing/invalid JSON). Make `deliver(message)` synchronous (no `await` inside), process the entire `orderMessages(answer.msgs)` batch synchronously (with delete-then-set LRU cap 50 calling `handlers.onSecretField?.('contextTokensJson', ...)` only when the JSON payload changed), and update `cursor = answer.get_updates_buf` + `handlers.onOffset?.(cursor)` synchronously immediately after the batch (including empty batches when `get_updates_buf` advances). When `fields.pollOffset` is absent, initial `getupdates` still sends `get_updates_buf: ''`.
3. **Rule `C5` `lastSendError` mapping, WeChat card copy, and stale-session guard (`apps/server/src/services/im/core.ts`, `apps/web/src/routes/im-page.tsx`, `apps/web/src/i18n/en.ts`)**:
   - Keep intentional `'drop'` semantics untouched (`drop-class sends vanish quietly without a recorded error` in `im-core.test.ts` remains unchanged and passing). In `deliverOnce(connId, msg)`, capture `const session = live.get(connId)` at entry, bail with `'offline'` before retry backoff if `live.get(connId) !== session`, and guard all `sendErrors.set` / `sendErrors.delete` / `markStatus('expired')` mutations with `if (live.get(connId) === session)` so stopped, deleted, or replaced sessions never stamp stale errors during `reconnectConnection` or `deleteConnection`.
   - In `im-page.tsx`, preserve `conn.statusDetail` when non-null; whenever `conn.statusDetail === null && conn.lastSendError !== null` (across ALL `ImConnectionStatus` values), render `· ` + `<span className="text-destructive" title={conn.lastSendError}>{t('最近一次回复发送失败')}</span>` (and add `'最近一次回复发送失败': 'Last reply failed to send'` to `apps/web/src/i18n/en.ts`).
   - Update `PLATFORM_COPY.wechat.info` to `'在平时的聊天里和 Coordinator 对话，回复数字或文字就能点卡片上的按钮。'` and add `'在平时的聊天里和 Coordinator 对话，回复数字或文字就能点卡片上的按钮。': 'Talk to the Coordinator in your usual chat. Reply with a number or text to choose a card option.'` in `apps/web/src/i18n/en.ts`.
4. **Manual Reconnect action in row menu (`apps/web/src/routes/im-page.tsx`)**:
   - In `connectionRow`'s `KeyedMenuContent`, when `live && !(conn.status === 'expired' && conn.platform === 'wechat')`, render a `KeyedMenuItem` with `shortcut="R"`, `data-testid={`im-reconnect-menu-${conn.id}`}`, `disabled={mutations.reconnectConnection.isPending}`, label `{t('重连')}`, calling `mutations.reconnectConnection.mutate(conn.id, { onError: (error) => toastError(t('重连失败，请重试。'), error) })` while keeping inline `重连` / `重新扫码` repair buttons for non-ready states unchanged.

### State transitions, readers, writers, and failure paths

| State | Writers | Readers | Transitions & Failure Paths |
|---|---|---|---|
| `im_connection.pollOffset` | `core.ts` (`savePollOffset` via `onOffset` and `persistPollOffset`), `backup-service.ts` (`NULL` on export/import) | `core.ts` (`startConnection` passes `fields.pollOffset`), `telegram.ts`, `wechat.ts` | Advances only after async download finishes (Telegram) or synchronous batch completes (WeChat); invalid/empty `pollOffset` falls back to `null`/`''`; deleted rows ignore late `onOffset` callbacks |
| `im_connection.secretCipher` (`contextTokensJson`) | `core.ts` (`createConnection`, `saveSecretField` via `onSecretField`), `backup-service.ts` | `core.ts` (`openFields`), `wechat.ts` (`connect` hydrates `Map`) | Encrypted via `deps.box.seal`; capped at 50 entries via delete-then-set LRU; corrupt JSON falls back to empty map; deleted row or corrupt `secretCipher` in `saveSecretField` is a safe no-op and `startConnection` marks corrupt cipher `error` |
| `sendErrors` in-memory map (`lastSendError`) | `core.ts` (`deliverOnce` when `live.get(connId) === session`; `reconnectConnection`/`deleteConnection` clear; `'drop'` never sets) | `core.ts` (`recordOf`), `im-page.tsx` (`connectionRow`) | Stale stopped sessions exit early or skip mutating replacement session state; next successful delivery or reconnect clears error; `im-page.tsx` maps `lastSendError` under Rule C5 for all statuses |
| `chiefMessage` card + `external_effect` (`im-send`) | `chief-question-store.ts`, `action-proposals.ts`, `core.ts` (`answerCard` via `onAction` or text reply) | `core.ts` (`onMessage` delivered-card lookup, `answerCard`) | Guarded by `delivered` `external_effect` (`connId` + `chatKey` + `requestId`, newest `createdAt, rowid`), `status === 'pending'`, single question, and paired sender check; already-answered cards reply `这条消息已经处理过了。` |

## Out of scope

- Changing intentional `'drop'` send-error classification (`errors.ts` / `imessage.ts`) or weakening `im-core.test.ts` drop-class test.
- Outbound binary media/file uploads from Cairn to IM chats or decrypting WeChat CDN AES inbound images (`wechat.ts` media CDN protocol deferred).
- Group-chat routing changes in Slack (`app_mention`) or Telegram (`mentioned` gating stays untouched).
- New database columns or Drizzle migrations (all persistence uses existing `pollOffset` and encrypted `secretCipher`).
- Multi-tenant SaaS or self-hosted VPS Docker Compose changes (covered by Wave 5 and scheduled Post-Wave-5 follow-up).
