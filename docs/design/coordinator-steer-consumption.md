## Contract and existing execution boundary

The in-server Coordinator uses the installed pi-durable input submission as its sole consumption authority. One immutable batch per steered owner message uses that waiting step's ID as its conversation-scoped request ID. Multiple inputs may be consumed in one runtime boundary; each submission independently supplies its actual entry ID. Content, target step and exact owner IDs are frozen before submission. No text or timestamp matching, alternate delivery mode, runtime dependency or lockfile change is introduced. Generic task steering and the existing daemon-hosted compatibility Coordinator do not supply native entry IDs; their existing transport remains unchanged and cannot claim native provenance.

Choose the transport from the claimed target: a chief step claimed with `machineId === null` is native; a machine-owned chief or generic task keeps the existing transport. Freeze that ownership with the batch. `coordinatorRunsOnPi()` is insufficient because it also includes server-context compatibility execution. Native batch creation replaces the native `steer_pending` write, and native pull/receipt replaces native fetch/ack; daemon machine routes retain their current schemas and behavior. Shared withdraw, pending-display, claim, stop, finish and stale-step paths must respect the retained native hold. A later route change cannot move a bound batch into the daemon buffer or ordinary queued execution before reconciliation.

SDK numeric IDs identify records only within one durable store incarnation. The installed SQLite allocator starts at 2, so a newly created store can reuse conversation, entry and task IDs. Initialize an opaque random `storeId` in an application-owned SDK SessionDoc, in the paused store before recovery/observation/resume; reopening reads the same value, and a recreated store initializes a new value. Record this identity in `coordinator_conversation` and freeze it into bound inputs, generation bindings and derived entry anchors. An ordinary reopen, version backup or same-store rewind keeps the epoch. Actual store replacement/reseed changes it. SDK calls still receive their original numeric IDs; host lookup and validation use `(threadId, storeId, conversationId, entryId/taskId)`. Include the epoch in generation-binding keys and all scoped indexes, caches, watermark/rewind validation and receipt-idempotency comparisons. Keep epoch null only for genuinely unbound inputs or unverified legacy provenance; it cannot be inferred from the current host row when accepting a receipt.

Store the identity without duplicating epoch columns: `coordinator_conversation` keeps `storeId` plus the raw SDK `conversationId`; `coordinator_input`, `coordinator_entry` and `coordinator_run` store the canonical qualified key `${storeId}:${sdkConversationId}` in their existing `conversationId` field. One typed encoder/parser validates an opaque delimiter-safe epoch and a valid numeric SDK ID. All native callbacks construct this key from their captured opened-store identity. Server validation compares the supplied key to the host's encoded current pairing; it never fills a missing caller epoch from that row. Decode a qualified key for SDK access only after its epoch matches the actually opened SessionDoc. Migrate every numeric-conversation consumer, including rewind and source resolution, to the helper. Raw historical keys are a conservative legacy provenance case, not accepted native callback identity or permission to query/release input against a new store.

The SDK store's SessionDoc is the incarnation authority; the host row records its active pairing. Host and SDK databases cannot switch atomically: after a crash between set-aside/open and host update, read the actual paused store identity and finish the pairing before dependent work. Never relabel old inputs/runs with the new epoch, and never query a fresh store to decide whether an old-epoch submission was placed. Reconcile old work before replacement; uncertain old work stays explicit. First upgrade initializes the marker once and associates existing anchors only with the verified existing store; unprovable historical rows remain incomplete. Callbacks capture the epoch of the harness that produced them, and stale-epoch callbacks cannot mutate current mappings or watermarks. A receipt replay for an already consumed input is idempotent only when its frozen epoch/conversation/entry all match. Reusing a host initial request across epochs requires a distinct, lifecycle-approved execution identity; an old consumed or uncertain input is not retagged or automatically replayed.

Native transcript row identity also includes the epoch: the old `${stepId}-e${entryId}` format alone can overwrite an earlier answer when a step runs against a replacement store. Use one shared native source-ID encoder/parser carrying step, epoch and entry, preserve existing stored row IDs, and accept legacy IDs only through verified legacy anchors. Scope native tool-row identities too, while retaining raw SDK/provider call IDs in tool payloads. Live and recovery mirroring use the same identity function. Historical source resolution matches the source answer's own epoch against immutable receipts, rather than requiring the answer to belong to the currently active store; rewind execution accepts only an anchor valid for the selected store/conversation.

## Persistent state and transitions

Add a Coordinator-only batch table: ID, thread ID, target step ID, exact owner message IDs, frozen content, bound runtime conversation ID, state (`pending`, `consumed`, `released`), consumed entry ID and timestamps. Keep the waiting owner step until a durable consumption receipt. Batch creation and its `steer` hold are one server-DB transaction. The native server API reads this queue instead of consuming `steer_pending`; a second arrival creates another immutable batch.

`pending/unbound -> pending/bound`: a claimed native target pulls the oldest pending batch and binds the current recorded runtime conversation. A repeated pull returns the same batch. Submit with request ID equal to batch ID; retry/reopen reuses the same submission. Admission is not consumption.

Initial inputs are identified by `(threadId, stepId, kind=initial, qualifiedConversation)`, with database-enforced uniqueness for that initial identity. Preparation returns its persisted batch ID as the SDK request ID; runtime lookup, liveness and recovery use that returned ID rather than assuming it equals the host step. The first initial batch may retain the step ID. A lifecycle-approved execution after a genuine reseed allocates a fresh initial batch/request ID, preserving old records and frozen owner sets; retries in the same qualified conversation return that same batch. A new epoch alone does not authorize repeating completed work or bypass an unresolved old admission. Adopt an existing pre-upgrade claimed input only after exact lookup of its old request ID in the verified old store, preserving that request identity and proving its initial owner members independently of the turn's eventual owner set.

Native pull may exclude request IDs whose durable admission the runtime has confirmed in this exact target/conversation. The default empty exclusion set retains the retry contract. This is a per-runtime scheduling cache, not another persisted state: add an ID only after successful `submit` or exact request lookup proves a matching input record. Validate its batch membership, target and bound conversation; discard the cache on target/conversation change. A lost pull/submit response leaves the ID eligible until an exact lookup or idempotent retry proves admission. After recovery reconciles receipts and terminal records, rebuild the cache from remaining queued inputs before resuming. Exclusion never expands owner IDs, authorizes an image, deletes a held step, releases input or bypasses the receipt barrier.

One serialized poll drains current eligible batches in order without waiting for placement or final answers, so an admitted input waiting behind `ask_user` cannot prevent the next image from being admitted. Stop/turn finalization cancels further pulls and joins the in-flight drain before receipt reconciliation, release or gate teardown. Input arriving after the runtime boundary may still execute in a successor turn; admission draining does not promise that all arrivals share one model request. For any recovered record, an entry takes precedence over terminal status; terminal without entry permits release, queued only permits admission exclusion. The installed SDK throws `ConversationIdle` before creating a submission for `whenIdle: 'reject'`: after all submit attempts for that ID are joined, authoritative idle rejection plus exact absence in the intact bound conversation also proves non-admission. Transport errors, timeouts and generic exceptions remain uncertain and retain pending work.

`pending/bound -> consumed`: observe an input submission with an actual entry. In one server-DB transaction, validate batch/thread/target/conversation/member identity, write owner-to-entry mappings, add only these consumed owners to the producer, mark the named batch consumed and delete only its waiting step. Repeat is idempotent; a different entry/conversation is rejected. A late acknowledgment cannot touch a later batch. Initial input mapping also happens at placement, without retroactively mapping the turn's eventual owners to its first entry.

Consumed `coordinator_input` records are the immutable native provenance ledger. Resolve a native assistant source from that producer's consumed initial/steer records in the source's exact conversation, ordered by numeric input entry ID and strictly before the assistant entry. Validate each surviving authentic owner source and deduplicate owner IDs only after selecting eligible receipts. `coordinator_entry` remains a derived assistant-source/rewind index: its single `chiefMessageId` key can overwrite a user's old entry when the same owner input is consumed again, so its latest user mapping is not native historical authority. An existing native ledger with no eligible receipt never falls back to the mutable owner set. Only historical producers with no native input records use the previously approved conservative compatibility resolver. Pending/released inputs grant nothing; missing source entry identity or unavailable/deleted owner material remains incomplete. Rewind may invalidate derived anchors but does not rewrite consumed history into the new conversation.

`pending -> released`: only after the runtime proves rejection/abortion without an input entry, or after a stopped/retired runtime is reconciled and proves no placement, release that named batch. In the same server transaction, retire its held step and enqueue one ordinary successor with a fresh step/request ID and the same frozen content and authentic owner IDs. Record the successor ID for idempotent release. Reusing the held step ID would reacquire the old rejected/aborted SDK submission instead of executing the queued work. Initial placement maps the submission's frozen owner IDs, which need not equal its execution step ID; pending-message UI continues to identify the original owner message. An uncertain receipt stays pending; it is never treated as delivered or silently discarded. A placed-but-unanswered submission is still consumed. Stop joins or aborts the native run and reconciles receipts before releasing unconsumed input. Restart reconciles pending batches by request ID in their bound conversation before resuming dependent work. Rewind/reseed cannot reuse a mapping from an old runtime conversation or a deleted owner message.

Recovery runs under the existing thread lease when opening or waking a thread, before claiming a held child as ordinary work, even when its parent is failed, stopped or abandoned. Include threads with pending batches in recovery discovery. Open the durable store paused, attach its observer, and read every bound pending batch by its exact conversation/request ID, including settled submissions. Persist all records with an entry first; terminal parent status does not invalidate a genuine receipt. For an unplaced record on a retired parent, abort it and reread its durable terminal state before releasing. A missing request in an intact, paused bound conversation proves non-admission; an unavailable store or missing conversation leaves an observable blocked pending batch. Only after this reconciliation may `openReconciledHarness` settle stale submissions, run `hasContentBeyond`, move aside/reseed the store, clear entry mappings or resume tasks. Keep the observer attached for the lifetime of that harness. A crash after placement but before host persistence recovers through this same request lookup, without submitting again or depending on the parent's run loop.

After receipt persistence, replay the corresponding stored native transcript through existing `entryRowSources`, using the original target step for assistant row IDs and the frozen conversation identity for mappings. Page through the complete bounded input/run interval, including stored tool results; this restores rows only and never executes tools. Prove interval ownership from durable submissions/run identity, not neighboring timestamps or a steer entry treated as a new producer. Advance the handled watermark only after every entry through that point is accounted for and all required rows/mappings are durable; inputs with no visible row still require a persisted receipt. Never jump over unknown/unprocessed content by taking the maximum receipt/store entry. A crash during replay repeats idempotent row writes, and a crash after receipt commit still discovers replay debt from the lagging watermark even when no batch remains pending. Refresh reconciliation facts from the host DB before `hasContentBeyond` or a reseed decision. Preserve an existing `rewind:` watermark until rewind synchronization handles it; recovery cannot replace that intent with a normal mirrored watermark.

An initial submission's `entry..answer` is not the producer's complete interval. Installed `generation.answer()` may append that answer, place a queued steer and start a new generation in the same commit. Recovery considers every exact submission belonging to the target, including its later answers. Candidate intervals alone do not establish ownership: `GenerationTask` handover creates a new conversation-owned task with empty input, and the internal `submissionIds` option becomes tracing context rather than a stored task-to-input edge. Persist a native generation-task binding keyed by conversation/task ID, derived from a stored `pi.live.run` value's `taskId` and exact `inputs` submission IDs resolved to one target. The commit observer captures this value without calling Session APIs; the existing ordered persistence pipeline stores the binding. Before a generation makes a provider request, its barrier requires the binding to be durable. Paused recovery also reads the current `LiveDoc.run` or `runFailure` to recover an unacknowledged binding; missing, mixed-target or unknown input identity remains blocked. Keep terminal task bindings for replay, independent of the current gate or latest owner index. This belongs to runtime integration, not the inactive foundation PR.

Validate assistant entries through `EntryRecord.byTaskId` and their durable generation binding. Validate tool results through their `ToolTask` record: a model tool names its exact assistant entry and call ID, its task owner names that assistant's generation, and all conversations must agree. A generation's terminal result entry ID supplies an additional consistency check. Read complete task/entry pages and join tool results across pages before calling `entryRowSources`; unknown or unowned model-visible entries stop watermark progress. Known bookkeeping/compaction entries need explicit classification rather than being assigned to the nearest producer. A normal host turn retains its gate and mirror until all admitted target-owned inputs and their auto-started generations settle; original `initial.wait()` alone is insufficient. Stop/retire joins or aborts that work and reconciles it before clearing ownership. The admission poll itself still never waits for an answer.

Rewind first stops and reconciles the old conversation, then forks/reseeds and invalidates old mappings. A proven placed batch stays consumed and is never replayed into the new conversation; deleted owners receive no new mapping or grant. A surviving provably unplaced owner returns to ordinary queued work; thread deletion removes its batches. Upgrade coverage must include old native `steer`/`steer_sent` holds and `steer_pending`: migrate provably unsent work to identified batches once, and reconcile any existing durable admission before releasing sent work. Uncertain old admissions remain blocked and explicit. Generic/daemon buffers are outside this migration.

Legacy unsent migration may be delivered as an uncalled C helper and activated only in D. Run it under the thread lease after excluding the old native fetcher, before resuming or ordinary claiming. In one host transaction, reread the legacy native buffer, its exact target and pending waiting steps. A concrete waiting row with `holdReason === 'steer'` and the matching still-present native buffer has not passed the old fetch transition for this queued attempt: old fetch changes holds to `steer_sent` before deleting/returning that buffer. Freeze each surviving authentic waiting step's own original prompt, owner IDs and scope into an unbound batch, immediately release it to one fresh ordinary successor, then remove the obsolete buffer once its pending work is accounted for. Preserve the owner messages. The successor receives ordinary scoped/volatile context; do not split merged buffer text or copy that whole buffer into every successor. Repeating migration creates no additional successor. The old active model finishes or is reconciled before these ordinary successors are claimed.

`steer_sent` proves neither rejection nor non-admission, even if another buffer exists; leave it explicitly blocked without an exact SDK identity. Malformed/mismatched native state, unknown ownership or evidence of an earlier unresolved sent attempt also remains blocked. Current `steer` state proves only this attempt's pre-fetch position, not that the owner was never submitted in an earlier attempt. Remove no unidentified pending work, and leave daemon/generic buffers unchanged. Migration tests assert one successor execution per migrated attempt and no duplicate queue delivery, without claiming exactly-once external side effects from the model.

## Ordering and lifecycle inventory

Attach a stored-commit observer before native tasks resume; recover an initial snapshot of relevant submission records, then process live placements. Queue host receipt persistence in one ordered pipeline. Both transcript mirroring (including deltas) and Coordinator tool dispatch await that pipeline. A persistence failure blocks the dependent action, remains observable and is retried from the same persisted submission. Do not wait for `Submission.wait()` to discover consumption: it waits for a final answer.

The synchronous observer only captures stored publication data and queues receipt work; it calls no Session API. Process every placement in a publication before releasing dependent mirror/tool actions, irrespective of change order within that publication. Use one recoverable receipt drain per harness: keep a failed receipt at its head, expose the failure, retry that receipt, and keep barriers closed until it commits. A rejected promise must not permanently poison later retries. The tool barrier ends before calling `relayTool` or awaiting `ask_user`; long-running tools and their results never occupy the receipt queue. Mirror callbacks also await the barrier outside Session commit callbacks. Otherwise an unanswered question can deadlock the very steer receipt needed to continue it. Shutdown joins the drain before detaching the observer or closing storage; errors retain pending work for restart.

| Placement and mirror/tool | Persist receipt before exposing or dispatching from the dependent answer, even before turn settlement. |
| New arrival and late acknowledgment | Old acknowledgment affects only its named batch; identical text and a shared input boundary preserve all distinct IDs. |
| Receipt or acknowledgment failure | Keep waiting work and replay the same submission; never submit a second input or claim a missing receipt. |
| Stop, completion and abandoned target | Reconcile placements; restore only provably unconsumed work, including when a stop overlaps placement. An admitted-then-aborted batch executes once under its fresh successor ID; repeated release creates no second successor. |
| Process restart | Read settled and unsettled submissions by request ID before replay or reseed; recover placement with a failed parent and a lagging mirror watermark. |
| Rewind, reseed and thread removal | Validate the bound conversation and surviving owner IDs; retire stale batches and clean up their dependent rows. |
