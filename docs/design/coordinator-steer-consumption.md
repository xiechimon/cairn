Measured baseline: the real Coordinator regression `coordinator/steer-provenance.test.ts` ends with no inherited image grant after consuming an image steer. Delivery has two independently reviewable PRs: first the inactive table/migration and atomic input-state API with its failure tests; then native runtime, recovery, resolver and lifecycle integration with end-to-end acceptance. The foundation has no production callers or queue activation and changes no existing transport. It freezes initial inputs as well as steers so successor steps retain authentic owner identity. ## Contract and existing execution boundary

The in-server Coordinator uses the installed pi-durable input submission as its sole consumption authority. One immutable batch per steered owner message uses that waiting step's ID as its conversation-scoped request ID. Multiple inputs may be consumed in one runtime boundary; each submission independently supplies its actual entry ID. Content, target step and exact owner IDs are frozen before submission. No text or timestamp matching, alternate delivery mode, runtime dependency or lockfile change is introduced. Generic task steering and the existing daemon-hosted compatibility Coordinator do not supply native entry IDs; their existing transport remains unchanged and cannot claim native provenance.

Choose the transport from the claimed target: a chief step claimed with `machineId === null` is native; a machine-owned chief or generic task keeps the existing transport. Freeze that ownership with the batch. `coordinatorRunsOnPi()` is insufficient because it also includes server-context compatibility execution. Native batch creation replaces the native `steer_pending` write, and native pull/receipt replaces native fetch/ack; daemon machine routes retain their current schemas and behavior. Shared withdraw, pending-display, claim, stop, finish and stale-step paths must respect the retained native hold. A later route change cannot move a bound batch into the daemon buffer or ordinary queued execution before reconciliation.

## Persistent state and transitions

Add a Coordinator-only batch table: ID, thread ID, target step ID, exact owner message IDs, frozen content, bound runtime conversation ID, state (`pending`, `consumed`, `released`), consumed entry ID and timestamps. Keep the waiting owner step until a durable consumption receipt. Batch creation and its `steer` hold are one server-DB transaction. The native server API reads this queue instead of consuming `steer_pending`; a second arrival creates another immutable batch.

`pending/unbound -> pending/bound`: a claimed native target pulls the oldest pending batch and binds the current recorded runtime conversation. A repeated pull returns the same batch. Submit with request ID equal to batch ID; retry/reopen reuses the same submission. Admission is not consumption.

`pending/bound -> consumed`: observe an input submission with an actual entry. In one server-DB transaction, validate batch/thread/target/conversation/member identity, write owner-to-entry mappings, add only these consumed owners to the producer, mark the named batch consumed and delete only its waiting step. Repeat is idempotent; a different entry/conversation is rejected. A late acknowledgment cannot touch a later batch. Initial input mapping also happens at placement, without retroactively mapping the turn's eventual owners to its first entry.

Consumed `coordinator_input` records are the immutable native provenance ledger. Resolve a native assistant source from that producer's consumed initial/steer records in the source's exact conversation, ordered by numeric input entry ID and strictly before the assistant entry. Validate each surviving authentic owner source and deduplicate owner IDs only after selecting eligible receipts. `coordinator_entry` remains a derived assistant-source/rewind index: its single `chiefMessageId` key can overwrite a user's old entry when the same owner input is consumed again, so its latest user mapping is not native historical authority. An existing native ledger with no eligible receipt never falls back to the mutable owner set. Only historical producers with no native input records use the previously approved conservative compatibility resolver. Pending/released inputs grant nothing; missing source entry identity or unavailable/deleted owner material remains incomplete. Rewind may invalidate derived anchors but does not rewrite consumed history into the new conversation.

`pending -> released`: only after the runtime proves rejection/abortion without an input entry, or after a stopped/retired runtime is reconciled and proves no placement, release that named batch. In the same server transaction, retire its held step and enqueue one ordinary successor with a fresh step/request ID and the same frozen content and authentic owner IDs. Record the successor ID for idempotent release. Reusing the held step ID would reacquire the old rejected/aborted SDK submission instead of executing the queued work. Initial placement maps the submission's frozen owner IDs, which need not equal its execution step ID; pending-message UI continues to identify the original owner message. An uncertain receipt stays pending; it is never treated as delivered or silently discarded. A placed-but-unanswered submission is still consumed. Stop joins or aborts the native run and reconciles receipts before releasing unconsumed input. Restart reconciles pending batches by request ID in their bound conversation before resuming dependent work. Rewind/reseed cannot reuse a mapping from an old runtime conversation or a deleted owner message.

Recovery runs under the existing thread lease when opening or waking a thread, before claiming a held child as ordinary work, even when its parent is failed, stopped or abandoned. Include threads with pending batches in recovery discovery. Open the durable store paused, attach its observer, and read every bound pending batch by its exact conversation/request ID, including settled submissions. Persist all records with an entry first; terminal parent status does not invalidate a genuine receipt. For an unplaced record on a retired parent, abort it and reread its durable terminal state before releasing. A missing request in an intact, paused bound conversation proves non-admission; an unavailable store or missing conversation leaves an observable blocked pending batch. Only after this reconciliation may `openReconciledHarness` settle stale submissions, run `hasContentBeyond`, move aside/reseed the store, clear entry mappings or resume tasks. Keep the observer attached for the lifetime of that harness. A crash after placement but before host persistence recovers through this same request lookup, without submitting again or depending on the parent's run loop.

After receipt persistence, replay the corresponding stored native transcript through existing `entryRowSources`, using the original target step for assistant row IDs and the frozen conversation identity for mappings. Page through the complete bounded input/run interval, including stored tool results; this restores rows only and never executes tools. Prove interval ownership from durable submissions/run identity, not neighboring timestamps or a steer entry treated as a new producer. Advance the handled watermark only after every entry through that point is accounted for and all required rows/mappings are durable; inputs with no visible row still require a persisted receipt. Never jump over unknown/unprocessed content by taking the maximum receipt/store entry. A crash during replay repeats idempotent row writes, and a crash after receipt commit still discovers replay debt from the lagging watermark even when no batch remains pending. Refresh reconciliation facts from the host DB before `hasContentBeyond` or a reseed decision. Preserve an existing `rewind:` watermark until rewind synchronization handles it; recovery cannot replace that intent with a normal mirrored watermark.

Rewind first stops and reconciles the old conversation, then forks/reseeds and invalidates old mappings. A proven placed batch stays consumed and is never replayed into the new conversation; deleted owners receive no new mapping or grant. A surviving provably unplaced owner returns to ordinary queued work; thread deletion removes its batches. Upgrade coverage must include old native `steer`/`steer_sent` holds and `steer_pending`: migrate provably unsent work to identified batches once, and reconcile any existing durable admission before releasing sent work. Uncertain old admissions remain blocked and explicit. Generic/daemon buffers are outside this migration.

## Ordering and lifecycle inventory

Attach a stored-commit observer before native tasks resume; recover an initial snapshot of relevant submission records, then process live placements. Queue host receipt persistence in one ordered pipeline. Both transcript mirroring (including deltas) and Coordinator tool dispatch await that pipeline. A persistence failure blocks the dependent action, remains observable and is retried from the same persisted submission. Do not wait for `Submission.wait()` to discover consumption: it waits for a final answer.

The synchronous observer only captures stored publication data and queues receipt work; it calls no Session API. Process every placement in a publication before releasing dependent mirror/tool actions, irrespective of change order within that publication. Use one recoverable receipt drain per harness: keep a failed receipt at its head, expose the failure, retry that receipt, and keep barriers closed until it commits. A rejected promise must not permanently poison later retries. The tool barrier ends before calling `relayTool` or awaiting `ask_user`; long-running tools and their results never occupy the receipt queue. Mirror callbacks also await the barrier outside Session commit callbacks. Otherwise an unanswered question can deadlock the very steer receipt needed to continue it. Shutdown joins the drain before detaching the observer or closing storage; errors retain pending work for restart.

| Path | Required behavior and negative control |
| --- | --- |
| Composer and explicit steer | Freeze content and exact IDs once; repeated steering does not create a second batch. |
| Pull and durable admission | Lost pull/submit response returns the same identity; no owner expansion before placement. |
| Placement and mirror/tool | Persist receipt before exposing or dispatching from the dependent answer, even before turn settlement. |
| New arrival and late acknowledgment | Old acknowledgment affects only its named batch; identical text and a shared input boundary preserve all distinct IDs. |
| Receipt or acknowledgment failure | Keep waiting work and replay the same submission; never submit a second input or claim a missing receipt. |
| Stop, completion and abandoned target | Reconcile placements; restore only provably unconsumed work, including when a stop overlaps placement. An admitted-then-aborted batch executes once under its fresh successor ID; repeated release creates no second successor. |
| Process restart | Read settled and unsettled submissions by request ID before replay or reseed; recover placement with a failed parent and a lagging mirror watermark. |
| Rewind, reseed and thread removal | Validate the bound conversation and surviving owner IDs; retire stale batches and clean up their dependent rows. |
| Platform and upgrade | Native has one batch path; generic/daemon keep one existing path. Native held steps cannot leak into either claim path; migrate unsent legacy native holds and expose uncertain sent admissions. |
| Receipt barrier | A live `ask_user` permits receipt persistence; inject a host write failure, retry it, and prove mirror/dispatch stays blocked until the mapping commits. |
| Reply resolution and image delivery | Preserve entry-order cutoffs; earlier answers exclude later images; quoted post-consumption answers inherit authorized bytes. |
| Repeated owner consumption | Consume the same owner under two producers/entries, overwrite its derived user index, then quote both answers: each resolves its own historical receipt and excludes later inputs or another conversation. A native producer with no eligible receipt cannot enter legacy fallback. |
| Recovery mirror coverage | Fail after receipt commit but before mirror/watermark, restart with a retired parent, and restore stable original row IDs without duplicate tool execution or reseed. Include more than one entry page, unknown intervening content, and an existing rewind watermark. |
