# Recover browser live updates after a disconnect

A new Cairn user watching a reply or a task stays on the same screen when Wi-Fi drops. The existing content stays visible and a quiet “Reconnecting…” status appears only while recovering. There is nothing to configure or buy, and no new account or key. Authentication is unchanged; the follow set, revision and pending refreshes live in memory only. This uses fresh subscriptions and reads of authoritative rows, not server replay, cursors or `Last-Event-ID` resume. The existing [transport research](../research/streaming-transport-sse-vs-websocket-2026-11-17.md#8-recommendation) documents why one SSE per tab and refetch on reconnect fit Cairn.

| Situation | What the user sees | What Cairn does | Wait and cost |
|---|---|---|---|
| First connection or navigation | Ordinary content and loading states, even if the first connection fails | Retry startup without announcing a disconnect. If an initial attempt failed, refresh watched queries once the first healthy follow is acknowledged. A newly watched conversation with cached data refreshes its saved transcript after follow acknowledgment. | One follow PUT per effective set; one transcript read on cold open, or one post-acknowledgment refresh when already cached |
| Wi-Fi returns or the server restarts | Same screen; current previews replace old ones; status disappears when recovered | Open a fresh team stream, replace the follow set and refresh persisted data | Reconnect backoff, one follow PUT, fresh reads for active or interrupted queries |
| Data was already loading when Wi-Fi returned | The old response cannot replace the visible data | Cancel earlier reads and fetch current data after the follow acknowledgment | A replacement read for each interrupted query |
| Old server | No streaming preview; saved replies and task transcript still update | Use legacy follows and refetch saved rows on conversation events, including the task pane's global Coordinator | One additional PUT if the old server rejects the versioned body |
| The live transport fails or a follow stalls | Current content stays visible. Only losing a transport after a valid hello shows reconnect status. | Retry with backoff and refresh watched queries once recovered; retire an attachment if there is an ambiguous unversioned write. A follow-only replacement recovers data without announcing a disconnect. | PUT deadline 10 seconds; stream backoff 1–30 seconds |

| State and owner | Reads, writes and transitions | Failure behavior |
|---|---|---|
| Desired set and revision, browser tab | First and last effective subscribers add/remove IDs; same-turn listener handoff keeps the follow. Each effective set change advances the revision. Hello attaches an empty server set; PUT sends the full desired set, even if empty, and coalesces newer changes. The current attachment accepts only the acknowledgment matching its latest desired revision. | Superseded completions cannot advance recovery. If an ID is followed again before its removal is confirmed, replace the attachment rather than assume the live prefix is complete. Detach aborts the request and clears retry timers. |
| Installed set and revision, server attachment | After body parsing and attachment authorization, replace the set synchronously: keep retained subscriptions, unsubscribe removed IDs and subscribe new IDs with current live snapshots. Hello announces revision support. A versioned PUT echoes the installed revision; a newly attached conversation starts its preview with an ordered reset before the current snapshot. An older revision cannot replace a newer set; a plain body is accepted on legacy attachments. Closing the stream retires its ID and all follows. | Invalid body or retired attachment changes nothing. Team publications serialize once; the frame number is in the SSE `id` field and starts anew for each team attachment. Standalone and machine streams are unchanged. |
| Unknown or legacy server, browser tab | Try the versioned body first. An explicit old-server body rejection resends plain `{ conversationIds }`; legacy success without a revision confirms legacy mode too. During legacy mode, persisted message events and Coordinator claims and terminal steps refetch the transcript without updating preview stores. Team todo events also refresh the matching transcript, because some saved rows have no message frame. | A timed-out or otherwise ambiguous legacy/unknown write retires the entire attachment before another PUT, so a late write cannot change the new set. |
| Current preview, browser tab | Only the current source may deliver frames. Hello discards previous-connection previews before subscribing; current live snapshots and subsequent frames apply in stream order. A same-turn subscriber handoff does not append the same preview twice. | Legacy/unknown sources never write preview fields. Retired source callbacks cannot mutate the replacement. |
| Query cache, browser tab | Recovery and live events share the refresh described in [One SSE stream per browser tab](./single-tab-stream.md#saved-data-and-query-refresh). Recovery selects all watched keys; live events select related keys. The current recovery remains pending while any selected key is refreshing, reading, or has a deferred refresh queued. A follow acknowledgment on a superseded attachment or revision cannot settle recovery. Todo events still patch detail and loaded board/Tasks rows, including equal-version updates from related records. Build frames are hints, not authoritative patches. | Success, final read errors, or an external cancellation without a replacement settle recovery; a queued refresh that loses its observer leaves the query stale without starting a read. A failed replacement does not restore a cancelled response. The business-silence timer starts when hello establishes the stream and resets at follow acknowledgment, so a failing follow write cannot disable team-stream reconciliation; transport liveness is independent. |
