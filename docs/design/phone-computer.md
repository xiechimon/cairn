# Android phone as a Coordinator computer — plan, 2026-11-27

Owner decision (ian, 2026-11-27, verbatim): `「1. 要：旧安卓手机要不要接进 Cairn，变成一台能让 agent 操作的设备？」` — yes. Product-shape decision (ian, 2026-11-27, verbatim): `「3. A」` — make phone access a product feature: any Cairn user can choose `添加安卓手机` in settings. Build the home version first: the phone is on the same network as a Runner Mac, paired once over wireless adb, with nothing installed on the phone by the user. The away-from-home tailnet version is a later slice: plan it to the end with exit criteria here, but build only the home slice now. Prior art and measurements: [`phone-agents-2026-11-20.md`](../research/phone-agents-2026-11-20.md).

`main` already carries the first Android-over-adb implementation from commit `2b2634e42`: the phone tools and refusals, the adb driver, pairing routes, the `phone` table, the machines UI and tests. This plan completes that path instead of adding a second one. The measured gaps are: a runner without adb cannot pair and the UI hides the entry (`实测` on the production Mac mini), the stored identity is the ephemeral wireless `ip:port` endpoint although adb pairing is designed to survive network reconnection (`实测` in `phone-android.ts` versus Google's adb guide), pairing lifecycle states can strand or revive access across timeout, restart and removal (`实测` in the review of this plan), and the flow has never been proven on the real runner (`实测`).

## User scenario

A Cairn user who has never heard of adb opens settings on their Mac, sees their local Runner and an `添加安卓手机` action beside it. They press it. The dialog says wireless debugging requires Android 11 or later, tells them exactly where to tap (`开发者选项 → 无线调试 → 使用配对码配对设备`) and asks for the shown private-network `IP:端口`, the six-digit pairing code, and explicit consent that screenshots and element text will be sent to the model provider. They press `配对`. If this runner does not have a compatible adb, Cairn downloads the pinned official Android platform-tools itself as part of that action; the user is not sent to Homebrew. When pairing succeeds the phone row says `就绪` under that Mac.

The user then tells the Coordinator `用我那台旧手机打开计算器，算 128*32 然后把结果告诉我`. The Coordinator sees the phone by name, calls `phone_observe`, taps the numbered elements with `phone_act`, and replies with the result. The phone activity list shows each tool call, its short summary, state, error and originating thread; screenshots themselves remain in the conversation/tool evidence, not in a new activity viewer. If the phone locks, the tool answer says the owner must unlock it; if the phone leaves the network, the row says `无法连接`; if the owner needs to type a password or confirm a payment, the agent asks for handoff and the owner uses the phone directly.

After a router restart or a phone IP/port change, the same phone remains one row and one pairing as long as wireless debugging is still enabled and Android/adb can reconnect on that trusted network. If the phone rebooted with wireless debugging off, the row says `无法连接`; the user turns wireless debugging back on and the existing pairing is reused. Only revoked adb authorization, a factory reset/profile change or an explicit removal requires pairing again. The owner can remove the phone from the row; Coordinator access stops immediately even if adb disconnection finishes afterwards.

"Nothing installed" means the user never installs or configures an app. The existing driver may push its pinned yadb input helper into `/data/local/tmp` the first time arbitrary text is typed; the consent text discloses that helper honestly. It is not a visible Android app and is not needed for the calculator acceptance journey.

- What they must already know: how to open developer options on their own Android phone. The dialog names the Android 11+ requirement and path; no adb, Homebrew, terminal or port-forwarding knowledge is required.
- Accounts, payments, keys: none. The only download is the pinned official Google platform-tools zip; pairing accepts only private home-network IPv4 endpoints in this slice.
- Where it stores what they give: the existing `phone` row stores the immutable row id used by audit/history, the mutable logical Android id, display name, owning machine, consent actor/time, pairing error and handoff state. `computer_call` continues to carry the auditable pairing and operation calls. No new table or migration is needed.
- Where they get stuck or what they see on failure: a wrong or expired pairing code leaves one phone row with an actionable pairing error and `重试`; offline or corrupt platform-tools download does not execute anything and is reported as a phone-support preparation failure; an old Android phone without the wireless-debugging menu cannot produce the requested code, so nothing is submitted; a locked phone, an unauthorized adb connection, a secure black screen, Cairn itself in the foreground and an ambiguous phone name keep explicit tool refusals.

| Situation | What they see | What the system does | Wait and cost |
|---|---|---|---|
| Runner Mac has no compatible adb | `添加安卓手机` is visible; after submit the button stays busy while support is prepared | Downloads the pinned platform-tools zip, verifies SHA-256, extracts `adb`, then pairs | One HTTPS download of about 16 MB, only after the user asks to pair |
| Runner already has a compatible adb | Same pairing flow | Uses it; no download | Pairing time only |
| Existing adb is broken or too old to pair | Same pairing flow | Falls back to the pinned managed adb instead of executing the broken one | One download |
| First wireless pairing | Busy pairing state, then `就绪` | `adb pair`, discovers the non-pairing connect endpoint, reads model and Android id, persists one logical phone row | Normally seconds; bounded by the five-minute pairing deadline |
| Phone gets a new IP or adb port while wireless debugging stays on | Same phone row returns to `就绪` when adb reconnects | Probe maps the stable Android id to the current endpoint | Up to one 15-second probe interval after adb itself reconnects |
| Phone rebooted with wireless debugging off | `无法连接`; no automatic re-pairing is claimed | Probe reports absence; when the owner re-enables wireless debugging, the existing adb authorization is reused | Next reconnect/probe interval |
| Phone locked, unauthorized or off Wi-Fi | Three distinct states: locked, authorization needed, or unreachable | Probe reports the real state; phone tools refuse without taking a screenshot in locked/secure states | Next probe interval |
| Owner removes the phone | Row disappears immediately; active phone work is cancelled | Server revokes consent first, then asks adb to disconnect best-effort | Immediate in the product |
| Agent operates the phone | Activity rows plus the conversation/tool evidence | Existing `phone_observe` / `phone_act` single path | Same as current computer-use calls |

## Scope

1. Keep one implementation: the existing adb driver, protocol tools, server routes, `phone` table and machine UI remain the single phone path. This change deletes no security refusal and does not add a parallel wireless bridge, a user-installed phone app, an iPhone path or a second phone-tool namespace.
2. Add `apps/daemon/src/computer/phone-bootstrap.ts`, the one owner of adb discovery, compatibility checking and preparation. An existing adb is used only when `adb version` exits zero and `adb --help` contains the `pair` subcommand; otherwise it is treated as absent for this feature. If no compatible adb exists on a macOS runner, the first user-initiated pairing downloads `https://dl.google.com/android/repository/platform-tools_r37.0.3-darwin.zip`, requires zip SHA-256 `df21339b9371fef9b19264404338dc686f59a88a1dce634b963da344909001d6`, extracts with the macOS system archiver into a staging directory, verifies extracted `adb` SHA-256 `a1c4253c2f7336dd3e600689aef1c451ca0c74a614ea8495a79058fcd7299de3`, marks it executable, writes a provenance marker and atomically moves it under the runner home. A partial download, bad hash, non-regular-file cache path or failed extraction never executes. The managed adb is re-used only while both marker and binary hash match. The pin is deliberate dependency state: it is changed only by a future commit that re-verifies Google's versioned artifact and release notes, never by runtime auto-update.
3. Make pairing wait on the same bootstrap promise instead of failing with `adb not found`. Concurrent preparation shares one download. On macOS runner startup, `detectExisting` checks for a compatible system adb or already-verified managed cache without downloading anything; if found, `setAdbPath` adopts it, announces `phoneHost`, and starts probing immediately so already-paired phones come back online after a restart. If no compatible adb exists, `createPhones` does zero downloads until the user initiates pairing; when preparation succeeds it swaps in the real `AdbRun`, starts/refreshes probing and announces the new capability. A failed preparation leaves no half-installed tree and is retryable by pressing `重试` or submitting pairing again.
4. Carry cancellation and deadline through the pairing path. The dispatcher passes its shutdown signal combined with `AbortSignal.timeout(remainingMs)` to `phones.manage`; `phones.manage` respects that signal across bootstrap download fetch, `/usr/bin/ditto` extraction and `AndroidPhone.pair` adb calls. A timed-out or shut-down attempt cannot keep downloading, extracting or pairing invisibly. On the server, `receiveComputerFrames` independently checks `deadlineAt <= now` on non-terminal `phone_manage` calls (failing with 409 and marking `error` + `phone.lastError`) even before the periodic reaper runs, and rejects frames after any terminal `computer_call` state (`done`, `error`, `interrupted`, or `cancelled` with `finishedAt`).
5. Close the server pairing lifecycle. The per-machine pair lock covers the whole single-flight in-process pairing critical section and rejects concurrent submissions with 409 immediately instead of queueing a second five-minute pairing behind the first; `machinePairingInFlight` checks the DB for active `phone_manage(pair)` rows across restarts. `sweepComputerHandoffs` gains a 15-second periodic invocation (not only server startup) so any `phone_manage` or handoff left open past `deadlineAt` is marked error when its deadline passes without touching other active calls; expired `phone_manage` rows update `phone.lastError` through the same pairing-failure writer. No timed-out attempt can remain `配对中` forever.
6. Show the phone entry for an online local macOS runner (local runner coverage matches the target Mac mini deployment) whether or not `phoneHost` is already true, while keeping existing paired phone rows loaded and removable even when that local macOS runner is offline. `phoneHost` continues to mean "adb is usable" for capability consumers, but it is no longer the discoverability gate. Under each online local macOS runner in `执行机`, the phone area always offers `添加安卓手机` when no pairing is in flight. The add-machine dialog keeps a shortcut only when exactly one hostable online runner exists; with zero or several it does not guess, and the per-machine rows are the entry. Owner and paired-device owner-equivalent sessions (paired via QR/device token) can pair/manage phones; non-owner sessions never see a working write action and the server remains the enforcement point.
7. Give every paired Android phone one stable logical id. After pairing/connecting succeeds, the driver reads `settings get secure android_id` through the connected shell and returns `android:<lowercase hex>` as `deviceId` when it is valid non-empty hex; this applies to wireless and USB so the same physical phone does not split by transport. The current wireless `ip:port` or USB serial remains transport state, not identity. If Android id cannot be read, pairing fails with an explicit error rather than persisting an endpoint that will fragment later.
8. Make probing report the same stable id for every connected device. The daemon probe reads Android id for devices in `device` state, keeps an internal `stable id -> current adb serial` map, and emits only the stable id in machine capabilities. Both `ip:port` serials and mDNS auto-connected instance serials (`<service-name>._adb-tls-connect._tcp`) are matched against the current `_adb-tls-connect` mDNS services on private IPv4 addresses, and attached instances suppress duplicate `seen` rows. If the same stable id appears over USB and Wi-Fi, it is one logical phone; the probe prefers the USB serial while it remains in `device` state because that transport does not depend on LAN discovery, otherwise the wireless serial. mDNS `seen` endpoints remain ephemeral discovery rows only until pairing; once the same IP or service instance is attached, they stay suppressed. If `probeAndroidPhones` itself fails (e.g., adb daemon error), `refresh` clears `latest` and `serialByDeviceId` and marks cached drivers unreachable rather than keeping stale transports.
9. Make transport replacement explicit inside the driver. `AndroidPhone` gets `updateSerial(serial)`: a pair success or probe may update the transport serial, and any change invalidates cached UI element numbering. The next `phone_act` using pre-change numbering returns a connection-changed error telling the agent to observe again; an in-flight adb call is not retried on a different endpoint. Only probe success and pair success write the serial map; `driverFor` reads it. Wireless use additionally requires current exact-endpoint mDNS corroboration; when that corroboration disappears the cached driver is marked unreachable and refuses observe/act instead of using a stale transport, until a later probe/pair success updates it. When a home router drops multicast or isolates mDNS, the phone reports `无法连接` rather than guessing an uncorroborated endpoint; a USB cable works as local transport fallback. Removal clears the mapping and withdraws the driver.
10. Preserve history without identity guessing. `phone.id` remains the audit/thread foreign key and never changes; `phone.deviceId` is mutable logical identity written only by `managePhone` after pair success. Creating a new pairing (`POST /api/machines/:id/phones`) records `consentAt` on the temporary endpoint row when the user submits consent, while `phoneComputerTarget` refuses all observe/act until `deviceId` is `android:<hex>`; retrying an existing row (`POST /phones/:phoneId/pair`) never alters `consentAt` or `name` before identity verification succeeds. If `POST /api/machines/:id/phones` completes on an already-paired `android:<hex>` phone on the same machine, `managePhone` merges the updated name/consent into the existing `phone.id`, re-points any `computer_call` references, and deletes the temporary endpoint row inside one transaction so history and row identity are preserved without violating the `(machineId, deviceId)` uniqueness constraint. Wireless endpoint-keyed rows created by the previous implementation are not operable after upgrade: an `ip:port` can be reassigned and adb authorization cannot prove the current endpoint is the phone the owner consented to. Those rows show the re-pair-needed state; retrying that explicit row updates the same `phone.id` to `android:<hex>`, preserving activity history. A discovery row is never treated as proof that an existing row is the same phone: same-IP reuse is forbidden. Once a row has a stable `android:<hex>`, a retry returning a different stable id fails closed as an identity mismatch and changes nothing; a factory reset/profile change therefore cannot inherit the old phone's consent, name or history.
11. Make removal product-immediate and cancellation real. Removal runs in one server transaction that cancels active phone calls (`state = 'cancelled'`, `finishedAt = now`), releases the phone lease and deletes the consent row, then settles pending call waiters so the Coordinator turn receives cancellation without killing the rest of the step (`stopSignal` is not sent for phone removal; `dispatch.ts` `cancelStep(stepId)` handles actual user-initiated step stops). Because `phone_manage(forget)` is asynchronous, it is not the authorization boundary: add a machine-authenticated `phoneConsent` check API (`POST /api/machine/phone-consent`), and `AndroidPhone` synchronously asks the server whether its exact `phoneId + deviceId` consent row still exists — and, for observe/act, whether its exact computer call is still dispatched or running — before every adb command that can observe or act. A missing row, mismatched id, cancelled/finished call, unreachable server or older/incompatible endpoint fails closed, so a runner that has learned of revocation or cancellation cannot execute another screenshot or action. On local LAN (`<5ms` per check; bounded by client request timeout), each `observe` makes ~4 checks and an `act` batch makes ~3 checks per action; if consent fails mid-batch after earlier actions ran, `act` uses `guardRefusal` to report the already-executed actions followed by the refusal rather than claiming nothing ran. Distributed revocation cannot be linearized: a command can race revocation in the network-propagation window after the server commits but before that runner's next consent answer, or in the smaller local window after an affirmative answer arrives but before the adb child process starts. No distributed or local authorization-then-launch design can close either window; even making authorization itself transactional would still leave the launch-after-authorization race. The precise guarantee is therefore: the server authorizes no new call after revocation; every adb command is preceded by a fresh consent check; commands can race only inside those explicitly acknowledged, physically unavoidable windows; late frames finish as cancelled/error and never recreate consent. Only after revocation does the server dispatch `phone_manage(forget)` best-effort when the machine is connected so the daemon aborts the driver's in-flight adb calls and runs `adb disconnect`. While a pairing completes, `setConsented` preserves any active driver whose `phoneId` remains consented across the endpoint-to-`android:<hex>` transition. Cancellation of the confirm dialog changes nothing; offline removal does not wait for adb.
12. Keep pairing owner-only, consent-required and machine-scoped exactly as the existing routes enforce. Tighten the endpoint schema for this home slice to private IPv4 ranges (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`) so the UI and server reject public-IP and tailnet input. This private range check is only a necessary transport filter, not proof of phone identity or network locality. Identity comes from adb pairing/authorization plus the stable Android id read over that authorized connection. Locality comes from mDNS: after pairing, connect only to a discovered `_adb-tls-connect` service on the same private IP as the pair endpoint; the insecure `:5555` fallback is deleted. Later probe/act accept a wireless serial only when the current probe also sees its exact `ip:port` in `_adb-tls-connect` mDNS, so a VPN/private-range route or adb cache alone is never enough. This is the product's operational definition of "same network"; the trusted home LAN itself is outside the threat model, and adb TLS plus stable Android id protects the phone session rather than the IP route. The design does not claim kernel-level proof of which interface a packet uses. USB serials are exempt because USB is physical rather than network access. A tailnet, public, non-mDNS-corroborated or otherwise nonconforming transport is never emitted or used. The command gate keeps phone control inside `phone_observe` / `phone_act` / `phone_manage`. Any bootstrap error shown to users is a short preparation failure; detailed adb stderr stays in machine logs.
13. Correct phone view state semantics. `unauthorized` is not `pairing` unless a pairing `computer_call` is actually in flight; it shows an authorization/re-pair-needed state with retry. `offline` is unreachable, not pairing. Pairing state reads only the server row/call state. Cancellation before submit sends no request; while a submit is pending the cancel control is disabled so the user is never told a pairing was cancelled when it is still running. Closing by Escape is disabled during the same pending interval.
14. Register the newly visible user surface in `scripts/product-surface-registry.json` for the phone pairing entry, `machine.capabilities.phoneHost`, `machine.capabilities.phones` and runner phone-support behavior, and regenerate/update the feature map if the registry requires it. Add fixture states for no adb, preparing support, paired-ready, pairing failure, unauthorized, offline and endpoint migration so the machines page can be reviewed without a phone.
15. Prove the slice in order: focused unit tests red on the parent; the machines-page e2e fixture path; a verify-cairn isolated stack walk of the user-visible states; then the real Mac mini runner. Real-device proof first attempts the owner's Pixel/old Android phone; if it cannot be made available, the owner-approved fallback is an Android emulator on the mini and the report says exactly which was used. The production proof records (a) the pairing dialog and successful pair and (b) a Coordinator/task agent observing and operating the phone, published on the owner's 8977 evidence page. The recording journey uses calculator taps, not arbitrary text input, so it does not depend on pushing yadb.

State, readers and writers:

- `phone.id`: immutable audit identity; written at row creation by the pair route; read by activity, handoff, leases and consent stamps. It never changes during endpoint or Android-id migration.
- `phone.deviceId`: logical Android identity; written only by `managePhone` after a successful daemon pair (temporary endpoint first, stable id when returned); read by server phone targeting, daemon consent stamps and web row merge. No UI code writes it directly.
- `phone.consentAt/consentedBy`: written on initial pair submission by the owner-only create route (inoperable until `deviceId` becomes `android:<hex>`); retry preserves existing consent until identity verification succeeds. Removal deletes the row before best-effort adb disconnect.
- `phone.lastError`: written by the server pairing completer/reaper from a bounded error string; read by the machines row. Transport stderr is not stored wholesale.
- `phone.handoff*`, busy state, leases and `computer_call`: their existing writers and readers remain the only path, except the lifecycle fixes named above; `computer_call.state` is additionally read by the machine-authenticated call-scoped consent check.
- pairing in flight: the database `computer_call` rows are the source of truth (`machinePairingInFlight`). The route lock rejects concurrent submissions immediately with 409; the periodic 15-second reaper writes terminal error state after deadline.
- daemon bootstrap cache: written only by `phone-bootstrap`; checked without network by `detectExisting` on startup and prepared on first pairing/phone operation. It is cache, not user data, and may be deleted safely.
- daemon `stable id -> current serial` map: memory only, written by probe/pair success, cleared on probe failure, read by `driverFor` and phone screens, cleared for a removed phone; loss on restart is repaired by the next probe. A wireless serial whose exact endpoint disappears from mDNS marks its cached driver unreachable rather than remaining usable.
- daemon `driverPhoneIds` map: memory only (`deviceId -> phoneId`), preventing stale presence replies right after pairing migration from killing the newly migrated driver while still allowing true removals to tear down the driver.
- driver transport generation: memory only, written by `updateSerial`; read by `phone_act` before using cached element numbers. A change invalidates the observation.
- machine capabilities `phoneHost` and `phones`: written by the daemon machine loop; read by the server link state and web. `phoneHost` is readiness, not permission to show the pairing entry.
- web pairing dialog fields and consent checkbox: local React state only; a successful submit closes the dialog and the server row is the source of truth.

Failure paths:

- Download offline, timeout, hash mismatch, archive extraction failure, disk/permission failure or cache tampering: no adb process is started; pairing fails with the preparation error and can be retried.
- Existing adb exits nonzero, lacks `pair`, or is otherwise incompatible: it is not used; the managed pinned adb is prepared instead.
- adb pair rejects the code, the code expires during first download, or discovery/connect fails after pair: pairing fails with adb's short reason; the same row keeps `重试` and does not duplicate. The user can reopen wireless debugging, generate a fresh code and retry with the new endpoint.
- Phone disappears after connecting but before identity read, or Android id is missing/unparsable: pairing fails explicitly; no stable consent is falsely reported ready.
- Runner disconnects or daemon shuts down mid-pairing: cancellation reaches download/adb; the server deadline/reaper marks the attempt failed and late success frames are rejected.
- Server restarts before the pairing deadline: the periodic reaper closes the attempt at deadline instead of leaving `配对中` forever.
- Phone locked, unauthorized, offline, secure screen or Cairn foreground: distinct UI states and existing tool refusals; no screenshot is taken in locked/secure states.
- Wireless debugging is off after phone reboot: the row is unreachable; re-enabling it reuses pairing. Revoked authorization requires pairing again.
- Removal while pairing or operating: consent deletion and call cancellation are atomic against new server dispatch; active phone calls settle without killing the rest of the step, `phone_manage(forget)` aborts the driver's remaining batch actions, late frames are rejected with 409 and never recreate consent, and an already executing physical tap is reported honestly rather than claimed undone.
- Stable-id retry returns a different Android id: pairing fails closed as an identity mismatch; the existing row, consent, name and history stay unchanged.

## Away-from-home slice — end state and exit criteria, not built here

Target end state: the same already-paired phone remains the same Cairn row when it leaves home Wi-Fi; the Runner reaches it over the tailnet; the same consent row, phone tools, activity log, handoff and removal UI are used; no second device object and no second agent API appears. The user does not run shell commands.

Build gates for that later slice, in order:

1. Real-device measurement: with wireless debugging already paired at home and Tailscale enabled on the Pixel, record whether adb listens on the tailnet interface, which port it uses, whether `adb connect <tailscale-ip>:<port>` succeeds from the Mac mini, and whether the connection survives Wi-Fi/cellular transitions. Evidence must be raw adb output plus a screen recording. If adb does not listen there, the no-user-install tailnet design is impossible and the slice stops at that documented negative result.
2. Discovery measurement: if the connection works, determine how the runner learns the ephemeral port without LAN mDNS. A manual port entry is not the target end state. If no passive mechanism exists, the slice must either use Tailscale service discovery that actually carries the port or admit that an on-phone companion/Tailscale app is required; that is a new owner decision because it changes the install constraint.
3. Security design: tailnet endpoints use `100.64/10`, outside this slice's private-LAN allowlist. That slice's plan must deliberately widen the schema, name the exact mesh boundary, update consent copy and prove public-IP adb remains rejected before implementation.
4. Implementation exit criteria if measurements pass: one stable phone row across home/away transitions; agent operation proven over tailnet with screen recording; lock/offline/handback states proven; a roaming transition does not duplicate the phone or lose activity; removing the phone stops access on both networks.
