## Tasks panel

- **TaskRow** (`thread/task-row.tsx`): one quiet line measured from the reference recording: one lead for every row (the list reads as one family): a 16px mark centred in a 28px box with no fill behind it. A row the owner can mark done shows the checkbox (its ring takes the accent when the task waits on the owner); a row that cannot be marked done shows one `ink-3` glyph of the same size in the same spot, with a tooltip that says why (the Coordinator's spiral for a question, the done or closed status glyph for a task; a failed task draws an outlined ring with a cross, stroke only, never a filled disc). The reference draws a grey tile behind that glyph; cairn leaves it out on the owner's instruction. Then the 14px regular title and, on resolved rows, the short date on the right; there is no running dot, the `进行中` section header says it; the `…` menu on hover or focus (always on touch). Rows are 46px with a 2px gap and `--radius-tile` corners.
- A row that stands for work shows state and age (glyph, title, reason, time), grouped by what needs the user, as in the references; in the sidebar the age follows L6. One line per row; the section header carries the state; the full status sentence `word · what → where · age` is the row's accessible description and its 600ms tooltip. Only rows that wait on the owner add one 12px `ink-3` meta line with `what`; resolved rows show their date; a compact age stamp (`7m`, `6h`, `2d`) sits before the `…` menu. Every row in an active section carries the age stamp.
- A task's PRs sit on one line under it on a tree elbow: each open PR as `#n — state`, merged PRs folded into `#n` or `N 个已合并`, with a hover card opening to the panel's left (slow on first hover, instant while one is open); no separate PR list. PR state colours come from `--pr-open`, `--pr-pending`, `--pr-failed` and `--pr-merged`, the one list-colour exception (L1, V5).
- Ticking a row selects it; a dark bar at the panel's foot reads `已选 N 个 · 完成 · ×`; marking done never opens the accept dialog. A change the user makes shows in the same frame (C24): marking a task that is not running done, renaming and moving update every list before the server answers, and a failure puts the row back and says so; a running task waits for the stop to be confirmed, since the server may only be stopping it.
- **Tabs** (reference recording 2:08-3:04): `进行中`, `接下来`, `定时`, `已完成` as plain labels with no counts, every label in `ink` (an idle tab is not dimmed; the selected one takes the `--sidebar-active` fill); each section header inside the tab carries its count. The `定时` tab is where schedules are managed: clicking a row opens a 320px popover editor beside it (next and last run, the trigger fields, `打开任务`, `取消`, `保存`), never a dialog; the row's `…` menu holds `立即运行`, `暂停定时`, `编辑`, divider, `删除…`. A `新建定时` row under the list opens the same popover with a task picker; the Coordinator can also create schedules from chat. One-time schedules that no longer run fold into a collapsed `已结束` group whose rows show the stop reason in Chinese. `/app?pane=tasks&tab=scheduled` opens the panel on this tab; picking another tab or closing the panel drops `tab` from the URL. There is no separate schedules page. An empty `定时` tab shows `还没有定时任务` and, 12px under it, one `secondary` pill `新建定时` (28px, the pill of the empty Tasks panel's `添加任务`).
- **Add a task** (`board/tasks-add-input.tsx`, reference recording 1:58 to 2:48, frame 2:48): the `+` in the panel head toggles one inline field 8px under the tabs, on any tab, with the panel's 8px side inset: 42px tall, `--radius-tile` corners, `--hover-1` fill, the focus ring on the whole field while it is being typed in. At the left a 24px `--sidebar-active` tile (6px corners) holds the 16px task glyph (`ListChecks`), centred in the 28px lead column of the task rows; the text starts on the rows' title column with the placeholder `添加任务…`; at the right a 28px submit button holds a 20px up arrow, `--text-tertiary` while the field is empty and `foreground` once there is text. Enter or the arrow saves the task without starting it (`createTodo`, `POST /api/projects/:id/todos`, phase `todo`), switches the panel to `接下来` where the new row heads the `待开始` list, and leaves the field open, empty and focused for the next one. An empty or blank field submits nothing. Escape, or `+` again, closes the field; a refused save keeps the text and shows `任务没有添加上，请重试。`. The empty panel's `添加任务` button opens the same field and the empty block hides while it is open. A task needs a project: in a project's conversation it is that project, in the all-projects conversation it is the only unarchived project; with several projects and none chosen, and in fixture data with no server, the text goes to the Coordinator instead (sent, or placed in the composer) and the field closes.
- **ScheduledTaskRow** (`design/prototypes/scheduled-task-row.tsx`, gallery only): still clock mark, name, trigger and next run, Active, Paused or Auto-disabled tag.

## Task thread panel

(`board/side-chat.tsx`, reference recording 2:12, 3:08 and 12:12-12:56; 1 CSS px = 1.47 frame px.) The task thread panel is the conversation, not a dashboard (C14).

- **Head**: a 68px head on one row, every control centred on the title block: the 36px back chevron, a 24px tile (6px corners, `background` fill, `--e1-lift` ring and soft drop, no border) holding the 16px task glyph (`ListChecks`, the glyph of the `任务` button and tab), its left edge 26px from the chevron's centre, then 12px to the title on one line (the title alone in `text-ui` regular `foreground`, the size and weight of the body text, truncated; the full title is its 600ms tooltip, and the task number shows nowhere in the panel) over the status line (`text-meta`: the state word in the task tone of the conversation chips, `taskStatusInk`: working blue, waiting green, failed red, quiet grey; then `· n 条更新`, the purpose, or machine and age in `ink-3`), then the `…` menu and close. The head status and the Tasks panel section come from one selector: a task waiting for a Runner reads `运行中` with `准备开工` as its reason, the same words a phase chip or tray row uses. The head carries no control for code changes, since most tasks have none. The `…` menu holds `完成`, `重命名`, `计划` (a dialog with `决定与更新` first, as an unboxed `text-ui` medium heading with its `n:nn 更新` time and ink bullets, then the plan document), `移到项目`, `路由覆盖`, `复制链接`, `归档`, `丢弃修改` and `删除`; it has no usage item.
- **Body**: the conversation in the main conversation's family, on a 16px gutter: the task purpose as plain text only when it differs from the title and the request; the originating request once with one right-aligned `在主对话中查看` link under it (`text-ui`, `foreground`, nothing on the left), and only when no `来源 Coordinator 编排会话` line already leads back; then the transcript with owner `--bubble-fill` bubbles on the right, unframed agent prose on the panel surface (`agent-measure`, no `--reply-bubble-fill`; consecutive agent rows 4px apart, 20px between turns), centred caption time dividers (`13:26 · 运行在 xmonsMac 上`) and collapsed `WorkTrace` groups. No divider before the first transcript row. Text the owner reads (purpose, bullets, prose, plan title and preview, quotes, review evidence, failure body) is `foreground`; only times, counts and captions take `ink-2` or `ink-3`. Nothing sits between the head and the conversation except the PR cards and the source-issue line when a task has them — no stage/progress stepper (`thread-facts` / `thread-progress`) on any task kind, research/info included, no extra bordered dashboard card, footer sentence or floating chip between head and composer. A finished task adds no `已完成` line because the head's status says it; when a changes card closes the turn, the trace summary names the work, not the file list.
- **WorkTrace** (Claude Code): a run of work folds into one `WorkTrace`: every prose reply between its tool calls joins it as a step in time order, and only the prose after the last call stays outside as the reply, so a finished turn reads as one summary line and one answer. The summary line carries no leading status glyph and no hover fill (its ink darkens instead), its text starts on the prose edge and failure is its text tag; a step row with nothing more to show (no output, no diff, no command beyond its own label) is a plain row with no chevron; a finished task (`done`, `review`) drops a checklist the agent left unfinished, while a failed, stopped or waiting one keeps it. `WorkTrace` stays collapsed to one summary line while running (typing dots, the current call's verb and target, never thinking prose, and a `>= 5s` elapsed timer followed by the step's output tokens when the engine reports them; the running block is the only live row, so no separate `live-row` sits under it, while prose written after a call, streaming or saved, joins the block until the step ends, so no text appears under the block and then vanishes into it) and after settling (past-tense summary, no timer), opening only when the user opens it, failed or not (a step row inside it likewise opens only on click). A row that appears after the first render (the todo card, a new block, the reply) enters with `row-enter` (220ms fade and 4px rise) and the running line's text swaps with a 160ms fade; step rows carry no duration; a failure the agent recovered from is not counted. A todo item's change of state fades over 200ms in place, an item added while the panel is open fades in, and the item just finished draws its check and sweeps its strike-through (`docs/design/surfaces/motion.md`, Growth). While background tasks run, a `后台任务` group in a trace card sits above the todo, one row each (kind, description, tool uses, elapsed or settled word, a stop square), a row opening to its prompt and its sub-agent calls as a `WorkTrace`; sub-agent calls never join the main trace, the spawning call reads `后台 <description>`, and the todo item marked `doing` carries `N 个后台任务进行中`. `agent-todo` sits at the tail below settled history and prose and above the single unframed live status row (`live-row`), which stays under a streaming reply and shows the step's output tokens after its timer; while a todo is open it sits right above the running block, at the head of the turn, so the running line keeps its place at the bottom, remaining visible across step completion while open items remain.
- **Live row**: while the task runs the transcript ends in a single unframed live status row (`TaskLiveRow`: three bare monochrome `typing-dot` marks plus shimmering status label and `>= 5s` elapsed timer); a blocked queue row (`queue-blocked`, `TaskBlockedRow`) renders as unframed status text without a `TypingDots` pill bubble.
- **Changes**: a task's code changes show as one compact result card where the work ends (after the last row): a 40px button inside a `TraceCard` (12px corners, inset `--border` ring) with the diff glyph, `改动 n 个文件` and `+n −n` (accessible description `查看变更`, no tooltip: the label is on the card); it opens the changes view in place of the transcript, and the back chevron (`返回对话`) or Escape returns to the conversation (one file shows its diff and a full-file toggle; several list their files with `全部展开` on the card). A failed load keeps the card with `变更加载失败`, so the view's retry stays reachable. There is no separate changes view or plan/changes switch.
- **Composer** (`detail/composer.tsx`): the main conversation's composer, built from its parts (`chief/composer-surface.tsx` class constants): the 46px field with the placeholder (`回复这个任务`) and the return glyph, then a tool row 6px under it with `+` at the left (attachments, review when offered) and the context ring at the right; at 640px and below `+` and the round send button sit inside the field, as in the main composer. While the task runs the stop square shows; queued messages and attachment chips sit above the line. Neither the task composer nor the transcript shows a turn's elapsed time, running or finished; the Coordinator home shows it on hovering the status mark. Task transcript messages carry the same hover toolbar as the Coordinator conversation (`MessageToolbar`, below the bubble, `below-start` on agent rows and `below-end` on owner rows, taking no layout space when hidden). The ring (`board/thread-usage-ring.tsx`) is the main composer's context ring and means the same thing (every thread, the Coordinator included, is the same kind of session): its label and arc are the share of the context window in use (`31%`), read from the task's optional `context` (`{ tokens, contextWindow }`, the shape of the Coordinator's `context`), with `上下文 31%` as its accessible name. When the task carries no context reading the ring is the bare track with no label and no arc, never a token total or cache share that could be read as context. Token total, cache hit, cost, models and machines live in the popover the ring opens (`用量`, a `上下文` row first when known: `31% · 62k / 200k`, with `重试` on a failed load); its tooltip is the short reading (`上下文 31% · $0.47 · Token 数：211.2k`, context first, then cost and tokens when known). The ring is absent when the thread has neither a context reading nor runs with something to show, and at 640px and below the same block sits in the `+` menu. There is no usage disclosure, menu item or dialog.
- **Thread action note** (`board/thread-actions.tsx`, above the task composer): a next step shows as a chip only where the owner must decide something the `…` menu does not offer as clearly: `批准计划` with `查看计划`, `开始` and `重试`. The row is the Coordinator's suggested-reply row (`REPLY_CHIP_CLS`, 28px pills 12px apart), its left edge on the composer's left edge and 24px above the composer, as in the main conversation; the reason sentence lives in the chip's tooltip and accessible description, not on the page. A task waiting for review shows no chip: finishing is `完成` in the `…` menu, as in the reference. An archived task replaces the composer with the bordered `这个任务已归档。取消归档后才能发消息。` card and its `取消归档` button, as in the reference.
- **Docking**: opened from the Tasks panel on a window wider than 1100px, the task does not replace the list: it opens between the conversation and the list, which stays in place with the open row on the `--sidebar-active` fill and `aria-current` (`SidePanel docked`, from the prototype direction "push"). The head then has no back or close control (the back chevron returns only for a sub-view such as the changes view), only `收起` (`ChevronsRight`) after the `…` menu, and the row adds no icon of its own. Clicking the open row again, `收起` or Escape collapses it; another row swaps it in place; the arrow keys on a focused row move to the next task. It takes 55% of the room left of the list, clamped to 440 to 600px (`dockedThreadLayout`, no resize handle), and floats over the conversation with the floating shadow when docking would leave the conversation under 400px, at the list's left edge. At 1100px and below the task replaces the list as before, with the back chevron returning to it. Below 640px the open task covers the phone chrome and tab bar (as the reference's phone task view) and only the composer remains at the bottom.

## Task header and status (task detail page)

- The task detail header is one 44px line (Amp): back, project tile + project name + `#seq` in `ink-3`, the title in sans 15px/600, the status as a ghost pill (bg only on hover, full radius, glyph in its tone, label in `ink`), then on the right the agent, ⋯ and the primary action when there is one.
- The right pane (`RightPane`, `DocPane`) is flat: a `--background` surface with one `--border` hairline on its left, no ring and no segmented control (Claude Code's right pane). The 40px header holds a plain dropdown title (`PaneTitle`: Plan or Changes) with the plan version beside it in `--text-tertiary` ("v2 · 10 min ago", still the version menu trigger), and on the right 26px icon buttons (`PaneViewButtons`, radius 7, hover `--menu-hover`) for plan and changes. Under the plan sit Branch, Usage and History as collapsible sections (`PaneSections`): 32px header in `--text-tertiary` meta 500 with a small triangle and an optional right-aligned summary, hairlines inset 14px between them; Usage starts open, Branch and History closed (Branch fetches its sync state only once opened); state is kept per section. Usage is one 6px stacked bar (1px gaps, neutral `content-secondary` fill) over a legend of label and tabular value, then cache hit rate, model and the cost group. Changes file rows read chevron, basename, directory in `--text-tertiary`, then +/- on the right; the change summary and expand-all sit on a thin row under the header.

## Engine run

(`board/engine-run-view.tsx`, view model `board/engine-run.ts`; `docs/design/durable-threads-and-engines.md`, The engine view.) A run the thread dispatched to an engine (Claude Code, Codex) has no card of its own; its events are the thread's own conversation, appended after the transcript (`engineTranscript`). It is a prototype on fixture data: the run is an optional `engineRun` on what the thread panel renders, no live response carries it, and a thread without it shows nothing extra. The plan is the agent checklist, engine text is a reply bubble, and reads, commands, edits and event types the adapter does not know are rows of one trace group (an unknown type keeps its raw payload as the row's output, so nothing is dropped). A failed step opens with its output; a step group longer than six rows shows its last five under one `之前的 n 步` row that unfolds the rest (`work-trace.tsx`, for every thread). An answered question becomes its text over a quiet `已允许这一次` or `已拒绝` note. Where the work ends, before the changes card: a pending question as a reply bubble over two suggested-reply chips (`允许这一次`, `拒绝`), and nothing else: the conversation carries no meta line or link. `原始输出` and, while the engine works, `接管` (`交还` while the owner holds it) are items of the head's `…` menu; the engine, elapsed time and cost live in the composer's usage popover (`引擎`, `时长`, `花费`), the same rows a live thread fills from its steps; the model choice and its reason are not shown. `原始输出` replaces the conversation with the engine's plain text log (mono `text-code`, read-only, kept at its end); the back chevron or Escape returns. `接管` opens a small dialog (`DialogShell` S) that says what takeover will do once the terminal exists; there is no terminal yet and none is faked: confirming only marks the run as held by the owner (`你已接管`) and hides the chips. A thread with an engine run ends 16px under its last row (`--chat-end-space`). In fixture mode only, a strip under the conversation (`下一步`, `自动播放`, `重来`, `事件 n / total`; `fixtures/engine-run-player.tsx`) reveals the scripted events one at a time and moves the thread head's state with the run. Scenarios: `/app?scenario=home-c-engine&thread=home-c-engine-<state>` with `running`, `waiting`, `finished`, `failed`, `unknown` or `long`.
