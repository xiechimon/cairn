## Problem

In the packaged Mac app the server and the Runner run as the logged-in user, and so does every agent session. Measured on 2026-11-17 (0.1.57–0.1.95): a session read `home/token` (owner token), `runner/machine.json` (machine token) and `home/server/server.db`, called the server API as the owner, called `/api/machine/token/<stepId>`, and wrote to `server.db`. The command gate blocks `ask` commands, but a session wrote the command into a script and ran the script; the gate matches command text, not what a process may touch, so it cannot be the boundary.

Two facts from the research change the scope:

1. **No harness adapter launches through `confine.ts` yet, on Linux either.** Only the startup preflight does. This design therefore needs a platform-neutral launch seam in the adapters; the Linux adapter migration is the same work.
2. **A Seatbelt profile enforces the needed denials for the whole process tree**, including a script the session writes and runs (实测 in the research note). A nested profile cannot be applied, so the harnesses' own sandboxes must be off and Cairn's profile is the only one.

## Threat model

The session is an LLM-driven process with shell and file tools, running as the user, prompt-injectable, and not trusted with Cairn's own credentials. In scope: reading or writing Cairn's secrets and state, impersonating the Runner or owner, reading the user's other credentials, writing outside its own worktree. Out of scope, stated as trust exceptions (same as Linux): readable non-denied host files, full outbound internet, shared devices, shared caches, and processes started outside the sandbox by the user.

## Paths a session must not read or write

Paths use the packaged layout; `userData` is `~/Library/Application Support/@cairn/desktop`. The policy takes them from the running app's actual configuration (`CAIRN_HOME` values, `config.workspacesDir`), not hard-coded strings.

Network: deny outbound connections to the server's port. The profile denies `localhost` and `*` on that port regardless of where the server lives — on this macOS the `remote`/`ip` filter grammar accepts only `localhost` and `*` as hosts (measured: `remote tcp "name:port"`, `remote ip "addr:port"` and bracketed IPv6 all fail profile compilation with `host must be * or localhost in network address`), so a host-scoped deny is not expressible and `*:<port>` is the strongest rule available. The same loopback detection used by server config (`isLoopbackHost` in `@cairn/shared/loopback`) covers `localhost`, `localhost.`, `*.localhost`, all of 127/8 after URL normalization, `::1`/`[::1]`, and IPv4-mapped `::ffff:127.0.0.0/8` in both dotted and compressed-hex forms. Deployment consequence: when `CAIRN_SERVER` points at a remote host on 443 or 80, the `*:<port>` deny cuts the session's outbound web on that port entirely — the Runner already holds the machine token and talks to the server for the session via `machine-client.ts`; sessions get no server credentials and have no reason to reach it. Other ports stay open so a session can run and test its own dev servers. This is defence in depth: with the token files unreadable, an unauthenticated call reaches no owner route.

Apple Events and LaunchServices are the escape that lets a session start an unsandboxed app. `(deny appleevent-send)` does not stop them (measured 2026-11-17, macOS 27.2). Denying the Mach services `com.apple.coreservices*` and `com.apple.lsd*` does: `open -a TextEdit` fails with "Unable to find application" and `osascript` to Finder never returns (killed by the probe's timeout). `claude`, Node, git, curl, gh, python3 and pnpm still run under that deny (measured). The profile carries that one `mach-lookup` rule; the probe test asserts both calls fail.

Outside-process isolation: `(deny signal)` and `(deny process-info*)` with `(target same-sandbox)` re-allows keep a session from signalling or inspecting the Runner, the server or the owner's other processes while its own children stay reachable. One channel remains open by measurement, not by intent: `KERN_PROCARGS2` lets a same-UID process read another process's environment block, and no name-based Seatbelt rule (`sysctl-read`, `process-info*`) fires for the numeric-MIB call. The rule that closes it at the source: **task-reachable envs carry only that task's own credentials; daemon and server envs carry no credentials at all** — the desktop scrubs `*_TOKEN`/`*_SECRET`/`*_PASSWORD`/`*_KEY`/`*_CREDENTIAL*`/`CAIRN_OTEL_*`/`OTEL_*`/`CAIRN_ALERT_SMTP_URL` (its userinfo can carry a relay password) from the server and Runner spawn envs and delivers OTel config as the `CAIRN_OTEL_ENV_FILE` flag pointing at the denied `otel.env`. Non-credential flags that match the shape are exempted by name (`CAIRN_REQUIRE_TOKEN` today: it is a boolean, not a secret); env-delivered real credentials like `CAIRN_API_KEY`, `CAIRN_GITHUB_OAUTH_CLIENT_*` and `E2B_API_KEY` are intentionally dropped on the desktop path — they belong in files the scrub cannot leak, so env-configured GitHub OAuth sign-in and `CAIRN_ORB_RUNTIME=e2b` do not apply to the desktop app (both remain env-config for standalone deployments, which never pass through the desktop spawn env). The owner's own shell processes (exported `GH_TOKEN` in a terminal) stay env-readable — a named residual no SBPL rule can close. One in-process residual remains by design: the confined pi-host exports its own spans, so the OTLP bearer reaches its `initialize` frame and lives in the sandboxed process — the same process that legitimately holds the step's GitHub credential.

One deliberate carve-out remains: `~/.config/git` stays readable (minus `credentials`, which is re-denied after the allow) because the harnesses' git invocations resolve config there. Antigravity without an API key originally needed the login keychain for its OAuth path and got `~/Library/Keychains` read-only; that widening is removed — host-mode Antigravity sessions now set `AGY_ACP_FORCE_FILE_STORAGE=1` + `AGY_CLI_FORCE_FILE_TOKEN_STORAGE=1`, so the runtime reads the same file tokens already linked into its isolated `HOME`, and credential stores stay unreadable for every runtime. `.agents/setup` and `.agents/resume` workspace hooks run through the same confiner as a `hook` harness (workspace, temp and caches only — no harness state); setup failure stays fatal, resume failure stays logged-and-continue.

SSH agent: session, `pi-host` and hook environments drop `SSH_AUTH_SOCK`/`SSH_AGENT_PID` (the agent socket would let a session sign as the owner; git auth for sessions goes through the step credential file, not the agent). The 1Password agent socket `~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock` is also denied by literal, since it sits outside every denied root and the temp-socket pattern.

Escape hatches: the profile denies `mach-bootstrap` — the inherited bootstrap port answers `launchctl print`, but job submission is gated server-side by that check, so `launchctl bootstrap` fails even from a copied binary (measured: `Bootstrap failed: 5: Input/output error`, no job lands). One residual the deny cannot close: the bootstrap port is inherited, not looked up by name, so `launchctl print`/`kickstart`/`kill`/`blame` against *existing* user jobs still answer — a copied `launchctl` can trigger or stop an owner job but cannot inject code into one (job arguments are fixed at submission, and submission is denied). `process-exec` literal denies on top for `launchctl`, `osascript`, `osacompile`, `open`, `security`, `sudo`, `su`, `crontab`, `shortcuts`, `automator`, `at`, `batch`, `systemsetup` and `spctl` (bypassable by copying the binary, which is why the mach-layer deny is the operative one — `/usr/bin/log` needs no entry: `log show` self-refuses under any sandbox profile). Keychain *services* are denied as Mach lookups (`com.apple.securityd`, `com.apple.SecurityServer`, `com.apple.secd`, `com.apple.trustd`) — `security find-generic-password` cannot reach items the file deny already hides; TLS certificate validation still works without them (measured: curl, git and node https all succeed under the deny — the earlier worry that SecurityServer carries TLS validation does not hold on this macOS). Anything that legitimately needs the keychain APIs breaks the same way — `codesign` signing, `git-credential-osxkeychain`, `ssh-add --apple-*`, SecItem/SecTrustEvaluate users — an accepted trade-off inside confined steps (signing belongs outside confinement). Host shells get the same denies; a host command that must talk to launchd or the keychain belongs outside confinement.

Host-shell write surface: host commands are agent-authored and run with `(allow default)`, so the profile also write-denies the deferred-persistence/exec-config surface — `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, `~/Library/{Input Methods,QuickLook,Audio/Plug-Ins,ScriptingAdditions,Python,Application Support/iTerm2/DynamicProfiles}`, `~/.vscode/extensions`, `~/.config/{git,fish,nvim,zsh,tmux,kitty,wezterm,alacritty,ghostty,direnv,autostart,systemd/user,environment.d,pip,go,zellij}`, `~/.emacs.d`, the Linux-side exec vectors `~/{bin,.local/bin,.local/share/applications,.local/share/nvim,.ipython,.jupyter,.vim,.bundle,.pip}`, and `~/.{gitconfig,gitmodules,lldbinit,gdbinit,vimrc,gvimrc,nvimrc,emacs,tmux.conf,screenrc,hgrc,curlrc,wgetrc,zlogin,zlogout,bash_login,bash_logout,bash_aliases,yarnrc,yarnrc.yml,xprofile,xinitrc,xsession,xsessionrc,pam_environment,pythonrc,condarc}` and `.config/mimeapps.list` (reads stay open; writing these files would run code unsandboxed at the owner's next login, git invocation, editor launch, shell start or desktop session). Git metadata gets its own regex deny, case-folded per character (libsandbox regexes are case-sensitive but APFS usually is not): writes to `<repo>/{.git,*.git}{,/modules|worktrees/<m>}/{config*,commondir,gitdir,info/attributes}`, every named githook file, and everything inside `.git/hooks/` subdirectories are denied — `git init`/`clone` only writes `*.sample`, which the name anchor excludes, while `core.hooksPath`/`core.sshCommand`/`core.pager`/`gitdir` redirects and hook-multiplexer dirs are all closed. A `file-write-unlink` rule on the `.git` leaf and on every `hooks/` directory stops the rename-out-and-symlink-in swap (`mv .git/hooks x; ln -s evil .git/hooks`) without touching `file-write-create`, so `git init`/`clone`/`worktree add` still work (measured). The names that stay writable (`objects`, `index`, `HEAD`, `refs`, `packed-refs`, `FETCH_HEAD`, `rebase-merge`, `sequencer`, `.git/info/exclude`, `.git/objects/info/alternates`, non-hook files directly inside `hooks/`) are what ordinary `git add`/`fetch`/`rebase` need; none of them executes on the host. The `write_file` file verb enforces the same surface in-process (the Seatbelt profile only wraps spawned commands; file verbs run inside the daemon): it refuses any target with a `.git` or `*.git` segment in either the requested path or its resolved form — so a symlinked `.git` ancestor cannot launder the segment away — plus every write-deny entry, re-resolves the destination directory after `mkdir` to catch a symlink swap racing the write, and renames into the resolved directory. Deny entries emit lexical + resolved variants so a dotfiles-symlinked `~/.config` or `~/.gitconfig` stays covered through both names; deny lists are chunked across multiple `(deny …)` lines because libsandbox rejects a rule once it grows past roughly 6-8 KB (allow lists are chunked the same way, and a single filter larger than the limit passes through whole rather than emitting a bare `(deny ACTION)`). The Linux bwrap host-shell ro-binds existing entries and masks missing ones so they cannot be planted: denied dirs get `--tmpfs`, write-deny dirs a read-only tmpfs, denied/write-deny files `/dev/null`, and a denied-file path that exists as a *directory* gets `--tmpfs`. Every existing-path mount is emitted at its canonical (resolved) destination, not the lexical list entry — a lexical name through a symlinked parent (`/var/run/docker.sock` → `/run/docker.sock`) makes bwrap die creating the mountpoint (measured on CI: `Can't create file …: No such file or directory`), while the resolved mount covers both spellings in-sandbox. A missing path outside the home (`/var/run/docker.sock`, `/run/podman/podman.sock`, `/run/user/<uid>/…`) is skipped outright — bwrap creates mountpoints on the bound host root and must never squat system names (measured: on a runner where `accessSync` calls `/var/run` writable, bwrap still dies `Can't create file …: No such file or directory`), and an unprivileged agent cannot plant there anyway; only caller-supplied `deniedRoots`/`agentDesktop` and names inside the home may be created, still gated by the nearest owner-writable ancestor. Names whose bare creation would break the owner's own startup chain are *materialized* host-side with semantics-preserving content, then masked like any existing path: `~/.bash_profile` chains to `.bash_login`/`.profile`, `.bash_login` to `.profile`, `.xinitrc`/`.xsession` exec the system X defaults, `.emacs` loads `~/.emacs.d/init.el`, `.claude.json` becomes `{}`, and `~/.gnupg` is created `0700` so gpg's homedir check still passes — a mountpoint cannot be unlinked from inside the sandbox, so the name stays pinned and unplantable while the host artifact preserves behavior. A *dangling* symlink at a denied name is unlinked first, then masked as missing (bwrap cannot mount over a dangling link; a broken link at a sensitive name is an acceptable casualty). Masking otherwise materializes real empty files/dirs in the owner home (`~/.ssh`, `~/.git-credentials`…), a documented side effect — the alternative is the agent planting them. `crontab`/`at`/`atq`/`batch` and the privilege-escalation set (`sudo`/`su`/`pkexec`/`doas`/`newgrp`/`sg`/`gpasswd`) are `/dev/null`-masked in their `/usr/bin` + `/bin` spellings since bwrap has no per-process exec filter. Linux `execute()` still lacks the git-metadata denies — Seatbelt regexes have no bwrap equivalent, and name-based rules cannot cover `GIT_DIR`/`--separate-git-dir` anyway; deferred to the Linux workstream.

Accepted write-side residuals: a worktree `.git` *file* (`gitdir:` pointer) can't be denied by name without also breaking `git init`; a symlinked `.git` directory resolves to a path without the `.git` segment and evades the regex — the unlink deny keeps `mv`/`rmdir` from *removing* a real `.git`/`hooks` directory, but an agent can still rename the *repository* itself and swap in a staged dir whose `.git` is a symlink, or plant a fresh trap repo (`mkdir fresh/.git` is allowed, then `mv staged-hooks fresh/.git/hooks` creates the dir without unlinking anything) — the grammar has no `vnode-type` filter (measured), so create-side planting can't be denied without also denying `mkdir .git`, which would break `git init`; the `\.git$` unlink anchor also covers plain *files* ending in `.git` (`rm notes.git` fails — cosmetic); gitdirs not named `.git`/`*.git` (`git init --separate-git-dir`, `GIT_DIR` env) evade every name-based rule by construction; `~/Library/Preferences` plists (Terminal/iTerm2 startup commands via `defaults write`) stay writable because denying the whole directory would break ordinary host commands; on Linux a *live* symlink at a write-deny name (`~/.gitconfig` → `~/dotfiles/gitconfig`) ro-binds its resolved target, so the link name itself can be unlinked and replaced inside the sandbox — pinning it would mean deleting the owner's working symlink, which is worse (the dangling-link case is unlinked safely; the live-link case is not). The same replace-the-name hole exists at a *read*-deny name (`~/.ssh` → `~/dotfiles/ssh`): the read stays masked through the link target, but the name can be removed and recreated as a real directory the host then owns — the name-based deny boundary cannot pin the name without deleting owner state, and bwrap has no mount flag that binds a link name rather than its target; a daemon running as root is outside the deployment model (mask mounts that would squat root-owned names like `/var/run/docker.sock` are skipped only because the unprivileged daemon cannot create them — confined root could plant the name either way), and the Linux profile binds `/` rw with no pid/net namespace, so `/proc` and process signalling remain model-level residuals for the Linux lane (#5401) rather than holes this list can close. These are the read-side "known gap" equivalents: a deny list is a floor, not a proof.

Step credential delivery is read-only: `creds/step-<id>-github/` (the `github-token` file and `gh/` config) reaches the profile through the caller's `readable` argument, not `state` — the session reads the token but cannot write, rename or symlink-swap the directory, so a compromised session cannot redirect the daemon's next `writePrivateFile` (`O_NOFOLLOW` guards only the leaf component) into an arbitrary owner directory. Both `state` and `readable` caller arguments must resolve strictly inside the daemon home, and env-derived harness state (`CLAUDE_CONFIG_DIR`, `GEMINI_CLI_HOME`, isolated `HOME`) must resolve inside the owner home or the daemon home — anything else fails closed before a single directory is created. Granted paths resolve their existing prefix only and keep the missing tail lexical: any existing symlinked component — a state dir, handoff dir, task temp leaf, extra state/readable entry or the pi resume file — fails closed with `Unsafe confinement symlink`, so a session cannot rename a symlink over a granted name and have the next `confine()` follow it into a task-chosen target. The check is anchored: each grant walks every existing component from a trusted root (the harness home, the workspace, task temp, or the longest matching granted root) with `lstat`, so a pivot planted at a writable intermediate ancestor — `.config → pivot` under a granted agent home — is refused the same way. Denied roots are emitted whether or not they exist at profile-build time, so a credential store created mid-session (first `gh auth login`, first `~/.cairn` write) is born denied.

Denied paths are resolved: every denied directory and file emits both its lexical path and, when it exists, its realpath — a symlinked `~/.zshrc` or `~/.config` (dotfiles-manager setups) is denied through both names instead of failing profile construction or escaping the deny by resolution. Grant-side paths stay strict: a symlink in a granted path still fails closed, except `readable` entries, which emit both `realpath(parent)/basename` and the leaf's own realpath — a symlinked `.config` parent keeps `.config/git` working, a symlinked leaf to a safe target stays readable under both names, and a symlinked leaf that resolves onto a denied path is refused outright. Because Seatbelt is last-match-wins and the readable allow follows the deny block, a denied path whose *resolved* variant lands inside a readable dir would otherwise be re-allowed; the profile therefore re-denies any denied path strictly inside a readable dir in a post-allow `(deny file-read* file-write* (subpath …))` line — the same line that covers `~/.config/git/credentials` and its parent-resolved form — so `~/.ssh` symlinked to `~/.config/git/ssh` stays denied while the rest of `~/.config/git` remains readable. A readable entry equal to a denied path always throws `Unsafe confinement readable overlap` — the `readableDeniedAllowed` exception existed only for the removed antigravity `~/Library/Keychains` carve-out — so a config mistake like `CAIRN_SKILLS_DIR=~/.ssh` fails closed instead of silently un-denying. The per-session `state` argument is restricted the same way: every caller-supplied state path must resolve strictly inside the daemon home (where `creds/`, `chat-sessions/` and `homes/` live); anything else throws `Unsafe confinement state path`, so a credential env like `GH_CONFIG_DIR=~/.config/gh` cannot widen a denied root into writable state.

Known gap, same as Linux: a deny list. A secret kept in a path nobody listed stays readable. The first mitigation is that Cairn's own state lives under two roots that are denied wholesale.

## How the Runner launches a session under the sandbox

One module, `apps/daemon/src/backend/confine.ts` (seam stays inside `backend/`), gains a macOS backend next to the bwrap one. Both take the existing `ConfinementPolicy`; a new `seatbeltProfile(policy)` returns SBPL text, a golden-file tested pure function, and `confineCommand(policy, command, env)` returns `{ command, args, env }` for the platform. On macOS that is `/usr/bin/sandbox-exec -p <profile> -- <command> ...`. The profile carries no secrets (paths only) and may sit in argv.

```
(version 1) (allow default)
(deny file-write*)
(allow file-write* <worktree> <git dirs> <task temp> <own state> <caches> /dev/null /dev/tty* /dev/fd)
(deny file-read* file-write* <each denied root>)      ; userData/home, userData/runner, credential dirs
(allow file-read* file-write* <this session's worktree> <git dirs> <own state>)   ; later rule wins
(deny file-write* <.git/config> <.git/config.worktree> <.git/hooks>)
(deny network-outbound (remote ip "localhost:<server port>"))
```

Rule order matters in SBPL (last match wins); the generator emits denied roots first, then the narrow re-allows, then protected-file denies, and a unit test asserts that order, mirroring Linux's "denied-parent masks, narrowly re-exposed paths, protected-file masks".

| Runtime | Seam | Change |
| --- | --- | --- |
| Claude Code | SDK option `spawnClaudeCodeProcess` (`claude-code.ts`, `spawnWithOAuthTokenOnFd`). Always install it, with or without the OAuth FD | spawn `sandbox-exec ... claude` with a cleared, allowlisted environment; leave the SDK's own `sandbox` off |
| Codex (ACP) | `AcpBackend` `spawnProcess` (`acp.ts:389`) | same prefix; require `full-access` mode after `session/new` and resume so Codex's own Seatbelt is off |
| Gemini (ACP) | same `spawnProcess` | same prefix |
| Pi | today the session, its file tools and its Bash tool run inside the Runner process (`pi.ts`), so a profile on the Bash tool alone leaves the Read/Edit tools able to read the token | move the Pi session into a child, `cairn-daemon pi-host`, speaking the versioned JSONL protocol already specified in the Linux design ("Pi protocol and state ownership"), launched through the same seam. No in-process fallback |
| `claude-code-bin.ts`, `claude-code-auth.ts` probes | direct `execFile` | go through the seam, or are declared not session launches and tested as such |
| `step-local-tools`, git helpers, `local-merge` | Runner's own work | not session launches; unchanged |

Runner-side start sequence on macOS: the Runner builds the policy from the claimed step (worktree, git dirs, temp, own state), generates the profile, spawns the confined process in its own process group (`detached`), and tracks the group. Stop and abort signal the group (`kill(-pgid)`), and the Runner's existing supervisor kills leftover groups after a crash. macOS has no cgroups, so this is weaker than the Linux ownership model: a descendant that calls `setsid` escapes group kill. It stays confined (the profile is inherited) but can outlive the step. Accepted for macOS; the sandbox, not process accounting, is the security property here.

Environment: pass only the allowlisted variables the step already assembles (`step-env.ts`), plus none of the Runner's inherited environment. Today `runnerEnv` hands the Runner's whole `process.env` and server origin to its children; the session must not get the server origin either.

The command gate stays as a policy layer for `ask` commands, but the design states plainly that the sandbox, not the gate, is the boundary.

## When the sandbox is unavailable

Same contract as Linux: an isolation failure is machine unavailability, never repeated task failure, and never a raw fallback.

- Startup preflight on macOS runs the real launch path against a scratch directory: apply the profile, then assert that a sentinel file in a denied root cannot be read, that a write to the scratch worktree succeeds, and that a write outside it fails. Pass means `ready`; any failure means `unavailable` with a bounded reason (`sandbox-exec-missing`, `profile-rejected`, `probe-failed`).
- `confinement-availability.ts` currently reports macOS as `not-applicable` and leaves dispatch unchanged. This changes to `checking → ready/unavailable` on macOS, using the existing observation fence, machines-page reason and one-notification-per-outage path. The reason enum in `@cairn/shared` gains the macOS values.

## Segment 4 design: the `pi-host` child

Scope: macOS only for launching; the seam (`confine(opts, 'pi', launch)`) is platform-neutral, so Linux bwrap plugs in later without changing the protocol. With no confiner (every non-macOS platform today) `PiBackend` runs the session in-process exactly as before.

### Roles

- Parent (`PiBackend` with a confiner): owns the session index (`recordSession`, `resolveSessionFile`), provider materialization (`models.json`, including learned compat, which is process state), remote and local tool callbacks, skills brief composition (`brief`), logging channels and the step's `StepEvent` stream. It holds no file or command executor for the child.
- Child (`cairn-daemon pi-host`, one per live session): runs the existing in-process session code (`PiBackend.openInProcess`), so Read, Edit, Write, Bash and local MCP stdio children all run inside the Seatbelt profile. It never touches the index, the daemon home or the server.

### Launch and state

Launch: the parent creates a private session directory under `sessionDir`, builds the policy through `confine(opts, 'pi', launch, state)` with `state = [agentDir, private session dir, resume file if any]`, and spawns the result detached (own process group) with stdio pipes and an environment of `withoutPinnedEnv(process.env)` plus the step env. If the confiner throws, or the spawn fails, `open` rejects: no handle, no in-process fallback, no second attempt.

Frames are one JSON object per line, `v: 1`, Zod-validated on both sides, at most 32 MiB each. Parent to child: `initialize`, `steer`, `tool_reply`, `stop`. Child to parent: `ready`, `event`, `usage`, `log`, `tool_request`, `steer_reply`, `ended`, `fatal`. Writers queue at most 1024 frames and wait for `drain`; an overflow fails the session. The child redirects its own `stdout` writes to `stderr` so a stray print cannot corrupt the protocol; the parent keeps the last 4 KiB of `stderr`, redacted with the session's API key, for failure messages.

| State | Entered by | Leaves by |
| --- | --- | --- |
| starting | parent spawns the child, sends `initialize` (SessionOpts without callbacks, serializable tool definitions, skills dirs, prompt, images, resume file) | `ready` (session id and file) goes to ready; `fatal`, EOF, invalid or oversized frame, or a 30 s timeout rejects the open and kills the group |
| ready/running | `ready`; the prompt, if any, was sent by the child's open | `event` frames in order, `usage` snapshots, `log` frames to the parent's log callbacks; `ended` goes to closed |
| stopping | parent `stop()` sends `stop`, rejects pending steers | `ended` or exit goes to closed; after 10 s the group is killed |
| closed | `ended`, a `done` event, or exit | the queue ends, pipes close, the process group is killed, the private directory is removed if empty |
| failed | child exit or EOF without `ended`, invalid frame, oversized frame, queue overflow, unknown tool id | one `error` StepEvent (`retryable: false`) with the redacted stderr tail, then the queue ends; success is never synthesized |

### Every path that reads or writes session state

1. Initialize: the parent resolves the resume file (missing transcript rejects with `SessionNotResumableError` before any child), materializes `models.json`, creates the private directory. The child validates the frame and opens the session. The API key travels in the initialize frame only (private pipe, never argv or env).
2. Prompt and events: the child sends the prompt in open; the parent receives `ready` first, then the ordered events. `onSession` is called by the parent from `ready`, so only the parent writes the index; the parent rejects a session file outside the private directory or the resume file.
3. Steer and images: parent `steer` sends a frame with correlation id; the child's `handle.steer` result returns as `steer_reply`. Steering after stopping or closed rejects locally; image bytes are checked by the existing `ensureImageInput`.
4. Tool request and reply: the child's remote and local tool wrappers send `tool_request` with a correlation id and the declared tool name. The parent runs only tools declared in this session's initialize (`remoteTools`, `localTools`), replies `tool_reply`; an unknown name or id fails the session. No other callback exists, and there is no generic filesystem or command request.
5. Usage and logs: `usage` snapshots after message ends and at `ended`; the parent returns the last one from `usage()`. `log` frames go to the named parent callbacks (`mcp`, `skills`, `gate`, `trust`, `otel`, `compaction`).
6. Stop: `stop()` sends `stop`; the child aborts the session, flushes spans, sends `ended` and exits.
7. Child crash or parent loss: the parent sees exit or EOF and fails as above; the child sees stdin EOF, stops the session and exits.
8. Invalid or oversized frame: either side treats it as fatal; the child exits, the parent kills the group.

### Failure behaviour

An isolation failure (confiner throws, profile rejected, spawn error) rejects `open` with a scrubbed message and starts nothing. A crash mid-session produces the single error event. Descendants of the child inherit the profile; the group kill is best effort on macOS (a `setsid` descendant outlives the step but stays confined), the same accepted limit as the other harnesses.
