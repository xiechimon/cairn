# Coordinator Diagnostics and Shared Tool Resolution — plan, 2026-11-27

## User scenario

A first-time Cairn user or self-hosted operator meets this change when Coordinator stops acting on their Mac after a server or runner restart, or when a recent build or Coordinator turn fails and they inspect `GET /api/teams/:id/chief/diagnostics`. They only need their team ID and existing server access token (if authentication is enabled); no extra accounts, secrets, or database tables are created. The endpoint reads existing SQLite state (`chief_thread`, `chief_message`, `machine`, `step`, `build`, `todo`, `mcp_connector`, `mail_account`) and the optional deploy record JSON file without performing network calls or MCP hydration. The `coordinator` section reports a synchronous snapshot of the tool set and cached connector tools that `resolveCoordinatorRemoteTools` produces right now (excluding live introspection of an already-open pi session registry and unhydrated `toolsJson = null` connector caches), checks the 8 unconditional core Coordinator tools (`create_todo`, `todos`, `projects`, `machines`, `open_thread`, `message_thread`, `threads`, `needs_you`), checks whether the owner's local Mac host is connected and usable (`ownComputerReady`, `ownComputerReason`), lists non-retired team machines with normalized capability DTOs, and returns the team's 5 most recent failed steps with OpenTelemetry `traceId` values. Unknown teams, side threads (`chief-digest-*`, `chief-memory-*`), or unknown `threadId` filters return HTTP 404.

## Scope

1. Add `resolveCoordinatorRemoteTools(deps, options)` in `apps/server/src/services/coordinator-diagnostics.ts` to compute `{ tools, groups, ownComputerReady, ownComputerReason }` using `teamOffersDesktop`, `ownComputerOffered`, `ownComputerTarget`, `browserOfferFor`, `offeredPhoneNames`, `coordinatorToolDefs`, and `connectorToolDefsForTeam`, where `groups` has exact shape `{ router: boolean; desktop: boolean; ownComputer: boolean; browser: boolean; ownerChrome: boolean; phones: string[]; connectorToolCount: number }`.
   - `ownComputerReady` is `false` with `ownComputerReason: 'no active Coordinator thread for team'` when `threadRow` is `null` or `undefined`. When `threadRow` is present, evaluate both `shellTarget = ownComputerTarget(deps, threadRow, 'user_computer_shell')` and `actTarget = ownComputerTarget(deps, threadRow, 'user_computer_act')`: `ownComputerReady` is `shellTarget.kind === 'ready' || actTarget.kind === 'ready'`; when `false`, `ownComputerReason` prefers `actTarget.text` if it is more specific than `OWN_COMPUTER_NO_MAC` (e.g. `OWN_COMPUTER_NO_ACCESSIBILITY` or `OWN_COMPUTER_NOT_OWNER`), otherwise `shellTarget.text`.
2. Refactor `apps/server/src/coordinator/index.ts` and `apps/server/src/services/machine-claim.ts` to call `resolveCoordinatorRemoteTools` instead of duplicating `coordinatorToolDefs(...) + connectorToolDefsForTeam(...)` assembly. Keep `createServerRuntime` callbacks, `routerTools`, `includeSubagent`, `mailTurn` (`[]`), `memoryEditTurn` (`WORKER_MEMORY_REMOTE_TOOLS`), and `deferred: true` for tools outside `CORE_COORDINATOR_TOOLS` and `SUGGEST_REPLIES_TOOL_NAME` in `machine-claim.ts` unchanged.
3. Add `buildCoordinatorDiagnostics(deps, teamId, threadId?, options?: { routerTools?: boolean })` in `apps/server/src/services/coordinator-diagnostics.ts` returning:
   - `deploy`: `readDeployStatus(deps.deployRecordPath).deployed` (`null` when missing or invalid JSON).
   - `serverVersion`: `readServerVersionInfo({ deployRecordPath: deps.deployRecordPath })`.
   - `threadId`: when `threadId` is given, look up that `chiefThread` scoped to `teamId` and reject missing threads, cross-team threads, or side threads (`isChiefSideThreadId`) with `notFound`; when omitted, pick the latest non-archived main `chiefThread` for `(teamId, deps.user.id)` first, falling back to the latest non-archived main `chiefThread` for `teamId` (`projectId IS NULL`, excluding `chief-digest-*` and `chief-memory-*`, ordered by `updatedAt DESC, createdAt DESC`), or `null` if none exists.
   - `coordinator`: `{ offeredToolCount, offeredTools (sorted), coreToolsPresent, missingCoreTools, groups, ownComputerReady, ownComputerReason }` checking `['create_todo', 'todos', 'projects', 'machines', 'open_thread', 'message_thread', 'threads', 'needs_you']` against the offered tools. Because diagnostics is synchronous and read-only, `connectorToolCount` reflects cached `toolsJson` on `connected` HTTP connectors plus active IMAP mail accounts without triggering network hydration.
   - `machines`: non-retired team machines (`teamMachines(deps.db, teamId)`) mapped to `{ id, name, kind, online, hubConnected, latestCliVersion, capabilities: { ownComputer: boolean, ownComputerShell: boolean, browser: boolean, computer: boolean, mcpServers: string[], skills: string[] } }`.
   - `recentFailures`: up to 5 latest `step` rows with `status = 'failed'` scoped to `teamId` (via `build -> todo.teamId` or `chiefThread.teamId`, not filtered by `threadId`), ordered by `coalesce(step.finishedAt, step.createdAt) DESC, step.createdAt DESC, step.rowid DESC`. Each item returns `{ stepId, buildId, kind, status, failureCode: step.failureCode ?? build.failureCode ?? null, errorMessage, createdAt, finishedAt, traceId }`, where `errorMessage` uses `build.errorMessage` for build steps (or `null` when cleared by build restart) and falls back to parsed `chiefTurnErrorContentSchema.message` from `chief_message` (`id = 'chief-err-' || step.id`) for chief steps (or `null` when absent), and `traceId` uses `otlpTraceIdOfStep({ kind, buildId, stepId })`.
4. Register `GET /api/teams/:id/chief/diagnostics` in `apps/server/src/routes-chief.ts`, guarded by `requireTeam(ctx, teamId)`, reading optional `?threadId=` query param, and returning JSON 200.
