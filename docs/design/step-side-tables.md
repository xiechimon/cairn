# Move six step column groups into domain-owned side tables — plan, 2026-11-28

Owner-approved decoupling series, row #36 (not GitHub issue #36), following row #35 (`5da06807e`). `step` keeps lease and run core; quota, subscriptions, schedule, memory trace, skill injection and blocker handoff move to six side tables. This is a storage-ownership change, not a query latency project. Today the lease schema changes whenever a provider adds account attribution or memory adds a trace, and core whole-row queries load all six domains. Physical ownership, not wrappers over shared storage, is the approved requirement. A claim winner still commits all domain side effects atomically; lease generation and ownership do not move. No wire, REST, SSE or UI behavior changes.

**Release split (owner-approved): expand now, contract only after measured evidence.** This release creates and backfills the six domain tables, moves every runtime reader and writer, and preserves the eleven old physical columns for a pre-expand executable. No manual bridge, new updater protocol, feature flag, compatibility mirroring, or dual read/write. A separate destructive change owns deletion; this commit cannot satisfy its gate.

## User scenario

Tasks, account attribution, scheduling, and the runner protocol do not change. Installing this version adds storage and copies existing metadata; a running step keeps its lease identity. A pre-expand executable can still open the schema, and query the retained columns. A database-side write fence rejects incompatible old step mutations instead of silently accepting updates that the new code could not see. On rollback, keep any expanded file that contains accepted changes; only restore an untouched predeploy snapshot when existing recovery establishes that replacement will not discard accepted writes. Never require users to install a bridge.

## Scope

1. **Six side tables (`apps/server/src/db/schema.ts`, next unused journal migration, suffix `_step_side_tables`)**. Each has `stepId text PRIMARY KEY NOT NULL REFERENCES step(id) ON DELETE CASCADE` plus the moved columns with their current types and JSON modes:
   - `step_quota`: `quotaBlock`, `fallback`, `ranModel` (all nullable).
   - `step_subscription`: `claudeSubscriptionId`, `devinSubscriptionId`, `antigravitySubscriptionId` (nullable).
   - `step_schedule`: `scheduleId`, `scheduledBy` (nullable). Keep the later `step.doubaoSubscriptionId` in core in this eleven-column change. Preserve its claim, clears and attribution through the same CAS as the sibling account group; it is not silently moved as a twelfth column.
   - `step_memory_trace`: `memoryTrace` (`NOT NULL`).
   - `step_skill_injection`: `skillInjection` (`NOT NULL`).
   - `step_blocker_handoff`: `blockerHandoff` (`NOT NULL`).
   Keep the eleven old physical columns, triggers and indexes in this release, while the runtime Drizzle `step` exposes only the core. Include the retained columns in a generation-only schema so a normal future Drizzle generation cannot propose dropping them by accident. `build.scheduledBy`, `schedule.lastRun*`, `gate_verdict.ranModel`, `step_route` and lease hold/status fields are unchanged.
2. **Sparse null-equivalence**. A step with no data in a group has no row. A row exists iff at least one of its columns is non-null; writers delete the row when a patch leaves every column null. SQL `NULL` is the only "absent" value. JSON that means something while empty (`{"hits":[]}` skill check with no hits, `[]`, `{}`, a trace with empty arrays) is stored verbatim and reads back as present, so `null` and `{"hits":[]}` stay different. Backfill copies the raw `text` byte for byte (no `json()` normalization); conditions are `IS NOT NULL`.
3. **One additive migration, atomic, no history change.** Create all six domain tables and backfill with six `INSERT … SELECT` statements inside the existing Drizzle migration transaction. Do not update, drop or rebuild `step`. Its complete original rows, rowids, triggers and indexes are retained. Old columns are read for this one backfill only; already applied migration journals are not re-run. No compatibility view or triggers keep the snapshots of old and new storage synchronized.
4. **Leaf group modules own reads and writes** (`apps/server/src/services/step-groups/{quota,subscription,schedule,memory-trace,skill-injection,blocker-handoff}.ts`). Each imports only `db/schema` and shared types (no import of `chief.ts`, `coordinator-steps.ts`, `machine-claim.ts`, `machines.ts`; `node scripts/import-cycle-gate.mjs` stays green) and exports: a row type that equals today's fields; `read…`/`readMany…` (by step id); a left-join column set for list reads; `write…` (upsert patch where `undefined` keeps and `null` clears, deleting the row when all columns end null); and, where the old code wrote under a predicate, a `write…Guarded` that is one `INSERT … SELECT … FROM step WHERE <same predicate> ON CONFLICT DO UPDATE` so guard and write are one statement.
5. **Move every reader and writer in this one patch, no dual path**. There is no runtime dual read, dual write, fallback read of the old column or feature flag. TypeScript no longer compiles `step.<column>` for the 11 columns, which finds every ORM use; a source scan in the proving test finds raw-SQL strings. Whole-row consumers (`select().from(step)`, nested `{ step, … }` candidates, `DELETE … RETURNING`) are changed to read only the groups they actually use via a join or a group read. The full list is the inventory below.
6. **Writers run in the same transaction as the guarded core transition, never after an `await`**. A group write follows its core CAS in the same `withFencedTransaction`/`db.transaction` and runs only when the CAS changed one row: claim (`acquireWorkerStepLease`, `acquireChiefStepLease`) writes subscription ids, `ranModel`, `fallback`, `skillInjection`, `blockerHandoff` only for the winner; park (`claimed → waiting_quota`) writes `quotaBlock` with the status change; step creation writes `step_schedule` in the transaction that inserts the step; initial claimed `step_memory_trace` writes retain `status = 'claimed'` and the `claimedAt` generation predicate, while pending steer writes retain their own original predicates. A losing CAS writes no group row, so a stale claim, a released step or a superseded turn cannot leave a stale quota, subscription, trace, skill or blocker row. If a fenced side update leaves an all-null compound group, remove the row in the same transaction after a successful guard; a side statement failure rolls back the core change. When a predicate depends on the old core row (notably unread steer retirement), use the core update's returned IDs for the side delete; do not re-run old predicates on changed rows. Clear single-column NOT NULL groups with a guarded DELETE rather than an upsert of null. Step creation takes schedule attribution as insertion input so it and the core row are durable before any enqueue wake/publication; an expired or losing trigger commits and publishes neither.
7. **Reads join only where a read needs a group**. `lastHeartbeatAt`, `claimedAt`, `status`, `machineId`, `claimCount`, `mcpGrant` stay core; `heartbeatStep`, abandoned sweeps and core-only queue predicates read no side table; quota/account queue projections explicitly join their groups. Quota/model selection, account hold, schedule history, memory usage, skill/blocker projections and the claim payload read exactly their group.
8. **Wire, REST, SSE, UI, daemon and shared protocol are unchanged**. `packages/shared/**`, `apps/daemon/**`, `apps/web/**`, claim/heartbeat/finish routes, `step.done.quotaBlock`, `quotaWait`, `skillInjection`, `todo.blockerHandoff`, memory usage DTOs and `runnerProtocolVersion` do not change; an older runner continues an already-claimed step over HTTP (it never opens SQLite).
9. **Deploy and rollback.** Rehearse a backup, then migrate before serving; the expansion, three `step` mutation triggers and journal are atomic. The legacy app's SQL can still read the original columns. Inserts, updates (including core-only) and deletes require the connection-local deterministic `cairn_step_write_generation()` scalar, registered by `openConnection` for file/memory/serialized DBs and on handles migrated by `migrateDatabase`. A pre-expand binary has no scalar, so SQLite rejects its writes before any `step` mutation; the normal latest server has it and no dual storage. Also fence the unconditional `UPDATE agent_memory SET layer …` in `foldMemoryIndexes`, which every supported legacy packaged server invokes in `openDbWithHandle` before serving HTTP and before product writes. Its `BEFORE UPDATE OF layer` trigger requires the same registered function even on an empty store. This is a startup writer fence, not a migration of memory data. Without it a legacy archive route can commit and publish a todo change before an incompatible step stop is rejected. Old SQL clients can still open and read retained fields; the legacy service cannot accept a partially committed archive/stop. Verify that the sealed prior build exits before listening, archive and stop cannot reach it, and the file is unchanged. Already-running old servers are excluded by the confirmed stop boundary; don't certify older unsupported binaries as writable or automatically recoverable. An old deployment controller may label a structurally readable code-only fallback healthy; this is **not writable health**. The revised watcher checks the live migration marker against the deployed release before any same-SHA shortcut. On mismatch it treats the installation as needing forward recovery, stops local services under the existing deploy lock before applying a compatible CI-green repair, keeps the live file and snapshots, and uses the same target path to resume writes. It does not wait to drain stale leases on a fenced step schema. Current rollback code never restores a snapshot with accepted writes or calls a legacy rollback writable. An unchanged desktop updater cannot rely on a live legacy server to drain a stranded claim. The startup fence runs before that server can listen or publish a resident owner. In the sealed `desktop-v0.1.823` sources the lease and busy checks permit update when the resident owner is absent or dead; a refused startup therefore removes the condition that can strand the update without changing the signed feed. A proposed separate manifest checkpoint is not used: the fence already prevents the incompatible process from becoming a resident writer. A guard-equipped foreground/background updater retains the repair from expanded probation and takes its next signed compatible candidate after confirming stops, without waiting to drain old claims. An explicitly opened old SQLite connection may read legacy columns but cannot write them. Self-host has no desktop feed dependency: mini production must already be running the [roll-forward prerequisite](step-roll-forward.md), and the next watcher invocation uses fresh main scripts even if the app on disk is older. Before enqueue, check an actual sealed old app on a migrated copy and rehearse the server/Runner rollback with the refreshed watcher. Before desktop publication, signed CI smoke must exercise failure and automatic recovery with the unchanged supported legacy updater and with the guard owner; require the old service to stay unavailable, the subsequent signed compatible offer to install without a manual step, and the same file to accept a new write. A live claimed sentinel must survive both attempts. No new manifest, manual bridge, unsigned substitute or fake readiness signal satisfies this gate.
10. **Proof and contract exit.** The populated-copied-DB test verifies exact per-step values, retained legacy SQL, side cascades, and heartbeat/claim identity. Existing product/wire tests retain their assertions as controls. The separate contract change is blocked until deployment telemetry or authoritative per-install records show every installation eligible for that rollout has actually passed a tested rollback guard. Evidence must include Mac desktop auto-update (including skipped releases and inactive installations), self-host watcher, direct supported server/restore paths, and old artifacts on a copied DB. A missing or unknown install is not covered and blocks destructive delivery to it; no time-based assumption and no manual bridge. Test that the guard prevents reopening a contracted DB with old code, preserves accepted writes, and supplies forward recovery. Only then remove the generation-only columns and drop the eleven physical columns in a separately reviewed migration.

## States, transitions, readers, writers

Step lease core is unchanged: `pending → claimed` (`tryClaim` → `acquireWorkerStepLease`; chief `claimPendingChiefStep` → `acquireChiefStepLease`), `claimed → claimed` (heartbeat), `claimed → pending` (`releaseStepLease`, requeue), `claimed → done | failed | stopped | waiting_quota`, `waiting_quota → pending` (`sweepQuotaWaitSteps`, `retryQuotaWaitNow`), hard delete. Claude window refresh can also park `pending → waiting_quota` and refresh metadata in place in `waiting_quota`. Group rows add no new step status. Group lifecycle against those transitions:

| Group row | Created / replaced | Cleared | Deleted with step |
|---|---|---|---|
| `step_quota` | `ranModel` + `fallback`: claim win, model-fallback requeue, provider rename; `quotaBlock`: park, `writeClaudeQuota`, rate-limit recovery, successor copy in `releaseCoordinatorInput` | Manual retry and Claude recovery can clear the block (the generic automatic sweep retains it); the Coordinator model-switch release also clears the model pin, fallback and subscription binding. Remove the quota row only if all its columns are null. | cascade |
| `step_subscription` | claim win (Claude/Devin enabled-id lookup and Antigravity binding stay in the winning transaction) | `releaseParkedCoordinatorSteps` | cascade |
| `step_schedule` | creation of the step (`builds.ts` `enqueueStep`, scheduler dispatch, chief enqueue, steer); write before transaction commit and before publication; preserve the worker start/steer attribution asymmetry | never (immutable after creation) | cascade |
| `step_memory_trace` | Initial claim trace in worker/remote chief payload or in-server chief: preserve the original `status='claimed'` and generation guard. `stageSteeredMemory` instead targets a pending waiting step. Concurrent actors: scheduler tick, `claimStep` from several runners, finish/heartbeat from the owning runner, stop/archive/close, the stall monitor, quota probes, backup/restore and the deploy lease. A group write never runs outside the transaction that won the core CAS or under its own guarded statement; core CAS loss is the single serialization point, as today.

### Failure paths

| Path | Behavior |
|---|---|
| Migration SQL error, disk full, lock timeout or process death before commit | No partial side tables or journal entry; the original schema and data remain intact. An unsuccessful rehearsal leaves running services alone. |
| Process death after commit/before readiness | Reopen uses the recorded migration; no repeated backfill and no writes to legacy columns. |
| Previous executable opens the expanded DB | Its projections can read the retained schema, but it cannot successfully mutate a step; any HTTP-only health finding says nothing about write readiness. The updater moves forward on a compatible healthy build and retains originals until then. |
| Same SHA or incompatible active release without a record | Watcher probes before same-SHA return and calls the marked repair path under the lock. The journal owner records the transition; stranded claims are retained, not waited on after confirmed stop. |
| Stop unconfirmed, probe unreadable, or no compatible green candidate | Keep live DB and original artifacts. Without a journal an unreadable marker leaves the running service alone; with a journal preserve the hold and retry on the next wake. |
| Interrupted or repeated repair failures | Finish only the recorded candidate when exact local server, configured Runner and marker attest; otherwise confirm stops again, keep the pins, and select the next eligible build. |
| Running or older Runner on an upgraded server | Runner talks only HTTP. Same generation/ownership predicates; a restart retry succeeds if still owning the lease, and a superseded report stays rejected. |
| Side deletion/update race | Foreign-key cascade on hard delete; side writers participate in the same guarded SQL or transaction as the original core change. Empty/missing rows resolve to the original null shape. |
