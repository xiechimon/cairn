## Capture contract and states

**Proposed:** `absent -> collecting (turn-local memory) -> sealed (one committed row)` or `unusable` (reason only). Seal at every terminal Coordinator outcome, after awaited tool calls and their database commits, before publishing completion/starting the next turn. Failed/stopped turns may retain diagnostic snapshots but are ineligible for scoring. Crash/lease-loss recovery never reconstructs a missing snapshot from current tables.

Persist at turn end, but capture inputs when read: collect the initial complete routing world at claim/context assembly and ordered tool-boundary read views, each with call ID, input/output, logical time, pre-call world and committed effects. The live handler and capture share the same short database transaction/read view; never hold a transaction across model/network waits. Deduplicate equal projections. The final post-tool world is audit data, not replay's starting state: a newly created todo must not exist before its replayed `create_todo`. Preserve negative lookups, empty collections, ordering, provenance and time-dependent inputs. Concurrent changes between calls belong to the corresponding views; unrepresentable interleavings make the case unusable. Candidate calls use captured state through real handlers, never canned successful tool responses; uncaptured reads fail closed. No claim that one end-time query reproduces earlier reads.

| Read boundary (source files under `apps/server/src/services/`) | Required captured closure, scoped to this team and reachable records |
| --- | --- |
| Context/prompt assembly (source map below) and `chief-tools.ts:projects` | Verbatim assembly inputs and source prompt/context digests; source request, ordered input/steered message IDs and text, thread/team/project chip, supplied context; all project routing fields including archive/configuration and todos needed for counts. |
| `chief-tools.ts:todos` -> `todos.ts` | List/detail/filter/page inputs; todos including request/siblings/dependencies/archive/order; all build history; steps and quota/hold/fallback state; `todoTag`, tags, GitHub label links; token usage; schedule state; ownership inputs from `owner.ts` (messages/questions, projects, builds, steps, gate state); verification verdict/head/digest from `verified.ts`. |
| `chief-router-tools.ts:open_thread` -> `thread-message.ts` -> `builds.ts` | Team/archive checks, latest/historical builds and steps (`stoppedBeforeFirstRun`), retry parking/failure windows, prior errors, retry lessons (feedback, plans, messages, gate digests/verdicts and referenced research), routing rules/work policies, research prerequisite/deduplication state and dependencies. |
| `chief-tools.ts:create_todo` -> `coordinator-request.ts` -> `todos.ts` and the same start-build path | Cited owner/answered-question messages, source todo segments, split siblings, referenced dependencies, attachment authorization metadata, sequence/order allocation, tags/labels and project configuration; include post-create detail reads and auto-created research work as effects, not initial rows. |
| Shared routing/availability dependencies | Machine online/runtime/capability/quota projections, stored step routes, model catalog, team usage policy, active-subscription availability/expiry as a boolean/time projection, and captured clocks. Never subscription tokens or credential rows. |

Each row is a versioned schema contract, not permission to dump whole rows. Record complete collections where alternate tool arguments may read them. Prompt-injected memory/history and skill metadata are required captured inputs, not exclusions. Additional filesystem reads, attachment contents or external-service reads not captured under this contract remain ineligible under the eval design; reference metadata alone does not enable replay. A new read dependency must extend capture, seeding and its parity test together.

## Prompt/context input parity

**Recon (Observed):** the production assembly chain is [`buildChiefSystemPrompt` / `chiefClaimContext`](../../apps/server/src/services/chief.ts), [`chiefTurnContext`](../../apps/server/src/services/coordinator-steps.ts), and [`claimedPayload`](../../apps/server/src/coordinator/index.ts) through [`runCoordinatorTurn`](../../apps/server/src/coordinator/runtime/turn.ts) and the runtime context projection. The legacy [`machine-claim.ts`](../../apps/server/src/services/machine-claim.ts) also consumes `chiefTurnContext`. The following source map is an audit starting point; the implementation must derive its versioned input contract from the actual production assembler arguments/read dependencies and generation boundary, not maintain an independent hand list.

| Production boundary | Verbatim inputs to retain at the read/injection boundary |
| --- | --- |
| `chief.ts:buildChiefSystemPrompt` | Team charter including empty/default distinctions; coordinator profile/provider/model; ordered project metadata (`id`, `name`, `repoKind`, optional description/GitHub repo); the exact ordered skill IDs/names/descriptions returned by the scan; each memory entry as injected, with title/content, IDs, omitted/file counts; ordered digest message contents and parsed items. Capture the router-state/needs-you projections and their ownership inputs at assembly time even in phase 1. Preserve section order and source section hashes. |
| `coordinator-steps.ts:chiefTurnContext` and `project-instructions.ts:projectTurnContextTraced` | Step/thread/team/agent/project scope, original prompt and trigger/digest branch; selected project name/instructions and injected project memories, including omissions; the skill scan used for route suggestions and exact generated route section; supplied memory blocks and ordered project/route sections. Capture each read separately if two scans/injections differ. |
| `coordinator/index.ts:claimedPayload` and legacy claim | Exact submitted instruction, wake/history markers, selected model/provider/thinking level, remote tool definitions and order; cold/warm decision inputs (last usage, resolved retention policy and clock), summary hint and volatile sections. Capture resolved non-secret policy values rather than raw environment values. |
| `runtime/seed.ts`, durable conversation context, `runtime/turn.ts` steering/compaction and `runtime/volatile.ts` / `cold-slim.ts` | Ordered prior messages/entries with IDs, roles, content blocks, tool calls/results and source ordering; seeded history and compaction summaries/digest, active conversation/head, model-switch folds, accepted steering inputs in consumption order, history markers, clocks and cold/warm projection inputs. Retain the actual post-projection messages and instructions at each model request, including volatile injection, so persisted conversation history is not approximated from transcript rows. |

**Single path (Proposed):** capture every value fed into prompt/context assembly verbatim in turn-local memory, preserving whitespace, null/empty distinctions, order and content blocks; do not summarize, reread live state or substitute source model output for candidate output. Record source code SHA, prompt/assembler version, runtime/projection version, model/provider/thinking and tool-schema version alongside inputs. Fixed prompt text belongs to that pinned source version; retain its rendered instructions and per-request context digests as parity evidence, not as the candidate's instructions. The existing privacy allowlist/redaction and bounds still apply before any persistence: if safe capture cannot preserve a required input exactly, mark the case unusable, never silently score a changed prompt.

**Evidence (Proposed):** run a real source assembly/generation boundary, capture its inputs, then in a disposable environment run the pinned source assembler and context projection using only the snapshot, with live reads denied. Compare SHA-256 of exact UTF-8 system prompt text and canonical ordered request messages/tool definitions against digests measured independently at the original generation boundary, for every request/steering boundary. Also compare against the safely persisted representation; any required-field redaction or mismatch fails eligibility. This is a reconstruction test, not a digest comparison of a stored prompt with itself. Remove or reorder each input category, including a prior turn/digest, charter, memory, skill description and project instructions, as negative controls; adding a production assembly read without capture must fail parity.

After source parity passes, replay re-renders the system prompt and context with the candidate code over those same captured exogenous inputs, retaining candidate-generated messages/tool effects. Candidate prompt digests may differ intentionally: record them for the before/after comparison (including #3688), never require candidate/source prompt equality. Memory/history already injected into context requires no extra tool allowlist entry; a new tool read still needs its own captured closure.

## Storage, paths and failures

**Proposed:** `coordinator_turn_snapshot` stores `teamId`, unique `turnId` (step ID), unique `sourceTraceId = otlpTraceIdOfTurn(turnId)`, schema version, terminal outcome, `capturedAt`, expiry, status/reason, redaction count, payload bytes, SHA-256 of canonical redacted JSON and nullable payload. Insert once; identical completion retries return the row, conflicting retries report unusable without replacing it. Schema/identity/digest must agree; capture time is not a surrogate row timestamp.

| Path | Behavior and failure |
| --- | --- |
| Claim/context and the four tool boundaries above | Collect bounded allowlisted projections; collection/serialization failure records an unusable reason and releases payload memory, while tools keep their existing behavior. |
| `coordinator/server-api.ts:done` and legacy `machine-finish-step.ts`, converging on `coordinator-steps.ts:finishCoordinatorTurn` | Sole sealer after tool commits, before terminal publication; use a separate snapshot transaction. Write/validation/redaction failure rolls back only that transaction: the turn still succeeds. Emit a payload-free reason metric/log; best-effort unusable row, otherwise absence is authoritative. No delayed live reread retry. |
| Trace emission (`runtime-otel.ts`) | Attach turn/trace ID, snapshot status/version/digest; export failure neither deletes the local row nor changes turn outcome. |
| Trusted harvest, then replay seeding (future protected eval PR) | Read snapshot by team + turn/trace, validate identity/version/digest/completeness/outcome/expiry, freeze payload into Langfuse item input and pin dataset version. Seed initial world and ordered views in disposable DB; preserve candidate effects. Missing, pending, failed, expired, corrupt, unknown-version or unsupported reads => `incomplete: snapshot <reason>`, never a scored regression or live fallback. Restore `todos`/`open_thread` eligibility only with full closure parity. |
| Retention/deletion | Daily bounded cleanup deletes expired rows after 30 days; harvest checks expiry even if cleanup fails. Cap retained payload at 256 MiB/team, evict oldest sealed rows first; missing rows become unusable. Team/privacy deletion removes snapshots too. Curated Langfuse inputs are independent copies governed by dataset retention/deletion, not pointers to expiring rows. |

Bound each turn to 2 MiB UTF-8 redacted JSON, 10,000 total projected records and 128 call views, enforced during collection and serialization. Exceeding any bound stores only an unusable reason; never truncate into an eligible case. These limits and retention are Proposed local decisions, not upstream guarantees.

## Privacy and acceptance

**Proposed:** allowlist fields first; exclude credentials, encrypted envelopes, auth headers, environment values, machine addresses and filesystem paths. Apply the same shared `redactSecrets` used by `runtime-otel.ts` before persistence and again at export; store hit counts only. Redaction/key collision or removal of a required replay field makes the case unusable. Restrict local reads and harvest to authorized team/trusted operator paths; no public endpoint or public-repo fixture containing harvested owner text. Keep expected answers outside snapshots/candidate input.

## Implementation phases and Red first

Each phase ships as its own implementation PR, branched from main after its prerequisite merges; protected eval consumption remains separately owner-reviewed. Both phases keep the accepted state machine, sealing point, insert-once semantics, failure isolation, bounds, retention, privacy and no-live-fallback contract. This PR changes documentation only.

### Phase 1: prompt/context, projects and create_todo

Deliver the storage/capture/seal lifecycle, all prompt/context inputs above, and full `projects` and `create_todo` closures. This supports routing evals and the #3688 before/after. `create_todo` includes its existing auto-start/research path, post-create reads and effects even where it shares dependencies with phase 2; phase 2 defers direct `todos`/`open_thread` tool eligibility, not dependencies phase 1 already executes. Record closure coverage/version explicitly; phase-1 cases invoking either deferred tool are incomplete, with those tools still outside the replay allowlist.

**Red first:** write each assertion before implementation, demonstrate failure on current main, then green on phase 1:

1. Reconstruct source system prompt and every request context from captured inputs and compare generation-boundary digests. Cover prior turns/digest, charter, team/project memories, skill scans/routing, project metadata/instructions, steering, warm/cold/seeded/compacted context and source model/prompt version; each missing/reordered input fails. Candidate prompt rendering changes on the same inputs without overwriting the source evidence.
2. Timestamp-free schema plus harvest after later mutation/deletion; real source/replay parity for `projects` and `create_todo`, including quoted splits, owner/answered-question messages, dependencies, tags, attachment authorization metadata, auto-start/research and post-create reads. Preserve pre/post-create separation, concurrent writes and time-based routing/quota inputs.
3. Duplicate/conflicting finish, crash/recovery, failed/stopped turns and both completion entry paths; injected snapshot write failure leaves the turn successful and harvest unusable.
4. Bounds, expiry/cap cleanup, team deletion/isolation, fake-token redaction, forbidden fields, corruption/unknown schema and uncaptured-read denial. Deferred `todos`/`open_thread` calls fail closed rather than score or use live state.

### Phase 2: todos and open_thread

Add the complete `todos` and `open_thread` closures from the capture table: ownership/build/step/verification state and all transitive dependencies. Extend capture, seeding, schema coverage and parity together, then re-enable each tool in the replay allowlist only after its full closure passes. Phase-1 snapshots without those views remain incomplete for these tools; do not backfill from live state.

**Red first:** demonstrate each failure on the merged phase-1 baseline, then green on phase 2:

1. Real source/replay `todos` parity for list/detail/filter/pagination, request/siblings/dependencies/archive/order, all build history, steps/quota/hold/fallback, tags/labels, usage/schedules, ownership and verification head/digest/verdict; later mutation/deletion cannot change the captured result.
2. Real source/replay `open_thread` parity for initial start and restart, team/archive checks, stopped-before-first-run, retry parking/failure windows, prior errors/lessons, routing/work policies, research prerequisites/deduplication and dependencies, including committed effects and failed calls.
3. Ordered views under concurrent writes and time-dependent ownership/quota/retry changes; alternate candidate arguments use complete captured collections and preserve candidate effects. Missing closure, unsupported reads or unrepresentable interleavings yield incomplete, never canned success or a live fallback.
4. Phase-1 snapshot/tool-coverage rejection and phase-2 allowlist admission only after closure parity; run the phase-1 lifecycle/privacy/failure checks against the expanded payload and its bounds.

**Finish line:** each phase proves its own red-to-green assertions with targeted tests plus an isolated running server's real tools, persisted row and harvest; no live-instance writes. This PR provides design evidence only. **Ladder:** the missed prompt inputs are addressed by the production-derived capture contract and planned generation-boundary parity negative controls; executable safeguards land in phase 1 because this round is docs only.
