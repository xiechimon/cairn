# Self-deploy on omarchy

`cairn-self-deploy.timer` runs `scripts/ops/deploy-watch.sh` every minute. The watcher finds the newest first-parent main commit after the deployed one whose required checks (`check`, `pack-smoke`, `e2e-gate`) are all green and runs `scripts/ops/deploy-self.sh <sha>` for it. Both scripts copy themselves into the state directory before running, because the deploy switches the checkout they live in.

For the first upgrade from the idle-gated runner, stage the reviewed bootstrap launcher before running a deploy. The old timer cannot load this fix by itself because it waits for idle before checkout. Set `TARGET_SHA` to a full green main SHA whose diff from the deployed revision is server-only, then run:

```sh
CAIRN_CHECKOUT="${CAIRN_CHECKOUT:-$HOME/Code/AgentProjects/cairn-exec}"
CAIRN_DEPLOY_STATE="${CAIRN_DEPLOY_STATE:-$HOME/.local/state/cairn-deploy}"
export CAIRN_CHECKOUT CAIRN_DEPLOY_STATE
git -C "$CAIRN_CHECKOUT" fetch origin main
mkdir -p "$CAIRN_DEPLOY_STATE"
git -C "$CAIRN_CHECKOUT" show "$TARGET_SHA:scripts/ops/bootstrap-deploy.sh" >"$CAIRN_DEPLOY_STATE/bootstrap-deploy.sh"
bash "$CAIRN_DEPLOY_STATE/bootstrap-deploy.sh" "$TARGET_SHA"
```

The launcher stages the target's runner outside the checkout before execution. That runner still enforces all normal checks and takes the existing deploy lock; the timer can remain enabled. A daemon-affecting bootstrap against a server without lease support refuses rather than interrupting work. After this server-only upgrade, the normal watcher uses the new bounded-drain implementation.

`deploy-self.sh` refuses (exit 2) a SHA that is not on `origin/main`, lacks a green required check, or arrives while an `autonomy-paused` issue is open. It also refuses one that changes the `allowBuilds` block of `pnpm-workspace.yaml`, an install or prepare script in any `package.json`, `.pnpmfile.*` or `.npmrc`; deploy those by hand after review. It waits (exit 75, retried on the next tick) while `~/.local/state/cairn-deploy/hold` exists. Server-only changes preserve both daemons and do not wait for idle steps. Daemon-affecting changes first require `GET /api/server/deploy/lease` to succeed. Every lease request carries the owner token from `${CAIRN_HOME:-~/.cairn}/token` as a Bearer header, read from a header file so it stays out of argument lists and logs, and only when `CAIRN_HEALTH_URL` is a loopback `http://` address ([design](deploy-lease-auth-design.md)). The refusal names what the server answered: `unauthorized (HTTP 401)` with the token cause, `lacks the deployment lease endpoint (HTTP 404)` for an older server, so lease support must first arrive in a server-only release, or `unreachable` when no response arrives within 10 seconds. Shared runtime code, dependency manifests and unknown runtime paths count as daemon-affecting; the server schema table-name registry, its vocabulary test and generated protocol snapshot do not affect the daemon artifact. A run of an orb trial, or anything else that must not see a restart, writes one line naming itself into that hold file and removes it when done.

After rehearsal and build, a daemon-affecting deploy acquires a durable singleton `deploy_lease` row through the owner-only lease endpoint. The row holds its UUID owner, `draining` status and one-hour expiration; all machine claim entry paths recheck it, including pending long polls and the final claim transaction. Existing steps can heartbeat and finish. The deploy waits at most `CAIRN_DEPLOY_STEP_WAIT_SECONDS` (default 1800, maximum 1800) for claimed machine steps to finish, then replaces services. Timeout exits 75 with `starved: steps never idle`, leaves running steps intact, and resumes claims. EXIT cleanup first calls the DELETE endpoint to release the lease and wake pending claim polls, then releases only its owned DB row and reads it back even when the HTTP server failed; interrupted ownership is retained in `lease-owner` for recovery, and expiration prevents an abandoned permanent pause. Every recovery attempt atomically reacquires an owned lease in the DB and runs the same bounded drain check even after the previous attempt resumed claims and removed its owner file; an existing live lease belonging to another deploy is preserved. A resume verification failure exits 3. Runtime eligibility settings never change.

A deploy rehearses the target's migrations on an online copy of the live DB in a scratch worktree, builds web assets and, when affected, the daemon in the live checkout, stops the server and only the affected daemons, snapshots the DB to `~/backups/cairn-server/predeploy/stopped-<time>-<previous sha>.db` (newest 10 kept), starts the server, waits for `/app` 200 and `/api/user/me` 200 or 401 three times in a row, starts the daemon and waits for its machine heartbeat. A failed health check rebuilds and restarts the previous commit (exit 1). When any row differs from the snapshot outside the operational `__drizzle_migrations` and `deploy_lease` tables and the heartbeat columns (`machine.lastSeenAt`, `machine.capabilities`, `autonomy_state.lastEvaluatedAt`), the DB is kept and only code rolls back; if the previous commit is then unhealthy, the run exits 3 with that DB still in place. Without such writes the failed DB moves to `predeploy/failed-<time>-<sha>/` and the snapshot is restored. The current deployment lease owner is reinstated after copying the snapshot and before starting services, so historical pause ownership cannot be revived. A failed rollback exits 3. A run killed mid-deploy leaves `~/.local/state/cairn-deploy/in-progress` with its phase (`building`, `switching`, `restoring` or `restored`); the next run, or `deploy-self.sh --recover`, restores the live DB from the snapshot first when a restore was under way (never after it completed, so writes accepted by the restarted previous build survive) or the DB is missing, then finishes the target if it is healthy or rolls it back. No service starts while `server.db` is missing. A checkout already at the target counts as deployed only with a matching deploy record or a healthy server. There is no `/api/health` endpoint or `vp.mjs doctor`; the server probes are `/app` and `/api/user/me`. A failed SHA is recorded in `~/.local/state/cairn-deploy/failed/<sha>` and never retried; the next green main commit is.

The result goes to `~/.local/state/cairn-deploy/deployed.json` and `~/.cairn/server/deploy.json`: `{sha, previous, result, failed, snapshot, at, host}` with `result` one of `deployed`, `rolled-back`, `rolled-back-code` or `rollback-unhealthy`.

After each record is written, if `~/.local/state/cairn-deploy/notify.sh` is executable (override with `CAIRN_DEPLOY_NOTIFY`), the same JSON is fed on stdin. A missing, non-executable, failing or timed-out notify (`CAIRN_DEPLOY_NOTIFY_TIMEOUT`, default 5s when `timeout` is on PATH) never changes the deploy exit status. There is no webhook; host-local scripts are the only success callback.

When the oldest undeployed main commit landed more than 2 hours ago, the watcher opens the issue `deploy lag: omarchy is behind main` (or comments on it once per main head) with the last bounded drain failure explicitly named as `starved: steps never idle`, or the other recorded reason, and closes it once the deployed SHA equals main. The lookup retains the bot-author filter and quoted lag-title search. A failed close makes the watcher tick fail, so the next tick retries recovery instead of reporting success.

Install from `scripts/ops/systemd/` into `~/.config/systemd/user/`: `cairn-server.service`, `cairn-daemon.service`, `cairn-coordinator.service`, `cairn-self-deploy.service` and `cairn-self-deploy.timer`. Every unit runs from the dedicated clone `~/Code/AgentProjects/cairn-exec`, which only deploys move; lanes work in `~/Code/AgentProjects/cairn` and its worktrees, so a deploy never switches a checkout under them. The server binds `127.0.0.1:8787` and is reached through `tailscale serve`; host-specific settings (proxy, secrets) go in `~/.config/cairn/server.env` or unit drop-ins. The self-deploy service starts without an App token. Each individual `gh` call invokes `~/.cairn/tools/app-token/as-bot.sh`; artifact installs, migrations and builds receive no inherited GitHub token or Git command-auth configuration. Before enabling the timer, install the reviewed `as-bot.sh`, `as-bot-policy.mjs` and `token.mjs` from `scripts/ops/host/tools/app-token/` together into `~/.cairn/tools/app-token/`, retaining the existing private key and App configuration. The policy admits only the exact deploy-lag recovery close command, with an explicit Cairn repository, numeric issue ID and full deployed SHA. Then:

```sh
systemctl --user daemon-reload
systemctl --user enable --now cairn-server.service cairn-daemon.service cairn-self-deploy.timer
```

The Coordinator runs inside `cairn-server.service` (D114), so a deploy needs no unit of its own; see the Coordinator section of `docs/ops/control-plane-omarchy.md`.

Deploy one SHA by hand with `scripts/ops/deploy-self.sh <sha>`; roll back by deploying the previous SHA, or by restoring a `stopped-*.db` snapshot with both units stopped.
