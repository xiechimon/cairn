# Self-deploy on omarchy

Status: the omarchy deployment these units ran was torn down on 2026-11-18 and no host runs the watcher today. The Mac desktop app is the shipped product: its embedded server is packaged by the `desktop-release` workflow, which publishes a `desktop-v*` release on every push whose app sources moved since the last tag, without waiting for `check`/`pack-smoke`/`e2e-gate`. Kept as the reference for re-installing self-deploy on the next deployment host.

`cairn-self-deploy.timer` runs `scripts/ops/deploy-watch.sh` every 5 minutes. The watcher waits for main to settle: it records the main head it first sees in `~/.local/state/cairn-deploy/main-seen` and deploys only once that head is unchanged for `CAIRN_DEPLOY_QUIET_SECONDS` (default 240, so one quiet tick), or once main has been ahead of the deployed commit for `CAIRN_DEPLOY_MAX_WAIT_SECONDS` (default 1800), so a run of merges ships as one restart without starving. It then finds the newest first-parent main commit after the deployed one whose required checks (`check`, `pack-smoke`, `e2e-gate`) are all green and runs `scripts/ops/deploy-self.sh <sha>` for it. Both scripts copy themselves into the state directory before running, because the deploy switches the checkout they live in.

For the first upgrade from the idle-gated runner, stage the reviewed bootstrap launcher before running a deploy. The old timer cannot load this fix by itself because it waits for idle before checkout. Set `TARGET_SHA` to a full green main SHA whose diff from the deployed revision is server-only, then run:

```sh
CAIRN_CHECKOUT="${CAIRN_CHECKOUT:-$HOME/Code/AgentProjects/cairn-exec}"
CAIRN_DEPLOY_STATE="${CAIRN_DEPLOY_STATE:-$HOME/.local/state/cairn-deploy}"
export CAIRN_CHECKOUT CAIRN_DEPLOY_STATE
git -C "$CAIRN_CHECKOUT" fetch origin main
mkdir -p "$CAIRN_DEPLOY_STATE"
git -C "$CAIRN_CHECKOUT" show "$TARGET_SHA:scripts/ops/bootstrap-deploy.sh" >"$CAIRN_DEPLOY_STATE/bootstrap-deploy.sh"
bash "$CAIRN_DEPLOY_STATE/bootstrap-deploy.sh" "$TARGET_SHA"
```

The launcher stages the target's runner outside the checkout before execution. That runner still enforces all normal checks and takes the existing deploy lock; the timer can remain enabled. A daemon-affecting bootstrap against a server without lease support refuses rather than interrupting work. After this server-only upgrade, the normal watcher uses the new bounded-drain implementation.

`deploy-self.sh` refuses (exit 2) a SHA that is not on `origin/main` or lacks a green required check. It also refuses one that may add or change an install hook in a `package.json`, one that changes `.pnpmfile.*`, `.npmrc`, a `package.yaml` or `package.json5` manifest or a `binding.gyp`, and one whose `pnpm-workspace.yaml` may permit a new install script; deploy those by hand after review. Each changed `package.json` is parsed as JSON at both commits: a script whose name contains `install`, `prepare` or `prepublish`, or starts with `pnpm:`, that is new or whose command changed refuses, as does any change to the `pnpm` field, a `scripts` value that is not an object and changed, a manifest that is not a regular file (such as a symlink), or one that does not parse. The guard checks what pnpm runs at install; it does not review the code those scripts, the build or the migration rehearsal execute, which green CI on main vouches for. Removing a hook or changing any other script deploys normally. It parses `pnpm-workspace.yaml` at both commits with the checkout's `yaml` package and refuses when `allowBuilds` gains a `true` entry or stops listing a `false` one, when `allowBuilds` holds anything but booleans and changed, when another top-level key naming builds, scripts, hooks, the pnpmfile or config dependencies changed, when the target uses a merge key, or when either file does not parse. An entry added as `false`, or a `true` entry turned to `false` or removed, permits no install script and deploys normally. The watcher runs the deployed checkout's `deploy-self.sh`, so a change to this guard takes effect only once it is deployed; when the old guard refuses the commit that carries the new one, run the bootstrap launcher above with that commit, which runs the target's own `deploy-self.sh` with the same rehearsal, snapshot and lease. It waits (exit 75, retried on the next tick) while `~/.local/state/cairn-deploy/hold` exists. Server-only changes preserve both daemons but still stop the server, so they take the same deployment lease after the build: no Runner step or Coordinator turn is claimed from then on, and the deploy waits up to `CAIRN_DEPLOY_SERVER_STEP_WAIT_SECONDS` (default 600, maximum 1800) for claimed steps to finish, then restarts the server anyway, since a server restart leaves Runner work running. A server-only deploy whose lease request gets no answer or a 404 restarts the server without a drain; a 401 or 403 refuses as below. Daemon-affecting changes first require `GET /api/server/deploy/lease` to succeed; an older server without that endpoint refuses them, so lease support must first arrive in a server-only release. Every lease request carries the owner token as a Bearer header, read from the `CAIRN_TOKEN` line of `~/.cairn/token` (override the file with `CAIRN_DEPLOY_TOKEN_FILE`; a server that takes `CAIRN_TOKEN` from `~/.config/cairn/server.env` needs that path here). The token goes to `curl` on stdin, never on its command line. The token is sent only when `CAIRN_HEALTH_URL` is a loopback `http://` address. With no token the request is sent without the header, which only an auth-off server admits. The refusal names what the server answered ([design](deploy-lease-auth-design.md)): a 401 or 403 refuses with `server rejected the deployment lease request`, the token file and the cause (not loopback, file missing, no `CAIRN_TOKEN` value, or not accepted); a 404 refuses as a missing endpoint; no response within 10 seconds refuses as `no response to the deployment lease request`. Shared runtime code, dependency manifests and unknown runtime paths count as daemon-affecting. These do not affect the daemon artifact and deploy without stopping the daemon: the server and web apps, the iOS app, the integration test and eval workspace, everything under `docs/` and `.github/`, the top-level `README.md`, `README.zh.md`, `AGENTS.md`, `CLAUDE.md` and `CONTEXT.md`, the deploy scripts themselves, the server schema table-name registry, its vocabulary test and the generated protocol snapshot. The list names only paths that are never bundled into the daemon; anything else, including any path not on it, still restarts the daemon, so a misjudged path over-restarts rather than skipping a needed restart. A run of an orb trial, or anything else that must not see a restart, writes one line naming itself into that hold file and removes it when done.

After rehearsal and build, a daemon-affecting deploy acquires a durable singleton `deploy_lease` row through the owner-only lease endpoint. The row holds its UUID owner, `draining` status and one-hour expiration; all machine claim entry paths recheck it, including pending long polls and the final claim transaction. Existing steps can heartbeat and finish. The deploy waits at most `CAIRN_DEPLOY_STEP_WAIT_SECONDS` (default 1800, maximum 1800) for claimed machine steps to finish, then replaces services. Timeout exits 75 with `starved: steps never idle`, leaves running steps intact, and resumes claims. EXIT cleanup first calls the DELETE endpoint to release the lease and wake pending claim polls, then releases only its owned DB row and reads it back even when the HTTP server failed; interrupted ownership is retained in `lease-owner` for recovery, and expiration prevents an abandoned permanent pause. Every recovery attempt atomically reacquires an owned lease in the DB and runs the same bounded drain check even after the previous attempt resumed claims and removed its owner file; an existing live lease belonging to another deploy is preserved. A resume verification failure exits 3. Runtime eligibility settings never change.

A deploy rehearses the target's migrations on an online copy of the live DB in a scratch worktree, builds web assets and, when affected, the daemon in the live checkout, stops the server and only the affected daemons, snapshots the DB to `~/backups/cairn-server/predeploy/stopped-<time>-<previous sha>.db` (newest 10 kept), starts the server, waits for `/app` 200 and `/api/user/me` 200 or 401 three times in a row, starts the daemon and waits for its machine heartbeat. A failed health check rebuilds and restarts the previous commit (exit 1). When any row differs from the snapshot outside the operational `__drizzle_migrations` and `deploy_lease` tables and the heartbeat columns (`machine.lastSeenAt`, `machine.capabilities`, `autonomy_state.lastEvaluatedAt`), the DB is kept and only code rolls back; if the previous commit is then unhealthy, the run exits 3 with that DB still in place. Without such writes the failed DB moves to `predeploy/failed-<time>-<sha>/` and the snapshot is restored. The current deployment lease owner is reinstated after copying the snapshot and before starting services, so historical pause ownership cannot be revived. A failed rollback exits 3. A run killed mid-deploy leaves `~/.local/state/cairn-deploy/in-progress` with its phase (`building`, `switching`, `restoring` or `restored`); the next run, or `deploy-self.sh --recover`, restores the live DB from the snapshot first when a restore was under way (never after it completed, so writes accepted by the restarted previous build survive) or the DB is missing, then finishes the target if it is healthy or rolls it back. No service starts while `server.db` is missing. A checkout already at the target counts as deployed only with a matching deploy record or a healthy server. There is no `/api/health` endpoint or `vp.mjs doctor`; the server probes are `/app` and `/api/user/me`. A failed SHA is recorded in `~/.local/state/cairn-deploy/failed/<sha>` and never retried; the next green main commit is.

The result goes to `~/.local/state/cairn-deploy/deployed.json` and `~/.cairn/server/deploy.json`: `{sha, previous, result, failed, snapshot, at, host}` with `result` one of `deployed`, `rolled-back`, `rolled-back-code` or `rollback-unhealthy`.

After each record is written, if `~/.local/state/cairn-deploy/notify.sh` is executable (override with `CAIRN_DEPLOY_NOTIFY`), the same JSON is fed on stdin. A missing, non-executable, failing or timed-out notify (`CAIRN_DEPLOY_NOTIFY_TIMEOUT`, default 5s when `timeout` is on PATH) never changes the deploy exit status. There is no webhook; host-local scripts are the only success callback.

When the oldest undeployed main commit landed more than 2 hours ago, the watcher opens the issue `deploy lag: omarchy is behind main` (or comments on it once per main head) with the last bounded drain failure explicitly named as `starved: steps never idle`, or the other recorded reason, and closes it once the deployed SHA equals main. The lookup retains the bot-author filter and quoted lag-title search. A failed close makes the watcher tick fail, so the next tick retries recovery instead of reporting success.

Install from `scripts/ops/systemd/` into `~/.config/systemd/user/`: `cairn-server.service`, `cairn-daemon.service`, `cairn-coordinator.service`, `cairn-self-deploy.service` and `cairn-self-deploy.timer`. Every unit runs from the dedicated clone `~/Code/AgentProjects/cairn-exec`, which only deploys move; lanes work in `~/Code/AgentProjects/cairn` and its worktrees, so a deploy never switches a checkout under them. `cairn-server.service` uses `Restart=always`: a signal from another process (measured on 2026-11-11: a `pkill -f` pattern that also matched the server ended it with exit code 0 and it stayed down 18 hours under `Restart=on-failure`) restarts it after 5 seconds, while `systemctl --user stop` during a deploy still keeps it stopped. The server binds `127.0.0.1:8787` and is reached through `tailscale serve`; host-specific settings (proxy, secrets) go in `~/.config/cairn/server.env` or unit drop-ins. The self-deploy service starts without an App token. Each individual `gh` call invokes `~/.cairn/tools/app-token/as-bot.sh`; artifact installs, migrations and builds receive no inherited GitHub token or Git command-auth configuration. Before enabling the timer, install the reviewed `as-bot.sh`, `as-bot-policy.mjs` and `bot-identity.mjs` from `scripts/ops/host/tools/app-token/` together into `~/.cairn/tools/app-token/`. The policy admits only the exact deploy-lag recovery close command, with an explicit Cairn repository, numeric issue ID and full deployed SHA. Then:

```sh
systemctl --user daemon-reload
systemctl --user enable --now cairn-server.service cairn-daemon.service cairn-self-deploy.timer
```

The Coordinator runs inside `cairn-server.service`, so a deploy needs no unit of its own; see the Coordinator section of `docs/ops/control-plane-omarchy.md`.

Deploy one SHA by hand with `scripts/ops/deploy-self.sh <sha>`; roll back by deploying the previous SHA, or by restoring a `stopped-*.db` snapshot with both units stopped.
