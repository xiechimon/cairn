## Newcomer framing

Someone who installed Cairn today asks the Coordinator for a slide deck, spreadsheet, or document and opens the result in Cairn's right-hand [artifact panel](../design/artifact-panel.md):

- **Where they meet it and why it is there**: today Cairn renders files inside its own tabbed artifact panel beside the chat and lets them pin comments, edit whiteboards, and export HTML/PNG/PDF/original files without leaving the thread; `open-artifact` offers full WYSIWYG editors and richer exports (PPTX, XLSX, DOCX, MP4) for nine artifact types. (verified)
- **What they must already know**: with Cairn's current viewers or a browser-ported editor, only how to talk to the Coordinator. If Cairn embedded `open-artifact`'s daemon (`harness-kit` / `--stdio`), they would meet a second local service (`open-artifact` daemon on `127.0.0.1` + `*.frame.localhost`), a second artifact store on disk (`~/OpenArtifact` or `<workspace>/artifacts/`), and a second comment/Ask flow that stops working when they open Cairn from mobile, remote web, or an in-server Coordinator thread without a local daemon. (derived)
- **Accounts, payments, and keys**: none for local usage — `open-artifact` is Apache-2.0 and local-first (`README.md`, `LICENSE`). Publishing `open-artifact` artifacts to a remote web address adds external infrastructure (a self-hosted VPS with two registrable domains and wildcard DNS/TLS, or a Cloudflare Workers Paid plan starting at $5/month per `docs/hosting.md`). (verified)
- **Where it stores what they give**: Cairn stores files as 10 MiB-capped attachments and tracks versions and comments in the server's SQLite `design_version` and `design_comment` tables; `open-artifact` stores multi-file folders on disk (`project/`, `db/`, `sheet/`, `doc/`, `comments.json`, `history/`, `_blobs/`). (verified)
- **Where they get stuck**: under daemon embedding, a remote or mobile Cairn user cannot load `127.0.0.1:<port>/a/<id>` (`embedUrl`), comments split across two incompatible systems, and multi-file folder artifacts exceed or bypass Cairn's attachment lifecycle. (derived)

## 0. Conclusions

1. **What Cairn is using today**: Cairn runs **neither** `open-artifact` nor `open-design`'s daemon. As documented in [`apps/web/src/vendor-open-design/NOTICE.md`](../../apps/web/src/vendor-open-design/NOTICE.md) and [`docs/design/design-surface.md`](../design/design-surface.md), Cairn vendored and adapted Apache-2.0 source files from `nexu-io/open-design@07258801` (comment bridge, sandbox shim, snapshot bridge, anchor drift ladder, viewport presets, draw overlay, ZIP/handoff helpers, basic file viewers, and server-side Office zip text extraction). On top of those, Cairn's [`ArtifactPanel`](../../apps/web/src/board/artifact/artifact-panel.tsx) lazy-loads standard OSS libraries (`@excalidraw/excalidraw`, `pdfjs-dist`, `docx-preview`, `papaparse`, `shiki`, `marked`, `mermaid` per [`apps/web/package.json`](../../apps/web/package.json)) and persists everything in Cairn's own `attachment`, `design_version`, `design_comment`, and `design_share` SQLite tables. (verified)
2. **Assessment of `open-artifact`**: Technically ambitious and well-factored — 9 interactive web editors, 6 Rust/WASM crates (WebGL2 canvas, Excel formula engine, whiteboard geometry, export zip/PDF/PNG, motion GIF/MOV/flash check, data rules), a clean `window.openartifact` capability contract (`CONTRACT_VERSION = '1.4.0'`), and a documented integration SDK (`@open-artifact/harness-kit`). At the same time, it is 10 days old (`v0.17.0`), ~660k LOC of fast-moving code where the editor packages are private and not published on npm. (verified)
3. **Can Cairn integrate it today?**: Technically runnable on a local Mac host (Cairn already mandates Node `>=22.19`, satisfying Open Artifact's `>=22.18`), **but embedding its daemon (`harness-kit` or `--stdio`) is a poor architectural fit** — it breaks Cairn's in-server Coordinator and remote/mobile clients, splits storage out of Cairn attachments, and introduces a second incompatible comment system. **Recommendation**: keep Cairn's panel and `design_version`/`design_comment` single-path store; build Cairn's already-specified HTML `<section>` **Slides** viewer first while borrowing Open Artifact's Slides authoring skill (and optionally its browser-side `.pptx` export); only if true in-panel WYSIWYG editing is demanded later for Slides or Sheets, port a single editor behind a Cairn browser `CapabilityProvider` (the exact daemon-less pattern used by Open Artifact's own static playground). (derived)

Notes on path (a) and path (c):

- **Why `--stdio` vs `@open-artifact/harness-kit`**: Cairn's daemon, server, and desktop app are all Node/TypeScript, so `@open-artifact/harness-kit@0.17.0` (published on npm) would be used directly rather than `open-artifact harness --stdio` (which exists for Python/Go/Rust hosts per `docs/integrating/non-node.md`). - **Why path (c) works mechanically, and what it costs to maintain**: reading [`website/playground/src/provider/demo-provider.ts`](https://github.com/JimLiu/open-artifact/blob/e1458242772eb2b3e23dc33d1f9fb01d0686fc1d/website/playground/src/provider/demo-provider.ts) confirms every Open Artifact editor talks exclusively to `window.openartifact` (`CapabilityProvider`), allowing even `docs-editor` and WASM `sheets-editor` to run in-browser without a daemon.
