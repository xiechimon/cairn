# Research: bot identity, human co-authorship and human override on GitHub (2026-11-07)

Question. In products and open-source projects where an AI or bot agent writes, opens and merges code on GitHub: (1) when does the bot act under its own identity (GitHub App or bot account) versus as the human (user token), (2) how is the human who instructed the work credited, (3) how does a human override a bot's hold or block? Then: does ian's proposal fit cairn ("work ian instructed carries ian as co-author; anything cairn does on its own uses the `cairnwright` App")?

Labels: measured = read or run first-hand this round; inferred = derived from measured, checkable; guess = the rest. Sources are official docs, source code at the cited path, or the running product. Docs were fetched on 2026-11-07. Cairn code was read from `origin/main` @ `4a14b42bb` (it already contains the G14 draft and hold-label mechanism from #3401, which `review-findings-before-ready-2026-11-07.md` only proposed). The worktree itself is behind main.

## Summary

1. Every product that separates "who acted" does it with a distinct write identity, and then puts the human in a field the bot cannot forge: Copilot writes the requester as co-author, bars the requester from approving, and refuses to mark its own PRs ready or merge them (measured, docs below). Renovate defines "its own commits" by git author email and stops touching a branch someone else edited (measured, source). Dependabot stops rebasing once extra commits appear and takes human commands as `@dependabot` comments (measured, docs).
2. Copilot draws the same line as ian's proposal, at the trigger: a personal automation is attributed to the user who made it, a shared automation to Copilot (measured, docs). So "instructed by ian" versus "cairn on its own" has a direct precedent, and the trigger, not the verb, decides the identity.
3. Spike on the live repo, 2026-11-07 (measured, PR #3409, now closed): with the `cairnwright` installation token, the App converted a PR to draft, marked it ready, added a label, opened a review thread, replied to it and resolved it. Every timeline event shows `cairnwright[bot]` with `actor.type = Bot`. The same operations by cairn today show `xiechimon` (`User`), e.g. `convert_to_draft` and `ready_for_review` on #3401. That is the cause of the five G14 failures: the hold and the override are the same actor.
4. Recommendation: split cairn's GitHub writes by trigger into two token types the compiler can tell apart, run all autonomous writes (hold, draft/ready, labels, thread replies and resolves, status, PR creation, push) as the App, keep human-clicked writes (merge button, anything ian types into cairn) on ian's OAuth token, record co-authorship server-side as a commit trailer, and make "human override" mean "a timeline event whose actor is not the App". Details and touched files in "Fit for cairn".

## Fit for cairn

### What cairn does today (measured, `origin/main` @ `4a14b42bb`)

- One identity for every GitHub write: `githubTokenOrNull` / `teamGithubToken` in `apps/server/src/services/github-connection.ts` returns the team's OAuth App token (scope `read:user repo`, `packages/shared/src/records/github.ts:17-21`). About 15 call sites use it: `pr-watch.ts:396`, `pr-wakes.ts`, `pr-review-findings.ts`, `builds.ts` (merge via `githubMergePull`, `builds.ts:2271`), `autonomous-merge.ts:275`, `ci-loop.ts`, `ci-corrections.ts`, `todos.ts`, `issue-intake.ts`, `merge-gate-github.ts` (commit statuses), `machine-step-token.ts:44` (the git push credential handed to the daemon), `git.ts:313`.
- The G14 hold is `desiredAction` in `apps/server/src/services/pr-review-findings.ts`: label `cairn-review-hold`, `convertPullRequestToDraft`, `markPullRequestReadyForReview`, `removeLabel`, all via that token. The override test is `overridden` in `apps/server/src/lib/github-review-findings.ts:118-124`: any `UnlabeledEvent` for the hold label after the head commit counts as a human override, and the event's actor is never read. Because cairn's own `removeLabel` and ian's removal both appear as `xiechimon`, cairn can read its own action as an override. That is the bug class "decision and override share an identity".
- App identity exists only on the dispatching host, outside the server: `docs/ops/agent-bot-identity.md` says opening PRs and pushing use `as-bot.sh`; "Merging, approving, and label changes … still use xiechimon's gh login". The App has Contents, Pull requests, Issues and Workflows read and write, no webhook, installed on `xiechimon/cairn` only. The private key is read only in host processes and never handed to an agent.
- Co-authorship today lives in host scripts: `as-bot.sh` exports `CAIRN_COAUTHOR`, `sign-commits.sh` and `merge-pr.sh` require `Co-authored-by: xiechimon` on bot commits (measured, `scripts/ops/host/`). The product's own commits use `identity: { name: user.displayName, email: 'cairn@localhost' }` (`apps/server/src/services/local-merge.ts:74`).

### Evaluation of ian's proposal against the prior art

The proposal matches the strongest precedents (Copilot row 1 and 2, Claude action row 3, Devin row 7) in the two choices that matter: an own identity for the bot, and the human credited as co-author. It differs from Copilot in one place it must copy: the human who instructed the work must not be able to satisfy the review requirement for it. Cairn already covers that, because App-authored PRs let ian approve (`agent-bot-identity.md`, Code Owners section). Two things the proposal leaves open, and the prior art answers:

1. Where the boundary sits. Copilot answers it by trigger (personal automation versus shared automation). Cairn's version: a write is "ian's" when it is the direct result of a click or message by ian in the cairn UI or chat in that moment; it is "cairn's" when a scheduler, sweep, reconciler, wake or agent step produced it. Inference from rows 1 and 2.
2. How the human override is expressed. Every product above makes the override an event with a human actor (comment command, checkbox edit, label, extra commit, closing the PR) and has the bot compare the actor with itself. Cairn should do the same: override means a timeline event for the hold label, the draft or ready state, or a thread resolve whose actor login is not `cairnwright[bot]`. This is only reliable once cairn's own writes stop using ian's token.

### How co-authorship is recorded

- Commit: append `Co-authored-by: <ian name> <id+login@users.noreply.github.com>` server-side, when the step was started by a human trigger, at the commit step in the daemon or at the push, not by prompting the model. Reason: Claude's action leaves it to the prompt (row 3), Copilot does it in the platform (row 1); an enforceable record needs code, and the repo already has a `commit-author` workflow that can verify it. The identity comes from the team's GitHub connection (login via `githubUserLogin`; the numeric id needs one more field, inferred). Work cairn starts on its own carries no human co-author trailer; the App is the only author. For credit direction, follow Copilot (human co-authors the bot's commit), not Codex CLI (bot co-authors the human's commit).
- PR: author is the App; ian is requested reviewer (and optionally assignee), the body says who requested the work. Copilot and OpenHands both use the reviewer request as the "please look" signal.
- GitHub shows the trailer's person only for emails tied to an account, so the noreply form with the numeric id must be used (docs, row 14).

### How a human overrides, concretely

- Hold on: App adds `cairn-review-hold` and converts to draft (as today, under the App identity).
- Override: ian removes the label, marks the PR ready, or resolves the thread, in GitHub or in the cairn UI. `overridden` becomes "an `UnlabeledEvent`, `ReadyForReviewEvent` or thread resolution after the current head whose actor is not `cairnwright[bot]`". The GraphQL timeline items expose `actor { login __typename }` for these events (inferred from the REST fields and the spike; verify with one GraphQL query before coding).
- Cairn's own `removeLabel` or `markReady` after the findings clear are App events and never count as override.
- Loop guard: Devin's docs warn "All bots" can loop (row 7); the filter that ignores the App's own events is the same guard.
- Mergify stays the second line: `#review-threads-unresolved = 0` in `queue_conditions`, plus `@mergifyio dequeue` as the manual stop. `-author = cairnwright[bot]` in the default queue already uses identity.

### Making the mistake impossible (project rule: a repeated error gets a constraint, not another rule)

The G14 breakage recurred five times, so a convention is not enough. Introduce two branded token types, `AppToken` and `UserToken`, returned by distinct functions, and make every write function in `apps/server/src/lib/github*.ts` accept exactly one of them in its signature. A lint rule (biome `noRestrictedImports`, as `biome.json` already does for locked seams) forbids calling `githubTokenOrNull` from a file that performs writes. The G14 functions then physically cannot be given ian's token, and the merge function cannot be given the App's. (inferred: this follows from the TypeScript design; the biome mechanism exists in the repo, to be confirmed against `biome.json` when implementing.)

### Risks and failure modes to test first

- Key custody. The server holding an App private key widens a boundary the ops doc explicitly keeps narrow ("never handed to an agent"). The alternative is a small server-side mint endpoint on the host that returns a one-hour installation token and never exposes the key, which keeps the key where it is today (inferred). Needs ian's decision.
- Multi-repo and other teams. The App is installed only on `xiechimon/cairn`. For any other repository the App token fails; the fallback must be the user token with an explicit "unattributed: written as the connected user" marker in the PR panel, not silent (the Claude FAQ documents the same silent identity change as a pitfall, row 3).
- Permissions. Commit statuses need a new permission; any GraphQL mutation not yet exercised (for example `addLabelsToLabelable` on `labelableId`) needs one run as the App, like the spike did for the others.
- Stale override events. The existing logic ignores events before the head commit; keep that, and add a test where the App removes the label (no override) and where ian removes it (override).
- Human actions made through cairn's UI with the user token still look like ian, which is correct. The danger is only a code path that should be autonomous using the user token; the branded types are the defence.
- Squash-merge attribution is unchanged: the `commit-author` rules and `merge-pr.sh` constraints in `agent-bot-identity.md` still apply.
