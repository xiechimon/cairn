# GitHub push capability: how runner systems avoid impossible work

Date: 2026-11-27. Method: read primary docs and the pinned GitHub GraphQL schema in this session; each row says what was read first-hand (observed) or derived from it (inferred). The repository incident motivating this work was a Mac mini runner without a GitHub login: the worker finished, then the branch could not be pushed.

## Prior art

| Source | How it does it | Trade-offs | Evidence |
|---|---|---|---|
| GitHub Actions self-hosted runners | Jobs choose runners through labels and runner groups. Labels are static capability declarations; the scheduler does not prove that a declared capability still works. | Simple routing, but a wrong or stale label still sends work to a machine that fails later. | observed: https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/using-labels-with-self-hosted-runners |
| Buildkite agents | Agents advertise tags such as `docker=true`; pipeline steps target those tags. Tags can come from the host or cloud metadata. | Good capability-routing model, but tags are still declarations, not a live permission check. | observed: https://buildkite.com/docs/agent/v3/cli-start#setting-tags (read through the text mirror because the HTML page returned 403) |
| Mergify merge queue | Mergify orders already-created pull requests and uses CI checks as the admission evidence before merge. | This is a merge-queue analogue, not machine routing: it validates the artifact, not the executor. It reinforces the pattern that admission should use fresh evidence rather than hope. | observed: https://docs.mergify.com/merge-queue/ |
| GitHub GraphQL `Repository.viewerPermission` | The schema says `viewerPermission` is the user's permission level on a repository and is null for a GitHub App. `ADMIN`, `MAINTAIN` and `WRITE` explicitly include push; `READ`, `TRIAGE`, `MODERATE`/`TRIAGE_PLUS` do not. | Exactly answers “can this account push?” without a destructive write probe. It requires a user token on the runner, which is the same identity the worker's `git`/`gh` commands use. | observed: https://docs.github.com/public/fpt/schema.docs.graphql (`viewerPermission`, `RepositoryPermission`) |
| GitHub CLI `gh auth status` | Tests each known account's authentication state and exits 1 when the selected host/account has auth issues; `--hostname` narrows the check. | A login check alone is not enough for per-repository permission, but it is the cheap prerequisite and it notices login/logout/account-switch changes. | observed: https://cli.github.com/manual/gh_auth_status |
| OWASP Secrets Management cheat sheet | CI/CD secrets should be centrally controlled, short-lived where possible, authenticated and audited; avoid spreading secrets casually. | The probe must not copy or transmit tokens. It reports only a permission enum and a timestamp; the token stays inside `gh` on the runner. | observed: https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html |
| Cairn's own git credential path (this repository) | `apps/daemon/src/step-prompt.ts` tells workers on GitHub projects to use the machine's own `git`/`gh` for commit, push and PR; `apps/daemon/src/step-git-tools.ts` uses per-step credentials only for daemon-run git operations, with machine credentials as fallback. | Therefore server-issued git credentials do not remove the need for the runner's GitHub login on GitHub-backed projects. | observed: `apps/daemon/src/step-prompt.ts`, `apps/daemon/src/step-git-tools.ts`, `apps/daemon/src/step-closing-git.ts` |
| Existing Cairn capability routing | Machines report capabilities in presence, the server stores them on the machine row, and claim/routing reject ineligible machines instead of assigning impossible work. | This is the natural local pattern: dynamic machine-reported capability plus server-side fail-closed routing and a queue explanation. | observed: `docs/research/capability-routing-2026-11-06.md`, `apps/server/src/services/machine-routing.ts` |

## Pattern that fits Cairn

Use GitHub Actions/Buildkite's capability-routing shape, but make the capability evidence-based rather than a static label. The runner is the only place that holds the identity whose permission matters, so it must probe. The server is the only place that knows all pending work and alternative machines, so it must gate. The user only needs the outcome: the task waits, naming the computer that cannot push and the login action.

A destructive “try pushing a ref” probe is not acceptable: it writes to user repositories and can trip hooks. GraphQL `viewerPermission` is the correct read-only check. `ADMIN`, `MAINTAIN` and `WRITE` are push-capable; every other state, a missing repository, missing login, missing report, stale report or probe error is fail-closed for assignment. Fail-closed is right here because the cost of a false negative is a queued task, while the incident's false positive costs an hour of agent work.

## Recommendation

1. The server includes the team's active GitHub-backed repository refs in the machine presence response. This adds no token or secret to the wire.
2. The daemon probes those repos with `gh auth status --hostname github.com` plus `gh api graphql` for `repository(owner,name){viewerPermission}`; it caches positive and negative results for a short TTL and invalidates them when the active GitHub login fingerprint changes.
3. The daemon reports only `{ repo, state, checkedAt }` inside machine capabilities. States: `write`, `no-write`, `unauthenticated`, `unknown`. No token, scope list, account name or API response body crosses the wire.
4. The server treats a GitHub-backed `build`/`session`/`merge`/workspace `verify` step whose route allows branch push as requiring `write` for that exact repo. Missing, stale, non-write or unknown reports make the machine ineligible. Hosted and local repositories are unchanged; `plan` and `review` are unchanged.
5. Queue projection maps that rejection to one plain blocked state naming the machine and telling the user to run `gh auth login` on it (or grant that login access to the repository). This follows the existing queue-refusal surface rather than a new notification system.
