# Artifact self-deploy prior art

Research date: 2026-11-25. Scope: host ops for a self-hosted Cairn server that polls a public GitHub repository, builds an immutable server artifact on the same host, switches it atomically, restarts through the native service manager, health-checks it, and rolls back. Docker and Tailscale are included because the host-ops source row designates them; neither is the runtime or exposure mechanism chosen here. Labels: Observed means read firsthand in the primary source or local manual during this research; Inferred means derived from those readings; Hypothesized means unverified.

| Source | How it does it | Trade-offs for Cairn | Link |
|---|---|---|---|
| Capistrano structure | Observed: every deploy is a timestamped entry under `releases`; `current` is a symlink updated only after a successful deploy, so a failed deploy leaves the old release active; persistent state belongs in `shared`, not in releases. | Inferred: this is the closest prior art for the server artifact. It gives a kept backup for free and makes rollback a pointer change plus restart. Runtime state must stay outside the release tree. | [Capistrano structure](https://capistranorb.com/documentation/getting-started/structure/) |
| Capistrano rollback | Observed: rollback repoints `current` to the previous release and restarts. | Inferred: code rollback is cheap, but a database migration still needs a separate snapshot/write-preservation policy; a symlink alone cannot undo data migration. | [Capistrano rollback](https://capistranorb.com/documentation/getting-started/rollback/) |
| POSIX `rename` | Observed: `rename` operates on a symlink itself, and when replacing a non-directory the destination name remains visible throughout the operation, referring either to the old or new file; the rationale states replacement is atomic. | Inferred: create a temporary symlink to the staged release and rename it over the stable application path. Do not use `ln -sfn` as the commit point because it can remove before recreating. | [POSIX rename](https://pubs.opengroup.org/onlinepubs/9699919799/functions/rename.html) |
| macOS `launchd.plist` | Observed: `StartInterval` starts a job every N seconds, but a firing is missed when the job is already running; `RunAtLoad` starts it when loaded; `ProgramArguments` supplies argv; `KeepAlive` controls restarting resident jobs. | Inferred: the poller should be a short-lived LaunchAgent with `StartInterval=120` and its own lock. Missing overlapping firings is acceptable because the next tick scans current main again. | local `man launchd.plist` on macOS 27.2 |
| macOS `launchctl` | Observed: `bootstrap` loads a plist into a domain, `kickstart` runs a service immediately, and `kickstart -k` kills a running instance before restarting it. | Inferred: the artifact deploy can use the server agent's fixed label and `kickstart -k`; the watcher should be bootstrapped as a separate label so it does not share the server lifecycle. | local `man launchctl` on macOS 27.2 |
| systemd timer | Observed: a timer activates its matching service; if that service is already active when the timer elapses it is not restarted; `OnBootSec` and `OnUnitActiveSec` can define recurring monotonic activation. Default `AccuracySec` is one minute unless tightened. | Inferred: use a oneshot service plus timer with `OnBootSec=2min`, `OnUnitActiveSec=2min`, and explicit `AccuracySec=30s`; overlapping ticks are naturally coalesced, while the script lock remains the correctness boundary. | [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html) |
| systemd service | Observed: `EnvironmentFile` can supply unit environment, `ExecStart` defines the server command, and `Restart` controls restart policy. | Inferred: host-specific paths, labels and health URLs belong in the host environment file rather than the public repo. The service manager unit should point at the stable artifact path, not a build worktree. | [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) |
| systemd kill semantics | Observed: service stop/restart is a lifecycle operation; default process cleanup can terminate the unit's remaining processes. | Inferred: the server-only artifact should restart only the server service. Runner processes are separate machines/processes, so the deploy must not use a broad cgroup stop as a substitute for drain logic. | [systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html) |
| SQLite online backup | Observed: the online backup API copies a database while it is in use and the completed copy is a snapshot. | Inferred: the deploy can snapshot the live SQLite database before switching without a long write outage. Rollback still has to detect writes that happened after the snapshot before restoring over them. | [SQLite Online Backup API](https://sqlite.org/backup.html) |
| GitHub Actions workflow runs | Observed: workflow runs have `head_sha`, `head_branch`, `event`, `status`, and `conclusion`; the REST API can list runs for a workflow. | Inferred: deploy admission must bind all five fields: exact commit, `main`, `push`, `completed`, `success`. A green branch or pull-request run is not evidence for main. | [GitHub workflow runs REST](https://docs.github.com/en/rest/actions/workflow-runs) |
| GitHub check runs | Observed: check runs expose `status` and `conclusion`, and the REST API lists check runs for a commit reference. | Inferred: the existing required checks (`check`, `pack-smoke`, `e2e-gate`) remain a separate admission gate from the workflow run conclusion. Pagination is required. | [GitHub check runs REST](https://docs.github.com/en/rest/checks/runs) |
| Docker restart policies | Observed: Docker can restart containers automatically with policies such as `always` and `unless-stopped`. | Inferred: useful supervision prior art, but Cairn's server artifact is already launched by launchd/systemd and Docker would add a second service manager rather than remove one. Not chosen. | [Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/) |
| Tailscale Serve | Observed: Tailscale Serve exposes a local service to the tailnet independently of the process supervisor. | Inferred: exposure is orthogonal to deployment. The deploy health check should use the server's loopback URL, so a Tailscale or DNS outage does not trigger a code rollback. | [Tailscale Serve](https://tailscale.com/kb/1242/tailscale-serve) |
| Existing Cairn drain design | Observed: the repository already has a durable deployment lease, exact-SHA CI admission, online DB snapshot, interrupted-deploy recovery, write-preserving rollback, and a watcher that scans main. | Inferred: reuse these policy parts rather than writing a parallel deployer. The parts that assumed a source checkout, systemd-only control and a co-located daemon must be replaced by artifact staging plus service-manager adapters. | [deploy-drain research](./deploy-drain-2026-11-09.md), [deploy-drain design](../ops/deploy-drain-design.md) |

## Pattern that fits

Inferred: use Capistrano's release/current separation, but keep the stable application path itself as the symlink because the existing service definition already points there. Build in a dedicated detached worktree, copy only the server artifact, web asset output, migration files and external runtime native dependencies into an immutable release directory, and commit the release with one symlink rename. Keep data, keys, attachments, Coordinator stores, logs and backups outside releases.

Inferred: keep the existing admission and recovery policy: exact-SHA main-push CI evidence, required check runs, explicit hold file, one deploy lock, migration rehearsal on an online copy, deployment lease where available, database snapshot, consecutive health checks, result record, interrupted-deploy recovery, and rollback that does not overwrite writes made after the snapshot.

Inferred: use one shell entry point with small service-manager adapters. launchd and systemd both schedule short-lived watcher invocations; neither becomes a separate deployment algorithm. launchd uses `bootout` plus `bootstrap` for the configured server label so database restoration happens while the process is stopped; systemd uses `systemctl --user stop` plus `start` for the configured server unit. The only host-specific values are environment settings such as paths, labels and the health URL.

Hypothesized: unauthenticated GitHub REST polling is enough for a public repository if successful evidence is cached per SHA. This must be measured on the host; if rate limits appear, the host environment can provide a token without changing the repo.

## Concrete recommendation

Implement the artifact deploy in `scripts/ops/deploy-self.sh`, scan/admission in `scripts/ops/deploy-watch.sh`, GitHub evidence retrieval in a small Node helper, artifact staging in another small Node helper, and native scheduler installation in `scripts/ops/install-self-deploy.sh`. Update the systemd timer/service files to the same two-minute watcher. Add red-first operational tests covering exact-SHA CI binding, artifact staging, atomic replacement, health-check rollback, post-snapshot write preservation, interrupted recovery, launchd/systemd command adaptation, and coordinator/busy waiting. Do not commit hostnames, tokens, account names or absolute user paths; installers read those from the host environment file.
