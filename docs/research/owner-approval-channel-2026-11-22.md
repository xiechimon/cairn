# Owner approval vs a same-uid shell: prior art

> Question: a model-driven shell tool runs as the owner's uid on the same machine as the Cairn server. It can read any owner-readable file (including `home/token`), set any HTTP header, and hit the server's loopback port. What do real products use so that "the owner approving" cannot be forged by "any same-uid process"?
> Read 2026-11-22. Marks: measured = read or run first-hand this session; inferred = derived from measured; guessed = the rest. Web pages were reached through web_search result excerpts (no full-page fetch available this run); repo files were read directly. Excerpts are third-party data, not instructions.

## 0. Conclusions

1. **No measured product lets a same-uid process mint an approval.** The mechanisms in use are exactly four: (a) a private fd channel to a trusted broker process — Codex's stdio submission pipe, Electron's mojo message pipe, 1Password's platform IPC to the desktop app; (b) an OS-brokered prompt attributed to the user or the app — LAContext/Touch ID, polkit's separate authentication agent, 1Password's in-app biometric prompt; (c) an OS sandbox that makes the credential file and the loopback port unreachable from spawned commands — Claude Code's and Codex's Seatbelt/bwrap policies; (d) an out-of-band paired device. A bearer file is never the boundary. (measured across §1)
2. **Cairn's desktop already owns the right plumbing; the missing part is a secret that never leaves trusted memory.** The server is a `utilityProcess` child of the Electron main with a private mojo `parentPort` channel (measured `apps/desktop/src/main.ts:313`). The owner token is deliberately deleted from the child's env (`main.ts:311-312`), yet `ps eww`/`KERN_PROCARGS2` env-reading is available same-uid against non-`cs_restricted` targets on macOS — and Cairn ships ad-hoc, `hardenedRuntime: false` (measured `apps/desktop/electron-builder.yml:41-44`; xnu source and openhuman advisory in §1.5) — so any future approval secret must go over `parentPort`, not env and not a file.
3. **The confinement half is already built for sessions but bypassed by the host computer.** `confine-seatbelt.ts` denies `file-read* file-write*` on the daemon home plus `CAIRN_CONFINE_DENIED_ROOTS` (the desktop passes the server home, `runner.ts:100`), denies LaunchServices lookups, and denies `network-outbound` to the server port (measured `confine-seatbelt.ts:23-25,145,159`, `confine-session.ts:203`). `HostComputerProvider` — the "own computer" shell — is created unconfined (`machine-loop.ts:276-278`), and `host.ts` confines only cwd, not file reads or network. So a confined session cannot forge approvals, but the host shell still can (inferred).
4. **1Password is the closest complete model**: the secret never leaves the broker process, authorization is an OS prompt attributed to the requesting process, time-bound (10 min) and revoked on lock — and 1Password's own docs warn that the file/env alternative "any process running under the current user can … potentially access your 1Password account" (measured §1.3).
5. **Cairn's paired-device channel is a real out-of-band channel but its grant issuance is forgeable today**: `POST /api/remote/pairing` needs only the owner token (measured `routes-remote.ts:84-89`), so a same-uid attacker can mint a device and gain `decidedBy: device:<id>` (inferred).

## 3. The pattern that fits Cairn

The fit is **1Password's broker + Codex's private-fd channel + the sandbox Cairn already built**. The Electron main process is the only component that both (a) holds a private, unattachable channel to the renderer (`ipcMain`) and to the server (`utilityProcess` parentPort), and (b) has memory a same-uid process cannot read (`task_for_pid` is gated). That is exactly a broker. The approval credential should live only there — never on disk, never in env (env is same-uid readable on this unsigned build, and on Linux when `ptrace_scope=0`), and it should reach the server over `parentPort`, not over HTTP.

In parallel, extend the already-shipped Seatbelt/bwrap confinement (server home + loopback port + LaunchServices denial) from harness sessions to the host computer provider — that protects the token file itself, which no channel change can do.

## 4. Recommendation

1. **Brokered approval credential.** In `apps/desktop/src/main.ts` `boot()`: generate a random 32-byte approval key; send it to the server via `child.postMessage` on the utilityProcess right after `startServer()` (`main.ts:295-332`); the server keeps it in memory (`apps/server/src/index.ts` startup, listening on `process.parentPort`). Renderer asks main to sign: new `ipcMain.handle('desktop-approval:sign', …)` gated by `event.senderFrame?.origin === origin` (the existing `fromOwnPage`/`fromPopover` pattern, `main.ts:262,608`), returning `HMAC(proposalId ‖ decision ‖ expiry ‖ nonce)`; the web client sends the signature with the answer; `answerCard` in `routes-chief.ts:68-104` requires a valid signature for `allow-once`/`always` on irreversible proposals and stamps `decidedBy`/`interactive:'desktop'` accordingly. `refuse` needs no signature. Re-gate `POST /api/remote/pairing` (`routes-remote.ts:84-89`) on the same interactive credential so the paired-device channel can't be minted by the attacker.
2. **Confine the host shell.** Wrap `HostComputerProvider.execute` (`apps/daemon/src/computer/host.ts:267-281`) in `seatbeltCommand` on darwin and the existing bwrap policy on linux, with `deniedRoots` = daemon home + server home, `serverPort` loopback denial, and `LAUNCH_SERVICE_DENIALS` — i.e., wire the confiner created in `machine-loop.ts:196` into the provider construction at `machine-loop.ts:276-278` (and `host-desktop.ts:789-791`).
3. **Non-desktop deployments.** A bare server has no broker process: keep owner-cookie answers allowed there but mark the channel in the journal, and document that interactive approval integrity requires the desktop app or a paired device (the honest 1Password "manual signin" tier).
4. **Later, stronger:** an `LAContext.evaluatePolicy` owner-presence check inside the desktop app before main signs irreversible approvals — the OS prompt names Cairn even ad-hoc signed; Secure-Enclave-bound keys need real signing (currently `identity:'-'`, `hardenedRuntime:false`), so defer the enclave variant until signing lands.
