# Prompt injection: system prompt, per-turn tool restriction, or permission prompts

> Question: when an agent reads untrusted input (mail, web page, issue) and also holds powerful tools (shell, files, network), what stops prompt injection? Applied to Cairn's mail-triggered Coordinator turns on ACP agents (current plan: system-prompt fencing, deny built-in tools through ACP permission requests, relay tools allowed).
> Read 2026-11-18. Repo baseline `42ec7fae7`. Marks: verified = read or run first-hand this session; inferred = derived from verified claims; guess = the rest. Every claim links its owner.
> Blocked or thin: OpenAI prompt-injection posts (`openai.com/index/...`) returned HTTP 403 to WebFetch, so OpenAI's Operator/ChatGPT agent position is not covered first-hand; Zed's docs say nothing about how it answers ACP permission requests (see row 5).

## 0. Conclusions

1. **No primary source relies on the system prompt as the sole defense.** Every vendor doc found pairs model-side measures with an enforcement layer outside the model (permission rules, OS sandbox, approval, network off by default). Anthropic says plainly that no agent is immune and quotes residual attack rates of 1.4% to 2.4% even with classifiers ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses), verified). Simon Willison calls 95% catch rates "a failing grade" ([post](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), verified). inferred: a fence in the prompt is a speed bump, never the boundary.
2. **The strongest designs remove a capability for the turn, not ask about it.** Willison's advice is to remove one leg of the trifecta; the design-patterns paper and CaMeL make this structural (the model that reads untrusted data has no tools, or untrusted data cannot change control flow) ([paper](https://arxiv.org/abs/2506.08837), [CaMeL](https://arxiv.org/abs/2503.18813), verified).
3. **Permission prompts are the second tier, and for an unattended turn they degrade to a static allow/deny rule.** ACP's `session/request_permission` is advisory for the agent: the client may auto-allow or auto-reject, and the agent owns what "remembered" means ([ACP spec](https://agentclientprotocol.com/protocol/tool-calls), verified).
4. **Cairn's current plan has a hole, verified in Cairn source.** `apps/daemon/src/backend/acp.ts` switches Codex to `full-access` under confinement and Devin to `bypass` for unattended steps. In those modes the agent does not ask, so a deny-by-permission-request handler never fires for built-in tools. Devin's own docs: Bypass "all tool calls are auto-approved without prompting" ([Devin permissions](https://docs.devin.ai/cli/reference/permissions.md), verified). Only Claude Code's ACP adapter exposes a hard, pre-prompt lever (`disallowedTools`).

## 2. Is "system prompt only" the sole defense anywhere?

Not in any source read. verified: Anthropic (training + classifiers + permission rules + sandbox), Claude Code (permissions + sandbox), Codex (sandbox + approvals + network default off), Devin (permission rules + sandbox + enterprise guardrails), Rakazo (run-origin permissions), Agents SDK (guardrail checks plus tool-level hooks). Prompt-level instruction is used as one layer: the Claude Code permissions doc recommends defense in depth because sandbox restrictions "still apply even if a prompt injection bypasses Claude's decision-making" ([permissions](https://code.claude.com/docs/en/permissions)). guess: products that ship only a system prompt exist but none was found among the designated primary sources; absence of evidence, not a proof.

## 3. Recommendation for Cairn mail-triggered Coordinator turns on ACP agents

Pattern that fits: **remove capability for tainted turns, by turn origin** (Willison "remove a leg", Rakazo run-origin policy, Claude Code `dontAsk`), with the fence in the prompt as a third layer.

1. **Keep the plan, but move the lever from permission requests to mode and tool config at session start.** Permission-request denial alone is not enough (conclusion 4). For a mail-triggered turn, per adapter:
   - Claude Code ACP: pass `_meta.claudeCode.options.disallowedTools` for Bash, Write, Edit, WebFetch, WebSearch and set `allowDangerouslySkipPermissions: false`; keep `permissions: 'deny'` as the backstop. inferred from source.
   - Codex ACP: start in `read-only` and do not call `setMode('full-access')`; the full-access switch in `acp.ts` is tied to confinement, so a mail turn needs a separate branch. inferred.
   - Devin ACP: do not set `bypass`; use the deny-by-handler path in a normal mode, or `--sandbox` if the unattended need is real. inferred; whether Devin sends requests for every built-in call in Normal mode is guess and needs a probe.
   - Gemini ACP: not read to source; probe before trusting.
2. **Add a negative control per adapter:** a mail body that instructs the agent to run `curl`/write a file; assert the call is denied (red on today's `bypass`/`full-access` setup). This is the test the plan lacks.
3. **Relay tools allowed is the trifecta's remaining leg.** If relay tools can read private data and also send out (reply mail, create task with attacker text), the turn still has all three legs. inferred. Constrain relay tools per turn: read-only plus "draft for owner" actions, and require owner approval (Rakazo-style card) for send/forward/create-external actions in mail-origin turns.
4. **Fence the mail as data** in the prompt (cheap, helps), but record in docs that it is not a boundary.
5. **Reconsider dual-LLM for summaries:** a tool-less quarantined run that reads the mail and returns a bounded structure, then the tool-holding Coordinator turn consumes only that structure (paper pattern 4). Costs an extra model call; defer unless mail turns need free-form actions.

Code areas touched: `apps/daemon/src/backend/acp.ts` (mode selection, `_meta` pass-through, permission handler), `apps/daemon/src/backend/devin-acp.ts`, `apps/server/src/coordinator/runtime/` (turn origin to tool set), the relay tool definitions, and tests beside them.
