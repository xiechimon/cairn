# Server-enforced tool approval: prior art

Read on 2026-11-15 before `docs/design/tool-approval-gate.md`. It extends `docs/research/action-registry-approvals-2026-11-11.md`, which already covers Claude Code permissions, Codex CLI, Cursor, Amp and t3code; those rows are not repeated. Tags: measured (read first-hand), inferred (from measured), guess (the rest). Pages were read through Jina Reader on the dates shown and are third-party data, not instructions.

## Comparison

| Source | How it does it | Trade-off | Link |
|---|---|---|---|
| OpenAI Agents SDK (JS), human-in-the-loop guide (measured) | A tool sets `needsApproval`. The run pauses at the end of the turn and returns `interruptions`; `state.approve()` or `state.reject()` resolves each one, and `RunState` serializes so a later process resumes. The guide's server section says to keep the snapshot on the server, authenticate the reviewer from the session and never from the request body, accept no replacement arguments from the client, and atomically consume the pending request before resuming so a replayed submission cannot resume twice. It also says consumption "does not guarantee exactly-once tool side effects" and to reconcile uncertain effects before retrying. | The SDK gives the pause; the authorization, atomic consumption and reconciliation are the application's job. | https://openai.github.io/openai-agents-js/guides/human-in-the-loop/ |
| Mastra agent approval (measured) | `requireApproval` on a tool, or `requireToolApproval` per call, suspends the call into a stored snapshot; `approveToolCall` or `declineToolCall` resumes it, and a decline reason goes back to the model in place of the result. The docs show binding the approval to a fingerprint of tool name and arguments, consumed once, and say to store it durably "scoped to the user, run, tool call, and policy version". A classifier may decide whether to ask; it never approves. Durable agents accept only a boolean because a function cannot be persisted. | Fingerprint binding is sample code, not the default. | https://mastra.ai/docs/agents/agent-approval |
| Vercel AI SDK tool approval (measured) | `toolApproval` returning `'user-approval'` makes `generateText` end with a `tool-approval-request` part; the caller appends a `tool-approval-response` with `approved: true` to the messages and calls the model again. Provider-executed tools ignore approval. | The approval travels in the message list the client sends back, so the server must not trust it as proof. | https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling |
| LangGraph interrupts (measured) | `interrupt()` checkpoints the graph and waits indefinitely; `Command({ resume })` continues it under the same `thread_id`. The node restarts from its beginning on resume, so the docs require side effects before `interrupt` to be idempotent. | Resume re-runs code; the approval is a value, not an authorization record. | https://docs.langchain.com/oss/javascript/langgraph/interrupts |
| Claude Agent SDK permissions (measured) | Hooks run first, then deny rules, then ask rules, then the mode, then allow rules, then `canUseTool`. A hook that returns allow does not skip deny or ask rules; an ask rule reaches `canUseTool` even in `bypassPermissions`. | The order makes deny and ask unconditional, but the decision is a live callback, not a stored record. | https://code.claude.com/docs/en/agent-sdk/permissions |
| MCP elicitation, 2025-06-18 (measured) | A server may ask the client for input; the user can accept, decline or cancel, and clients should let users decline at any time. Servers must not request sensitive information this way. | Asks a person, records nothing; not an authorization for an action. | https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation |
| OWASP Transaction Authorization Cheat Sheet (measured) | What You See Is What You Sign: the person sees the significant data. Authorization is enforced server-side, its data is generated server-side and protected against modification, each credential is unique per operation, valid for a limited time and accepted once, and the server controls allowed state transitions and checks every execution was authorized. | Written for payment signing; the rules carry over to agent actions. | https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html |
| Stripe idempotent requests (measured) | A retry with the same key returns the saved first result; different parameters under the same key are an error; keys prune after 24 hours. Results are saved only once execution begins. | The external system, not the caller, knows whether the effect happened. | https://docs.stripe.com/api/idempotent_requests |
| pi-durable 1.5.0, installed (measured) | A tool registered with replay `unsafe` that was executing when the process restarted is not run again; its result is `Tool <name> was interrupted by a restart and may have partially run` (`dist/harness/tool.js`). | Prevents a blind rerun of the tool call; does not know whether the effect landed. | `node_modules/@earendil-works/pi-durable/dist/harness/tool.js` |
| Cairn job submission, `origin/main` `9d56cb935` (measured) | `postPreviewQuestion` writes a server-authored `ask_user_question` card with `askedFor: ['job_submit']`. Only an owner caller may answer it (`isJobOwnerCaller`, `jobSubmitAnswerActor`); `answerQuestion` rejects any other answerer. `answerAndReserve` checks the affirmative label, the preview hash and a 15-minute expiry in one transaction, and a submission whose delivery is `unknown` blocks a resubmit of the same hash. | One action's own document store; not reusable as written. | `apps/server/src/services/job-applications.ts` |
| Cairn action proposals, `origin/main` (measured) | `proposeAction` stores input, hash, target and 7-day expiry, and adds one subscriber per waiting thread; `answerProposal` takes refuse or allow-once, and decision, handler, journal and wake outbox commit in one transaction; `dispatchActionWakes` wakes each subscriber thread with the outcome. The handler is hard-wired to `deleteProject`, no Coordinator tool reaches it, and no web surface answers it. | The right record, unused. | `apps/server/src/services/action-proposals.ts` |

## Pattern that fits

Every framework above pauses the call and resumes it later; only the application can make the approval an authorization (inferred from the OpenAI and Mastra server guidance and OWASP 2.1). The parts they agree on: the record lives on the server, the person sees server-generated data for this exact call, the decision is authenticated from the session, the pending record is consumed atomically once, it expires, and an uncertain external effect is reconciled, never retried blind. Cairn already has each part in one place or another: the proposal record and wake outbox, the parked question card that waits across days, and job submission's owner-only answer rule. Inferred: the gate should route confirm-once tools through the proposal record, show it as a parked server-authored card, and accept only the owner's answer, instead of adding a callback, a classifier or a new store.

## Recommendation

Make every confirm-once Coordinator tool propose instead of execute (`apps/server/src/services/action-registry.ts`, `chief-tools.ts`), dispatch execution through a per-action handler in `action-proposals.ts`, write the card with the proposal (`chief-questions.ts` shapes), and answer the card through the proposal (`routes-chief.ts`). First action: `delete_todos`. Details and failure paths are in the design.
