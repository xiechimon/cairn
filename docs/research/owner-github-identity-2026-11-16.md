# GitHub identity for a fresh Cairn installation

Recommendation v2 (inference): distribute one shared public GitHub App client ID with device flow and expiring user tokens. Installation selects repositories; user tokens are bounded by the intersection of user permissions and App installations. Keep tokens encrypted in the trusted personal server and remove product installation-token/bot fallback. OS isolation and passkeys are explicitly deferred, so same-UID credential theft remains a residual risk, not a contained attack. This supersedes the broad OAuth and isolated-publisher recommendation.

All observations below are first-hand source/document reads on 2026-11-16, not a live authorization or mutation of a real GitHub account. Documentation was fetched through agent-reach's Jina backend. No credentials, host configuration or GitHub settings were changed.

## Repository evidence

Observed: `apps/web/src/pages/project-new-page.tsx` starts GitHub connection from new-project repository selection; `routes-resources.ts` exposes authorization-code start/callback and read/delete connection routes. `packages/shared/src/records/github.ts` requests `read:user repo`. `services/oauth.ts` requires configured client ID+secret, fetches user identity and encrypts tokens via `github-connection.ts`. There is no GitHub device/PAT UI in this path. `docs/configuration.md` documents self-registration. The shipped desktop has no bundled GitHub OAuth registration found in this inventory.

Observed: `github-autonomous-token.ts` prioritizes installation tokens, falls back to user OAuth and separately reads App commit identity. `machine-step-token.ts` sends GitHub credentials to the daemon. `step-env.ts` exports raw non-App credentials; `runtimeChildEnv` only removes them conditionally for the App credential-file path. `StepAppCredential` creates files under the daemon UID, not an independent OS isolation boundary. `git.ts`/workspace publication can use machine fallbacks. These need removal from GitHub agent execution, not merely renaming App credentials to user credentials.

Observed: `build-github-merge.ts` checks task ownership, PR branch/base and checkpoint, calls `assertMergeRequiredChecks` and sends a normal SHA-pinned GitHub merge request, not an APPROVE review or admin merge. `merge-required-checks.ts` currently discards `required-checks-none`; an unprotected fresh repository therefore needs an explicit trusted no-CI/expected-check policy rather than treating an empty list as success. REST head pinning does not pin the base atomically.

Observed: `commitIdentityViolation` already accepts owner identities from policy on same-repository branches and rejects forks claiming them. `localCommitViolation` and `pushViolation` reject owner commits in agent environments; installed `as-bot.sh` and tracked `sign-commits.sh` set bot author+committer and append a human trailer. The repository-local policy cannot be used as the distributed product's source for arbitrary users.

Observed: Octokit's [`oauth-methods` refresh implementation](https://github.com/octokit/oauth-methods.js/blob/main/src/refresh-token.ts) requires `clientSecret` and unconditionally sends `client_secret`; its device-code exchange supports secret-free requests but the refresh method does not. This cannot satisfy Cairn's required secret-free device-issued refresh contract. Keep a thin fixed-endpoint HTTP bridge in the existing `FetchLike` GitHub integration rather than add an SDK plus a second refresh implementation. Device attempt ownership, cancellation and connection compare-and-swap remain application state, not a generic OAuth client or a new parser.

Not verified: new device authorization, fresh-account consent screens, organization approval, sandbox implementation and real user-owned task publication. Those require implementation and separately approved operational validation; this research does not claim they already work.
