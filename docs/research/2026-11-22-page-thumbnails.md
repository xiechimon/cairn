# Thumbnails for agent-made HTML pages

Date: 2026-11-22. Evidence marks: measured = read first-hand in the linked primary source or first-party response; inferred = derived from measured; guess = unverified.

## Question

The "made" panel renders every agent-made HTML page live in a sandboxed `srcdoc` iframe (`sandbox=""`, CSP `default-src 'none'`, 800x600 scaled to the card). A page that is small in bytes but expensive to render (tens of thousands of blurred or animated elements) stalls the panel for 1-5 s. How do comparable products thumbnail user-generated HTML and app previews: do lists show a static image or a live iframe, where and when is the image made, and what shows when there is none? Does that support option A′ (the desktop main process renders the page once in a hidden, offscreen, sandboxed `BrowserWindow` with JS and network off, captures it with `webContents.capturePage`, and the card shows that image, with a text fallback)?

## Other no-extra-download approaches

- **Client-side capture in the panel's renderer (html2canvas or dom-to-image), the CodeSandbox in-preview pattern.** It must lay out and paint the heavy DOM in the panel's own process, which is exactly the 1-5 s stall we are removing. It also needs a CORS image proxy (CodeSandbox runs `h2c-proxy.csb.dev`) and re-implements CSS painting with known fidelity gaps, such as filters and blur. Worse than A′ on cost and fidelity. inferred
- **Live iframe only when on screen (IntersectionObserver), or one at a time.** Nothing new to build, but a single heavy page still stalls the panel the moment it scrolls into view, and the iPhone pays again on every view. CodePen keeps iframes but falls back to images on mobile, which is the same lesson. Not better. inferred
- **Server-side headless Chromium (Puppeteer or Playwright, as CodePen and Lovable use per inferred).** Works without the desktop app, but it is a ~100+ MB browser download for every standalone-server user. That fails the "no extra download" constraint. inferred
- **Title, icon or text card only (Claude artifacts, Bolt).** Zero cost, but it drops the visual preview the panel exists for. This stays as A′'s fallback, not as the main path.
- **User-uploaded thumbnail (CodeSandbox, Lovable, v0, Replit).** No author is in the loop for agent-made pages. Not applicable.

None of these is better than A′ on every axis. The only advantage any of them has is coverage when the desktop app is absent (headless Chromium), and it costs a download. A′'s text fallback covers that case.

## Pattern that fits

Capture once, show a static image, fall back to text. This matches Lovable, v0 and CodePen (measured): galleries use `<img>` and never iframe-per-card, and CodePen is the clearest case because it switches to images where rendering is expensive. CodeSandbox shows that keeping generated captures is optional, but its fallback is "no image", which is weaker than a text summary. Electron already provides the capture engine inside the app (`capturePage` plus `stayHidden`, sandbox, `javascript:false`), so A′ needs no new dependency.

## Recommendation (A′)

- `apps/desktop/src/main.ts`: the server is spawned by `utilityProcess.fork` (line ~321) and already uses `child.postMessage`. Add a request/reply message pair, `{type:'thumbnail', id, html}` → `{id, jpeg}`. The handler opens a `BrowserWindow` with `show:false`, `webPreferences:{sandbox:true, javascript:false, offscreen:true, backgroundThrottling:false}`, size 800x600, and refuses every non-`data:` request through `session.webRequest`. It loads the page, waits for `did-finish-load` plus one frame, then calls `capturePage(undefined,{stayHidden:true})` and `.toJPEG(70)`. A hard timeout destroys the window and replies "none". Use one window at a time, queued.
- `apps/server/src/routes-uploads.ts`: next to `GET /api/attachments/:id` (line ~84), serve the stored `<id>.thumb.jpg` (for example `?thumb=1`) under the same auth. At publish, ask desktop main for a capture when the channel exists. With no channel, or a failed capture, store nothing.
- `apps/web/src/board/made-carousel.tsx` and `apps/web/src/board/made-files.tsx`: the live `srcdoc` iframe (made-files.tsx ~line 99) becomes `<img loading="lazy">` of the thumbnail. When there is no thumbnail, show the text summary card. The live iframe opens only in the expanded viewer.
- Tests: a heavy page must not mount an iframe in the card, and with no desktop channel the card must show the text fallback.

## Probe on the pinned Electron (45.2.1, macOS arm64)

measured with a throwaway script, `show:false`, 800x600:

- `offscreen: true` + `capturePage()` rejects with `UnknownVizError`; the `paint` event after load returns an 800x600 `NativeImage`. A non-offscreen hidden window's `capturePage()` works but returns a device-pixel image of the frame-sized content (1600x1136). The change uses `offscreen` + `paint`, not `capturePage` as recommended above.
- A `data:` URL of a 2 MB page fails with `ERR_INVALID_URL`; a custom scheme served by `session.protocol.handle` on an in-memory partition loads it.
- `javascript: false` keeps `<script>` from running; `webRequest.onBeforeRequest` cancels the page's `https://` image.
- Destroying the last open window quits the app (no `window-all-closed` listener), so capture only runs once the tray popover window exists.
- Load + first frame: simple page 0.2 s, 5 000 blurred animated elements 1.3 s, 55 000 elements (2 MB) 5.4 s, all in the hidden window's own renderer.
