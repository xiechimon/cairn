# Cairn Cloud Always-On Server Hosting Research (2026-11-25)

**Question:** How do comparable agent products host their per-user always-on servers / sandboxes, and which hosting infrastructure should Cairn Cloud rent to run each paying user's always-on Cairn server?

**Scope:** Read-only research; no sign-ups, payments, or API keys created. Prices were read from official pages on 2026-11-25; USD figures exclude tax. Hourly-billed platforms are normalized at **730 hours/month**; fixed monthly bundles use official list prices. "20 GB persistent disk" is compared as "at least 20 GB of usable persistent storage", without requiring a separate attached volume when VPS plans (Lightsail / DigitalOcean / Hetzner) already include 20–80 GB system disks.

**Evidence tags:** `` `实测` `` = directly read from official docs, official pricing pages, open-source code, or Cairn's own first-hand trial report; `` `推断` `` = mathematically or logically derived from those facts; `` `猜测` `` = not confirmed from primary sources. Secondary articles are not used as evidence.

Related internal docs: [`cairn-cloud-2026-11-25.md`](./cairn-cloud-2026-11-25.md) covers Hermes / Letta / OpenClaw / Dusk business models and the initial Cairn Cloud architecture; [`cloud-pricing-2026-11-25.md`](./cloud-pricing-2026-11-25.md) covers Creem, Clerk, and the Fly+InstaBox hybrid pricing model. This report focuses specifically on **hosting provider selection** without repeating their full arguments.

## 1. Executive Conclusions

1. **Mainstream coding-agent products do not run one always-on 2 vCPU / 4 GB machine per user.** (`` `推断` ``) Cursor, Codex, Claude Code, Amp, Devin, OpenHands, and Codespaces share a common pattern: allocate an isolated VM/container per task or session, sleep/pause/stop after a few minutes of idleness, and resume from disk snapshots, PVCs, or saved VM state. What stays around long-term is **data and checkpoints**, not continuously billed CPU/RAM. Cursor explicitly hibernates and deletes agent VMs on lifecycle timers; OpenAI Codex guarantees task workspace recovery for 7 days by default; Amp pauses orbs after 5/20 minutes of inactivity; Codespaces defaults to a 30-minute idle stop. See §2.
2. **Cairn's "always-on server" is not a coding sandbox — it is a small control plane / brain.** (`` `推断` ``) A heavy Cairn user's brain uses roughly **170 MB RSS and 280 MB of data**; heavy execution happens on the user's own Runners or separate coding VMs. This measured baseline comes from [`cairn-cloud-2026-11-25.md §4`](./cairn-cloud-2026-11-25.md). Provisioning a fixed "2 vCPU / 4 GB always-on" box for every Plus user would severely over-provision; that spec is useful as a horizontal comparison benchmark, not as the default Plus brain tier.
3. **Recommendation: run each user's always-on Cairn brain on a DigitalOcean Droplet; use AWS Lightsail as the secondary supply plane for cost-sensitive or broader Asian region coverage; do not use E2B / Daytona / Modal as the always-on brain.** (`` `推断` ``)
   - DigitalOcean 1 GB / 1 vCPU / 25 GB Droplet is `$6/mo`, daily backups +30% (`$1.8`), API supports enabling backups at creation time, single-Droplet SLA is 99.99%, Singapore/Bangalore regions exist, and direct VM networking avoids Host header rewriting and platform WebSocket/SSE limits. Given Cairn's measured 170 MB RSS, 1 GB has much safer headroom than Lightsail's 512 MB tier. See §5.
   - AWS Lightsail 1 GB / 2 vCPU / 40 GB is `$7/mo` with broader Asian regions and generous transfer allowances, but uses burstable CPU (10% sustained baseline on 1 GB), has only a 99.5% single-instance SLA, and still bills when stopped. Good as a secondary region/cost plane, not an unexamined single bet. See §5.
   - InstaBox fits **on-demand wakeable fallback coding VMs** (consistent with the existing pricing report), not the sole always-on brain host: region cannot be selected (observed in AWS Oregon), public proxy rewrites `Host`, free tier cannot stay always-on, and SLA is only stated for Enterprise. See the InstaBox row in §4 and §4.1.
4. **Under a strict horizontal "2 vCPU / 4 GB + 20 GB, 24/7 no-sleep" benchmark, only VPS hosts (Lightsail / DigitalOcean / Hetzner) land near `$20–31/mo`, Render/Railway/Northflank cost `$50–90/mo`, and E2B/Daytona/Modal cost `$121–176/mo`.** (`` `推断` ``, §4) Thus `$20 Plus` can never promise an always-on 2 vCPU / 4 GB machine running heavy workloads; the brain must be right-sized and heavy work must stay on Runners or pausable coding VMs.
5. **Margin takeaway:** With a DigitalOcean 1 GB brain for Plus, including daily backups and estimated Creem fees, COGS is `~$8.98/mo`, yielding `~$11.02` / **55.1%** variable gross margin on `$20`; Pro with a 2 GB brain has `~$17.95/mo` COGS, yielding `~$32.05` / **64.1%** variable gross margin on `$50` (`` `推断` ``, §6). This excludes central control plane amortization, support, abuse, and refunds, but is far healthier than the negative margins of an always-on 2 vCPU / 4 GB model.

### 2.2 Region Disclosure Across Products

- **User-selectable regions:** Codespaces lets users pick a default region (`` `实测` ``: [default region](https://docs.github.com/en/codespaces/setting-your-user-preferences/setting-your-default-region-for-github-codespaces)); Coder and self-hosted runner products leave region selection to the deployer (`` `推断` ``); Daytona shared regions are only `us` and `eu` (`` `实测` ``: [Daytona regions](https://www.daytona.io/docs/en/regions/)).
- **Vendor-hosted without user-facing region controls:** Cursor discloses AWS/Firecracker and isolated AWS accounts without exposing per-user region selection in public docs; Codex, Claude Code, Amp-hosted orbs, Devin, and Replit likewise do not expose per-task region selection as a primary public control (`` `推断` `` from the official docs cited in §2.1).
- **Single-region / non-selectable:** InstaBox/Dusk machines cannot pick a region and Cairn's trial landed in AWS Oregon; t3code has no vendor cloud region because it runs on user hardware (`` `实测` ``/`` `推断` ``).

### 2.3 Industry Patterns

- **Split the brain/control plane from execution sandboxes** (`` `推断` ``): Letta separates cloud memory/brain from Cloud Sandboxes / BYOM computers; Claude Code self-hosted runners, Devin Local Hands, and Amp self-hosted orb providers all route execution into user/org networks. Cairn's Runner architecture aligns directly with this pattern.
- **Perceived always-on != 24/7 CPU billing** (`` `推断` ``): Dusk, Amp, Claude, and Cursor create the feeling of continuous availability via fast wake and state restore. However, because Cairn runs 15-second-granularity crons, IM long-polling/webhooks, and Runner routing, the **brain** itself should stay truly always-on while **coding VMs** should not.
- **Durability belongs on disk / object storage / checkpoints, not process memory** (`` `推断` ``): Devin discards session edits unless persisted externally; Codex warns saved VM state does not replace git; most Amp self-hosted backends cannot preserve memory. Cairn should keep all authoritative state in SQLite/attachments/object storage and treat memory pause purely as an optimization.

## 3. Cairn's Actual Hosting Requirements

1. **Must stay always-on:** Cairn server/brain handling SQLite, projects, chat history, attachment index, schedules, IM/webhooks, and Runner routing (`` `推断` `` from Cairn architecture and [`cairn-cloud-2026-11-25.md`](./cairn-cloud-2026-11-25.md)).
2. **Does not need to stay always-on:** execution on users' own Mac/Linux/Windows Runners, fallback coding VMs, and heavy build/test/browser runs. These should auto-pause/stop (`` `推断` ``, consistent with [`cloud-pricing-2026-11-25.md`](./cloud-pricing-2026-11-25.md)).
3. **Right-sizing specs:** A heavy Cairn user's brain was measured at ~170 MB RSS; 1 GB RAM gives ~6x headroom, whereas 512 MB gives ~3x headroom but is tighter during backups, upgrades, and attachment indexing (`` `推断` ``). Hence this report recommends starting Plus at 1 GB rather than 512 MB or 4 GB.
4. **Networking requirements:** Direct HTTPS/WSS from browsers, desktop, and mobile; outbound Runner connections; rock-solid WebSocket/SSE; no Host header rewriting that breaks pairing origin validation (`` `推断` ``; InstaBox testing already exposed Host rewriting issues on Cairn).
5. **Backup requirements:** Provider snapshots are disaster recovery, not Cairn's promised "daily encrypted backups". Cairn should still push encrypted backups to object storage (R2/B2) and use provider snapshots for fast host recovery (`` `推断` ``).

## 5. Recommended Architecture & Provider Selection

### 5.1 Recommended Topology

```text
User browser / desktop / mobile
        │ HTTPS/WSS
        ▼
One always-on Cairn brain VM per user (DigitalOcean Droplet, 1–2 GB)
        │ outbound HTTPS/WSS/SSE
        ▼
User's own Mac/Linux/Windows Runners (heavy execution runs here first)

Optional fallback:
Cairn brain wakes an InstaBox coding microVM (when no user runner is online)
        │ auto-pause/stop after task finishes and idles
```

This matches the "Fly Brain + InstaBox Coding VM" split in [`cloud-pricing-2026-11-25.md`](./cloud-pricing-2026-11-25.md), shifting the primary brain host from Fly to DigitalOcean/Lightsail because:

1. Cairn's brain is a long-lived stateful server rather than an ephemeral container; fixed-price VPSes with bundled system disks fit better (`` `推断` ``).
2. Direct VMs on DigitalOcean/Lightsail sit outside platform HTTP proxies, eliminating Host rewriting and proxy WebSocket timeout surprises (`` `推断` ``).
3. Measured brain RSS is only 170 MB, so 1–2 GB VPSes provide ample headroom without paying for 2 vCPU / 4 GB (`` `推断` ``).
4. Fly remains a strong runner-up if the team wants immutable containers + volumes + API with minimal OS maintenance, though it costs more at 20 GB persistent storage and in Asian regions than small Lightsail/DO droplets (`` `推断` ``).

### 5.2 Primary Choice: DigitalOcean Droplet

**Recommended tiers** (`` `推断` ``):

- **Plus:** Basic Regular Intel 1 GB / 1 vCPU / 25 GB at `$6/mo`; daily backups +30% (`$1.8`).
- **Pro:** 2 GB / 1 vCPU / 50 GB at `$12/mo`; daily backups +30% (`$3.6`).
- Default region Singapore or closest to user; fill Asian coverage gaps with Lightsail Tokyo/Hong Kong/Seoul (`` `推断` ``).
- Provision via cloud-init installing Cairn server, Caddy/TLS, systemd auto-start, and firewall; also push encrypted backups to R2/B2 (`` `推断` ``).

**Why not blindly pick the cheapest Lightsail tier** (`` `推断` ``): Lightsail 1 GB `$7` looks attractive, but its sustained CPU baseline is only 10% (and 5% on 512 MB), while Cairn brains run daily encrypted backups, dependency installs, self-updates, and attachment indexing. DigitalOcean Basic also uses shared/variable CPU and **does not guarantee a dedicated constant 1 vCPU**; DO is chosen for its 99.99% per-Droplet SLA, clean daily-backup semantics, and simple API — not for guaranteed CPU throughput. If telemetry shows DO 1 vCPU throttling on backups/indexing, upgrade to 2 GB/2 vCPU or move to Fly/dedicated CPU rather than assuming a VPS is inherently faster.

### 5.3 Secondary Supply Plane: AWS Lightsail

Keeping Lightsail as the second supply plane has three advantages (`` `推断` ``):

1. Broader Asian region footprint than DigitalOcean;
2. 1 GB / 2 vCPU / 40 GB at `$7/mo` has solid economics for low-load brains;
3. AWS APIs, quotas, Organizations, and the Partner Program scale well, though default quotas and partner tiers must be requested ahead of time (`` `实测` ``: [Lightsail Partner Program](https://docs.aws.amazon.com/lightsail/latest/userguide/lightsail-partners.html)).

Three operational traps must go into runbooks (`` `实测` ``):

- Stopped instances still bill until deleted ([billing FAQ](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-frequently-asked-questions-faq-billing-and-account-management.html));
- Deleting an instance deletes its automatic snapshots unless copied into manual snapshots ([instance FAQ](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-instances.html));
- Burstable baselines are low, so Lightsail 2 vCPU cannot be treated as 2 constant cores ([baseline CPU](https://docs.aws.amazon.com/lightsail/latest/userguide/baseline-cpu-performance.html)).

### 5.4 Platforms Not Recommended for the Always-On Brain

- **InstaBox:** Keep as fallback coding VM. Strong API, fast pause/resume, and cheap per-second runtime, but regions are not selectable (observed in AWS Oregon only), Host rewriting broke Cairn pairing, and always-on is not its sweet spot (`` `推断` ``).
- **Fly.io:** Technically viable and proven by Hermes for per-user agents; good fallback if Cairn prefers containerized immutable deploys with less OS ops. Recommended behind DO/Lightsail here due to lower cost/stability of right-sized VPSes (`` `推断` ``).
- **Render/Railway/Northflank:** Good for Cairn's central control plane or small internal services, too expensive per paying user (`` `推断` ``).
- **E2B/Daytona/Modal:** Built for ephemeral coding sandboxes, unsuitable as 24/7 user brains (`` `推断` ``).
- **Hetzner:** Still competitive in Europe, but 2026 price hikes and stock availability warnings weaken its "cheapest universal VPS" edge; treat as a tertiary provider rather than primary (`` `推断` ``).

## 7. Engineering Capabilities Cairn Must Build

1. **Provisioner / tenancy control plane:** Create per-user VMs, inject cloud-init, assign subdomains and TLS certs, track provider/region/instance IDs, and handle deletion + 30-day retention (`` `推断` ``). Keep this proprietary, as recommended in the earlier Cairn Cloud report.
2. **Reverse-proxy `Forwarded` / `X-Forwarded-Host` handling in Cairn server:** InstaBox testing already showed Host rewriting triggers pairing 403; even with DO/Lightsail first, Cairn should handle forwarded headers cleanly so future proxy layers do not regress (`` `推断` ``; trial report).
3. **Daily encrypted backups independent of platform snapshots:** Platform snapshots must not be the sole backup; deleting a Lightsail instance deletes automatic snapshots, and DO backups only restore inside DO. Cairn should push encrypted `CAIRN_HOME` backups to R2/B2 and regularly test restores (`` `推断` ``).
4. **Avoid over-abstracting providers early:** Start with a minimal 7-action interface (`create/delete/start/stop/snapshot/backup/region/status`) rather than supporting ten providers upfront; implement DigitalOcean + InstaBox coding VMs in week 1, keeping Lightsail behind the interface (`` `推断` ``).
5. **Observability:** Report CPU, memory, disk, SQLite size, and backup duration from every brain; track burst capacity on Lightsail and disk/backup success on DO (`` `推断` ``).
6. **Abuse controls:** Keeping no free cloud tier is the right first gate, but rate limits, egress alerts, CPU/crypto-mining anomaly detection, and payment risk checks are still required on any cheap VPS fleet (`` `推断` ``).

## 8. Final Recommendation

**Choice for Cairn Cloud** (`` `推断` ``):

1. **Primary always-on Cairn brain: DigitalOcean Droplets** — Plus on 1 GB / 1 vCPU / 25 GB, Pro on 2 GB / 1 vCPU / 50 GB, with daily backups enabled at creation.
2. **Secondary region/cost plane: AWS Lightsail** — expand usage once brain telemetry confirms fit with burstable baselines, especially for Asian regions DigitalOcean lacks.
3. **Keep InstaBox as on-demand fallback coding VM, not always-on brain** — continue routing heavy tasks to users' own Runners first.
4. **Keep Fly.io as containerized alternative** — re-evaluate Fly 512 MB brains + volumes if VPS OS fleet maintenance exceeds `$1–2/user/mo`.
5. **Skip Render/Railway/Northflank/E2B/Daytona/Modal for per-user always-on brains** — either unit economics fail or the platform is built for short-lived sandboxes.

In one line: **Cairn Cloud should sell an "always-on brain", not an "always-on heavy coding machine"; the former is profitable on 1–2 GB VPSes, while the latter loses money at `$20/mo`.** (`` `推断` ``)
