## 1. Short answer

1. **Orca does not auto-pick tasks from a queue either.** Its own docs say a Run "never schedules or places workers" ([docs/site/content/docs/cli/orchestration.mdx:29](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/docs/site/content/docs/cli/orchestration.mdx#L29)). An LLM coordinator starts workers; the system's job is to wake it on every worker event, and the guide tells it to re-read the ready list on each wake ([skill-guides/orchestration/references/coordinator-loop.md:15](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/skill-guides/orchestration/references/coordinator-loop.md#L15)). The only unattended starter is cron-style Automations: a 60 s tick ([src/main/automations/service.ts:44](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/automations/service.ts#L44), [src/main/automations/service.ts:110](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/automations/service.ts#L110)). Measured
2. **Cairn has the same LLM-starts-work shape but a weaker wake.** A task created by the Coordinator sits in `phase='todo'` until the Coordinator also calls `open_thread` (`apps/server/src/services/chief.ts:1358`); no scheduler tick starts it, and the only wake kinds are `gate`, `settle`, `failed` (`packages/shared/src/records/chief.ts:227`) plus `question`. 11-08 shows 29 `create_todo` calls against 21 `open_thread` calls in the Coordinator transcript; 8 todos (140, 141, 149, 150, 158-161) were created and never started, 16-17 h before the sweep. Measured (DB)
3. **Orca's real strength is "no silent stop"**: every way a worker can stop (finished, errored, needs-input, exited) becomes one idempotent high-priority mail to the owner ([src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts:83](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts#L83)). Cairn has three silent stops: research review under the default merge policy has no owner, a worker's ruling request is free text, and a Coordinator wake that ends with no state change is never re-fired (section 4). ## 3. What Orca does that matters for "my harness does not execute"

- **Edge plus level.** A wake is an event, but the coordinator's contract on every wake is to re-read the whole ready list and start what it shows ([skill-guides/orchestration/references/coordinator-loop.md:15](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/skill-guides/orchestration/references/coordinator-loop.md#L15)) and to re-read handled mail if it lost track ([skill-guides/orchestration.md:77](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/skill-guides/orchestration.md#L77)). A missed event therefore costs one wake, not the task. Cairn's wake prompt carries one todo's facts (`apps/server/src/services/chief.ts:1228` (wakeFactText)); nothing re-reads "what is unstarted". Inferred
- **Worker stop is a typed event with a stable id.** `finished | errored | needs-input | exited`, one mail per stop, idempotent, wakes the owner, never settles the Dispatch itself ([src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts:15](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts#L15), [src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts:83](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts#L83)). A deliberate wait (`check --wait`, an open question, helper Dispatches) is exempt, so there is no noise ([src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts:90](https://github.com/stablyai/orca/blob/f10be535ca2a0641afe05821356d01144308884f/src/main/runtime/orchestration/workers/turn-stops/worker-turn-stop-report.ts#L90)). ## 5. Pattern that fits, and recommendations (input for the stall-fix design agent)

Pattern: **keep the LLM as the decision maker, but make the server the level-triggered owner of "nothing may sit"**. Concretely, every state that is not terminal and not progressing has exactly one owner and one timer; the owner is a person or the Coordinator; a wake that produces no state change is re-fired or escalated. Orca gives the stop-event vocabulary and hosting; Claude Code's supervisor gives the "restart what exited, never interrupt what works" rule. Cairn already has the right primitive (`reconcileOwners` on the tick, `lastNotifiedWork` checkpoint); the gaps are states it does not model.

Each item names the failing test to write first (research doc rule: red before green) and the code areas.

**R1. Level-triggered "unstarted" reconciler (highest value, symptom 3).** On `runTick` (next to `reconcileOwners`, `apps/server/src/services/scheduler.ts:522`): for non-archived, non-snoozed todos with `phase='todo'`, `latestBuildId` null, `blockedBy` satisfied (`splitBlockersSatisfied`) and age over N minutes (suggest 10), start a build with `triggerSource: 'chief'` exactly as `dispatchSplitChildren` does (`apps/server/src/services/builds.ts:1324`), bounded by project concurrency and `assertProjectWritable`; todos created by the user in `todo` stay user-started. Alternative with less automation: a new wake kind `unstarted` plus re-fire after M minutes. Prefer the direct start because the contract "create then open" is the root cause, so also fold it into one call (`create_todo` with `start: true`, or `open_thread` implied for Coordinator-created todos). Touches: `services/scheduler.ts`, `services/builds.ts`, `services/chief-tools.ts` and `packages/shared/src/protocol/chief-tools.ts` (tool schema), `services/owner.ts` (new `up_next` staleness state), `packages/shared/src/records/chief.ts` if a wake kind is added. Red test: create a Coordinator todo, advance the clock 15 min with no `open_thread`, assert a build row exists. Needs a decision (not mine): is automatic start of Coordinator-created todos allowed without ian's confirm, given `autonomy` policy? Guess that it is, since `open_thread` is already in the Coordinator's prompt as the default.

**R2. No ownerless states, and no one-shot wakes (symptoms 1 and 4).** (a) `reviewOwnership` for `output='info'` must return the Coordinator for every policy (`apps/server/src/services/owner.ts:62`), plus an auto-accept rule after a timeout so research cannot wait forever; (b) a wake that ends with the same `workKey` after T minutes is re-fired once with the previous turn's last message attached, then escalated to a push for the owner, mirroring `recoverGateWake` but for no-op turns (`apps/server/src/services/chief.ts:1184`). (c) A wake turn must end in a recorded action (`notify_user`, `ask_user`, `complete_todos`, `message_thread`, `close_todos`); "quiet by default" (`chief.ts:1432`) stays for noise, not for failures. Touches: `services/owner.ts`, `services/chief.ts` (`enqueueOwnershipWake`, `recoverGateWake`, `wakeFactText`), `services/scheduler.ts`. Touches `services/retry-parking.ts`, `services/model-liveness.ts`.
