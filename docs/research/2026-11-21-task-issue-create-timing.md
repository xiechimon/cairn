# Task issue creation timing: when a chat-created task should get its GitHub issue

Status: research, 2026-11-21. Question: cairn opens one GitHub issue per task in a GitHub-linked project (`sourceKind = 'github-issue-self'`), created eagerly at task creation. Chat one-off requests ("install X") therefore open noise issues. Options: (a) eager at creation — old behavior; (b) lazy at first delivered artifact (commit/PR); (c) never auto-create. Sister doc: `task-issue-lifecycle-2026-11-09.md` covers issue *closing*; this doc covers issue *creation*.

Evidence labels: `实测` = read first-hand this session (primary doc page or source file), `推断` = follows from `实测` facts, `猜测` = everything else. cairn facts read in this worktree.

## 2. Facts in cairn today (`实测`, this worktree)

- `createTodo` plans and fires the issue eagerly: `planSelfIssue` when `sourceKind === undefined && withoutSelfIssue !== true` and the project is GitHub-backed with a connection (`todos.ts:601-604`, `1047-1053`), then `scheduleSelfIssueCreate(deps, id)` at `todos.ts:656` — inside task creation, before any work exists.
- `runSelfIssueCreate` (`todos.ts:1189-1253`) is idempotent: effect-ledger dedupe `(teamId, todoId, owner, repo)`, a marker probe (`<!-- cairn:todo <id> -->`), and an early return when `sourceRef !== null` (`todos.ts:1200`). Firing it from additional trigger points is safe.
- The opt-out already exists: `withoutSelfIssue` is set for untrusted turns (`chief-tools.ts:717,735`, forwarded at `coordinator-request.ts:509`) — the codebase already accepts "not every task deserves an issue".
- Delivery evidence lands in two places: `applyStepReport` writes `build.prUrl`/`prNumber` when the machine's report attaches a PR (`machine-finish-step.ts:290-305`, `422-425`), and `completeStepSettled` settles a build step with `outcome.hasChanges`/`workBranchDrift`, calling `finishTodoDone` for code outputs (`build-step-complete.ts:143`, `316-321`). `completeStep` wraps the settle in a transaction (`build-step-complete.ts:135-141`).
- The daemon measures `hasChanges` itself at step closing (`apps/daemon/src/step-closing-git.ts:115`: `headAhead > 0 || artifactBranches.length > 0`) — it is a git measurement, not an agent claim.
- The issue exists to be closed by `Closes #N`: `ensurePullClosesTaskIssue` (`pr-closing-line.ts`) runs on every PR-watch sweep and before the merge PUT (`task-issue-sync.md` §"Landing"). So creation must precede merge — Linear's literal merge-time trigger is too late for cairn.
- Deferral is already tolerated: the reconciler only selects rows with `sourceRef IS NOT NULL` (`task-issue-sync.ts:103`), so a task with intent-but-no-issue is invisible to the sweep; `desiredIssue`'s `'wait'` branch already handles a successor whose issue is pending (`task-issue-sync.ts:56-57`); the detail UI already renders `sourceKind`-set/`sourceRef`-null as `GitHub issue 未建成` with a retry button (`apps/web/src/detail/source-issue.tsx:47-64`); `POST /api/todos/:id/github-issue/retry` → `retrySelfIssueCreate` (`routes-todos.ts:56`, `todos.ts:1255`) creates on demand for `sourceRef === null` rows — a ready-made manual escape hatch.

## 3. Pattern that fits cairn

Every source splits the same way (`推断`): **the tracking record is either an input to the agent, or it materializes at a delivery event — never at chat/task-creation time.** Agent products keep the record internal (session, thread, task, agent) and emit exactly one artifact: a PR. Repo-automation products attach links and create records on branch/commit/PR-open/merge events. The single auto-create precedent — Linear creating issues for unlinked PRs *at merge* — fires on proof that the work produced a code artifact. cairn's eager creation is the outlier: no prior art opens a tracker issue because a chat produced a task row.

cairn-specific constraints shape the trigger inside option (b):

1. The self-issue's job is repo-side visibility plus being the target of `Closes #N` on landing (`task-issue-sync.md`). Both jobs only exist for tasks that deliver repository artifacts, so "first delivered artifact" is the right moment — earlier than Linear's merge-time choice, since the issue must exist before the closing line is written and before any merge commit.
2. Rejected triggers: build start is still eager (plan-only or chat-answered tasks may never commit); PR merge is too late (the issue is the `Closes #N` target, not just a record); commit-message `Closes #N` on local-landing paths (`local-merge.ts`, per `task-issue-lifecycle-2026-11-09.md` §2.3) needs the issue before the merge commit is created.
3. Rejected option (c): the self-issue is load-bearing for the documented landing path and for GitHub-side visibility; dropping it removes a feature, not just noise.
4. Keep `sourceKind = 'github-issue-self'` at creation as the intent marker (drives the UI source line, the retry endpoint, `planProjectMove`'s `targetOpensIssues` logic at `todos.ts:883-889`); its meaning becomes "this task gets a GitHub issue when it delivers".

## 4. Recommendation

Adopt **(b) lazy creation on first delivery evidence**:

1. Remove `scheduleSelfIssueCreate(deps, id)` from `createTodo` (`todos.ts:656`); keep `planSelfIssue` and the `sourceKind` assignment (`todos.ts:601-604`, `628-634`), gated on `output === 'code'` so info outputs never carry the mark.
2. Fire `scheduleSelfIssueCreate` when a task first proves it produces repo artifacts — in `completeStepSettled` (`build-step-complete.ts:316-321`): `isBuildStepKind(stepRow.kind)` settled successfully AND (`outcome.hasChanges === true` OR the build row carries `prNumber`/`prUrl`, which `applyStepReport` writes at `machine-finish-step.ts:422-425` earlier in the same report flow). The guard `row.sourceKind === 'github-issue-self' && row.sourceRef === null` is enforced in a single exported trigger plus `runSelfIssueCreate`'s own early returns (`todos.ts:1192`, `1200`) and ledger dedupe.
3. Remove the project-move re-fire (`todos.ts:843-845`): movable cards are unstarted by definition (`canMoveTodoProject`), so a moved card has never delivered — leave creation to the delivery trigger; a donor-ref card moved across repos still resolves via `replacesOtherRepo` (`todos.ts:1194-1199`) on delivery.
4. Bound `desiredIssue`'s `'wait'` (`task-issue-sync.ts:56-57`): a superseding task may now *never* create its issue; waiting forever blocks the predecessor's close. Wait only while a create is actually in flight.
5. UI copy: `source-issue.tsx:47-64` `GitHub issue 未建成` implies failure; under lazy policy a never-delivered task is pending-by-design — hide the pending line while `hasChanges` is false (retry button remains the escape hatch once a delivered task's create failed).
6. Red-first tests: a chat-created task in a GitHub-linked project must produce zero `POST /issues` until delivery; issue creation on first `hasChanges` settle; none for a successful leg with `hasChanges === false`; manual retry on an undelivered task answers 409.
