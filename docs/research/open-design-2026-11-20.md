# OpenDesign: click-to-comment on previews, and what Cairn could take from it (2026-11-20)

Two questions from ian:

1. Can **we** (the Cairn team) use OpenDesign to make prototypes that ian annotates with click-to-comment, with the comments handed back to the coding agents?
2. Can **Cairn the product** integrate it — a task produces a prototype into an OpenDesign workspace and comments come back as task input; Cairn copies the click-to-comment pattern in its own previews; or OpenDesign runs as a Cairn app/connector?

Newcomer framing: a Cairn user who has never heard of OpenDesign would meet it as either (a) a separate app the task's prototype link opens in, where they click elements and leave notes instead of typing feedback into chat, or (b) an invisible detail — the same comment UX built into Cairn's own preview. Option (a) asks them to keep a second app running (Docker or a desktop install) and to learn its project model; option (b) asks nothing new. Nothing here costs money: OpenDesign is Apache-2.0 and BYOK, and this note proposes using only its free local path.

## 0. Conclusions

1. **Yes to (1), and it is cheap: use the OpenDesign daemon as a comment server for HTML our agents already write.** A Docker container gives a token-authed daemon + web UI where ian clicks elements in our HTML and the coding agent reads the comments back over REST (`GET /api/projects/:id/conversations/:cid/comments`) or `od comment list --json`. Proven end-to-end on this machine: project created, HTML uploaded, comment pinned from the UI, read back via REST — no agent runtime inside OpenDesign required. (verified, sections 3 and 5)
2. **The strongest anchor is ours to make.** OpenDesign comments anchor to `data-od-id` attributes the *generating* agent is instructed to write into the HTML, falling back to selector + htmlHint + position + text with a four-state drift ladder (`anchored` / `reanchored` / `stale` / `lost`). Our `options-prototype` template would need `data-od-id` on commentable elements — a template change, not a product change. (verified, sections 1.2 and 4)
3. **For (2), the designed integration point already exists.** `docs/orchestrator-workspaces.md` defines an "externally prepared workspace" contract (orchestrator owns checkout/writeback, OpenDesign edits a scratch dir and reports a result package), `POST /api/runs` is a documented headless entry, and `GET /api/runs/:id/result-package` is the stable output boundary. A Cairn lane could drive OpenDesign entirely over REST — but the comments leg still needs REST/`od` CLI because **OpenDesign's MCP server exposes 21 tools and none of them touch comments**. (verified, sections 2 and 5)
4. **Embedding OpenDesign inside Cairn is possible but the fit is awkward.** It is a second product with its own daemon (Express + SQLite + Next.js + Electron shell), its own agent spawning, a ~weekly release cadence, and a self-positioning as a coding-agent control plane — i.e. it partially overlaps what Cairn itself is. Shipping it as a Cairn app means packaging a fast-moving third-party daemon; adopting the comment pattern natively in Cairn's own preview is more work once but owns the loop. (derived, section 6)
5. **Maturity is real but the 108k stars deserve a caveat.** Repo created 2026-04-28, 108,555 stars and 12,305 forks on 2026-11-20 — roughly 0→100k in seven months, an unusual trajectory even for a viral product. Activity underneath is genuine: v0.27.2, weekly-ish releases, 1,431 open issues with fresh detailed reports from many distinct users, 27 shipped agent adapters. (verified numbers; the suspicion about star inflation is guess)

## 1. What OpenDesign is

Apache-2.0 "collaborative AI design agent workspace", self-positioned as the open-source alternative to Anthropic's Claude Design (their 0.1.0 release notes say exactly that; the positioning is confirmed by third-party coverage: [XDA comparison](https://www.xda-developers.com/built-same-app-with-claude-design-and-open-design/)). Local-first: an Express + SQLite daemon owns all state under one data dir (`OD_DATA_DIR`, `~/.od` by default), a Next.js web app talks to it over same-origin HTTP + SSE, an Electron shell wraps it for desktop, and `od` is a bin hitting the same REST API — their AGENTS.md mandates CLI parity for every user-facing capability. ([architecture.md](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/docs/architecture.md), [apps/daemon/AGENTS.md](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/AGENTS.md) "CLI and Surface Parity") (verified)

### 1.1 How it runs agents

27 shipped runtime defs in [`apps/daemon/src/runtimes/defs/`](https://github.com/nexu-io/open-design/tree/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/runtimes/defs), listed in [`registry.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/runtimes/registry.ts): amr (their bundled vela), claude, codex, **devin**, opencode, byok-opencode, hermes, trae-cli, grok-build, kimi, cursor-agent, qwen, qoder, copilot, amp, pi, kiro, kilo, vibe, deepseek (×2), aider, antigravity, reasonix, codebuddy, mimo, atomcode — plus user-declared local profiles. The daemon scans PATH (plus toolchain dirs: mise, fnm, homebrew, etc.) and spawns the CLI as a child process; Claude gets `claude` with stream-json parsing and per-flag capability probing (`claude.ts`), ACP-family agents go through a shared ACP layer. BYOK needs an OpenCode binary *inside the daemon's environment* — a provider key alone does not spawn anything. (verified: [`docs/headless-byok.md`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/docs/headless-byok.md), defs source)

### 1.2 The comment system (the part ian asked about)

**Capture.** The daemon serves preview HTML at `/api/projects/:id/raw/<file>` and **injects a "preview bridge" into the served document** when `odPreviewBridge` query params ask for it (`scroll`, `selection`, `snapshot`, `observability`, `comment`, …) — [`applyUrlPreviewBridgesToHtml`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/routes/project/index.ts) near line 7334; the web iframe requests `odPreviewBridge=scroll&odPreviewBridge=selection&odPreviewBridge=snapshot&odPreviewBridge=observability` ([`FileViewer.tsx`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/web/src/components/FileViewer.tsx) line 451). So the bridge travels with the file, not the app: any HTML the daemon serves can be commented on. In comment mode a click resolves the element to a `PreviewCommentTarget`: `filePath`, `elementId`, `selector`, `label`, visible `text`, bounding `position`, `htmlHint`, computed `style`, optional `podMembers` / `slideIndex` / screenshot `markKind` for draw-mode marks. Contract: [`packages/contracts/src/api/comments.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/packages/contracts/src/api/comments.ts). (verified — also verified live, section 5)

**Anchor.** `data-od-id` attributes are the strong identity: the generation skills instruct the agent to emit them on meaningful elements (e.g. [`skills/faq-page/SKILL.md`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/skills/faq-page/SKILL.md) line 66), and FileViewer calls an element without one un-annotated. Re-resolution each render runs the drift ladder in [`apps/web/src/comments/anchor.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/web/src/comments/anchor.ts): exact id+selector+file hit → `anchored`; re-found after content change → `reanchored` ("based on older vN" badge); fuzzy match on selector+htmlHint+position → `stale`; nothing → `lost` (ghost pin at `lastGoodPosition`). Comments on HTML without `data-od-id` still work through the fuzzy path, just weaker. (verified)

**Store.** SQLite `preview_comments` table with columns for every contract field plus `pin_seq` (permanent pin number, globally serialized through the collab cloud on team projects) and `sortKey` (sidebar drag order) — [`db.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/db.ts) lines 298+, 3859. Status lifecycle: `open → attached → applying → needs_review → resolved | failed`. (verified)

**Read/write surface.** Full REST parity under `/api/projects/:id/conversations/:cid/comments` (list, create, pull, PATCH status/anchor/reorder, delete), project-scoped list + unread tracking at `/api/projects/:id/comments/read`, and `od comment list|pull|create|update|status|delete|read|align|sync-state|retry-backfill` in [`cli.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/cli.ts) lines 459-468 with `--daemon-url` and `--json`. All gated on the workspace-identity machinery when the project is team-bound; personal/local projects are open to the daemon token. (verified)

**Feed to the agent.** Two paths, both landing in the same place:

- *Send to chat*: the UI's "Send to chat" button stages comments as `commentAttachments` on the next `POST /api/runs` (composer staging in [`ChatComposer.tsx`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/web/src/components/ChatComposer.tsx); request field in [`chat.ts` contract](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/packages/contracts/src/api/chat.ts)).
- *Saved pins*: saved comments go through the same attachment serialization when sent.

[`chat-prompt-inputs.ts`](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/apps/daemon/src/runtimes/chat-prompt-inputs.ts) `renderCommentAttachmentHint` serializes them into an `<attached-preview-comments>` prompt block carrying elementId, file, label, position, currentText, htmlHint, computedStyle, optional screenshot path + markKind + image attachments — wrapped in a **hard-scope instruction**: change ONLY the identified elements, surface anything outside scope as a follow-up note instead of editing. Mid-run feedback queues as `RunSubmission { source: 'queue' }` and delivers after the current turn (the 0.10.0 "comment at the speed of thought — into a queue" feature, [RELEASE-NOTES-0.10.0.md](https://github.com/nexu-io/open-design/blob/07258801b9e4ae80553816bb1606af7aa9a63dff/RELEASE-NOTES-0.10.0.md)). (verified)

**Team/sharing.** On shared (team-workspace) projects, comments sync through OpenDesign's collab cloud relay with a durable local outbox (`apps/daemon/src/collab/comment-relay-outbox.ts` and ~25 sibling files); external "user" authors can comment via share link + sign-in (`authorKind: 'user'`). For a single-user local daemon none of this is needed. (verified of the code; team flow not operated)

## 3. Cairn's current prototype flow (for comparison)

`options-prototype-cairn` produces **one static grayscale HTML file** — three structural directions switched with keys `1/2/3`, `E` cycling states, handwritten why-notes with arrows. It is saved under `.claude/prototypes/` (gitignored), opened with `open <file>`, and ian picks a direction *in the conversation*. There is no element-level feedback channel: defects and picks come back as prose. (verified: `.claude/skills/options-prototype-cairn/SKILL.md`)

In the product today, produced artifacts surface as **made-cards** on the board whose preview is a static `<img src={previewUrl}>` ([`made-carousel.tsx` apps/web/src/board/made-carousel.tsx](apps/web/src/board/made-carousel.tsx) lines 99-107) and a **file preview panel** rendering text/markdown/image attachments ([`file-preview-panel.tsx`](apps/web/src/board/file-preview-panel.tsx)). There is no live-iframe artifact preview in Cairn, so there is currently nowhere for a comment pin to live inside the product — adopting the pattern means adding the iframe surface first. Task input arrives via `POST /api/todos/:id/messages` → `messageThreadAsUser` ([`routes-todos.ts`](apps/server/src/routes-todos.ts) line 89), and a connector/action registry exists (`connectorActionId` in `packages/shared/src/action-registry.ts:136`). ## 6. Recommendation

### (1) Cairn team uses OpenDesign for annotated prototypes — **yes, pilot it now; effort ~half a day; reversible**

The flow needs nothing beyond the Docker image:

1. Agent (or the `options-prototype` step) produces HTML with `data-od-id` on commentable elements — add one line to the prototype template/skill instructing that. Cost: one template edit.
2. Create project + upload file over REST (two curl calls; a 50-line script could wrap create+upload+print-URL).
3. ian opens the workspace URL, enters Comment mode, clicks, notes; saved or mid-run comments both land in the same table.
4. The working agent polls `GET …/comments` (or `od comment list --json --daemon-url …`), formats `elementId`/`selector`/`htmlHint`/`note` into its prompt context, and marks `resolved` via PATCH when done.

Effort: a scratch script + one template line; the review loop needs no Cairn code. Risks: (a) ian must keep a container/app running and learn OD's project model — the prototype link replaces "open file.html" with "open OD workspace", mildly heavier; (b) fuzzy anchoring on our files is weaker than OD-generated files until our template emits `data-od-id`; (c) the ghcr `latest` image lagged the repo (0.25.1 vs 0.27.2) — pin a version tag, not `latest`. Open issues worth knowing: [#9230](https://github.com/nexu-io/open-design/issues/9230) comment context dropped on their newest runtime path, [#9303](https://github.com/nexu-io/open-design/issues/9303)/[#9305](https://github.com/nexu-io/open-design/issues/9305) comment-save failures in team contexts, [#7008](https://github.com/nexu-io/open-design/issues/7008) cannot comment into nested iframes — none block the single-user local flow. (derived on the workflow, verified on every API it touches)

### (2) Cairn product integration — **two of the three shapes are viable; recommended order is B then A**

- **(a) OD as a driven service (task → OD workspace → comments back as task input):** technically clean — `POST /api/import/folder` or `/api/projects`, `POST /api/runs` with our chosen agent/BYOK, `GET …/result-package`, comments polled into `POST /api/todos/:id/messages`. Effort: days — OD lifecycle (container or bundled daemon), port/token management, artifact upload, comment→message formatting, status mapping. Risks: shipping a second product's daemon with a weekly release cadence; OD overlaps Cairn's own control-plane role, so we'd be running an agent orchestrator inside our agent orchestrator; comment reads are REST-only (their MCP has no comment tools). *Do it only if the (1) pilot proves ian actually annotates this way.*
- **(b) Adopt the pattern natively in Cairn previews:** the copyable core is small — serve result HTML through our server with an injected bridge script (click → element picker → selector+htmlHint+bbox+computed style), store a comment row, render pins over the iframe, fold open comments into the next `messageThreadAsUser` payload or a dedicated comment step. Skip their team cloud, pin serialization and drift ladder on day one; anchor on `data-od-id`-equivalent (`data-cairn-id` our generators emit) + selector fallback. Effort: the biggest of the three (a real feature: preview iframe surface doesn't exist in Cairn today — made-cards are static images), call it a week for a minimal honest version. It owns the loop, needs no dependency, and is exactly what (1) validates before building.
- **(c) OD as Cairn app/connector via MCP:** weakest fit. `od mcp` covers start_run/get_run/files — making a prototype yes, reading comments **no** (no comment tools). The comment leg would drop to REST anyway, so the connector adds a transport without removing work. Not recommended.

Bottom line: pilot (1) this week — it costs a template line and a script. If ian's annotation rate justifies it, build (2b); treat (2a) as the fallback if we want OD's generation skills too, and skip (2c).

## 7. Can OpenDesign replace options-prototype as the base for our prototypes?

Question added by ian mid-research: can Open Design replace our hand-built grayscale HTML prototypes — the options-prototype skill — as the base, so we stop building that tooling ourselves. One premise check first: the current skill (repo `options-prototype-cairn` and the global `options-prototype`, both read) has **no click-anywhere comment mode and no comments.md export** — feedback returns as prose in the conversation. So the comparison is against the tooling as it actually is: one HTML file, three directions on keys `1/2/3`, `E` cycling states, handwritten why-notes, `open <file>` to hand over. (verified)

Answers, each verified on the running container (0.25.1, 2026-11-20):

- **Can it render an arbitrary local HTML file or a generated prototype?** Yes. I hand-wrote a miniature options prototype (three directions, `1/2/3` keys, note panel, `data-od-id` on elements) and uploaded it with `POST /api/projects/:id/files`; the daemon versioned it and served it with the preview bridge. Caveat: it renders inside OD's device-viewport surface — a "Desktop" fit-zoom container, my 1200px stage showed at 55% — usable, but smaller and less bare-window than `open file.html`. (verified)
- **Can the owner click an element and leave a comment?** Yes, on our format. Comment mode → click the CTA → popover with label/size/color/font → note saved → the comment badge counts it. Strongest anchor needs `data-od-id`; our template has none today (one line to add). (verified)
- **Can comments be exported or read by an agent (file / API / MCP)?** API: `GET …/comments` JSON plus unread tracking via `comments/read` — verified by reading back the UI-created comment. CLI: `od comment list --json` (TSV/`--json`, `--daemon-url` for a remote daemon).
