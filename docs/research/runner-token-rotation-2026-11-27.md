# Prior Art: Runner / Agent Token Rotation (2026-11-27)

## Designated Sources and Findings

| Source | How it rotates / re-authenticates agent credentials | Trade-offs | Link |
|---|---|---|---|
| Tailscale | [verified] Node keys expire (180 days default for user-authenticated nodes). Admin console row `...` menu offers `Temporarily extend key` (30m) or `Reauthorize machine` (when a new auth URL is already signed), and `Disable Key Expiry` / `Enable Key Expiry`. Actual key renewal happens on the host via `tailscale up --force-reauth`; Tailscale warns running it over Tailscale SSH drops the active session. | Strong trust boundary (new key must be initiated/authenticated on the node), so a compromised machine cannot hijack a pushed key; however, admins cannot silently push a fresh credential to an online machine in one click from the console. | https://tailscale.com/docs/features/access-control/key-expiry |
| GitHub Actions self-hosted runners | [verified] Registration uses a short-lived (1h) registration token (`config.sh --token`), exchanged once for a host-local RSA key pair (public key stored on GitHub, private key kept on disk), which mints ephemeral per-job tokens. There is no server-initiated in-place token rotation: recovery requires removing the runner in Settings → Actions → Runners (or deleting `.runner`) and re-registering. | Minimal blast radius for job tokens and zero long-lived static bearer secret, at the cost of losing the runner registration row, identity, and configuration whenever credentials must be rotated. | https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/remove-runners ; https://docs.github.com/en/rest/actions/self-hosted-runners ; https://docs.github.com/en/actions/concepts/security/compromised-runners |
| Buildkite agents | [verified] Separates a long-lived cluster/organization agent token (`BUILDKITE_AGENT_TOKEN`) from internal session tokens (valid until disconnect) and job tokens (valid until job finish). Supports optional `expires_at` and two-tier revocation: `Revoke token` (blocks new agents, connected agents continue) vs `Revoke token and agent access` (rejects derived session/job credentials and triggers agent shutdown). Rotation is manual: create a new token, update secrets/agent config, restart/roll agents, then revoke the old token. | Clean separation between bootstrap credential and runtime session/job credentials, plus safe rollout when rotating proactively; still requires out-of-band config distribution and host restarts rather than one-click UI rotation. | https://buildkite.com/docs/agent/self-hosted/tokens |
| Cairn today (`POST /api/machines/:id/revoke`) | [verified] Clears `tokenHash = null`, sets `retiredAt`, clears `team.defaultMachineId`, marks offline, and sends SSE `shutdown` (`apps/server/src/services/machine-revoke.ts`). `apps/web/src/resources/machine-row.tsx` only offers `设为默认执行机` and `删除执行机`. | Invalidates the leaked token at once, but retires the machine row, clears the team default, and forces a full re-pair. | `apps/server/src/services/machine-revoke.ts` ; `apps/web/src/resources/machine-row.tsx` |

## Pattern That Fits Cairn

- **Preserve the machine identity and routing state**: Unlike GitHub Actions (which deletes and recreates the runner row), Cairn's `machine.id` is referenced by `team.defaultMachineId`, `routingRule.machineId`, `todo.routeOverride`, `step`, `phone`, and `computer`. In-place rotation updates `machine.tokenHash` on the existing row without retiring it or clearing defaults/routes/history.
- **Two-phase authenticated handoff for online runners (inspired by Buildkite's live session separation, adapted for Cairn's SSE + HTTPS channel)**:
  1. Server generates a fresh token (`newMachineToken()`) and `rotationId` in memory only (never returned to the web UI, never persisted as plaintext, never broadcast on SSE).
  2. Server pushes `{ type: 'token.rotate', rotationId }` over the runner's active `/api/machine/stream` SSE connection (`MachineWakeHub`).
  3. The runner claims the replacement token over its authenticated HTTPS channel (`POST /api/machine/token-rotate/claim` with `{ rotationId, connectionId }`, `Cache-Control: no-store`), atomically writes `machine.json` (`0o600`), and proves receipt via `POST /api/machine/token-rotate/ack` authenticated by the **new** token.
  4. Only upon `ack` (or upon timeout/disconnect/offline) does the server commit `tokenHash = H(new)` atomically with optimistic CAS (`WHERE tokenHash = oldTokenHash`), immediately returning `401` for the old token on every machine endpoint while handing off the old SSE connection cleanly (without `shutdown`, entering the 45s offline grace) so the runner stays Online and in-flight steps continue.
- **Immediate cutover + single-step reconnect guidance for offline or unreachable runners**: When the runner is offline, disconnected mid-handoff, or fails to acknowledge within 5s, the server immediately commits `tokenHash = H(new)` (old token returns `401` at once) and sets `machine.tokenReauthRequired = true`. The Runners row surfaces `需要重新连接` and the exact one-line reconnect command (`CopyCommand`) until that computer reconnects or re-enrolls.
- **Threat-model boundary (learned from Tailscale & Buildkite)**: Pushing a new token over the existing channel is designed for leaked credentials (`machine.json` or token pasted into chat/logs) or routine rotation on a machine the owner still controls. If a laptop was stolen or a teammate left and still holds the device, the owner should use `删除执行机` (or `POST /api/machines/:id/revoke`) so an untrusted device cannot claim the rotated token.

## Concrete Recommendation and Touched Areas

- `packages/shared/`: extend `machineRecordSchema` (`tokenReauthRequired`), `machineStreamEventSchema` (`token.rotate`), `MACHINE_WIRE_EXTENSIONS` (`/api/machine/token-rotate/claim`, `/api/machine/token-rotate/ack`), and add `rotateMachineTokenResponseSchema`.
- `apps/server/`: add `machine.tokenReauthRequired` column + Drizzle migration; add `pushTokenRotate` and `handoffConnection` on `MachineWakeHub`; implement `rotateMachineToken`, `claimMachineTokenRotation`, and `ackMachineTokenRotation` in `apps/server/src/services/machine-rotate-token.ts`; register `POST /api/machines/:id/rotate-token` and the two `/api/machine/token-rotate/*` endpoints.
- `apps/daemon/`: handle `token.rotate` in `machine-loop.ts` via `MachineClient.claimTokenRotation` / `ackTokenRotation`, persist `machine.json` before ack, swap `inMemoryToken`, reconnect SSE with 0ms backoff, and retry 401 claims immediately when `inMemoryToken` rotated.
- `apps/web/`: add `更换令牌` (`shortcut="R"`) with one-step in-menu confirmation (`确认更换令牌`) in `apps/web/src/resources/machine-row.tsx`, toast feedback, and offline `tokenReauthRequired` status + `CopyCommand` drawer.
