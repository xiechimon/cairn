## 1. Newcomer Framing: What a Cairn User Meets

For a developer who installed Cairn today and wants to talk to their Coordinator from Apple Messages on iPhone:

- **Where they meet it**: **Settings → Chat Apps (`im-connections`)** (`apps/web/src/routes/im-page.tsx`). Selecting **iMessage** asks them to pick an already-enrolled always-on Mac Runner. `实测`
- **What they must already have**: An always-on Mac signed into Messages.app (either their own Apple ID for "text yourself" self-chat, or a dedicated bot Apple ID), kept awake (`caffeinate` / Energy Saver), with Cairn's daemon (`@xiechimon/cairn-cli`) running on that Mac. `实测` ([docs/design/remote-reach.md](../design/remote-reach.md), [apps/web/src/routes/im-page.tsx](../../apps/web/src/routes/im-page.tsx))
- **Accounts, keys, and permissions asked**: Zero cloud API keys or fees for the local `imsg` path (`$0`). macOS requires two TCC grants in **System Settings → Privacy & Security** for the **parent process hosting the Cairn daemon** (e.g., `node`, Terminal, or Cairn.app): (1) **Full Disk Access** to read `~/Library/Messages/chat.db`, and (2) **Automation → Messages** for `/usr/bin/osascript` to send replies. Contacts access is optional (name lookup only). `实测` ([openclaw/imsg permissions.md](https://github.com/openclaw/imsg/blob/v0.21.1/docs/permissions.md))
- **Where credentials/state live**: The bound `machineId` is sealed in Cairn's existing SQLite `im_connection.secretCipher` via `KeySecretBox`; `imsg` itself runs locally on the Mac and stores nothing in the cloud. Cairn auto-downloads `imsg` `v0.21.1` into `~/.cairn/imsg/imsg` with SHA-256 verification. `实测` ([apps/daemon/src/imsg-bridge.ts](../../apps/daemon/src/imsg-bridge.ts), [apps/server/src/services/im/core.ts](../../apps/server/src/services/im/core.ts))
- **Where users get stuck today**: First-time TCC prompts can be missed or misbound to the wrong parent process; macOS app/OS updates can leave stale TCC entries; if Full Disk Access or the Mac goes offline, the current UI (`im-page.tsx`) hides the Reconnect button on `degraded` connections and gives no macOS permission checklist. `实测`

### Key Technical Takeaways from Prior Art

1. **`imsg rpc` (`openclaw/imsg`) remains the clear best substrate for Cairn.** BlueBubbles adds Electron, unsigned `.dmg`, and Firebase baggage while OpenClaw itself abandoned it for `imsg`; DIY `chat.db` + `osascript` reimplements hard-won edge cases (`typedstream`, WAL rotation, Tahoe ghost rows, 8s verification, disposition tracking); `@photon-ai/imessage-kit` adds a native `better-sqlite3` ABI dependency to Node without matching `imsg`'s RPC isolation; and Linq/Sendblue/Messages for Business violate either Cairn's `$0` local-first positioning or its outbound-only (no public webhook) rule. `实测` / `推断`
2. **SIP-disabled private IMCore is unsuitable as Cairn's default.** On macOS 15/26 (Sequoia/Tahoe), Apple's library validation and `imagent` entitlement checks actively break dylib injection, and requiring `csrutil disable` disables Apple Silicon iOS-app support and weakens host security on a Mac that also runs Cairn tasks. Cairn's choice to stay on standard `imsg` (FDA + Automation only, numbered text replies for cards) is right. `实测` ([imsg advanced-imcore.md](https://github.com/openclaw/imsg/blob/v0.21.1/docs/advanced-imcore.md), [BlueBubbles Private API](https://docs.bluebubbles.app/private-api/installation))
3. **Where OpenClaw leads Cairn is operational closed-loop hardening around `imsg rpc`.** OpenClaw doesn't change the `imsg` transport — it wraps it with `since_rowid` cursor recovery, backlog-bomb fencing, separate send-vs-watch permission health reporting, and explicit TCC diagnostics. `实测`

### B. Remaining Open Closed-Loop Gaps (Requires Design / Product Decisions)

1. **No `since_rowid` recovery across restarts & no push-flush backlog fence (`HIGH`)**:
   - `apps/daemon/src/imsg-bridge.ts` calls `watch.subscribe` with `{ attachments: true }` and no `since_rowid`. Whenever `imsg rpc` respawns (crash, `-32004`, `watch.overflow`) or the Mac reboots, messages arriving during the gap are permanently dropped (`imsg` defaults `since_rowid` to `maxRowID()`). `实测`
   - Conversely, blindly passing a very old `since_rowid` without a stale-backlog age fence risks triggering an Apple Push-flush "backlog bomb" (OpenClaw fences live rows >15 min old and caps replay to 500 rows / ~2h). Note that `im_connection.pollOffset` already exists in `apps/server/src/db/schema.ts`, and `imSeenInbound` already dedupes `msg-<rowid>`. `实测`
2. **Binary resolution mismatch with design doc & platform guard (`MEDIUM`)**:
   - `docs/design/im-bridge.md` specifies `CAIRN_IMSG_BIN → managed ~/.cairn/imsg/ → PATH`, whereas `ensureImsgBin()` (`apps/daemon/src/imsg-bridge.ts`) checks `CAIRN_IMSG_BIN` and `~/.cairn/imsg/imsg` only, ignoring Homebrew `imsg` on `PATH` and downloading `imsg-macos.zip` unconditionally without checking `process.platform === 'darwin'` first. `实测`
   - On `ensureImsgBin()` failure (e.g., offline Mac or non-macOS host), `runSession` schedules infinite backoff retries up to 60s. `实测`
3. **Outbound AppleScript Automation (`-1743`) & timeout (`-1712`) errors are invisible on connection status (`HIGH`)**:
   - Because `watch.subscribe` only needs Full Disk Access, a connection can report `status: 'ready'` while every outbound reply fails with `-1743` (*Not authorized to send Apple events to Messages*) or `-1712` (timeout / hidden TCC modal). `实测` ([OpenClaw troubleshooting](https://docs.openclaw.ai/channels/imessage/troubleshooting))
   - In `imsg-bridge.ts`, `imsg` `-32603` (internal/AppleScript error) falls through to `'retry'`, triggering 4 retries before `core.ts` writes `sendErrors.set(connId, ...)` in memory only (lost on server restart; `conn.status` stays `'ready'`). `实测`
   - In `machine-loop.ts` (`imsg-bridge.ts` line 379), `imsg rpc` spawns with `stdio: ['pipe', 'pipe', 'inherit']`, so stderr diagnostics never reach `statusDetail` or Settings > IM. `实测`
4. **Settings > IM UI ergonomics & TCC onboarding gap (`MEDIUM`)**:
   - `apps/web/src/routes/im-page.tsx` only renders `repairButton` (`Reconnect`) when `conn.status === 'expired' || conn.status === 'error'`. Because `imsg-bridge.ts` posts `status: 'degraded'` for missing FDA, `watch.overflow`, or offline Mac, users see `"degraded"` (`不稳定`) with **no Reconnect button** and **no macOS TCC guide** (which parent app needs FDA, Automation → Messages, toggle-off/on after updates, Mac keep-awake). `实测`
   - `ImessageConnectDialog` (`im-page.tsx` lines 409–414) falls back to `allMachines` if no machine reports `capabilities?.osPlatform`, potentially letting a user select a Linux machine when its capability probe hasn't landed yet. `实测`
5. **Multi-chunk send retry amplification, card-slot overwrite, and self-chat `sender` variance (`MEDIUM`)**:
   - `apps/server/src/services/im/imessage.ts` chunks texts >60,000 chars (`IM_SEND_TEXT_CHUNK`), but only creates a `trackedSent` ack promise for the *last* chunk; if chunk 2 times out (`retry`), `core.ts` retries the entire message and duplicates chunk 1. `实测`
   - `session.cards` in `imsg-bridge.ts` is a `Map<chatKey, ...>`, so two concurrent question/approval cards in the same chat overwrite the earlier card, and `replyToMessageId` on `im.send` is ignored (requires SIP-off bridge, so plain/quoted text fallback is the non-SIP boundary). `实测`
   - `imsg` `v0.20.0+` populates `sender` with the user's own account on outgoing 1:1 messages (`CHANGELOG.md` `#358`), whereas `senderIdOf()` falls back to `'self'` only when `msg.sender` is empty. In real self-chat across iPhone + Mac mini (`#5392`), the pairing request sender ID may be the Apple ID email/phone rather than `'self'`, and must be verified live on the Mac mini. `推断`
6. **End-to-end live verification on a physical Mac mini remains unexecuted (`BLOCKER for production sign-off`)**:
   - Issue `#5392` was closed/deferred on 2026-11-24 pending physical Mac mini Apple ID sign-in. Every test in `imsg-bridge.test.ts` and `im-imessage.test.ts` runs against a mocked `ChildProcess` / fake RPC stream. `实测`
