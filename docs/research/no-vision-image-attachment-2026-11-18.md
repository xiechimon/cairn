# Image attachments delivered to a text-only model: prior art and fallback design

Started: 2026-11-18. Scope: a user pastes a screenshot into a chief thread; the chief's driving model is text-only (`input: ['text']`). The coordinator's `attachment` tool returns an opaque image block the model cannot perceive, and no tool path exists to read the bytes. What do comparable agent runtimes do when a tool result or user message carries an image to a model without image input — strip it, send it anyway, substitute text, materialize it to a path, or delegate it to a vision model — and which fallback fits cairn's coordinator?

## The pattern that fits cairn and why

Every inspected runtime that does handle the case converges on **capability check → text substitution**: pi-ai downgrades at the adapter, Codex strips at prompt build (and refuses at tool level, and blocks at paste level), cairn's own daemon skips delivery and notes it in the prompt. None of them recover the content — except the community `cc-vision-hook`, which is the only measured instance of the delegation pattern: send the image to a configured vision model, return a description, cache it. The four realistic options for cairn's coordinator:

**a. Honest text placeholder in the `attachment` tool** (symmetric with `computer_observe`). The `seesImages` check already exists at `tools.ts:172`; applying it at `:202` is a few lines. The placeholder can name `fileName`, `sizeBytes`, `mimeType` — all present in the relay JSON (`chief-tools.ts:639-647` returns full `readAttachmentMeta`) — and name a next step (ask the owner via `ask_user`, matching `SCREENSHOT_UNAVAILABLE_OBSERVE`'s style of pointing at alternatives). It also makes the *stored* toolResult text, so transcript and wire agree and replay/rewind stays clean (same hygiene argument as `cold-slim.ts:102-108`'s post-use omission note and pi-coding-agent's `<file name>` handle). What the agent does next: only escalate to the human — the content is unrecoverable. Cheapest, zero new failure classes.

**b. Coordinator-side vision-caption sub-call returning text.** Inside the tool's `execute`, `api.models` is the full `Models` catalog — `getModels().find(m => m.input.includes('image'))` discovers a vision-capable model among the registered providers (fixed + router + summary + step), and `api.models.completeSimple(visionModel, { messages: [{ role:'user', content:[text, image] }] }, { maxTokens, timeoutMs })` performs the caption exactly like `suggest-replies.ts:113` and `summarizerFor` (compaction.ts:184) already do. The runtime is a named seam exception for LLM access, so this is architecturally legal; a turn-span emit like `recordSuggestionSpan` (suggest-replies.ts:153-175) keeps it observable in Langfuse. What the agent does next: reads the transcription/description and usually answers directly — this is the only option that restores actual content, and the incident's class (a screenshot) is precisely where a vision model's description beats raw OCR. Cost: one extra model call per image fetch, a new latency/failure edge, caption fidelity risk (mitigate with "transcribe visible text verbatim first, then describe"), and discovery depends on a vision model being registered on the thread's catalog.

**c. Materialize to a path + agent self-OCR.** Dead end for the chief: its tool surface is remote-relayed defs (no Read, no bash, no filesystem tool — `coordinatorToolDefs`/chief-tools.ts). The bytes already live server-side at `attachmentsDir/<storageKey>` (attachments.ts:325-331), but nothing the chief can call would read them, so a path alone is a locator with no reader. Workers already have this via `resolveStepImages` because they hold fs tools. Pairing materialize with a *server-side* reader collapses into (b) or a tesseract subprocess — i.e. the reader, not the path, is the substance.

**d. Combination: caption when a vision model is discoverable and the call succeeds; otherwise the honest placeholder.** The failure union is small and orderable: no vision model in `getModels()` → placeholder; `completeSimple` throws/times out/stops non-`stop` → placeholder (never `isError` — the tool's job is to return what it can). Under (d) the agent's next step degrades gracefully: full description when a vision route exists, owner escalation when it does not — and either way the stored message is text.

**Recommendation: (d) extended to three tiers, inside the coordinator, at the tool boundary.** Rationale: pi-ai already guarantees the wire never hard-rejects, so the only open question is content recovery, and only a vision call recovers content for a screenshot; `cc-vision-hook` demonstrates the pattern works on real sessions. Doing it inside the tool (not via hook/`additionalContext`) is *stronger* than the reference implementation: cairn owns the tool result, so it can return text *instead of* the image, avoiding cc-vision-hook's known limit. Owner ruling (2026-11-18): **tesseract OCR is the tier between caption and escalation** — the machine should read the image itself before ever asking the user, and the result must be labeled as OCR. So the chain is: vision caption → tesseract OCR (labeled transcript) → honest placeholder with `ask_user` only when nothing else can read the image. Materialize-to-path (c) is rejected for the chief as unactionable.

## Concrete recommendation

1. **`apps/server/src/coordinator/runtime/tools.ts`** — in `coordinatorTool`'s `execute`: lift the existing model/`seesImages` resolution (`:167-172`) so the `attachment` branch shares it. In the `def.name === 'attachment'` branch (`:196-207`), when `attachment.mimeType.startsWith('image/')`: if `seesImages`, keep `prepareCoordinatorImage`; else call a captioner and return `[{ type:'text', text: <caption + attribution> }]` on success or `[{ type:'text', text: <placeholder naming fileName/sizeBytes and the next step> }]` on failure. The placeholder should mirror `SCREENSHOT_UNAVAILABLE_OBSERVE`'s shape: state the limit, name the artifact, point at `ask_user` (owner can describe the screenshot) — e.g. `"Attachment <fileName> (<mimeType>, <sizeBytes> bytes) is an image; this model cannot see images, and no vision-capable model is configured to describe it. Ask the owner for a text description via ask_user."` (wording to match repo voice; final wording is a detail).

2. **New `apps/server/src/coordinator/runtime/image-text.ts`** (name TBD): `describeImageForModel(models, image: { data, mimeType, fileName? }, opts)` — discovery `models.getModels().filter(m => m.input.includes('image'))`, preference order: same provider as the driving model first, then lowest declared `cost.input`, then stable id order (deterministic, no new config). Call `models.completeSimple(visionModel, { messages: [{ role:'user', content: [captionPrompt, imageBlock] }] }, { maxTokens ≈ 1200, timeoutMs ≈ 45_000, toolChoice:'none' })` — parameters in cc-vision-hook's measured range (`timeoutMs 45000, maxTokens 1200`). Prompt: "Transcribe all visible text verbatim, then describe the image for an agent that cannot see it." Attribute the result (`"Attachment <fileName> described by <provider>/<modelId>:"`) so the transcript does not misattribute generated text to the owner. Emit a coordinator turn span like `recordSuggestionSpan` does. Non-`stop` results, throws, timeouts → `undefined` → caller falls to the placeholder.

3. **What to do when no vision model is configured**: run the tesseract OCR tier before any escalation — `tesseractOcrRunner` probes the binary (`--list-langs`, cached), writes the bytes to a temp file and transcribes `stdout` (`-l eng+chi_sim` reduced to whichever preferred languages the binary reports, 30s timeout, output cap). Its transcript is labeled as machine OCR. Only when the binary is missing or fails does the (a) placeholder run. Landed in `runtime/image-text.ts` with this change; the step-log line and a transcript marker remain follow-ups.

4. **`resolveStepImages` / worker path**: leave unchanged in this change (single path per change; the worker's skip-and-note is deliberate and workers can Read materialized paths). If the owner wants workers to get captions too, that is a follow-up in `apps/daemon/src/` using its `ModelRuntime`/`completeSimple` surface — flagged, not folded in.

5. **Tests** (`apps/server/test/coordinator/tools.test.ts`, the existing `toolThenAnswer` harness already parameterizes `input: ['text']` at `:194` and `fauxProvider` accepts per-model `input` at `:53`): (a) red test — text-only model + image relay returns image block today (visible as `(tool image omitted…)` on the wire); after the change assert a *text* toolResult that names `image.png` and contains either the caption or the guidance, and no `type:'image'` block; (b) vision model registered on the same faux provider → caption text returned and attributed; (c) caption call failing → placeholder naming the file. Optionally cache captions by `attachmentId` (cc-vision-hook caches by content hash) — decide in implementation; not required for correctness.

6. **Do not touch**: `boundCoordinatorImages` / `imageOmissionNote` (they bound vision-model transcripts; with text-returning tools the no-vision case never stores an image block anyway), `readAttachmentMeta`, `mcp-face.ts:207`, `machines.ts:710` (see open questions).

## Open questions for the owner

1. Should the caption call's image content be fenced/attributed in the transcript like `untrusted-report` content is (`chief-tools.ts:640-646`)? A caption is model-generated text about an owner-supplied image — low risk, but it re-enters the context as text the chief will trust.
2. Discovery scope: is searching the thread's *registered* catalog (`api.models.getModels()` = fixed + router + summary + step providers) enough, or should a vision model be discoverable across **all** team providers (a `provider`-table scan + `providerBinding`-style key resolution)? The registered-catalog approach covers the common case (a team whose router/summary provider has Claude) with zero new plumbing.
3. Should captioning be a routing concern — a new `ROUTING_USES` slot (`model-routing.ts:3-10`) or reuse `coordinator`/`mechanical` — and should the banned-model list surface apply to whichever model is picked?
4. Cache policy: per-`attachmentId` in-process memo, DB row, or none? Re-fetching the same attachment currently re-runs the caption.
5. Does the MCP face (`mcp-face.ts:207`) need the same guard — external MCP clients calling `attachment` get raw base64 JSON regardless of their own image capability — or is that the client's contract?
6. ~~A tesseract tier as a zero-provider fallback~~ — resolved by the owner: wanted, landed as tier two. Deployments without tesseract degrade to the placeholder unchanged.
