# Prior Art: Command Execution and Sandboxing in OpenClaw and OpenManus

Research date: 2026-11-25. Compares how two open-source personal agents (**OpenClaw** and **OpenManus**) execute shell commands on a user's own computer and what sandboxing and approval controls they apply, alongside **Cairn**'s current implementation verified from this worktree.

2. **What is denied by default**:

## What Fits Cairn and Why

For a newcomer who installs Cairn on their Mac today and asks the Coordinator to operate on local files, apps, and toolchains, **Cairn's Coordinator model is materially stronger than both OpenClaw's and OpenManus's defaults**: `推断`

- **Why OpenManus's pattern does not fit**: Default-unsandboxed host execution (`PythonExecute` + `Bash`), a `use_sandbox` flag wired only into `StrReplaceEditor`, and a Docker helper running `exec_create(..., privileged=True, user="root")` show what happens when container isolation is bolted on as an afterthought — users think they are protected while the actual shell/code path runs unconfined or privileged. `实测` / `推断`
- **Why OpenClaw's default (`mode: "off"`, `security: "full"`, `ask: "off"`) and Docker-only sandbox do not fit Cairn's Coordinator**: OpenClaw gives zero host confinement out of the box, and once turned on, Docker/Podman isolates the agent *away* from the owner's Mac filesystem, apps, and local dev tools — requiring Docker Desktop / Colima setup and breaking the Coordinator's core purpose (working directly on the user's own computer). Conversely, Cairn's per-command Seatbelt/`bwrap` deny-overlay works out of the box with zero setup, lets ordinary local commands run smoothly, and protects credentials, Keychains, Mach escape hatches, and Cairn's own server port by default. `推断`
- **Why OpenClaw's `allow-always` persistent shell allowlist should NOT be copied onto Cairn's `host.shell.escalate`**: Because `user_computer_shell` runs arbitrary `bash -lc` strings, remembering "always allow unsandboxed" for a binary or pattern punches a permanent hole through credential confinement. Even OpenClaw had to build a large SQLite/Postgres policy engine, executable realpath/content-hash binding, single-file-operand drift checks, and `strictInlineEval` (`python -c`, `node -e`, `osascript -e`) just to keep `allow-always` from becoming a bypass. Keeping Cairn's unsandboxed escalation strictly `allow-once` is simpler and safer. `推断`
- **What DOES transfer cleanly from OpenClaw to Cairn**:
  1. **Host execution hygiene on the unsandboxed/host path**: OpenClaw's explicit rejection of loader/PATH overrides (`DYLD_*`, `LD_*`, `PATH`), `RLIMIT_CORE=0`, and awareness of inline-eval / mutable-script TOCTOU drift during human approval waits. `实测` / `推断`
  2. **Closing the Coordinator vs. Coding-Task confinement gap without reviving `pi-host` or requiring Docker for every local Mac user**: Today Cairn's Coordinator commands are OS-confined while coding-task commands (`pi`, `claude-code`, `acp`) run completely unconfined on the host (`0b0d06261`). Reusing Cairn's already-shipped per-command `createHostShellConfinement` (`host-shell-confinement.ts`) on coding-task bash calls gives immediate credential/Keychain/escape-binary protection with zero Docker dependency, while OpenClaw's hardened Docker flags (`--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--network none`, `validateSandboxSecurity` bind denylist) serve as the blueprint if Cairn later offers an opt-in container backend for untrusted/remote tasks. `推断`
