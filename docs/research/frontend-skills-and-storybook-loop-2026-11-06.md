# What makes good-looking AI frontends: your starred skills, the Storybook self-check loop, and the gap to the cairn gallery (2026-11-06)

Labels: **`实测`** = original text, files or command output read in this round (including original text read by this round's sub-agents); **`推断`** = derived from `实测`, can be re-checked; **`猜测`** = everything else. This note is research only; no code was changed. What the previous note [`ai-frontend-quality-2026-11-06.md`](ai-frontend-quality-2026-11-06.md) already covered is not repeated here: the Vercel DESIGN.md eval, Anthropic's frontend-design skill, reference-product briefs, PR screenshot statistics and recommendations R1-R7. This note adds only three things: the mechanisms of the starred repositories, the concrete practice of the Storybook loop, and an item-by-item comparison with the gallery.

## 0. Conclusions

- **Use both, but quality is really held in the repository process.** Of the 23 relevant repositories, 8 give only a skill (plain-text instructions): emilkowalski/skills, jakubkrehel/skills, make-interfaces-feel-better, garden-skills, cult-ui, mattpocock/skills, karpathy-skills, and the current baoyu-design. Their evidence of effect is all supplied by the authors themselves. The ones that can offer "run it and you know whether it passed" are skill plus script:
  - impeccable's `detect`, 65 rules, runnable in CI;
  - taste-skill's `consistency.mjs`, 100-plus geometric checks;
  - agent-native's guard, which scans only added lines;
  - archify's `browser-check`, which checks clipping, occlusion and small text;
  - diagram-design's `lint-render.py`, which takes one screenshot before and one after releasing overflow and compares them;
  - base-ui's Argos pixel regression.

  (`实测`)
- **The skill sets direction, the script proves.** A rule written as text is not necessarily acted on after the agent reads it. agent-native's guard file records: the same correction appeared 79 times in two weeks, three rewrites of the text rule did not suppress it, and finally it was changed to a script interception (`实测`). This is the same conclusion as ian's "corrections rely on constraints" (`推断`).
- **No vendor has the agent automatically take a reference image and judge "is it good".** Each one's approach:
  - Amp: the agent screenshots and eyeballs it itself, comparing against the intent described in the prompt (`实测`).
  - Storybook MCP: runs only interaction tests and a11y tests, and explicitly leaves "does it look good" to humans (`实测`).
  - Chromatic, Argos: baselines must be accepted by a human (`实测`).
  - Claude Code official: endorses "a browser screenshot next to the mockup" as a check, but the mockup has to be pasted in by a person (`实测`).

  "Good" is ultimately set by humans. What machines can guarantee is only three things: what changed, whether anything broke (clipping, contrast, a11y), and whether the agent has looked.
- **The three things that matter most** (`推断`):
  1. Every state has a URL an agent can open directly, so a screenshot is cheap;
  2. Deterministic checks after rendering;
  3. Baseline changes must be put in front of a human.

  Structurally, the cairn gallery is already on par with Amp's "storybook": what Amp uses is also a self-built gallery route, not Storybook.js (`实测`). The gaps: a single state cannot be opened by URL, there is no 375px snapshot, there are no render-time checks, and nothing forces "it counts as done only after looking". The existing 6 UI gates are all source-level checks (`实测`).
- **What to copy**:
  - Do not move a whole skill over. taste-skill and garden-skills are written for marketing pages and would hurt a dense operations UI like cairn (`推断`).
  - What to take are these repository tools: shadcn's `data-preview` state pinning and coverage check, base-ui's "one snapshot automatically per demo", the render probes of archify / diagram-design, agent-native's added-lines-only guard, and Doop's reminder in tool output that "you have not looked yet".
  - Keep only a very short cairn UI loop note as a skill.

**Distilled mechanisms** (`推断`):
1. **One stable address per state**: Amp uses hash sections, Storybook uses story ids. With it, "taking a look" is cheap, which is the premise of the whole loop.
2. **How to open**: Playwright MCP navigate plus screenshot, or Storybook MCP preview plus test-run. None directly uses `iframe.html?id=`.
3. **The comparison target has three layers**:
   - deterministic tests: interaction, a11y, judged by machine;
   - the last accepted baseline: the machine reports "it changed", the human judges "is the change right";
   - intent or mockup: only the agent or a human eyeballing.
4. **There are only two enforcement points**: baseline approval blocking CI (Chromatic, Argos), and the harness Stop hook. Everything else is advice in AGENTS.md.

- There is also a page-level set: `?scenario=<id>` from `src/fixtures/scenario.ts`, 192 scenarios, effective only in dev and fixture mode.

## 4. Recommendation: a cairn version of the gallery self-check loop

Overall approach:
- Keep the self-built gallery, do not introduce Storybook. Reasons (`推断`):
  - Amp's practice already proves a self-built page is enough;
  - Storybook MCP provides no screenshots or visual diff, the very part cairn needs;
  - Migrating 127 specimens is costly.
- Fill in three things: state addresses, render-time checks, enforced looking.
- Pair every step with a check that can run.

**The part made into a skill**: a project skill of at most 80 lines (a new `ui-loop-cairn`, or a section of `verify-cairn`), plus one entry line in the root `AGENTS.md`. Content:
- When a specimen must be added, and the fixed state checklist (open-design's five states, plus disabled and pinned interaction states);
- Usage of `gallery:shot`, and the seven one-line self-assessment template (Doop);
- Review only the diff, marking each finding Introduced / Regression / Pre-existing (jakub `interface-review`);
- The motion scale (emil `review-animations`, extracting the 10 items);
- `break-ui`-style worst-case data (emil);
- Baseline tamper resistance, and the honest disclosure of "not reviewed by human eyes" (pstack, archify).

Feasibility is high: it is all text, and several reference repositories are MIT or Apache, so they can be rewritten and cited. Per the previous note's recommendation, each rule is A/B tested before being included (`推断`).

**The part made into repository tools**, which are what can be enforced:
- specimen id plus `?only=` / `theme` / `w` parameters (step 1);
- coverage test (step 1);
- `data-preview` pinning (step 2);
- `gallery:shot` script (step 3);
- render probe spec and contrast test (step 4);
- 375 snapshots (step 5);
- comparison image from the accept script, plus the pr-evidence rule (step 6);
- an added-lines-only anti-pattern guard (agent-native style), to carry the audit's anti-patterns and the previous note's R2 / R3.

The suggested order is 1 -> 6 -> 4 -> 3 -> 2 -> 5 -> 7. Reasons (`推断`):
- 1 and 6 are small changes and directly close the two biggest gaps, "no address" and "can accept without looking";
- 4 has the largest payoff but needs false-positive tuning, so it is third.

**Not recommended**:
- Introducing Storybook.js: MCP takes no screenshots and migration is costly (`推断`).
- Installing taste-skill or garden-skills wholesale: they are written for marketing pages.
- Having the agent automatically take a reference image to judge "does it look alike": no vendor does this, and impeccable's own `COMP-FIDELITY.md` also admits that a model judging a replica from memory is unreliable (`实测`).
