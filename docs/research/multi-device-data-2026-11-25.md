# Prior Art & Architecture Analysis: Multi-Device Live Data for Cairn

Research date: 2026-11-25. Evaluates how existing personal agents, self-hosted apps, local-first sync engines, and SQLite replication systems keep the same data live across multiple user devices while handling host downtime — and compares three concrete architectures for **Cairn**.

Evidence tags used throughout: `实测` (read or run first-hand from official docs, pinned GitHub commits, or this Cairn worktree), `推断` (derived directly from `实测` facts), `猜测` (unverified; not used for core claims).

---

## 1. The Newcomer & The Owner's Problem

### Starting with a Newcomer (One Mac, Day One)

Someone who installs Cairn on their MacBook today has never heard of a "resident host", SQLite WAL, or a Runner (`推断`).

- **Where they meet this & why**: On Day 1 they open Cairn and expect a single, continuous workspace — no host picker, no network configuration, no accounts beyond the LLM provider they already use. Their data lives quietly on their MacBook. Later, when they add a second device (a phone on the go, or a Mac mini at home so tasks keep running overnight), they expect to open Cairn on the second device and immediately see the exact same threads, tasks, and memories — never a blank workspace (`实测` / `推断`).
- **What they must already know**: On Day 1, nothing. When adding a second device, at most how to pair via QR/code (or sign in to their Tailscale / Cairn Connect tunnel) and decide which machine stays on (`推断`).
- **Accounts, payments & keys asked of them**:
  - *Single Mac*: $0, no Cairn cloud account; only their own LLM provider key/login.
  - *Multi-device (Mac mini at home)*: $0 if using LAN/Tailscale Free; optional ~$0–$5/mo for encrypted R2/S3 backup or Cairn Connect relay.
  - *Multi-device (Optional always-on VPS / future Cairn Cloud)*: ~$5–$10/mo host if they do not want home power/Wi-Fi to be a single point of failure.
- **Where their data is stored**: In one authoritative `CAIRN_HOME` directory (SQLite DB, per-thread Coordinator stores, attachments, hosted repos, encrypted secrets via `secretbox.key`), with optional bounded read-only cache on companion devices (`实测` / `推断`).
- **Where they get stuck today / what happens when it fails**: Today, Cairn's desktop host switcher (`apps/web/src/resources/desktop-host-panel.tsx`, `apps/desktop/src/main.ts:1351-1500`) switches the Electron window between `"This computer"` and `"Mac mini"` — two completely separate SQLite databases (`实测`). Switching showed the owner an empty app, making it look like his data was gone. Even worse, when configured to connect to `"Mac mini"` and the mini is unreachable, `main.ts:546` calls `window.loadURL(origin)` with no offline cache and no fallback UI — and because `desktop-host:switch` IPC requires `senderFrame.origin === origin` (`main.ts:1444-1448`), the user cannot even reach Settings to switch away (`实测`).

### The Core Tension

The owner has two Macs (a MacBook he carries, a Mac mini that stays on at home) plus a phone. He wants:
1. **One live shared view**: Type on one device, see it immediately on the other — never two split datasets.
2. **Resilience when the Mac mini is down or unreachable**: The MacBook should not become a brick when the mini loses power, reboots, or loses Wi-Fi while he is on the road.

## 2. Prior Art — Personal Agents First (Deep Dive)

Because Cairn is a personal agent orchestrator with live sessions, long-term memory, schedules, webhooks, and multi-machine execution, the closest prior art is other personal agents running on users' own machines.

**Headline finding (`实测` across all 4 personal agents):** **Zero** of the four major personal agents (**OpenClaw, Hermes Agent, Letta, nanobot**) do active-active multi-device SQLite sync or automatic multi-host failover. Every single one keeps **one authoritative host per dataset** (either a single always-on home/VPS gateway, an independent per-machine gateway shown side-by-side without sync, or a cloud control plane with stateless local execution machines).

### 2.1 OpenClaw (`openclaw/openclaw` @ [`51c00073`](https://github.com/openclaw/openclaw/commit/51c00073fb40068e05c771fa4cffe5880ea8e2da), 2026-11-25)

- **Architecture**: Single master **Gateway** control plane + thin companion clients and peripheral **Nodes** ([`docs/concepts/architecture.md#L10-L18`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/concepts/architecture.md#L10-L18), [`docs/gateway/remote.md#L8-L12`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/remote.md#L8-L12)). `实测`
- **Which machine runs the Gateway (single vs. multiple)**:
  - Runs as one long-lived `openclaw gateway` process on a single host — recommended on an always-on VPS or home desktop if your laptop sleeps ([`docs/gateway/remote.md#L101-L106`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/remote.md#L101-L106)). `实测`
  - Running multiple Gateways on one machine requires strict `--profile` isolation (separate config, state dir, workspace, and ≥120 port spacing). Startup acquires a 3-layer singleton lock (`state.<hash>.lock`, `gateway.state.lock`, and TCP `127.0.0.1:18789`) — sharing mutable state across two Gateways is explicitly forbidden ([`docs/gateway/multiple-gateways.md#L10-L26`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/multiple-gateways.md#L10-L26), [`docs/gateway/gateway-lock.md#L17-L45`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/gateway-lock.md#L17-L45)). `实测`
  - **Even with PostgreSQL 16–18**, OpenClaw explicitly states: *"Multiple active Gateways sharing a store: Not supported — No shared-store failover or active-active ownership protocol"* ([`docs/gateway/postgresql.md#L13-L17,L175-L176`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/postgresql.md#L13-L17)). `实测`
- **Where state & conversations live**:
  - **Gateway host (source of truth)**: Control-plane DB `~/.openclaw/state/openclaw.sqlite` (config, device pairings, exec approvals, Cron definitions/runs, `session_state_events`, `durable_background_processes`); per-agent data DB `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite` (sessions, `transcript_events` with optional zstd compression, memory vector index, standing intents, auth profiles; cold archives in `sessions/cold/`); human-readable Memory Core files (`AGENTS.md`, `MEMORY.md`, `USER.md`, `memory/YYYY-MM-DD.md`); `~/.openclaw/credentials/` ([`docs/reference/database-schemas/layout.md#L12-L61`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/reference/database-schemas/layout.md#L12-L61), [`docs/concepts/memory-architecture.md#L11-L61`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/concepts/memory-architecture.md#L11-L61)). `实测`
  - **Every client device**: Local `client/credentials.sqlite` (private identity + per-origin device tokens). Native iOS/Android/macOS apps keep a **bounded local SQLite read cache** (Swift GRDB: `maxCachedSessions = 50`, `maxCachedTranscripts = 50`, `maxCachedMessagesPerSession = 200`; Android Room: `GatewayCacheDatabase`) plus a **persistent offline Outbox** (≤50 queued commands per Gateway, 48h TTL, 48–50 MB attachment cap) ([`ChatTranscriptCache.swift#L41-L52`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/apps/shared/OpenClawKit/Sources/OpenClawChatUI/ChatTranscriptCache.swift#L41-L52), [`ChatCommandOutbox.kt#L18-L62`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/apps/android/app/src/main/java/ai/openclaw/app/chat/ChatCommandOutbox.kt#L18-L62)). Control UI (Web) caches shell, sidebar, recent transcripts, drafts, and ≤32 thumbnails (≤8 MiB) for offline warm reload, while session metadata edits (rename/archive/delete) sit only in an in-memory queue ([`docs/web/control-ui/offline-and-reconnect.md#L68-L186`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/web/control-ui/offline-and-reconnect.md#L68-L186)). `实测`
- **How phone, second computer, and nodes connect**:
  - **Phone (iOS/Android)**: Companion app connects over WebSocket (LAN / Tailnet / HTTPS reverse proxy) with two roles — an `operator` WS for chat/UI and a `node` WS for camera/location/screen/notifications; Android can hold operator links to multiple Gateways simultaneously, but only the focused Gateway holds phone node capabilities ([`docs/platforms/ios.md#L22-L24`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/platforms/ios.md#L22-L24), [`docs/platforms/android.md#L17-L44,L160-L166`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/platforms/android.md#L17-L44)). IM apps (Telegram, WhatsApp, Discord, Slack, Signal, iMessage) talk to the single Gateway process ([`docs/concepts/architecture.md#L10-L18`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/concepts/architecture.md#L10-L18)). `实测`
  - **Second computer**: macOS app runs in **Remote over SSH** (auto-managed `ssh -N -L` to `127.0.0.1:18789`) or **Remote direct (`ws`/`wss`)** via Tailscale Serve or Cloudflare Access; optional "Also run a Gateway on this Mac" starts an **isolated local Gateway** with zero sync to the remote one ([`docs/platforms/mac/remote.md#L117-L178`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/platforms/mac/remote.md#L117-L178)). CLI/TUI (`openclaw attach`/`resume`) attaches live without copying transcripts ([`docs/concepts/session-attachment.md#L11-L31`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/concepts/session-attachment.md#L11-L31)). `实测`
  - **Paired Nodes**: Connect outbound over WS (LAN/Tailnet/SSH/CF Access/iroh relay "OpenClaw ID Labs"). Even with `--session-host` executing local file/process tools on the node, **sessions, memory, and web search remain owned by the Gateway** ([`docs/nodes/node-host.md#L37-L119`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/nodes/node-host.md#L37-L119), [`docs/nodes/session-hosting.md#L157-L162`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/nodes/session-hosting.md#L157-L162)). `实测`
- **What other devices can do when the Gateway host is off**:
  - **Read**: Native iOS/Android/macOS can browse the bounded local SQLite cache (≤50 sessions, 200 msgs/session); Control UI Web can warm-reload cached sidebar/transcripts/≤32 thumbnails; CLI and Nodes cannot read anything ([`ios.md#L25-L26`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/platforms/ios.md#L25-L26), [`offline-and-reconnect.md#L125-L186`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/web/control-ui/offline-and-reconnect.md#L125-L186)). `实测`
  - **Write**: Native apps queue up to 50 messages in SQLite Outbox (expire after 48h); Web persists drafts and holds metadata edits in RAM only; approvals, settings, and terminals are disabled ([`ios.md#L27-L28`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/platforms/ios.md#L27-L28), [`offline-and-reconnect.md#L68-L110`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/web/control-ui/offline-and-reconnect.md#L68-L110)). `实测`
  - **Run agents / tools / Cron**: **Everything stops.** Nodes cannot run agents or Cron without the Gateway; Cron lives inside the Gateway process and reschedules (rather than immediately storm-replaying) overdue agent jobs on restart ([`docs/automation/cron-jobs/how-it-works.md#L16-L27`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/automation/cron-jobs/how-it-works.md#L16-L27)). `实测`
- **Conflict handling on reconnect**: No multi-master DB merge exists. Outbox items use idempotency keys and are cleared only after confirmed in `chat.history`; if `branchEpoch`, default agent owner, or session settings changed while offline (or delivery is unconfirmed), items are **parked as Failed for human review** instead of blindly replaying ([`ChatCommandOutbox.kt#L29-L40,L69-L132`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/apps/android/app/src/main/java/ai/openclaw/app/chat/ChatCommandOutbox.kt#L29-L40)). `实测`
- **Setup required**: Always-on host + one of 6 remote paths (Tailscale Serve preferred, Tailscale direct/Funnel, SSH tunnel, Cloudflare Access, or OpenClaw ID iroh relay) + per-device and per-node approval + optional `openclaw backup enable` (AES-256-GCM to disk or Cloudflare R2) ([`docs/gateway/tailscale.md#L17-L41`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/gateway/tailscale.md#L17-L41), [`docs/install/backups.md#L61-L72`](https://github.com/openclaw/openclaw/blob/51c00073fb40068e05c771fa4cffe5880ea8e2da/docs/install/backups.md#L61-L72)). `实测`

### 2.2 Hermes Agent (`NousResearch/hermes-agent` @ [`b7ee21c1`](https://github.com/NousResearch/hermes-agent/commit/b7ee21c14e38316273f88d8ed112491ba1c87d15), 2026-11-25)

- **Architecture**: **Independent Gateway per machine** (multiplexing multiple isolated profiles per host) + **multi-connection federated Desktop/Webapp** that displays all registered gateways side-by-side **without syncing state across machines**, plus optional **Hermes Cloud** hosted migration ([`website/docs/user-guide/multi-connection-desktop.md#L7-L13,L85-L89`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/multi-connection-desktop.md#L7-L13)). `实测`
- **Where state lives**: Each host/profile owns its own `$HERMES_HOME/state.db` (SQLite WAL: `sessions`, `messages`, FTS5, `delivery_obligations`, `runtime_epoch`, `session_admissions`, `worker_executions`), `memories/{MEMORY,USER}.md`, `SOUL.md`, and `cron/jobs.json`. Single-writer enforced via `gateway.lock` flock + `F_OFD_SETLK` WAL lock + `runtime_epoch` fence ([`session-storage.md#L3-L28,L124-L155`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/developer-guide/session-storage.md#L3-L28), [`lockguard.py#L1-L17`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/persistence/sqlite/_state/lockguard.py#L1-L17)). Desktop stores `gateway-connections.json`, UI prefs, unsent drafts, and local copies of **Bot Mode** multi-agent group rooms only ([`desktop.md#L170-L175,L233`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/desktop.md#L170-L175), [`bot-mode.md#L147`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/bot-mode.md#L147)). `实测`
- **How devices connect**: Desktop simultaneously maintains live connections to Local, Remote HTTP(S), SSH-tunneled gateways, and Hermes Cloud (`gateway → profile → sessions` sidebar; explicit rule: *"Profiles, chats, messaging, and cron stay with their own gateway"*). No native iOS/Android app exists; phones use 20+ IM adapters, the Gateway Webapp (`:9120`), or third-party SSH clients ([`multi-connection-desktop.md#L42-L48,L85-L89`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/multi-connection-desktop.md#L42-L48), [`platform-support.md#L18-L65`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/getting-started/platform-support.md#L18-L65)). Moving data between hosts is explicit zip `Backup & Transfer` / `Transfer to Hermes Cloud` (which disables messaging bots on the copy because *"a bot token can only be used by one running Hermes at a time"*, [`backup-and-transfer.md#L18-L49`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/backup-and-transfer.md#L18-L49)). `实测`
- **When a Gateway host is off**:
  - **Read**: Ordinary chats have **no offline cache** — the gateway is simply badged offline and retried every 30s, while other registered gateways (e.g. Local or Hermes Cloud) remain live ([`multi-connection-desktop.md#L189-L198`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/multi-connection-desktop.md#L189-L198)). Only Bot Mode group rooms remain readable locally ([`bot-mode.md#L147`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/bot-mode.md#L147)). `实测`
  - **Write**: **No offline outbox** — submitting while offline throws `"Hermes is offline right now. Reconnect, then send it again."`; unsent drafts/image recovery logs stay local for manual resend ([`en_clarify.ts#L3`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/apps/desktop/src/i18n/en_clarify.ts#L3), [`desktop.md#L233,L313`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/desktop.md#L233)). `实测`
  - **Run / Cron**: Everything on that host stops. On reboot, interrupted `started` turns are fenced as `unknown` (pausing that session FIFO until human `/discard`, [`gateway-internals.md#L83-L101`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/developer-guide/gateway-internals.md#L83-L101)), `delivery_obligations` replays unsent replies, and missed recurring crons coalesce into **1 catch-up run** by default (`missed_runs.py#L1-L42`). `实测`
- **Conflict handling**: Single-writer per host (`expected_revision` CAS on `session.mutate`, `request_id` dedupe); only Bot Mode rooms merge per-gateway versions with deletion tombstones ([`canonical-gateway-protocol.md#L33-L45`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/apps/desktop/docs/canonical-gateway-protocol.md#L33-L45), [`bot-mode.md#L147`](https://github.com/NousResearch/hermes-agent/blob/b7ee21c14e38316273f88d8ed112491ba1c87d15/website/docs/user-guide/bot-mode.md#L147)). `实测`

### 2.3 Letta (`letta-ai/letta-code` @ [`c67a0d59`](https://github.com/letta-ai/letta-code/commit/c67a0d59263262a947b3dce3420b2c35b46bd829), `docs.letta.com`)

## 5. Three Candidate Architectures for Cairn

### Candidate 1: Single Authoritative Host + Thin Multi-Device Clients with Read Cache & Safe Outbox

*(The pattern used by OpenClaw, T3 Code, nanobot, Home Assistant, and Letta's server/cloud modes — with an optional **Always-On Cloud Host / $5 VPS** deployment option alongside the home Mac mini option.)*

- **How it works**:
  - Exactly **one** Cairn server holds `CAIRN_HOME` (`server.db`, `coordinator/*.sqlite`, `attachments/`, `repos/`, `secretbox.key`) and runs Coordinator, Scheduler, IM/Mail, Webhooks, and Machine routing.
  - All other devices (MacBook Desktop app, phone PWA/browser) connect as thin clients to that one server. Crucially, the MacBook Desktop app **still runs its local Runner (`apps/daemon`)** registered with that server (`main.ts:1384-1422` already does this!) so tasks targeting the MacBook's local files/apps/terminal work seamlessly.
  - **What changes from Cairn today** to fix both pain points:
    1. **One-click "Move my workspace to Mac mini" migration** (bundle `CAIRN_HOME` + `secretbox.key` cleanly, retire the old local DB so users never see an empty app when switching).
    2. **Bounded local read cache + offline shell** (T3 Code + OpenClaw pattern): Desktop/Web caches recent threads, tasks, memories, and drafts locally in IndexedDB/SQLite, explicitly badged **`Offline · Cached`** when unreachable, with a native Electron recovery bar (so disconnecting never bricks the window or hides Settings).
    3. **Safe, bounded offline Outbox** (OpenClaw + T3 Code pattern): Let users write messages/drafts and triage tasks while offline; replay on reconnect **only if** the thread version/epoch has not diverged (otherwise park for 1-click user review).
    4. **Multi-route auto-switching** (T3 Code pattern): Auto-prefer LAN → Tailscale → Cairn Connect tunnel (`docs/research/cairn-connect-2026-11-14.md`) so moving between home Wi-Fi and cellular rarely drops the connection.
    5. **Optional Break-Glass Backup + Cloud Host path**: Add continuous encrypted backup (Litestream for `server.db` + R2 sync for `coordinator/*.sqlite`, `attachments/`, `repos/`, user-held recovery key) so a dead Mac mini can be restored onto the MacBook in minutes. And for users who never want home power/Wi-Fi downtime to stop them, document/support running the single Cairn server on a **$5/mo VPS (or future Cairn Cloud)** while **both** the Mac mini and MacBook connect as Runners (just like Letta Cloud + BYOM)!

| Scenario | What the User Sees | What the System Does | Wait & Cost |
|---|---|---|---|
| **1. MacBook & mini both serve as Runners. | <50ms LAN / ~100ms WAN; $0 (Tailscale) or ~$0–$5/mo (tunnel/backup). |
| **2. Mac mini off while on the road** | **Home-mini deployment**: Banner `Mac mini offline · Showing cached view`. User can read recent threads/tasks/memories and draft/queue replies; cannot run new Coordinator turns or schedules until mini returns (unless user triggers manual Break-Glass Restore). **Optional VPS/Cloud deployment**: **100% live** — MacBook & phone read, write, chat with Coordinator, and run tasks on MacBook Runner uninterrupted; only Mac-mini-local files are offline. | Home-mini: serves local read cache + stores drafts/Outbox locally; retries LAN/Tailscale/tunnel automatically. VPS/Cloud: control plane stays up; `machine-routing.ts` routes eligible steps to MacBook Runner. | Instant cached read; 0s downtime on VPS ($5/mo). Break-glass restore on dead mini: ~1–2 min manual action. |
| **3. Both on, network split (home Wi-Fi/ISP down)** | Same as Scenario 2 on the MacBook (`Offline · Cached`). Mac mini keeps running schedules, IM bots, and background tasks safely at home with **zero split-brain**. | MacBook cannot reach mini, stays read-only + queued Outbox. Queued MacBook messages either send cleanly or appear as `Needs review` if that thread changed while offline. | Client fetches missed SSE/snapshots; Outbox checks thread version/epoch before submitting (parks drifted items). - **User setup**: Enable Resident Host on Mac mini (1 toggle) + Tailscale or Cairn Connect tunnel + pair MacBook & phone (1 QR / migration click). Optional: R2/S3 bucket for encrypted Litestream backup, or $5/mo VPS to remove home SPOF.
- **Cost**: $0/mo (LAN/Tailscale) to ~$5/mo (Cairn Connect / R2 backup / tiny VPS).
- **Implementation size**: **Small–Medium (~3–5 weeks total, shippable in incremental PRs)**: migration wizard + Electron offline shell/recovery (~1 wk), client read cache + `Offline · Cached` state + safe Outbox (~2 wks), multi-route probing & optional Litestream encrypted backup/break-glass restore (~1–2 wks). Touches `apps/desktop/src/main.ts`, `apps/web/src/api/`, `apps/web/src/resources/desktop-host-panel.tsx`, and a small backup/migration service in `apps/server/`.

### Candidate 2: Single Authoritative Host + Live Warm Replica on Every Device with Takeover When Host Is Gone

*(Litestream continuous WAL replication to S3/R2 + encrypted mirror of `coordinator/*.sqlite`, `attachments/`, `repos/`, `secretbox.key` + leased failover/promotion when the Mac mini is unreachable.)*

- **How it works**:
  - Mac mini runs as primary, streaming `server.db` WAL every ~1s via **Litestream** (`v0.5.18`, supports `darwin-arm64`) to an S3/R2 bucket, plus a custom sync worker pushing immutable `attachments/`, `coordinator/*.sqlite` snapshots, and `repos/` bundles (all encrypted with the user's `secretbox.key`).
  - MacBook continuously follows the replica (via `litestream restore -f` or `litestream-vfs` + asset mirror) so it holds a ≤5s warm copy locally.
  - Because **Litestream has no leader election and corrupts the bucket if two writers ever replicate concurrently** (`实测`, Litestream Tips), takeover **must** be gated by an external **fencing lease** (e.g. S3/R2 conditional `If-Match` lease object or Cloudflare Durable Object): before starting as primary, the MacBook acquires `epoch = N+1`, fences the mini's lease, opens the restored DB, starts its local Cairn server + Coordinator + Scheduler, and updates a cloud router/relay so the phone and webhooks redirect to the MacBook.

| Scenario | What the User Sees | What the System Does | Wait & Cost |
|---|---|---|---|
| **1. Mac mini on (normal)** | Identical live view on all devices (same as Candidate 1). | Mac mini is primary (lease `epoch = N`); streams LTX every 1s + asset deltas to R2; MacBook follows replica in background while UI talks live to mini. | <50ms live UI; ~1–5s replica lag; ~$1–$5/mo R2 + relay/lease infra. |
| **2. Mac mini off while on the road** | UI detects mini unreachable, immediately shows ≤5s warm local replica read-only, and offers **"Take over on this MacBook"**. After clicking (or auto-failover after lease TTL ~30–60s), MacBook becomes full live Cairn: read, write, Coordinator, schedules, local tasks all work! | MacBook acquires cloud lease `epoch = N+1` (requires internet!), finishes restoring latest LTX + `coordinator/*.sqlite` + attachments, boots local Cairn server, starts Litestream writer for `epoch = N+1`, repoints tunnel/relay. *(If MacBook has NO internet at all, e.g. on a plane, it CANNOT safely acquire the lease — stuck read-only!)* | 10–60s takeover wait; 1–5s of unshipped mini writes potentially lost. |
| **3. Both on, network split (home ISP down, MacBook on 5G)** | **Dangerous edge case:** MacBook has 5G so it *can* reach the cloud lease and take over — meanwhile the Mac mini is still alive at home with no internet! Mini must **immediately self-fence** (stop Coordinator, Scheduler, IM bots, and writes) within lease TTL (~30–45s) when it loses lease heartbeat, otherwise both run schedules/tasks on diverged DBs. | Cloud lease advances to `N+1` (MacBook). Mini fails lease renewal and halts its server (`Fenced` state). Any in-flight turn on the mini during the 30s grace window is aborted/lost and its unshipped SQLite writes are discarded on rejoin. | 30–45s fencing window; aborted in-flight turns on mini; high risk if fencing has any bug. |
| **4. Mac mini comes back after MacBook took over** | User either stays on MacBook until clicking **"Hand back to Mac mini"**, or mini automatically catches up in standby and requests handback. Brief pause (~5–15s) during clean cutover. | Mini checks cloud lease on reconnect, sees `epoch = N+1`, **discards any unshipped local writes**, wipes/restores from R2 LTX + `coordinator/*.sqlite` + attachments + repos, and enters standby. Clean handback flushes MacBook WAL → R2 → advances lease `N+2` → mini boots. | 5–30s cutover; nontrivial failure states if MacBook lid closes mid-flush! |
| **5. New user with only one Mac** | Works locally on Day 1, but enabling multi-device immediately requires cloud object storage (R2/S3) + lease broker + recovery key setup. | Local-only until user provisions backup/lease credentials and enrolls 2nd host. | Medium setup friction once 2nd Mac added. |
| **6. Phone** | Works seamlessly **only if** Cairn operates a cloud routing layer (like Cairn Connect) that dynamically repoints the phone's URL from Mac mini to MacBook during takeover; if using static Tailscale URL, phone breaks during takeover! | Cloud relay/DNS repoints to whichever Mac holds current lease; webhooks (`github-webhook`, `schedule-webhook`) must also flow through the relay. | Requires always-on cloud relay ($5+/mo operator infra). |

- **User setup**: Cloud bucket (R2/S3) + cloud fencing lease/relay (operated by Cairn or self-hosted) + `secretbox.key` transfer + Litestream sidecar on both Macs.
- **Cost**: ~$1–$5/mo cloud storage + mandatory always-on cloud lease/relay service.
- **Implementation size**: **Large (~3–5 months + high ongoing reliability burden)**: Must build and TLA+-verify lease fencing across `server.db`, `coordinator/*.sqlite` (every `pi-durable` harness), `attachments/`, and bare `repos/`; Litestream sidecar supervision + `epoch`-prefixed bucket paths to prevent LTX corruption; server-side self-fencing of `scheduler.ts`, `coordinator/index.ts`, `im/core.ts`, `mail-connector.ts`, and `machine-claim.ts`; clean handback state machine; dynamic relay repointing for phone & webhooks.
- **The irony (`推断`)**: Safe failover in Candidate 2 **already requires an always-on cloud component** (the fencing lease + R2 bucket + phone/webhook relay). If a user is willing to depend on a cloud component when their Mac mini is down, running the lightweight Cairn server itself on a $5/mo cloud host (Candidate 1's Cloud Host option) is **far simpler, has zero split-brain, zero failover lag, and works even when the Mac mini is off and the MacBook lid is closed**!

### Candidate 3: Full Local-First Multi-Master Sync (CRDT / `cr-sqlite` / Automerge / Custom Op-Log)

- **How it works**:
  - Every device (MacBook, Mac mini, and potentially phone) runs a full local Cairn database and accepts reads and writes independently offline or online.
  - Changes synchronize peer-to-peer (over LAN/Tailscale) and/or via an always-on encrypted sync relay so devices don't need to be online at the same time.
  - Because `cr-sqlite` hard-rejects Cairn's **81 foreign keys** and **42 secondary `UNIQUE` indices** (`实测`, `tableinfo.rs`, `schema.ts`) and has had no release since Jan 2024, and Automerge replaces SQL entirely with NoSQL JSON documents (`实测`), Cairn would have to either (a) strip all relational constraints across 92 tables and adopt a custom fork of `cr-sqlite` + build a custom sync relay, or (b) build a bespoke domain op-log/CRDT layer on top of SQLite (plus content-addressed sync for `attachments/`, `repos/`, and `coordinator/*.sqlite`).
  - **Fundamental architectural flaw for an agent orchestrator (`推断` from `实测` Cairn + OpenClaw/Hermes/Letta/T3)**: CRDTs merge *data*; they **cannot** make two disconnected servers safely execute non-idempotent side effects once. Two offline devices cannot both run Coordinator turns, cron schedules, Telegram/WeChat polling, GitHub PR reviews, or Runner step claims without duplicating LLM spend, double-sending external messages, and forking `pi-durable` agent transcripts. You *still* have to add single-owner election on top of the CRDT layer!

| Scenario | What the User Sees | What the System Does | Wait & Cost |
|---|---|---|---|
| **1. Mac mini on (normal)** | Instant local UI speed; edits sync across devices in <1s. | Local SQLite write → op-log/CRR delta pushed over WS to peer / sync relay → merged into remote SQLite. | <10ms local write; <1s sync; requires sync relay ($5+/mo) for async/phone sync. |
| **2. Mac mini off while on the road** | Full offline read and write of tasks, notes, and local state on MacBook; can run local Coordinator turns *if* MacBook elects itself active agent runner. | Local DB accepts all writes; deltas buffer locally until mini or sync relay is reachable. | Instant local writes; external webhooks/IM bots still down unless hosted in cloud. |
| **3. Both on, network split** | **Worst failure mode**: Both MacBook and Mac mini accept writes and (if both allow agent execution) both run Coordinator turns, fire schedules, poll IM/mail, and create conflicting task states on the same threads! | When network heals, CRDT merges column-level LWW silently — potentially combining half of MacBook's turn state with half of mini's, duplicating tasks/replies/external emails, and breaking relational invariants (since FKs/UNIQUEs had to be disabled). | Instant locally, but severe semantic corruption & duplicate side effects on reconnect. |
| **4. Mac mini comes back** | Automatic background merge for simple text/fields, **but** forked Coordinator conversations, duplicate schedule runs, and conflicting task transitions require complex merge UI or produce confusing interleaved transcripts. | Exchanges deltas since last peer clock; merges CRR rows / CRDT docs; still needs bespoke reconciliation for `coordinator/*.sqlite`, `attachments/`, and bare Git `repos/`. | Seconds to merge data; high manual cleanup for forked agent runs. |
| **5. New user with only one Mac** | Seamless on Day 1, **but** every feature in Cairn pays permanent complexity tax (no checked FKs, slower CRR writes ~2.5x, special migration discipline across 255+ migrations). | Local DB carries CRR clock/tombstone overhead even with 1 device. | 0s user setup; permanent engineering drag. |
| **6. Phone** | Full offline read/write only if shipping a native/WASM SQLite + CRDT engine on iOS/Android + encrypted cloud sync relay (since Syncthing has no official iOS app and direct P2P fails behind mobile NAT when mini sleeps). | Mobile downloads full/partial CRR delta log via cloud relay; must handle E2EE key distribution (`secretbox.key`). | High mobile & relay complexity; ~$5+/mo relay infra. |

- **User setup**: E2EE sync password/key pairing across devices + always-on sync relay account (for phone and asynchronous MacBook↔mini sync).
- **Cost**: $5+/mo relay infra (if Cairn hosts it) or self-hosted relay.
- **Implementation size**: **Massive (~6–12+ months complete rewrite)**: Re-architect all 92 tables / 81 FKs / 42 UNIQUEs, rewrite `pi-durable` Coordinator harnesses for mergeability, build an E2EE sync protocol + relay server, build blob/Git sync, AND still build distributed single-owner locking for Coordinator/Scheduler/IM/Webhooks.

## 6. Recommendation: What Fits Cairn and Why

### The Verdict

**Adopt Candidate 1 (Single Authoritative Host + Local Read Cache & Safe Outbox), paired with two targeted resilience layers:**
1. **For home-Mac-mini users**: Local read cache + safe Outbox + multi-route auto-switch + continuous encrypted Litestream/R2 backup with manual **Break-Glass Restore** (no automatic split-brain failover).
2. **For zero-home-SPOF users (including ian if mini downtime is unacceptable)**: Support running the lightweight Cairn **control-plane server** on an always-on **$5/mo VPS (or future Cairn Cloud)** while **both** the Mac mini and MacBook stay enrolled as **Runners** (`apps/daemon`).

### Why This Beats Candidates 2 and 3 (Grounded in `实测` Prior Art)

1. **Unanimous personal-agent consensus**: OpenClaw, Hermes Agent, Letta, nanobot, and T3 Code all hit the exact same physics — personal agents have single-owner execution loops (turns, schedules, IM bots, webhooks, tool calls) that cannot be CRDT-merged. Even **Linear** (famous for local-first UX) keeps centralized Postgres authoritative, leaves ~95% of data on the network, uses no CRDTs, and explicitly calls offline mode *"a failsafe and not a full-fledged feature"* (`实测`).
2. **Candidate 3 (`cr-sqlite` / Automerge) is structurally incompatible with Cairn**: Cairn has **92 SQLite tables, 81 enforced foreign keys, 42 unique constraints, 255 migrations**, per-thread `pi-durable` SQLite stores, `secretbox.key`, attachments, and bare Git repos (`实测`). `cr-sqlite` hard-rejects all 81 FKs and 42 UNIQUEs and has no sync transport (`实测`); LiteFS is Linux-only and unmaintained (`实测`); 2-node rqlite has 0 fault tolerance (`实测`).
3. **Candidate 2 (live warm replica + automatic failover) has a hidden paradox**: Making Litestream failover safe against split-brain requires an **always-on cloud fencing lease + R2 bucket + dynamic cloud relay** (`实测` / `推断`). Yet if you already rely on an always-on cloud service to coordinate failover when the Mac mini is unreachable, putting the single Cairn server itself on a $5/mo cloud host (Letta Cloud + BYOM pattern) gives **true 100% uptime for MacBook & phone when the Mac mini is off**, with **1/10th the complexity and zero split-brain risk** — because Cairn's `apps/daemon` Runner architecture *already* decouples control plane from machine execution (`实测`, `apps/desktop/src/main.ts:1384-1422`)!

### Concrete Implementation Plan & Code Areas Touched

1. **Phase 1 — Fix the "empty app" & "offline brick" immediately (Weeks 1–3)**:
   - **Workspace migration on host setup** (`apps/server/src/routes-remote.ts`, `apps/desktop/src/main.ts`, `apps/web/src/resources/desktop-host-panel.tsx`): When connecting a second Mac to a primary host (or promoting Mac mini to primary), offer a 1-click **"Move local data to Mac mini"** export/import (moving `server.db`, `coordinator/*.sqlite`, `attachments/`, `repos/`, `secretbox.key`) and hide the confusing two-database switcher behind an explicit advanced action. Ensure the MacBook auto-enrolls its local Runner against the remote server seamlessly.
   - **Offline-resilient desktop shell & read cache** (`apps/desktop/src/main.ts:497-552,1444-1500`, `apps/web/src/api/`): Handle `did-fail-load` cleanly; allow switching/reconnecting from the native app menu even when the remote origin is unreachable; persist a bounded client read cache (recent threads, tasks, memories, like T3 Code's `client-runtime` and OpenClaw's 50-session cache) clearly badged **`Offline · Cached`**.
   - **Safe, bounded offline Outbox** (`apps/web/src/api/`): Persist queued chat messages/drafts and lightweight triage actions locally; on reconnect, verify thread revision/epoch before submitting and park drifted items for user confirmation (borrowing OpenClaw's `ChatCommandOutbox` & T3 Code's `ThreadTriageOutbox` `seenState` guard).
2. **Phase 2 — Multi-route reachability + Encrypted Break-Glass Backup (Weeks 4–5)**:
   - **Auto-probing routes** (`apps/desktop/src/connections.ts`, `apps/server/src/lib/remote-routes.ts`): Store LAN + Tailscale + Cairn Connect tunnel URLs for the same `environmentId` and auto-switch to the fastest reachable route (borrowing T3 Code's 60s `BETTER_ROUTE_CHECK_INTERVAL_MS` supervisor).
   - **Encrypted continuous backup & Break-Glass Restore** (`apps/server/src/services/backup-status.ts`, new backup service): Optional Litestream (`v0.5.18`) continuous WAL replication of `server.db` + periodic encrypted mirror of `coordinator/*.sqlite`, `attachments/`, and `repos/` to user-owned R2/S3 (with a printable recovery key for `secretbox.key`). If the Mac mini dies permanently, the MacBook can explicitly **"Restore from backup & make this Mac primary"** in minutes (revoking the old host's tunnel/pairing tokens to prevent split-brain).
3. **Phase 3 — Optional Always-On Control Plane (Zero Home-SPOF Mode)**:
   - Package Cairn server as a lightweight single-container / 1-click VPS deployment (or future Cairn Cloud) using the exact same single-host code path. Both Mac mini and MacBook connect as desktop clients + Runners; phone connects via HTTPS. If the Mac mini loses power or Wi-Fi, the MacBook and phone stay **100% live** (read, write, Coordinator, schedules, webhooks, and MacBook-local execution).
