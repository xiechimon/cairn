# Effort / thinking level per provider — research for #5371

Issue: https://github.com/xiechimon/cairn/issues/5371 — "evaluate whether thinking levels should give different effort per provider; today it looks like one unified set of levels."

Measured 2026-11-22 against this tree, the locally installed CLIs (Claude Code 2.1.329, codex-cli 0.166.0, Devin CLI 3000.14.30821, agy 1.5.13, amp), and the products' own documentation. Claims are marked **measured** (read or ran first-hand today), **derived** (follows from a measured fact), or **guessed**.

## The newcomer

Someone who installed Cairn today connects a provider in Settings > Model (an Anthropic or OpenAI key, a ChatGPT Codex sign-in, a Claude subscription on a Runner machine, a Devin or Antigravity subscription, or an OpenAI/Anthropic-compatible endpoint URL) and picks a model for the Coordinator and for tasks. Next to each model sits a `思考` dropdown — the thinking control this issue is about. It asks for no account, payment, or key of its own; the choice is stored server-side in the team database (`routing_rule.thinkingLevel` for the Coordinator/compaction/session rows, `teamTopModels.models[].thinkingLevel` for frequently used models, `project.modelOverrides.coordinator.thinkingLevel` for a project override), all `null` meaning "use the provider's default". When the stored level is one the selected model's backend does not offer, the dropdown either does not render at all (the model has fewer than two distinguishable settings) or shows "Default"; a stale level picked before the model lists were measured keeps working through the backends' own fallbacks. If a level the backend truly rejects were sent, the step would surface the provider's API error on the run, not silently succeed — except on paths that send nothing (see "silently ignored" below), where picking a level changes nothing.

## Why

The issue asks whether the thinking dropdown should offer different effort per provider instead of one unified scale. Since 2026-11-20 (b64956fd8, design doc `docs/design/thinking-levels.md`) each model already lists only the levels its backend distinguishes — but the *names* are still one shared vocabulary of seven English words, and it is fair to ask whether "High" should mean the same thing on DeepSeek as on Claude, whether a level a user saves should travel when the router swaps the model underneath it, and whether Cairn should just pick effort itself. This file answers that with the code as it stands and with what comparable products ship.

## What Cairn does today (measured in code)

**Vocabulary.** One enum, `THINKING_LEVELS = off | minimal | low | medium | high | xhigh | max`, `packages/shared/src/thinking-levels.ts:3`, served to the web app on `GET /api/capabilities` (`apps/server/src/routes-resources.ts:374`).

**Per-model capability.** Every `ModelSourceModel` carries `thinkingLevels`, `thinkingDefault`, `inServerThinkingLevels`, `inServerThinkingDefault` (`packages/shared/src/records/model-source.ts:75-78`), filled in `apps/server/src/services/providers.ts`:

| Runtime | Source of truth for levels | Default shown as | Where applied |
|---|---|---|---|
| claude-code (Runner) | `claudeCodeThinkingLevels(modelId)` — only `claude-{opus,sonnet,haiku,fable}-N` with N ≥ 5 gets `low…max` (`thinking-levels.ts:9-14`); docs upstream say Opus 4.6–4.8 also support effort, so the gate under-offers for 4.x (derived) | `claudeCodeThinkingDefault` → `medium` for 5-5 ids, else plain "Default" | `toEffort` → Agent SDK `Options.effort`; `off`/`minimal` send nothing = model default; an unsupported stored level throws fail-closed (`apps/daemon/src/backend/claude-code.ts:1697-1701`) |
| pi on a Runner | pi-ai catalog: `getSupportedThinkingLevels` + per-model `thinkingLevelMap`, deduped by `distinctThinkingLevels` (`apps/server/src/coordinator/runtime/provider.ts:71-88`); custom endpoints register `reasoning: false` → no levels | `clampThinkingLevel(model, 'medium')` | `createAgentSession({thinkingLevel})`; pi-coding-agent clamps an unsupported level to the next supported one (`apps/daemon/src/backend/pi.ts:1265-1276`) |
| pi in the server (Coordinator + compaction turns) | `inServerThinking` — only the Codex subscription registers `reasoning: true` + the catalog map; every other pi provider returns `levels: []` (`provider.ts:90-98`) | `off` for codex models whose map allows it, else unknowable | `stepProvider` builds the provider; level flows from `routing_rule` via `routeOf`/`turn.ts:237`; non-Codex providers send no reasoning field, so a stored level is silently ignored there |
| Devin (ACP) | ACP `thought_level` select option, probed per selected model via `set_config_option`; learned values reported back; seeds in `DEFAULT_DEVIN_MODELS` (`apps/daemon/src/backend/acp.ts:131-145`, `model-source.ts:52-68`) | the option's `currentValue` right after the model is selected | `session/set_config_option` with an exact-match value only; `off` → `none` (`acp.ts:870-881`) |
| Antigravity (managed ACP) | same `thought_level` mechanism through the managed probe (`apps/daemon/src/backend/antigravity-managed.ts:200-209`); seeds in `DEFAULT_ANTIGRAVITY_MODELS` | same | same |
| Gemini ACP | none — `GEMINI_CAPABILITIES.thinkingLevels` stays empty; no model source is listed | n/a | nothing is sent |

Measured per-model level sets live in `docs/design/thinking-levels.md` (e.g. deepseek-flash: `off,low,high,max` default `high`; deepseek-v4-pro: `off,high,max`; zai/moonshot: `low,high,max`; codex gpt-6.1-sol in-server: `low…max` default `off`).

**UI rule.** `ThinkingLevelSelect` (`apps/web/src/resources/thinking-level-select.tsx`) renders `Default` plus the model's own levels, names the default's resolution ("Default (Medium)"), and renders nothing when the entries resolve to fewer than two distinct settings — so a model with no adjustable thinking shows no control instead of an inert one. Coordinator/compaction rows read `coordinatorThinkingLevels` = `inServerThinkingLevels` when set, else `thinkingLevels` (`apps/web/src/api/mappers.ts:1523-1532`).

**Where the same stored value crosses providers.** Two paths matter:

- A Coordinator-picked frequent model travels *with* its level: `frequentModelFor` returns the `TopModel` including `thinkingLevel` into `request.model` (`apps/server/src/services/coordinator-request.ts:466`, `routing-rules.ts:290-294`), which overrides the session rule wholesale. Same provider, same model, user's own saved pair — fine.
- Difficulty routing substitutes the model but keeps the rule's level: `profileForStep` for session steps replaces `provider`/`modelId` from `decideStepRoute` (easy/standard/hard → different model ranking in `packages/shared/src/capability-routing.ts:51-55`) while inheriting `base.thinkingLevel` unchanged (`routing-rules.ts:510-515`). A level saved for one provider's model is then clamped by a different provider's map at run time — the only place the "unified" level auto-crosses providers today (derived). A hard `fallback` (`stepRow.fallback`) deliberately drops it to default (`machine-claim.ts:324,412,869`, `info-card-runner.ts:191`).

**Where Cairn picks effort itself.** Only for its own internal uses: `resolveRouting` assigns `low` to mechanical/nightly-scan and `high` to coordinator/implementation/review/eval edges on the model-routing graph (`packages/shared/src/model-routing.ts:119`). Task difficulty picks a *model*, not an effort — there is no difficulty→effort mapping (measured).

**The pattern.** Every product that exposes effort does it the same way: the vendor publishes each model's real levels and a default; the product offers exactly those, names what the default resolves to, and clamps or rejects out-of-range picks. No one offers a normalized cross-vendor scale — Claude Code's docs say explicitly the scale is calibrated per model and the same name is not the same value across models. Speed is a separate axis where it exists (Amp Speed, Devin `-fast`/`-lightning`, Cursor Fast, Conductor Fast Mode). Codex additionally shows the shape Cairn already has for its rows: per-use defaults (`plan_mode_reasoning_effort`, `agents.default_subagent_reasoning_effort`) — the same idea as Cairn's per-row `routing_rule.thinkingLevel`.

## Scenario table

| Situation | What the user sees | What the system does | Wait / cost |
|---|---|---|---|
| Task on claude-opus-5-5 via Claude Code, user wants deeper reasoning | `思考` dropdown: Default (Medium), Low, Medium, High, Xhigh, Max | Stored on the routing rule / frequent model; `toEffort` sends the SDK `effort` | Higher effort = more thinking tokens, slower turns |
| Task on the same model via a custom pi endpoint | No dropdown (custom endpoints register `reasoning: false`) | Nothing is sent; the endpoint's default applies | Nothing to wait on — control honestly absent |
| Coordinator on the Codex subscription in-server | Default (Off), Low…Max | `reasoning.effort` sent per turn via the catalog map | Off is cheapest; higher efforts cost more tokens per Coordinator turn |
| Coordinator on any other pi provider (Anthropic key, DeepSeek, custom) | No dropdown | `reasoning: false` — no reasoning field is sent at all | Same as above: honestly absent, but the user cannot raise Coordinator effort there |
| Task on Devin swe-2-high | Default (High), Medium, High, Max | ACP `set_config_option thought_level` exact match | Per-model pricing on Devin's side; `high` is its tuned default |
| Task on Devin model never run before | No dropdown | First run probes the model's `thought_level` values and reports them; the selector appears afterward | One real run before the control exists |
| Task on Antigravity gemini-3.8-flash | Default (High), Low, Medium, High | same ACP mechanism via the managed probe | — |
| Hard task, session rule model unavailable | Router substitutes another provider's model | The rule's stored `thinkingLevel` is applied to the substitute and clamped by its map; a `fallback` pin drops it to default | Possible surprise: a `max` saved for Claude lands as `max`/`high` on Codex |
| Easy task | Router picks haiku-class model by difficulty ranking | Effort stays whatever the chosen model's level is — no automatic lowering | — |

## Recommendation

**Keep the per-model control; add nothing new.** The evaluation the issue asks for resolves to this: the "unified seven levels" is a presentation vocabulary over per-model sets, and the wire value is already per-provider — `minimal` becomes `low` on Codex, `off` becomes `none` over ACP, unsupported entries are never shown. That is exactly the shape every reference that exposes effort uses (Claude Code, Codex, Amp, Conductor pass-through, Devin, Antigravity), and the two that don't normalize either (Zed's boolean, Cursor's first-party-only control) confirm there is no cross-vendor scale to align to — Claude Code's own docs say the same level name is not the same value across models.

**Do not have Cairn auto-pick effort.** Provider defaults are already tuned per model (Claude `medium` on 5.5, Codex `low` on 6.2 vs `medium` on older, Devin `currentValue`, Amp's recommended mark); "Default (named)" already defers to them. The only place Cairn chooses effort itself is its own internal uses on the routing graph (`low` for mechanical/nightly-scan, `high` otherwise) — that stays platform-owned and is right.

**Real gaps worth follow-up tickets, not settings:**

1. In-server pi providers other than the Codex subscription send no reasoning at all (`provider.ts:94` returns `levels: []`), so the Coordinator's thinking cannot be raised on an Anthropic/OpenAI/custom pi provider — the one place "think harder" is literally impossible today. Unblocking needs the pi-ai catalog `compat` flags (`forceAdaptiveThinking`, `supportsMidConvoEffort`) and a live run per `docs/design/thinking-levels.md`.
2. Vocabulary drift: Codex already advertises `ultra` (and `persistent`, `none`, `minimal` in `enabled-reasoning-efforts`); `THINKING_LEVELS` cannot name them. Extend the enum only when a provider Cairn actually drives advertises a new level.
3. `claudeCodeThinkingLevels` gates on major ≥ 5, so claude-opus-4-6/4-7/4-8 get no selector although upstream docs list them in the effort table (4.6 lacks `xhigh`). Small under-offer.
4. `profileForStep` keeps the rule's `thinkingLevel` when difficulty routing swaps the model across providers (`routing-rules.ts:510-515`) — clamped downstream, but a `max` saved for Claude can land on Codex. Acceptable today; revisit only if users read it as surprising.

**Explicitly not recommended:** a normalized "how hard" dial across providers (nothing to normalize to — the scales are vendor-calibrated); Amp-style sticky effort across model changes (Cairn deliberately reverts to Default — safer for a dispatch product whose steps run unattended); a per-task effort parameter on the Coordinator's dispatch tool (a frequent model already binds model+level as a preset; two entries for the same model at different levels are impossible today only because `frequentKey` dedups on provider+modelId — worth revisiting only if someone actually wants "opus-low" and "opus-max" side by side).

Code areas any follow-up would touch: `packages/shared/src/thinking-levels.ts` (vocabulary), `apps/server/src/coordinator/runtime/provider.ts` (in-server reasoning registration), `packages/shared/src/thinking-levels.ts:9-14` (the claude-code major gate), `apps/server/src/services/routing-rules.ts:485-516` (level on routed substitution).

## Status update (2026-11-25)

**Already shipped since 2026-11-22:**

- **Gap 1 resolved (`830558c2f`)**: `stepProvider`, `inServerThinking`, and `piThinking` (`apps/server/src/coordinator/runtime/provider.ts`) borrow `reasoning`, `thinkingLevelMap`, and `compat` from the `@earendil-works/pi-ai` catalog for every matching provider and API (`z-ai` → `zai`, `z-ai-coding-cn` → `zai-coding-cn`, plus `openai-codex`). `materializeProvider` (`apps/daemon/src/backend/pi.ts`) preserves catalog reasoning flags for aliased preset providers, while custom providers (`workbuddy`, uncatalogued relays) remain `reasoning: false` with no dropdown.
- **Gap 3 resolved (`830558c2f`)**: `claudeCodeThinkingLevels` / `claudeCodeThinkingDefault` (`packages/shared/src/thinking-levels.ts`) use the Claude Code 2.1.x deny lists (`CLAUDE_NO_EFFORT`, `CLAUDE_NO_XHIGH`, `CLAUDE_NO_MAX`, `CLAUDE_EFFORT_DEFAULT`) across 4.5–4.8 and 5.x models (`claude-opus-4-7` default `xhigh`, `claude-opus-4-6`/`claude-sonnet-4-6` without `xhigh`, `claude-opus-4-5` without `xhigh`/`max`, `customBackend: true` returning `[]`).
- **Compaction thinking level**: `summarizerFor` (`apps/server/src/coordinator/runtime/compaction.ts`) now honors an explicit `compaction` routing rule's `thinkingLevel` (`off` omits `reasoning`, unset/`null` keeps `'low'`), and falling back to the Coordinator route no longer leaks the Coordinator's own `thinkingLevel` into compaction summaries.

**Remaining open items (product / upstream SDK boundaries):**

- **Gap 2 (Codex `ultra`)**: Local `codex-cli 0.166.0` (`~/.codex/models_cache.json`) advertises `ultra` on `gpt-6.*` models, while `@earendil-works/pi-ai` `THINKING_LEVELS` still stops at `max`. Extending `THINKING_LEVELS` waits on upstream `pi-ai` support.
- **Antigravity API-key / OAuth model discovery**: `antigravity-managed.ts` (`withThinkingLevels`) probes `thought_level` per model when a Runner has host Antigravity sign-in (`agy 1.5.17` lists `gemini-4-neon`, `gemini-4-carbon`, `gemini-4-argon`, `gemini-4-hydrogen`, `gemini-3.8-flash`, `claude-opus-5-5`, `claude-sonnet-5-5`, `gpt-oss-120b-medium`), whereas `antigravity-subscription-models.ts` and `antigravity-subscription-verification.ts` only extract model IDs and `antigravitySubscriptionModelSchema` is `z.strictObject({ id, name })`. Teams using an Antigravity API key or OAuth without a host-signed-in Runner only see `thinkingLevels` for `DEFAULT_ANTIGRAVITY_MODELS` (`gemini-3.8-flash`).
- **Devin unrun models & Gap 4 (cross-provider swap)**: Devin models outside `DEFAULT_DEVIN_MODELS` still learn `thought_level` lazily on first task run via `acp.ts` (`onDevinModels`), and `profileForStep` (`apps/server/src/services/routing-rules.ts`) still passes `base.thinkingLevel` through when capability routing swaps between `claude-code` and `openai-codex` (clamped downstream).
