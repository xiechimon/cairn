## Is the process sound?

The intent matches the prior art. One required check, failed only by unresolved P0/P1, is how a repo should use Codex if it wants a gate at all: OpenAI tells you the comments are not a replacement for branch protection, and the other products either refuse to block or make blocking opt-in and severity-scoped. Google's guide says to approve an improvement and to mark nits so they do not loop. Cairn's check does the first part. The 77 replies that name a fixing commit are the part that is earning its cost, with the caveat that this note did not re-verify each diff.

Three mechanisms undid that shape tonight.

1. `#review-threads-unresolved = 0` re-blocks on P2. The check and `AGENTS.md` both say P2 does not fail the gate. The queue rule does not read the badge. One P2 held a green PR for 302 minutes.
2. The round cap labels and stays red. Seven PRs were told to reconsider at round 3 and kept pushing through rounds 4 to 8. Authors wrote "not fixing, past the cap" and then fixed on the next commit, or resolved a P1 with "not fixed" and the check went green. The cap is text. Resolution is the real signal, so a declined P1 and a fixed P1 look the same.
3. A seven-minute flake on main became a five-hour dequeue. The brake pauses on the first non-success `workflow_run` of `ci`. Mergify treats that status as a failed merge condition, leaves the queue, and will not come back until a command. The successful second attempt did not undo the label.

The bot-author split was not a cost on this sample. Migration renumbering was: 11 subjects across five PRs, and one queue exit on the drizzle meta files, independent of review quality.

## Recommendation

Do not weaken the P0/P1 check. Change the three amplifiers. This PR does not.

**Option A, recommended.** Four edits, in this order.

1. Stop the queue waiting on every thread. In `origin/main:.mergify.yml`, delete `#review-threads-unresolved = 0` from the `default` and `bot` `queue_conditions`. Leave `check-success = @github-actions/review-gate`. P2/P3 stay comments. `AGENTS.md` already says to answer them and, if they are real and outside the PR, to use the deferral sentence. Update that paragraph so it no longer says every thread must be resolved before the PR enters the queue. GitHub conversation resolution stays off; do not turn it on.
2. Make the round cap a pass. In `scripts/ops/review-gate/codex-gate-core.mjs`, `decide()` currently returns `conclusion: 'failure'` when `round >= BLOCK_ROUND_CAP`. Return `success`, keep `addHuman`, and list the still-open P1 URLs in the summary. `BLOCK_ROUND_CAP` stays 3. The author records those P1s under Risk before the next push; `scripts/pr-evidence-gate.py` does not check that list today, and this option does not add that check unless a later PR wants it. A pass with a label matches "after three rounds, rethink or hand it to ian" better than another red head.
3. Do not pause the fleet on the first failed attempt. `.github/workflows/autonomy-brake.yml` calls `scripts/autonomy-brake.mjs pause` when a `ci` `workflow_run` on `main` completes with a conclusion other than `success`. Pause only if the latest attempt of that run is still a failure, or if a second attempt of the same SHA also failed. Attempt 2 of run 43087659803 was the counterexample.
4. Do not let `dequeued` outlive the flake. `merge_queue.dequeued_label` in `.mergify.yml` is doing what Mergify documents. Either drop the label, or, when the brake issue closes, remove `dequeued` from PRs whose last dequeue reason was `autonomy-brake` and post the requeue. The resume path is `scripts/autonomy-brake.mjs`. A human removing the label was not enough tonight: Mergify put it back in 15 seconds until a queue command landed.

**Option B.** Review the final head only. Codex reviews each push because automatic review is on; the trigger is a Codex setting, not a file in this repo ([the same GitHub integration page](https://developers.openai.com/codex/integrations/github)). The gate already keys on the current head. The cost is that each one-finding push is a new round. Option A.2 is the repo-side control. Changing the Codex trigger is outside the repo and would also delay the first review.

**Option C.** Leave the P0/P1 check as it is, and do only A.1, A.3, and A.4. That keeps the loop, which reached round 8 twice tonight, but it removes the two waits that were not review quality: the P2 queue condition and the flake label.

Not recommended: blocking on P2 or P3, requiring conversation resolution in branch protection, or treating Copilot-style "never fail the check" as the whole policy. The 77 named fixes are the reason the P0/P1 check exists. The cap and the queue condition are why it felt endless.
