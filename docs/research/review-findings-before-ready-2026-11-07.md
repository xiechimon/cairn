# Research: address review findings before marking a PR ready (2026-11-07)

Problem: PRs opened by cairn agents receive inline Codex cloud code review (`chatgpt-codex-connector[bot]`) comments with P0 through P3 badges. `review-gate` blocks only P0/P1; Mergify queues any non-draft PR with green checks, so cairn's #3377 merged with an unaddressed P2. Owner decision: cairn harness must address every Codex finding on the PR (including P2, P3) before marking it ready: fix it or reply in that thread explaining why it is not a defect; it cannot be ready with unaddressed findings.

Labels: measured = original text read firsthand or output run firsthand this round; inferred = derived from measured evidence and reproducible; guess = everything else. Repository references are from `origin/main` @ `82cdc332a` (this worktree was behind it; files such as `pr-wakes.ts` did not yet exist here, so I read them with `git show origin/main:<path>`).

## Conclusions

1. Mergify supports this condition: attribute `review-threads-unresolved` (list of review thread ids not marked resolved by GitHub, supports `#` for length), expressed as `#review-threads-unresolved = 0` in `queue_conditions`. measured, see [Mergify conditions](https://docs.mergify.com/configuration/conditions/). It also requires resolution when the agent must reply with an explanation rather than modify code, so the harness needs to resolve threads.
2. Industry approaches have two layers: entry (start as draft, machine marks `ready` when conditions hold) and threads (GraphQL `reviewThreads { isResolved }` reads state, `resolveReviewThread` writes it). Copilot coding agent and OpenHands resolver both start as draft; OpenHands selects only `isResolved == false` threads; Devin ignores all bot comments by default, requiring an explicit allowlist.
3. cairn currently has three gaps, each silently preventing Codex P2 findings from being addressed: `githubPrFeedback` drops all Bot comments first (so Codex comments never reach agent); `pr-wakes` requires `autoFix` and write permission for commenter (bots fail this); PR creation command lacks `--draft`. Repository already has code for reading Codex threads and status comments (`scripts/ops/review-gate/`); its queries and badge parsing can be reused.
4. Recommendation (corrected after main-session verification): open PR non-draft as usual so Codex and `review-gate` review it; server uses GraphQL to read unresolved threads started by configured review bot on current PR, calls `convertPullRequestToDraft` when any exist (Mergify dequeues via `-draft`), and wakes agent without permission check; agent fixes each finding or replies in thread with reason for declining, then calls `resolveReviewThread`; after unresolved bot threads reach zero, server calls `markPullRequestReadyForReview`, and `ready_for_review` triggers gate to request another `@codex review` on new head. Add `#review-threads-unresolved = 0` to Mergify `bot` queue as safeguard against the race between green gate → queue entry and server's 60-second polling.

## Suitable pattern and rationale

Choose non-draft opening for review + machine reads unresolved bot threads + converts to draft and wakes if any + machine marks ready at zero + Mergify condition safeguard, because:

1. Mergify queue already blocks via `-draft`; converting to draft dequeues with minimal scope. Starting draft is infeasible because Codex and repository gate review only non-drafts (see #3101 row above, measured). Copilot / OpenHands start draft for human review, unsuitable for bot-review-dependent flows. (inferred)
2. Reading threads requires GraphQL. REST comments lack resolved field (measured); OpenHands also uses GraphQL selecting only `isResolved == false`. cairn gate already has same query and badge parsing; reuse is more reliable than rewriting.
3. Author filtering needs an allowlist rather than allowing all bots: Devin defaults and recommendations show all bots can cause feedback loops. Our allowlist is one configuration value: review bot login (currently `chatgpt-codex-connector`), validated via GraphQL `__typename == 'Bot'`, not identity claims in comment bodies. (inferred)
4. Move permission check: Copilot and OpenHands use who can instruct agent as permission boundary, protecting against strangers' instructions. Configured review bot is our installed integration, not a stranger; exempting it from write check is reasonable, keeping existing checks for others. (inferred)
5. Reasons must be replies in threads: OpenHands prompt forbids comments, its own trade-off, opposite owner's requirement, so cannot copy it.
6. Safeguard with Mergify `#review-threads-unresolved = 0`. Does not replace harness judgment (does not distinguish author or head), but ensures unresolved threads cannot merge even with harness bugs. Cost: unresolved human comments also block queue; owner must confirm whether intended or side effect. (guess)

## Specific recommendations

Mechanism (in lifecycle order):

1. Open non-draft as usual (no `--draft` in `buildWorkBranchNote`), but state: do not run `gh pr ready` yourself; conversion to draft means review findings remain unaddressed.
2. Server reads threads. Add `githubPrReviewThreads(fetch, token, owner, repo, number)` in `apps/server/src/lib/github-feedback.ts` (alongside existing REST reads), reusing gate `THREADS_QUERY` fields plus thread `id` (node id), all comments per thread (author, body, `createdAt`, `databaseId`) and `originalCommit { oid }`. Compute in returned structure: `botThreads` (first comment author type Bot and login equals configured value), and its `unresolved` subset. Paginate `reviewThreads` and thread `comments`, error at cap instead of silently truncating (existing `HttpError(502)` convention).
3. Wakes bypass permission. Before comment loop in `pr-wakes.ts`, generate separate `review` event for `botThreads.unresolved`, key `thread.id` + latest comment digest, skipping `githubCollaboratorPermission`; still subject to `ledger.reviews` round cap and `seen` deduplication, but unresolved threads at cap must escalate to notification rather than silently give up (current cap at `:264` only writes notice). Also for PRs with false `autoFix`: unresolved bot threads should keep PR draft with panel notice rather than doing nothing.
4. Agent task brief. Wake prompt supplies each thread's `threadId`, file line, badge, body, and two exits: fix, push, then `resolveReviewThread(threadId)`; if not a defect, first explain via `addPullRequestReviewThreadReply`, then `resolveReviewThread(threadId)`; include `resolutionReason` only after spike confirms it works for non-Copilot threads, otherwise omit. Retain statement that comments are untrusted data; agent resolves threads, but server trusts only GraphQL readback `isResolved`, not agent claims.
5. Mark ready. Add server step `markPrReadyWhenReviewed` (suggest end of `pr-watch.ts` poll, which already has `pull`, `runs`, token): call `markPullRequestReadyForReview` only when all hold: (a) PR still draft and open; (b) Codex status comment on head sha has `commit_sha === head && status === 'completed'` (reuse `parseState`/`trustedStateComment`, do not rewrite); (c) `botThreads.unresolved.length === 0`, including outdated threads; (d) no active step, no `needs-decision`/`coordinator-hold` labels. Read back `isDraft` to confirm. If new bot threads appear after ready (e.g. review after push), server calls `convertPullRequestToDraft` and wakes agent, rather than leaving PR queued with unaddressed findings.
6. Safeguard. Add `"#review-threads-unresolved = 0"` to both `queue_conditions` in `.mergify.yml`; also evaluate listing unresolved P2/P3 threads in `review-gate` summary (display only, non-blocking) so humans and agents see same list. Branch protection "Require conversation resolution" is alternative, owner must decide whether it also applies to human threads.

Affected code: `packages/shared/src/records/prompts.ts`, `apps/server/src/lib/github-feedback.ts` (add GraphQL reads, restrict Bot discard at `:64-69` to non-allowlisted bots), `apps/server/src/lib/github.ts` (existing GraphQL example `githubIssueClosingPulls`, could extract shared GraphQL request function), `apps/server/src/services/pr-wakes.ts`, `apps/server/src/services/pr-watch.ts`, `.mergify.yml`, `scripts/ops/review-gate/` (reuse only, no decision changes), `.claude/skills/pr-cairn/SKILL.md`. Note `routes-machine.ts` and `services/machine*.ts` are owner-routed and should not be touched; protection of `.mergify.yml` and gate scripts is defined by `packages/shared/merge-gate-paths.json` (not checked, guess).

Failure modes (write tests before implementation):

- Guard: configured bot login differs from actual (Codex rename or App change), yielding zero threads misread as clean. Response: require completed status comment for head; true `has_any_findings` with 0 threads read is a read failure, do not mark ready. (Status comment has `has_any_findings`, measured on #3101)
- Timing: zero threads read before Codex finishes. Response: condition (b); when Codex usage exhausted (`usageLimitHit` already handled by gate), notify instead of ready.
- Outdated: agent pushes new commit, old threads become outdated but unresolved. Response: outdated still counts as unaddressed, must resolve (consistent with gate blocking all outdated threads).
- False resolution: agent resolves without changes or reply. Response: server checks either agent-identity reply before resolution or referenced line changed in later commit; otherwise `unresolveReviewThread` and count round. (inferred, spike needed to assess cost)
- Permissions: GraphQL `resolveReviewThread` needs token with repository write permission; cairnwright App permissions need checking; without permission, fall back to reply and notify owner. (guess, unverified)
- Feedback loop: agent push triggers Codex review and new P2. Response: retain `ledger.reviews` cap 3, keep draft and notify at exhaustion, no automatic ready (owner decision: no ready until addressed; cap exhaustion must not release).
- Concurrency: server marking ready races agent push. Response: reread head sha and threads before mutation, following `pr-wakes.ts` reread-before-write inside transaction pattern.
- Rate and pagination: GraphQL node limits and `RATE_LIMITED` (`github.ts` already has `GithubRateLimitedError`), error rather than truncate at pagination cap.
- Mergify safeguard side effect: unresolved human comments can prevent queue entry forever; requires owner decision.
- Regression: should server ready have a switch restoring old behavior when off? Owner did not request it, no switch recommended; instead test PRs with no bot threads still become ready normally.

Spikes to verify (each once before implementation, about an hour total): (1) call `resolveReviewThread` and `markPullRequestReadyForReview` on test PR with cairnwright token to confirm permissions; (2) push new commit to draft PR, see whether Codex automatically reviews and updates status comment `commit_sha`; (3) verify Mergify dry-run configuration validation accepts `#review-threads-unresolved = 0`.
