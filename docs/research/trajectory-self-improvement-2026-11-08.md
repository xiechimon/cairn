4. Recommendation (§5): a default-off daily **trajectory review** routine. It opens one Coordinator thread per day, the way research intake does. It works in four stages: (1) deterministic failure-signature clustering over yesterday's window, with no LLM; (2) capped reflection on the new or rising clusters only; (3) one proposal per cluster, aimed at the strongest correction rung, and normal builds and PRs only for code, lint and test rungs; (4) measurement by a **protected** recurrence metric plus the existing hillclimb ruler. A new hard check refuses any loop-originated PR that touches the ruler. Today a protected path only asks for review; it does not refuse (`实测`, §3.3).

### 1.1 Guardrails the prior art agrees on

What a self-improving loop may change:

- Content in a bounded scope: memory files (Codex, the Anthropic memory tool), instructions or prompts (DSPy), a skill library (Voyager), the agent's own code (DGM, sandboxed only). (`实测`, rows above.)

What stays fixed:

- **The metric and the held-out set** (DSPy test set; DGM hidden checker).
- **The approved baseline**, which changes only by explicit review (Langfuse CI doc).
- **The evaluator**, which is a separate component from the reflector (Reflexion).
- **The write scope** (Codex: local write only, no network, no approvals; Anthropic: path rejection).
- **The path from a scheduled finding to a PR**, which keeps a human-attended step (Braintrust).
- **Lineage**, so every change can be rolled back (DGM).
- **Cost**, through bounded work per run and pausing when credits run out (Codex, Braintrust, LangSmith).

(`推断`, synthesized from the `实测` rows.)

## 2. Pattern that fits cairn

Take the Braintrust Patterns lifecycle (discover → refresh → close, 14-day comparison) and the Amp standing-thread shape. Drive them with **deterministic** clustering, because Langfuse Topics is Cloud-only and the loudest failures are infra signatures that need no LLM. Bound the LLM step like Codex: run only on a non-empty delta, cap the work. Keep the DSPy/DGM ruler separation as a hard check, not a convention. Keep Braintrust's "scheduled runs don't push" in a cairn form: the routine *proposes and dispatches* through the normal Coordinator → build → PR → review-gate → merge-route path, and never merges or touches gates itself. (`推断`)

## 5. (c) Recommended design

### 5.1 Failure modes, listed first so tests come first

1. **PR flood**: a burst like 11-06 produces hundreds of findings.
2. **Ruler edit**: the loop changes a grader, cases, the pack schema or the recurrence metric itself.
3. **Objective hacking**: a fix that rewords or swallows the error string makes the signature count drop while the failure remains. This is the DGM finding.
4. **Runaway cost**: re-reflecting full history; 200k-token packs; repeated runs on the same day.
5. **Duplicate work**: re-opening a finding that already has an issue, PR or thread.
6. **Wrong rung**: an infra or config fault (the model 404) "fixed" in code, or a hard rule stored as memory.
7. **Self-reference**: the loop's own builds' failures feed its own metric.
8. **Hallucinated evidence or injected issue text**. The existing evidence-index check and fencing in `reflectPacks` already handle this (`实测`).
9. **Quota exhaustion**: CLAUDE.md forbids switching models on quota, so the run must pause.

### 5.2 Shape

A daily **trajectory review** routine in the server scheduler. It is off by default behind a new env flag (`CAIRN_TRAJ_REVIEW=1`), and a test proves it stays off without the flag, matching the harness-profile rule. Each day it opens one Coordinator thread, `Trajectory review <day>`, with `sourceKind: 'trajectory-review'` and ref `trajectory-review:<day>`, the same dedupe pattern as `research-intake.ts`. This is the "separate standing thread" ian asked for. One thread per day keeps each day's evidence and decisions reviewable, the way LangSmith reports and Braintrust runs do. (`推断`)

| Stage | What it does | LLM? | Code area |
