# iOS APNs push: provider API, self-hosted relays and tap-to-open (2026-11-14)

Marks: **Measured** = read or run first-hand this session (link given); **Inferred** = derived from measured facts, re-checkable; **Guess** = everything else. They correspond to `实测`, `推断` and `猜测` in the review convention.

## Question

Cairn's server already sends Web Push (VAPID, `web-push`) from `apps/server/src/services/push.ts`, with triggers in `owner.ts`, `chief-questions.ts`, `chief-report.ts`, `machine-computer.ts`, `mail.ts` (digest) and `push-alerts.ts` (required alerts). The native app in `apps/ios` should receive the same notifications through APNs, and a tap must open the matching thread or question. Every operator self-hosts the server.

1. What does the APNs provider API require in 2026 (hosts, JWT, headers, payload, error handling), and is Node's built-in `http2` enough?
2. How do self-hosted products (ntfy, Home Assistant, Mastodon via Ice Cubes, Bitwarden/Vaultwarden, plus t3code) send APNs, register and prune tokens, and route a tap?
3. What is the SwiftUI side on iOS 26/27, and what can the Simulator do?

Repository facts (Measured, this worktree at `05cb5b737`):

- `PushMessage` is `{ title, body, href, tag }`; `buildPushPayload` sends `notification.navigate = origin + href` and `tag` (`services/push.ts` L30-35, L105-126). TTL is 3600 s; 404/410 from the push service deletes the row (L38-39, L181-193).
- Every trigger calls `pushToUserSafely` or `sendPushToUser`, so a second transport added inside `sendPushToUser` reaches all of them (`chief-questions.ts:195`, `owner.ts:222`, `chief-report.ts:845`, `machine-computer.ts:700`, `push-alerts.ts:225`; `mail.ts:133` queues the digest that `sweepPushDigest` sends).
- Hrefs in use: `/app?chief=<threadId>` (question asked), `/app/todo/<id>` (needs you), `/app` (report, digest), `/app?pane=machines&machine=<id>&screen=1`.
- `push_subscription` has `endpoint`, `p256dh`, `auth` (all NOT NULL) and `pairedDeviceId` (`db/schema.ts` L689-702). `revokePairedDevice` deletes subscriptions by `pairedDeviceId` (`services/paired-devices.ts:251`). The subscribe route caps 20 rows per user and team and rate-limits (`routes-push.ts` L140-200).
- `jose@6.2.12` is in `pnpm-lock.yaml` only as a dependency of `@modelcontextprotocol/sdk` (L6345); `apps/server/package.json` does not list it. The iOS app has bundle ID `dev.cairn.ios`, `CODE_SIGN_STYLE: Automatic`, no entitlements file, no `onOpenURL` and no app delegate (`apps/ios/project.yml`, `Cairn/App/CairnApp.swift`).

## Why the relays exist, and why Cairn doesn't need one

- APNs authorizes a token only for the team and bundle topics behind the provider key; a token from another app or environment returns `DeviceTokenNotForTopic` or `BadDeviceToken` (Measured, Apple docs above). ntfy, Home Assistant, Bitwarden and Ice Cubes each ship **one** App Store app that every self-hosted server shares, so only the vendor's key can push, and they run a relay (Measured for each relay, Inferred for the reason).
- Cairn has no shared App Store app. Each operator builds `apps/ios` with their own team (Automatic signing, `project.yml`), so the operator already owns the bundle ID and can create the `.p8` key in the same team. The self-hosted server can then talk to APNs directly. This has no third party, no quota and no content leaving the server, and it is the same trust shape as today's VAPID keys (Inferred).
- If Cairn later ships one TestFlight or App Store build for many operators, this flips: that build's team must run a relay (t3code, Vaultwarden shape), and self-hosted servers would forward to it as Vaultwarden does. Keep the device-token table and sender behind one function so that change is a transport swap (Inferred).
- The Ice Cubes trick, a Web Push endpoint pointing at an APNs relay, would reuse `web-push` unchanged, but it still needs a relay holding the operator's key plus a Notification Service Extension to decrypt. For a single operator that is more moving parts than a direct sender (Inferred).

## Recommendation

A direct APNs sender inside the existing pipeline, configured per operator, with tap routing through an observable router.

Server (`apps/server`):

1. **Config.** `CAIRN_APNS_KEY_PATH` (the `.p8`, read with the same 0600/no-symlink checks as `loadOrCreateVapidKeys`), `CAIRN_APNS_KEY_ID`, `CAIRN_APNS_TEAM_ID`, `CAIRN_APNS_BUNDLE_ID` (default `dev.cairn.ios`). APNs is off when any is missing, as Web Push is off without VAPID (Inferred from `pushToUserSafely`'s `vapid === null` early return).
2. **`services/apns.ts`** next to `push.ts`: one `node:http2` session per environment host, opened lazily, PING after an hour idle, reopened on `goaway` or error. JWT via `node:crypto` ES256 (`dsaEncoding: 'ieee-p1363'`), cached about 45 minutes and never re-signed inside 20 minutes. No new dependency (Measured, the Node check above).
3. **Payload mapping from `PushMessage`.** `aps.alert {title, body}` (title sliced like Web Push), `sound: "default"`, `thread-id` set to the thread or todo from `href`, `interruption-level: "active"`, a custom top-level `href` (the same relative path), `apns-collapse-id` = `tag` (SHA-256-hex-truncate it if over 64 bytes), `apns-expiration` = now + 3600 to match `TTL`, `apns-priority` 10 (5 for the digest), `apns-push-type: alert`, `apns-topic` = bundle ID. Keep the body under 4096 bytes. The digest body is already sliced to 800 chars (Inferred).
4. **Fan-out inside `sendPushToUser`**: query Web Push rows and APNs rows, send both, and count both in `PushOutcome`. Every trigger stays unchanged, so this is one pipeline (Inferred from the call sites listed above). Classify results: 200 accepted; 410 or 400 `BadDeviceToken` / `DeviceTokenNotForTopic` delete the token ("expired"); 403 `ExpiredProviderToken` re-signs once, then counts as failed; 429 and 5xx count as failed and are not retried inline (Measured, Apple error table).
5. **Storage.** A new `apns_device` table (`id`, `userId`, `teamId`, `token` unique, `environment` `sandbox|production`, `bundleId`, `pairedDeviceId`, `createdAt`) plus a Drizzle migration. Reusing `push_subscription` would need its NOT NULL `p256dh`/`auth` relaxed and a fake `endpoint`. Store environment and bundle per device, as t3code does, because Simulator and Xcode debug builds are sandbox while TestFlight is production (Measured, t3code and `aps-environment` doc). Extend `revokePairedDevice` to delete these rows too (`paired-devices.ts:251`).
6. **Routes in `routes-push.ts`.** `POST /api/teams/:id/push/apns-devices` with `{token (hex), environment}` (upsert by token, 409 if it belongs to another account, the same 20-row cap and `allowRequest` limit, `assertDeviceActive`), and `DELETE` with the same body. Return 404 when APNs is not configured, as `/push/key` does for VAPID.
7. **`push-alerts.ts` required delivery.** APNs 200 means accepted, not displayed. Receipts would need the app to POST `/push/receipts` from `willPresent`/`didReceive` or a Notification Service Extension. Leave required alerts on their current fallback path in the first change and say so in the PR (Inferred).

iOS (`apps/ios`):

1. **Entitlement.** Add the Push Notifications capability: `Cairn/Cairn.entitlements` with `aps-environment` (`development`), referenced from `project.yml` (`CODE_SIGN_ENTITLEMENTS`). Automatic signing switches it to `production` for distribution (Measured, `aps-environment` doc).
2. **`AppDelegate`** via `@UIApplicationDelegateAdaptor` in `CairnApp`. In `didFinishLaunching`, set `UNUserNotificationCenter.current().delegate` and call `registerForRemoteNotifications()`. Hand the token (hex) to `Session`, which POSTs it once signed in, and again at each launch (no caching). Implement `willPresent` (banner when in the foreground, unless that thread is open) and `didReceive`, which reads `userInfo["href"]` (Measured, Apple delegate and registration docs).
3. **Permission.** `requestAuthorization(options: [.alert, .sound, .badge])` after sign-in, not at first launch, so the prompt has context (Guess; Apple's "Asking permission to use notifications" page was not read this session: https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications).
4. **Router.** An `@Observable` `NotificationRouter` (or a `pendingRoute` on `AppModel`) that parses `href` into `.question(threadId)` for `/app?chief=`, `.todo(id)` for `/app/todo/`, `.machines(id)` and `.home`. The delegate sets it; `MainTabs` observes it and pushes onto its `NavigationStack`, waiting for `session.model` on a cold start. This is the Ice Cubes `handledNotification` and ntfy `selectedBaseUrl` pattern. `onOpenURL` is not the path for taps (Inferred). The same router can serve a later `cairn://` scheme.
5. **Tests.** A unit test for the href → route parser. A UI test that delivers a `.apns` file with `xcrun simctl push <booted> dev.cairn.ios` carrying `href` and asserts the destination screen. The Simulator's real sandbox token against a scratch server with ian's key is the end-to-end check (Measured that `simctl push` exists on the Mac; the token path is Inferred until run).

Needs ian: an Apple Developer key with APNs enabled (`.p8`, key ID, team ID), ideally one Sandbox and one Production team-scoped key, since keys are now environment-restricted (Measured, Apple token doc), and the paid team behind `dev.cairn.ios`. Downloading the key from his own account is covered by the standing authorization in `AGENTS.md`; 2FA prompts are his.
