# Prior Art: How Open-Source Personal Agents Handle Small Inline Actions & File Delivery

Research date: 2026-11-24.

Owner's verbatim question:

```text
什么叫轻任务交付，我服了，你去看看其他的开源personal agent咋做的，比如dusk agent、open manus bot
```

Concrete scenario lens used across every project:

```text
把我的简历 PDF 导出成 PNG 图片发给我
```

Evidence marking used on every claim:

- **`实测`** — read directly in primary source code, official repository documentation, or GitHub repository metadata via `gh api` during this session.
- **`推断`** — derived directly from `实测` source code and tool contracts, reproducible from the linked files.
- **`猜测`** — unverified lead (none relied on for conclusions below).

## Newcomer View & Why This Matters for Cairn

Before diving into the 10 open-source projects, consider a newcomer who installs Cairn today and has never heard of Coordinators, threads, worktrees, or runners:

- **Where they meet it and why**: In the main Cairn chat window, right after installing Cairn, they drop their resume PDF into chat and ask for PNG images back. They expect a personal assistant to run a quick command and reply with the PNGs in the same conversation within ~15–30 seconds — not to create a tracked ticket, spin up a runner worktree, and wait for an async "lightweight task delivery" workflow.
- **What they must already know**: Nothing beyond dropping a file and asking in plain language.
- **Accounts, payments, and keys asked of them**: None beyond their already-configured model provider/subscription (no extra cloud sandbox account needed when running on their own Mac or local Orb VM).
- **Where their files live**: Uploaded input files are stored in Cairn's team attachment store and staged read-only for the turn; generated PNGs are uploaded back into Cairn's team attachment store and rendered inline in chat.
- **Where they get stuck today (`实测`)**: Cairn's Coordinator system prompt (`apps/server/src/services/chief.ts:1859`) already says *"Things you can finish yourself in a few minutes you do yourself"*, and Cairn already wires `shell` (Orb VM) and `user_computer_shell` (confined Mac) on the Coordinator (`apps/server/src/services/coordinator-tool-defs.ts:42,63`). Yet Cairn currently **cannot** deliver the PNGs inline because:
  1. `attach_file` is withheld from the Coordinator (`apps/server/src/services/coordinator-tool-defs.ts:46`: `'the Coordinator attaches files through attachment'`), even though `attachment` (`packages/shared/src/protocol/chief-tools.ts:456`) is **read-only fetch** and `attachWorkerFile` (`apps/server/src/services/agent-attachments.ts:71-120`) only accepts claimed worker steps inside a worktree (`实测`).
  2. Inbound user attachments are handed to the Coordinator as base64 strings inside a tool result (`packages/shared/src/protocol/chief-tools.ts:972`) rather than staged as a readable file path on the Orb VM or Mac scratch folder (`实测`).
  3. On a host coding-harness Coordinator (`apps/daemon/src/backend/claude-code.ts:1057-1059,1457-1481`), built-in tools are locked to `Read`/`Glob`/`Grep` (`Bash` disallowed), and `list_files`/`read_file`/`write_file` are withheld on `coordinator-tool-defs.ts:43-45` despite already being implemented in `apps/daemon/src/computer/dispatch.ts:84-96,389-449` (`实测`).
  4. The prompt line *"When unsure, ask yourself whether the user wants an outcome or an answer"* (`apps/server/src/services/chief.ts:1859`) nudges the Coordinator to dispatch concrete small outcomes as background tasks (`实测` + `推断`).

## Executive Summary (TL;DR)

1. **10 out of 10 open-source personal agents run a 20-second PDF→PNG export INLINE inside the main chat turn (`实测` + `推断`).** Not a single project invents a separate "lightweight task delivery" ticket/worktree ceremony for it. Every project gives the main chat agent direct shell/code execution (`Bash`, `exec`, `terminal`, `developer::shell`, `PythonExecute`, `vm_exec`, or `host-shell-mcp`) and reserves sub-agent/task delegation strictly for parallel research, long-running multi-step work, context isolation, or peer-bot handoffs.
2. **Project identification resolved cleanly (`实测`)**:
   - **"dusk agent"** → **[DuskBotAI/duskbot](https://github.com/DuskBotAI/duskbot)** (★584, active 2026-11-24, `https://dusk.bot`), a local-first Electron multi-bot personal agent app where each bot has memory and a computer. Three unrelated GitHub repos with similar names were checked and ruled out (listed in §2).
   - **"open manus bot"** → **[milind-soni/OpenMausBot](https://github.com/milind-soni/OpenMausBot)** (★27,346, active 2026-11-24, `https://www.mausbot.com/`, note spelling *Maus* without the `n`), an open-source multi-bot personal agent desktop app with a built-in VM that shares core codebase lineage with DuskBot (`实测`). **[FoundationAgents/OpenManus](https://github.com/FoundationAgents/OpenManus)** (★59,025) is also covered in full.
3. **Isolation converges on two practical boundaries (`实测`)**:
   - **Container/VM boundary with zero inner prompts**: NanoClaw (every chat agent runs Claude Code/Codex inside a hardened Docker container with `bypassPermissions`), DuskBot/OpenMausBot (Local VM on `docker`/`podman`/`Apple container`, Cloud VM, or `bwrap` Bot-Box), OpenClaw/Hermes (hardened Docker/Podman/Modal/Daytona with `--cap-drop ALL` and `no-new-privileges`).
   - **OS-level host sandbox (`sandbox-exec` Seatbelt on macOS, `bwrap` on Linux) + optional approvals**: Letta Code, Open Interpreter (`main` Rust Codex-fork), nanobot — the exact OS confinement primitives Cairn already built in `apps/daemon/src/backend/host-shell-confinement.ts` (`实测`).
4. **File delivery back into chat converges on two mechanisms (`实测`)**:
   - **Dedicated `attach_file` / `send_file` / `message(media=...)` tool (cleanest for desktop/web & containerized harnesses)**: DuskBot & OpenMausBot (`attach_file` MCP tool translating VM/box paths → host attachment store → inline gallery), NanoClaw (`mcp__nanoclaw__send_file` via container `/workspace/outbox`), Letta Code (`MessageChannel(action="upload-file", media=...)`), nanobot (`message(media=[...])`).
   - **Output-text `MEDIA:<path>` scanning with path translation & safety allowlist**: OpenClaw (`MEDIA:` + `stageSandboxMedia()` + explicit `message` tool) and Hermes (`MEDIA:` + bare-path lifting + Docker `/workspace` host translation).
5. **Progress in chat stays quiet and inline (`实测`)**: Desktop/web personal agents stream a compact live status line + stdout tail (`NowCard` in DuskBot/OpenMausBot, `<LiveOutputView>` in Goose, `StreamingOutputDisplay` in Letta Code) and collapse finished tool calls into a single-line pill (`ActivityRun`), while IM-first agents (OpenClaw, Hermes, Letta Code Channels) edit one rolling progress bubble.

## 3. The Pattern That Fits Cairn (and Why)

### Rejecting "Lightweight Task Delivery" (Single-Path Design)

The survey gives an unambiguous answer to the owner's reaction: **do not build a "lightweight task" / mini-runner dispatch path.** Zero of the 10 open-source personal agents dispatch a 20-second file conversion to a separate task/worktree/runner. Creating a second task tier adds queue latency, a second mental model, and duplicated delivery/UI state while solving a problem that only exists because Cairn's Coordinator lacks file-in / file-out plumbing on the computers it **already** owns.

### The Composite Pattern That Fits Cairn

Cairn is uniquely close to **DuskBot / OpenMausBot + NanoClaw + Letta Code**:

1. **Inline execution on the Coordinator's existing confined surfaces (`实测` fit)**:
   - Keep the host Claude Code harness locked (`HOST_ALLOWED_TOOLS` in `apps/daemon/src/backend/claude-code.ts:1059`) so the harness process itself cannot bypass Cairn's confinement.
   - Run quick shell/file actions **inline in the Coordinator turn** through the two confined execution surfaces Cairn already ships:
     - **Default for uploaded files & web/utility work — Coordinator Orb VM (`shell` + un-withheld `list_files`/`read_file`/`write_file`)**: full VM isolation, pre-installed utility packages (`poppler-utils`, `imagemagick`, `ffmpeg`, `python3-pil`, matching DuskBot's `server/bot-tools.ts`) so PDF→PNG runs in seconds with zero apt approval prompt.
     - **When the file already lives on the owner's Mac — `user_computer_shell`**: already confined by macOS Seatbelt / Linux `bwrap` (`apps/daemon/src/backend/host-shell-confinement.ts`) + `ownComputerHardlineRefusal` (`packages/shared/src/protocol/own-computer.ts:20-173`).
2. **Bidirectional file bridge (DuskBot `attach_file` + `box-attachments.ts`, NanoClaw `send_file`, OpenClaw `stageSandboxMedia`)**:
   - **Inbound (Chat → Computer)**: Stage user-uploaded attachments (`![resume.pdf](attachment:...)`) as read-only files inside the Orb VM (e.g., `~/uploads/<id>-<name>`) or a turn scratch dir on the Mac, and hand the Coordinator the file path instead of forcing base64 through the LLM context.
   - **Outbound (Computer → Chat)**: Give the Coordinator a first-class **`attach_file({ path, caption?, computer?: 'vm' | 'mac' })`** tool that reads the generated file from the Orb VM (via `vm-desktop.ts`) or confined Mac host (via `host.ts` with `realpath`/`O_NOFOLLOW`, denying credential paths via `host-shell-confinement.ts`), runs the existing magic-byte + 10 MiB validation (`apps/server/src/services/agent-attachments.ts`), persists the attachment row, and appends `![caption](attachment:<key>)` straight into the Coordinator's chat reply — rendering inline PNG previews and download cards immediately.
3. **Sharp delegation boundary (Letta Code `Task.md` + OpenClaw `subagents.md`)**:
   - **Inline in Coordinator turn**: a handful of tool calls taking seconds to ~2 minutes whose output is an answer or a generated file/image/snippet (PDF→PNG, resizing images, scraping/checking a page, running a quick script on a local file).
   - **Dispatch a task (`open_thread`)**: changing code in a git repository, multi-step deep research, long-running jobs, or parallel background workstreams that should outlive the chat turn.
4. **Quiet inline progress (DuskBot `NowCard`/`ActivityRun`, Goose `<LiveOutputView>`)**:
   - Stream the already-implemented 250 ms `FramePoster` shell output (`apps/daemon/src/computer/dispatch.ts:68` → `computer_call.outputTail` in `apps/server/src/services/machine-computer.ts:187-249`) into a live single-line status + expandable tail inside the Coordinator turn, then collapse completed tool calls into a compact pill above the reply and inline PNG gallery.

### Scenario Table for the Recommended Design

| User Situation | What the User Sees | What Cairn Does | Wait & Cost |
|---|---|---|---|
| Drops `resume.pdf` in chat: *"Export to PNGs and send them to me"* (Orb VM connected) | Live status line (`Running pdftoppm…`), collapses to a 1-line tool pill, followed by inline PNG previews & download buttons in the same chat thread. | Stages `resume.pdf` read-only into Orb VM `~/uploads/…`, Coordinator runs `shell` (`pdftoppm -png`), calls `attach_file` for each PNG, appends `![page-1.png](attachment:…)` to reply. | ~5–20 s; 1 Coordinator turn (2–3 tool calls), zero runner/worktree startup. |
| Says *"Convert `~/Desktop/resume.pdf` on my Mac to PNGs and send them here"* (no upload, Mac connected) | Same live status line → collapsed pill → inline PNG previews in chat. | Coordinator runs `user_computer_shell` (Seatbelt-confined on Mac, using `qlmanage`/`sips`/`pdftoppm` into a temp folder), calls `attach_file({ path, computer: 'mac' })` (checked against `host-shell-confinement` read denies + `O_NOFOLLOW`). | ~5–15 s; 1 Coordinator turn, zero runner/worktree startup. |
| Uploaded file needs a missing Debian tool in Orb VM (beyond pre-installed defaults) | Inline approval card naming the apt package(s) (`install_packages`), then continues and attaches output. | Existing `holdPackageInstall` (`machine-computer.ts:1505`) pauses for owner approval, installs persistently in Orb VM, Coordinator resumes conversion and calls `attach_file`. | Approval time + ~15–30 s install (one-time per Orb VM). |
| Produced file exceeds 10 MiB or is an unsupported/blocked path (e.g. `~/.ssh/id_rsa`) | Plain-language explanation in chat (too large / blocked path) with next step (compress or split). | `host-shell-confinement` / Orb path validation rejects blocked paths; `agent-attachments.ts` enforces 10 MiB & magic-byte checks; no partial leak. | Immediate error returned to Coordinator turn. |
| No Orb VM and no Mac connected (cloud-only Coordinator) | Plain-language message explaining no computer is connected to run file conversion, with link to Computers settings. | Coordinator sees neither `vmComputer` nor `ownComputer` tools offered and tells the user directly instead of silently failing or creating a broken task. | ~2 s; 1 turn, no wasted task. |
| Asks *"Refactor the auth module and open a PR"* | Task card created & linked in chat (`open_thread`), runs asynchronously in a repo worktree and reports back when done. | Coordinator applies the delegation boundary and dispatches a task thread — heavy code work keeps full worktree, git, and CI isolation. | Minutes (async background task, unchanged). |

## 4. Concrete Recommendation & Code Areas Touched

Every path below was read directly in this repository (`实测`):

1. **Coordinator `attach_file` tool (protocol + server + daemon)**
   - `packages/shared/src/protocol/computer.ts`, `packages/shared/src/protocol/computer-tools.ts`, `packages/shared/src/protocol/own-computer.ts` — define Coordinator-scoped `attach_file` parameters (`path`, optional `caption`, optional target surface when both VM and Mac are connected) and wire frame/response types.
   - `apps/server/src/services/coordinator-tool-defs.ts` (lines 40–71, 107–139) — un-withhold `attach_file` (offered whenever `vmComputer` or `ownComputer` is true) and un-withhold `list_files`/`read_file`/`write_file` when `vmComputer` is true; remove the inaccurate comment `'the Coordinator attaches files through attachment'`.
   - `apps/server/src/services/agent-attachments.ts` (lines 13–120) — factor out the shared attachment validation & storage core (`attachmentMime`, `validateAttachmentUpload`, `writeAttachmentFile`) so both worker steps (`attachWorkerFile`) and Coordinator turns (`attachCoordinatorFile`) persist `attachment` rows and append `![caption](attachment:<key>)` tokens to the active reply message without requiring a worker worktree.
   - `apps/server/src/services/machine-computer.ts` (lines 1450–1560) & `apps/server/src/services/machine-relay.ts` (line 448) — route Coordinator `attach_file` calls to the target machine's Orb VM or Mac host provider and feed the returned file bytes into `attachCoordinatorFile`.
   - `apps/daemon/src/computer/dispatch.ts` (lines 84–96, 389–449), `apps/daemon/src/computer/vm-desktop.ts` (lines 1142–1170), `apps/daemon/src/computer/host.ts` (lines 344–430), and `apps/daemon/src/backend/host-shell-confinement.ts` — add binary `readFileBytes` (bounded to `ATTACHMENT_MAX_BYTES = 10 MiB`, `realpath` + `O_NOFOLLOW`, rejecting any path where `confinement.denied(resolved)` is true on Mac host).

2. **Inbound attachment staging (Chat → Orb VM / Mac)**
   - `apps/server/src/services/coordinator-request.ts` & `apps/server/src/services/machine-computer.ts` — when a user message includes `attachment:<key>`, offer a lightweight `stage_attachment` (or automatic staging on first `shell`/`user_computer_shell` turn) that writes a read-only copy into the Orb VM (`~/uploads/<id>-<filename>`) or confined host scratch dir, eliminating LLM base64 round-trips.
   - `apps/daemon/src/computer/vm-desktop.ts` — add binary write/stage helper alongside existing base64 file helpers (line 126) and pre-install lightweight document/media CLI utilities (`poppler-utils`, `imagemagick`, `ffmpeg`, `python3-pil`) in the Coordinator Orb VM image manifest.

3. **Coordinator prompt & inline progress UI**
   - `apps/server/src/services/chief.ts` (lines 1856–1862, `COORDINATOR_SYSTEM_PROMPT`) — replace the vague *"outcome or an answer"* split with the explicit inline-vs-task boundary (quick single-turn actions & file exports inline on VM/Mac + `attach_file`; repo changes, deep research, and long/parallel work via `open_thread`).
   - `apps/web/src/api/mappers.ts` (line 517 `pillOf` and Chief stream mapping) & Coordinator chat stream components — surface streaming `computer_call` `outputTail` while a Coordinator `shell`/`user_computer_shell` call is running, then collapse completed calls into a compact pill above the rendered attachment gallery (`apps/web/src/components/ui/attachment.tsx`, `apps/web/src/lib/markdown.ts`).

4. **Security invariants preserved (`实测`)**
   - Keep `HOST_ALLOWED_TOOLS` locked in `apps/daemon/src/backend/claude-code.ts` (lines 1057–1059, 1457–1481) — do **not** unlock host Claude Code `Bash`; all host commands continue to go through `user_computer_shell` (`host-shell-confinement.ts` + `ownComputerHardlineRefusal`) and Orb commands through `vm-desktop.ts`.
   - Enforce `confinement.denied()` + `O_NOFOLLOW` + regular-file check + 10 MiB cap + magic-byte validation on Coordinator `attach_file` so prompt injection in a PDF or webpage cannot exfiltrate `~/.ssh`, `~/.aws`, or `~/Library/Keychains` via `attach_file`.
