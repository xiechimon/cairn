# Ensuring Users Open the Newest Version of a Mac Desktop App After Updates Published While Closed (2026-11-25)

> **Question.** How do macOS desktop applications make sure the user opens the newest version even when a release was published while the app was closed? Cairn (Electron, self-signed codesign) currently checks and downloads updates only while running, swapping on quit or idle, so a release published while Cairn is closed leaves the user opening the old version first. Owner requirement: *"when the user opens Cairn, it is already the newest version."*
>
> **Evidence marks.** Every substantive claim is marked inline as:
> - **`实测`** — read or executed first-hand in this session (upstream source code at a named file/line, official first-party documentation, live official appcast/release metadata, `man` page, or read-only inspection on a local macOS 27.2.1 machine).
> - **`推断`** — derived directly from `实测` evidence and verifiable.
> - **`猜测`** — everything else (unverified implementation details of closed-source apps).

## 0. For Someone Who Installed Cairn Today (Newcomer View)

If the recommended design ships, a newcomer who dragged `Cairn.app` into `/Applications` sees almost nothing change day to day:

- **Where they meet it & why it is there:** On the first launch from a writable folder (such as `/Applications` as an admin user, or `~/Applications` as any user), macOS shows one system banner — *"Background Items Added: Cairn added items that can run in the background"* — and adds a **Cairn** toggle under *System Settings > General > Login Items & Extensions > Allow in the Background* (`实测` [Apple Login Items](https://support.apple.com/guide/mac-help/open-items-automatically-when-you-log-in-mh15189/mac)). That background task lets Cairn fetch and swap in new releases while Cairn is closed so opening Cairn lands directly on the latest build (`推断`).
- **What they must know / accounts, keys, payments:** None. Updates download from Cairn's public GitHub Releases over HTTPS and verify against Cairn's pinned self-signed certificate; no account, password, or payment is requested (`实测` [signature.ts](../../apps/desktop/src/signature.ts), [desktop-update-rollback.md](../design/desktop-update-rollback.md)).
- **Where data is stored:** One plist in `~/Library/LaunchAgents/app.cairn.updater.plist` (or embedded `Contents/Library/LaunchAgents/` if migrated to `SMAppService`), state in `~/Library/Application Support/@cairn/desktop/update-state.json`, and temporary staging folders beside the bundle (`<bundle dir>/.cairn-update-*`, `.cairn-previous/`) (`实测` [update-state.ts](../../apps/desktop/src/update-state.ts), [update-staging.ts](../../apps/desktop/src/update-staging.ts), [update-swap.ts](../../apps/desktop/src/update-swap.ts)).
- **Where they can get stuck or what they see on failure:**
  - If they are a **standard (non-admin) macOS user** running Cairn from `/Applications`, macOS denies writes to `/Applications`; the background agent exits quietly without prompting for a password, and Cairn continues to report `read-only` (moving `Cairn.app` to `~/Applications` unblocks automatic updates without admin rights) (`实测` [updater.ts](../../apps/desktop/src/updater.ts#L61-L73), local `ls -ld /Applications`).
  - If they **toggle Cairn off** in *Login Items & Extensions*, background checks while closed stop; Cairn gracefully falls back to in-app checks, idle/quit swap, and pre-window swap of any already-staged bundle (`推断`).
  - If a background-installed version fails to boot its server, Cairn's existing rollback guard restores `.cairn-previous/Cairn.app` automatically, relaunches it, records the version in `blocked`, and shows a one-line rollback notice (`实测` [main.ts](../../apps/desktop/src/main.ts#L1300-L1374), [desktop-update-rollback.md](../design/desktop-update-rollback.md)).

## 2. Detailed Prior-Art Findings

### 2.1 Chrome / Google Keystone and Chromium Updater (`chrome/updater`)

Chrome is the canonical macOS proof that *"user opens the newest version even after being closed"* requires an out-of-process `launchd` scheduler (`实测`):

1. **What runs while closed (`实测`):** On the local test Mac, `~/Library/LaunchAgents/com.google.GoogleUpdater.wake.plist` runs `~/Library/Application Support/Google/GoogleUpdater/Current/GoogleUpdater.app/Contents/MacOS/GoogleUpdater --wake-all ...` with `StartInterval = 3600`, `AbandonProcessGroup = true`, `LimitLoadToSessionType = Aqua`, and `AssociatedBundleIdentifiers = ["com.google.GoogleUpdater"]`. Upstream [wake_task.mm](https://github.com/chromium/chromium/blob/main/chrome/updater/mac/setup/wake_task.mm#L53-L90) generates this exact plist (`System` session in `/Library/LaunchDaemons` for system scope). Legacy Keystone agents (`com.google.keystone.agent.plist` and `.xpcservice.plist`) are migrated to empty `{}` stub plists plus CLI shims (`ksadmin`, `ksinstall`) ([functional_spec.md](https://github.com/chromium/chromium/blob/main/docs/updater/functional_spec.md#L411-L448)). Although `launchd` wakes `GoogleUpdater` hourly, `kDefaultLastCheckPeriod` in [constants.h](https://github.com/chromium/chromium/blob/main/chrome/updater/constants.h#L325-L345) throttles actual Omaha update checks to every **4.5 hours** (`1.0–1.2x` jitter).
2. **Swap moment (`实测`):** Updates arrive as CRX archives invoking `.install` / `.keystone_install` ([installer_api_mac.md](https://github.com/chromium/chromium/blob/main/docs/updater/installer_api_mac.md)). Chrome's [keystone_install.sh](https://github.com/chromium/chromium/blob/main/chrome/installer/mac/keystone_install.sh#L816-L980) exploits Chrome's versioned bundle layout (`Google Chrome Framework.framework/Versions/<ver>/` + `Current` symlink, confirmed on `/Applications/Google Chrome.app` locally): it `rsync`s the new version directory alongside any active version, then `rsync`s the ~50 unversioned outer files + `Current` symlink (with signals deferred) and updates `Contents/Info.plist` **last**, followed by `touch` and `lsregister -f`. Thus Chrome replaces the on-disk app **immediately upon download** whether Chrome is open or closed: closed users open straight into the new build; open sessions continue on the old `Versions/<old>/` directory until relaunch.
3. **Launch-time behavior (`实测`):** Chrome never blocks launch to fetch or swap updates. On startup it asynchronously calls `CRURegistration`'s `installUpdaterWithReply:` and `registerVersion:...` ([user_manual.md](https://github.com/chromium/chromium/blob/main/docs/updater/user_manual.md#L104-L114)).
4. **Manual bundle replacement (`实测`):** Local `~/Library/Application Support/Google/GoogleUpdater/prefs.json` stores `pv_path: "/Applications/Google Chrome.app/Contents/Info.plist"` and `pv_key: "KSVersion"` for `com.google.chrome`. Per [functional_spec.md](https://github.com/chromium/chromium/blob/main/docs/updater/functional_spec.md#L50-L56) and [lines 563–575](https://github.com/chromium/chromium/blob/main/docs/updater/functional_spec.md#L563-L575), the updater reads the live plist from disk so any drag-install over-installation is detected immediately and synced instead of overwritten.
5. **Notable macOS lesson (`实测`):** [wake_task.mm](https://github.com/chromium/chromium/blob/main/chrome/updater/mac/setup/wake_task.mm#L60-L63) carries an explicit warning: *"Explicitly logging switches are no longer necessary but are not removed because updating the plist file could cause a popup on newer macOS."* Never rewrite a LaunchAgent plist unless its contents actually change.

### 2.2 Sparkle 2

Sparkle 2 is the standard macOS native updater (confirmed locally inside `/Applications/ChatGPT.app/Contents/Frameworks/Sparkle.framework`, `实测`), and **explicitly does not update apps while closed** (`实测`):

1. **What runs while closed (`实测`):** Nothing. The [Sparkle repository](https://github.com/sparkle-project/Sparkle) ships no persistent LaunchAgent or daemon — only in-process `Sparkle.framework`, transient `Autoupdate` app, and optional sandbox XPC helpers (`Installer.xpc`, `Downloader.xpc`) ([sandboxing docs](https://sparkle-project.org/documentation/sandboxing/)).
2. **Swap moment (`实测`):** With `SUAutomaticallyUpdate = YES` ([customization docs](https://sparkle-project.org/documentation/customization/)), Sparkle checks on `SUScheduledCheckInterval` (default 86400 s, enforced minimum 1 hour), downloads, verifies EdDSA/codesign, and executes stage 1 preparation in `Autoupdate` (clearing quarantine, preserving Finder tags, pre-warming Gatekeeper via `gktool` on macOS 14.4+, [SUPlainInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/SUPlainInstaller.m#L46-L103)). `AppInstaller` then waits on `listenForTerminationWithCompletion:` ([AppInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/AppInstaller.m#L435-L445)) and runs stage 3 final swap only after the app terminates ([AppInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/AppInstaller.m#L797-L863)). If the app stays open for `SUScheduledImpatientCheckInterval` (default 1 week), Sparkle escalates to UI unless overridden by `updater:willInstallUpdateOnQuit:immediateInstallationBlock:` ([SPUUpdaterDelegate.h](https://github.com/sparkle-project/Sparkle/blob/2.x/Sparkle/SPUUpdaterDelegate.h#L430-L440)).
3. **Launch-time behavior (`实测`):** `startUpdater:` calls `scheduleNextUpdateCheckFiringImmediately:NO` ([SPUUpdater.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Sparkle/SPUUpdater.m#L475-L576)); if overdue it triggers `_checkForUpdatesInBackground` asynchronously without blocking window open.
4. **Manual bundle replacement & macOS 13+ TCC nuance (`实测`):** `SUPlainInstaller` compares `hostVersion` vs `updateVersion` and aborts with `SUDowngradeError` on downgrade ([SUPlainInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/SUPlainInstaller.m#L325-L343)). Crucially, on macOS 13+, `SUPlainInstaller` skips atomic `swapItemAtURL` and Gatekeeper pre-scan if `Autoupdate`'s Team ID does not match the new bundle's Team ID (or if `NSUpdateSecurityPolicy` is set), falling back to move-old/move-new to avoid triggering Privacy & Security prompts ([SUPlainInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/SUPlainInstaller.m#L347-L378)).

### 2.3 Squirrel.Mac, Electron `autoUpdater`, and `electron-updater`

1. **Squirrel.Mac / Electron `autoUpdater` (`实测`):** Electron's [auto_updater_mac.mm](https://github.com/electron/electron/blob/main/shell/browser/auto_updater_mac.mm#L90-L185) is a thin bridge over `SQRLUpdater`. Nothing runs while the app is closed. Once a running app downloads and verifies a zip or binary delta, `prepareUpdateForInstallation:` writes `ShipItState.plist` with `launchAfterInstallation: NO` and submits a **transient one-shot launchd job** (`<bundleId>.ShipIt`, `MachServices`, `KeepAlive: { SuccessfulExit: NO }`) via `SMJobSubmit` ([SQRLUpdater.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLUpdater.m#L1074-L1094), [SQRLShipItLauncher.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLShipItLauncher.m#L45-L179)). If target or parent dir is not writable (and `SquirrelMacEnableDirectContentsWrite` is unset), it prompts for admin authorization (`kSMRightModifySystemDaemons`) to submit into `kSMDomainSystemLaunchd` ([SQRLUpdater.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLUpdater.m#L415-L428)). `ShipIt` waits for all instances to terminate, backs up the old bundle, re-verifies the signature against `targetBundleURL`, renames in place (capped at `SQRLShipItMaximumInstallationAttempts = 3`), drains its Mach port, and exits ([ShipIt-main.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/ShipIt-main.m#L107-L260), [SQRLInstaller.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLInstaller.m#L253-L403)). Calling `quitAndInstall()` rewrites `ShipItState.plist` with `launchAfterInstallation: YES` and terminates the app so `ShipIt` relaunches via `posix_spawn` of the *new* `ShipIt` with `responsibility_spawnattrs_setdisclaim` ([SQRLUpdater.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLUpdater.m#L1096-L1116), [ShipIt-main.m](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/ShipIt-main.m#L197-L234)).
2. **`electron-updater` (`实测`):** In `electron-builder` v27, `autoInstallOnAppQuit` was replaced by `autoInstallEvent: 'onQuit' | 'onNextLaunch' | 'manual'` (default `'onQuit'`, `'onNextLaunch'` planned as v28 default to avoid OS shutdown killing Windows NSIS installers) ([AppUpdater.ts](https://github.com/electron-userland/electron-builder/blob/master/packages/electron-updater/src/AppUpdater.ts#L156-L178)). On **macOS**, however, [MacUpdater.ts](https://github.com/electron-userland/electron-builder/blob/master/packages/electron-updater/src/MacUpdater.ts#L264-L295) serves the downloaded zip over an authenticated localhost HTTP proxy to Squirrel.Mac and explicitly maps **both** `'onQuit'` and `'onNextLaunch'` to Squirrel.Mac's native quit-time swap; `installPendingUpdateIfAvailable()` resolves `false` on macOS ([AppUpdater.ts](https://github.com/electron-userland/electron-builder/blob/master/packages/electron-updater/src/AppUpdater.ts#L238-L246)). Even on Windows/Linux, `'onNextLaunch'` only installs a *previously downloaded* pending installer after re-validating it against fresh metadata — it never downloads a fresh release before opening the window.

## 3. macOS Mechanics That Govern Cairn's Design

### 3.1 `LaunchAgent` vs `SMAppService`, and `StartInterval` vs `StartCalendarInterval`

- **Legacy `~/Library/LaunchAgents/*.plist` vs `SMAppService.agent(plistName:)` (`实测`):**
  - Per Apple's [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice) and [Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), macOS 13+ lets apps embed agent plists in `Contents/Library/LaunchAgents/` (using bundle-relative `BundleProgram`) and register via `SMAppService.agent(plistName:)` — giving automatic Login Items attribution and automatic cleanup when the app is trashed.
  - **Trade-off for Cairn (`推断`):** Electron exposes no JS API for `SMAppService.agent` (only login items), so adopting `SMAppService` requires compiling a small native Swift/ObjC helper (like Cairn's existing `CairnTray`) and verifying how macOS handles `SMAppService` for a **self-signed** (`hardenedRuntime: false`, no Team ID) bundle. In contrast, Cairn **already** ships a pure-Node `~/Library/LaunchAgents/*.plist` installer using `launchctl bootstrap gui/<uid>` in [resident-host.ts](../../apps/desktop/src/resident-host.ts#L151-L190) (`实测`), which works immediately with self-signed builds. Adding `<key>AssociatedBundleIdentifiers</key><array><string>io.github.xiechimon.cairn</string></array>` fixes Login Items attribution for legacy plists (`实测` `man launchd.plist`, Apple docs).
- **`StartInterval` vs `StartCalendarInterval` (`实测` `man launchd.plist`):**
  - `StartInterval <N>` **misses scheduled firings while the Mac is asleep** (*"due to shortcomings in `kqueue(3)`"*) and skips firings if the job is already running. A laptop woken after sleeping overnight will wait up to another full interval before checking!
  - `StartCalendarInterval` **fires immediately on wake from sleep** whenever one or more scheduled intervals elapsed during sleep, coalescing missed events into a single run (`实测` `man launchd.plist`).
  - **Takeaway (`推断`):** Use **`StartCalendarInterval`** (e.g., two entries per hour at randomized per-install minutes `{ Minute: m }` and `{ Minute: (m + 30) % 60 }`), NOT `StartInterval`. Waking a laptop in the morning triggers an immediate coalesced check, and per-install minute offsets prevent thundering-herd spikes on GitHub Releases.

### 3.2 Writing `/Applications` (Admin vs Standard User) & App Management TCC

- **POSIX ownership (`实测`):** On macOS, `/Applications` is `drwxrwxr-x root:admin` (verified locally on macOS 27.2.1).
  - **Admin user** (default single-user Mac, `admin` gid 80): both the running app and a per-user `LaunchAgent` can create `.cairn-update-*` / `.cairn-previous/` in `/Applications` and `rename()` `Cairn.app` silently with zero prompts (`实测`).
  - **Standard (non-admin) user:** `access('/Applications', W_OK)` fails with `EACCES`. Without a root `LaunchDaemon` (which requires a `.pkg` + admin password up front, like Chrome system scope / MAU), standard users cannot write `/Applications`. Moving `Cairn.app` to `~/Applications` gives silent updates with zero admin prompts (`推断`, matching Slack IT guidance and Cairn's existing `updateBlocker` behavior in [updater.ts](../../apps/desktop/src/updater.ts#L69-L72)).
- **macOS 13+ App Management TCC (`实测`):** Under Apple's [NSUpdateSecurityPolicy](https://developer.apple.com/documentation/bundleresources/information-property-list/nsupdatesecuritypolicy) and App Management rules, macOS restricts one signed app from modifying *another* signed app's bundle unless they share a Team ID, declare `NSUpdateSecurityPolicy`, or have user-granted *Privacy & Security > App Management* (see also Sparkle's [SUPlainInstaller.m](https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/SUPlainInstaller.m#L348-L378)). Running the background updater via **`Cairn.app/Contents/MacOS/Cairn` with `ELECTRON_RUN_AS_NODE=1`** (the exact pattern in [resident-host.ts](../../apps/desktop/src/resident-host.ts#L114-L120)) keeps the mutating executable *inside `Cairn.app` itself* rather than invoking an unrelated `/usr/bin/node` or shell binary — minimizing TCC friction while staying compatible with Cairn's self-signed identity (`推断`; verify empirically on a clean macOS 15/26/27 profile during implementation).
- **Swapping a bundle whose own binary is running the updater (`推断`):** On APFS/POSIX, renaming `/Applications/Cairn.app` → `/Applications/.cairn-previous/Cairn.app` while `Cairn.app/Contents/MacOS/Cairn` (`ELECTRON_RUN_AS_NODE=1`) is executing is safe because the running process holds open descriptors/pages to the existing inode, and Cairn already performs this exact self-rename inside [updater.ts](../../apps/desktop/src/updater.ts#L337-L353) (`实测`). Once the short-lived updater exits, the next `launchd` wake resolves `/Applications/Cairn.app/Contents/MacOS/Cairn` to the **new** version.

### 3.3 The "Background Items Added" Login Items Notification

- On macOS 13+, registering any `SMAppService` agent or writing a plist to `~/Library/LaunchAgents/` triggers a system notification (*"Background Items Added"*) and adds an entry under *System Settings > General > Login Items & Extensions > Allow in the Background* (`实测` [Apple Platform Deployment](https://support.apple.com/guide/deployment/manage-login-items-background-tasks-mac-depdca572563/web), [Apple Login Items](https://support.apple.com/guide/mac-help/open-items-automatically-when-you-log-in-mh15189/mac)).
- **Attribution for self-signed Cairn (`实测` Apple docs + `推断`):** Without `AssociatedBundleIdentifiers`, macOS falls back to the signing certificate's organization (`xiechimon` in Cairn's cert) or the bare executable name. Including `AssociatedBundleIdentifiers: ["io.github.xiechimon.cairn"]` labels the entry cleanly as **Cairn**.
- **Avoid repeat popups (`实测` Chromium [wake_task.mm](https://github.com/chromium/chromium/blob/main/chrome/updater/mac/setup/wake_task.mm#L60-L63)):** Rewriting the plist file on every launch can re-trigger the notification. Cairn must write the plist **only when missing or when bytes actually differ** (e.g., if the user moved `Cairn.app` to a new path).
- **User revocation:** Users can disable the toggle at any time (`实测` Apple docs). Cairn must never fight a user toggle or assume the agent ran; in-app updates remain the fallback.

## 4. The Pattern That Fits Cairn — and Why

**Across all 10 external products/frameworks surveyed, only two achieve "open directly into the newest version after being closed" — Chrome (`GoogleUpdater`) and Microsoft AutoUpdate — and both use a `launchd` background agent (`实测`).** Every in-app framework (Sparkle 2, Squirrel.Mac, Electron `autoUpdater`, `electron-updater` on macOS, VS Code, Slack, Zed, Arc, Dia) leaves the user opening the old version whenever a release ships while the app is closed.

Evaluating Cairn's two candidates against Cairn's real measurements (`实测`):

1. **Why Candidate (a) (`launchd` updater agent) is the primary fit:**
   - It is the **only** mechanism that downloads and swaps a **349 MB zip / 991 MB unpacked bundle** *before* the user clicks Cairn, delivering **0 ms launch penalty** and zero double-launch flicker (`实测` sizes + `推断`).
   - Cairn already uses `ELECTRON_RUN_AS_NODE=1` + `~/Library/LaunchAgents/*.plist` in [resident-host.ts](../../apps/desktop/src/resident-host.ts) and already has `applyStagedUpdate`, `verifyCairnSignature`, `update-state.json`, and `armVersionGuard` rollback (`实测`). When the background agent writes `installed` to `update-state.json`, **Cairn's existing 30-second health guard automatically protects the first open of a background-installed release** — giving Cairn safer closed-app updates than Chrome or MAU (`推断`)!
2. **Why Candidate (b) splits in two — adopt `(b1)`, reject `(b2)`:**
   - **Reject `(b2)` (fetch + extract + swap from network at launch before window):** With 349 MB zips (`实测`), 991 MB `ditto` extraction (`实测`), and 1.77 s `codesign` (`实测`), blocking launch to download would stall startup for **35–100+ seconds** on every release (and Cairn ships multiple releases per day). Zero surveyed Mac apps do this; VS Code explicitly moved update checks past `AfterWindowOpen` + 30 s to protect launch speed (`实测`).
   - **Adopt `(b1)` (pre-window swap of an *already-staged* bundle):** If `update-state.json` already points to a valid staged bundle on disk (e.g. the previous Cairn session was force-quit, hit the `server === null` quit bug, or the background agent finished staging moments before the user clicked Cairn), verifying `codesign` (**1.77 s**) + two atomic `rename()`s + `app.relaunch()` takes only **~3–4 s** and closes the remaining seam without ever touching the network (`实测` + `推断`).

### Scenario Table (Recommended Hybrid: Candidate (a) + Candidate (b1))

| Scenario | What the user sees | What Cairn does | Wait / cost |
|---|---|---|---|
| Release ships while Cairn is closed; Mac is awake ≥ 30 min (or wakes from sleep before user opens Cairn) | Opens Cairn straight into the newest version | `app.cairn.updater` (`StartCalendarInterval`) downloads, verifies SHA-256 + `codesign`, confirms Cairn is closed, swaps atomically, writes `installed`; next open arms `armVersionGuard` | **0 s** at open; ~349 MB download in background while closed |
| Release ships < 30 min before open (agent hasn't finished yet) | Opens old version immediately; updates at idle/quit as today (if agent finished staging before click, ~3–4 s swap + relaunch via `(b1)`) | Agent yields if Cairn launches before swap (lock + running-app check); running Cairn takes over via existing `updater.ts` | 0 s (or ~3–4 s if already staged) |
| Previous Cairn quit while attached to `resident-host` / remote, or was force-killed with a staged update ready | ~3–4 s brief relaunch before window appears, then opens on newest version | `(b1)` pre-window check in `boot()` swaps valid `staged` bundle and relaunches; also fix `before-quit` so normal quit applies even when `server === null` | ~3–4 s once |
| User manually drags a newer/older `Cairn.app` into `/Applications` while closed | Nothing unexpected; manual copy is respected | Agent reads live `<bundle>/Contents/Info.plist` version (never downgrades or trusts stale state); boot discards mismatched `staged` record | — |
| Background-installed build crashes its server on first open | One-line rollback notice; previous version opens automatically | Existing `armVersionGuard` restores `.cairn-previous/Cairn.app`, writes `blocked`, relaunches; background agent skips `blocked.version` | One automatic rollback relaunch |
| User drags `Cairn.app` to Trash | Background agent stops and removes itself cleanly | On next tick, agent sees `<bundle>` missing → `launchctl bootout` + `unlink` its own plist (like Chromium Updater auto-uninstall) | Zero lingering orphan agent |
| User toggles Cairn off in *Login Items & Extensions*, or runs from read-only `/Applications` as standard user | No error popups or password loops | Agent disabled or exits 0 on `EACCES`; Cairn falls back to in-app checks + idle/quit + `(b1)` (or `~/Applications` for standard users) | Graceful degradation |

## 5. Concrete Recommendation & Code Areas Touched

Adopt **Candidate (a)** (a lightweight per-user `launchd` updater agent using `StartCalendarInterval`) combined with **Candidate (b1)** (pre-window swap of an already-staged bundle only) and **fix the `before-quit` `server === null` skip**:

1. **Extract pure, Electron-free update core (`apps/desktop/src/update-core.ts` — new, or refactored from `apps/desktop/src/updater.ts`):**
   - Move manifest fetch (`DESKTOP_MANIFEST_URL`), SHA-256 streaming download, `ditto` extraction, `verifyCairnSignature`, `readBundleVersion`, and `applyStagedUpdate` behind pure Node functions taking `{ bundlePath, userData, currentVersion }` so both the Electron app and the headless `launchd` worker share a **single path** (no duplicated download/verify/swap logic).
   - Add a file lock (`<userData>/update.lock` with PID + liveness check) shared by both the running app's `updater.ts` and the background worker so they can never stage or swap concurrently.
2. **Add headless background worker (`apps/desktop/src/background-updater.ts` — new; built via `apps/desktop/build.mjs` and bundled in `extraResources` in `apps/desktop/electron-builder.yml`):**
   - Executed by `launchd` via `<bundle>/Contents/MacOS/Cairn` with `ELECTRON_RUN_AS_NODE=1` and `CAIRN_BUNDLE_PATH=<bundle>` / `CAIRN_USER_DATA=<userData>`.
   - Algorithm:
     1. If `<bundle>/Contents/MacOS/Cairn` no longer exists (app trashed), uninstall `app.cairn.updater.plist` (`launchctl bootout` + `unlink`) and exit `0`.
     2. Check bundle writability (`access(dirname(bundle), W_OK)`) and non-translocated path; exit `0` quietly if read-only.
     3. Acquire `<userData>/update.lock`; exit `0` if held by another updater.
     4. Check if desktop Cairn is running (Electron `SingletonLock` in `<userData>` + process check for `<bundle>/Contents/MacOS/Cairn` excluding own PID and `resident-host` PID); if running, exit `0`.
     5. Read live `currentVersion = readBundleVersion(bundle)` and `state = readUpdateState(userData)`.
     6. If `state.installed !== null`: **do not overwrite an unconfirmed update** (let the user's next launch run `armVersionGuard` first so a rollback target `.cairn-previous` is never clobbered!).
     7. Fetch `DESKTOP_MANIFEST_URL`; compare against live `currentVersion` and `state.blocked`; if newer, download + extract + verify `codesign` (or reuse matching valid `state.staged`).
     8. Re-check that Cairn is **still closed** right before swap. If `resident-host` (`server-owner.json` with `managedBy: 'launchd'`) is alive, either hold swap while a Runner step is in flight or `launchctl kickstart -k gui/<uid>/app.cairn.host` immediately after swap so the resident server reloads from the new bundle.
     9. Run `applyStagedUpdate`, write `installed` (`previousVersion: currentVersion`, `previousApp`) and `staged: null` to `update-state.json`, remove the staging folder, append to `update.log`, and exit `0`.
3. **Register the `launchd` agent idempotently (`apps/desktop/src/updater-agent.ts` — new, modeled on `apps/desktop/src/resident-host.ts`):**
   - Label `app.cairn.updater`, path `~/Library/LaunchAgents/app.cairn.updater.plist`.
