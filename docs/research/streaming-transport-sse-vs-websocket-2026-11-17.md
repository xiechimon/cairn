# SSE versus WebSocket for streaming agent output to the UI (2026-11-17)

Question from ian: T3 Code streams agent events to its web, desktop and mobile UIs over one WebSocket (Effect RPC, `apps/server/src/ws.ts`), not SSE, and many personal-agent products do the same. What are the real benefits and costs of WebSocket versus SSE (and long-poll, HTTP streaming, WebTransport) for streaming token deltas, tool calls and step status to a UI, and what should Cairn do? This note follows the `research` skill: primary sources only, every claim marked, a comparison table, the pattern that fits Cairn, and a recommendation with code areas. It builds on [t3-code-runtimes-2026-11-17.md](t3-code-runtimes-2026-11-17.md) section 2 and does not repeat it.

Tag convention: **实测** = read or run first-hand this session (spec text, vendor page, source at a named commit, a command I ran); **推断** = derived from 实测, recheckable; **猜测** = the rest.

## 0. Conclusions

1. **Stay on SSE for server to web (and daemon to server); do not switch to a single WebSocket.** Cairn's UI channel is one-directional (agent output, step status), steer, stop and approvals already go over ordinary POSTs, and the resume story is "snapshot on subscribe plus refetch", which a WebSocket would not change. (推断 from 实测, sections 4 and 6)
2. **T3's WebSocket is chosen for T3's shape, not because SSE cannot stream tokens.** T3 is event-sourced with a per-thread sequence cursor and a replay protocol, multiplexes a shell stream and many thread streams on one socket, and needs one transport for web, Electron and React Native. Its docs do not state a reason against SSE; they give a header limit as the reason for query-string tickets. T3 itself still uses `EventSource` for media routes. (实测, section 5)
3. **Hybrid already exists in Cairn and in the references.** OpenCode serves its event stream over SSE and its PTY over a ticketed WebSocket; Vibe Kanban serves events over SSE and logs over WebSocket; OpenAI's Responses API streams over SSE by default and offers a WebSocket mode specifically for mid-turn steering and multi-lane tool loops. Cairn already runs WebSocket for the noVNC computer screen (`apps/server/src/services/computer-screen.ts`). Use WebSocket per bidirectional surface, SSE for fan-out. (实测, sections 5 and 6)
4. **Real SSE weak points in Cairn, measured or read (section 6):** (a) HTTP/1.1 origin limit: 6 open streams in one browser origin starve ordinary `fetch` (measured: 6 open, 7th `CONNECTING`, a plain API fetch got no response in 5 s); each Cairn tab holds two streams, so three tabs hit it. (b) No `X-Accel-Buffering: no` and no `no-transform`, so default nginx buffers the stream. (c) The server write queue per connection is unbounded (`createSerialConnection`), with no slow-consumer policy. (d) No `id:` on events, so native `Last-Event-ID` resume is unused; resume is refetch. (e) No foreground or online probe, `refetchOnWindowFocus: false`, so recovery after sleep waits for a 20 s `setTimeout` watchdog. (f) The daemon's delta POSTs are not chained or sequenced.
5. **Each fix is small and stays on SSE** (section 7). Switching to WebSocket would not fix (a) through (f) by itself: (a) trades for another connection kind, (c) and (e) need the same policies, (b) becomes "needs `Upgrade` support in every proxy" instead.
6. **Triggers to revisit:** an interactive channel that needs low-latency client-to-server frames on the same stream (terminal, live steer-while-typing, multiplexed lanes), or a need to run one connection for several conversations. Then add WebSocket for that surface only.

## 1. What each transport does and its protocol-level limits (question a)

| Mechanism | What it is | Limits that matter here | Source |
|---|---|---|---|
| SSE (`EventSource`) | A long-lived `GET` returning `text/event-stream`; one-way server to client; text only (UTF-8); events split by blank line; fields `data`, `event`, `id`, `retry`; lines starting with `:` are comments | The `EventSource` constructor takes only a URL and `withCredentials`; there is no way to set request headers; a response with 204 stops reconnecting | [WHATWG HTML §9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html) (实测) |
| WebSocket (RFC 6455) | An HTTP/1.1 `Upgrade` handshake, then a bidirectional framed protocol with text and binary frames, ping/pong control frames, close frames | No built-in resume, no message ids, no ack; reconnect is the application's job. Auth is "any HTTP client authentication available to a generic server" at the handshake, but the browser `WebSocket` API cannot set headers, so tokens go in the URL, cookies or a subprotocol. The browser API has no way to apply backpressure (MDN) | [RFC 6455 §5.5 and §10.5](https://www.rfc-editor.org/rfc/rfc6455), [MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket) (实测); header limit also confirmed by T3's and OpenCode's own source comments (section 5) |
| WebSocket over HTTP/2 and HTTP/3 | Extended `CONNECT` on one stream, enabled by `SETTINGS_ENABLE_CONNECT_PROTOCOL`; same framing | Requires the server and every proxy hop to implement it; otherwise the browser uses an HTTP/1.1 connection for the socket | [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441), [RFC 9220](https://www.rfc-editor.org/rfc/rfc9220) (实测); Go's `httputil.ReverseProxy` forwards `Upgrade` only on HTTP/1 connections, see section 3 |
| Long poll / HTTP streaming | Repeated requests that the server holds, or one response that never ends | Any intermediary may legally buffer a whole response, so streaming fails behind such proxies; long poll costs a request per batch; connection counts matter | [RFC 6202 §2 and §3](https://www.rfc-editor.org/rfc/rfc6202) (实测) |
| WebTransport | Multiplexed streams and datagrams over HTTP/3 (QUIC) | Browser support is "newly available" since March 2026 (MDN Baseline 2026); needs UDP and an HTTP/3 server path; Node's API reference has no WebTransport server (no match in `nodejs.org/api/all.html`); Tailscale's serve proxy is built on Go's `ReverseProxy`, which is an HTTP request/response proxy | [MDN WebTransport](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API), [Node API index](https://nodejs.org/api/all.html) (实测); "not a fit for Cairn's loopback and tailnet users" is 推断 |

SSE reconnection per the spec (实测, [§9.2.3 and §9.2.4](https://html.spec.whatwg.org/multipage/server-sent-events.html)): after a dropped connection the browser waits the reconnection time (the `retry:` field, default implementation-defined, "a few seconds"), optionally with exponential backoff, then reconnects and sends `Last-Event-ID` set to the last `id:` it saw. Without `id:` the header is never sent. The authoring notes advise a comment line about every 15 seconds to protect against legacy proxies that drop idle connections.

Connection limits (实测): MDN says that without HTTP/2, SSE is limited to 6 connections per browser and domain across all tabs, marked "Won't fix" in Chrome and Firefox, and that under HTTP/2 the limit is the negotiated number of concurrent streams, default 100 ([MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). HTTP/2 stream concurrency is `SETTINGS_MAX_CONCURRENT_STREAMS`, set per endpoint ([RFC 9113 §5.1.2](https://www.rfc-editor.org/rfc/rfc9113)). The old RFC 6202 text records the same pressure ("6 or 8 connections", easily reached with tabs). A browser WebSocket does not use the HTTP/2 stream budget unless the whole path implements RFC 8441. (推断; whether Chrome counts an HTTP/1.1 WebSocket against the 6-connection pool is 猜测, not measured.)

Auth with `EventSource` (实测 in Cairn and in the references): Cairn mints a one-time "stream ticket" by `POST /api/auth/stream-ticket` and puts it in `?ticket=` (`apps/web/src/api/sse.ts`, `streamUrl`; server `apps/server/src/routes-core.ts` line 104). T3 does the same for WebSockets: "since a WebSocket cannot set headers", RPC sockets use short-lived tickets obtained over authenticated HTTP ([environment-auth.md lines 79-84](https://github.com/pingdotgg/t3code/blob/0ff1495c05301c1f32503d7861bf9a917e521b40/docs/internals/environment-auth.md)). OpenCode's authorization middleware says the same for its PTY upgrade ([authorization.ts line 83](https://github.com/sst/opencode/blob/c658753fdb0eb94682c98256e854f6683d88aeb9/packages/server/src/middleware/authorization.ts)). So the header limit is shared, not an SSE-only cost. The alternative for SSE is `fetch` plus a streamed body, which allows headers and is what Cairn's daemon already does (`apps/daemon/src/machine-client.ts` `stream()`); parsing SSE by hand is then the cost (推断).

Net for a self-hosted, user-controlled deployment (Tailscale serve, Caddy, nginx): SSE needs nothing but one header for nginx; WebSocket needs `Upgrade` forwarding and, behind HTTP/2 front ends, an HTTP/1.1 fallback path (推断). SSE has the better default on the proxies Cairn users use.

## 3. Bidirectional needs (question c)

Cairn's UI to server actions are discrete commands: send message, steer, stop, approve, answer an ask. They are low-rate, need an HTTP status and an idempotent result, and already exist as POSTs. The daemon's inbound path is a claim long-poll plus an SSE "wake" stream, with `steer` and `stop` fetched over GET and acknowledged over POST (`apps/server/src/routes-machine.ts`, `/api/machine/stream`, `/steer`, `/steer/ack`, `/stop`). (实测)

A shared WebSocket would earn its keep only when the client's frames must arrive on the same ordered channel as server frames (OpenAI's `response.steer` references the live `previous_response_id` on the same connection), when handshake cost per command matters (T3 and OpenAI cite repeated round trips in tool-heavy loops), or for raw interactive streams (terminal, VNC). Cairn has no such token-level client frame today; the one interactive raw stream (computer screen) is already a WebSocket. (推断)

## 4. Resume, replay and back-pressure (question d)

| Concern | SSE standard behaviour | WebSocket standard behaviour | Product practice |
|---|---|---|---|
| Resume after disconnect | `Last-Event-ID` plus `id:` fields, if the server writes them | none; application protocol | MCP Streamable HTTP uses SSE `id` and `Last-Event-ID` for resumable streams, and says the server must not broadcast one message on several streams ([MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)); OpenAI background mode resumes by `starting_after=<sequence_number>` over SSE ([background guide](https://platform.openai.com/docs/guides/background)); T3 resumes WebSocket thread streams by `afterSequence` with replay, falling back to a snapshot when the cursor is pruned (`ws.ts` lines 1034-1130); OpenAI WebSocket mode recovers by reconnecting and continuing from `previous_response_id`, connections expire at 60 minutes ([WebSocket mode](https://platform.openai.com/docs/guides/websocket-mode)) |
| Back-pressure | The server's writes block on TCP; nothing in the protocol bounds a server-side queue | The browser API cannot apply receive backpressure (MDN) | OpenCode gives each SSE subscriber a bounded dropping queue (4096) and fails the subscriber with an overflow error when it fills, so the client reconnects and refetches ([event-feed.ts](https://github.com/sst/opencode/blob/c658753fdb0eb94682c98256e854f6683d88aeb9/packages/server/src/event-feed.ts)) |

All sources are 实测. The point for Cairn: resume is a data-model property (cursor in events, or snapshot on subscribe), not a transport property. WebSocket would not give Cairn resume; T3 had to build one on top.

## 6. Cairn's SSE as built, and what I measured (question f)

### 6.1 How it works (实测, read at `319985689`)

- **Three channels** declared in `packages/shared/src/protocol/sse.ts`: team (`/api/teams/:id/stream`), conversation (`/api/conversations/:id/stream`) and machine (`/api/machine/stream`, daemon). Routes use Hono `streamSSE` (`routes-core.ts` lines 266-295 for the team stream, `routes-builds.ts` lines 132-160, `routes-machine.ts` lines 442-478).
- **Server fan-out**: `TeamStreamHub` and `ConversationStreamHub` (`apps/server/src/services/events.ts`). Each connection is `createSerialConnection`: a per-connection promise chain `tail = tail.then(() => write(payload))` with a per-connection `seq`.
- **Live text**: `ConversationStreamHub` keeps the tail of the current text and thinking buffer per conversation (128 KiB, 128 conversations, in memory) and replays it to a new subscriber, together with the last activity and agent-todo, then publishes deltas. A `message` or terminal `step` event clears the buffer.
- **Heartbeat**: a `ping` data event every 15 s (`TEAM_STREAM_PING_INTERVAL_MS`), which also checks whether a paired device is still valid.
- **Web client** (`apps/web/src/api/sse-connection.ts`, `sse.ts`): own reconnect loop on top of `EventSource`; on `error` it closes and reopens with backoff 1 s to 30 s (fetching a fresh ticket); a 20 s silence watchdog closes and reopens; a business-silence timer calls `reconcile` (refetch of all stream query keys) while work is in flight, with the window doubling up to 5 min; a `seq` gap triggers `reconcile`; every reconnect after the first calls `resync`, which clears the live stores and invalidates all queries.
- **Daemon leg**: text and thinking deltas are batched every 250 ms (`DeltaRelay`) and each batch is one `POST /api/machine/tool/:stepId` (`transcript_delta`); finished segments are POSTed as rows (`step-transcript-stream.ts`); the daemon's inbound stream is a `fetch` of `/api/machine/stream` with a bearer header.
- **Server runtime**: `@hono/node-server` `serve(...)` on Node `http` (`apps/server/src/index.ts` line 316), so HTTP/1.1; the Electron app loads the same server over loopback. A `ws` WebSocket server already exists for the computer screen (`computer-screen.ts`, `server.on('upgrade', ...)`), authenticated by `wsProtocols`.

### 6.2 What I ran

Server started from this worktree with `PORT=8877` and a temp `CAIRN_HOME` (port checked free first; stopped and the temp directory removed afterwards; no real data touched). Results:

1. **Response headers** of `GET /api/teams/:id/stream` with `Accept-Encoding: gzip` and `Last-Event-ID: 41`: `200`, `content-type: text/event-stream`, `cache-control: no-cache`, `transfer-encoding: chunked`. There is no `x-accel-buffering`, no `no-transform`, no `content-encoding`. (实测)
2. **Frames over 45 s**: `data: {"type":"ping","seq":1}` at 0 s, `seq` 2 at 15.3 s, `seq` 3 at 30.2 s, `seq` 4 at 45.1 s. No `id:` or `retry:` field anywhere, so `Last-Event-ID` can never be sent or honored; `seq` restarts at 1 on each connection. (实测)
3. **Connection limit in a real browser (Chromium 156, `nextHopProtocol: http/1.1`)**: opened `EventSource` connections to the team stream with fresh tickets. Result: six reach `OPEN` (state 1); the seventh stays `CONNECTING` (state 0); then a plain `fetch('/api/server/backup')` to the same origin returned nothing within 5 s (my timeout) and my ticket fetch for an eighth stream hung. Closing the streams released the queue. (实测)

I did not measure: slow-consumer memory growth on the server (needs a publisher; no test endpoint exists), the sleep/wake gap on a real laptop, or any proxy (nginx, Caddy, Cloudflare, Tailscale) end to end. Those findings come from reading code and docs and are marked 推断.

| W4 | No event ids; resume is "reconnect, refetch all", and live text rebuilds only from the in-memory 128 KiB buffer (lost on server restart, or when the cap is exceeded: the head is dropped) | measurement 2; `CONV_TEXT_BUFFER_MAX_BYTES`; `sse.ts` `resync` | Low to medium: durable state is in rows, live text is cosmetic and finalized by a `message` row, so the failure is a short flicker. Class: gap on reconnect, covered by refetch. |
| W5 | Recovery after sleep or background waits for the 20 s watchdog (a `setTimeout`, throttled when hidden over 5 minutes); there is no `visibilitychange` or `online` handler on the stream, and `refetchOnWindowFocus` is `false` | `sse-connection.ts` `armWatchdog`; grep of `visibilitychange`, `online` in `apps/web/src`; `design/product-providers.tsx` line 59; T3 notes the same problem and probes on foreground | Medium on laptops and phones, 推断. Class: dead half-open connection detection. |
| W6 | Daemon delta POSTs are fire-and-forget from a timer: `flush()` calls `void flushNow()` without waiting for the previous POST, no per-delta sequence, so two in-flight POSTs can arrive out of order or one can be lost (logged only) | `delta-relay.ts`, `step-transcript-stream.ts`, `machine-client.ts` `transcriptDelta` | Low: the finished segment row replaces the live text; 推断, not measured. Class: unordered delivery. |
| W7 | `ping` is a data event, so every ping runs `JSON.parse` and `onEvent` in the UI (the machine stream uses `: ping` comments, which its `fetch` reader ignores) | `routes-core.ts`; `routes-machine.ts` line 466 | Cosmetic; not a defect, see recommendation 6. |

None of W1 to W7 is a limit of SSE as a protocol. W1 is the only one SSE shares with a naive WebSocket design on the same origin (a WebSocket per tab per stream), and it disappears under HTTP/2 or with one stream per tab.

## 8. Recommendation

**Stay on SSE and harden it (option A); keep WebSocket as a per-surface tool (option B) when an interactive stream is requested.** Reasons, each from the evidence above: the channel is one-way and commands are POSTs (section 3); resume is solved by snapshot-on-subscribe plus refetch and would have to be rebuilt on a WebSocket (section 4); SSE has the better defaults on the proxies Cairn users run (section 2); the references that stream model output use SSE and reserve WebSocket for raw interactive surfaces (section 5); every measured or read weak point is fixable without changing transport (section 6.3).

Concrete changes, with code areas (each its own small commit; none done here, this note is research only):

1. **W1, one multiplexed stream per tab.** Merge the conversation stream into the team stream (or open the conversation stream only for the foreground thread and close it for hidden tabs), or serve over h2 where possible. Areas: `apps/web/src/api/sse.ts`, `api/provider.tsx`, `board/use-thread-chat.ts`, `chief/use-chief-surface.ts`, `apps/server/src/routes-core.ts`, `routes-builds.ts`, `services/events.ts`. Test: with seven open streams to one origin a normal request must still complete. A cheaper first step: `BroadcastChannel`/`SharedWorker` leader election so one tab holds the streams (推断, 猜测 on how it behaves in Electron).
2. **W2, add the headers.** `X-Accel-Buffering: no` and `Cache-Control: no-cache, no-transform` on all three `streamSSE` routes (OpenCode sets both). Test: header assertion beside the existing stream tests.
3. **W3, bound the queue.** In `createSerialConnection` count pending writes; past a cap close the stream (the client already reconnects and refetches), as OpenCode does at 4096. Areas: `apps/server/src/services/events.ts`; test with a never-resolving writer.
4. **W5, probe on foreground.** Add `visibilitychange` and `online` handlers in `sse-connection.ts` that, when a stream has been silent longer than one ping interval, reopen immediately instead of waiting for the 20 s timer (T3's approach, simplified). Areas: `apps/web/src/api/sse-connection.ts`.
5. **W4 and W6, only if they show up in a trace.** Optionally write `id:` equal to a per-conversation counter so a text buffer can be resumed exactly, and chain or sequence the daemon's delta POSTs (`delta-relay.ts` `flush` awaiting the previous send). Do not add a cursor protocol (T3's `afterSequence`) unless live text correctness becomes a requirement; final rows already heal.
6. **W7, leave `ping` as a data event.** A comment line (`: ping`) is invisible to `EventSource` `onmessage`, so the 20 s watchdog in `sse-connection.ts` could no longer see liveness; the `: ping` form is right only for the daemon's `fetch` reader. Change it only if the browser client moves to `fetch` streaming (option D). Recorded to avoid a wrong fix.

If ian chooses **option C** (switch), the minimum is: the RPC and subscription schema in `packages/shared/src/protocol/`, a `ws` upgrade route next to `computer-screen.ts` with ticket auth, per-subscription sequence cursors in `TeamStreamHub` and `ConversationStreamHub` with a replay store, a client supervisor to replace `sse-connection.ts`, the daemon wake stream moved or left on SSE, documentation of `Upgrade` for nginx and Caddy, a check that Tailscale serve delivers it, and removal of the SSE routes in the same change. T3's `connection-runtime.md` and `ws.ts` lines 1034-1130 are the reference implementation to copy from. I estimate this at several times the cost of A (猜测).

If ian chooses **option B**, add the WebSocket route only for the specific surface and reuse the existing ticket and `wsProtocols` mechanism from the computer screen; leave the SSE channels as they are.
