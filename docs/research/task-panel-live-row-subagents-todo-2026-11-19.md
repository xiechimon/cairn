**Pattern that fits Cairn [inferred].** Claude Code, Cursor and Zed converge on two delivery modes: queue to turn end by default, and an explicit "send now" that lands at the next tool boundary rather than killing work. Cairn already implements the boundary half (`flushSteers` waits for `runningTools` to drain), so the gap is in the UI and in the wire. For the row, the industry split is a live, approximate counter during the turn and the authoritative count at the end. Codex's `thread/tokenUsage/updated` and the SDK's own "approximate progress for spinners" wording on `thinking_tokens` both point that way.

**Recommendation (A).**
1. The daemon emits one `step_live` activity patch: `startedAt` (step claim time), `phase` (from `system/status` + `session_state_changed` + last tool name), and `tokens`. During a turn, `tokens` is the sum of output tokens seen so far: `thinking_tokens.estimated_tokens` while thinking, plus `message_delta.usage.output_tokens` from partial stream events (already enabled with `includePartialMessages: true`). On `result`, `tokens` is replaced with `result.modelUsage` totals. The web computes elapsed from `startedAt` locally, with no per-second traffic. [inferred] Touches `apps/daemon/src/backend/claude-code.ts` and `apps/daemon/src/activity.ts`, the `stepActivitySchema` in `packages/shared/src/records/step.ts`, and `live-engine-run.ts` (fill `elapsedSeconds`).
2. Keep the existing queued-capsule plus "Send now" UI and its tool-boundary semantics. Label the default as "queued until this step ends" and "Send now" as "delivers after the current tool call", matching the Claude Code and Cursor wording [inferred]. Do not adopt Claude Code's "send now backgrounds running work" (`backgroundTasks()` control) in the first cut: it changes the agent's work and needs its own design [inferred].
3. Optional later, single path only: stop maintaining Cairn's own boundary gate and send queued input as `SDKUserMessage{priority:'next'}`, once a logged-in probe confirms what `priority` does [guess → verify first].

**Pattern that fits Cairn [inferred].** Desktop's Background tasks pane, the Devin CLI subagent panel and the Codex "Active / Done" list all agree on the row: description, status, elapsed time, a work counter (tool uses or tokens), a stop control, and click-through to the sub-agent's own stream. Devin and Codex go further: rows persist across reload, and Codex lists finished rows as "Done · N". Claude Code's CLI instead drops finished rows after 30 s. Cairn is a persisted task panel, not a terminal, so the Devin/Codex persistence model fits better. The engine already gives Cairn everything the row needs, keyed by `task_id`, plus `tool_use_id` to join back to the `Agent`/`Bash` call in the main transcript. Sub-agent frames carry `parent_tool_use_id`, so the inspector's collapsed tool stream is a filter on the same message stream.

**Recommendation (B).**
1. **Single source of truth in the daemon:** extend `BackgroundSubagents` into a task registry for `local_agent` and `local_bash` (skip `ambient`/`skip_transcript`). Fields: `taskId, toolUseId, taskType, description, subagentType, prompt, isBackgrounded, startedAt, status, usage{total_tokens,tool_uses,duration_ms}, lastToolName, summary, outputFile, endedAt`. Reconcile membership against `background_tasks_changed` (REPLACE) so a missed edge cannot leave a row spinning [measured advice in `sdk.d.ts` L3496]. The continuation logic keeps reading the same registry, so no second tracker is added. [inferred]
2. **Wire:** report the registry as a step-scoped record through the existing machine report path (the way `agent_todo` is reported) and persist it server-side, not only in the in-memory hub (see C). [inferred] Touches `apps/daemon/src/backend/claude-background-subagents.ts`, `claude-code.ts`, `apps/server/src/routes-machine.ts`, `apps/server/src/services/machines.ts` and `events.ts`, `packages/shared`.
3. **Stop:** add a daemon control that calls `query.stopTask(taskId)`, and declare `perTaskStopAffordance: true` at initialize. Then the existing whole-run Stop no longer silently kills background agents, and each row's stop button is the per-task path [measured semantics, `sdk.d.ts` L1715–1735, L4289]. Requires a design note because it changes Stop's behavior. [inferred]
4. **Inspector:** show the delegated `prompt` (from `task_started.prompt`, else the `Agent` tool_use input `prompt`), the model (`Agent` input `model`, else `AgentOutput.resolvedModel`/`modelsUsed` on completion [measured, `sdk-tools.d.ts` AgentOutput]), and the sub-agent stream: transcript rows whose `parent_tool_use_id === toolUseId`, collapsed. By default only tool_use/tool_result frames are forwarded. Turn on `forwardSubagentText` only if the inspector needs the sub-agent's prose. [measured]
5. **Todo linkage ("1 running task"):** the engine does not link a todo item to a task. Derive it: count the registry's running tasks while a todo item is `in_progress`, and attach the count to that item. [inferred; there is no engine field for this]
6. **Optional:** `agentProgressSummaries: true` gives a one-line `task_progress.summary` for each row, at the cost of an extra forked model call about every 30 s [measured]. Leave it off until the row is shipped.

The opencode v2 approach therefore fits: derive the pinned list from the latest todo tool call in the persisted transcript, and treat the live `agent_todo` event only as the fast path.
