# Long-term memory and context compaction for personal agents: how others do it, and what the Coordinator should adopt (2026-11-07)

Labels: **measured** = official documentation text or pinned-commit source code read this round; **inferred** = follows from measured facts and can be re-checked; **guessed** = everything else, including things read only as search snippets, third-party retellings, or mechanisms not seen first-hand.

## 0. Conclusions (5 lines)

1. **cairn already has half of it**: the Coordinator already has a Letta-style "always-injected core memory" (`save_memory` / `update_memory`, the whole block goes into the system prompt every turn, quota 100 entries) and "searchable raw history" (`search_history` / `read_history`), plus pi-durable's threshold compaction. What is missing is not new storage but three things: no loss of facts before compaction, events kept out of memory, and a token cap on memory injection. (Measured: `services/memory.ts`, `services/chief-tools.ts`, `coordinator/runtime/compaction.ts`)
2. **No one treats the event stream as memory.** Letta wraps events as `system_alert` user messages that get summarized along with the conversation; Codex's memory extraction first filters the rollout down to "memory-relevant" entries; Grok Bot records "a dated log of what it did", not the raw events. (Measured: Letta `system.py`; Codex `memories/README.md`; Grok Bot docs)
3. **Flushing durable facts before compaction** is the only mechanism worth adding: Letta sends the model a warning at 75% of the context so it saves memory first; the Anthropic memory tool protocol says the context may be reset at any moment and unrecorded progress will be lost. cairn already has the `beforeCompact` hook, which is exactly where this attaches. (Measured: Letta `settings.py`, `agent.py`; Anthropic memory tool docs)
4. **Background "consolidation" should be low-frequency, read only the main conversation, and expire by usage**: Codex has two phases (per-session extraction, then global consolidation, ordered by `usage_count` and expired by `max_unused_days`), Letta sleeptime runs once every N turns. cairn's daily `chief-digest` review can be reused for this role; do not build a second rolling summary. (Measured: Codex, Letta source)
5. **Not worth copying**: mem0 extraction every turn, Graphiti's full graph, Rewind-style full recording, Amp-style thread switching, Muse's person profile pages. Reasons in section 3. **Blocked items**: ChatGPT memory (Cloudflare 403, body not read), and the internal mechanisms of Instinct / Dot / Rewind-Limitless / Muse (no first-party architecture description).

## 3. The six questions per product: only filling in what the table left unclear

**Per-turn cost** (the column the table lacks most, collected here):

- Letta: core blocks go into the system prompt whole and are paid for in full every turn; the cap is by character count (`CORE_MEMORY_HUMAN_CHAR_LIMIT = 20000` and others). One compaction = one summary call, by default using a small model (Haiku-class for Anthropic), the summary cut to 50,000 characters. (Measured: `constants.py`, `summarizer_config.py`)
- Codex: the injected `memory_summary` is cut to 2,500 tokens, the rest is read by tools on demand; the background pipeline pays for one extraction plus one consolidation separately. (Measured)
- Claude Code: `MEMORY.md` first 200 lines or 25KB, topic files read on demand, and after a write that exceeds the limit it is prompted to rewrite. (Measured)
- mem0: each `add` costs one retrieval plus one LLM extraction plus one batch embedding; `search` needs only an embedding, no LLM (inferred: only the signatures and the add path were read).
- Graphiti: several LLM calls per episode (extract entities, extract edges, de-duplicate; the count was not tallied, guessed), no LLM call at query time (measured).
- Pi, Grok Bot, Muse, ChatGPT: not published.

**Letta's concrete compaction behavior** (for reference for cairn's summary prompt): the default mode is `sliding_window`; starting at 30%, it evicts another 10% of messages each time until what remains plus the system prompt is below 70% of the window (inferred: from `goal_tokens = (1 - p) x context_window` and the loop; the field description, function comment and code in the source disagree on "keep or evict 30%", the code takes precedence); the cut point must land on an assistant message; a pending approval request cannot be evicted. The summary prompt requires URLs, issue numbers and file names to be kept verbatim, and to write "**Lookup hints**: when details do not fit, record the topic and keywords so they can be found later in the message history". (Measured)

## 4. Which patterns suit a never-ending Coordinator thread, and which do not

### Suitable

| Pattern | Source | Why it suits | cairn today |
|---|---|---|---|
| Small, always-injected core memory with a hard cap | Letta core blocks, Claude Code `MEMORY.md`, Codex 2,500-token summary | The thread never ends, and the only thing not eaten by compaction is this; the cap makes per-turn cost predictable. ### Not suitable

| Pattern | Source | Why it does not suit |
|---|---|---|
| Calling an LLM to extract memory every turn (or every message) | mem0 | The Coordinator may receive hundreds of events per day; "retrieve 10 old memories plus one extraction" for each is pure cost, and what gets extracted is event noise. (Inferred) |
| A full temporal knowledge graph | Graphiti | Needs a graph database and many LLM calls; a team-level memory of 100 entries has no use for it. The only thing worth borrowing is temporal validity, which cairn already has. (Inferred) |
| Record everything, then search | Rewind / Limitless | The opposite direction: the Coordinator's full truth is already in `chief_message`, what is missing is curation. |
| Switching threads / manual handoff | Amp | This thread is designed never to be replaced (the baseline already argued this). The Grok Bot docs also advise "start a new thread or new Bot when the work changes", rejected for the same reason. |
| A background process that builds a profile page for every relevant person | Muse (WIRED retelling, secondhand) | Introduces a third-party privacy surface and does not fit the Coordinator's "team and tasks" scope. (Guessed) |
| Memory manageable only by chat, no UI | Grok Bot | cairn already has a UI, do not regress. |
| Unlimited injection plus relying on the model to tidy up | cairn today | See above, a cap must be added. |

## 5. Recommendation: the plan merged with the runtime baseline
