# Chief outbox persistence: prior art

Read on 2026-11-15 through agent-reach (GitHub CLI and raw source). Verified means read first-hand at the commit named; inferred means derived from what was read; guess means the rest. Extends `docs/research/message-first-sending-2026-11-11.md`, which covered the server-side retransmission rule.

The question: a message the user sent shows a `sending` bubble and the composer clears, but the server has not accepted it yet. The renderer crashes, or the tab closes or reloads. What keeps that message, and how is it sent again without a duplicate?

| Source | How it does it | Trade-off | Link |
|---|---|---|---|
| t3code mobile thread outbox (`1b14aade4de1`) | Verified. One JSON file per queued message, keyed by `messageId`, written atomically (`thread-outbox-storage.ts`). `enqueue` publishes the row to memory and writes the file in a serialized mutation queue. Delivery calls `confirmQueued` first, which waits for that write, so a lost write cannot follow a successful send (`thread-outbox-manager.ts`). On start `load()` reads every file and adds the rows that are not already in memory. Delivery removes the file only after the server acknowledged (`completeQueuedMessageDelivery`). ## Pattern that fits

Inferred from t3code and Matrix: persist the queued row, with its original client id, before the request leaves; delete it only on acknowledgement; on start read the rows back and send each again under the same id. The server ledger turns a resend of an accepted message into a retransmission.

t3code waits for the write before it sends, which closes the window where a crash after `fetch` started but before the row reached disk loses the message while the server never saw it. Matrix and Zulip write synchronously to `localStorage`, so they get the same ordering for free.

Cairn's chief routes claim the client id in the same SQLite transaction as the insert (`submitChiefMessage`), so two tabs that both resume one row both get the one stored message. That is why this needs no Web Locks drainer: the fencing in `docs/design/message-first-sending.md` protects routes that do not claim first, and the chief composer posts only to routes that do.

## Recommendation

Persist the chief outbox rows in IndexedDB (one row per client id, like t3code's one file per message), through a thin wrapper over the IndexedDB API rather than `idb-keyval`: the store needs four operations, one of them a conditional write inside a single transaction, and an open that is blocked must reject rather than wait. Wait for the write before each POST, delete on ack, resume `sending` rows automatically under their key. Keep today's failure path: a failed send returns its text to the composer, and the returned key is persisted too, so sending the same text again after a crash still reuses it. Touches `apps/web/src/chief/outbox.ts` and `apps/web/src/chief/use-chief-surface.ts`. Design: `docs/design/chief-outbox-persistence.md`.
