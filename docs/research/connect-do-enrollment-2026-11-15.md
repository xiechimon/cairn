# Personal SQLite Durable Object relay: enrollment and account trust

Research date: 2026-11-15. Research only; not a production design or deployment authorization.

### WebSocket ratio and rounding

**Observed:** An initial Worker WebSocket upgrade counts as a Worker request; subsequent frames routed through the Worker do not count as Worker requests. A DO connection needs a request to establish it. DO incoming application messages use a **20:1** message-to-compute-request billing ratio: **100 incoming messages = 5 metered requests**. Outgoing WS messages and incoming WS protocol pings have no request charge. Analytics shows actual messages, not the discounted request count. [Workers][wp] [DO][dp]

**Observed:** DO compute billing subtracts the included monthly allocation and then rounds billable usage **up to the next billable unit**. The official examples round 500,000 excess requests to 1,000,000 requests ($0.15), and 152,960 excess GB-s to 1,000,000 GB-s ($12.50). Do not present a Paid estimate as a perfectly linear fraction of those units. **Unverified:** The primary page does not specify a per-connection/per-day rounding algorithm for fractional 20:1 message requests; do not invent `ceil(messages/20)` per socket as vendor behavior. [Source][dp]

**Inferred:** Count both directions as **incoming** to the DO when a host and browser each send a frame into the relay. A forwarded outbound frame is not another incoming message, but a peer's reply is. Automatic application ping/pong avoids extra wall time with `setWebSocketAutoResponse()`, not a documented blanket exemption of all incoming application traffic from the request meter. [Pricing][dp] [WebSockets][ws]

### Before authentication is not before metering

**Observed:** Worker pricing meters inbound Worker requests, with no authentication-success exemption; DO pricing meters requests sent to the object. The [prototype Worker](../../scripts/ops/connect-do-prototype/worker.ts) calls `admission()` before `RELAY.getByName('personal').fetch(request)` and repeats admission inside the DO. [Workers pricing][wp] [DO pricing][dp]

**Inferred:** Rejecting an unauthorized HTTP request before DO dispatch can avoid the DO request, constructor and storage work, but cannot undo its Worker ingress request or CPU. HTTP 401/403/429 generated by the Worker is still Worker execution. A valid session lookup inside a DO also consumes DO resources even if eventually denied. Public health, enrollment attempts, login failures, reconnect storms, invalid frames and application heartbeats must enter the budget. No application-only limiter is a proof against exhausting the account's ingress allowance. Pre-Worker edge enforcement could help, but its exact Free feature availability and metering need separate validation. [Workers][wp] [DO][dp] [OWASP][ows]

**Observed:** Free DO overages fail further operations of the exhausted type; daily limits reset **00:00 UTC**. Workers Free exhaustion returns **1027**; configurable routes can fail open or closed, and Cloudflare recommends fail closed for security-critical Workers. Paid excess usage is billed rather than using the Free daily ceiling as a spending cap. [DO][dp] [Workers limits][wl] [Workers pricing][wp]

**Inferred:** Use fail-closed relay admission and no origin bypass. Free exhaustion is an availability failure, not an automatic authorized upgrade to Paid. If the account later moves to Paid for another application, the relay's exposure changes too; a “Free forever” guarantee cannot be derived from its initial plan. [Workers][wp] [DO][dp]

### Shared headroom, not a fresh allowance per installation

**Inferred:** For every meter, available headroom is the published account/product allowance minus other workloads' consumption minus operational reserve. Multiple relay installations, namespaces or hostnames do not each receive a fresh account allowance. Report estimated demand and a private local readiness status, not personal usage or account identifiers in public docs/logs. Include Worker ingress/CPU, DO requests, duration, SQL rows/storage, class/script capacity and hosted Builds if selected. A noisy experiment can interrupt unrelated account applications. [Limits][wl] [DO][dl] [Billing scope][billing]

**Inferred — generic illustrations, not acceptance measurements:**

- At the pricing page's **0.128 GB** allocation convention, one continuously non-hibernating DO uses `86,400 × 0.128 = 11,059.2 GB-s/day`, about **85.1%** of 13,000 GB-s. Two such independent objects exceed Free duration before allowing for any other workloads. [Source/convention][dp]
- A hypothetical **17 sockets × 120 incoming messages/minute × 1,440 minutes/day ÷ 20 = 146,880 metered DO requests/day**, excluding connection requests. This already exceeds the 100,000 request allowance. The local prototype's finite output caps and host bottleneck can stop it earlier; this is an upper-envelope illustration, not observed sustained throughput. [Pricing][dp] [Prototype](../design/connect-do-prototype.md)
- Even one SQL counter-row update per incoming message can exhaust **100,000 rows written/day** far before the corresponding **2 million messages** would consume 100,000 compute requests at 20:1. Index updates, constructors, sessions and revocation writes add demand. A byte budget is not a SQL-operation budget. [Pricing][dp] [SQLite][sql]

## Official spending controls: new, account-wide and incomplete

**Observed:** Official Workers and DO spending limits were announced **2026-11-13**. There are **separate product-wide limits**, not a single application cap: Workers covers requests/CPU; DO covers requests, duration, SQLite rows read/written and legacy KV operations. Both deduct included usage first, apply to the **current subscription billing period**, and count usage already recorded before a policy was created. Neither targets an individual Worker, DO namespace or metric. [Announcement][newlimits] [Billing][billing]

**Observed:** Current billing instructions use **Billing > Spend Management**, require billing-edit permission and an amount **greater than zero**, with up to **two decimal places**. Email policies notify at **80% and 100%**; email alerts alone do not block. Dashboard-created spending limits do not automatically set a notification recipient. A limit's “On” or threshold event is not proof that enforcement has propagated. The announcement uses “Spend limits” and configurable alert examples instead: documentation/UI terminology is not completely aligned. [Billing][billing] [Announcement][newlimits]

| When the policy blocks | Documented effect / gap |
| --- | --- |
| Workers | **Observed:** New invocations, including incoming HTTP, cron, queue, email and calls from other Workers/DOs are rejected. HTTP receives **1103**; rejected invocations are not billed. Static assets that do not invoke Worker code remain available. [Source][wsp] |
| Durable Objects | **Observed:** New stub requests, SQL reads/writes, SQLite growth and `setAlarm()` are blocked. Pending alarms are held subject to the documented **seven-day** recovery limit. Error can be `Exceeded the account's spending cap for Durable Objects.` [Source][ds] |
| Already-open DO WebSockets | **Observed:** **Messages are not blocked by the limit.** Already-running requests can keep accruing duration. [Source][ds] |
| Data and other products | **Observed:** Stored data and the shared Workers Paid subscription fee are excluded; existing stored data remains billable. | Timing/recovery | **Observed:** Reporting/enforcement delays and failures can exceed the configured amount. **Inferred:** Configure both product controls only with the account owner's informed approval; never silently change a shared account's limit during enrollment. [Billing][billing] [DO][ds] [OWASP][ows]

**Unverified:** Availability of the policy editor on a particular Free account was not exercised. A positive-dollar post-included-usage policy is not a substitute for Free quota accounting. [Billing][billing] [DO][ds]

## Hibernation, storage and trust implications

**Observed:** `ctx.acceptWebSocket()` enables incoming WS hibernation; ordinary `ws.accept()` pins duration for the connection. Outbound connections, outstanding I/O/`waitUntil`, unfinished handlers and `setTimeout`/`setInterval` callbacks prevent hibernation. The lifecycle describes eviction after **10 seconds** of eligible inactivity; pricing says eligible idle time is already unbilled **before** actual eviction. Pending I/O can keep an object in memory for up to **15 minutes per operation**. [WebSockets][ws] [Lifecycle][life] [Pricing][dp]

**Inferred:** Do not add a ten-second billed tail after every message or multiply one object's duration by its socket count. Conversely, model-response waiting, upstream network calls, streams and ordinary WS APIs can keep active wall time accruing even when CPU use is tiny. Both machine and clients should connect inward; this does not require a Worker-initiated socket to the private host. [Pricing][dp] [Lifecycle][life]

**Observed:** Hibernation re-runs the constructor and discards ordinary in-memory state; socket attachments can restore connection metadata. Full object shutdown/runtime movement or code updates can terminate WS connections. Index row changes count as additional SQL writes. SQLite `deleteAll()` removes SQL and KV data atomically; at compatibility dates **2026-02-24 or later** it also deletes active alarms. Empty SQLite databases consume approximately **12 KB**, and write metadata can remain until `deleteAll()`. [WebSockets][ws] [Lifecycle][life] [SQLite][sql] [Pricing][dp]

**Inferred:** Keep durable ownership/session revocation separate from volatile connection attachments; do not put reusable bearer secrets in attachments. Reconstruct authorization and budgets after hibernation without resetting them. Bound constructor/schema/session-lookup operations and handle quota/storage-full failures explicitly. Stopping sockets or deleting the Worker is not evidence that all stored data and charges have been removed. Cleanup must be an explicit owner-authorized procedure, not a public reset endpoint. [SQLite][sql] [Pricing][dp] [OWASP session][session]

**Observed:** Cloudflare terminates TLS at its inbound proxy; secrets are encrypted configuration bindings but are delivered in usable form to Worker code. [Security model][security] [Secrets][secrets] **Inferred:** WSS protects traffic on the network but does not hide relay plaintext from Cloudflare, deployed code, account administrators or anyone who can deploy replacement code. A personal Cloudflare account is infrastructure ownership, not end-to-end confidentiality. No model key belongs in the relay. Treat any future E2EE claim as a separate protocol/security task, not a property of DOs. [OWASP][ows]

**Inferred:** Minimize and clearly explain requested scopes; account/user reads plus script/DO deployment scope are a candidate starting point, **not a verified sufficient set**. [OAuth scope documentation][auth] [Installed source observation above](../../scripts/ops/connect-do-prototype/package-lock.json)

**Observed:** By default Wrangler stores OAuth access/refresh tokens in a **plaintext TOML file**. `--use-keyring` opts into an encrypted credential file with the key in the OS keychain. The documented persistent keyring preference can fall back to plaintext with a warning; explicitly setting `CLOUDFLARE_AUTH_USE_KEYRING=true` instead causes failure if the backend is unavailable. **Inferred:** A guided installer should check for unexpected credential overrides, present the selected account privately, use supported secure local storage and fail rather than silently accept weaker storage. Do not read credentials into a Cairn web page or send them to any provisioning service. Do not automatically log out an existing user's shared Wrangler session; credential removal/revocation requires explicit explanation and consent. OAuth authorization is installation authority, not a browser relay session. [Source][auth]

**Observed:** Worker secrets are hidden from dashboard/Wrangler reads after definition but available to Worker code. Do not put sensitive values in Wrangler `vars` or Git. Required-secret declarations can fail a deployment that lacks configured secrets, and `--secrets-file` supports uploading secrets with code; secrets omitted from that file are preserved from the prior version. [Source][secrets]

**Inferred:** Generate independent high-entropy host credentials, setup proof and session-signing/verifier material locally; do not reuse an owner's Cloudflare token, the prototype's shared client capability, or a model key. Use protected local handoff/temporary files or pipes supported by the reviewed installation path; never secret argv, URL query, Git, build logs, diagnostics, telemetry or screenshots. An initially deployed relay must remain inert until all owner-binding material is configured. Updating one secret at a time can deploy intermediate states, so every intermediate state must fail closed. [Secrets][secrets] [OWASP session][session]

## Secure browser-cookie WebSocket authentication

**Observed:** Browsers automatically include eligible cookies during WS handshake and cannot set an arbitrary Authorization header through the standard constructor. Cookie-based WS is vulnerable to cross-site WebSocket hijacking without explicit defenses. OWASP requires an exact Origin allowlist, valid sessions, per-message authorization, expiry handling and immediate closure on logout. [WHATWG][whatwg] [OWASP WS][ows]

**Inferred — recommended security contract, not an implemented API:**

1. Serve the relay browser entry and WS endpoint on one exact HTTPS/WSS origin where feasible. Authenticate enrollment over HTTPS, then issue an opaque relay-specific session cookie with **`Secure; HttpOnly; SameSite=Strict; Path=/`**, **no `Domain`**, preferably a **`__Host-`** name. SameSite=Lax is a compatibility alternative requiring an explicit reason; neither replaces CSRF protection. Use a CSPRNG and server-side expiration/revocation, not just cookie expiry. OWASP gives **128 bits minimum** for a custom session identifier and prefers stronger generated verifiers; a fresh **256-bit** value is a conservative project choice, not a vendor requirement. [Session][session] [CSRF][csrf]
2. Before `101`, require the exact approved Origin (scheme/host/port), the valid cookie, an allowed route/method and unexpired authorization. Reject absent or `null` Origin on the browser route. Do not use wildcards, substring checks, CORS success or `Sec-WebSocket-Protocol` as proof of origin/identity. Put independently authenticated native/host traffic on a separate route/policy: non-browser clients can forge Origin. [OWASP][ows] [WHATWG][whatwg]
3. Protect enrollment, pairing, renewal, revocation and owner changes with framework CSRF protection or a session-bound synchronizer token on same-origin state-changing HTTPS requests, plus Origin/Fetch Metadata checks as applicable. Never make public GET perform ownership changes. Reject unsupported cross-origin arrangements rather than switching casually to `SameSite=None`. [CSRF][csrf]
4. Do not put long-lived session/host/setup credentials or CSRF secrets into WS URLs or subprotocol strings. If additional upgrade CSRF proof is required, the standard browser API's header restriction must be respected. A **short-lived, single-use, session-bound upgrade permit cookie**, minted through a CSRF-protected same-origin POST and consumed atomically before upgrade, is a candidate mechanism. It needs a separate reviewed concurrency/replay contract; it is **not** directly prescribed by OWASP. If state lives in a DO, checking it can itself consume quota before application authentication completes. [WHATWG][whatwg] [OWASP WS][ows] [CSRF][csrf] [Pricing][dp]
5. Validate current session/role and recipient authority before every protected action or delivery, including after hibernation. Revocation must close all session sockets; protect idle recipients as well as senders from post-expiry delivery. Bound connections, incoming/outgoing sizes, rates, work and queueing independently. OWASP's **64 KB or less** and **100 messages/minute** are example starting points, not Cloudflare allowances or a project throughput guarantee. [OWASP][ows]
6. Prefer request/event-driven expiry checks and a carefully specified connection lifetime over DO `setInterval` revalidation, which defeats hibernation. Silent expired sockets must never receive protected data; immediate logout requires an explicit revocation event/path and connection index. OWASP's “every **30 minutes** is common” revalidation example does not authorize a 30-minute revocation gap. Log status/counters, not cookies, bearer material or message bodies. [OWASP][ows] [Lifecycle][life]

**Unverified:** Exact mobile browser cookie behavior, cross-origin embed needs, partitioning/SameSite behavior on the chosen hosting names, immediate idle-socket expiry implementation, upgrade-permit consumption races, session-store quota failures, and logout across hibernated sockets must be settled in the separate design and authorized acceptance. This report does not endorse a cross-site cookie deployment. [Browser standard][whatwg] [OWASP][ows]

## First owner: bind before exposing, never public claim-first

**Inferred — required trust property:** Nobody who merely learns the public relay URL may become owner, even when the relay has no owner yet. Deployment completion and Cairn ownership are different authorities. Provision an explicit, private proof tied to the authorized installation; an empty owner row must mean **locked/unconfigured**, never “first visitor wins.” [Deploy Button][button] [Cloudflare OAuth][auth] [OWASP session fixation controls][session]

**Inferred — candidate enrollment pattern:** A trusted local installer generates an installation identity/key or one-time high-entropy setup proof, deploys its public verifier or secret binding through authenticated Cloudflare management access, and retains the corresponding private proof locally. It then connects that proof to the **already authenticated local Cairn owner** through the separate Cairn design. Redemption must prove possession, bind the intended relay/deployment and owner/device, be short-lived, atomically single-use and close on successful binding. Host credentials alone must not implicitly create Cairn ownership. Keep recovery/rebinding behind the same deployment-owner authority, not a new public claim endpoint. [Auth][auth] [Secrets][secrets] [OWASP session][session] [OWASP CSRF][csrf]

**Inferred:** A button-only route cannot safely infer that its next anonymous visitor is the person who authorized Cloudflare/GitHub. It needs a private setup credential or an authenticated management-owner confirmation independent of public URL discovery. Do not redirect a secret in a query string, print it in build output, or make the setup URL itself a durable bearer credential. Prefer the local path because it can perform this handoff without a new hosted identity/provisioning broker. [Button][button] [Session][session] [CSRF][csrf]

**Unverified/blocking:** The exact existing Cairn owner/device/session bootstrap integration is intentionally left to the independent design author. No local unauthenticated-loopback exception, public owner claim, arbitrary HTTP forwarding, host-takes-owner shortcut or implementation API is approved by this research. [Existing experiment boundaries](../design/connect-do-prototype.md)
