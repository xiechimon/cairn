# Prior art: OS-level confinement of AI-agent task processes and credential brokering

Research date: 2026-11-22. Supports the cairn credentials / macOS task-confinement design. Scope: how existing products confine agent *processes* on macOS (Seatbelt) and Linux (bubblewrap), and how they isolate credentials (resolved-outside delivery, per-step tokens, egress proxies that inject secrets).

Evidence marking, per claim:

- **`实测`** — read the file / ran the command / fetched the doc myself this session.
- **`推断`** — derived from `实测` facts, reproducible.
- **`猜测`** — not verified; treat as a lead, not a fact.

Local probes ran on this Mac (`studioMac-0001`, macOS 27.2.1, `/usr/bin/sandbox-exec` present and working). Codex source was cloned read-only to `/tmp/codex-src` (codex-cli 0.166.0 installed locally; source at HEAD ~Nov 2026). Anthropic's `@anthropic-ai/sandbox-runtime` was cloned to `/tmp/srt-src`. Claude Code 2.1.330 and Amp binaries are installed locally.

## TL;DR

1. **Everyone serious on macOS converged on `sandbox-exec` + a `(deny default)` SBPL allowlist** — Codex (`codex-rs/sandboxing`, four composed `.sbpl` files), Anthropic's sandbox-runtime (one generated profile, `(deny default (with message ...))`), Gemini CLI (six bundled `.sb` profiles). Cairn's `seatbeltProfile()` is instead `(allow default)` + deny overlays — workable, but every new exfil channel (mach services, fcntl, unix sockets) must be enumerated by hand; the deny-default camp enumerates the grants instead. `实测`.
2. **Keychain is a Mach-service problem, not just a file problem.** Verified on this Mac: `(deny mach-lookup)` of `com.apple.SecurityServer` (+`com.apple.securityd.xpc`) blocks `security` and `SecItemCopyMatching`; **but the file deny on `~/Library/Keychains` alone also blocks both APIs** (errSecNoSuchKeychain). Conversely: a profile that *allows* `com.apple.SecurityServer` and leaves `~/Library/Keychains` readable returns the full `Claude Code-credentials` payload (773 bytes) with no prompt. Codex and Gemini both allow `SecurityServer` in their profiles (TLS validation uses it) — their sandboxed processes can read the login keychain. `实测`.
3. **Credential isolation has two convergent answers.** (a) *Keep secrets out of the sandboxed process entirely*: deliver over an fd/stdin gate (cairn Linux already does this — `confinementGate` frame over stdin, `--clearenv`), or a per-step scoped token file (`StepAppCredential`). (b) *Sentinel + egress proxy*: Anthropic srt and Codex both ship the same architecture — env inside the sandbox holds a placeholder (`fake_value_<uuid>` / Codex `dummy_value`), a host-side MITM/HTTP proxy substitutes the real value only for destinations on a per-credential allowlist (`injectHosts` / destination authorization). This is the broker pattern consensus. `实测`.
4. **sandbox-exec is deprecated-but-present** — the man page has said DEPRECATED since ~2017 (local footer: "Mac OS X March 9, 2017"); it still ships and works on macOS 27.2.1. Codex, srt, Gemini, Chromium all depend on it; Apple tracks the missing replacement at apple/containerization#737. `实测` / secondary.
5. **Env-passed secrets are not readable by same-uid siblings on macOS 27** (`ps eww`/`ps -E` returned nothing even unsandboxed — SIP-era procargs restrictions), and Seatbelt blocks `kern.procargs2` under deny-default since it's not in any sysctl allowlist. Passing resolved creds via env is therefore not a *local leak* class on macOS; the real risk is the task itself holding the value. `实测`.
6. **Process cleanup:** Linux `--die-with-parent` + systemd `KillMode=control-group` (cairn already) covers it. macOS Seatbelt has no die-with-parent; Codex solves it with `.process_group(0)` + `kill(-pgid, SIGKILL)`. srt kills only the direct child. `实测`.

## macOS details

### Codex's seatbelt composition (`实测`, `/tmp/codex-src/codex-rs/sandboxing/`)

`create_seatbelt_command_args_with_profile` (`seatbelt.rs:772`) emits, in order:

1. `seatbelt_base_policy.sbpl` — `(deny default)`; `process-exec/fork`, `signal`/`process-info*` same-sandbox, `/dev/null` write (CHAR-DEVICE-guarded), ~50-name `sysctl-read` allowlist (Chrome-derived), `RootDomainUserClient` iokit, `com.apple.system.opendirectoryd.libinfo` mach, `ipc-posix-sem`, `__KMP_REGISTERED_LIB_*` shm, PowerManagement, PTY (`pseudo-tty`, `/dev/ptmx`, `/dev/ttys*` + `com.apple.sandbox.pty` extension + a fallback ioctl for pre-existing ttys).
2. File-read policy — full-disk → `(allow file-read*)`; else per-readable-root `(allow file-read* (require-all (subpath <R>) (require-not (literal/subpath <excluded>)) ...))`; root `/` allowed minus `unreadable_roots` when full-disk + exclusions.
3. File-write policy — full-disk → `(allow file-write* (regex #"^/"))`; else per-writable-root require-all with `read_only_subpaths` + `protected_metadata_names` (`require-not` regex). Literal-vs-subpath chosen by `lstat` (file → literal, dir/missing → subpath).
4. Network policy — three shapes: managed proxy (loopback bind/inbound/outbound + `localhost:<port>` per proxy port + `com.apple.TrustEvaluationAgent` + unix-socket allowlist); enabled → `(allow network-outbound)(allow network-inbound)`; disabled → nothing (denied by default). `seatbelt_network_policy.sbpl` adds SecurityServer/networkd/ocspd/trustd(.agent)/configd/bsd.dirhelper/opendirectoryd.membership + AF_SYSTEM proto-2 socket + `net.routetable` sysctls.
5. `seatbelt_preferences_policy.sbpl` (cfprefsd + user-preference-read) — only when reads are unrestricted.
6. `seatbelt_read_only_platform_defaults.sbpl` — the "minimal" platform read set when the policy asks for it.
7. `(allow file-read* (subpath "/Applications"))` for process profiles.
8. Daemon-socket protection when write isn't full-disk (`seatbelt_daemon.rs`): deny read/write + unix-outbound on the app-server socket dir + `file-write-unlink` on every ancestor.
9. `(deny mach-lookup (xpc-service-name-prefix ""))` — blanket deny of per-app XPC services.
10. Unreadable-glob denies: `deny file-read* file-write* (regex ...)` per glob + `deny file-write-unlink` on glob ancestors (rename-bypass fix).
11. Protected-ancestor `file-write-unlink` denies (renaming a writable dir can't relocate read-only descendants out of their carve-outs).
12. `(deny system-fcntl (fcntl-command 80 110))` — F_MAKECOMPRESSED / F_TRANSFEREXTENTS write-via-fcntl hole.
13. TIOCSTI ioctl deny for the inherited-terminal profile.

Modes: `read-only` = root read + scratch writes (`/private/tmp`, `/private/var/tmp` via `seatbelt_scratch.rs`); `workspace-write` = root read + writes to project roots / `/tmp` / `$TMPDIR` / configured roots, with `.git`, `.agents`, `.codex`, `.aws` inside each writable root kept read-only; `danger-full-access` / `external` = unrestricted. Env goes to the child verbatim (`SandboxExecRequest.env` → `spawn_process` → `Command::env`) — secrets are a *policy* problem for codex, not a plumbing problem; the credential broker in `network-proxy` is their answer when the managed proxy is on.

### srt's profile (`实测`, `/tmp/srt-src/src/sandbox/macos-sandbox-utils.ts`)

`(deny default (with message "<tag>"))` — the log tag is what makes `log stream`-based violation attribution per-command. Mach allowlist (lines 1099–1114): `com.apple.audio.systemsoundserver`, `distributed_notifications@Uv3`, `FontObjectsServer`, `fonts`, `logd`, `lsd.mapdb`, `PowerManagement.control`, `system.logger`, `system.notification_center`, `opendirectoryd.libinfo`/`.membership`, `bsd.dirhelper`, **`com.apple.securityd.xpc`**, `com.apple.coreservices.launchservicesd`; plus `com.apple.SecurityServer` (line 1236) and opt-ins for `trustd.agent` (weaker network isolation), AppleEvents+lsopen, user-specified names. `(allow user-preference-read)` always. Network: nothing except localhost proxy ports + optional `allowLocalBinding` (`network-bind/inbound (local ip "*:*")` + `network-outbound (remote ip "localhost:*")` — the comment explains `*:*` is needed because IPv4-mapped `::ffff:127.0.0.1` doesn't match Seatbelt's `localhost`) + unix-socket allowlist. Writes: allow-only. Reads: allow-default with the deny-with-carve-out machinery; `credentialDenyOnly` entries are the one deny class never carved by allows.

Env handling on macOS: `env -u <name>` per denied credential + `NAME=<sentinel>` per masked one + proxy env vars, all on the `env` argv in front of `sandbox-exec` — sentinels (not secrets) appear in `ps`.

### Keychain under Seatbelt — probes on macOS 27.2.1 (`实测`)

Probe = `security find-generic-password -s "Claude Code-credentials"` (item confirmed present in `login.keychain-db`, `acct="unknown"`, `svce="Claude Code-credentials"`) and a Swift `SecItemCopyMatching` script:

| Profile | `security` CLI | SecItem |
|---|---|---|
| unsandboxed | exit 0; `-w` → 774 bytes | status 0, len 773 |
| `(deny default)` + minimal mach allowlist | exit 44 (not found) | — |
| + `(allow mach-lookup "com.apple.SecurityServer")` | exit 0; `-w` → 774 bytes | — |
| + `com.apple.securityd.xpc` only | exit 44 | — |
| `(allow default)` + `(deny mach-lookup SecurityServer securityd.xpc)` | exit 44 | status −50 |
| `(allow default)` + `(deny file-read* file-write* ~/Library/Keychains)` | `-w` → empty | errSecNoSuchKeychain (−25300) |

Readings: (a) `com.apple.SecurityServer` is the load-bearing name for the legacy `security` CLI path — codex and Gemini allow it for TLS reasons, which is exactly why their sandboxes can read the Keychain. (b) Denying `~/Library/Keychains` at the file layer independently blocks both APIs (the login-keychain enumeration needs the db file). (c) Belt-and-suspenders is cheap: file deny on `~/Library/Keychains` **and** `/Library/Keychains` (System keychain — cairn currently misses this) + `mach-lookup` denies on `SecurityServer`/`securityd.xpc`. (d) Caveat to test: `SecurityServer` denial may break TLS-validation paths in tools that consult it rather than trustd — codex's own comment says system libcurl needs `com.apple.TrustEvaluationAgent` (a *different* name it can keep).

Also measured: `ps eww`/`ps -E` on a same-uid child shows no env on this macOS (SIP procargs restrictions) — env-injected secrets aren't a same-user-snooping leak on macOS 27; `kern.procargs2` isn't in codex's or srt's sysctl allowlists either (denied under deny-default).

## The pattern that fits cairn

Cairn's constraint differs from the agent CLIs: the daemon launches *whole harness sessions* (claude, pi, ACP adapters), not one bash command at a time; the harness itself must reach the model API and the cairn server; and credentials are already resolved **outside** (server → `MachineTokenResponse` → `StepCredentials` → `step-env.ts` env). So the right composite is:

1. **Keep the `(allow default)` + deny-overlay profile shape** (already written and tested in `confine-seatbelt.ts`) but close the verified holes:
   - `MACH_SERVICE_DENIALS`: add `(deny mach-lookup (global-name "com.apple.SecurityServer") (global-name "com.apple.securityd.xpc"))` — measured to block `security` + SecItem even with the keychain db readable.
   - File denies: add `/Library/Keychains` (System keychain) alongside `~/Library/Keychains` — measured to block keychain reads independently of the mach denies.
   - Consider codex's `(deny system-fcntl (fcntl-command 80 110))` (write-via-fcntl) and `file-write-unlink` ancestor denies if any denied path ever sits inside a writable root (today's denied roots are all outside writable roots, so the rename class is mostly closed already — `推断`).
2. **Keep env delivery out of argv**: cairn Linux already does this right — `confinementGate` reads the env JSON frame over stdin post-`--clearenv` (`confine.ts`). On macOS, env isn't a sibling-leak (measured), but putting `CLAUDE_CODE_OAUTH_TOKEN` in `spawn` env is still a `kern.procargs`-class risk on older OSes and visible to anything the task can ptrace in the same session; the existing **fd-3 delivery** (`CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, used for orbs in `claude-code.ts` `spawnClaudeProcess`) is the pattern to extend to macOS tasks — prior art for "secret never in env" is exactly the GH-OIDC env-free claim (identity from the job itself), systemd `$CREDENTIALS_DIRECTORY`, and SPIFFE's attestation.
3. **Process-group cleanup on macOS**: seatbelt has no `--die-with-parent`; adopt codex's `process_group(0)` + `kill(-pgid)` in the daemon's macOS spawn path (`spawnClaudeProcess` / the `confine` wrapper) so harness grandchildren can't orphan. Linux already covered via `KillMode=control-group` + `assertConfinementCleanup`.
4. **The broker, when cairn wants per-destination scoping**: the srt/Codex consensus is *sentinel in the sandbox, real value in a host-side proxy, substitution gated by destination*. Cairn already owns the egress path candidates (the machine-client channel, `proxy.ts`, the git credential file refresh in `StepAppCredential`). A pragmatic v1 that needs no MITM: per-step scoped tokens resolved outside (what `StepAppCredential` does for git) + env/fd delivery — the "broker holds long-lived, workload holds scoped" pattern from Vault Agent / GH OIDC. The sentinel+proxy v2 only pays for itself if tasks must present user-level secrets (npm, AWS, netrc) to first-party endpoints.
5. **Do not grant `SecurityServer` for TLS "just in case"** — trustd/`trustd.agent`/`ocspd`/`TrustEvaluationAgent` cover validation without opening Keychain (codex grants SecurityServer anyway; that's the leak to avoid, `实测` it suffices for `security -w`).
6. **Antigravity's `Library/Keychains` readable carve-out** (`confine-session.ts:201`) re-opens full login-keychain reads — verified path: file readable + SecurityServer allowed → full item retrieval. It exists because the Gemini-class CLIs keychain-store OAuth; the narrow fix is denying the securityd mach names *for that harness too* and checking whether its token reads still work through the file path alone, or brokering the item.
