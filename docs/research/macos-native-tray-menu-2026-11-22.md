# Cairn's native macOS tray menu

A new Cairn user clicks the menu-bar icon to open Cairn or use desktop controls. The approved migration changes who draws and tracks that menu, not account setup or permissions. This note covers the host API, not which rows to ship. **Evidence** means first-hand code or documentation reading, not a live UI test; **inference** means a recommendation derived from it.

## Prior art

| Source | Evidence | Trade-off for Cairn (inference) |
|---|---|---|
| Electron `45.2.1` — [Cairn pin](../../apps/desktop/package.json), [Tray docs](https://github.com/electron/electron/blob/v45.2.1/docs/api/tray.md#L312-L330), [macOS implementation](https://github.com/electron/electron/blob/v45.2.1/shell/browser/ui/tray_icon_cocoa.mm#L397-L427) | `setContextMenu(menu)` creates a native controller and assigns its `NSMenu` to the `NSStatusItem`; `null` detaches it. `popUpContextMenu()` posts a UI task to click the attached status item if its menu isn't open. An explicit `menu` temporarily replaces the native menu, simulates a status-button click and then restores the attached one. Tracking can run a nested event loop. The position argument is Windows-only. | Attach the default menu; reserve programmatic popup for a genuinely separate trigger. A temporary override adds lifetime and re-entry concerns without making the menu more native. |
| Apple AppKit — [`NSStatusItem.menu`](https://developer.apple.com/documentation/appkit/nsstatusitem/menu), [`NSMenu.popUpContextMenu`](<https://developer.apple.com/documentation/appkit/nsmenu/popupcontextmenu(_:with:for:)>), [`menuNeedsUpdate`](<https://developer.apple.com/documentation/appkit/nsmenudelegate/menuneedsupdate(_:)>), [`menuWillOpen`](<https://developer.apple.com/documentation/appkit/nsmenudelegate/menuwillopen(_:)>), [`autoenablesItems`](https://developer.apple.com/documentation/appkit/nsmenu/autoenablesitems) | An attached menu replaces the status item's single-click action. AppKit's separate context-popup API takes an event and view; that's not how Electron's tray popup is implemented. AppKit permits item updates in `menuNeedsUpdate` at the start of tracking, before validation; `menuWillOpen` is not a menu-editing hook. AppKit auto-enables items by default. | Let AppKit own normal activation and keep slow application work off the menu-opening path. |
| Open-source `tray-icon` — [pinned macOS backend](https://github.com/tauri-apps/tray-icon/blob/bd709f8981e845e963eb16dec019d98d02b70664/src/platform_impl/macos/mod.rs#L528-L542) | For configurable left/right activation, it temporarily assigns an `NSMenu`, calls `performClick`, then clears it. It retains the menu across the nested event loop because tracking can re-enter `set_menu`. | Explicit activation is viable when needed, but not a reason to add a second opener to an attached menu. |

## Cairn recommendation

- **One opener for normal activation.** Attach a nonempty `Menu.buildFromTemplate(...)` with `setContextMenu`. Remove macOS's rendered-window toggle and don't call `popUpContextMenu` from its `click` or `double-click` event. **Evidence:** on the attached-menu path, [Electron's view sends click notifications before calling AppKit to open the menu](https://github.com/electron/electron/blob/v45.2.1/shell/browser/ui/tray_icon_cocoa.mm#L174-L284); Apple's action guarantee does not suppress those Electron events. `setIgnoreDoubleClickEvents(true)` treats each click count as a single click, not as a duplicate filter. **Inference:** a JS opener on that same event can compete with normal native opening.
- **Update item values before tracking.** **Evidence:** the [macOS controller](https://github.com/electron/electron/blob/v45.2.1/shell/browser/ui/cocoa/electron_menu_controller.mm#L510-L597) disables automatic enablement and copies `enabled`, `visible`, `checked`, and `label` from the model in `menuNeedsUpdate`; [it refreshes again on close and emits the show notification from `menuWillOpen`](https://github.com/electron/electron/blob/v45.2.1/shell/browser/ui/cocoa/electron_menu_controller.mm#L639-L696). The [public `Menu` docs](https://github.com/electron/electron/blob/v45.2.1/docs/api/menu.md#event-menu-will-show) describe `menu-will-show` for `menu.popup()`, not as a tray refresh hook. **Inference:** keep the existing native items in sync from host state before opening, including async Runner outcomes. Don't rely on mutations while the menu is tracking; if rows must be added, removed, or reordered, attach a fresh menu while closed. The [Linux reattachment rule](https://github.com/electron/electron/blob/v45.2.1/docs/api/tray.md#L350-L378) is not a macOS requirement for these item properties.
- **Keep application state authoritative.** **Evidence:** Electron [flips checkbox state before invoking the item callback](https://github.com/electron/electron/blob/v45.2.1/shell/browser/api/electron_api_menu_item.cc#L509-L570); Cairn's [previous fallback template](https://github.com/xiechimon/cairn/blob/c5df42332e20b4be67487c49012f63c04c4a39e7/apps/desktop/src/tray-menu.ts) closes over the old Keep Awake value. **Inference:** use the menu selection as a request, then reconcile it with actual host state. Keep manual screen-awake state separate from the [scheduled wake-ahead icon state](../../apps/desktop/src/keep-awake.ts). Reuse the native template for the supported desktop targets rather than keeping a rendered fallback.

**Verification gap, not an API blocker.** No live macOS menu was opened in this research. The [previous desktop smoke](https://github.com/xiechimon/cairn/blob/c5df42332e20b4be67487c49012f63c04c4a39e7/apps/desktop/scripts/smoke-mac.mjs#L128-L175) emits a test event and checks a renderer DOM; it cannot prove native behavior. Before release, exercise a real menu-bar click, secondary/control-click (the old Mac popover handles right-click), quick double-click, keyboard/VoiceOver activation, Escape, and reopen after successful and failed state changes. Assert one menu session per activation and one side effect per selection. Verify secondary-click delivery before deciding whether an explicit right-click-only fallback is needed; never add a second opener to primary click.
