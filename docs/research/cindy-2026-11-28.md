## 0. Executive summary

1. **What it is (`实测`)**: an open-source consumer AI agent that runs on the user's own computers and phone,
   with a desktop app, a mobile app, and a hosted account layer. Its pitch is "all your devices, one Cindy;
   your computer becomes your server, no server rental" ([README.md:26–37](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L26)).
2. **What is open and what is not (`实测`)**: this repository holds the desktop and mobile clients and shared
   packages; the backend is a separate, non-public repository
   ([README.md:162](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L162)). The hosted model
   service, account system, relay and marketplace live on that side.
3. **How work runs (`实测`)**: `packages/maker-core` drives every session through one of four harnesses —
   Claude Agent SDK, Codex app-server, Pi, and ACP plugin engines — behind one `BaseAgent`/`Session`
   event stream ([repo-map.md:69](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/dev-rules/repo-map.md#L69),
   `packages/maker-core/src/agents/base-agent.ts:3075`, `session.ts:558`).
4. **Where it is strong vs Cairn (`实测`/`推断`)**: breadth of surfaces (Android, browser-into-headless host,
   five hook channels plus WeChat), breadth of model access (managed service, BYO subscription, API keys, local models,
   account pools), and a plugin/skill ecosystem. Cairn is stronger on landing trust (evidence-bound merge
   gate, protected eval ruler), on self-hosting privacy, and on having already split control from execution.
5. **Where it is weak (`实测`)**: 4,153 open issues+PRs after 19 weeks, a backend it does not open, telemetry
   on by default, third-party agent binaries fetched at install, and a large migration *away* from an
   Electron-main-holds-everything architecture
   ([docs/host/README.md:13–21](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/host/README.md#L13)).
6. **Recommendation (`推断`)**: do not fork or copy the product shape. Take three mechanisms with different
   costs — account-pool selection rules (prior art for Cairn's already-decided #2331/D50), a memory
   review/consolidation pass, and connector capability consent — and leave the rest. Details in §6.

## 1. What it is, who it is for, and how a newcomer starts

- **Thesis (`实测`)**: "Cindy is an open-source AI agent, ready out of the box and yours to shape. Connect
  your computers and phone, bring the models and subscriptions you already use, and build a companion that
  knows how you like to work." ([README.md:22–24](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L22)).
- **Audience (`实测`)**: mass-market users, not developers: "Cindy is an open-source AI assistant for the
  general public" and the product principles say every simplification the user sees is complexity the product
  principles say every simplification the user sees is complexity the product absorbs
  ([AGENTS.md:21](https://github.com/makecindy/cindy/blob/d2f9f71c/AGENTS.md#L21) and its product-rules pointer).
  The README nevertheless spends most of its developer section on a contributor setup, because the repo *is*
  the client.
- **Shape (`实测`)**: a "companion" (Cindy's word for a persona with instructions, memory, skills and recurring
  work) that belongs to the account, not to a machine; one computer is its **home computer**, and other
  computers and the phone are entry points
  ([cloud-companions.md:17–26](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/cloud-companions.md#L17)).
  The cloud stores the conversation layer only; tool calls, thinking and full run records stay on the home
  computer (`cloud-companions.md:26`).
- **Newcomer path (`实测`)**: download for macOS / Windows / Linux / iOS / Android from `cindy.app/download`
  ([README.md:103](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L103)); sign in or choose
  **Skip Sign-In**; connect a model in a first-run guide; create a companion (which immediately starts its
  first "hello" turn and needs an available model); open a project and ask for work
  ([first-run-guide.md:17–40](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/first-run-guide.md#L17),
  [README.md:110–127](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L110)).
- **Accounts and keys (`实测`)**:
  - A Cindy account is **optional**: Skip Sign-In runs local agents offline, shown as "Not signed in"; account-backed
    services are unavailable in that state ([README.md:168](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L168)).
  - Model access has four doors: Cindy's managed service (free credit for new accounts, paid expands the model
    range), a subscription the user already pays for (Claude Code, Codex plans), any provider API key, or a
    local model ([README.md:98–101](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L98),
    `first-run-guide.md:30–40`).
  - It deliberately does **not** read API keys out of other tools' config files (`first-run-guide.md:68`).
  - Two regions are separate products with separate accounts and endpoints: `global` and `cn`
    ([region-and-editions.md:17](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/region-and-editions.md#L17),
    [config/endpoint.json](https://github.com/makecindy/cindy/blob/d2f9f71c/config/endpoint.json) — auth, chat,
    device-link, agent-net, model-access and hooks each on their own host).
- **Payments (conclusion `实测`, figures `猜测`)**: the client is free and provider limits still apply; the paid offering is
  Cindy's managed model service and the hosted account services
  ([README.md:98–105](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L98) links `cindy.app/pricing`).
  I did not fetch the pricing page, so this note states no price.

## 2. Architecture

### 2.1 Agent loop and harnesses

- One orchestration core, four engines (`实测`): `maker-core` owns session orchestration and the event stream
  and has no Electron dependency (`repo-map.md:69`); engine adapters live in
  `packages/maker-core/src/agents/{claude-code,codex,pi,acp}`. ACP engines are third-party plugins that
  Cindy drives but does not inject its system prompt into
  ([maker-core-and-agent-behavior.md:9–17](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/dev-rules/maker-core-and-agent-behavior.md#L9)).
- Tool loop safety is a shared mechanism, not a prompt: `ToolLoopGuard` detects repeated identical tool calls
  and long read-only churn (`agents/shared/loop-guard.ts:279`), and the doc explains why a naive "three
  contract errors then stop" rule was switched **off** for all three engines rather than tuned
  (`maker-core-and-agent-behavior.md:92–130`).
- Failure and recovery are written as contracts (`实测`): startup-cleanup proof, event-stream pause
  (`holdEventStream`), context-overflow handoff and replay budgets, with an explicit rule that a generic
  exception is *not* proof a process exited (`maker-core-and-agent-behavior.md:19–92`, `:171–210`).
  This is the most valuable *documentation* practice in the repo: every failure path names what counts as
  proof and what the user sees.
- Multi-agent inside one product (`实测`): Orca gives one Lead session and N Worker sessions, each a full session
  with its own model, tools and visible history — not one-shot subagents
  ([orca-team-architecture.md:45](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/dev-rules/orca-team-architecture.md#L45)).

### 2.2 Models and providers

- The client carries a provider catalogue, per-model metadata, pricing display and routing
  (`packages/model-providers/src/{modelRegistry,catalog,byok,localModelCatalog}.ts`); the authoritative
  catalogue is delivered by the server and the gateway lives in another internal repository
  (`docs/dev-rules/model-catalog-maintenance.md:1–8`).
- A session's runtime selection is modelled as four layers — `baseline` (what the user saved), `effective`
  (what is running), `pending` (accepted, applies at the next turn), `generation` (a monotonic version so a
  stale cross-task write cannot overwrite a newer choice) — and the Agent itself can retarget a session or
  lower/raise effort through two tools (`get_session_runtime` / `set_session_runtime`)
  ([session-runtime-control.md:1–30](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/session-runtime-control.md#L1)).
  Automatic degradation is off by default, bounded to two hops, and refuses `A → B → A`
  (`session-runtime-control.md:42–60`).
- Account-level quota is handled rather than surfaced as an error: at a 5-hour/weekly limit the turn pauses,
  shows "will continue at X · cancel", and resumes on its own; a turn with output sends a continue instruction,
  a zero-output turn re-sends the original text
  ([usage-limit-auto-continue.md:14–20](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/usage-limit-auto-continue.md#L14)).
  Since 0.1.148 a subscription and an API key can share one OpenAI pool, with order, weight and concurrency,
  and "the same session continues on a backup account" when one runs out or fails auth
  (release [v0.1.148](https://github.com/makecindy/cindy/releases/tag/v0.1.148), `实测` release-note text).

### 2.3 Tools, skills, plugins

- Built-in tools are MCP servers (`packages/lizi-mcps`: Google, GitHub/GitLab, browser, scheduler; plus
  `cindy-tools` for the "Ghost" control plane and a `cindy_helper` that can list machines, query capabilities,
  and request remote-control consent) (`repo-map.md:69–90`,
  [agent-capabilities.md:1–30](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/dev-rules/agent-capabilities.md#L1)).
- Skills are `SKILL.md` packages, discovered from the user's own Claude/Codex/Pi directories, installable from
  a SkillHub marketplace, and four authoring Skills ship inside the app
  (`apps/desktop/resources/system-skills/{cindy-skill-creator,cindy-plugin-creator,cindy-theme-creator,learn}`).
- Plugins (`实测`) are `.cindy` packages with a v3 manifest declaring capabilities, run in a sandboxed process
  with an explicit permission boundary, and carry a red line: an upgrade must leave every installed,
  approved, enabled plugin working without re-asking
  ([plugin-security-and-authoring.md:385, 410, 1074](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/dev-rules/plugin-security-and-authoring.md#L385)).

### 2.4 Where it runs

- Today the **desktop Electron main process is the brain**: business logic, local DB, device-link, MCP
  integrations and "cindy-brain" all live in `apps/desktop/src/main` (`repo-map.md:57`).
- A **Node Host** (`apps/host`) is being built to run the same business body headless on a server, with the
  existing renderer reused in a browser through a host-channel shim
  ([docs/host/README.md:13–21](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/host/README.md#L13),
  `apps/web/shim.js:1–10`). Phase 1 is verified on a self-use macOS instance; headless Linux and cloud pilots
  are still open (`docs/host/README.md:20–26`). This is a migration *in progress*, not a finished split.
- **Mobile** is a control surface, not an executor: Expo/React Native, same account, remote control of desktop
  devices, mirrored sessions (`repo-map.md:58`); a browser page can also be served by Host over the LAN.
- **Remote SSH workspaces and remote desktop** extend the same idea: agents on an SSH host, and a phone
  remote desktop for when chat is not enough (`repo-map.md:72–74`, `README.md:31–36`).

### 2.5 Memory

- File-based, per workdir, **shared across all engines**, reached only through a `cindy_memory` MCP server so
  each engine's native auto-memory does not fork the truth
  ([memory/system-prompt.md:3–5](https://github.com/makecindy/cindy/blob/d2f9f71c/packages/maker-core/src/memory/system-prompt.md#L3)).
- Four entry types (user / feedback / project / reference) with a required `**Why:**` and
  `**How to apply:**` on feedback; a live `MEMORY.md` index is inlined at the top of the turn; search is FTS5;
  a `memory_review` pass runs an LLM review that returns suggestions the agent then executes; `memory_consolidate`
  merges shards atomically; writes warn on shard/index size and hard-fail past the hard cap
  (`system-prompt.md:7–49`, `packages/maker-core/src/memory/{fts,manager,storage}.ts`).
- Companions that migrate between computers carry their memory as shards to the cloud, while the workspace
  files stay on the home computer (`cloud-companions.md:56`, `:2.1`).

### 2.6 Scheduling and automations

- `packages/maker-scheduler` is a pure cron engine with storage/runner/notifier interfaces (`repo-map.md:75`,
  `packages/maker-scheduler/src/routines.ts`). Since 2026-11-08 a companion's scheduled work is an ordinary
  project automation in `.cindy/automations/schedules.json`, on the same scheduler as project automations
  ([bot-routines.md:1–8](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/bot-routines.md#L1)).
- Trigger kinds (`实测`): time, host events, plugin-declared events, and local webhooks — deliberately **no
  public webhook address** (`docs/product-rules/schedule-webhook-trigger.md:1–20`;
  `packages/maker-scheduler/src/{webhook-queue,plugin-events,pr-trigger}.ts`).
- Each rule chooses `persistent` (reuse one session so context accumulates) or `fresh` (a new session per
  trigger, closed after the run); a busy target defers the batch and retries after 30 s; paused rules clear
  their cursor and do not back-fill (`bot-routines.md:50`).

### 2.7 Multi-machine

- Devices of one account connect through a `device-link` protocol with an IPC allowlist, and the account's
  computers are "the agent's body": a top-level `list_machines` tool reads each online computer's live
  CPU/memory/disk and reports why one is unreadable (`offline`, `remote_control_off`, `update_required`,
  `unreachable`) instead of dropping it from the list
  ([cindy-machines.md:34–50](https://github.com/makecindy/cindy/blob/d2f9f71c/docs/product-rules/cindy-machines.md#L34),
  `packages/device-link/src/machineStatus.ts`).
- Two deliberate rules: expose the situation to the model and let it decide how many workers to open, and do
  not encode "max N" limits in the host (`cindy-machines.md:12–30`).
- Model connections can be **shared** to other devices and to other accounts with a member budget
  (`docs/product-rules/provider-sharing.md`); a self-hosted relay is planned for the connectivity layer
  (`docs/self-hosted-relay-plan.md`).

### 2.8 UI surfaces

`实测` from the tree: Electron desktop; Expo mobile (iOS and Android); the desktop renderer served to a
browser by Node Host; five hook channels in the endpoint manifest (Telegram, Feishu, Discord, Slack, X), plus WeChat through `packages/wechat-ilink`; and a web "shared task" join page for guests
(`config/endpoint.json`, `shared-task-mode.md:13–30`).

### 2.9 Data, telemetry, region

- Telemetry is **on by default** in official builds: TapDB records launches, return visits, a device id,
  OS/app version, and later a regional account alias that links daily model choices and token totals; chats,
  prompts, files and working-directory data are excluded. Opt-out exists in Settings → About → Usage
  statistics; local mode reports nothing; a documented mobile SSO exception can start reporting without an
  explicit consent record ([README.md:254–299](https://github.com/makecindy/cindy/blob/d2f9f71c/README.md#L254)).
- Region is a build identity with its own endpoints and its own account realm, not a runtime toggle
  (`region-and-editions.md:17–40`, `config/endpoint.json`).

## 3. Real user pain in the tracker (titles `实测`, causes `推断`)

The repository uses issues as its work log — a bot files issues, labels carry pipeline state
(`status:ci-running`, `status:auto-fixing`, `touches:security`). Six titles that describe user-facing pain:

- [#1991](https://github.com/makecindy/cindy/issues/1991) (27 comments) — the Pi harness exposes project resources
  differently from Claude Code/Codex (project skills off, user-scope skill paths wrong). *Cause `推断`: four
  engines share one contract on paper, not in resource discovery.*
- [#12315](https://github.com/makecindy/cindy/issues/12315) — an ACP plugin engine's MCP schema (~60 KB) makes 26
  core tools disappear. *`推断`: tool-surface size is a per-engine limit nobody validates before a turn.*
- [#11640](https://github.com/makecindy/cindy/issues/11640) — switching a model over device-link is hard-rejected
  because a custom provider lacks a verified context window. *`推断`: remote model claims are validated
  fail-closed with no "accept anyway" path.*
- [#7489](https://github.com/makecindy/cindy/issues/7489) — cross-task messaging intermittently returns
  `TASK_ACTION_AUTHORIZATION_EXPIRED` with no place for the user to renew it. *`推断`: an internal grant
  outlives its UI.*
- [#11641](https://github.com/makecindy/cindy/issues/11641) — 0.1.141 crashes at launch on macOS 13 because a
  widget binary references a missing Swift runtime symbol. *`推断`: minimum-OS support is not gated by CI on
  the oldest supported OS.*
- [#500](https://github.com/makecindy/cindy/issues/500) — on Windows a background plugin's focus request steals
  focus over the foreground app.

Reading: the pain is **engine-surface divergence and recovery UX**, not missing features. Cairn's spec 18 §5
recorded the same class of debt for its own runtime surface; the parts it named since closed (machine capability
advertisement, strain-aware routing, a Coordinator `machines` tool), while what Cindy shows is a second, harder
version of it: one contract across four engines whose resource discovery and tool-surface limits differ.
That is the part worth studying rather than the feature list (`推断`).

### 4.1 What Cindy genuinely does better

1. **One companion across devices, including the phone.** The home computer runs the agent; the cloud carries
   the conversation layer and the companion's identity, memory, skills and automation definitions; a second
   computer can take over as home and keep the same chat
   (`cloud-companions.md:17–40`). Today Cairn reachable from the phone means the server must be reachable
   (`README.md` Tailscale section); a laptop-only install with a closed lid has no phone surface. *This is the
   clearest product gap, and also the most expensive to close (`推断`).*
2. **Model access breadth.** A managed service that works on first login, subscription detection, key+subscription
   pooling, provider groups with automatic switch, and plugin engines (`README.md:98–101`, `session-runtime-control.md:42–60`).
   Cairn deliberately resells nothing, so this is a strategy difference, not a bug — but the *pool mechanics*
   are prior art Cairn can use (§6.1).
3. **Extension ecosystem.** Skills discovered from the user's existing agent directories, a SkillHub, and
   sandboxed plugins with declared capabilities and a no-re-ask upgrade rule (`plugin-security-and-authoring.md:1074`).
4. **Onboarding as a guided inventory of what the person already has**: other computers, another AI tool's tasks,
   existing Claude/Codex skills and MCP servers, and the model they already pay for (`first-run-guide.md:17–40`).
5. **Root-cause documentation.** The failure-contract style (`maker-core-and-agent-behavior.md:19–210`,
   `orca-team-architecture.md:996–1084`) is better than Cairn's records at stating *what counts as proof*.

### 4.2 What Cairn genuinely does better

1. **Landing trust.** A verdict counts only for the patch it judged (digest + head), and the eval ruler cannot
   be edited by the agents it judges (`apps/server/src/services/merge-gate/readiness.ts`, `AGENTS.md:15`).
   No product merge gate for users exists in the client (`推断`: the repo's own review is a bot pipeline,
   `REVIEW.md`, and users merge their own work in GitHub).
2. **Self-hosted truth and privacy.** One server owns the data; no analytics; no resold compute
   (`docs/privacy.md:3–5`, `README.md` "Wait, what are you selling?"). Cindy's host layer is closed and its
   official builds report usage by default.
3. **A finished control/execution split.** Cairn already runs the brain on the server and the work in worktrees
   on Runners, with several clients. Cindy is mid-migration out of Electron main (`docs/host/README.md:13–21`),
   which is the harder direction to travel.
4. **A smaller, opinionated surface.** No team features, no multi-user shared tasks, no region matrix
   (`docs/spec/18-positioning-and-differentiation.md` §4). Cindy carries the complexity of all three
   (`shared-task-mode.md:13`, `region-and-editions.md:17`).
5. **Machine truth is already strain-aware.** Routing refuses a machine whose memory/CPU/disk is strained
   (`services/machine-routing.ts:352`, `packages/shared/src/records/machine-capabilities.ts:6–24`), and the
   Coordinator sees OS, distribution and capabilities (`services/coordinator-context.ts:344`).

  and attribution notices (Cindy's NOTICE names "Copyright 2026 XD Inc."), state that files were modified, and
  carry any NOTICE text into Cairn's `docs/third-party-notices.md`. Because Cindy has no per-file headers,
  provenance must be recorded by path and commit, not by header.
- **What the licence does not cover** (`实测`): model weights, datasets, prompts, trademarks and "other separately
  identified materials" (README:319–322); the Claude Code, Codex and Pi binaries, which are downloaded per
  platform and not committed (README:160); the closed backend repository (README:162); plugin and marketplace
  content, whose notices/SBOMs are generated separately (`docs/legal/notices/`).
- **Practical consequence (`推断`)**: copying a *mechanism* and writing it in Cairn's own idiom (as this note
  recommends) needs no licence work at all. Copying *source files* needs the NOTICE and modification record.
  Do not copy the Pi/Claude/Codex vendor integration code wholesale: the binaries and their terms are third-party.

## 6. What is worth borrowing

Each item names the Cairn area it would touch and the user it helps. Items are ordered by value per unit of
risk, not by Cindy's prominence.

### 6.1 Account-pool selection rules — prior art for an already-decided feature

- **Cindy's version (`实测`)**: subscription and API key merge into one pool with order, weight and concurrency;
  when an account runs out or fails auth the same session continues on a backup account (release v0.1.148).
  Automatic degradation is bounded (two hops, no `A → B → A`) and refuses implicit "first available" fallback
  (`session-runtime-control.md:42–60`).
- **Cairn's position (`实测`)**: #2331/D50 already decided a *smallest* pool: several stored accounts, selection
  inside the claim transaction, rerun a rejected step on the next account, park only when all are spent
  (`docs/research/2026-11-22-multi-claude-accounts.md:191`). Not built yet: only one account is enabled
  (`apps/server/src/db/schema.ts:1648`), and set-level fallback refuses another account of the same provider on
  quota exhaustion (`apps/server/src/services/model-fallback.ts:228`).
- **Borrow**: the selection ordering (exclude accounts with a live block; prefer the thread's prior account;
  else pick the account whose largest window renews soonest) and the explicit *no implicit fallback* rule.
  **Leave**: mid-step session continuation to a backup account — it contradicts Cairn's "a step is bound to
  one account at claim" model and its cache/account-switch finding
  (`docs/research/2026-11-22-multi-claude-accounts.md:180`).
- **User scenario**: the owner runs two Max accounts; a nightly build hits the 5-hour window at 02:00 and parks
  until 06:00 while the second account is idle. With the pool it finishes on the second account and the first
  is preferred again after its window resets.
- **Cost/risk**: touches claim, quota gate and notifications — persisted state and dispatch, so **High** tier
  when built. This note only records the prior art.

### 6.2 A memory review/consolidation pass with a size budget

- **Cindy's version (`实测`)**: index always visible, FTS5 search, `memory_review` (LLM suggestions, agent
  executes), `memory_consolidate` (atomic merge), soft/hard size caps and a refusal past the hard cap
  (`memory/system-prompt.md:7–49`).
- **Cairn's position (`实测`)**: records with scopes, corrections and invalidation; a lexical recall that injects
  at most four entries per turn (`apps/server/src/services/memory-recall.ts:7`); no consolidation or review pass
  (`grep consolidat|memory_review` over `apps/server/src` returns nothing).
- **Borrow**: a periodic pass (schedule or on-demand) that proposes duplicate merges and stale retirements, with
  the agent or the owner confirming, plus a stated entry/size budget so months of memory do not silently
  degrade recall. Keep Cairn's DB records and corrections; do not move memory into a worktree file.
- **User scenario**: six months on one project, ~150 memory rows, contradictory notes about a deployment;
  each new thread recalls four and rediscovers the rest. The pass merges the duplicates and retires what the
  repository now contradicts, so the agent stops re-asking settled questions.
- **Cairn area**: `apps/server/src/services/memory.ts`, `memory-recall.ts`, `memory-edit.ts`,
  `coordinator-steps.ts:65`; a schedule rule for `teammate-memory-review`-style cadence.
- **Cost/risk**: small if the pass only *proposes*; persisted state if it applies edits — **Medium**.

### 6.3 A per-task runtime switch that is explicit about when it applies

- **Cindy's version (`实测`)**: `baseline` / `effective` / `pending` / `generation`; a busy session returns
  `deferred` and the change applies at the next turn boundary; a stale generation cannot overwrite a newer
  choice; the user's own selection clears a temporary override
  (`session-runtime-control.md:1–30`).
- **Cairn's position (`实测`/`推断`)**: model and provider are resolved per step, and a chief-model fallback +
  restore message exists (`apps/server/src/services/chief-model-switch.ts`); I found no endpoint or UI to
  re-target a running **task**, and no generation guard on such a write.
- **Borrow**: the three-layer state and the "applies at the next send" contract, plus a visible line saying
  what is running and what is queued. This prevents the failure the owner would meet as "I changed the model
  and it did not change" or "a fallback undid my choice".
- **User scenario**: mid-build the owner wants the stronger model for the remaining steps. Today the edit is
  either ignored until a later step or races automatic fallback (`推断` from per-step resolution); afterwards the
  thread shows which combination actually produced the output.
- **Cairn area**: `apps/server/src/services/{builds,step-route,model-fallback}.ts`, `apps/web` task header.
- **Cost/risk**: dispatch semantics — **High** if it changes how a step binds a provider; a read-only "what is
  effective" projection could be **Small** first.

### 6.4 Capability consent for connectors, with an upgrade-never-re-asks rule

- **Cindy's version (`实测`)**: a v3 manifest declares capabilities; permissions are an authorization boundary;
  an upgrade must leave every installed, approved, enabled plugin working without re-asking — a missed migration
  is rated P0 (`plugin-security-and-authoring.md:385, 410, 1074`).
- **Cairn's position (`实测`)**: MCP connectors carry OAuth metadata, cached tools and secret storage
  (`apps/server/src/services/mcp-servers.ts`), but a connector's tool set is discovered, not consented to item
  by item, so a new tool appears without the owner seeing it.
- **Borrow**: a stored, human-readable capability list per connector (read mail, write mail, post to GitHub) shown
  once at connect/upgrade, with the rule that an upgrade adding *no* new capability never prompts. Leave the
  plugin runtime itself: Cairn runs third-party code only where the user installs it (skills, MCP servers), has no
  local plugin host with declared capabilities, and adding one is a supply-chain decision, not a research borrow.
- **User scenario**: a mail connector ships a "send" tool in an update; the owner sees one line — "this connector
  can now send mail as you; allow?" — instead of discovering it in a task's tool list after the fact.
- **Cairn area**: `apps/server/src/services/mcp-servers.ts`, `apps/web` connector settings.
- **Cost/risk**: **Medium**; no new execution surface.

### 6.5 Path→rule reading index (engineering, not product)

- **Cindy's version (`实测`)**: rules declare *when* they must be read; `pnpm rules:for <paths>` prints the
  required reading for a diff, CI runs `rules:changed`, and PR labels carry `touches:security`,
  `touches:core`, `touches:docs-only` (`AGENTS.md:38–46`, GitHub labels).
- **Cairn's version (`实测`)**: `scripts/design-rules-for.mjs` does this for UI paths only, plus the plan-gate tiers
  and `feature-map`.
- **Borrow**: extend the same generated index to the other risky seams (protocol, migrations, secrets, merge
  queue) so a reviewer is handed the rows a diff touches instead of remembering them.
- **User scenario**: a change touches token rotation and the merge queue; the reviewer receives the two rule rows
  and the one test file that must run, instead of the owner catching it in production.
- **Cost/risk**: **Small**; it changes developer process, not the product.

## 7. What to avoid

1. **A closed backend as the brain.** Cindy's account, catalog, relay and marketplace are not in the open repo
   (`README.md:162`). Cairn's promise is one self-hosted server; borrowing the cloud-companion *idea* is fine,
   making the cloud the only truth is not (`推断`).
2. **Team and shared-task surfaces.** Cindy lets a guest join one task with equal agent permissions
   (`shared-task-mode.md:13`); Cairn ruled team features out (`docs/spec/18-positioning-and-differentiation.md` §4).
3. **Telemetry on by default.** Official builds report launches and, after sign-in, model choices and token
   totals, with a documented mobile SSO consent exception (`README.md:254–280`). Cairn's privacy doc promises
   the opposite.
4. **Fetching third-party agent binaries during install.** `pnpm install` downloads Claude Code, Codex, ripgrep
   and Pi per platform (`README.md:160`, `scripts/ensure-agent-binaries.mjs`). That is their model; Cairn's
   install discipline (`--ignore-scripts`, explicit downloads) is stricter on purpose.
5. **Keeping business logic in the desktop main process.** Cindy is spending a multi-phase migration undoing
   it (`docs/host/README.md:13–21`); Cairn already has the split and should not regress for surface parity.
6. **Two regional editions with separate account realms and endpoints** (`region-and-editions.md:17`). It buys
   market access, not product truth; Cairn has one origin.
7. **An issue tracker as the work log.** 4,153 open issues+PRs, bot-filed, with pipeline labels, after 19 weeks
   (GitHub API). Useful for a funded team; noise for a one-person product.
8. **A four-engine, per-session switch as a default.** Cindy's own README admits a switch does not make engine
   states identical — it hands off or rebuilds context (`README.md:64–66`); the tracker shows the resulting
   divergence (#1991, #12315). Offer it only when a user asks, and prove the handoff on a real thread.

## 8. Recommendation

**Verdict (`推断`)**: Cindy is the strongest consumer-facing execution of ideas Cairn already holds at the
architecture level, and a poor template for Cairn's product shape. Read it for three things, in this order:

1. **#2331/D50 selection rules** — cheap to adopt because the decision exists; the pool is the only item here
   that removes real idle time for the owner (§6.1).
2. **Memory review/consolidation** — small, local, and pays off exactly in the long-running single-person use
   Cairn is built for (§6.2).
3. **Connector consent + upgrade-no-re-ask** — medium, and it closes a "new tool appeared silently" hole (§6.4).

Treat task-level runtime switching (§6.3) as a deliberate feature with a High-tier plan, not as a parity chore.
Do **not** pursue: Android, a hosted brain, team sharing, a plugin marketplace, or a region split; each either
contradicts a Cairn ruling or buys surface without trust.

The one strategic observation worth keeping: the two products are travelling toward each other — Cindy is
extracting a headless host from an Electron app, Cairn is adding desktop, mobile and chat surfaces to a
headless server (`推断` from `docs/host/README.md` and `apps/desktop/README.md`). Neither needs the other's
starting point; both need the other's *finish line* discipline.
