Marks: **`实测`** = read first-hand this session (file/URL given). **`推断`** = derived from `实测`, checkable. **`猜测`** = unverified.

Refs: `docs/design/mcp-inventory.md` sections "Replay identity and durable receipts" (line ~64) and "State readers/writers and tests-first matrix" (line ~104); issue #3760 ("a per-machine, per-source monotonic invalidation sequence plus a server-acknowledged high-watermark the daemon reports after its outbox is durably cleared").

## Question

Receipts deduplicate invalidation replays by `(machineId, sourceKey, invalidationId)` and currently retire only with the machine identity, so a long-lived machine accumulates them without bound. We need a transition where the server may delete receipts once it has durable proof that no replay can still need the stored receipt — and every replay must stay a no-op. The candidate shape is TCP-style: a monotonic per-source sequence plus a client-reported high-watermark. Each prior-art source below answered the same question.

## Pattern that fits this project

The shape that survives every crash and still stays a no-op on replay is shared by TCP and Atomix and is precisely the issue's sketch:

1. **One monotonic sequence per (machineId, sourceKey) incarnation** labels each event (Kafka's per-partition seq; Atomix's per-session `sequence_num`; TCP's per-connection octet space).
2. **A stored receipt per event above a watermark** answers "was this applied and what did it return" (Kafka `findDuplicateBatch` returning original offsets; JetStream PubAck returning original `seq`; Atomix `getResult` returning the cached `Result`).
3. **A scalar retired watermark replaces receipts below it.** The watermark is durable server state advanced only when the reporter proves it no longer needs the receipt (Copycat keep-alive `commandSequence`/`commandLowWaterMark`; rsm `LastInputSequenceNum` + open-set filter; TCP `SND.UNA`/`RCV.NXT`).
4. **A replay at or below the watermark returns a benign ACK, never re-applies** (TCP re-ACK-and-drop; Copycat null result; JetStream consumer ack for a non-pending seq). Kafka's choice — a fatal `OutOfOrderSequenceException` — is the wrong polarity for us: our replay-below-watermark is an expected edge (outbox corruption, restored backup), not a bug.
5. **Sequence space is scoped to a storage incarnation.** Kafka's PID-per-session and TCP's ISN-per-connection both exist so that a peer who lost sequence memory cannot collide with retired numbers. That is the missing piece for daemon state loss.

Why not the alternatives: a pure time-window (JetStream `Duplicates`) expires receipts while replays can still happen — the plan's "connection timeout is not a retention boundary" already rejects it, and JetStream itself treats it as best-effort, storing the dup again (fail-open). A pure count-window (Kafka's 5 batches) leaves below-window replays as fatal errors and needs a durable contiguous-sequence channel, which our invalidation POSTs are not (each event is independent; gaps are allowed). The Atomix model is the closest structural match because the reporter (daemon) is exactly the party that knows which receipts it no longer needs.

## Recommendation for the plan amendment

Amend `docs/design/mcp-inventory.md` **"Replay identity and durable receipts"** (and the matching matrix rows in **"State readers/writers and tests-first matrix"**) as follows. The retired watermark is the "equally durable no-replay proof" the section already requires; "fail closed for new coverage rather than silently expire receipts" is unchanged — retirement is now driven by proof, not by capacity.

### Fields

- `invalidationSeq` — per-(machineId, sourceKey, outboxEpoch) monotonic sequence, allocated by the daemon **in the same durable write** that persists the outbox event (`invalidationId`, metadata). Persisted `lastIssuedSeq` per source alongside the outbox so allocation survives restart.
- `outboxEpoch` — opaque random daemon-generated ID persisted inside the outbox store at store initialization; carried on every invalidation report and watermark report. Regenerated only when the outbox store is initialized fresh (reinstall/wipe). A restored backup keeps its epoch, so restored replays still dedup. This is the TCP ISN / Kafka PID analogue and is deliberately *not* the connection epoch: connection epochs remain excluded from dedup identity (existing rule stands).
- Server tables: `invalidation_receipts(machineId, sourceKey, outboxEpoch, invalidationId, invalidationSeq, appliedRevision, metadataHash, appliedAt)`, one watermark row per `(machineId, sourceKey)` holding `retiredSeq`, and per `machineId` one current-`outboxEpoch` pointer plus the set of superseded epochs. The watermark row **is** the compacted tombstone for every receipt at or below it — one durable row substitutes for N receipts.
- Daemon-side retireable value needs no extra durable write: `retireableSeq = min(outstanding outbox seq for source) − 1`, or `lastIssuedSeq` when the outbox is empty (derived from durable contents, so it cannot lie after a restart — `推断` from the persisted-outbox design).

### Durable-writes ordering

1. Daemon: one durable write `{invalidationId, invalidationSeq, outboxEpoch, sourceKey, metadata}` into the outbox → send. (Existing rule plus seq/epoch.)
2. Server: one transaction `{insert receipt, apply revocation}` → ACK carrying `{invalidationId, appliedRevision}` (existing rule; the ACK shape gains `outboxEpoch`/`invalidationSeq` echo for observability only).
3. Daemon on ACK: durably delete the matching outbox row (existing rule). Its next authenticated control POST or report carries `{outboxEpoch, retireableSeq}` — piggybacked, no new channel, re-sent until the server acknowledges a watermark ≥ it. A lost report only delays compaction (fail-safe direction).
4. Server on watermark report: **one transaction** `{retiredSeq = max(retiredSeq, reported), delete receipts ≤ retiredSeq under that epoch}` → respond. The report is idempotent; a replayed or lower report is a no-op.
5. Server restart: receipts and watermark rows are durable state — unchanged.

Crash-position analysis: crash between 3's delete and 4's report leaves receipts (safe); crash between the daemon sending the report and receiving the ACK re-reports (idempotent); crash inside 4's transaction is atomic by construction. The watermark can only over-claim if the daemon reports a seq that was never ACKed — prevent by deriving `retireableSeq` strictly from durably-cleared rows (the contiguous-prefix rule, same as `moveAckFloor` stopping at the first gap and TCP's cumulative semantics). State this trust assumption explicitly in the doc: like Atomix's keep-alive, the server cannot independently verify the reported frontier — it only ever retires receipts for events the reporter itself proved it delivered.

### Retired-replay response

On ingress after machine authentication, evaluate in this order:

1. `outboxEpoch` in the machine's superseded-epoch set → retired ACK.
2. `outboxEpoch` neither current nor superseded → a recreated outbox: atomically move the old epoch into the superseded set and delete all old-epoch receipts and watermarks, then apply the event normally (supersession).
3. Under the current epoch, `invalidationSeq ≤ retiredSeq` for that `(machineId, sourceKey)` → return a **retired ACK**: the same response shape as a duplicate ACK but with the receipt body replaced by `{retired: true, retiredSeq}`. No `coverageRevision` advance, no side effects, no change to replacement work. Keeping it ACK-shaped preserves one code path — the TCP duplicate-ACK analogue, not Kafka's fatal out-of-order error.
4. Receipt found for `(machineId, sourceKey, outboxEpoch, invalidationId)` → return the stored receipt (existing dedup hit).
5. Otherwise → normal apply/insert. Metadata conflict for an existing `invalidationId` → `invalid` (existing rule).

`retiredSeq` never moves backward; reports are only meaningful under the machine's current epoch. Decided after review: a retired ACK resolves in two daemon-side ways — it matches an outbox entry already cleared (in-flight duplicate) and is ignored, or it matches an event still pending in the outbox, which is impossible under a consistent store and therefore detects rolled-back daemon state; the daemon then reinitializes the outbox (new epoch) and resubmits instead of silently dropping the event.

### Epoch mechanism for daemon state loss

- Normal daemon restart: `outboxEpoch`, `lastIssuedSeq` and outbox rows all persist; replay resumes and retireable re-derives — nothing special.
- Daemon storage reinitialized (reinstall, wipe): new `outboxEpoch` → fresh sequence space starting low without colliding with retired numbers. Decided after review — epoch supersession rather than multi-epoch retention: accepting the machine's first new-epoch event atomically retires all old-epoch receipts and watermarks, because a daemon that lost the store can never replay from it; later old-epoch submissions take the retired-ACK path. Multi-epoch retention was the alternative: it would keep old-epoch receipts dedupable, but a restored-backup daemon reusing a retired sequence number would then be silently dropped; supersession plus the pending-retired-ACK contradiction rule turns that drop into a self-healing resubmission.
- Machine re-key / identity retirement: unchanged. `machineId` is the outermost dedup dimension; receipts and watermarks under the retired identity retire with it (existing rule).
- Server restart / leader failover: watermark and receipts are durable; `retiredSeq` is never reset by process lifetime — same rule as "connection timeout is not a retention boundary".

### Test-matrix rows to add

New rows in "State readers/writers and tests-first matrix" (plus extending the existing "ACK lost, reconnect, replay is a no-op" row's restart variants):

| Path | Expected behavior and mandatory test |
|---|---|
| Watermark compaction | Apply+ACK events, daemon durably clears outbox, reports `retireableSeq`; server retains only seq > watermark; each retired replay returns the retired ACK with no revision advance, no side effect and unchanged replacement work; repeat across server restart |
| Lost watermark report | Drop the report; receipts persist and still dedup; the daemon re-reports on a later control exchange; server compaction is idempotent; repeat after daemon restart |
| Retired replay from stale outbox | Replay a persisted-ID event with `invalidationSeq ≤ retiredSeq` (simulated corruption/restore); retired ACK returned, no-op; coverage and outstanding work unchanged; the daemon ignores it when the outbox entry is already cleared, and reinitializes plus resubmits when the event is still pending |
| Daemon outbox reinitialization | Wipe the outbox → new `outboxEpoch`; low sequence numbers apply as new events without colliding with retired space; the first accepted new-epoch event retires all old-epoch receipts and watermarks atomically |
| Restored daemon backup | An outbox restored with its old epoch replays pending events and resolves each as stored receipt or retired ACK; a retired ACK against a still-pending event triggers reinitialization and resubmission, never a silent drop or re-apply |
| Watermark monotonicity and epoch scoping | An equal/lower `retireableSeq` report is ignored; reports under a non-current epoch do not compact the current epoch's receipts |
| Retired ACK and confirmation | A retired ACK for an already-cleared event is ignored; one for a still-pending event is a state contradiction that forces outbox reinitialization and resubmission; a normal stored-receipt or retired resolution unblocks the request-bound confirmation so the negative read does not stay `unknown` |
| Retireable frontier cannot skip un-ACKed seqs | With seq N+1 ACKed but N pending, the daemon reports ≤ N−1; out-of-order ACKs only advance the contiguous cleared frontier; verified across a daemon restart |

Carrier (decided): the derived watermark rides on every invalidation submission, every enrollment/reconnect control exchange and periodic reconciliation, and the response acknowledges the applied value — no dedicated channel, and loss only delays reclamation.
