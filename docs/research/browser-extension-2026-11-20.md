# Should Cairn ship a Chrome extension to drive the owner's logged-in Chrome?

Status: research, 2026-11-20. No product code changed. Question (ian): ship a Chrome browser extension so agents can drive the user's own logged-in Chrome, instead of (or in addition to) today's daemon-launched Chromium over CDP (`apps/daemon/src/computer/browser.ts`, `host-desktop.ts`, `apps/daemon/computer-image/`).

Evidence labels: `实测` = read first-hand from primary source code, official documentation, or this repo's own source in this session; `推断` = follows directly from `实测`; `猜测` = everything else. External-product claims were read by research subagents against the cited primary sources (official docs, GitHub source, Chromium source); local claims were read from this repo's source directly.

Builds on: [`stealth-browsers-2026-11-17.md`](stealth-browsers-2026-11-17.md), [`computer-login-handoff.md`](../design/computer-login-handoff.md), [`own-mac-computer.md`](../design/own-mac-computer.md), [`cloakbrowser-computer.md`](../design/cloakbrowser-computer.md).

## 2. Why now

### 2.1 Chrome 136+ blocks remote debugging on the default profile

From Chrome 136, `--remote-debugging-port` and `--remote-debugging-pipe` are no longer respected on the **default** Chrome user-data directory; they must be accompanied by `--user-data-dir` pointing at a non-standard directory, which uses a different encryption key. The stated motive is infostealers extracting cookies. `实测` ([Chrome blog, remote-debugging-port](https://developer.chrome.com/blog/remote-debugging-port)). Chrome for Testing keeps the old behavior. `实测` (same page). Practical consequence: a debug port cannot drive the owner's real default profile and its logins. `推断`.

Chrome 144 adds the only first-party, non-extension escape hatch: the owner enables `chrome://inspect/#remote-debugging`, and each connection shows a consent dialog plus a "controlled by automated test software" banner. `实测` ([Chrome blog, DevTools MCP](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session), [auto-connect docs](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect)). Browser Use's own migration note confirms: pointing `user_data_dir` at the default directory raises because "Chrome 136+ refuses remote debugging on it". `实测` ([Browser Use MIGRATING.md](https://github.com/browser-use/browser-use/blob/main/MIGRATING.md)).

So the two viable transports for the owner's real logins are a **`chrome.debugger` extension** or the **Chrome 144 consent-gated port**, and only the extension gives per-site permission granularity (§3).

### 2.2 The observed failure that motivated the question

Today, with the Claude in Chrome extension attached, `Page.captureScreenshot` timed out on zhipin.com and on one Cairn tab, while DOM reads and JS eval still worked (`实测`, observed 2026-11-20). This is consistent with a documented Chrome behavior, not necessarily zhipin anti-debug: inactive or background tabs produce no rendered frames, so CDP callers must `bringToFront` before capturing, and regular Chrome can only screenshot the active tab (`实测`, [puppeteer#12712](https://github.com/puppeteer/puppeteer/issues/12712)). The zhipin-specific half is unconfirmed — no primary source documents zhipin's detection; the repo's own runbook records that a CDP debug port "almost always" triggers zhipin's security-check page (`实测`, `~/.agents` `agent-reach` career runbook). Conclusion: an extension path must bring the tab to front before every screenshot, and even then it does not fix zhipin.

Pattern across every vendor: **the local extension is the fix for "real logins + residential IP + real fingerprint", and the cloud/sandbox browser (or, for Cairn, the stealth VM) is the fix for "hostile anti-bot sites".** No source shows a way to beat active anti-debug sites with the extension, and OpenAI explicitly retired its standalone Atlas browser in favour of the extension. `实测` (§3 rows, Atlas retirement).

## 4. Recommendation

**Ship a Chrome extension as an additional, opt-in path — not a replacement for the daemon-launched Chromium.** Adopt the Playwright MCP `--extension` architecture as the reference (open-source Apache-2.0, `chrome.debugger` CDP in a Manifest V3 extension + a loopback WebSocket relay, no native messaging, per-tab/per-origin ownership and a `cdpPolicy` that refuses browser-wide state). Build Cairn's own extension on that model, gated by per-origin approvals reusing the own-Mac approval machinery. Keep the VM Chromium/CloakBrowser as the default and the only path for stealth and anti-debug sites such as zhipin.

Why "in addition", not "instead":

1. **The extension wins exactly where the VM loses, and vice versa.** The extension is the only way to reach the owner's real signed-in sessions (Gmail, LinkedIn) and a residential IP without a license key, now that Chrome 136 has closed the debug-port route to the default profile (§2.1). The VM Chromium/CloakBrowser is the only path that handles hostile anti-bot sites; the extension carries the `chrome.debugger` infobar and the `Runtime.enable` CDP signal that DataDome/Cloudflare check, and the observed zhipin `captureScreenshot` hang shows it is not a stealth answer (§2.2). Every peer keeps both a local browser and a cloud/sandbox browser for the same reason (§3).
2. **Do not use `--remote-debugging-port` as the primary attach path.** It is whole-browser, unauthenticated-on-loopback, loses per-site gating, and Chrome 144's consent banner plus Chrome 136's default-profile block make it strictly worse than an extension. `agent-browser`'s existing `--auto-connect` is a fallback if a zero-extension attach is ever wanted, at the cost of per-origin control (§3).
3. **The screenshot bug is a real, fixable cost of the extension path, not a blocker.** Bring the target tab to front before every capture (`实测`, puppeteer#12712); zhipin remains unsupported on the extension and stays on the VM.

## 5. What would have to change

If this research is accepted, the implementation touches these areas (all names follow today's layout):

1. **New Manifest V3 extension** (new top-level package, e.g. `apps/extension/`): manifest with `debugger`, `tabs`, `tabGroups`, `storage`, scoped `host_permissions`; a `connect.html` approval page; per-origin prompt UI. Mirrors Playwright's extension, not a fork of it.
2. **Daemon transport** — `apps/daemon/src/computer/`: a new `extension-browser.ts` implementing the same `browser_navigate` / `browser_snapshot` / `browser_act` surface over CDP-via-relay, plus a loopback WebSocket relay (Playwright's `cdpRelay.ts` pattern) so no native-messaging host is needed — the daemon already runs on the Mac host via the Electron runner (`实测`, `own-mac-computer.md`). Add bring-to-front before screenshot (§2.2).
3. **Server gating** — `apps/server/src/services/machine-computer.ts`: a new capability flag (e.g. `ownChrome`), reusing the own-Mac gate shape (owner-only switch, per-origin `action_proposal` cards, refuse the browser-state CDP methods Playwright's `cdpPolicy` refuses). The `browser_*` tool names can stay; the extension is a new provider behind them.
4. **Security surface** — add the extension relay and its approval gate to the `externalEntryAuth`/`machineAndCommandBoundary` lists in `packages/shared/merge-gate-paths.json`, and run `/security-review` before landing.
5. **Unchanged** — the VM Chromium + CloakBrowser path, the CDP→no-CDP zhipin takeover, and `stealth: true` stay exactly as they are. The extension is surfaced as "use my Chrome", never as the default browser.

Open design decisions for a follow-up (not resolved here): whether the extension path is offered in the same turn kinds as own-Mac (owner-started only), and whether an LLM "guardian" risk layer like OpenAI's is wanted at launch or deferred.
