# Sharing one GitHub grant between product surface and agent tool surface — the design

Follow-up to `docs/research/github-auth-two-surfaces-2026-11-17.md`, which established *that* shared-grant products exist. This document answers *how* they structure the sharing: where the bearer is resolved, who refreshes, what revoke does, how install-vs-authorize is sequenced, and whether the shared grant needs MCP-specific scopes. Sources are first-party only; every claim is marked verified / inferred / unverified.

## The one hard constraint (verified, GitHub docs)

> "You can use the refresh token to generate a new user access token and a new refresh token. **Once you use a refresh token, that refresh token and the old user access token will no longer work.**" — https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens

Rotation invalidates **both** halves of the grant: the spent refresh token *and* the access token it just replaced. Two consumers that each store their own `(ghu_, ghr_)` pair and refresh independently will livelock-break each other — whichever refreshes second kills the other's stored tokens, and a `ghu_` minted by the first refresh dies at the second. A shared grant therefore needs exactly **one refresh writer**; other consumers must read through it. cairn's `github_connection` refresh path already has single-writer mechanics (in-process `refreshChains` map + `connectionGeneration` optimistic update, `apps/server/src/services/github-connection.ts:131-256`); the connector path has a *second* independent refresher on its own sealed copy (`refreshGithubApp`, `apps/server/src/services/mcp-servers.ts:1216-1261`) — that second writer is the thing the merge deletes.

Secondary facts from the same doc (all verified): user access tokens are `ghu_`, expire after 8 h; refresh tokens `ghr_` expire after 6 months; `scope` in the refresh response is always the empty string for GitHub Apps ("the user access token is limited to the permissions that both your app and the user have"); `offline_access` is the only supported scope value; refresh of a device-flow grant needs no `client_secret` — matching `github-device-core.ts:137-157`. Revocation surface: `github_app_authorization` webhook fires when the user revokes; continued use of a revoked token returns 401 (https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

## What the shared-grant products actually do — mapped to the design questions

**Bearer resolution.** Every shared-grant design resolves the bearer **at call time from the credential owner**, never by copying the token into the tool surface's store:

- VS Code (both paths): fetch a session token when the connection needs it — `$getTokenForProviderId` on connect and each auth-retry; `_initialGitHubMcpToken` at the moment the runtime asks. The MCP server definition stores only `{providerId, scopes}` — a *reference*, not a credential.
- Copilot Connectors: the reference is even thinner — the server is connector-owned and GitHub brokers everything.
- `bearer_token_env_var` / `gh auth token`: the config stores a *pointer* (env var name); the credential store (`gh`) owns the value.
- Codex cloud: account-level broker; nothing stored client-side at all.

Nobody injects a token snapshot into MCP-server persistent storage. (Session-start injection exists only where the credential is minted per run — Copilot cloud agent's repo-scoped token — which is a *narrower* agent credential, the opposite of sharing the user's grant.)

**Refresh ownership.** Exactly one refresher in every design: the provider (VS Code `IAuthenticationService`), the platform (Copilot cloud agent, Codex connector, GitHub-side connectors), or the external store (`gh`). The tool surface re-asks the owner on failure instead of refreshing — VS Code's 401 path re-runs the whole acquisition (`forceNewRegistration`), it does not keep a refresh token. This is forced by the rotation semantics above: a second refresher isn't merely redundant, it's destructive — its first rotation invalidates the access token the other consumer may still be holding *and* the refresh token the other has stored. Verified against GitHub's own words: the old access token dies with the spent refresh token.

**Revocation semantics.** Two models appear:

- *Fail-closed propagation* (VS Code): auth-session change events revalidate every running MCP server; lost session → the server is **stopped**, not quietly degraded. Disconnected surfaces recover through the ordinary interactive auth path.
- *Broker degrade* (Codex/Connectors): disconnect on the product side ends the surface; there is no separate MCP grant to clean up.

Both treat the shared grant as the single source of truth — revocation is observed once, at the owner, and the tool surface converts it into "needs auth", never into its own error state. cairn already has the analogs: `github_connection.disconnectedReason` / row deletion on the owner side, and `needs_auth` + `withheldMcp` on the connector side.

**Install vs authorize.** Three arrangements:

- *Combined*: Codex via `request_oauth_on_install` (registration-level flag; install redirects straight into `/login/oauth/authorize`, then repo selection). Note the limit (verified, GitHub docs): on-install authorization runs the **web application flow** — redirect + code exchange — not device flow; and it covers only the installing user ("if the app was installed on an organization account, you will need to use the web application flow or device flow to generate a user access token for other users").
- *Two steps, user-ordered*: cairn today (device auth grant; install URL offered separately; `githubConnectorInstalled` polls `GET /user/installations`), and ChatGPT's own troubleshooting docs explicitly describe install and repo access as "separate steps".
- *No install concept*: VS Code/JetBrains/VS hosts — they hold an OAuth-app grant only; repo access is whatever the token can see, and org-level gating is the app's `oauth_application_policy`, not an installation.

For a GitHub App like `cairnwright`, install and user-authorization are genuinely different objects (installation scopes repo access; the `ghu_` scopes user identity) — every first-party product keeps them separable underneath even when the UX is one screen.

**Scope model.** No MCP-specific scopes exist. The remote server is scope-agnostic (any valid token; `ghu_` included); a GitHub App user token's `scope` field is always empty — effective access comes from app permissions ∩ user permissions ∩ installation. VS Code does preserve an *upscope* path in case a challenge ever arrives with scopes, but treats reuse as correct for the scope-less initial request — which is what the GitHub MCP issues (verified in vscode source + the live `ghu_` acceptance test from the prior doc).

## The pattern that fits cairn

cairn's shape matches **VS Code's declared-provider model**, adapted for a server-side credential owner:

- cairn's MCP connector already stores a *reference shape* (`authKind='github-app'`, `oauthCipher` with its own token pair). The shared-grant version of that is exactly what `authentication: {providerId, scopes}` is in VS Code: the connector keeps `{authKind, catalogId='github', url}` and points its credential lookup at `github_connection` — `github` plays the role of `providerId`.
- Bearer resolution at call time, in the two places a bearer is materialized today: `checkMcpConnector`'s probe (`mcp-servers.ts:617-659`) and `deliverableConnector`/`stepConnectorEndpoints` (`mcp-servers.ts:1094-1142`) — both currently read `bearerOf()` → `openGithubApp()`. Both become "resolve the team's `github_connection` token through `teamUserToken`/`connectionToken`", which carries the refresh-with-single-owner semantics, the `disconnectedReason` check, and `refreshChains` dedup for free.
- The connector's own grant machinery — `GithubAppSecrets`/`sealGithubApp`/`openGithubApp` (`mcp-servers.ts:552-598`), `refreshGithubApp` (`mcp-servers.ts:1216-1261`), the connector device-flow attempt map + `saveGrant` (`mcp-github-connector.ts:63-232`), `tokenGeneration`/`authRevision` for token updates — collapses to status bookkeeping only. This is the single-path requirement in concrete form: the same edit must remove the second refresh writer and the second stored pair; keeping `refreshGithubApp` "as fallback" reintroduces the rotation livelock GitHub's docs forbid.
- `github_device_core.ts` stays shared as-is: it already serves both surfaces' minting (`requestGithubDeviceCode`/`pollGithubDeviceCode`/`refreshGithubDeviceToken`); after the merge only `github_connection`'s device flow (`github-connection-device.ts`) mints, and `refreshGithubDeviceToken` has exactly one caller.
- Revocation maps one-to-one: `disconnectedReason`/row delete → connector probe sees `reason='github-disconnected'`/`'no-github-connection'` → status `needs_auth` → `deliverableConnector` returns null → slug lands in `withheldMcp` (`mcp-servers.ts:1099,1133-1136`). Same shape as VS Code's session-removed → `server.stop()`.
- Connector lifecycle survives independently: users still add/remove/check the `github` connector, pick toolsets via URL path, and the row keeps `status`/`toolCount`/`checkedAt`. What disappears is the *duplicate device dialog* — creating the connector when `github_connection` exists just binds it; when it doesn't, the UI routes to the connection flow first (one auth for both surfaces).
- Install stays a second, user-visible step (`githubConnectorInstalled` + the `/installations/new` URL, `mcp-github-connector.ts:36-43,234-248`): same separation GitHub documents for GitHub Apps and the same two-layer model OpenAI describes for Codex. `request_oauth_on_install` remains an available registration-level UX upgrade but is not required for the merge — and it wouldn't replace device flow anyway.

The alternative (broker service — a minting endpoint the MCP client calls per request) is what Copilot Connectors does, but it buys nothing here: cairn already hands the daemon an `McpConnectorEndpoint` with headers (`stepConnectorEndpoints`), so "call time" for the tool surface is connector delivery — resolving from `github_connection` at that point is already the latest-possible read.

## Concrete recommendation

One `github_connection` grant; the `github` connector resolves its bearer through it.

- `apps/server/src/services/mcp-servers.ts` — replace the `github-app` branch of `bearerOf`/`deliverableConnector`/`checkMcpConnector` with `teamUserToken`-backed resolution (`GithubTokenDeps` extended into `McpConnectorDeps`, or a narrow `resolveGithubBearer(teamId)` dep); delete `refreshGithubApp`, `sealGithubApp`, `openGithubApp`, `GithubAppSecrets`, and the `oauthState.refreshes`/`githubDevice` entries that only served that path; `authKind` gains/retains a marker meaning "bearer comes from the team's GitHub connection" (a new `authKind` value or a `catalogId==='github' && authKind==='github-app'` convention — decided at design time, with a migration for existing `oauthCipher` rows: drop the cipher, point at the connection).
- `apps/server/src/services/mcp-github-connector.ts` — replace `startGithubConnectorDevice`/`pollGithubConnectorDevice`/`cancelGithubConnectorDevice` + `saveGrant` with a bind-or-create against `github_connection` (create connector → require `hasGithubConnection`, or trigger the connection's device flow then create on completion); `githubConnectorInstalled` re-reads the connection token instead of `openGithubApp`; `githubConnectorAvailability` unchanged.
- `apps/server/src/services/github-connection.ts` — becomes the single credential owner it already is structurally; confirm `refreshChains` + `connectionGeneration` cover connector-driven concurrent reads (they do — `deliverableConnector` and probes funnel into the same `connectionToken`), and that `refreshLeaseUntil` semantics are honored for multi-writer safety if a second server process ever refreshes (inferred — field exists at L76 but check the lease writer before relying on it).
- `apps/server/src/routes-resources.ts` — the `mcp-connectors/github/device*` routes retire or redirect to the `github/connection/device` routes (L926-946 vs L1041-1074); the connector create route documents "requires github connection"; `stepConnectorEndpoints` callers (`routes-machine` token path) need no shape change — `withheldMcp` already carries the failure mode.
- `apps/server/src/services/github-device-core.ts` — unchanged shared code; `refreshGithubDeviceToken`'s caller count drops to one.
- Edge cases to spec in the design doc: reconnect of the `github_connection` must invalidate in-flight connectors' cached views (it doesn't cache any — call-time reads — so this is free); `userId`/`login` shown on the connector record comes from the connection row (`login`) instead of `GithubAppSecrets.login` (`toConnectorRecord`, `mcp-servers.ts:227`); the `adoptGithubProfile` side-effect on first connect keeps running on the connection path only (`routes-resources.ts:865`).

Red-first test shape (per repo rules): on current code, two rotations — connector refresh after connection refresh, or vice versa — leave one side holding a dead `ghu_`+`ghr_`; a test that exercises `refreshGithubApp` after `refreshDeviceGrant` on the same upstream grant should assert the failure the merge removes, then assert post-merge that the connector path can never hold its own pair (no `oauthCipher` for `authKind=github-app`) and that a probe/delivery after connection disconnect returns `needs_auth`/`withheldMcp`.
