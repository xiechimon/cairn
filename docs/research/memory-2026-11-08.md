## Current implementation findings

`实测`: [memory.ts](../../apps/server/src/services/memory.ts) already has capped injection, overlap candidates, exact duplicate rejection, team/project/layer/thread scope, versioned update and hard delete. Its 3,000-token cap was absent when the earlier research was written; do not dispatch it again.

`实测`: [memory-consolidation.ts](../../apps/server/src/services/memory-consolidation.ts) already adds a weekly bounded pass to the digest and applies validated merges/expiry. The old research's propose-only suggestion is not the current implementation.

`实测`: [routes-agents.ts](../../apps/server/src/routes-agents.ts) exposes team list, promote and delete, but no HTTP edit endpoint. [chief-settings.tsx](../../apps/web/src/chief/chief-settings.tsx) now queries memory at team scope after #3608 removed the retired `agentActor` gate. It still renders only title/body and nothing for an unresolved list request. It provides neither mutation controls nor explicit memory read error/loading states.

`推断`: the registry's claim that settings can delete/promote is stronger than the inspected settings implementation. Backend capability does not prove frontend reachability. The frontend design must close this gap without pretending existing screenshot fixtures already cover it.

## Pattern and recommendation

`推断`: keep curated scoped facts and canonical history separate; expose a quiet topic list and inspect-before-action detail, borrowing Claude's documented Manage/Topics model while retaining Cairn's real settings and dialog components. Do not copy account-memory toggles or incognito behavior: those would be new product modes outside this design.

`推断`: preserve #3608's team-scoped availability, make loading/error distinct from empty, and use the existing promotion/delete endpoints with explicit confirmation and query refresh. Inline editing is not designed as a nonexistent endpoint; correction remains available through the Coordinator's existing tools.
