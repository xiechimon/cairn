# Task issue lifecycle: closing the per-task GitHub issue on landing, cancel, supersede and failure

Status: research, 2026-11-09. No code changed. Question: cairn opens a GitHub issue for each task. How do products that create or sync an issue per unit of work close it when the work lands, and what do they do on cancel, supersede or failure? cairn's plan is `Closes #N` in the PR body for every merge route (REST merge, Mergify squash queue, human merge), plus an explicit REST close with `state_reason: not_planned` on cancel, archive or supersede.

Evidence labels: `实测` = read first-hand in this session (primary doc page, source file, or a GitHub API response), `推断` = follows from `实测` facts, `猜测` = everything else. Docs were fetched through Jina Reader on 2026-11-08/09. cairn facts were read in this worktree at `fdd497fb7` and from the `xiechimon/cairn` GitHub API.

## 2. Facts that decide the design

### 2.1 GitHub rules (`实测`, [linking doc](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue))

1. Keywords are honored in the **PR description** (the docs say "pull request description"; Linear additionally reads titles, GitHub's doc does not mention titles) and in **commit messages**.
2. PR-description keywords are "interpreted only when the pull request targets the repository's default branch. If the pull request targets any other branch, then these keywords are ignored, no links are created, and merging the PR has no effect on the issues."
3. Commit-message keywords close the issue "when you merge the commit into the default branch", without listing the PR as linked.
4. Keyword syntax: `KEYWORD #N`, `KEYWORD owner/repo#N`; colons and uppercase allowed (`Closes: #10`, `CLOSES #10`). Multiple issues need the keyword repeated.
5. REST `PATCH /repos/{owner}/{repo}/issues/{issue_number}`: `state_reason` is one of `completed`, `not_planned`, `duplicate`, `reopened`, `null`, and is "Ignored unless `state` is changed". `duplicate_issue_id` (integer issue **ID**) names the original for `state_reason: duplicate` ([REST](https://docs.github.com/en/rest/issues/issues#update-an-issue)).
6. Merge method: the GitHub docs do not condition linking on merge/squash/rebase; the link lives on the PR, and the PR-merged event is what closes (`推断`). Observed directly for squash below.
7. GitHub native merge queue: docs are silent on keywords (`实测` absence); closes are `推断` because the queued PR ends as merged into the default branch.

- PR #2447, #2050, #2416 (merged by `cairnwright`, cairn's own route): issue closer is the PR itself (`实测`). Their squash messages also carried the keyword, so these do not isolate body vs commit (`实测`).

### 2.3 cairn code today (`实测`)

- `apps/server/src/lib/github.ts` `githubCloseIssue`: PATCH `state: closed` with `state_reason` `not_planned` (string reason, plus a comment) or `completed`.
- `apps/server/src/services/builds.ts` `closingLine`: emits `closes #N` only for same-repo issues; cross-repo sources get no line, although GitHub supports `closes owner/repo#N` (`实测` doc).
- `apps/server/src/services/local-merge.ts`: local landing writes `Closes owner/repo#N` into the **commit message**, which is the commit path (closer = Commit, PR not linked).

## 3. Pattern that fits cairn

All products split cleanly into two halves (`推断` from §1):

- **Landing** is driven by the platform's own merge signal: GitHub keyword (Copilot, OpenHands, Sweep), or a PR-merged event mapped to a state (Linear, Plane, Jira automation). Nobody closes the issue by polling for a merge and then calling the API, except as a repair path.
- **Not landing** (closed PR, cancel, supersede, failure) is never a keyword: Plane and Jira map "closed without merge"/"declined" to an explicit state; Linear lets cancel/duplicate close PRs from the issue side; Sweep and OpenHands leave the issue open on supersede or failure, because the work is still wanted.

cairn's plan matches this split and is sound, with these refinements:

1. **Keep `Closes #N` in the PR body as the single landing path** for API merge, Mergify squash queue (including batch drafts, `实测` #3047) and human merge. Keep it on its own line at the end of the body (Copilot's convention) so prose edits cannot drop it (`推断`).
2. **Guard the default-branch rule.** A task PR whose base is not the default branch (stacked `Depends-On` PRs) gets no link. Either retarget before merge or, on the PR-merged webhook, check `closingIssuesReferences` / issue state and close with `state_reason: completed` via REST as the repair path (`推断`). Whether GitHub re-reads the body after an automatic retarget to `main` is unverified (`猜测`).
3. **Do not switch Mergify to `fast-forward` or `merge-batch`** without re-testing closes: those merge the batch PR, not the original (`实测` doc), so the PR-body link on the original is not guaranteed (`猜测`).
4. **Cancel / archive**: REST close with `state_reason: not_planned` plus a comment saying why, as planned (`实测` API supports it).
5. **Supersede**: prefer `state_reason: duplicate` with `duplicate_issue_id` (the successor issue's ID, not number) when the successor is another issue; it records the relation in the timeline. Use `not_planned` when there is no successor issue (`推断`). If the successor reuses the same issue (new PR, same task), keep the issue open and move `Closes #N` to the new PR, as Sweep does (`实测` Sweep pattern).
6. **Failure** (step fails, PR closed unmerged, task will retry): leave the issue open, like OpenHands/Sweep; close `not_planned` only when the task itself is abandoned (`推断`).
7. **Local landing** writes the keyword into the commit message, so the closer is a Commit and the PR shows no link (`实测` #2379 pattern). Acceptable, but the merged-handler repair check in item 2 should also cover it (`推断`).
8. Extend `closingLine` to emit `closes owner/repo#N` for cross-repo source issues; GitHub supports that syntax (`实测` doc). Permission requirements for cross-repo closes were not checked (`猜测` that the merging actor needs write on the issue repo).

Recommendation: ship the PR-body keyword as the only landing path, plus one idempotent repair on PR-merged (if the task's issue is still open, PATCH `state: closed, state_reason: completed`), and REST closes with `not_planned` (cancel/archive/abandon) or `duplicate` + `duplicate_issue_id` (supersede by another issue). Leave the issue open on failure and on same-issue supersede.

## 4. Why #3418 stayed open, and what was built

- PR #3422 (opened by `app/cairnwright`, base `main`, merged by Mergify squash) names its issue only as a link, `[#3418](https://github.com/xiechimon/cairn/issues/3418)`, with no keyword; `closingIssuesReferences` is empty (`实测`, `gh pr view 3422 --json closingIssuesReferences,body`). The worker writes the PR body itself with `gh pr create`, so the body carried no keyword. `closingLine` only fed the commit message of cairn's own REST merge, which Mergify-merged PRs never take (`实测`, `builds.ts` at `fdd497fb7`).
- Built (one landing path): `apps/server/src/services/pr-closing-line.ts` appends `Closes #N` for the task's own issue (`github-issue-self`, or an imported `github-issue` in the same repo) to an open PR body that does not already close it. The PR watch runs it on every sweep of an open PR, so a worker rewrite that drops the line gets it back. The REST merge runs it once more before the merge `PUT` and refuses to merge when the edit fails. `closingLine` is deleted; the REST merge commit message is now always cairn's own line.
- Not landing (separate PR, `docs/design/task-issue-sync.md`): one level-triggered reconciler derives the desired issue state from the task row as it is now and a sweep applies it. Cancelled, archived and deleted tasks close their self-created issue as `not_planned` with a one-line comment; an archived `done` task whose issue is still open closes as `completed`; `close_todos` takes `supersededBy` and the comment links the successor issue; a reopened task reopens it; a failed task leaves it open. A first design hooked each transition and kept missing paths (delete during creation, reset, creation retry), which is why it became a sweep.
- Departures from §3: supersede uses `not_planned` with a link, as the owner asked, not `duplicate` (the successor is often a different scope, so "duplicate" would overstate it). There is no PR-merged repair close: a PR that lands on a non-default branch has not landed on the default branch, so its issue stays open by design. Local landing keeps the commit-message keyword in `local-merge.ts`, because it has no PR to carry a body.
