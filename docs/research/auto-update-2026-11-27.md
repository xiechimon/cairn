# Fleet Auto-Update Prior Art (Desktop, Resident Server, and Standalone Runner, 2026-11-27)

> **Question.** Cairn's Mac desktop app already updates itself, swaps on quit/idle, and rolls back on startup failure (`docs/design/desktop-update-rollback.md`), while a second computer — a resident server on a home Mac mini or a standalone Runner — lags behind or only reports `"Needs a Cairn update"` (`docs/design/version-skew.md`). How do **GitHub Actions self-hosted runner**, **VS Code Remote**, **Tailscale**, **Amp**, and standard **host service managers (`launchd` / `systemd` / Docker)** automatically update multi-machine fleets without interrupting active work, recover from bad updates, and refuse read-only installs cleanly?
>
> **Reused baseline.** Builds on [`docs/research/version-skew-2026-11-25.md`](version-skew-2026-11-25.md).
>
> **Marks.** **`实测`**: read first-hand in this session (official docs, upstream source, or Cairn repo source at the named file). **`推断`**: derived directly from `实测` facts and verifiable. **`猜测`**: everything else (explicitly marked if any).

## 2. Pattern That Fits Cairn

1. **Server-initiated release discovery + bidirectional fleet convergence (Tailscale + GitHub Runner)**:
   - Every Cairn server periodically checks `DESKTOP_MANIFEST_URL` (the existing public GitHub Releases manifest, no API rate limit).
   - If a newer release exists and the server hosts a writable updater (`updater.supported === true`), the server triggers its own idle-safe update (`requestHostUpdate`) without waiting for a laptop to connect.
   - Whenever `max(latestRelease, serverVersion) > runnerReleaseVersion` (or `runnerNeedsUpdate`), the server advertises `{ targetVersion }` to connected Runners in `POST /api/machine/presence` responses and pushes `{ type: 'runner.update', targetVersion }` over the existing SSE stream (`/api/machine/stream`), matching GitHub Runner's push + Tailscale's control notice.
   - When a desktop app connects to a remote server that is newer than the laptop (or knows of a newer release), `remote-version` nudges the laptop's existing `createUpdater().check()` so the laptop catches up at idle without user clicks.
2. **Headless health guard & rollback on BOTH resident server and standalone Runner**:
   - **Resident Mac mini server (`background-updater.mjs`)**: after swapping `Cairn.app` and kickstarting `app.cairn.host`, instead of leaving `state.installed` unconfirmed for a closed GUI, `background-updater` probes the resident server across the 30s/60s `GUARD_HEALTHY_AFTER_MS` window. Healthy → clears `installed` and prunes `.cairn-previous`; crash/3 failed probes → restores `.cairn-previous/Cairn.app`, kickstarts the previous server, writes `blocked`, `notice`, and `host-update-status.json` `rollback` so remote clients show one clear line.
   - **Standalone Runner (`apps/daemon`)**: uses versioned immutable install slots (`<CAIRN_HOME>/self-update/versions/<ver>/`) + a thin stable launcher loop (`self-update-bootstrap.ts` inside `cli.ts`) so `systemd`/`launchd`/desktop never lose track of the PID. The active Runner downloads + SHA-256 verifies + smoke-tests (`--version`) the new archive in the background, pauses new claims and drains `inFlight === 0 && journal.pending === 0` (like GitHub Runner's `jobDispatcher.WaitAsync()`), writes `pending = targetVersion`, and exits `75`. The thin launcher spawns `targetVersion`; if it exits or fails to confirm `healthy.json` within the probation window, the launcher atomically flips `activeVersion` back to `previousVersion`, records `blocked`, and relaunches `previousVersion`.
3. **Explicit read-only install refusal (Tailscale `ForAutoUpdate` + Amp Homebrew rule)**:
   - `classifyRunnerInstall` detects `desktop-bundled` (updated by parent `.app`), `homebrew` (`/Cellar/`, `/opt/homebrew/`, `/usr/local/Cellar/`), `docker` (`/.dockerenv`, `/run/.containerenv`), `development` (`.ts` entry or git repo checkout), and non-writable folders (`read-only`), returning `supported: false` with a clear reason so Runners UI keeps today's plain `"Needs a Cairn update"` / manual-update hint and never enters a crash or no-op loop.
4. **Backward-compatible wire & manifest isolation**:
   - `desktop-latest.json` (`z.strictObject`) stays untouched; Runner archives (`cairn-runner-<ver>-<platform>-<arch>.*`) publish alongside a separate `runner-latest.json` manifest.
   - Bare `GET /api/server/version` keeps its exact v1 strict schema for older desktop clients; `?schema=2` opts into `{ latestRelease, rollbackNotice }`.
   - `DAEMON_VERSION` (`0.2.3`) stays untouched for existing CLI/MCP protocol gates; Runner release tracking uses a new `runnerReleaseVersion` field baked by `apps/daemon/build.mjs`.
