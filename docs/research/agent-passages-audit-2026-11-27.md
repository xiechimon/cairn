# Agent Passages Audit Across All 55 Features (2026-11-27)

## Executive Summary

This audit evaluates every feature row in `.claude/skills/verify-cairn/feature-map.json` (55 features total) across three operational verification axes required for end-to-end agent autonomy and production reliability:

1. **Local live stack passage**: real Hono + SQLite server and Vite web app (without `?scenario=` or `page.route` network stubs), tracked via `.claude/skills/verify-cairn/vp-registry.json`.
2. **Production Mac mini check**: deployed SHA alignment (`~/cairn-server/DEPLOYED_SHA`, `~/.cairn-server/server/deploy.json`, `GET /api/server/deploy`, `GET /api/server/version`, runner checkout HEAD), live runner health, read-only SQLite state (`server.db`), and non-destructive user-journey verification over SSH (`macmini`).
3. **Failure visibility**: whether a failure produces deterministic, machine-readable diagnostics across HTTP APIs, SQLite rows, server/runner logs, and OpenTelemetry / Langfuse v4 traces (`docs/ops/langfuse.md`, `otlpTraceIdOfTurn`, `otlpTraceIdOfBuild`).

### Inventory Counts (Observed 2026-11-27)

- **`feature-map.json` rows**: **55** features (`45 shipped`, `8 partial`, `2 planned`; centrality: `20` C1, `10` C2, `23` C3, `2` C4).
- **`vp-registry.json` inventory**: **66** registered feature keys, **108** total cases (**50 `current`**, **57 `stale`**, **1 `host-bound`**).

  - **17 `current`** (features with at least one `current` live-stack case; 8 of those also carry additional `stale` cases).

  - **1 `host-bound` + `stale`** (`harness-dispatch`, via `local-daemon-executor`).
  - **32 `none`** (no direct `vp-registry.json` entry or linked recipe). Of those 32, 11 have partial overlap with unlinked `vp-registry.json` keys (for example `chief-unread`, `paper-sidebar`, `schedules-dialog`, `machine-binding`, `machine-concurrency`, `machine-stale-sweep`, `project-identity`, `ansi-error-display`, `failed-run-error`, `thinking-delta`, `pi-convergence`, `glass-journeys`), while **21+ features have zero live-stack `vp-registry.json` coverage anywhere**.

Even e2e specs without `?scenario=` (such as `apps/web/e2e/chief-home-chat.spec.ts` and `apps/web/e2e/detail-continue-thread.spec.ts`) stub backend HTTP and SSE traffic in Playwright, so they verify UI rendering and client contracts rather than real server SQLite state, daemon claims, or tool assembly.

## Top Blocking Gaps Closed in This Change

### 1. Coordinator Tool Drop and Disconnected Local Mac Runner After Runner Restart

- **Symptom and root cause**: In `apps/server/src/coordinator/index.ts` and `apps/server/src/services/machine-claim.ts`, Coordinator remote tools are assembled dynamically per turn via `coordinatorToolDefs(...)` (`apps/server/src/services/coordinator-tool-defs.ts`) plus `ownComputerOffered(...)` (`apps/server/src/services/own-computer.ts`), `teamOffersDesktop(...)`, `browserOfferFor(...)`, `offeredPhoneNames(...)`, and `connectorToolDefsForTeam(...)`. `ownComputerTarget(...)` requires a `local` machine row with `capabilities.ownComputer` / `capabilities.ownComputerShell`, an active `machineHub` WebSocket connection (`deps.machineHub.isConnected(row.id)`), and granted macOS Accessibility permissions. Previously, no HTTP endpoint or health probe surfaced whether `CORE_COORDINATOR_TOOLS` were assembled or whether the local Mac runner stayed connected and ready after a runner or server restart.
- **Deploy blind spot**: `scripts/ops/deploy-watch.sh` and `scripts/ops/deploy-self.sh` verify `GET /api/server/deploy` / `/api/server/version` and launchd job state (`launchctl print`), which can all return green even when `machineHub` lacks a connected local runner, Accessibility permission is missing, or Coordinator tool assembly drops tools.
- **Closure**: Closed by `GET /api/teams/:id/chief/diagnostics` (backed by `coordinator-diagnostics.ts` sharing `resolveCoordinatorRemoteTools` across both `apps/server/src/coordinator/index.ts` and `apps/server/src/services/machine-claim.ts`) and asserted by `agent-passage.mjs health` (`coreToolsPresent === true`, `hubConnected === true`, and `ownComputerReady === true` when a local Mac exists).

### 2. Top 3 Core Journeys Not Chained in One Command Across Local Live Stack and Production Mac Mini

- **Gap**: The primary user loop (`create a task from Coordinator` -> `task runs on chosen computer` -> `task result back in chat`) spanned separate unit tests, fixture e2e specs, and stale ADR-0019 `vp-registry.json` scripts (`chief-dispatch-judgment`, `chief-segments`, `stop-button`, `review-modal`). `scripts/ops/eval-daily.mjs` exercises batch LLM evals (`eval/run.ts`) on a dedicated checkout rather than fast non-destructive passage checks against the local live stack or production Mac mini.
- **Closure**: Closed by `agent-passage.mjs top-journeys` (chaining `health` -> `coordinator-task` -> `computer-run` -> `chat-result`, writing redacted `result.json`, cleaning up synthetic probe artifacts, and auto-running `diagnose` on failure) and registered under `vp.mjs drive agent-passages` (`health` and `top-journeys` cases via `drive-agent-passages.mjs`).

### 3. Post-Landing Production Verification Missing from `AGENTS.md`

- **Gap**: `AGENTS.md` `## Ship` stopped after `push-queue.mjs` landing on `main`, `ci` diffing, and worktree cleanup. Nothing in the ship contract required verifying that production Mac mini deployed the landed SHA or passed `agent-passage.mjs health` / `top-journeys` after deploy.
- **Closure**: Closed by adding post-landing production verification rules to `AGENTS.md` `## Ship`.

## Infrastructure Baseline Across the Three Axes

- **Local live stack (`.claude/skills/verify-cairn/SKILL.md`)**: `vp.mjs launch` starts an isolated server (`8791`) and Vite dev proxy (`5273`) with a fresh scratch `CAIRN_HOME` and SQLite DB. Over half of `vp-registry.json` (`57/108`) is marked `stale` because ADR 0019 made `machineId` required on `POST /api/teams/:id/agents` or because legacy CSS selectors (`.board-topbar-title`, `.profile-hint`, `.ui-checkbox`) were removed.
- **Production Mac mini (`scripts/ops/deploy-watch.sh`, `scripts/ops/deploy-self.sh`, `apps/server/src/routes-core.ts`)**: `deploy-watch.sh` polls `origin/main` for green `check`, `pack-smoke`, and `e2e-gate` and invokes `deploy-self.sh`. `GET /api/server/deploy` (`apps/server/src/services/deploy-status.ts`) reads `deploy.json`, and `GET /api/server/version` (`apps/server/src/services/server-version.ts`) reports version, commit, `busy` (`chiefThread.activeRun` or `claimed` step), and host updater status. Neither endpoint inspects `machineHub` connectivity, runner checkout SHA parity, Coordinator tool availability, or end-to-end task execution.
- **Failure visibility (`docs/ops/langfuse.md`, `apps/server/src/routes-chief.ts`)**: SQLite remains the source of truth (`step`, `build`, `todo`, `chief_thread`, `chief_message`, `coordinator_input`, `machine`, `action_proposal`). Self-hosted Langfuse v4 (`events_only`) receives OTLP traces keyed by `otlpTraceIdOfTurn(stepId)` and `otlpTraceIdOfBuild(buildId)` via `GET /api/public/v2/observations?traceId=<id>&fields=core,basic,metadata,usage,model`. Without a unified `diagnose` / diagnostics endpoint, correlating a stalled task or tool drop required manual SQLite queries plus log tailing and manual trace ID hashing.
