## 2. Google rules on scaled and AI-generated content (exact text)

From [Spam policies](https://developers.google.com/search/docs/essentials/spam-policies) (measured):

> "Scaled content abuse is when many pages are generated for the primary purpose of manipulating search rankings and not helping users. This abusive practice is typically focused on creating large amounts of unoriginal content that provides little to no value to users, no matter how it's created."

Examples:
- "Using generative AI tools or other similar tools to generate many pages without adding value for users"
- "Scraping feeds, search results, or other content to generate many pages (including through automated transformations like synonymizing, translating, or other obfuscation techniques)"
- "Stitching or combining content from different web pages without adding value"
- "Creating multiple sites with the intent of hiding the scaled nature of the content"
- "Creating many pages where the content makes little or no sense to a reader but contains search keywords"
- And: "If you're hosting such content on your site, exclude it from Search."

**Doorway abuse** is pages "created to rank for specific, similar search queries" that lead users to intermediate pages less useful than the final destination. Per-persona or per-phrasing variants of one answer are the textbook case.

The March 2024 policy announcement says scaled production is abusive "if done for the purpose of manipulating search rankings," whether by AI or by people. [Google blog](https://developers.google.com/search/blog/2024/03/core-update-spam-policies)

[Using generative AI content](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content): AI is fine "when researching a topic, and to add structure to original content." "Manually factcheck and review all AI-generated content for accuracy… before publishing." The same review applies to titles, meta descriptions, structured data and alt text. Disclosing how content was made "can help give your readers more context."

[Helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) warning signs: "Are you using extensive automation to produce content on many topics?", "mainly summarizing what others have to say", "primarily made to attract visits from search engines". It asks for a who/how/why: real authorship, no "fabricated creator profiles", and disclosure of automation.

**Design rules derived from these (inferred):**
1. **One page per distinct question that has a distinct answer.** A new page needs a different answer, not a different phrasing. Phrasing variants become FAQ entries or headings on the canonical page.
2. Every page carries Cairn-specific facts that no other site has: real commands, real screenshots, config keys, error strings from `apps/`, measured timings, linked GitHub issues. A page whose answer could have been written without the repo is not published.
3. Persona pages exist only when the steps or the recommendation actually differ, for example Claude Code subscriber vs API-key user vs Windows runner. Otherwise use one page with sections.
4. Every page goes through a fact-check gate: commands run, links resolve, claims trace to repo source. A visible note "Written with AI assistance from the Cairn source, checked on <date> against v<version>" covers the how/why.
5. Do not translate pages into Chinese mechanically. Write Chinese pages from Chinese-community questions (V2EX, Zhihu, Juejin). The policy names translation as an obfuscation technique when it adds no value.
6. Publish in batches you can review, and do not stand up a second site to hide the scale.

## 5. Closed-loop design for cairn.xmon.me

### 5.1 Pain-point intake (weekly)
Sources, all through public APIs or the agent-reach channels:
- GitHub issues and discussions on `xiechimon/cairn` and on adjacent repos (issues in Claude Code, Codex CLI, Gemini CLI, Conductor, Crystal, vibe-kanban and similar). Signal: titles of the form "how do I run N agents in parallel", "worktree", "approve from phone", "use my subscription".
- Reddit (r/ClaudeAI, r/ChatGPTCoding, r/LocalLLaMA, r/macapps), HN ("Ask HN" plus comments on agent-tool launches), V2EX and Zhihu for Chinese.
- Competitor comparison and alternatives pages, plus the questions the panel engines themselves suggest ("people also ask", related questions).
- Output: `questions.jsonl` rows with `question, persona, source_urls[], frequency, intent (how-to | compare | troubleshoot | what-is), cairn_answer_exists (yes/partial/no)`. Clustering merges paraphrases into one canonical question, and that merge is what prevents doorway pages.

### 5.2 Page templates (each needs owned data; inferred)
| Template | Owned data per page | Example |
|---|---|---|
| Overview / hub (per persona) | Persona-specific setup path, supported models and runners | "Cairn for Claude Code subscribers", "Cairn on a Mac mini as a 24/7 runner" |
| Q&A (one canonical question) | Direct 2-3 sentence answer first, then steps with real commands and screenshots, source links into the repo | "Can I run several Claude Code agents in parallel on one Mac?" |
| How-to (task) | Tested steps against a pinned version, an expected-output screenshot | "Approve an agent's merge from your phone" |
| Comparison (`Cairn vs X`, `X alternatives`) | A feature matrix with a date and a source link for every claim about X. Concedes where X is better | "Cairn vs Conductor", "Claude Code desktop alternatives" |
| Troubleshoot (per real error string) | Exact error text from the code or issues, cause, fix, version | "Runner shows offline after sleep" |

On-page: answer in the first paragraph; `FAQPage` / `HowTo` JSON-LD only where it matches the visible text; `lastUpdated`; internal links from hubs to leaves; one canonical URL per cluster; a version and verification date stamp.

### 5.3 Generation plus quality gate
1. A generator agent drafts from the question row and repo sources (docs, `apps/` strings, README, release notes). It must cite repo paths for every product claim.
2. Gate, in CI, failing the build:
   - **Uniqueness:** embedding similarity against every published page must be below a threshold, and if not, the draft is merged into the existing page. **Owned-fact check:** at least N repo-traceable facts or commands per page.
   - **Fact check:** each command exists in the CLI or docs; each link returns 200; claims about competitors carry a source URL and a date.
   - **Banned patterns:** no keyword-stuffed titles, no claimed features absent from source (the drafted `llms.txt` "planned" items must stay labelled planned).
   - An independent model reviews each page against the question ("Does this fully answer it? Anything false?"). The plan-gate convention of a different reviewer model applies here too.
3. A human spot-check sample before publishing (for example 10% of each batch, plus every comparison page, since those make claims about third parties).

### 5.4 Publish and submit
- Starlight builds the sitemap automatically. After each deploy, a script POSTs the changed URLs to IndexNow (key file in `site/public/`), and optionally pings the GSC sitemap.
- Keep `robots.txt` as it is (allow all).

### 5.5 Metrics loop (weekly snapshot into one table)
Per URL: GSC index state and coverage reason, impressions, clicks, average position; Bing clicks and AI citations; Cloudflare visits by referrer (AI engines vs search vs other); panel citations by engine. Global: `.dmg` downloads net of noise, stars gained, 14-day GitHub referrers. Attribution (inferred): page → AI or search referrer visit → click to GitHub or download (count outbound clicks on Cloudflare only as visits, per `OPERATIONS.md`) → weekly dmg and star deltas. The aggregate relation from page to download can only be correlated week over week. Per-page download attribution is not available without a redirect or download-link measurement. A same-site `/download` redirect that logs the landing page could do that, but it is a new measurement mechanism and needs the owner's design approval.

### 5.6 Auto-maintenance rules (decided by the agent, reviewed in a weekly diff)
| Condition (judged over ≥4 weeks, because a low-traffic site is noisy) | Action |
|---|---|
| Page cited by any panel engine, or sends AI referrers, or top-decile clicks | **Expand:** add sibling questions from the same cluster as sections or new pages, refresh screenshots, add internal links to it from hubs |
| Cluster whose pages drive downloads or stars (correlated) | **Expand the direction:** mine more questions in that cluster next intake |
| Indexed with impressions but CTR or position poor | **Rewrite:** title and first paragraph, fresher data |
| "Crawled – currently not indexed" after 6+ weeks | **Rewrite or merge** into the nearest stronger page, with a 301. Never just delete (see `OPERATIONS.md`) |
| "Discovered – not indexed" | Internal links plus an IndexNow resubmission. This is a crawl budget or authority problem, not a page problem |
| Duplicate or near-duplicate flagged by GSC, or similarity above threshold | Merge plus 301 |
| Product changed (release notes touch the feature) | **Re-verify** the page against the new version, immediately, not in the weekly batch |
| Panel shows competitors cited for a question Cairn answers | Check what the cited page has (comparison table, community thread). Improve the page, and log the gap for off-site work (README, discussions) |

### 5.7 Phased rollout
| Phase | Scope | Exit criterion |
|---|---|---|
| 0 (week 0) | Owner actions done (below). Baseline panel: 40-60 questions × 3 engines, Cairn cited 0 times today (guess, to be measured). Baseline GSC and Bing | Baseline table exists |
| 1 (weeks 1-4) | 50-100 pages: 5 persona hubs, about 40 Q&A, about 15 how-to, about 10 comparisons, about 15 troubleshoot. English first, then Chinese from Chinese-sourced questions | ≥80% indexed in GSC; zero gate failures shipped; at least 1 panel citation |

**Stop rule (inferred):** If the indexed share of new pages falls below 50%, or GSC shows a manual action, freeze generation and audit. Google is telling you the pages add no value.

### 5.8 What runs as a weekly Cairn schedule vs owner actions
Weekly Cairn schedule (a project with no extra accounts beyond the keys below):
- Intake: mine the sources, then cluster into `questions.jsonl`.
- Generate and gate the new batch, then commit through the normal landing path (preflight, then push-queue; the site deploys on landing).

4. **Payment decisions:** OpenAI, Perplexity and Anthropic API keys with billing for the panel (about $10-20 per month total, inferred). Or start with only the one already funded.

## 6. Conflicts and open questions
- "Thousands of pages per phrasing and persona" collides with Google's scaled content and doorway policies, and with the repo's own `OPERATIONS.md`. The compliant version is one page per distinct question with owned data. Inferred: Cairn has hundreds of those, not thousands, today.
- The brief says to enable Vercel Analytics. The repo records that Cloudflare was chosen and Vercel is not used. Recommendation: keep Cloudflare and add no second beacon.
- Download counts are dominated by updaters and scanners. Use net `.dmg`.
- At 6 stars, off-site mentions (Reddit, HN, awesome-lists, comparison posts by others) probably matter more for AI citations than on-site volume (guess). The loop should log those gaps but not automate posting (posting to third-party sites is an external action that needs the owner's approval).
