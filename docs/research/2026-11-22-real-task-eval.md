# Real-task end-to-end eval for Cairn: prior art and a design sketch (2026-11-22)

Question: the owner wants to know whether Cairn can handle real tasks, end to end — not whether a change regressed routing. Today's suite (`eval/`) is a change gate: 28 runtime tasks replay scripted model answers through `fauxProvider`, and 10 lane tasks (`fix-typo`, `rename-var`, …) run `devin -p` directly, never through the Coordinator. Neither arm drives the product path a user's request actually travels: Coordinator chat → plan → dispatch → code → verify → land. This document surveys how benchmarks and agent vendors evaluate real work, then sketches a daily real-task eval for Cairn.

Evidence markers: **Observed** = read first-hand in this pass (linked page, file, or command output); **Derived** = consequence of Observed; **Unverified** = not checked. `[repo]` marks facts from prior in-repo research (`docs/research/2026-11-21-eval-gate.md`, `docs/design/eval-gate.md`), where they were themselves marked Observed.

## 2. What the field converges on

1. **Task realism beats task count.** Every credible suite sources tasks from *real work artifacts* — merged PRs (SWE-bench), paid freelance jobs (SWE-Lancer), traced production sessions (CursorBench), maintainer-authored work (FrontierCode), real failures (Anthropic). 20–50 good tasks beat 500 bad ones at small scale (Anthropic; the Aider 225 were *calibrated* against 7 solvers).
2. **Contamination is managed by recency + private sourcing, not by hope.** SWE-bench-Live's moving monthly split; CursorBench mining internal sessions; FrontierCode's maintainer-authored tasks; METR's no-training requests. A task set built from *this repo's own merged issues* is as private as the repo itself and dates continuously.
3. **The environment is half the benchmark.** Verified exists because env failures were misgraded as agent failures; SWE-bench-Live's whole contribution is automated env setup (RepoLaunch); Terminal-Bench separates the verifier env from the agent env; Anthropic demands a clean env per trial (their own Claude cheated via leaked git history). For Cairn: a fresh `CAIRN_HOME` + fresh fixture clone per trial, or the trial doesn't count.
4. **Score the outcome, not the path — and keep the test hidden.** SWE-bench never shows the tests; Terminal-Bench's verifier lives outside the agent env; Anthropic: grade what was produced, not the tool-call sequence; FrontierCode's blocking criteria grade mergeability. LLM/agentic graders are the *accepted* tool for underspecified tasks (Cognition, Cursor, Anthropic all use them) — but always calibrated against humans, given an "Unknown" escape, and audited via transcripts.
5. **Publish cost and latency next to score.** Terminal-Bench prints $0.2k–$16.5k per suite; Aider prints $/run and s/case; Amp prints $0.58/task and 92s; FrontierCode plots score-vs-$/rollout. A number without its cost is unactionable.
6. **Small-N verdicts are per-case flips and repeats, never means.** 2–6pp single-run noise makes suite-mean deltas under ~3pp meaningless at any affordable N; the tools that work: repeated trials, per-task paired comparison (Cairn's gate already does this), pass^k for consistency, and human transcript review (Anthropic's step 6 — nobody trusts a score nobody read).
7. **Cadence: continuous beats ceremonial.** Factory runs daily; OpenHands runs label-triggered sizes + nightly + release; Descript keeps separate quality and regression suites; capability evals graduate into regression suites as pass rates climb.

## 3. Design sketch: a daily real-task eval for Cairn

### 3.0. Who meets this

Someone installs Cairn today, types a real request into the Coordinator ("fix the flaky retry in dispatch", "add a `--since` flag to `cairn tasks`"), and watches it plan, dispatch, code, verify and land. Today nothing measures whether that journey ends in a working result. The gate suite proves the Coordinator *routes* correctly under a scripted model; this eval proves the *product* does the work. A Cairn user gains: every day, evidence that the whole path they use works on tasks like theirs — and each new daily failure becomes a filed bug before they hit it. For the owner it turns "we built many features but don't know if Cairn can handle real tasks" into a number with a trend line, a cost, and a failure stage.

### 3.1. Scenario table

| Situation | What the user/owner sees | What the system does | Wait & cost |
|---|---|---|---|
| Daily cron (say 05:00 UTC) | GitHub step summary + `real-eval.json` artifact: per-task pass/fail, stage reached, cost, wall time | Workflow boots a scratch Cairn stack (fresh `CAIRN_HOME`, ports from `docs/ops/worktrees-and-ports.md`), clones fixture repo at the task's merge-base, drives the Coordinator over its real HTTP/chat surface with the task text, lets dispatch run the lane on SWE-2 where a free tier exists, then runs hidden checks | ~1–2 h wall; Devin subscription quota (free where the plan allows); $0 Langfuse |
| Task = merged repo issue | Task text is the issue body as filed | Result scored by the repo's own test suite + the merged PR's test files (F2P/P2P-style): run tests before patch (must fail) and after (must pass), plus existing-suite still green | Per task ~5–20 min of agent time |
| Task has no tests | Deterministic artifact checks authored at task-writing time (file exists, `pnpm build` passes, command output matches) + a short rubric scored by a judge run *outside* the agent env | Same as above; rubric criteria are concrete and checkable | Judge adds seconds |
| A task flakes | Report marks it `flaky` after k repeats disagree; never silently averaged | k=2 repeats per task per day while N≤30 (Anthropic's 20–50 guidance); flakiness itself is a metric | Doubles session spend; still cheap vs the signal |

### 3.2. Concrete shape

- **Driver**: a headless client that talks to the real Coordinator API exactly like the web UI does (same endpoints the `verify-cairn` stack exercises) — *not* `devin -p` on a fixture and *not* `fauxProvider`. The thing under test is the whole product: planning quality, dispatch eligibility, lane execution, verification, landing. Per the harness-variance paper, harness-level differences exceed model-level ones; testing the real path is the point.
- **Task set**: start ~15–30 tasks. Source A: this repo's own merged issues/PRs — real problem statements with maintainer-accepted reference diffs and tests, mined by a harvest script (issue → merge-base → merged test files become hidden checks). Source B: 2–3 small public repos with real CI where the same recipe works. Tasks live under `eval/` (already `humanQueue.evalConfig`-protected); expected outcomes never enter the agent-visible workspace.
- **Scoring**: tier 1 deterministic — repo's own tests F2P/P2P-style, build/lint/typecheck, declared artifact checks. Tier 2, only where tier 1 can't reach — a narrow rubric judged outside the agent env, criteria written so two engineers would agree (Anthropic), judge gets an "insufficient evidence" out (Cognition's evaluator-calibration lesson). No judge in v1 unless a task truly needs it; v1 tasks are chosen to be deterministically checkable.
- **Budgets**: daily run ≈ task_count × k sessions on the Devin subscription (today's `EVAL_MAX_DEVIN_RUNS` pattern applies — 30×2 = 60 sessions/day ceiling); per-task wall-clock cap; report prints sessions/tokens/cost next to every task like Aider/TB do.
- **No Langfuse**: the run's ground truth is `real-eval.json` in the CI artifacts + the step-summary table; day-over-day diffing reads artifacts through `gh api`. Langfuse can *also* receive traces where it already exists, but the eval stands alone — removes the `EVAL_ENABLED`+secrets hard dependency that today's weekly run has.
- **Anti-cheat**: tests/checks hidden from the agent env (SWE-bench, TB); fresh env per trial (Anthropic); a periodic `/fortify`-style review where a human tries to pass a task without doing the work (TB's cheat trial, adapted as an occasional manual check, not a pipeline).

The stage column is the product-first payoff: "Cairn failed at dispatch" names the user-facing component that broke, which is something no issue-resolving benchmark can tell this product.

### 3.4. What this does not try to be

Not a public leaderboard; not an LLM-judge-heavy quality score (v1 has no judge); not a gate — it informs, it doesn't block `queue/main`; not a replacement for the existing regression suite (they answer different questions: "did this change break routing" vs "can the product do real work"). And per Amp's warning, it stays a regression/consistency instrument — forward-looking product quality still needs real use.
