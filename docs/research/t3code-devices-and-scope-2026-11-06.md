# t3code machines (Environments) and settings scope: hands-on research and comparison with cairn

Date: 2026-11-06. Screenshot directory: [`t3code-devices-and-scope-2026-11-06/`](t3code-devices-and-scope-2026-11-06/).

Tag convention: **`实测`** (measured) = operated t3code by hand this time, or read the original text/source; **`推断`** (inferred) = derived from measured facts, can be rechecked; **`猜测`** (guess) = everything else.

## 0. Conclusions first

1. **The "Devices" ian mentioned is not the machines page in t3code.** t3code's Settings → Devices (phone icon) manages the iOS simulator / Android simulator (Device panel), see [02](t3code-devices-and-scope-2026-11-06/02-devices-page.jpg), [03](t3code-devices-and-scope-2026-11-06/03-devices-add-source-menu.jpg), [04](t3code-devices-and-scope-2026-11-06/04-devices-add-ssh-host.jpg). Machines are managed under **Connections → Environments** (server icon), see [07](t3code-devices-and-scope-2026-11-06/07-environment-added.jpg). So the page to compare with cairn's "Machines" page is **Environments** (plus **Sharing & access** for the local machine), not Providers and not Devices. (`实测`)
2. **t3code's scope has three layers: device-local / environment (machine) / project override.** The sentence at the top, "Applying settings for [project] on/across [environment]", appears only on server-side settings pages. Pure device-preference pages (General, Appearance, Chat, Diffs, SnapShots, Environments, Sharing & access, About) do not show it. (`实测` + source `SettingsScopeSentence.tsx:46-55`)
3. **Providers is per machine.** It only shows "on <some machine>" and has no "All environments" option (screenshot not kept: the Providers machine scope menu listing only individual machines, with no "All environments" entry). Threads, Source control, Worktrees, Scheduled tasks, Browser, Devices and Labs default to "across All environments" and write in bulk to every online machine ([21](t3code-devices-and-scope-2026-11-06/21-threads-environment-menu-all-option.jpg)). A project can override only a whitelist of 27 keys, plus the provider switches. (`实测` + source)
4. **t3code runs an agent on another machine by "each machine runs a full server, and the client connects to several at once".** Under the composer there is a "Run on" machine picker ([15](t3code-devices-and-scope-2026-11-06/15-composer-run-on-machine-picker.jpg)). Once a thread is created it is pinned to that machine; when the machine is offline only a reconnecting banner is shown, and the thread is not moved to another machine (screenshot not kept: an existing thread whose machine is offline, showing only the reconnecting banner). cairn's structure is a central server plus daemons claiming work; when the preferred machine is unavailable, the task automatically overflows to other machines. The two models differ. (`实测` + source)
5. **#3196 needs a change of comparison target and of several state displays, not a rewrite.** The machines page should be compared with Environments' single-column rows, with Routes/Permissions expanding inside the row, instead of the left-right two-pane layout from Providers. Offline rows must state the reason and retry information. Machines with the same name must be distinguishable. The "scope" selector becomes the t3-style sentence form. The project axis does not currently exist on the cairn server; that item goes to ian to decide. See §5. (`推断`)

## 3. t3code's scope model

### 3.1 Three storage layers

| Layer | Where stored | Examples | Evidence |
|---|---|---|---|
| Device-local (client) | Local to the browser / desktop app, `ClientSettingsSchema` | Appearance, confirmation dialogs, notifications, load-balancing preference ("Preferences are saved separately in each client") | `实测` [27](t3code-devices-and-scope-2026-11-06/27-general-device-only-no-scope.jpg); source `packages/contracts/src/settings.ts:375`; doc `remote-access.md` "Balance new threads" |
| Environment (machine / server) | That machine's `userdata/settings.json` (`ServerSettings`) | Provider instances (binary path, CODEX_HOME, accounts), default model, permissions, workspace, snooze, worktree location | `实测`: read the `settings.json` of sandboxes A and B; source `settings.ts:1227` |
| Project override | The same `settings.json`, `projectSettingsOverrides[<projectId on that machine>]` | Whitelist of 27 keys: `defaultModelSelection`, `defaultRuntimeMode`, `defaultThreadEnvMode`, worktree, branch naming, PR merge method, `enableAgentBrowserAccess`, `enableAgentDeviceAccess`, etc.; plus `providerInstances.*.enabled` | Source `settings.ts:1067-1095` (`PROJECT_SCOPED_SERVER_SETTING_KEYS`), `1098-1136`; measured, see below |
| Repository file | `t3.json` in the repository | Project scripts, workspace, etc. | Source `packages/shared/src/projectSettings.ts:19` (source = environment / project / t3.json); UI text "Projects and their t3.json can override it" ([20](t3code-devices-and-scope-2026-11-06/20-threads-all-scope.jpg)) |

Value precedence is project override → t3.json → environment → built-in default (source `projectSettings.ts:97-151`; UI hints "Inherited from environment", "Overridden for this project", "Built-in default · 2 project overrides", [23](t3code-devices-and-scope-2026-11-06/23-inherited-from-environment-tooltip.png), [24](t3code-devices-and-scope-2026-11-06/24-overridden-for-this-project.jpg), [26](t3code-devices-and-scope-2026-11-06/26-all-scope-shows-2-project-overrides.png)). (`实测`)

**How a "project" spans machines:** repositories with the same git remote on two machines are merged into one logical project (`example/walk-shared`, [14](t3code-devices-and-scope-2026-11-06/14-project-picker-shared-repo-grouped.jpg)). Under "All environments", changing this project's Permissions to Supervised wrote one `projectSettingsOverrides[local projectId].defaultRuntimeMode = "approval-required"` into each of A's and B's `settings.json`, so the All view shows "2 project overrides". This override then really took effect when a new thread was created on B: running `pwd` first raised an approval prompt ([35](t3code-devices-and-scope-2026-11-06/35-thread-on-b-project-override-asks-approval.jpg)). Grouping-key source: `packages/client-runtime/src/state/projectGrouping.ts:129-164`. (`实测`)

### 3.2 Behavior of the scope sentence

- Component: `apps/web/src/components/settings/SettingsScopeSentence.tsx`. - When an offline machine is selected, the per-machine page is replaced entirely by "Reconnect omarchy to change its settings." ## 4. Running an agent on another machine: t3code vs cairn

### 4.1 t3code (`实测`)

1. **Connect a machine**: Environments → Add environment → fill in host and pairing code ([06](t3code-devices-and-scope-2026-11-06/06-add-environment-dialog.jpg)). Once added it appears in the list; the row shows the address, Connected, Routes, Permissions, plus an enable switch and a ⋯ menu ([07](t3code-devices-and-scope-2026-11-06/07-environment-added.jpg), [08](t3code-devices-and-scope-2026-11-06/08-environment-row-menu.jpg)). Routes lists this machine's several reachable addresses, which can be reordered by dragging ([09](t3code-devices-and-scope-2026-11-06/09-environment-routes.jpg)). Permissions are the 16 permissions the current connection has on that machine ([10](t3code-devices-and-scope-2026-11-06/10-environment-permissions.jpg)).
2. **Choose a machine**: for a new thread, the first chip under the composer is the machine. When the project is on only one machine the chip is grey and not clickable ([13](t3code-devices-and-scope-2026-11-06/13-machine-chip-disabled-single-machine-project.jpg)); when the project has checkouts on several machines it opens the "Run on" list ([15](t3code-devices-and-scope-2026-11-06/15-composer-run-on-machine-picker.jpg)). With Load balancing on, the machine is chosen automatically by idle CPU and memory multiplied by the machine preference, with four preference levels Normal / Prefer / Less often / Manual only ([11](t3code-devices-and-scope-2026-11-06/11-load-balancing.jpg), doc `remote-access.md`).
3. **Run**: the thread executes on B. `pwd` printed a path in the sandbox's scratch directory for the B project; the URL is `/<environmentId>/<threadId>`; the sidebar card's hover tooltip lists project, machine, branch and model (screenshot not kept: the sidebar thread card tooltip showing project, machine, branch and model for a thread that ran on B).
4. **Offline**:
   - The Environments row turns red: "T3 Code on omarchy did not answer · retrying in 7s · attempt 3 · Details" ([30](t3code-devices-and-scope-2026-11-06/30-environment-offline-row.jpg));
   - An amber banner "omarchy is reconnecting" appears under the draft ([33](t3code-devices-and-scope-2026-11-06/33-composer-offline-machine-banner.jpg));
   - An existing thread stays on its original machine and shows only the same banner; it is not moved to another machine (screenshot not kept: an existing thread whose machine is offline; doc says "Existing threads stay where they started").
5. **Machines delegating to each other (Beta, not measured)**: Labs → Linked environments ([38](t3code-devices-and-scope-2026-11-06/38-labs-linked-environments.jpg)). With both machines opted in you can run `t3 environment link`, and then an agent uses `delegate_task` to hand a task to the other machine, where it runs as an ordinary thread; the receiving thread is labelled "From <this machine>"; access permission has five levels from read-only to full-access; a link is valid for 30 days. (doc `remote-access.md` §Link another environment; CLI `t3 environment link --help` `实测`)

### 4.2 cairn (source `实测`)

- **Structure**: one central server, with daemons on each machine that actively claim steps (`apps/server/src/services/machine-claim.ts`). t3 has the client connect to N peer servers at once, each storing its own threads and settings. (`实测` + `推断`)
- **Choosing a machine**:
  - The agent's `machineId` (owning machine);
  - The work-routing rule `routing_rule.machineId` (preferred machine per "purpose", unique per team, `schema.ts:517-541`);
  - `pinnedMachineName` on a todo (`packages/shared/src/records/prompts.ts:415-432`, written into the prompt: "the user specified that this task runs on that machine").
- **Dispatch order** (`machine-routing.ts:130-165`): first look for the machine of the previous session (when offline, a grace period `SESSION_GRACE_MS` = 5 minutes), then the preferred machine (released immediately if unavailable, or after `OVERFLOW_AFTER_MS` = 10 minutes if busy), after which any eligible machine can claim. Eligibility checks whether the runtime is enabled, the model, capabilities, the local path, Claude rate limits, login and quota (`dispatch-eligibility.ts:265-285`).
- **Comparison**:
  - cairn automatically moves a task to another machine, whereas t3 never moves an existing thread;
  - cairn's preferred machine hangs on the "purpose rule / agent", while t3's machine preference hangs on the client's "machine", plus a manual choice each time;
  - cairn has no "checkouts of the same repository on several machines": `project.localPath` is single, and a local project can only run on its owning machine (`dispatch-eligibility.ts:277`). (`实测`)
