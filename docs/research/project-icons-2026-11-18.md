# Project icons: prior art for a larger set and a name-derived default

Started: 2026-11-18. Scope: cairn's new-project dialog has an icon picker over a curated 32-name lucide list (`packages/shared/src/records/project.ts` `PROJECT_ICONS`, `apps/web/src/board/project-icon-map.ts` + `project-icon-picker.tsx`). The owner wants (a) more icons, possibly "a third-party set", and (b) a deterministic icon auto-assigned from the project name (suggested: hash). Name backfill from repo/dir already exists (`project-new-page.tsx` `backfillName`, :171-186) and is out of scope. What do comparable products do for project icons — set size, search, auto-assignment — and which mechanism fits cairn's monochrome-lucide, Chinese-UI constraints?

## Evidence boundary

Measured means read or executed during this investigation: repo files cited by `path:line`; `lucide-react@1.52.0` and `lucide-static@1.52.0` artifacts fetched from unpkg/jsdelivr and inspected (counts computed locally); the lucide repo's `icons/*.json` and `icon.schema.json` fetched from GitHub; a `git clone --depth 1` of `pingdotgg/t3code` and `boringdesigners/boring-avatars` read source-level; Linear's GraphQL SDL and the raycast/extensions `linear-icons` asset dir (227 SVGs, a third-party mirror that can lag Linear's own set); linear.app changelog, lucide.dev, iconify.design, unplugin-icons README, notion.com help/releases/API docs, support.claude.com and code.claude.com docs fetched via web tools. Inferred means derived from those observations. Guessed means not verified — Linear's and claude.ai's live pickers were not operated (no account in this session), and Notion's icon-search keyword localization is unverified.

## The pattern that fits cairn and why

Every measured product that auto-marks a project does one of two things: **generated default at creation** (Linear: server fills varied icon+color; Notion: random emoji on "Add icon") or **deterministic derive at render** (T3 monogram+color from name; GitHub identicon from user ID; boring-avatars from name). The two differ on one axis that matters for cairn: whether the mark survives a rename and a growing icon list. GitHub hashes the immutable ID for exactly this reason; boring-avatars' `hash % list.length` shows the failure mode — grow the list and every unpersisted mapping reshuffles; lucide's `toBeRemovedInVersion` aliases show the same risk on the name side.

Constraint check against cairn's gates:

- **Monochrome lucide-only** rules out @iconify runtime fetch (external API dependency + multi-style sets), unplugin-icons (no runtime enumeration for a picker, and again multi-style), and the emoji/monogram/cover modes Linear, Notion, T3 and claude.ai all ship (V3 bans emoji-as-icon, V11 bans letter tiles for projects). The universe is lucide, full stop. The question is only the *selectable* subset.
- **Chinese UI**: the known gap is English-only icon names. Measured: lucide publishes English-only names/tags (`tags.json`, `icons/*.json`); Linear is English-only end-to-end; Notion's icon set is English-named (localization unverified); T3 searches English substrings only. Nobody solves Chinese icon search — a small Chinese keyword layer would put cairn *ahead* of every measured product, and it is only maintainable over a curated set (~96 × a handful of aliases), not 1,866.
- **Deterministic auto-assign**: reuse the existing in-repo precedent — `avatarTint`'s FNV-1a (`avatar-tint.ts:5-15`) — over the trimmed project name, modulo the icon list.

Three realistic shapes:

**a. Curated-expanded set (recommend ~96) + hash→persist at creation.** Expand `PROJECT_ICONS` to a reviewed ~96 (still one style, still hand-auditable, names verifiable against lucide-static's `tags.json` keys in a test), add a web-side `PROJECT_ICON_KEYWORDS` map (English + Chinese aliases) feeding the existing `includes` filter, and derive the default server-side in `createProject` (`icon: body.icon ?? projectIconForName(name)`) so `/api/projects`, the dialog, and the chief tool all get it. Persisted → renames don't shuffle it, list growth can't remap it, no migration needed, existing projects keep `box` (owner's stated trade-off; a one-line backfill stays available). Cost: one enum expansion + keyword table upkeep.

**b. Full-lucide dynamic set + hash→persist.** T3's proven architecture: schema drops to a kebab-pattern string, picker searches `iconNames`/`tags.json`, render lazily via a one-chunk `import * as Lucide` (NOT `lucide-react/dynamic` — 2,130 modules per official docs) or `icon-nodes.json`, with a `Box` fallback for stale names. Cost: ~1.7 MB pre-gzip lazy chunk (1,866 icon modules at ~0.8 KB each plus the 250 KB barrel — measured on unpkg) or a 781 KB geometry JSON; search still English-only (the Chinese gap gets *worse* at 1,866 names); stale-name handling needed forever (aliases die on schedule, v1 already deleted brand icons); V9's "the project icon set" gate needs rewriting; 1,866 choices in an 8-col grid is a worse picker than Linear's keyworded 227.

**c. Render-derive (`icon == null → derive(name)`) without persisting.** Instantly gives every iconless project repo-wide a distinct mark; the reset button naturally lands on the derived mark. But the icon changes on rename (name is mutable — worse than T3's monogram because the mark isn't self-evidently the name), the mapping remaps on every list growth (boring-avatars caveat), and V11/L3's "no picked icon → box" rule flips repo-wide in one commit. Rejected.

**Recommendation: (a).** It delivers both asks — "more icons" via a ~3× curated expansion with Chinese keywords (strictly better search than Linear/T3 for this UI) and "hash from name" via persisted FNV-1a derive at creation — inside every existing design gate, with no new runtime dependency and no stability hazard.

## Concrete recommendation

1. **`packages/shared/src/records/project.ts`** — expand `PROJECT_ICONS` from 32 to ~96 curated names. Keep the list append-only after this lands: removal breaks stored values the way lucide aliases die, and list order is the hash domain for future derives. Add `projectIconForName(name: string): ProjectIcon` — FNV-1a over the trimmed name's code points (same hash family as `avatarTint`, `apps/web/src/lib/avatar-tint.ts:5-15`; move or mirror ~10 lines), `hash % PROJECT_ICONS.length`. Add `icon: projectIconSchema.optional()` to `createProjectBodySchema`.
2. **`apps/server/src/services/projects.ts`** — in `createProject`'s insert (~:171): `icon: input.icon ?? projectIconForName(input.name)`. Covers `POST /api/projects`, the web dialog, and `chief-tools.ts:815` `create_project` in one path.
3. **`apps/web/src/board/project-icon-map.ts`** — add components for the new names; add `PROJECT_ICON_KEYWORDS: Record<ProjectIcon, string[]>` with English + Chinese aliases (e.g. `rocket: ['rocket','launch','火箭','发射']`); a test asserting every enum entry has a component and at least one keyword, and every name exists in lucide (`lucide-static` `tags.json` is already a root dep — a vitest can read it via the lockfile-installed version, or embed the name list).
4. **`apps/web/src/board/project-icon-picker.tsx`** — filter over `name + keywords` instead of name only (fixes the Chinese-search gap; keep the 8-col grid, cap scroll height for 96).
5. **`apps/web/src/pages/project-new-page.tsx`** — pre-select `projectIconForName(name)` in the picker as the name is typed (live preview); pass `icon` in the create body and delete the post-create patch call (`:380-385`). Preview and persisted value are identical because both run the same shared fn on the submitted name.
6. **Render sites** — no change: `ProjectAvatar`/`ProjectGlyph` keep `icon → component, null → Box`; existing projects stay on box. Optionally harden `project-avatar.tsx:18` to `PROJECT_ICON_COMPONENTS[icon] ?? Box` so a stale stored name can't crash the tile (same fallback shape `sidebar-project.tsx:72` already has).
7. **Fixtures/tests** — `apps/web/src/fixtures/records.ts` if scenarios need icon coverage; picker spec asserting a Chinese query hits an icon; a `createProject` service test asserting derived icon determinism (same name → same icon) and explicit-icon precedence.

If the owner later wants the full set anyway, option (b)'s measured path is T3's: string schema + kebab regex, lazy single-chunk `import * as Lucide`, `Lucide.icons` membership check for stale names, `tags.json` for search — and a stated reason for each, since every one of those steps buys real cost for icons the monochrome rule will never style differently.

## Landed decision (2026-11-18)

Shipped as **(a) curated-96 + zh keywords** for the set, but **render-derive** — the file's option (c) — for the default, not persist-at-create: `icon ?? projectIconForName(name)` resolves at every render site (`projectIconOrAuto` in `packages/shared`). Rationale: the requested behavior is "the icon follows the name" — persist-at-create can't follow a rename without an extra auto/picked flag (a persisted-state design); derive covers existing iconless projects at once, keeps `icon: null` meaning "automatic" (reset lands on the derived mark), and needs no server or schema change. Remap-on-list-growth is pinned by `apps/web/test/project-icons.test.ts` (name→icon pairs) so a reorder or append becomes a deliberate, test-visible event.
