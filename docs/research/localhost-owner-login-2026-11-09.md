# Letting the owner's own browser in on the same machine (2026-11-09)

> **Question.** How do self-hosted, single-owner web apps let the owner's browser on the same machine (localhost) in without a pasted credential, and how do they defend against (a) DNS rebinding, (b) cross-site requests from any website to localhost (CSRF, WebSocket hijacking, Chrome Private/Local Network Access), (c) other local users and processes on a shared machine, (d) a reverse proxy or tunnel on the same host (nginx, caddy, cloudflared, ngrok, `ssh -R`) laundering remote traffic into loopback? Also: on cairn's host, a same-host `curl https://<node>.ts.net/api/teams` returns 200 through `tailscale serve`. Can any local uid do that, and can the backend tell the request came from the machine itself?

## 3. Tailscale serve and traffic from the serving machine itself (v1.104.2)

**Q1. Does serve add `Tailscale-User-Login` when a local process connects to the node's own 100.x address? Yes, for an untagged node.** `实测` (code) plus the host observation in the question.

1. In kernel-TUN mode, serve opens a host-level listener on each node address and port, documented as existing "purely for connections from the machine itself, as that goes via the kernel". It sets `SrcAddr = conn.RemoteAddr()`. [`ipn/ipnlocal/serve.go:107-167`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L107-L167). On Linux the listener is bound to `tailscale0` with `SO_BINDTODEVICE`, and the comment states that "connections to the node's Tailscale IP from the local host are delivered via the tunnel interface". [`peerapi_linux.go:19-50`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/peerapi_linux.go#L19-L50). On the server host, `ss` shows tailscaled listening on `<self-v4>%tailscale0:443` and `[<self-v6>]%tailscale0:443`. `实测`
2. A same-host client connecting to the node's own address gets the node's own address as its source IP. That is the Linux local-delivery default, so `SrcAddr` is the node's own 100.x address. `推断`
3. `addTailscaleIdentityHeaders` deletes `Tailscale-User-Login/-Name/-Profile-Pic`, `Tailscale-Funnel-Request` and `Tailscale-Headers-Info`. It then calls `b.WhoIs("tcp", c.SrcAddr)`, returns early only on a WhoIs miss or a tagged node, and otherwise sets login, name, picture and the headers-info URL. [`serve.go:1098-1127`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L1098-L1127). The comment `// traffic from outside of Tailnet (funneled or local machine)` at line 1116 does not match the lookup below. `推断`
4. `LocalBackend.WhoIs` resolves the address through `nodeByAddr` ([`local.go:1734-1793`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/local.go#L1734-L1793)). `updateNodeByAddrLocked` adds **`nm.SelfNode`'s addresses first**, then the peers' ([`node_backend.go:712-734`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/node_backend.go#L712-L734)). `nodeByIDLocked` returns the self node ([`node_backend.go:307-317`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/node_backend.go#L307-L317)). So WhoIs of the node's own IP succeeds, and the user is the node owner. `实测`
5. On the host, `tailscale whois <own IPv4>` returns the self node, `Tags: null`, and a non-empty login. `实测`. The client web UI's `errTaggedLocalSource` (`client/web/auth.go:79,120-121`) shows Tailscale itself treats "a local source is the same node" as an expected WhoIs result. `实测`

**Q2. Can any local uid do it? Yes.** Nothing on this path looks at the local caller. The listener is plain TCP on `tailscale0`, which any uid can connect to; serve terminates TLS with the node certificate; the identity is derived only from the source IP. The cairn socket's 0600 mode does not help, because tailscaled (root) is the peer that connects to it. Any uid that can run `curl https://<node>.ts.net/...` is admitted as the owner, with the same-origin rule applying only to non-read methods. `推断` from steps 1-4.

**Q3. Does serve forward the source address to the backend, including Unix-socket targets?** `实测`

- `addProxyForwardedHeaders` runs for every proxied request, Unix socket included (`Rewrite` calls it at [`serve.go:997`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L976-L1003)). It **sets** (replacing any client value) `X-Forwarded-Host: <In.Host>`, `X-Forwarded-Proto: https` when TLS, and **`X-Forwarded-For: <SrcAddr IP>`**. [`serve.go:1088-1096`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L1088-L1096)
- **No port is forwarded.** There is no `X-Forwarded-Port`, no `Forwarded`, and no other header carrying the source port. `实测` (no such strings in `serve.go`)
- For a Unix-socket target, the outbound `Host` is rewritten to `localhost` ([`serve.go:991-995`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L991-L995), URL from `http://localhost` at [`serve.go:885-903`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L885-L903)). ## 4. Patterns

All entries are `推断` from §1-§3.

1. **Nobody in the set identifies the browser by peer uid.** Every product that admits the owner's localhost browser without a typed secret does one of these:
   - **trusts loopback outright**: Syncthing's default, Ollama, Open WebUI single-user, HA `trusted_networks` with loopback, `tailscale web` login mode, Tailscale serve self-traffic;
   - **hands over a secret out of band at launch**: Jupyter's token URL and redirect file, VS Code's `?tkn=` redirect, t3code's `--bootstrap-fd` for its own renderer;
   - **uses a step-up the attacker cannot complete**: the Tailscale manage client's check mode.

   Peer uid via `SO_PEERCRED` is the norm for **Unix-socket CLIs** (Tailscale, Docker). For TCP loopback, Tailscale's netstat-to-PID approach was retired for named pipes, and peercred still leaves it unimplemented.
2. **A Host allowlist is the rebinding defence for unauthenticated loopback servers, and only for them.** It does nothing for (d): Ollama documents the Host rewrite for nginx, ngrok and cloudflared. Products with a real credential (VS Code, code-server, t3code) skip the Host check, because rebinding cannot carry the credential.
3. **The launch-time secret handoff is the common seamless path.** The launcher already runs as the owner, so it passes a secret to the browser it opens:
   - Jupyter: a redirect HTML file holding the token;
   - VS Code: a `?tkn=` URL that is turned into a cookie and stripped;
   - t3code desktop: an inherited fd plus an HMAC window token.

   The browser then holds a credential bound to the real origin, which defeats (a), (b) and (d) together. For (c), it depends on the channel: an fd or a 0600 file holds; argv or a world-readable file does not.
4. **Ambient credentials need fetch metadata.** Every product with a cookie or an IP/identity-based admit pairs it with `Sec-Fetch-Site: same-origin` or Origin == Host, and treats a missing header as not proof (OWASP, Tailscale web, t3code). `SameSite=Lax` alone is not enough on localhost, because other ports are same-site (t3code's "Cookies span ports").
5. **"Refuse identity from a proxy" is the only (d) defence that keys on the source**, and it works only when the proxy declares itself (HA's `trusted_proxies`, plus XFF from an undeclared proxy getting a 400). Raw TCP forwards (`ssh -R`, socat) are invisible to every source-based check, including peer uid when the owner runs them.
6. **Serve's identity header asserts "a device of the owner", not "the owner's browser".** For self-traffic the device is the server itself, so the assertion covers every local uid and every same-host tunnel that ends in a connection to the node's own IP. Tailscale's own manage UI does not let WhoIs alone change state; it adds check mode. Serve gives the backend exactly one bit to tell self-traffic apart: `X-Forwarded-For` equals the node's own address.

### 5.2 Behaviour

- On Linux, a request whose TCP peer is `127.0.0.1` or `::1`, whose client socket in `/proc/net/tcp{,6}` is owned by the server uid, whose `Host` is `127.0.0.1`, `localhost` or `[::1]` with the server's own port, and which carries no relay header, is the owner. This reuses the #3440 ambient-owner path: one `ownerIdentity` context value (`tailscale` with a login, or `loopback`), one fetch-metadata rule, owner-only routes allowed, paired-device Bearer tokens keep their narrower authority.
- The fetch-metadata rule now refuses `Sec-Fetch-Site` other than `same-origin` or `none` on reads as well, for both listener classes (OWASP "treat same-site conservatively", `实测`). Unsafe methods still need `same-origin` or a matching `Origin`.
- The uid is looked up once per connection. A lookup failure, an ambiguous match or a non-Linux platform fails closed to the token gate. Container mode (`CAIRN_REQUIRE_TOKEN=1`) never trusts loopback, because everything in a container shares one uid.

### 5.3 Fix carried with it

On the socket listener, tailnet identity is refused when `X-Forwarded-For` is one of the serving node's own Tailscale addresses (§3 Q3). Same-machine browsers then authenticate only through the loopback rule above, where the uid is known. The sidecar mode strips `X-Forwarded-For` and is unchanged.

### 5.5 Residual risk

A relay that the owner runs as the server uid, forwards other parties' traffic to the loopback port with a loopback `Host`, and adds no relay header (raw `ssh -R` or `socat`, a proxy that rewrites `Host`) passes owner trust on. That is the same trust same-uid processes already have through the token file; `SECURITY.md` names it.
