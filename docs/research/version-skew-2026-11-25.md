# Version Skew Across Client, Server, and Background Agent (2026-11-25)

> **Question.** Cairn runs as three independently updated parts: the Electron desktop shell (`apps/desktop`), the server plus the web UI it serves (`apps/server` + `apps/web`), and the runner daemon (`apps/daemon`). When any pair drifts apart — a new server handing steps to an old runner, a new web page calling a missing `window.cairnDesktop` method on an old shell, or remote mode blocking the shell's own updater — users hit stranded tasks, misleading prompts, or dead buttons. Why don't users hit this on Amp, and how do Amp, VS Code Remote, Cursor, hybrid Electron desktop apps (Slack, Discord, Linear), and Tailscale prevent or bound version skew?
>
> **Marks.** **`实测`**: read first-hand in this session (official docs or upstream source at a named file/commit/URL). **`推断`**: derived directly from `实测` facts and checkable. **`猜测`**: everything else (explicitly marked if any).

## 2. Detailed Notes per Reference Product

### 2.1 Why the Owner Never Sees Version Skew on Amp

- **Cloud-first execution (`Orbs`)**: On `ampcode.com` and in the Amp desktop/mobile apps, agent threads run in cloud **Orbs** managed by Amp itself ([`ampcode.com/docs/orbs`](https://ampcode.com/docs/orbs)) (`实测`). The UI, control plane, and orb runtime all belong to one release pipeline (`推断`).
- **Self-updating background runners**: When users run agents on their own hardware via `amp --no-tui`, the runner checks for new releases roughly once an hour, installs automatically (`amp.runner.autoUpdate.enabled`, default `true`), and restarts when no thread is running — capped at once every 12 hours, or once no turn is mid-flight if threads stay attached for a day ([`ampcode.com/docs/cli/runners`](https://ampcode.com/docs/cli/runners), [`ampcode.com/docs/cli/settings`](https://ampcode.com/docs/cli/settings)) (`实测`).
- **Auto-updating CLI and desktop apps**: Interactive CLI defaults to `amp.updates.mode = "auto"`, desktop apps check for updates on their own ([`ampcode.com/docs/apps/mac`](https://ampcode.com/docs/apps/mac)), and `@ampcode/sdk` enforces a minimum CLI version (`npx -y @ampcode/sdk install`) ([`ampcode.com/docs/sdk`](https://ampcode.com/docs/sdk)) (`实测`).
- **Why Cairn still differs**: Cairn allows **self-hosted / resident servers** (`apps/server` on a Mac mini, Linux box, or container) whose web bundle and DB schema advance independently of a user's laptop shell (`apps/desktop`) and standalone CLI/launchd runners (`apps/daemon`) (`实测` in Cairn `docs/design/remote-server-version.md` and `apps/desktop/src/main.ts`). Amp has no self-hosted control-plane server lagging behind a client (`实测` from `ampcode.com/docs`).

### 2.2 VS Code Remote & Cursor Remote-SSH: Commit Pinning vs. Long-Lived Servers

- **VS Code's model**: The client carries a `commit` string in `product.json` and bootstraps a matching `vscode-server` binary per commit (`~/.vscode-server/cli/servers/<Quality>-<commit>/server`) ([`code.visualstudio.com/docs/remote/faq`](https://code.visualstudio.com/docs/remote/faq), [`remoteAgentConnection.ts`](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/platform/remote/common/remoteAgentConnection.ts)) (`实测`). During WebSocket handshake, `remoteExtensionHostAgentServer.ts` strictly enforces `rendererCommit === myCommit` and otherwise returns `Client refused: version mismatch` (`实测`).
- **Why Cairn should NOT copy commit pinning for Server ↔ Desktop**: A Cairn server owns persistent SQLite state, active Coordinator turns, scheduled jobs, and multi-device browser/mobile/desktop connections (`实测` in Cairn `apps/server`). Two laptops on different app builds (or a browser tab + a desktop app) cannot each spin up their own commit-pinned server process against the same database (`推断`).
- **What Cairn SHOULD copy from Cursor**: Cursor's **two-tier minimum version policy** ([`cursor.com/help/troubleshooting/minimum-version.md`](https://cursor.com/help/troubleshooting/minimum-version.md)) separates a soft warning window (**Minimum supported version**, ~2 months) from a hard cutoff (**Minimum allowed version**, ~3 months), never deletes local state, and gives the user a clear **Update** button in both phases (`实测`).

### 2.3 Hybrid Electron Desktop Apps (Slack, Discord, Linear)

- **Two clocks in one window**: In Cairn (just like Slack, Discord, and Linear), the Chromium `BrowserWindow` loads the **server's** HTML/JS bundle (`origin`), while `apps/desktop/src/preload.ts` and `apps/desktop/src/main.ts` remain at the **desktop shell's** installed version until the user quits or idle-restarts (`实测` in `apps/desktop/src/preload.ts`, `apps/desktop/src/main.ts`, [`slack.engineering`](https://slack.engineering/building-hybrid-applications-with-electron/), [`electronjs.org/docs/latest/api/context-bridge`](https://www.electronjs.org/docs/latest/api/context-bridge)).
- **The exact Cairn failure**:
  1. When `apps/web/src/resources/antigravity-subscriptions.tsx` added `cairnDesktop.antigravity.signIn`, an older desktop shell (`< desktop-v0.1.729`) still exposed `window.cairnDesktop` without `antigravity.signIn`, causing `antigravityBridge()` to return `null` and the dialog to tell the desktop user `"在 Cairn 桌面 App 中打开这一页，即可重新登录 Antigravity。"` (`实测` in `apps/web/src/resources/antigravity-subscriptions.tsx` lines 41-46 and 227-229).
  2. In `apps/desktop/src/main.ts` line 1359, `desktop-update:install` gated on `allowLocalCredentials` (`activeConn.kind === 'local'`), while `desktop-update:state` and `desktop-update:check` remained open, rendering an `"Update to X"` button in remote mode that silently returned `undefined` (`实测` in `apps/desktop/src/main.ts` lines 1356-1361).
- **What the hybrid Electron pattern requires**:
  1. Never disable the shell's own updater in remote mode (`推断`).
  2. Expose an explicit shell version + bridge capability descriptor from `preload.ts` so the web bundle distinguishes **"browser (no shell)"** from **"old desktop shell missing capability X"** and maps the second case to **"Update Cairn"** (`推断`).

### 2.4 Tailscale: Capability Integer + Server-Driven Upgrade Hints + Idle Auto-Update

- **Capability integer instead of brittle semver parsing**: `tailcfg.CurrentCapabilityVersion` (`152` in [`tailcfg/tailcfg.go`](https://raw.githubusercontent.com/tailscale/tailscale/main/tailcfg/tailcfg.go)) is sent at handshake and map registration (`实测`). Cairn already moved in this direction on `fix-claim-gen-compat` (`0aa637eac`) by adding `capabilities.claimGeneration: true` in `packages/shared/src/records/machine-capabilities.ts` (`实测`). Generalizing this to a monotonic `runnerProtocolVersion` integer plus additive capability flags prevents protocol skew from stranding steps (`推断`).
- **Server-driven `ClientVersion` notices**: Control pushes `LatestVersion` and `UrgentSecurityUpdate` to clients (`tailcfg.ClientVersion` in `tailcfg.go`) (`实测`). Cairn's `machine-row.tsx` (`0aa637eac`) already surfaces `"需要更新 Cairn"` (`Needs a Cairn update`) when `runnerNeedsUpdate(machine.capabilities)` is true (`实测`).
- **Activity-aware auto-update**: Tailscale schedules client auto-updates around node activity and leaves immutable containers to update via redeploy (`tailscale.com/docs/features/client/update`) (`实测`). Amp's runner uses the exact same rule: wait until 0 active threads/turns, bounded by a cooldown (`ampcode.com/docs/cli/runners`) (`实测`).

## 3. Pattern That Fits Cairn

Cairn should combine **four** proven mechanisms rather than adopting strict 1:1 commit pinning:

1. **Server-Authoritative Compatibility Window with Monotonic Protocol Integers + Capability Flags (Tailscale + Cursor)**:
   - **Runner ↔ Server**: Monotonic `runnerProtocolVersion` + additive `MachineCapabilities` (`packages/shared/src/records/machine-capabilities.ts`). Inside the window, the server adapts (e.g., `claimGenerationAccepted` in `machine-claim-scope.ts`) and flags lagging runners as `Needs a Cairn update`. Outside the minimum floor, the server **refuses claims before assigning steps** so no step ever strands.
   - **Page ↔ Shell Bridge (`window.cairnDesktop`)**: `preload.ts` exports a frozen `shell` descriptor (`shellVersion`, `bridgeVersion`, `capabilities`). The web bundle distinguishes *no shell* vs. *old shell missing capability* vs. *out-of-window shell* (`MIN_SUPPORTED_BRIDGE_VERSION` warn vs. block).
2. **Symmetric Self-Updating Edges Around Idle Work (Amp + Tailscale + Electron)**:
   - **Desktop shell** updates in **both** local and remote mode via `createUpdater` + `createIdleWatch`, and never leaves a dead Update button (`apps/desktop/src/main.ts`, `apps/web/src/board/desktop-update.tsx`).
   - **Remote server** is probed by a newer desktop shell via `GET /api/server/version` and nudged via `POST /api/server/update` (`remote-version`), updating when active turns and claimed steps drop to `0`.
   - **Standalone / launchd runners** (`apps/daemon`) auto-update when idle (0 claimed steps, cooldown-capped) if managed/writable, or report `"Needs a Cairn update"` when package-managed/read-only.
3. **Single Clear Recovery Action (`"Update Cairn"`)**:
   - Whenever any pair exceeds its compatibility window or lacks a required capability, every affected surface presents one clear **"Update Cairn"** action (never a silent no-op and never `"open this page in the desktop app"` inside Electron).
