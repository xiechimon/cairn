# Prior art: upstream-done-starts-downstream and waiting-on-a-human (2026-11-09)

Date: 2026-11-09
Status: research

Question: how do Linear, GitHub Actions, Temporal, Apache Airflow and Buildkite (a) start downstream work when upstream finishes, (b) block a job on human input, and (c) handle a failed or handed-off job that nobody acts on?

Evidence labels: `Measured` = read first-hand in this session from the official doc page linked in the row (doc pages were read through a fetch tool that returns quoted extracts; Linear was fetched raw with curl); `Inferred` = derived from Measured and checkable; `Guess` = everything else. "Not documented" means the page linked was read and is silent on it.

## Pattern that fits

- Measured (GitHub, Airflow, Buildkite): the dependency is recorded structurally on the downstream unit when it is defined (`needs`, trigger rule on an edge, `depends_on`), not as a note a person reads later.
- Measured (Airflow `none` / `scheduled`, Buildkite "Wait for unblocking", GitHub "Pending"): the downstream unit exists before it can run and sits in a named, visible waiting state.
- Measured (Airflow `scheduled` is set by the scheduler) and Inferred (GitHub, Buildkite, Temporal): the system, not a person, starts the downstream once the condition holds.
- Measured (GitHub skipped, Airflow `upstream_failed`, Buildkite `waiting_failed`, Temporal Parent Close Policy): upstream failure or cancel propagates a terminal, visible state to the downstream by default; continuing anyway is an explicit opt-in on the downstream (`always()`, `all_done`, `allow_dependency_failure`, `soft_fail`).
- Measured (GitHub required reviewers, Airflow `assigned_users`, Buildkite `allowed_teams`, Temporal `pending_request_id`): human input is a first-class blocking step with a named set of allowed responders and an answer bound to that specific request.
- Measured (GitHub 30 days then fail, Airflow `response_timeout` with `defaults`, Temporal cookbook timeout result): an unanswered request ends at a defined time with a defined outcome. Buildkite documents no such timeout, and none of the five documents escalation to a second person; Linear's SLA only changes a color (Measured). Inferred: escalation, where needed, is built by the user on top of the timeout.

## Linear's relation is informational, and cairn's `blockedBy` mostly is too

Measured (Linear): a "blocked by" relation changes only the sidebar display; on resolution it "moves under Related", with no status change, assignment or notification described. Measured (cairn, read in this worktree): `todo.blockedBy` is consumed by `splitBlockersSatisfied` (`apps/server/src/services/todos.ts`), used only when dispatching split children (`apps/server/src/services/builds.ts`); by `releaseResearchBeforePlanHolds` (`apps/server/src/services/research-before-plan.ts`) for research-before-plan holds; and by `blockerHandoffForClaim` (`apps/server/src/services/blocker-handoff.ts`), which only passes blocker context to a step being claimed and does not gate the claim (Inferred from the function returning a record or null). Inferred: for every other todo, `blockedBy` behaves like Linear's relation: nothing holds the downstream in a waiting state, nothing starts it when the blocker reaches done, and a failed or cancelled blocker propagates nothing. That is the gap all four orchestrators close by putting the dependency, the waiting state and the start in the scheduler.
