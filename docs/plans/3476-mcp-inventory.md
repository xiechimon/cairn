## Proposed wire and persistence boundary

The daemon creates a fresh allowlisted object before any serialization: schema version, server-issued scan generation, server process epoch, coverageRevision and connection epoch, informational daemon scan timestamp, source kind enum, scope enum, project identifier and checkout identity for project sources, source status enum, entries with opaque comparison identity, optional owner-allowlisted display name, transport enum and enabled/configuration state. Do not spread parsed configuration into reports. Exclude command, arguments, URL (including host/path), description, env/header names and values, OAuth fields, raw filesystem paths, parser messages and stacks. A raw server name is never reported unless the owner has explicitly allowlisted that exact name on that machine. Every other entry contains only its opaque comparison identity, no raw-name field, and the fixed `name-withheld` diagnostic; the UI displays it as unnamed. Heuristic name redaction is not used: safe-looking credentials are indistinguishable from ordinary names. The approved identity contract below replaces the former heuristic proposal.

Use fixed diagnostics only: absent, unreadable, invalid, unsupported, partial, complete, revision-changed, name-withheld, identity-unavailable, confirmation-timeout, control-unavailable. A confirmed missing file within an available, safely resolved source root is an `absent` observation with zero entries and complete coverage, not an I/O error. An unavailable root, unreadable file, invalid input or symlink escape remains incomplete; ENOENT caused by an unavailable checkout or dangling symlink does not prove absence. Invalid entries make the source partial, retaining valid metadata without authorizing negative comparisons. Bound file sizes, source counts and entry counts; exceeding a bound is partial, never silently complete. Validate the exact report again at authenticated server ingress before persistence, with errors that never interpolate received data. Old daemon reports remain explicitly legacy/unknown coverage.

## Approved display-identity contract

| Decision | Status |
|---|---|
| Exact per-machine owner allowlist is the only permission to report a raw name; all other entries are opaque and unnamed | Approved by the coordinator under the owner's no-credential-disclosure requirement |
| Five-minute freshness lifetime and daemon-outbound generation control protocol | Proposed; unchanged by the identity decision |

The allowlist defaults empty and lives only in owner-managed daemon-local storage. It matches the exact decoded name, without case folding, prefix, wildcard or substring rules; it is not inferred from a known-server catalog or copied from another machine. The owner must not allowlist a credential value. The optional display name does not become the comparison key, and an allowlisted label on one machine does not authorize another daemon to send that label. Server-originated requests cannot add names, modify the local allowlist or ask a daemon to hash an arbitrary supplied name. Discovery and permission to display metadata grant no MCP or secret access. Allowlist removal suppresses future projections; it cannot promise recall of a label the owner previously authorized for disclosure.

Every entry, including an allowlisted one, uses a full HMAC-SHA-256 identifier over an unambiguous, domain-separated encoding of the protocol version, team/correlation group and exact name. Daemons in the same correlation group share the same random 256-bit inventory identity key, so equal names compare equal across machines while different names remain distinct. Do not include machine or checkout identity in the MAC input; harness, scope and checkout remain external comparison dimensions. Send only the digest and a non-secret opaque correlation-group/version identifier, never the key, raw MAC input, name prefixes or an unkeyed name hash. The server cannot compute candidate-name hashes without the key. Opaque equality is deliberate leakage, not a claim of anonymity against an allowlisted label or a compromised participating daemon.

Key custody and sharing: the first participating daemon generates the identity key locally using the operating system CSPRNG. A dedicated daemon-only privacy-key store, separate from authentication/configuration sources, protects it with owner-only permissions (0600 file in a 0700 directory) or a verified OS secret store. The key is never sent to or stored by the server, browser, database, telemetry or logs. Sharing uses owner-mediated out-of-band provisioning: the owner verifies the recipient daemon identity and approves a recipient-bound encrypted export/import between the two daemon-local stores over a trusted administrative channel. Cairn server APIs, presence, profiles, session rules and enrollment payloads never carry the key or its provisioning bundle. Do not use command arguments, shell history, repository files or printed plaintext for transfer; the owner handles the encrypted bundle, not a plaintext key. No automatic key distribution occurs on machine enrollment. Provisioning API and crypto-library selection remain implementation work behind daemon backend bridges; this document approves the custody boundary, not an unverified cryptographic implementation.

No usable key means `identity-unavailable` and incomplete comparison coverage, never a fallback to raw names, plain hashes or an automatically generated per-machine key. Rotation provisions a new shared key and group/version to all intended daemons, then requires fresh projections; incompatible correlation groups or mixed versions compare as unknown, never missing. Old identifiers remain historical and are not joined across rotations. Key revocation invalidates the affected comparison group until reprovisioning; removal of a daemon requires a new key for the remaining group. Local allowlist changes, key rotation and key loss must invalidate projection caches so old cached labels/identifiers cannot be retransmitted as current observations. The coverage-revocation amendment below specifies the lifecycle correction tracked in #3676; its mandatory tests must precede runtime implementation. Privacy-key isolation remains a separate unresolved design gap in #3711.

## Inventory freshness lifecycle

Proposed policy for review: bind each scan to the current server process epoch and a monotonically increasing generation per machine and source/checkout key. Authoritative age uses monotonic elapsed time from issuance, including system suspend, with a 300_000 ms lifetime. Store `issuedAt`, `expiresAt` and `receivedAt` as informational wall-clock timestamps, never as an eligibility predicate. At issuance also record the monotonic start; acceptance and every inventory read require elapsed age below 300_000 ms in the issuing epoch. A completed expiry is irreversible for that generation, including wall-clock rollback from after expiry back inside the displayed interval. Every server restart invalidates previous epochs and outstanding generations before serving inventory; persisted observations remain historical/unknown until rescanned. This deliberately trades restart availability for fail-closed freshness. Clock implementations must be verified on supported platforms; if suspend-aware monotonic age is unavailable, fail closed rather than use wall time.

Control path: the daemon opens the existing authenticated outbound `/api/machine/stream` SSE connection independently of task claims and worker capacity. Extend its versioned machine event schema with a metadata-only inventory-control notification, dispatched through the existing machine-targeted hub; the daemon responds through an authenticated immediate POST using its existing machine-client request machinery. These inventory event/POST fields are proposed additions, not implemented APIs. Enrollment/reconnect initiates an immediate control exchange; the existing 60_000 ms inventory poll is background reconciliation only, never a confirmation, invalidation-ACK or UI-read delivery gate. The server atomically maintains at most one outstanding generation per key. Initial or invalidated sources receive a generation in an immediate control exchange; healthy sources become renewal-due at monotonic age 240_000 ms. Polls return an existing unexpired generation unchanged, never superseding a slow scan. A manual-refresh request records one pending rescan, coalescing further manual requests without cancelling the current scan. Source changes, root removal and connection loss instead use the invalidation transition below, revoking accepted evidence as well as cancelling obsolete scan work. Acceptance, reported failure and deadline expiry retire the outstanding generation; the next immediate control exchange issues a new one if pending, renewal-due or without valid coverage. Normal completion without pending work waits for the renewal threshold. Reconnect never clears a recorded revocation; it starts a new connection epoch and requires a new scan. Server restart invalidates prior accepted observations and outstanding work before serving inventory. A disconnected or failed scan is not retried in a tight loop; stream reconnection initiates reconciliation and the ordinary poll schedule provides background recovery. Issuance and pending flags do not renew existing observations or authorize negative comparisons.

### Sticky coverage revocation

Maintain a persisted `coverageRevision` and a revoked/eligible state per machine and source/checkout key. A source-change notification, root removal/unavailability, identity-key loss/rotation, or connection loss revokes accepted coverage and retires outstanding work atomically, increments coverageRevision, and records a pending rescan where the source still exists. Connection loss applies to every source on that machine. Retain old entries only as explicitly stale history; their original lifetime cannot make them eligible again. No successful heartbeat, root reappearance, reconnect or cached report clears revocation. Only acceptance of a new complete or confirmed-absent observation under the current revision and connection epoch clears revoked state atomically with storing that observation; issuance, acknowledgement and partial/failed scans do not.

The connection epoch identifies the daemon's logical presence session, not each HTTP poll or socket. Enrollment or reconnect after a detected session loss starts a new epoch; normal requests within the session retain it. Presence-loss detection and explicit disconnect both revoke coverage before a later online transition can be visible.

The daemon sends detected invalidations through a dedicated authenticated metadata-only control message before submitting further complete observations. Until that invalidation is acknowledged, local scans cannot restore negative coverage. The server linearizes invalidation with issuance and report acceptance; a generation captures the current coverageRevision and connection epoch at issuance. Its captured revision must equal the current coverageRevision at acceptance, and its connection epoch must still be current. An invalidation during a scan retires that generation, so a delayed result from before the event is rejected even if its five-minute lifetime remains. Duplicate invalidations use the durable event identity below, not the transport session, and do not repeatedly advance the revision. The invalidation ACK is the direct POST response containing the stable event identity and its originally applied revision. It acknowledges delivery only, not current coverage. A lost ACK leaves that same event pending, without a hot retry loop.

### Replay identity and durable receipts

Each real local change creates a daemon-persisted invalidationId before its first send, together with its immutable source key and metadata. The opaque random ID contains no source contents or name. Retransmission, SSE replay, lost ACK, daemon restart and reconnect reuse that exact ID, not a new per-connection ID. sourceKey includes harness, source kind, scope and project/checkout identity where applicable, never a raw local path.

After authenticating the current machine, the server deduplicates by (machineId, sourceKey, invalidationId); connection epoch is not part of this dedup key, nor is the server process epoch. Store the receipt and revocation transition atomically, before ACK. A duplicate returns the stored receipt without advancing coverageRevision or repeating any side effect, and must not retire replacement work issued since the original event. Conflicting metadata for an existing key is rejected with the fixed `invalid` diagnostic, not treated as a new event. Durable receipts or equivalent tombstones survive reconnect and server restart for the event's entire replayable lifetime; connection timeout is not a retention boundary. Receipt retirement requires permanent retirement of the authenticated machine identity, or an equally durable no-replay proof. If retention/storage bounds cannot preserve deduplication, fail closed for new coverage rather than silently expire receipts.

An ACK never rolls the current coverageRevision backward: its originally applied revision can be older than subsequent revocations. The daemon removes only the matching persisted event from its outbox, leaving newer pending events intact. A replayed ACK does not restore coverage, change an epoch, or apply an old generation. Any replacement work accompanying an ACK is a separately evaluated view of the current outstanding generation and current revision/connection/server epochs, not part of the cached receipt. Replaying the invalidation neither cancels nor recreates that work or renews its deadline; stale previously bundled work is discarded, and reconnect reconciliation obtains the current view. Connection loss remains a separate invalidating transition; replaying an earlier local event must not repeat that transition.

Unlike durable invalidations, confirmations deliberately remain one-use and scoped to their read request, machine/source, captured coverageRevision, server epoch and connection epoch. Reconnect cancels the old challenge; no confirmation reply is replayed into a new session or read. Replacement scan results also retain generation/revision/epoch checks and cannot cross reconnect. Source/comparison cache keys stay epoch-scoped because cached evidence must not survive session loss; those keys are not deduplication identities for durable events.

Manual refresh alone does not revoke an accepted observation: it remains eligible only for its original lifetime unless a real invalidating event, failed/partial replacement or expiry intervenes. A manual request does not bump coverageRevision or extend any deadline. This preserves the normal one-in-flight rule while making safety invalidations its explicit cancellation exception. Root-unavailable state issues no successful absent-file report; root reappearance requests a fresh scan under the new revision. Concurrent source invalidation and report acceptance are serialized: acceptance first is immediately revoked by the event; invalidation first makes that old report ineligible.

All inventory reads require the non-revoked current coverageRevision and connection epoch in addition to freshness and complete coverage. Persist revocation independently of presence. Comparison and source cache keys include coverageRevision and connection epoch, and invalidation evicts dependent results in the same server transition. Publish a metadata-only invalidation event so clients discard missing/disabled conclusions and show stale/unknown while retaining historical observations separately. Reconnect/resume revalidates instead of restoring a cached conclusion. Persist each unacknowledged invalidation with its original invalidationId and sourceKey on the daemon and submit it immediately on detection. Stream reconnect or an inventory-control challenge triggers immediate replay of that same idempotent event before any confirmation; periodic reconciliation remains a fallback, not the normal ACK path. The event is not dropped on request failure or reconnect; there is no hot retry loop. While any event is pending, the daemon refuses inventory-read confirmation even if ordinary machine heartbeats continue. Merely withholding new complete uploads does not revoke old server evidence.

Every missing/disabled conclusion requires a fresh, request-bound inventory confirmation from each participating daemon, ordered with that daemon's invalidation stream and matching the accepted revision/session. The server immediately pushes a one-use confirmation challenge through the already-held machine SSE stream; the daemon handles it independently of scanning and agent workers and sends its authenticated POST response immediately; cached confirmations and prior presence pulses cannot satisfy a new read. If confirmation is unavailable, mismatched, or blocked by an unacknowledged invalidation, the read returns unknown, never an older negative conclusion while waiting. A confirmation neither changes the scan lifetime nor clears revocation; only a replacement scan can do that. The acknowledgement/confirmation path must be serialized with local change detection, so a detected change before confirmation blocks the result. Normal undetected changes after a successful observation are still bounded by its lifetime; no asynchronous design can promise to know a remote change before it becomes observable. Do not cache a reusable negative conclusion across requests or let a client resume one without revalidation.

### Immediate delivery and bounded reads

Each UI/API negative-read request has one monotonic 2_000 ms deadline from server receipt, including control dispatch, invalidation ACK processing and daemon confirmation. This is a proposed response budget, not a claim that an arbitrary network always responds within it. On a healthy held stream, delivery begins immediately and confirmation takes one push/POST round trip with no 60-second scheduling delay. The inventory handler must not wait for a task slot or a filesystem scan. Pending invalidations replay immediately when a challenge arrives; the handler confirms only after their direct ACK, within the same read deadline. If any required exchange cannot finish, return unknown with confirmation-timeout, without restoring old negative coverage or extending a scan lifetime.

Cross-machine challenges are sent in parallel under one shared deadline, not sequentially and not one timeout per machine. At the deadline retain valid per-machine results for this request and mark only unconfirmed participants unknown; an all-machine negative conclusion requires every relevant participant to confirm. No cell waits for the slowest daemon's next scheduled poll or extends the overall deadline. The UI immediately shows checking for unconfirmed cells while keeping historical observed entries visibly separate, never a cached missing/disabled conclusion. On completion show that request's results; timeout becomes unknown with a retry affordance, not an indefinite spinner. Changing selectors or closing the surface aborts outstanding requests and discards late results.

No connected/authenticated control stream means immediate unknown with control-unavailable, even if ordinary machine presence is online. Reuse the current stream abort/disconnect listeners, token checks, parser and reconnect backoff; do not add a second long-poll loop or socket. Stream loss cancels pending challenges and revokes the affected inventory connection epoch before subsequent reads; server restart also discards them. Successful reconnect performs immediate reconciliation and requires new accepted coverage before confirming negative results. Missed SSE notifications are not durable acknowledgements: reconnect reconciliation recovers pending work; a stalled but not yet detected stream is still bounded by the read deadline. Client abort, shutdown, timeout and disconnect release every waiter/timer; confirmation/work replies after a terminal state, from an older epoch, or consuming an already-used challenge are ignored. Invalidation delivery receipts instead match the stable persisted event identity and never restore coverage, so a receipt returned to an authenticated reconnect can safely acknowledge its old event. No automatic read retry or keep-alive loop is introduced.

The daemon reads each source after receiving its generation; cached metadata cannot satisfy a new generation. Server ingress atomically accepts a matching outstanding generation and epoch once, only before its monotonic deadline, then retires it. Duplicate, older, expired and prior-epoch inventory report uploads cannot replace newer observations or extend freshness; replayable invalidation receipts follow the separate stable-identity rules above. A failed/partial observation immediately revokes complete coverage, retaining previous entries only as stale history. A hung scan keeps its generation until its deadline, then becomes unknown and eligible for a new scan through the next control exchange; it cannot be starved by successive poll responses. A delayed upload never gains a fresh window on arrival. Presence, enrollment replay and cached retransmission cannot accept scans or renew deadlines; enrollment/reconnect can only request a new scan through the control path.

For every API read and negative comparison, fresh means an accepted complete or confirmed-absent observation in the current process epoch, with unexpired monotonic age, current coverageRevision/connection epoch, non-revoked coverage, no newer failure and an online machine; a negative read additionally requires its request-bound inventory confirmation. Offline, restarted, expired or unsupported-clock observations remain unknown until a new scan is accepted. Persist generation identity and history independently of machine `lastSeenAt`; do not restore negative coverage from persisted wall-clock deadlines.

The API returns server-derived freshness, an informational wall deadline and `remainingTtlMs` computed from authoritative age. The UI expires data using elapsed time from request start, conservatively including network delay, and revalidates on reconnect/resume or epoch change; local wall-clock rollback must not renew it. Any cached comparison expires at the earliest participating source lifetime and includes the epoch in its key. Read predicates enforce expiry even if sweepers, heartbeats or UI timers stop. Mandatory fake-clock tests cover exact expiry, rollback into a formerly valid interval, forward/backward wall jumps, suspend, process restart, healthy periodic renewal, duplicate polls, slow in-flight scans, pending refresh coalescing, failure/expiry recovery, delayed/prior-epoch uploads and offline/reconnect.

## Source coverage and comparison

Enumerate Claude user and embedded project entries, known local project `.mcp.json`, Codex user and trusted project TOML, and pi user/project JSON. Verify Claude and Codex paths, environment overrides, precedence and trust from primary documentation/source before tests. Do not recursively search the home directory or invent paths for projects absent from that machine. Report project-not-materialized and unsupported adapters as unknown coverage. Preserve source provenance and duplicate definitions; do not lowercase away distinct names or claim runtime-effective precedence without evidence.

Identify each project checkout by project identifier plus `base` or `conversation` kind; conversation checkouts also carry the existing Cairn conversation identifier. Bind each identity to exactly one explicitly supplied local root, keeping that mapping on the machine. The base repository and per-conversation worktrees are separate sources, never interchangeable fallbacks. Include the observed Git HEAD object identifier, or a fixed unknown-revision state, without exporting branch names, filesystem paths or configuration-content hashes. Missing or ambiguous root mappings remain unknown. Persistence and caches key project sources by machine, harness, project, checkout identity and source kind; UI selectors expose the checkout and observed revision.

Read HEAD before and after all project-source reads for one observation. Require the same known object identifier and unchanged local root binding; a changed or unreadable HEAD produces partial coverage with the fixed `revision-changed` diagnostic, not a revision-labelled complete report. Do not retry inside the scan; any later attempt requires a new generation. Detect source replacement or modification during reading through descriptor identity and metadata checks, failing partial when unstable. HEAD equality alone does not certify uncommitted-file immutability or detect an external switch-away-and-back; comparison claims observed stable metadata, not an atomic Git snapshot. Tests must move HEAD between source reads, change the root binding and mutate a source during its read, with no negative coverage from the mixed result.

Comparison key: opaque HMAC identity within the same correlation group/version and selected harness and scope; optional display names never determine equality. Unnamed entries remain comparable across machines sharing that key. Missing/unavailable keys and incompatible correlation groups make negative comparisons unknown; all required sources must have identity coverage as well as configuration coverage. Otherwise, project scope also selects the project and checkout identity, not endpoint or command equivalence. Compare base with base or the same conversation across machines, never union different checkouts. Show revision differences; unmatched checkout identities or different/unknown revisions are unknown for negative comparisons. Present observed, missing, disabled and unknown separately. Missing requires every relevant source in that comparison scope to satisfy the server-authoritative freshness predicate and complete coverage; both successfully parsed complete sources and confirmed absent sources satisfy coverage. Partial, offline, stale, legacy and unavailable-project reports cannot prove absence. Never union project-local definitions into global machine capability eligibility.

## Frontend design brief still required

Reuse existing resource rows, query boundaries and machine detail panels.
