## Proposed wire and persistence boundary

The daemon creates a fresh allowlisted object before any serialization: schema version, server-issued scan generation and server process epoch, informational daemon scan timestamp, source kind enum, scope enum, project identifier and checkout identity for project sources, source status enum, entries with opaque comparison identity, optional owner-allowlisted display name, transport enum and enabled/configuration state. Do not spread parsed configuration into reports. Exclude command, arguments, URL (including host/path), description, env/header names and values, OAuth fields, raw filesystem paths, parser messages and stacks. A raw server name is never reported unless the owner has explicitly allowlisted that exact name on that machine. Every other entry contains only its opaque comparison identity, no raw-name field, and the fixed `name-withheld` diagnostic; the UI displays it as unnamed. Heuristic name redaction is not used: safe-looking credentials are indistinguishable from ordinary names. The approved identity contract below replaces the former heuristic proposal.

Use fixed diagnostics only: absent, unreadable, invalid, unsupported, partial, complete, revision-changed, name-withheld, identity-unavailable. A confirmed missing file within an available, safely resolved source root is an `absent` observation with zero entries and complete coverage, not an I/O error. An unavailable root, unreadable file, invalid input or symlink escape remains incomplete; ENOENT caused by an unavailable checkout or dangling symlink does not prove absence. Invalid entries make the source partial, retaining valid metadata without authorizing negative comparisons. Bound file sizes, source counts and entry counts; exceeding a bound is partial, never silently complete. Validate the exact report again at authenticated server ingress before persistence, with errors that never interpolate received data. Old daemon reports remain explicitly legacy/unknown coverage.

## Approved display-identity contract

| Decision | Status |
|---|---|
| Exact per-machine owner allowlist is the only permission to report a raw name; all other entries are opaque and unnamed | Approved by the coordinator under the owner's no-credential-disclosure requirement |
| Five-minute freshness lifetime and daemon-outbound generation control protocol | Proposed; unchanged by the identity decision |

The allowlist defaults empty and lives only in owner-managed daemon-local storage. It matches the exact decoded name, without case folding, prefix, wildcard or substring rules; it is not inferred from a known-server catalog or copied from another machine. The owner must not allowlist a credential value. The optional display name does not become the comparison key, and an allowlisted label on one machine does not authorize another daemon to send that label. Server-originated requests cannot add names, modify the local allowlist or ask a daemon to hash an arbitrary supplied name. Discovery and permission to display metadata grant no MCP or secret access. Allowlist removal suppresses future projections; it cannot promise recall of a label the owner previously authorized for disclosure.

Every entry, including an allowlisted one, uses a full HMAC-SHA-256 identifier over an unambiguous, domain-separated encoding of the protocol version, team/correlation group and exact name. Daemons in the same correlation group share the same random 256-bit inventory identity key, so equal names compare equal across machines while different names remain distinct. Do not include machine or checkout identity in the MAC input; harness, scope and checkout remain external comparison dimensions. Send only the digest and a non-secret opaque correlation-group/version identifier, never the key, raw MAC input, name prefixes or an unkeyed name hash. The server cannot compute candidate-name hashes without the key. Opaque equality is deliberate leakage, not a claim of anonymity against an allowlisted label or a compromised participating daemon.

Key custody and sharing: the first participating daemon generates the identity key locally using the operating system CSPRNG. A dedicated daemon-only privacy-key store, separate from authentication/configuration sources, protects it with owner-only permissions (0600 file in a 0700 directory) or a verified OS secret store. The key is never sent to or stored by the server, browser, database, telemetry or logs. Sharing uses owner-mediated out-of-band provisioning: the owner verifies the recipient daemon identity and approves a recipient-bound encrypted export/import between the two daemon-local stores over a trusted administrative channel. Cairn server APIs, presence, profiles, session rules and enrollment payloads never carry the key or its provisioning bundle. Do not use command arguments, shell history, repository files or printed plaintext for transfer; the owner handles the encrypted bundle, not a plaintext key. No automatic key distribution occurs on machine enrollment. Provisioning API and crypto-library selection remain implementation work behind daemon backend bridges; this document approves the custody boundary, not an unverified cryptographic implementation.

No usable key means `identity-unavailable` and incomplete comparison coverage, never a fallback to raw names, plain hashes or an automatically generated per-machine key. Rotation provisions a new shared key and group/version to all intended daemons, then requires fresh projections; incompatible correlation groups or mixed versions compare as unknown, never missing. Old identifiers remain historical and are not joined across rotations. Key revocation invalidates the affected comparison group until reprovisioning; removal of a daemon requires a new key for the remaining group. Local allowlist changes, key rotation and key loss must invalidate projection caches so old cached labels/identifiers cannot be retransmitted as current observations. The implementation must address the separate accepted-coverage revocation gap tracked in #3676 before relying on these transitions.

## Inventory freshness lifecycle

Proposed policy for review: bind each scan to the current server process epoch and a monotonically increasing generation per machine and source/checkout key. Authoritative age uses monotonic elapsed time from issuance, including system suspend, with a 300_000 ms lifetime. Store `issuedAt`, `expiresAt` and `receivedAt` as informational wall-clock timestamps, never as an eligibility predicate. At issuance also record the monotonic start; acceptance and every inventory read require elapsed age below 300_000 ms in the issuing epoch. A completed expiry is irreversible for that generation, including wall-clock rollback from after expiry back inside the displayed interval. Every server restart invalidates previous epochs and outstanding generations before serving inventory; persisted observations remain historical/unknown until rescanned. This deliberately trades restart availability for fail-closed freshness. Clock implementations must be verified on supported platforms; if suspend-aware monotonic age is unavailable, fail closed rather than use wall time.

Control path: the daemon makes an authenticated outbound inventory poll on enrollment/reconnect and every 60_000 ms while connected, supplying only the known source keys. The server atomically maintains at most one outstanding generation per key. Initial or invalidated sources receive a generation on the next poll; healthy sources become renewal-due at monotonic age 240_000 ms. Polls return an existing unexpired generation unchanged, never superseding a slow scan. A source-change or manual-refresh request records one pending rescan, coalescing further requests without cancelling the current scan. Acceptance, reported failure, deadline expiry, root removal or disconnect retires the outstanding generation; the next poll issues a new one if pending, renewal-due or without valid coverage. Normal completion without pending work waits for the renewal threshold. Reconnect and server restart invalidate prior outstanding work and require new generations. A disconnected or failed scan is not retried in a tight loop; the ordinary poll schedule is the only recovery trigger. Issuance and pending flags do not renew existing observations or authorize negative comparisons.

The daemon reads each source after receiving its generation; cached metadata cannot satisfy a new generation. Server ingress atomically accepts a matching outstanding generation and epoch once, only before its monotonic deadline, then retires it. Duplicate, older, expired and prior-epoch uploads cannot replace newer observations or extend freshness. A failed/partial observation immediately revokes complete coverage, retaining previous entries only as stale history. A hung scan keeps its generation until its deadline, then becomes unknown and eligible for a new scan on the next poll; it cannot be starved by successive poll responses. A delayed upload never gains a fresh window on arrival. Presence, enrollment replay and cached retransmission cannot accept scans or renew deadlines; enrollment/reconnect can only request a new scan through the control path.

For every API read and negative comparison, fresh means an accepted complete or confirmed-absent observation in the current process epoch, with unexpired monotonic age, no newer failure and an online machine. Offline, restarted, expired or unsupported-clock observations remain unknown until a new scan is accepted. Persist generation identity and history independently of machine `lastSeenAt`; do not restore negative coverage from persisted wall-clock deadlines.

The API returns server-derived freshness, an informational wall deadline and `remainingTtlMs` computed from authoritative age. The UI expires data using elapsed time from request start, conservatively including network delay, and revalidates on reconnect/resume or epoch change; local wall-clock rollback must not renew it. Any cached comparison expires at the earliest participating source lifetime and includes the epoch in its key. Read predicates enforce expiry even if sweepers, heartbeats or UI timers stop. Mandatory fake-clock tests cover exact expiry, rollback into a formerly valid interval, forward/backward wall jumps, suspend, process restart, healthy periodic renewal, duplicate polls, slow in-flight scans, pending refresh coalescing, failure/expiry recovery, delayed/prior-epoch uploads and offline/reconnect.

## Source coverage and comparison

Enumerate Claude user and embedded project entries, known local project `.mcp.json`, Codex user and trusted project TOML, and pi user/project JSON. Verify Claude and Codex paths, environment overrides, precedence and trust from primary documentation/source before tests. Do not recursively search the home directory or invent paths for projects absent from that machine. Report project-not-materialized and unsupported adapters as unknown coverage. Preserve source provenance and duplicate definitions; do not lowercase away distinct names or claim runtime-effective precedence without evidence.

Identify each project checkout by project identifier plus `base` or `conversation` kind; conversation checkouts also carry the existing Cairn conversation identifier. Bind each identity to exactly one explicitly supplied local root, keeping that mapping on the machine. The base repository and per-conversation worktrees are separate sources, never interchangeable fallbacks. Include the observed Git HEAD object identifier, or a fixed unknown-revision state, without exporting branch names, filesystem paths or configuration-content hashes. Missing or ambiguous root mappings remain unknown. Persistence and caches key project sources by machine, harness, project, checkout identity and source kind; UI selectors expose the checkout and observed revision.

Read HEAD before and after all project-source reads for one observation. Require the same known object identifier and unchanged local root binding; a changed or unreadable HEAD produces partial coverage with the fixed `revision-changed` diagnostic, not a revision-labelled complete report. Do not retry inside the scan; any later attempt requires a new generation. Detect source replacement or modification during reading through descriptor identity and metadata checks, failing partial when unstable. HEAD equality alone does not certify uncommitted-file immutability or detect an external switch-away-and-back; comparison claims observed stable metadata, not an atomic Git snapshot. Tests must move HEAD between source reads, change the root binding and mutate a source during its read, with no negative coverage from the mixed result.

Comparison key: opaque HMAC identity within the same correlation group/version and selected harness and scope; optional display names never determine equality. Unnamed entries remain comparable across machines sharing that key. Missing/unavailable keys and incompatible correlation groups make negative comparisons unknown; all required sources must have identity coverage as well as configuration coverage. Otherwise, project scope also selects the project and checkout identity, not endpoint or command equivalence. Compare base with base or the same conversation across machines, never union different checkouts. Show revision differences; unmatched checkout identities or different/unknown revisions are unknown for negative comparisons. Present observed, missing, disabled and unknown separately. Missing requires every relevant source in that comparison scope to satisfy the server-authoritative freshness predicate and complete coverage; both successfully parsed complete sources and confirmed absent sources satisfy coverage. Partial, offline, stale, legacy and unavailable-project reports cannot prove absence. Never union project-local definitions into global machine capability eligibility.
