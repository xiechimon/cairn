## Rule for the rate limit (new failure mode F4b, beside F4 in failure-modes.txt)
F4b  sender permission read is rate limited     no import; 202 ignored, reason code `rate-limited`
     (429; 403 with x-ratelimit-remaining 0 or   (a new code, not `permission-unreadable`, so the log tells a
     retry-after; 403 whose message says rate    rate limit from a broken read); detail "github rate limited
     limit)                                      reading the permission of <login> on <repo>" plus
                                                 " (resets at <ISO>)" when GitHub gave x-ratelimit-reset or
                                                 retry-after; log line adds status and resetAt; not cached
                                                 (hasRepoTriage throws before the cache write), so the next
                                                 delivery reads again and imports once the limit is over.
Picked `rate-limited` over reusing `permission-unreadable`: the poller already logs rate limits on their own
line with the reset time, and the operator needs the same distinction on the webhook side. The `result`
stays `ignored` and the status 202, as the task asked; other errors from the read still propagate.

## Open question (not changed here)
Round 4 does not count a `ready-for-agent` label applied through a GitHub App (performed_via_github_app on
the labeled event), because under a user-to-server app token the actor is the authorizing user, so an agent
session holding the owner's authorization could feed intake its own issues. The `pacman` webhook judges the
event's `sender` only and reads no app field of the payload (githubIssuesEventSchema has none), so if a
user-to-server app token makes the authorizing user the sender, as it makes them the event actor, the label
counts. The webhook therefore applies the same permission check
and in-flight cap as the poller but not the app-label rule. Whether the webhook needs an equivalent (for
example a read of the issue's events before importing) is a decision for #1459, not part of this merge.
