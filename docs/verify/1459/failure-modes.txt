#1459 webhook `pacman` trigger: failure modes, listed before the tests
Rule (decision, issue comment 6316379513): on `issues` + `labeled` + label
`pacman`, import only when the event's `sender` has triage, write, maintain
or admin on the repository, read with the same permission read and cache the
#1406 poller uses; a failed or impossible read imports nothing and is logged;
the import counts against the per-project in-flight cap (3 open github-issue
tasks outside done and closed, the poller's count); createdBy stays the seed
user. Every refusal answers 202 with a reason (`result` plus `detail`), the
way the receiver answers every other settled event today.

Response shape used below: 202 {result, deliveryId, detail}. `ignored` is the
receiver's existing answer for "nothing to do here"; `misconfigured` is its
existing answer for "the server side is not set up" (no repo mapping, no
GitHub connection).

Not changed, recorded as a known limit: the payload's only authentication is
the URL token; a holder of that token can forge `sender`. Before this change
such a holder could import any issue with no check; the D5 check guards the
GitHub-side triggers (issue templates, outside labelers), not a leaked token.
Revoking the token (DELETE /api/teams/:id/webhook-tokens/:tid) remains the
remedy.

2026-10-22 note, round 2 review (/code-review on the round 2 diff). Added, nothing above edited.

Correction to the 2026-10-21 note on F15: the import's own 404 is not reached only through a deleted connection.
GitHub's 404 on the issue or labels read (issue missing or deleted, or not visible to the team token) arrives as the
same HttpError 404. Since b9f6d92f the webhook tells them apart by reading the team token again: token gone ->
"github connection not found" (reason no-github-connection, W16); token present -> "issue <repo>#<n> not found on
GitHub (or not visible to the team token)" (reason issue-not-found, W19). Both answer 202 misconfigured and log a
refusal line.

Correction to F19 in the same note: the generic detail keeps the permission verdict out of the answer text, but the
outcome after the permission check (created, duplicate, issue-not-found) still differs from a refusal, so a holder
of the URL token can still infer whether a login has triage. Revoking a leaked token remains the remedy.
