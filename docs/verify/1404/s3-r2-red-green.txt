F5' (revised) A verdict for a build that does not exist is stored. Pin: buildId FK -> build.id,
    insert throws. stepId deliberately has no FK (F17/F18); the step id is written by the
    server's gate code (S5a), so a verdict whose stepId has no step row is stored.
F17 A later migration recreates `step` the way drizzle-kit emits it (create __new_step, copy,
    DROP TABLE step, rename). drizzle runs every pending migration inside BEGIN/COMMIT and
    SQLite ignores PRAGMA foreign_keys=OFF inside a transaction, so DROP TABLE step's implicit
    delete fires the stepId cascade: every gate_verdict row is gone while the step rows are
    copied back, at server boot, with no error. A lost `tampered` verify verdict lets a later
    pass clear a gate that S2 treats as permanently blocked for the build.
    Pin: synthetic drizzle-shaped recreate of step after the real journal keeps every verdict
    and every step row (and the synthetic migration is shown to have run).
F18 A step is deleted while its build stays (a retry or a cleanup in a later segment): the
    cascade removes the recorded verdict, so a `block` or `tampered` stops counting.
    Pin: DELETE FROM step keeps the verdict; DELETE FROM build still removes it.
F19 A migration after the gate migration recreates `build` (or `todo`, whose delete cascades into
    build through build.todoId): the same transaction rule wipes all four gate tables.
    Pin: a database migrated through the gate migration, with a row in each gate table, keeps
    every row after the rest of the journal applies. No later migration exists at this head, so
    the test is green on both legs; s3-r2-mutations.txt shows a drizzle-shaped build or todo
    recreate turning it red and the same build recreate with the gate rows moved aside and
    written back staying green. The rule is written next to the gate tables in schema.ts.
F20 gate_verdict.expectedHeadSha nullable: a verdict without the head the server pinned at
    dispatch is stored and can never be bound. Pin: insert with null throws NOT NULL.
F21 gate_round.patchDigest nullable: SQLite UNIQUE treats NULLs as distinct, so a build could open
    any number of rounds with a null digest. Pin: insert with null throws NOT NULL.
F1' (test robustness) The upgrade test called the head's seed() on a pre-gate database; a later
    column added to user or team would break it. Now user and team are seeded with raw SQL
    (seedTeam), as seedBuild does for the other tables.

Choice for build recreates: the test, in behavioral form (F19), plus a schema comment. A text
check for DROP TABLE `build` in later migrations would miss a todo recreate, which deletes every
build through the build.todoId cascade (s3-r2-mutations.txt: it also turns F1 red because the
upgraded database loses its build row); F19 runs the real later migrations over seeded rows and
catches both. The schema comment above the gate tables says a later recreate of build or todo
must move the gate rows aside and write them back, and names F19.
