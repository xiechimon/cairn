## Follow-up findings and disposition

1. **Medium: merged read/write grants allowed wrong-kind authorization.** The original MCP face merged both grant arrays before registration. A write tool named only in `read` could therefore be exposed. [PR #2308](https://github.com/xiechimon/cairn/pull/2308), merged into this branch as `ea82eb595`, fixes this with `grantsByKind`: only the array matching `MCP_TOOL_REGISTRY.kind` counts. This revision preserves that implementation unchanged. Runtime MCP tests now also prove that `Start Thread` and `Reply Thread` in `read` neither register nor authorize their write tools.
2. **Medium: the key dialog offered both columns for every tool.** Reproduced in the web render test and two browser tests. Each registry entry now has a checkbox only in its own kind column. Individual selection, Grant all, and submitted arrays respect that kind. Grant submission lives in `api-key-grants.spec.ts`, with both API-key source paths mapped to it by `e2e:affected`; focus-ring geometry remains in its original spec.
3. **Low: unbounded Thread content.** Reproduced through the MCP SDK client for starts, Coordinator replies, work queueing, and work steering. No shared web-composer maximum was found. Both content schemas now use Zod `.max(32 * 1024)`: 32,768 JavaScript string code units, not a UTF-8 byte limit. Each path rejects 32,769 before persisting messages or turns and accepts 32,768. Identifier schemas remain separate.
4. **Low, reported: work steering bypasses archived/closed/latest-run guards.** Not reproduced on this branch. Measured source and runtime tests show that `messageTodo` reaches `sendBuildSteer`, which already checks all three conditions before delivery, just as `queueTaskMessage` does. `requireWorkConversation` also rejects a pointer to another work Thread's run. Added MCP tests reject archived and closed Threads, a mismatched run pointer, and an obsolete run ID without messages, steering signals, or new turns; the positive control steers only the current run. The legacy `message_todo` implementation is unchanged.
5. **Info: start status was hard-coded to `working`.** Reproduced with turns that settle during the start call. `start_thread` now uses the same persisted question/turn status calculation as `read_thread`; tests cover immediate `idle` and `failed` results as well as the existing `working` path.
6. **Info: non-interactive Codex approval setup was incomplete.** The setup section now includes `-c 'mcp_servers.cairn.default_tools_approval_mode="approve"'` for `codex exec`, matching the already recorded real-session evidence. Files under `real-sessions/` were not modified.
