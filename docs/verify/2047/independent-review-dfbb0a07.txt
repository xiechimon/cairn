## What it does

A rejected `git push origin refs/heads/<branch>` is no longer always an error. When the rejection text looks like a fast-forward rejection, `gitPrim.push` re-reads the requested branch (`refs/heads/<branch>`, not `HEAD`) and the `origin` address, then performs one fetch of that branch into a unique proof ref through a child-only temporary remote name whose URL is the single raw configured `remote.origin.url`. If the local tip is an ancestor of the fetched tip, the call returns normally and reports both SHAs through `onAlreadyContained`, which `WorkspaceManager.push` logs as one line. Everything else (hook rejection, auth, unrelated permanent failure, any failed proof step) keeps the original error object, so `GitPushHookError` and credential-fallback precedence survive.

## Good

- Branch identity is bound to the attempt, not to the worktree: `apps/daemon/src/git.ts:462-471` reads `refs/heads/${branch}` before the push and `apps/daemon/src/git.ts:522-523` re-checks it, so a detached `HEAD` no longer certifies unrelated work (control: `apps/daemon/test/git.test.ts:986-999`).
- Uncertainty always degrades to the original failure: every guard throws the pre-built `rejection` (`apps/daemon/src/git.ts:511`, `541`, `523`, `549`, `595`), and the error object identity is preserved, so `withGitCredentialFallback` (`apps/daemon/src/git.ts:179-181`) and `withGitNetRetries` (`apps/daemon/src/git.ts:723-731`) classify exactly as before. The new `isPushRejectedNoFastForward` (`apps/daemon/src/git.ts:144-147`) also stops pointless retries of a non-retryable rejection.
- Raw vs expanded URL is handled correctly: the pre-push `remote get-url` result (`fetchUrl`, expanded) is used only for equality comparisons (`git.ts:472-486`, `522-523`, `595`); the value passed to the child fetch is the single raw configured string (`git.ts:478-481`, `566-567`). It is passed through `GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`, never on the command line, so `insteadOf` expands exactly once (lesson `docs/lessons/2047-double-url-rewrite.md`, control `apps/daemon/test/git.test.ts:1092-1109`).
- Inherited child configuration is composed, not clobbered: `inheritedGitConfigCount({ ...process.env, ...env })` (`git.ts:543`) appends one key after the parent's validated `GIT_CONFIG_COUNT` run; when the parent is malformed it restarts at 0 and the child's own credential/terminal-prompt settings still land.
- Proof evidence is unique and non-shared: `refs/cairn/push-check/<uuid>` with `--refmap=` and `--no-write-fetch-head` (`git.ts:555-565`), so no FETCH_HEAD, no `refs/remotes/origin/*`, no persistent config. Cleanup is in a `finally` (`git.ts:583-585`) and the trace temp dir in an outer `finally` (`git.ts:598-600`); tests assert the ref namespace is empty afterwards (`git.test.ts:977-980`).
- Error precedence is explicitly tested: hook failure beats containment (`git.test.ts:938-960`), branch-gated hooks still receive `refs/heads/work` because the push names the ref (`git.test.ts:1090-1103`; the historical object-id regression is preserved in `docs/verify/2047/oid-hook-red.log`).
- Real-Git controls are genuine negative controls, not tautologies: the suite contains explicit red evidence against main (`docs/verify/2047/main-red.log`), against the original PR source (`original-seven-red.log`, `original-eight-red.log`), against the double-expansion draft (`double-rewrite-red.log`), and against the object-id draft (`oid-hook-red.log`), each mapping to one of the twelve failure modes in `docs/verify/2047/failure-modes.md`.

## Bad

- Cosmetic-only: the report line hardcodes `origin/<branch>` (`apps/daemon/src/workspace.ts:327`) although the operation is on `origin` by construction, so the wording is accurate; no finding.
- The callback is fire-and-forget logging with no return value, so a caller cannot distinguish "pushed" from "already contained" except through the log. No current caller needs more (`apps/daemon/src/workspace.ts:322-331` is the only call site), so this is acceptable rather than blocking.
- No issue found in the changed code after checking: requested-branch identity, raw/expanded URL handling, inherited config composition, proof-ref uniqueness and cleanup, FETCH_HEAD/tracking/config invariance (all three evidenced in `docs/verify/2047/proof-observation.json`), hook propagation and error precedence.

## Ugly

- The delivery decision is formulated on the rejection text (`/(?:non-fast-forward|fetch first)/`, `apps/daemon/src/git.ts:146`) rather than on exit structure. This is safe in the "fails closed" direction — a false negative just rethrows the ordinary error — but it means a localization of Git's message would silently disable the feature; the operational symptom would be the pre-#2047 behaviour, not a false success.
- Residual, unverified-by-design races are documented in the author's own review and are real: branch and address rechecks observe mutations rather than lock arbitrary external writers (`git.ts:522-523`, `595`), and the remote can advance after the proof fetch. Both can at worst turn an already-contained push back into an error, never turn a rejection into a success; the tests cover the observable part (`git.test.ts:1002-1024`, `1070-1089`). `core.hooksPath` is deliberately not overridden, so an unknown repository hook can still influence the fallback path; that is the same trust surface the push itself already has.
- `gitPrim.push` has grown into a long linear guard chain (`apps/daemon/src/git.ts:455-601`); the conditions are individually named via comments-free structure, but the function is now the densest block in the file.
- Evidence provenance: `latest-main-equivalence.json` covers five files and refers to the prior revision `4155ffa1`; `source-files.json` hashes still match the observed product files (`apps/daemon/src/git.ts` = `0386826…`, which equals `proof-observation.json`), and `url-rewrite-original-runtime.json` is explicitly the historical `f379788e` observation. The snapshot's `docs/verify/2047/review.md` records this ordering correctly, so no artifact is presented as covering a revision it does not cover.

## Tests

- Positive path: real `--no-ff` merge on top of the local commit certifies delivery and reports the actual remote tip, not the local one (`git.test.ts:901-921`, `1033-1052`; workspace-level `workspace-cred-fallback.test.ts:202-216`).
- Negative paths each isolate one failure mode: divergent advanced tip (`git.test.ts:923-936`, `workspace-cred-fallback.test.ts:218-238`), missing/narrowed fetch mapping with stale tracking state (`git.test.ts:964-985`), detached HEAD (`986-999`), hook rewinding the source ref (`1002-1024`), one and two push destinations (`1026-1043`), hook repointing `origin` (`1069-1089`), chained `insteadOf` rewrite (`1092-1109`), multiple fetch URLs (`1128-1146`).
- Acceptance of legitimate configurations is also tested, so the guards are not merely refusing everything: ordinary alias (`1111-1126`), missing fetch mapping with a genuine containing merge (`1033-1052`).
- Hook behaviour: rejected hook without retry (`938-960`, unchanged #1829), branch-gated hook input (`1090-1103`).
- Gaps, stated plainly: everything is local bare repositories plus synthetic HTTP credential controls; hosted-provider rejection wording, server-side hooks and a deployed daemon are not exercised (the observer says so itself: `providerMode` in `proof-observation.json`). The recheck races have no concurrent-writer test, by construction. `withGitNetRetries`' new short-circuit has no dedicated unit test with a synthetic rejected-push message; it is covered indirectly by the `non-fast-forward` tests, which would still pass if the retry guard were absent (it would simply retry and eventually rethrow) — a cheap missing assertion, not a correctness hole.
- The six-test workspace suite cannot pass without a commit identity, which is exactly what the follow-up fixed; `fixture-identity-red.log`/`fixture-identity-green.log` are the required negative/positive pair for that fixture change.
