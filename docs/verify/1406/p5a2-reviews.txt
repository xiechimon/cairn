Surface: services/mcp-face.ts (AGENTS.md security list: MCP auth / external
entry), services/github-reads.ts (team token use, third-party text to an LLM),
lib/github.ts, services/chief-tools.ts, shared chief-tools.ts.

Checked, no vulnerability found:
1. Tenancy. MCP: teamId comes from the API key row, tool registration is still
   grant-filtered (unchanged). Chief: teamId from the chief thread. The
   project row is selected by id AND teamId; another team's project id gets
   the same 404 as a missing one, before any token is opened or any request
   sent (tests 1, M1). Only the caller team's own connection token is used.
2. Token handling. The token goes only into the Authorization header
   (authHeaders); URLs carry none; error results are built from fixed text
   plus owner/repo, never the URL or token; an undecryptable token gives a
   fixed 409 text (SecretBoxError message not echoed). Tests assert the token
   is absent from URLs, results and errors.
3. Request forgery / path traversal. Host is fixed (api.github.com). owner and
   repo come from the project row, must pass isGithubRepoRef and must not be
   '.' or '..' (new guard: '../user' passes the shared regex and
   `repos/../user/issues` normalizes to GET /user/issues, the token owner's
   issues across all repos). Query values go through URLSearchParams
   (branch cannot add parameters); state / status are enum-checked; page /
   perPage are positive integers, perPage capped.
4. Third-party text to the model. Lists carry no issue or PR bodies; titles,
   labels, branch names, logins and workflow names are structured fields with
   format characters (bidi overrides, zero-width, tag characters) and control
   characters stripped and lengths capped (200 / 100 code points); the tool
   descriptions say they are third-party data. Titles can still contain
   natural-language instructions; that is inherent in returning titles and
   is what the data framing addresses.
5. Availability. Each read times out at 6000 ms (below the 10 s relay tool
   timeout); the daemon retries replaySafe reads only on 5xx, so one tool call
   makes at most three GitHub requests; rate limits map to 429 (no retry).
   Response pages are capped at 30 entries.
6. Regex cost. The cleaning and rate-limit regexes are single character
   classes / a literal, linear in input size.

Not fixed here (pre-existing, outside this diff; for the user):
A. shared isGithubRepoRef accepts '.' and '..' as owner or repo. A project
   with githubRepo '../user' (settable by a team member through POST
   /api/projects or by the chief through connect_repo) makes the existing
   GitHub calls built on repoPath (REST issue picker list and import, the
   source-issue echo, the #452 issue write-back, the P5a-1 intake reads) hit
   other api.github.com paths with the team token, e.g. GET /user/issues.
   Same team, same token, so no cross-tenant read, but it escapes the
   repository the project names. The read tools in this change refuse such
   rows. Fix: reject '.' / '..' segments in isGithubRepoRef (shared) so
   creation, connect_repo and every reader share one rule.
B. requireProjectRow in mcp-face.ts (create_todo) and chief-tools.ts (docs,
   create_todo, update_project, connect_repo) does not check the project's
   team; an MCP key of team A can create a todo pointing at team B's project
   id. Self-hosted installs have one team, so this is latent.
C. save_memory content is inlined into the chief system prompt every turn
   (chief.ts); if the chief saves text taken from a GitHub title, that text
   becomes system prompt. Unchanged by this diff (titles are now cleaned and
   bounded before they reach the chief).
