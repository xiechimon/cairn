Read 2026-10-21 from docs.github.com (markdown bodies via

https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json

== 1. List repository issues: GET /repos/{owner}/{repo}/issues
URL: https://docs.github.com/en/rest/issues/issues#list-repository-issues
- "GitHub's REST API considers every pull request an issue, but not every
  issue is a pull request. For this reason, "Issues" endpoints may return
  both issues and pull requests in the response. You can identify pull
  requests by the pull_request key."
  -> the intake reuses projectIssue, which drops entries with pull_request.
- labels: "A list of comma separated label names." state: default open,
  open|closed|all. sort: default created (created|updated|comments).
  direction: default desc. per_page: "The number of results per page (max
  100)", default 30. page: default 1.
- Status codes: 200, 301, 404, 422.
- Fine-grained token permission (permissions-required-for-fine-grained-
  personal-access-tokens page, "Repository permissions for Issues"):
  GET /repos/{owner}/{repo}/issues = Issues read.
  Captured header: X-Accepted-Github-Permissions: issues=read,
  X-Accepted-Oauth-Scopes: repo.
- Intake request: state=open&labels=ready-for-agent&sort=created
  &direction=asc&per_page=100. sort=created plus direction=asc is a stable
  order (best-practices page: "If you page through a list, use a stable sort
  order. Some parameters, such as sort=updated, reorder the list whenever an
  item changes"), and the first page holds the oldest issues.

== 2. Get an issue: GET /repos/{owner}/{repo}/issues/{issue_number}
URL: https://docs.github.com/en/rest/issues/issues#get-an-issue
- 301 if transferred; 404 if transferred to or deleted from a repository the
  authenticated user cannot read; 410 Gone if deleted from a repository the
  user can read. Status codes 200, 301, 304, 404, 410.
- The close reconcile reads only `state` (open|closed); 404/410/any failure
  leaves the task alone.

== 3. List issue events: GET /repos/{owner}/{repo}/issues/{issue_number}/events
URL: https://docs.github.com/en/rest/issues/events#list-issue-events
- "Lists all events for an issue." per_page max 100, default 30; page
  default 1. Status codes 200, 410.
- Labeled Issue Event fields: id, actor (Simple User, login required),
  event, created_at, performed_via_github_app, label {name, color}.
- Event types page
  https://docs.github.com/en/rest/using-the-rest-api/issue-event-types:
  labeled = "A label was added to the issue or pull request."; unlabeled =
  "A label was removed from the issue." Both are available in the issue
  events API and the timeline API. Common properties: id, node_id, url,
  actor ("The person who generated the event."), event, commit_id,
  commit_url, created_at.
- The docs state no ordering. The capture of #1450 with per_page=3 shows
  oldest first (labeled 06:18:33, unlabeled 06:20:05, auto_merge_enabled
  06:38:28 on page 1) and Link rel="next" / rel="last" to page 2. So the
  newest event is on the last page; a page with rel="next" is not the whole
  history, and the intake does not take the issue (it never trusts array
  position: newest = max created_at, ties by id).
- Pagination page
  https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api:
  "When a response is paginated, the response headers will include a link
  header. If the endpoint does not support pagination, or if all results
  fit on a single page, the link header will be omitted."
- Events vs timeline: the events API was chosen. Both carry labeled and
  unlabeled with actor; the timeline also carries comment events (with
  comment bodies) and cross-references, so it pages sooner and would bring
  issue text into the poller. Timeline also lists 400/404/410.
- Fine-grained permission: issues/{n}/events = Issues read (with an
  additional-permission mark: pull_requests read for PR events; captured
  X-Accepted-Github-Permissions: issues=read; pull_requests=read).

== 4. Get repository permissions for a user:
   GET /repos/{owner}/{repo}/collaborators/{username}/permission
URL: https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user
- "Checks the repository permission and role of a collaborator. The
  permission attribute provides the legacy base roles of admin, write, read,
  and none, where the maintain role is mapped to write and the triage role
  is mapped to read. The role_name attribute provides the name of the
  assigned role, including custom roles. ... The calculated permissions are
  the highest role assigned to the collaborator after considering all
  sources of grants, including: repo, teams, organization, and enterprise."
- Status codes: 200, 404 ("Resource not found").
- Response schema: permission (required string), role_name (required
  string), user (null or Collaborator with permissions {pull, triage, push,
  maintain, admin} and role_name).
- OpenAPI example (no example on the docs page itself):
  {"permission":"admin","role_name":"admin","user":{"login":"octocat",...}}
  -> fixture permission-admin.docs-example.json (URL fields stripped).
- Fine-grained permission: listed under "Repository permissions for
  Metadata" (read). Unlike GET .../collaborators/{username} ("The
  authenticated user must have push access to the repository to use this
  endpoint"), the permission endpoint states no push requirement.
- Intake rule (D5 "triage or above"): qualifies when role_name is one of
  triage, write, maintain, admin; or permission is write or admin (maintain
  maps to write); or user.permissions.triage is true (custom roles built on
  triage). permission=read alone does not qualify, because it covers both
  read and triage. 404 = not a collaborator (or the token cannot see the
  repo) = a definite "no", cached like any other answer for 15 minutes per
  team, repo and login. Any other failure is not cached and means "not this
  sweep".

== 5. Conditional requests and rate limits
URLs: https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests
      https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
- "Most endpoints return an etag header ... If the response has not
  changed, you will receive a 304 Not Modified response. Making a
  conditional request does not count against your primary rate limit if a
  304 response is returned and the request was made while correctly
  authorized with an Authorization header."
- "Make authenticated conditional requests, so that unchanged data does not
  count against your primary rate limit."
- "The primary rate limit for unauthenticated requests is 60 requests per
  hour." Authenticated user requests: 5,000 per hour.
- The intake never reads anonymously (no token = team skipped), sends
  If-None-Match on the list, events and issue-state reads, and treats 304
  as "unchanged, reuse the cached copy", never as "empty".

== Captures (xiechimon/pacman, 2026-10-21, through the container proxy)
The proxy authenticates GitHub API requests itself (responses carry
Github-Authentication-Token-Expiration and X-Ratelimit-Limit: 15000), so
these captures are authenticated reads, not anonymous ones.
- GET /issues?labels=ready-for-agent&state=open&per_page=2 -> 200,
  ETag "b51d4b87...", Link <...&after=<cursor>&page=2>; rel="next".
  Same request with If-None-Match: that ETag -> 304 Not Modified,
  X-Ratelimit-Used 143 before and after (the 304 did not count).
- GET /issues?labels=ready-for-agent&state=open&sort=created&direction=asc
  &per_page=100 -> 200, 9 issues (#1394 ... #1457), no PR, no Link header
  -> fixture issues-ready-for-agent.json.
- GET /issues?state=open&per_page=5 -> includes PR #1456 with a
  pull_request object -> fixture issues-open-with-pr.json.
- GET /issues/1406/events?per_page=100 -> two labeled events (enhancement,
  ready-for-agent), actor xiechimon, performed_via_github_app.slug claude
  -> fixture events-1406.json. The actor is the user even when the label
  was applied through an app.
- GET /issues/1450/events?per_page=100 -> labeled, unlabeled
  (needs-decision), auto_merge_enabled, merged, closed, head_ref_deleted
  -> fixture events-1450.json (real unlabeled shape).
- GET /issues/1445 -> 200 state closed, state_reason completed; with
  If-None-Match -> 304, X-Ratelimit-Used unchanged -> fixture
  issue-1445-closed.json.
- GET /collaborators/{xiechimon,octocat}/permission -> 403 from the proxy:
  {"message":"Access to this GitHub API path is not permitted through this
