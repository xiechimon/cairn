# Cairn desktop

An Electron shell for macOS and local Linux x64 builds. The main process starts the bundled Cairn server on Electron's own Node with `utilityProcess.fork`, bound to `127.0.0.1` on a free port with `CAIRN_HOME` under the app's `userData` directory, waits until it answers, and opens its web UI in a window. The server writes its owner token to `CAIRN_HOME/token`; the main process reads it and adds `Authorization: Bearer <token>` only to requests whose initiator is the app's own origin, so the window signs in as the owner on macOS, where the server's loopback owner check is Linux-only. `CAIRN_TOKEN` and `CAIRN_AUTH` are removed from the server's environment so the token file is always the one in use. Once the server answers, the main process enrolls this computer as the server's local Runner: it starts an enrollment and confirms it with the owner token (`/api/machine/enroll/start` and `/confirm`, the same pair the browser approval uses), writes the returned `machine.json` (mode 0600, in a 0700 directory) under `userData/runner`, and starts the bundled daemon with `cairn start --foreground --server <origin>`. The daemon runs on Electron's binary with `ELECTRON_RUN_AS_NODE=1`, so anything it starts through `process.execPath` is Node too; it is restarted up to five times if it exits, and the enrollment is repeated at every launch, which rotates the machine token. Links to other origins open in the default browser. A menu bar icon (`assets/trayTemplate*.png`, drawn from `apps/web/public/logo-mark.svg`) shows the server address and offers Open Cairn and Quit Cairn; while Keep the Screen On holds the display awake, or a scheduled run is about to start, it switches to `assets/trayAwakeTemplate*.png`, the same spiral with a cup in its lower right corner. Closing the window only hides it and the server keeps running; the Dock icon or Open Cairn brings it back. Quitting the app stops the Runner and then the server with SIGTERM and removes the icon.

## Telemetry

The server's stdout and stderr (the main process pipes them instead of inheriting them, since a Finder launch has no terminal) are written to `~/Library/Application Support/@cairn/desktop/logs/server.log`, and the main process's own `console` output to `logs/main.log`. Each file is mode `0600`, capped at 5 MB, and keeps one backup (`server.log.1`, `main.log.1`); the Runner keeps writing `runner/daemon.log` itself. Complete lines pass through a redactor that replaces the owner token and the `CAIRN_OTEL_HEADERS` values with `[redacted]` before they reach disk.

Export to an OTLP collector such as Langfuse is off unless `~/Library/Application Support/@cairn/desktop/otel.env` exists. It is dotenv text with `CAIRN_OTEL_ENDPOINT`, optional `CAIRN_OTEL_HEADERS` and optional `CAIRN_OTEL_ENVIRONMENT` (default `mac`), and must be mode `0600`; a file readable by others is ignored. The main process reads it once at launch and passes the file path to the server and the Runner as `CAIRN_OTEL_ENV_FILE`; the header secret never enters a child process environment (a same-UID session can read another process's environment block through `KERN_PROCARGS2`). Each side reads the file itself and takes only the three `CAIRN_OTEL_*` keys. Quit and reopen Cairn after editing it. Design: `docs/design/desktop-otel-export.md`; reaching the deployment's Langfuse from a Mac: `docs/ops/langfuse.md`.

The macOS package is released automatically. Linux x64 can be packaged locally as a portable archive; Linux releases and automatic updates are not provided. The research behind the stack is `docs/research/desktop-app-stack-2026-11-08.md`.

## Build

Start in a checkout with Node.js 22.19+ (22 or 24 LTS), Git and pnpm installed:

```bash
git clone https://github.com/xiechimon/cairn
cd cairn
pnpm install --frozen-lockfile --ignore-scripts
```

```bash
pnpm --filter @cairn/web build
pnpm --filter @xiechimon/cairn build
pnpm --filter @xiechimon/cairn-cli build
node apps/server/scripts/stage-web.mjs
pnpm --filter @cairn/desktop stage-server
pnpm --filter @cairn/desktop stage-runner
pnpm --filter @cairn/desktop dist:mac
```

`stage-server` copies the server's `dist`, `web`, `drizzle` and the `better-sqlite3` runtime (its Node-API prebuilds load under Electron unchanged) into `apps/desktop/server`. `stage-runner` runs `pnpm deploy --prod --ignore-scripts` for `@xiechimon/cairn-cli` with a hoisted `node_modules` into `apps/desktop/runner`, installing the platform-specific optional packages for the target `ARCH` (default: the host's), so an x64 build staged on an arm64 Mac carries x64 binaries. The daemon runs the `claude` it finds on `PATH` or in the usual install folders; when it finds none, the Claude Agent SDK falls back to its bundled `claude`, so `stage-runner` fails unless `@anthropic-ai/claude-agent-sdk-<platform>-<arch>/claude` resolves from the SDK, and the release checks the same in the packaged app with `scripts/check-runner-claude.mjs`. `dist:mac` writes arm64 and x64 DMG and zip files to `apps/desktop/release`. Without signing variables the build is ad-hoc signed (`identity: '-'`). Releases are signed by `scripts/sign-mac.cjs` with Cairn's own self-signed certificate (`signing/cairn-mac-self-signed.crt`) when `CAIRN_MAC_SIGN_IDENTITY` and `CAIRN_MAC_SIGN_KEYCHAIN` are set, with no hardened runtime and no notarization, so Gatekeeper still asks before the first launch. A fixed certificate keeps the app's designated requirement the same across releases, so macOS keeps its Accessibility and Screen Recording grants after an update; an ad-hoc requirement is the build's cdhash and loses them. `scripts/check-signature.mjs` fails a build that is not signed by the given certificate. Where the certificate and key live, and how to rotate them, is in `docs/ops/desktop-signing.md`. The DMG must be built on macOS.

The real-click command `pnpm --filter @cairn/desktop smoke` requires an isolated macOS GUI session with `CAIRN_SMOKE_ISOLATED_SESSION=1` set explicitly: it launches `release/mac-arm64/Cairn.app` with Playwright, checks that the window is on the loopback server, that `/api/teams` answers 200 without a pairing step, that no pairing gate shows, and that a `local` machine comes online within 90 seconds, saves `release/smoke.png`, then checks that closing the window hides it while the server keeps answering and that quitting stops the server and the Runner. The `desktop-mac` workflow runs the same steps on a macOS runner for changes under `apps/desktop` and uploads `Cairn-<version>-arm64.dmg` and `smoke.png` as unzipped artifacts.

The `electron` package's install script is disabled in `pnpm-workspace.yaml`, so `pnpm install` does not download Electron. To run `pnpm --filter @cairn/desktop start` locally, run `node apps/desktop/node_modules/electron/install.js` once.

### Linux x64 archive

Run the same web, server, Runner build and staging commands above, then replace `dist:mac` with:

```bash
pnpm --filter @cairn/desktop dist:linux
mkdir -p "$HOME/.local/opt/cairn"
tar -xzf apps/desktop/release/Cairn-0.0.0-linux-x64.tar.gz -C "$HOME/.local/opt/cairn" --strip-components=1
"$HOME/.local/opt/cairn/cairn"
```

The archive bundles Electron, the server and Runner, so running it does not require Node.js. It needs a graphical Linux session, bubblewrap 0.11 or newer and a working systemd user session for task confinement, as described in `docs/getting-started.md`. It chooses a free loopback port and keeps its data under `$XDG_CONFIG_HOME/@cairn/desktop` (normally `~/.config/@cairn/desktop`). Use an independent `HOME` and `XDG_CONFIG_HOME` to test without importing existing model logins or app data. This command never publishes a release. Quit Cairn to stop its server and Runner.

Extract the app outside `/tmp`, which the task sandbox deliberately hides. A source checkout and build output may still live in `/tmp`.

The bundled Runner includes pi. In **Connect models → OpenAI Codex**, follow the browser device-login prompt; no separate Codex CLI or pi install is needed. With only Codex connected on fresh data, **Confirm settings** shows GPT-6.1 Sol for Coordinator and Tasks, with pi executing tasks. Confirm, then create a local Git project and ask for a small change. See [the first-result steps](../../README.md#connect-a-model-and-get-your-first-result). Claude Code is optional and needs its own installed CLI plus a subscription token connected in Model services. Devin is downloaded only for an enabled, unexpired Devin subscription.

On Linux the app runs the Runner in its own transient systemd user service and stops that service when the Runner is turned off or the app quits. It does not fall back to an unsandboxed Runner. See `docs/design/desktop-linux-runner.md` for ownership and failure behavior.

Run `pnpm --filter @cairn/desktop smoke:linux /absolute/path/to/cairn-linux/cairn /absolute/path/to/smoke.png` to check an extracted archive. The single-process Playwright check creates a fresh HOME and app data directory, checks owner sign-in and the pi Runner's actual sandbox readiness, quits the app, checks that the server and Runner stopped, and removes its temporary data. It does not log in to a model or claim a first task result.

## Releases

`desktop-release` publishes `desktop-v0.1.<N>` to GitHub Releases — `N` is decided once per run, never taken from the run number, so a rerun can never move the latest version backwards — with arm64 and x64 DMG and zip files named `Cairn-<version>-<arch>.<ext>`. It wakes on every `ci` run completed on `main` (`workflow_run`), on a fifteen-minute `schedule` backstop — GitHub's schedule trigger is best-effort and can delay or drop ticks — and on demand from the Actions tab (`workflow_dispatch`), and only while the selected ref is `main`: a dispatch on another ref stops before `decide`. All runs share one workflow-level concurrency slot that never cancels the running build, so releases are serialized: whichever run holds the slot resolves the current `main` tip and releases that commit, while a wake that finds the slot busy waits behind it — GitHub keeps only the newest waiting run, so a later wake or dispatch replaces an earlier pending one, which loses nothing because every run resolves the tip when it starts — the schedule is a backstop for wakes GitHub drops, not a bound on the wait, so a green tip can sit out more than one interval behind an active build. When a published stable `desktop-v*` release already covers the tip the run ends; otherwise `N` is always fresh — the first `desktop-v*` name held by no tag and no release, drafts included (the deciding token holds `contents: write`, the only scope GitHub answers drafts to); a nested or suffixed name like `desktop-v0.1.2/rc1` or `desktop-v0.1.2-rc1` occupies `desktop-v0.1.2` too, because git cannot create a ref under an existing nested tag and a suffixed name already claims the version, though such names never raise the base version. The workflow never deletes a release or a tag, so an aborted publish can leave a draft holding the name it tried — an operator who wants the number back deletes the stale draft on the Releases page — and a leftover tag, draft or prerelease never blocks the next run. The same step then checks on Linux whether anything the app ships changed since the highest-version published stable `desktop-v*` release (`apps/web`, `apps/server`, `apps/daemon`, `apps/desktop`, `apps/tsnet-sidecar`, `packages/shared` and the root package and lockfile files, not counting tests, e2e specs and Markdown) and starts the macOS build only if so — the predicate is identical whatever wakes the run, so a dispatch never forces a build. The `decide` job also requires the tip's own `ci` run's latest attempt to carry green `check`/`pack-smoke`/`e2e-gate` jobs (`scripts/ops/release-gate.mjs`) — pending or red evidence just skips to the next wake — and the `live-verify` job drives the new-task journey on an isolated verify-cairn stack before `publish` may run, archiving its evidence as a workflow artifact. `publish` stages the release as a draft pinned to the decided tag and the release SHA, uploads the assets to its numeric id, then re-reads the evidence before flipping it: the `main` tip (a moved tip aborts, so an out-of-order `ci` completion can never ship older code as the latest update), whether a published stable `desktop-v*` release already covers the SHA, whether the version still sits above the highest published stable release — a superseded version aborts rather than publishing without the mark, so `latest` never moves backwards — whether `desktop-v$VERSION` is still a free tag, whether the staged draft still is a draft at the decided tag and SHA — a draft whose state, tag or target moved is abandoned, never renamed back — and last of all, right before the publish call, the exact-SHA `ci` attempt's green status, so a rerun that started during the scans still aborts. Any failed check aborts the publish and leaves the staged draft behind for an operator. Only when everything holds does one `PATCH` flip the draft published with `make_latest`, which creates the tag at the checked commit. A red `main` tip stalls releases — intended, not a bug: the fix that lands on `main` next is judged by the next wake on its own, so nothing needs rerunning. To release the current tip after its run already ended, dispatch `desktop-release` on `main` again — a fresh run decides on the tip as it stands when the run takes the slot, so a dispatch queued behind an active build evaluates whatever tip is current then — and releases it only if it passes the same checks — not the tip that stood when it was sent. Rerunning a finished run's failed jobs is not a retry: a rerun reuses the old `decide` outputs — the resolved SHA and version — so it can only ever attempt the same commit again, and a run that began before the poller shipped must never be rerun at all, because GitHub reruns a workflow at its original revision, which has none of this gate. The version is stamped into the packaged `package.json` with `-c.extraMetadata.version`, so `app.getVersion()` reports it; the arm64 build passes `pnpm smoke` before anything is published.

## Updates

Each release also carries `desktop-latest.json` (`scripts/release-manifest.mjs`): the version and, per arch, the zip's name, size and SHA-256. The packaged app reads `https://github.com/xiechimon/cairn/releases/latest/download/desktop-latest.json` 10 seconds after launch, every hour, and when a window gains focus at least 10 minutes after the last check; this is a release download, not the REST API, so the API's 60-requests-per-hour limit for unauthenticated callers does not apply, and a latest release without the file (HTTP 404) means no update. `desktopUpdateFrom` in `@cairn/shared` turns a newer manifest into the zip URL for the running arch. The sidebar's bottom-left button (desktop only, through the `cairnDesktop` preload bridge) shows the state; clicking "Update to …" downloads the zip next to the running bundle, checks its SHA-256, unpacks it with `ditto`, swaps the bundle only when the unpacked app is signed with the committed Cairn certificate, and relaunches. Electron's `autoUpdater` and `electron-updater` are not used because Squirrel.Mac only installs a build signed with the same Developer ID, and these builds carry no Apple certificate. Updating needs Cairn in a writable folder such as `/Applications`; run from the DMG or a translocated path, the button says so instead.
