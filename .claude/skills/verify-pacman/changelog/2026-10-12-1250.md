## 实测坑（新增）

- **run_builds 派工即自动 watch → chief gate 回合步会插队**：相位一变
  （build 成进 review、子卡 done）就有 gate chief 步入队，假机器线性
  claim 会把 gate 回合当成目标步领走（症状：claim 载荷 agent 块 =
  chief 绑定 Agent 而非 persona）。修法 = claimUntil(kind) 循环——中途
  领到 gate 回合就空回合 done success 收掉再领。
- **worker 步材料载体 = claim 载荷 `instruction`**：stepRecordSchema 的
  step 本体不带 prompt（machines.ts 把 stepRow.prompt 拼进 instruction
  下发）——review meta header / verify 材料的断言要么打 DB step 行的
  prompt 列，要么打 claim 的 instruction，打 step.prompt 恒 undefined。
- **review 步的 agentId 只在 prompt meta header**：step 表无 agentId 列
  （agent 解析是 claim 面 agentForStep 的事，落 claim 载荷 agent 块）；
  fan-out 断言用 meta 首行 JSON，别拿步行 agentId 列比对。
- **message.content 的双包 JSON**：#902 坑的新形态——insertMessageRow
  存 `JSON.stringify(obj)` 时 drizzle json 列再包一层引号，裸读是
  「JSON 串的 JSON 串」，一次 JSON.parse 得 `'{'` 开头的字符串还要再解
  一次；纯文本宣告行（'发起了拆解'）一次即终值——判 `startsWith('{')`
  再二解。
- **run_builds 原先只落 plan/build 两槽**：assignment 扩四槽改了 shared
  assignmentSchema 与 REST 面，chief relay 路径的参数映射（services/
  chief-tools.ts）还是手写两槽——四槽指派被静默丢掉 review/verify，症
  状 = verify 步不入队。本票补齐（词表 def + 落库映射同步）。
- **DONE_ANNOUNCEMENT 值是「标记为已完成」**：非「🎉 任务已完成」
  （后者是 merge 步 done 的 celebrate 行，内联字符串不走常量）。
  settleSplitOnDone 走 insertGateAnnouncement → content 列 + actor 列
  分开，DB 断言比对 content === '标记为已完成' 且 actor === 'Chief'。
