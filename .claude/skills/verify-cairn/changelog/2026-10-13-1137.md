New custom probe `scripts/drive-1137-webhook-tracer.mjs` (GitHub webhook event
entry tracer, #1137): pure live stack + one real egress (gh token pulls the real
issue details of xiechimon/pacman#1137), zero daemon zero LLM zero browser.
Three-segment tracer evidence: request segment (response JSON + pino log line
deliveryId key), persistence segment (todo row sourceKind/sourceRef +
webhook_token.lastUsedAt), dispatch segment (chief_thread/chief_message/step
rows). Failure paths fully covered live: wrong token 401, same delivery 60s
window duplicate, same issue replay sourceRef persistent-gate duplicate (zero
side-effect assertion), ping noop, non-triggering label ignored, unmapped repo
misconfigured. live 18/18 PASS, evidence `docs/verify/1137/` with re-run recipe.

Seeding shape: github connection / agent / chief go through the service modules
directly (server source imported via `file://` absolute URL, tsx via
`pnpm -C apps/server exec tsx` — no tsx at the repo root, bare dependencies
only resolve inside apps/server, same pitfall as 926); the connection's REST
surface is monopolized by oauth and agent creation was tightened by the #1259
home-machine gate, the seeding is not the surface under test, same shape as the
direct DB rows in `apps/server/test/webhook.test.ts`.

Two new measured pitfalls:

- The pino log is in pretty multi-line form (the header line msg + the
  deliveryId line + the result line each occupy one physical line) — the
  "one delivery one record" assertion cannot require a single line to contain
  both deliveryId and result, take the block by a line window (deliveryId line
  +/- 1); the 401 path throws before respond(), producing no log line, the log
  assertion surface only counts consumed deliveries.
- Chief steps hang off the orchestration thread (`step.buildId = threadId`,
  not todoId), the agent binding is on the chief row
  (`chief_thread.chiefId -> chief.agentId`), do not guess column names when
  writing assertions.
