# 2026-10-10 · #1108 machine concurrency cap + queue visibility

New custom probe `scripts/drive-1108-concurrency.mjs`: real daemon + **gated stub
LLM** (each request hangs until the probe's `release(i)` — a controlled clock for
in-flight steps, daemon parallel timing orchestrable) + Playwright browser surface.
Scenario = re-enactment of the user's measured live incident (a cap=2 machine sent
3 pinned local chief rounds back to back). Four assertion families 15/15 PASS,
evidence `docs/verify/1108/`:

- A parallel real run: canon lines `(1 running)`/`(2 running)` + overlapping stub
  request intervals.
- B queue visibility: threads query turnQueue (position + waitingFor running/capacity
  snapshot) + drawer `排队中：等 …` presence row + machine page `执行中 2/2` read
  annotation and concurrency control.
- C slot handoff: releasing the first step -> done + finish wake -> the third step
  is claimed within seconds (canon line reappears as `(2 running)`), the drawer
  queue row exits, all three rounds end done.
- D write surface: PATCH {maxConcurrent} single field persists with readback + 0/17
  out-of-range 400.

The feature map gains the new page `features/machine-concurrency.md` (with drive
steps and gotchas).

New measured pitfalls:

1. **The PATCH agent slot bound to an Agent requires the `thinkingLevel` key**
   (nullable but a required key) — a missing key 400s and the error does not name
   which field is missing.
2. **The new-thread default pin chain goes through `chiefRow.machineId`** (inside
   `sendChiefMessage`, `body.pinnedMachineId ?? chiefRow.machineId ?? null`) — in
   the probe one PATCH of the chief `machineId` pins all new threads to this
   machine, no per-thread pin needed.
3. **The machine-page row order puts the locally-seeded row first** — the probe's
   concurrency-control assertions must pin position by `data-machine-id`;
   `.first()` grabs the seeded local row (it also carries a concurrency control,
   default 3), a false red.
4. The daemon's local concurrency gate reads `maxConcurrent` from GET me and takes
   up to 30s to refresh after a PATCH (one presence beat) — but the server gate is
   the authoritative side and still blocks at full load; in the probe's timing the
   PATCH precedes sending threads, so it is unfelt.
