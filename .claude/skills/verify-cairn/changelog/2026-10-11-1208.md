## New measured pitfalls

- **Card #26's "fallback" is not a dispatch fallback**: mea is online and the pin
  is honored, the plan step really ran on mea; the cause of death was the
  local-repo project (a Mac absolute path) failing clone 128 on mea. What
  actually moved the work to the local machine was the chief's `run_builds`
  explicit machineId reassignment (the transcript has the full reasoning, the
  board layer shows zero hint) — the visibility to pin is this seam, not a new
  offline automatic fallback (t-0047's semantic guardrail forbids it: "the
  semantics of a pin is determinism").
- **Enroll the machines before creating the todo cards**: createTodo validates
  the machineId and 400s out-of-bounds (machine-pin failure mode 1 rule), the
  seeding order = project -> two machines -> three cards.
- **The reassignment leg's receive path**: the probe does not receive (the chief
  step stays claimed, the build step stays pending) — cancel/done would push the
  phase to failed and the meta block (plan empty state) would not attach, the
  browser leg could not photograph the machine row at all.
- **The assignment dual slots are both required**: REST startBuilds'
  assignmentSchema has two nullable-but-not-optional slots, passing only the
  build slot 400s.
