# 2026-10-14 — #1303 chief unread badge (drive-1303-chief-unread)

New custom probe `scripts/drive-1303-chief-unread.mjs` (pure live stack +
fake-machine wire, zero daemon zero LLM). `--expect=old|new` two states in one
script: two assistant text rounds from the user count as 1 badge, whether the
`[wake:wake]` step after set_wake expiry counts the thread into unread, moving
the thread's last activity to 8 days ago and waiting one tick (the wake step
appearing = the tick ran) then whether it is marked read, and the badge text
when 100 unread threads pile up. 13/13 before the change, 13/13 after. Truth in
`docs/verify/1303/`.

## New measured pitfalls

- **The enroll response's machine id field is `machineId`**, not `id`. This
  probe takes `body.machineId ?? body.id`. Since #1259 agent creation still
  must carry machineId, the seed order stays provider -> api key -> enroll ->
  agent -> PATCH chief.
- **The claim long-poll is about 75s, this probe's fetch timeout is 35s**. The
  wake step is enqueued by the scheduler tick (15s) and then
  `machineHub.wake` releases the claim, measured to return within the timeout.
  If a re-run's claim is cut off by AbortSignal, the server does not claim on
  behalf of the disconnected request, just claim again.
- **The server process has no watch**. After changing `apps/server/src` you
  must cleanup and relaunch, otherwise `--expect=new` hits the old process.
- **Opening the drawer does not write `readAt`**. `routes-core.ts` notes the
  read/write path has no observation endpoint. Probe A6 pins both states with
  "open then minimize, badge and readAt unchanged". This ticket's expiry
  mechanism is the tick sweeping 7-day-idle threads, not open-means-read.
