## Baseline preconditions

- Run `launch.mjs` first: the isolated stack is ready (by default web `http://127.0.0.1:5273/app`, api `http://127.0.0.1:8791`, a fresh scratch DB, seeds a single-user Owner, no auth).
- A fresh DB is guaranteed by every launch (the `api-key` probe depends on the empty state); re-verification = relaunch, not reusing an old DB. For cases with `fresh-stack` in the registry, `vp.mjs drive` refuses to run on a stack that has already driven another case (exit 2), suggesting `vp.mjs cleanup` then relaunch `vp.mjs launch`.
- Ports occupied (8791/5273) -> another lane, switch `VERIFY_PORT`/`VERIFY_WEB_PORT`, do not kill.
- **When a worktree sits under `.claude/worktrees/`, changes made after launch are never served by vite**: `apps/web/vite.config.ts`'s `watch.ignored: ['**/.claude/**']` hits every file of such a worktree. After changing code, `vp.mjs cleanup` then `vp.mjs launch` first, otherwise you are driving the code as of launch time (#1402 negative control measured: a planted regression without relaunch, drive still PASSes).
- Drive only after `doctor.mjs` fully PASSes.
- Never drive an instance not started by this verification (the user dev stack on 8787/5173 is not touched even when running).
- The spec 11 three advance probes' run order: `drive-providers-tabs` (the pi empty-state assertion requires no custom provider in the DB) -> `drive-provider-picker` (the e2e creates a provider) -> `drive-machines-local` (idempotent, any order). Reversed order = false red on the tabs empty state.

## Driving conventions

- Driving goes exclusively through the single entry point `node .claude/skills/verify-cairn/scripts/vp.mjs drive <feature> [case]` (#1402); `vp.mjs list [feature]` lists registered cases and their preconditions. The script commands written in each feature file still run directly, but new cases are registered in `../vp-registry.json` first, no new ticket-named scripts. Each feature file lists the `vp.mjs drive <feature> <case>` command driving it at the end of "How to get to it (user POV)" (those without a current case say so, stale-judged ones note the reason); the registry gate (`scripts/vp-registry-gate.mjs`, run in the self-test) verifies these lines all point at registered cases and every feature with a recipe has such a line.
- Live surface only: URLs carry no `?scenario=` (that is the fixture surface).
- Prefer stable handles for selectors: `data-route`, `data-column-list`, `data-todo-id`, aria-label, class names; no coordinates/tab order.
- UI evidence = screenshots (1440x732, same convention as e2e) + the per-check checks in `result.json`.
- Change-type proofs must have a second pair of eyes: `GET /api/...` JSON truth + SQLite read-only rows (see each feature file).
- The second pair of eyes for **mechanism-type claims** (CSS/animation, on-disk or wire format, schema, shim traffic, verdict fields) = **compiled output / runtime artifacts**, not source, config or dependency lists — the claim -> artifact -> case path table is in SKILL.md "Mechanism-effect acceptance: real-artifact criteria (hard rule)".
- Close with `cleanup.mjs` to reap the stack; evidence by default lands in the **main checkout's** `.claude/verify-evidence/` (not the worktree), which is gitignored.
- **Evidence delivery must be archived into the PR**: on a checkout of the PR branch run `vp.mjs archive <ticket> --from <evidence directory>` to archive the evidence directory into `docs/verify/<ticket>/` and commit (copy-only, refuses if the target exists, no manual `cp`; `result.json` + screenshots, multiple evidence groups get a README index), the PR body references it via the commit SHA permanent link (`vp.mjs links <ticket>` prints it after push; the link shape is in SKILL.md "Evidence archive discipline"). Runtime evidence lands in `.claude/verify-evidence/` (gitignored); **a verify claim not referenced in the repo via a PR counts as unverified**.
- When reporting a skipped entry, include the commands attempted and the unmet preconditions; "verified from another entry" must not count as "this entry verified".

## Feature entry contract

Each feature file: an H1 title + one user-perspective paragraph, then four fixed H2s (order unchanged):

1. `Sub-features` — short ID + one line of behavior.
2. `How to get to it (user POV)` — every user entry point.
3. `Driving it with <harness>` — `Preconditions:` first, then paired bullets: user action + exact command + observable result.
4. `Gotchas` — pits that waste or void a verification.

The map does not write implementation details, only user paths, stable handles, required states, commands, observable proofs.
