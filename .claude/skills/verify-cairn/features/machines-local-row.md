# Machines-page local row + per-runtime brand marks + machine-level shell switch (machines page, spec 11 A8/A9/A7, #353/#354; #503 switch -> brand marks; XMON-113 in-row shell switch re-wired)

Users open the machines page (`/app/resources/machines`) and see the local machine pinned at the top of the list (hostname shown, not deletable), with the two official brand marks for pi / Claude Code in the row: enabled = the brand's original color, not enabled = 35% transparent — the read-only display surface of `enabledRuntimes`, with no per-runtime enable/disable controls (removed at #503, on the grounds that those switches were written but never read anywhere in the repo). At the row's tail there is **one live control** = the machine-level shell switch (XMON-113 R3; XMON-108 R1 provides the `machine.shellEnabled` field and the PATCH single-field pass-through): flipping it writes `{shellEnabled}` to `PATCH /api/machines/{id}`, with an optimistic update, a rollback on failure and a one-line `保存失败，请重试。` . The `Cairn 托管机器` facade row is removed — the hosted form does not exist in this architecture; what the user really owns is the local machine + self-connected LAN/VPS machines (add a machine = run the same CLI on the target machine, the dialog flow unchanged). Spec source: `docs/spec/11-模型服务与机器本地化.md` (A7-A9) + XMON-85 plan §1 / XMON-113.

## Sub-features

- `mach-local-row` the local row is pinned at the top of the list: seeded at server startup (`os.hostname()` matches an existing row -> backfill `kind='local'`, otherwise create the row, idempotent). Contract handle: `div[data-machine-id][data-kind="local"]` (the div element name is pinned to prevent cross-talk — the in-row shell switch also carries `data-machine-id`), the row text contains the hostname.
- `mach-local-nodelete` the local row is not deletable (no delete control / three-dot menu in the row, negative).
- `mach-facade-gone` the `Cairn 托管机器` facade row is removed (negative; a current leftover = a fixed decorative row rendered by the frontend, not data in the library).
- `mach-marks` the per-runtime brand marks in the local row: an `svg` (the official mark) inside the `[data-runtime="pi"|"claude-code"]` container; the text name is not on screen (#887 icon-only shape) — the readable name = the container's `aria-label` / `title`, the container text is empty (negative); the enabled state is carried by `data-enabled="true"|"false"` = `enabledRuntimes.includes(runtime)` (#503 read-only display, not a control).
- `mach-marks-consistent` the mark brightness states are consistent with `GET /api/teams/:id/machines`'s `enabledRuntimes`, and with the same set as SQLite's `machine.enabledRuntimes` (a JSON column).
- `mach-shell-switch-single` the in-row interactive control = the shell switch (`[role="switch"]`, `aria-label` = `远程 shell`; one per row, including the enrolling machine's row) + the concurrency selector since #1108 (the row's only `button`, see machine-concurrency.md); the per-runtime slots have zero `switch` and zero `button` besides the concurrency button (#503's dead controls still pinned negative). The criterion is not "the row may have no controls" but "the row may have no dead controls".
- `mach-shell-consistent` the switch's `aria-checked` is consistent with the `shellEnabled` recorded by `GET /api/teams/:id/machines` (idempotent: the expected value is derived from the API state).
- `mach-shell-write-api` a real click -> `PATCH /api/machines/{id}` carries only `{shellEnabled}` (single field; sending `enabledRuntimes` along would wholesale-replace that column) -> the API reads back the new value.
- `mach-shell-write-db` SQLite `SELECT shellEnabled FROM machine WHERE id=?` matches the API (the write really lands in the DB, not just an in-memory projection).
- `mach-shell-persist-reload` after flipping, reload and the switch echoes the new value (the read-side projection works).
- `mach-shell-restore` flip back to the initial value at the close (the stack state is restored, a rerun does not false-red).
- `mach-subline-shell-hint-only` the sub-line carries only the shell-switch explanation (the copy carrier = the getByText whole sentence `已授权「远程 shell」的 Agent 可在该机器上执行命令。`; #503's id tail and the `· max` read-only dead display are still negative — #1108's concurrency live control and the `执行中 n/N` read annotation are in the row's right segment, see machine-concurrency.md).
- `mach-shell-error` a PATCH failure -> the switch rolls back + `[role="alert"]` shows `保存失败，请重试。` (the visible feedback surface of the same rule as XMON-80; covered by the e2e stub, the probe does not stub so it is not in this list).
- `mach-kind-column` the machine table's three columns (A9 + XMON-108 migration): `kind` (default `'remote'`, the local row `'local'`) + `enabledRuntimes` (JSON, default `[]` = all off) + `shellEnabled` (bool, default 0) — camelCase column names (same shape as the existing columns), the observable truth for the SQLite assertions below.
- `mach-persist` after a reload, the mark brightness states are still consistent with the API.
- `mach-add-intact` the `添加机器` button (role=button, exact copy `添加机器`) -> the CLI-command dialog flow unchanged (the dialog structure unmoved).
- `mach-no-affordance` the row has no chevron decoration (the negative handle = the row-level clickable-semantics count 0: `[data-kind][role="button"]` / `[data-kind] a` — the decoration classes retired with #944, the A7 semantics re-pinned as "the row is not clickable").

## How to get to it (user POV)

- Board sidebar `资源` -> `机器` (`/app/resources/machines`).
- The local row = the list's first row; the middle segment's marks read-only-display which runtimes the local machine has enabled, the right edge of the row is the `远程 shell` label + the switch and the `执行中 n/N` read annotation + the `并发 N` selector (two live controls, each click writes to the DB).
- Add a LAN/VPS machine: the `添加机器` button -> the dialog gives a copyable CLI command (run it on the target machine).
- Driving (`vp.mjs list machines-local-row` lists all cases and usage):
  - `node .claude/skills/verify-cairn/scripts/vp.mjs drive machines-local-row local-row`: the local row, the brand marks, the shell-switch writeback.

## Driving it with verify-cairn

Preconditions:

1. `launch.mjs` brings the isolated stack up, `doctor.mjs` fully PASS. **No daemon needed** — the local row walks the server-startup seed path; the daemon loopback enroll landing `kind='local'` is a different path, not covered by this probe (it needs a real daemon, belonging to the stop-button family recipe).
2. Depends on the implementation surfaces: the machine three-column migration (A9/T1 + XMON-108) + the server-startup seed and the PATCH single-field pass-through (T2 + R1) + the page rewrite (T4 + the XMON-113 in-row switch).
3. The write-path probe really mutates the DB (flip -> persist -> flip back), so it must run against the isolated stack (`VERIFY_PORT` / `VERIFY_WEB_PORT` and `VERIFY_REPO_ROOT` see the README), never point it at a stack in use.

- **Local row + marks + shell-switch full chain.** **How to run:** `node <skill>/scripts/drive-machines-local.mjs` (self-sufficient) — 20 checks: page ready -> facade negative -> the API's local record (kind='local', name = os.hostname() exact match) -> the UI local row pinned first + hostname text -> the not-deletable negative -> the two marks in place (mark + name) -> **the mark UI = API consistency baseline** (brightness states vs enabledRuntimes, idempotent) -> **exactly one control in the row = the shell switch** (no button / no per-runtime switch) -> **the switch UI = API consistency baseline** (idempotent, no assumed initial value) -> the sub-line = the shell explanation -> **the write chain**: flip -> the API reads back the new value -> SQLite matches -> reload echoes -> flip back to the initial value -> the SQLite kind column -> SQLite enabledRuntimes same set as the API -> a full-page reload persists -> the add-machine dialog flow unchanged -> chevron negative.
- **Truth.** The `GET /api/teams/:id/machines` record (the kind/enabledRuntimes/shellEnabled fields) + the SQLite `machine` row (`SELECT kind, enabledRuntimes, shellEnabled FROM machine WHERE id=?`) and the UI (the mark's `data-enabled` / the switch's `aria-checked`) cross-checked three ways.
- **The switch's behavioral surface splits in two**: the failure rollback and the optimistic update need stubbing (the probe runs against a real stack), belonging to `apps/web/e2e/machines-shell-switch.spec.ts`; the probe only pins the real-stack read-write loop.
- **Idempotent**: a rerun on the same stack does not false-red — the expected values are derived from the API state, "initially all off" is not hard-coded.

## Gotchas

- **Red-state semantics**: same as providers-tabs.md — the probe precedes the implementation, red != the harness is broken; when the implementation and the map conflict, change the map first and then the probe.
- The A9 column names are camelCase (`kind` / `enabledRuntimes`); `enabledRuntimes` is a JSON text column, `JSON.parse` on readback.
- The runtime vocabulary `'pi'|'claude-code'` has its single source in shared (same vocabulary as the model-sources runtime and the providers-tab data-runtime); the brand-mark originals' provenance is recorded in the header of `apps/web/src/components/brand-marks.tsx`.
- The local-row name assertion = `os.hostname()` **exact match** (the A8 seed keys on the hostname); after a machine rename, the old row is matched by hostname to backfill the kind, no duplicate row creation (the idempotent semantics belong to the T2 implementation pin).
- The probe's wording of "not deletable" = no in-row button whose `aria-label` contains `删除` and no menu trigger (`[aria-haspopup="menu"]` count 0) — if the implementation provides an in-row menu other than delete, change the map first and then the assertion.
- **#944 carrier migration**: class-name hooks -> semantic/data-* carriers (assertion semantics unchanged) — the original `.res-grow` -> `div[data-machine-id]`, `.mach-runtime` / `.mach-mark` / `.mach-runtime-label` -> the `[data-runtime]` container + the inner `svg` + the `aria-label` readable name (the text name not on screen since #887, negative = the container text empty), `.mach-runtime--on` state class -> the `data-enabled` attribute, `.mach-shell-switch` -> `[role="switch"]`, `.res-row-desc` -> copy-first, `.res-add` -> role=button `添加机器`, `.res-row-chev` / `.res-row-more` negative -> the row-level clickable-semantics/menu-trigger count 0; the original res-main / res-main-col handles were renamed `.page-main` / `.page-main-col` with the PR 6 three-shell merger.
- **Do not mix up the two API prefixes**: the read is team-scoped `GET /api/teams/{tid}/machines`, the write is the team-less `PATCH /api/machines/{id}` (the apps/web e2e stub stepped on the same pit once). For stub route registration order = reverse matching order, register the catch-all first.
- **The switch write is a single-field body**: `{shellEnabled}`. Carrying `enabledRuntimes` along would wholesale-replace that column (since R1 the two fields are each optional, absent = untouched), both the probe and the e2e assert the body has exactly one key.
- The add-machine dialog gets only light assertions (the window opens + it contains the `cairn` command text) — the CLI-command detail surface belongs to the fixture e2e, this probe pins "the flow is unchanged", not the content.
