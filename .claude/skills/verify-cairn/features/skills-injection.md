# Skills execution-surface injection (daemon) + routing visible surfaces (web, #919)

Before creating each agent session, the daemon scans `CAIRN_SKILLS_DIR` (default `~/.agents/skills`) and delivers the `<available_skills>` catalog (name + description + location XML) through the briefing-file channel (since #958 it no longer enters the systemPrompt); when the agent matches by description, it uses the built-in `read` tool to read the full SKILL.md on demand via the location absolute path. The catalog is an index, not the full text — the token budget is linear in the number of skills, independent of the total length of all skills (#371, spec 14). The team library is distributed via the server manifest + on-demand pull (#920), and skills outside the whitelist are hard-blocked by both backends (#917).

**The web UI surface exists since #918** (the parallel ticket merged first; it is exactly what #919's seam-4 acceptance targets): the live-row disclosure surface `▶/✕ skill: <名>` rows (`data-testid="skill-line"`, live state only — #873's disclosure panel mounts only while liveStep is present) + the detail-page persistent summary row (`data-testid="skills-summary"`, read / blocked columns, derived from the persisted toolcall rows). The classifier single source = shared/skill-facts (the same function as the daemon's live-row judgment). Verification = the integration real stack (server + real daemon + stub LLM capture) + the `drive-919-skills-routing.mjs` live probe (the real-model behavior leg + the stub deny leg) + the fixture e2e `skills-routing.spec.ts` (the persistent surface; the live surface belongs to #918's unit/live probes).

## Sub-features

- `skills-catalog-inject` the catalog XML enters the LLM input surface via the briefing channel; existing sections (agent role / memory) are kept — append, not overwrite.
- `skills-read-through` the catalog location = the SKILL.md absolute path; the agent `read`ing that path is not refused (connectivity is hard acceptance — the catalog must not be a decoration).
- `skills-dir-env` `CAIRN_SKILLS_DIR` overrides the scan root; default `~/.agents/skills`; a missing/empty directory = an empty catalog, not fatal.
- `skills-cap` the catalog total is capped above 50; a single description over 200 characters is truncated with `…`; each lands a cap log line.
- `skills-log` the `[skills] <type>: <msg>` row family lands in daemon.log (type ∈ loaded / collision / invalid-frontmatter / missing-skill-md / cap / invalid / catalog / deny / denied-read / team / team-manifest-empty / team-skills-failed / filtered).
- `skills-facts-faces` (landed at #918, #919's seam-4 acceptance) the live-row disclosure rows (live state) + the persistent summary row (read / blocked columns); the fixture e2e pins the persistent surface and the zero-event control.
- `skills-routing-behavior` (#919's main criterion) a real dispatch with zero skill words on the ticket surface, the lane's own skill hits — four-surface evidence of the artifact marker + the transcript read row + the daemon.log catalog row + the detail-page summary-row screenshot.
- `skills-allowlist-split` (#1169) the agent's two skill fields split — `defaultSkill` (carried, single value, the detail-page overview Select) + `skillsAllowlist` (authorization, null = unlimited, [] = explicitly deny all, the detail-page permissions-tab checklist + the two-state mutual-conversion switch); legacy `[]` rows migrate to null (lifting the "a newly created agent is born deny-all"); the deny mechanism (#917) is unchanged. Verification = the `drive-1169-skills-split.mjs` live probe (the api phase pins the REST read/write surface / claim payload / checklist selection three surfaces with zero daemon + the behavior phase pins an unlimited agent reading SKILL.md with zero deny, real-model leg) + the migration backfill unit (agent-skills-split-backfill.test.ts) + the detail-page e2e (the two controls in agent-detail.spec.ts do not affect each other).
- `skills-native-plugin` (#1171) claude-backend team skills enter the CLI's native Skill discovery surface via the SDK's `plugins` option (-> `--plugin-dir`): the landing = the daemon cache's third partition `<teamSkillsCacheDir>/plugins/<key>/` (`.claude-plugin/plugin.json` with name=`cairn-team-skills` + `skills/<dirName>` hardlink assembly, key = sha256(view digest + the sorted allowed dirNames)); **zero writes to the task worktree**; the allowed set = `collectTeamSkillEntries` (the same scan source as the catalog/deny, filtered only by `skillsAllowlist`, **not narrowed by `injectedSkills`** — the selection never exceeds the authorization, same rule as #917); the version gate `MIN_CLAUDE_PLUGIN_VERSION=2.1.74` (single source probed at #1050, below the gate = a skipped line + the catalog fallback); the deny three-rule shape is unchanged (`Skill(name)` hits the plugin's qualified name via the alias); the catalog XML channel coexists as usual. The skill name = the `cairn-team-skills:<name>` qualified form + the unqualified alias; a name collision with a project/user skill = coexistence, the unqualified name goes to the incumbent side. Verification = `drive-1171-native-plugin.mjs` (the wire phase's fake CLI captures argv with zero LLM, 32 checks + the behavior phase real-model leg 10 checks: the transcript `Skill` tool-call segment row names the plugin's qualified name) + the unit `skills-native-plugin.test.ts` (34 checks, failure modes P1-P15).

## How to get to it (user POV)

- The user drops skills at `~/.agents/skills/<name>/SKILL.md` (frontmatter `name` + `description`; a missing name falls back to the directory name) -> once the daemon is up, dispatching any task -> the agent session automatically carries the catalog and reads on demand.
- Self-hosting: start the daemon with `CAIRN_SKILLS_DIR=/path/to/other` to load from there.
- UI configurability (an account-page input) = a later ticket, currently no entry.

## Gotchas

- **The read tool having no sandbox is a pi fact**: pi 0.86's `read` tool resolves any absolute path (`resolveReadPathAsync`), and there is no path whitelist on the daemon side — "extending the whitelist to skillsDir" needs no code change, the connectivity is proven by the (2) persistence assertion. Do not go looking for a nonexistent allowlist seam.
- **Rescanned on every session creation**: the catalog has no cache and no watcher, it takes effect between sessions even without a daemon restart; after editing SKILL.md, dispatch a new task to see it.
- **The dev machine's default directory is real data**: the default `~/.agents/skills` exists on this machine and has > 50 skills — other integration cases (m3a/m4b) running on the default skillsDir really inject the catalog (cap truncated), the containment assertions are unaffected, but daemon.log will show `[skills] cap:` lines, which is not a bug.
- **A skill with `disable-model-invocation: true` does not enter the catalog** (pi's `formatSkillsForPrompt` filters it) — it can only be triggered explicitly via `/skill:`, the on-demand read path does not apply to it.
- When the machine-loop test injects `opts.backend`, it does not go through PiBackend -> no skills injection; to verify injection you must go through the `createPiBackend` real path (the integration harness is exactly this shape).
- **The enroll default `enabledRuntimes:['pi']` is a real claim gate since #682** (`dispatch-eligibility.ts` runtimeGatePasses): a claude-code-runtime agent's steps stay **pending forever with zero daemon logs** on a pi-only machine (measured live 2026-10-07 on the #919 behavior leg, three rounds of 600s idle waiting). Before dispatching claude-code work, first `PATCH /api/machines/:id {"enabledRuntimes":["pi","claude-code"]}` (= the REST surface of the machines-page runtime switch; built into the drive-919 probe).
- **The step terminal vocabulary = `done`/`failed`/`stopped`** (shared stepStatusSchema) — `success` is not in the vocabulary; do not copy it wrong when a probe waits for a terminal state (drive-919's first version copied the nonexistent 'success' and idled 600s). The build table has no status column, the failure root cause is in `build.errorMessage`.
