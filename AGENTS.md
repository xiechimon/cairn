# Cairn Development Rules

Before any change under `apps/web/src`, invoke the `design-cairn` skill and run `node scripts/design-rules-for.mjs` on the files you will touch, before reading or editing the code — the printed rule rows are the ones that apply; `apps/web/DESIGN.md` holds the token frontmatter and the which-component table.

## Safety

- This repository is public: never commit secrets, credentials, internal addresses, personal information or quota details.
- A secret seen in plain text (diff, log, transcript, report) is leaked: tell the owner to rotate it first, then remove it from every commit that holds it. Pre-flight starts with `scripts/ops/secret-scan.mjs`, which runs gitleaks over the diffs and commit messages since `origin/main`; a missing gitleaks (`node scripts/ops/install-gitleaks.mjs` or `brew install gitleaks`) or an incomplete scan is red. For a false positive in a file, commit the printed Fingerprint line to `.gitleaksignore`; for one in a commit message, reword the message. An entry names a commit SHA, so after a rebase or amend rewrites that commit, add the line the next run prints.
- Never force push, use `--no-verify`, bypass hooks with `core.hooksPath`, or run `git reset --hard`, `git clean`, `git stash` or `git checkout .`. Never overwrite uncommitted work you did not write.
- Stage only your own changes with explicit paths; never use `git add -A` or `git add .`.
- Commit identity: every agent, on a host or in a Claude Code cloud session, commits as `xiechimon <157263579+xiechimon@users.noreply.github.com>`. Authorized host agents push with his existing user gh login using ordinary git/gh, without an App token; a cloud session pushes with its own session access. Existing `Claude <noreply@anthropic.com>` and bot commits remain accepted; preserve their authors. Git hooks are not installed; run verification explicitly before pushing. Details: `docs/ops/agent-bot-identity.md`.
- Do not run postinstall scripts without explicit user authorization; install dependencies with scripts disabled unless authorized.
- Seams: read the comments in `biome.json` before changing locked imports (`@earendil-works/*`, `@modelcontextprotocol/sdk`, `simple-git`, `isomorphic-git`, `cron-parser`) and consume them through thin bridges. Keep GitOps, MCP and LLM provider access behind `apps/daemon/src/backend/`; the exceptions are the in-server Coordinator runtime, `apps/server/src/coordinator/runtime/`, and the MCP connector client in `apps/server/src/services/mcp-servers.ts`.
- Never kill another lane's processes; inspect the PID, command and working directory before stopping a process you started. Shared ports, heavy slots and worktree rules: `docs/ops/worktrees-and-ports.md`.
- No change may edit what judges it: the eval suite (`eval/**` — task set, scorers and run configuration — is a `humanQueue.evalConfig` path in `packages/shared/merge-gate-paths.json`), and the gate reads the exam from the merge-base checkout at run time.

## Ship

Work lands on `main` through `scripts/ops/push-queue.mjs`, enforced by the `green-main` ruleset: `main` accepts only commits whose `check`, `pack-smoke` and `e2e-gate` checks are already green, so pushing an untested `HEAD:main` is rejected by GitHub itself. After `HEAD` has green `check` + `pack-smoke` + `e2e-gate` on its exact SHA from `preflight/*`, `push-queue.mjs` always submits `HEAD` to `refs/heads/enqueue/<ts>-<sha9>` and dispatches the `promote` workflow (`scripts/ops/speculative-queue.mjs`), which builds parallel speculative `refs/heads/queue/try/<id>` branches up to depth 4, runs CI concurrently across all speculative positions without cancellation, fast-forwards `main` in one batch to the furthest green prefix, cancels superseded runs, retries a failed/cancelled attempt once, and ejects only a confirmed-red head or conflicting commit while rebuilding surviving entries cleanly (`docs/design/tested-sha-landing.md`). There is no pull request, merge queue or PR-body format. Production safety lives in the deploy: the shipped product is the Mac desktop app, published by the `desktop-release` workflow, a level-triggered poller woken by every `ci` run completed on `main`, a 15-minute `schedule` backstop and manual dispatch to `main`. `desktop-release` runs serialize on one workflow-level concurrency group that never cancels the running release (a newer wake replaces only a pending one): each run scans current `main` history newest first, excluding ancestors of the highest-version published stable `desktop-v*` release, and selects the newest unreleased commit whose own push-to-main `ci` run's latest attempt completed `success` with green `check`/`pack-smoke`/`e2e-gate` jobs and whose app sources moved since that stable release; a pending or red tip does not block an older eligible commit — each run allocates at decide time the first `desktop-v*` version no tag or release — drafts included, which is why the deciding token holds `contents: write` — occupies — the workflow never deletes a release or a tag, so an abandoned publish just leaves a draft holding a version `decide` already skips (`scripts/ops/release-decide.mjs`, `scripts/ops/release-gate.mjs`, `scripts/ops/release-plan.mjs`); a run with no eligible candidate exits doing nothing and a later wake scans main again — the schedule is a backstop, not a bound on release latency. Builds and live verification pin the selected SHA; publish control uses the trusted workflow revision, not the older candidate's scripts. `publish` re-reads the candidate's same CI evidence — an attempt that started or turned red since the jobs read blocks it — and creates the release's tag only while that commit remains an ancestor of current `main` (`scripts/ops/release-tip.mjs`). Main advancing does not cancel it; a candidate outside main or without green CI never publishes. `publish` also waits on `live-verify`, a job that drives the new-task journey on an isolated verify-cairn stack and archives the evidence as a workflow artifact. A Claude Code cloud session lands work the same way: it lands work through `scripts/ops/push-queue.mjs` the same way and promotes it, whatever branch its session defaults name.

Work happens in worktrees, never in the primary checkout: a machine-level pre-commit hook there refuses commits, and its tree stays clean so `cairn-autopull` can fast-forward it to `origin/main`.

1. Work in your own worktree on a branch from the latest `origin/main`.
2. Commit any uncommitted changes. Tidy noisy intermediate commits into a few clear ones while they are still unpushed.
3. `git fetch origin main` and rebase onto the latest `origin/main`; resolve conflicts. If the rebase floods add/add conflicts in unrelated files, the clone is shallow: run `git rebase --abort`, `git fetch --quiet --unshallow origin main`, then rebase again.
4. Verify on GitHub runners: run `node scripts/ops/preflight.mjs --stamp-only` first when overlapping pre-flight with `review-head` so both share the exact stamped `HEAD`, then run `node scripts/ops/preflight.mjs --wait` (batches all review findings into one follow-up commit). It runs the mandatory fast gate, waits when two preflight `ci` runs are already active, force-pushes that `HEAD` SHA (nothing, if `HEAD` moved meanwhile) to your own `refs/heads/preflight/<lane>` and watches the `ci` run there; the repo is public, so standard runners cost nothing and a docs-only head greens in about a minute. That green run is the admission ticket: `push-queue.mjs` refuses a head whose `check` + `pack-smoke` + `e2e-gate` contexts are not green on GitHub (or cleanly rebased from a green `preflight/<lane>` commit with identical patch-ids via `scripts/ops/rebase-equivalence.mjs`; a clean rebase-only head change reuses the preflight verdict without re-running pre-flight because `queue/try/*` still tests the merged tree, whereas any conflict edit or code change requires re-running pre-flight). `preflight.mjs` stamps the owner trailer before pushing, so the SHA it tests is the one that lands. Do not rebase after pre-flight turns green unless `push-queue` reports a conflict. `pnpm prepush` and `pnpm test:changed` are optional fast local iteration. `pnpm test:changed` runs the changed test files and the tests named after changed source files, within a 10-minute budget; CI runs the full suite. Do not run `vitest --changed` locally: a shared package change selects nearly every test. Web e2e runs in CI after the push, not locally; while writing or fixing a spec, run that one spec with `pnpm exec playwright test <spec>`. When the change alters user-facing behavior, walk the touched journeys on a `verify-cairn` live stack before claiming it works — fixture e2e and source review do not prove live behavior; keep the evidence (screenshots, requests, or DB rows) and show it to the owner in the wrap-up as screenshots of each touched journey or a live page he can open; a claim he cannot see is an unverified claim. Mechanics: `docs/design/preflight-ci-verification.md`.
5. Push without force, through the one script that owns the merge queue and fast-forwards `main`: `node scripts/ops/push-queue.mjs`. It applies to every agent and human, whatever tool made the commits (Amp, Claude Code, a Cairn task, your own shell). Never run `git push origin HEAD:queue/main`, `git push origin :refs/heads/queue/main` or `git push origin HEAD:main` by hand, and never write a loop that deletes or recreates `queue/main` or another lane's `enqueue/*` / `queue/try/*` ref. Once `HEAD` has green `check` + `pack-smoke` + `e2e-gate` on its exact SHA from `preflight/*` (or on a tested clean-rebase ancestor with identical patches, in which case `speculative-queue.mjs` always runs `queue/try/*` before `main`), `push-queue.mjs` pushes `HEAD` into `refs/heads/enqueue/<ts>-<sha9>` and dispatches `promote.yml`, while `node scripts/ops/push-queue.mjs --wait` polls every 15s until `origin/main` advances past your change or reports an ejection comment. The script stamps a `Lane: <machine id>/<worktree>` trailer on commits that carry no `Amp-Thread-ID` or `Lane`, so ejections name an owner. The `promote` workflow runs `scripts/ops/speculative-queue.mjs --enforce` across up to 4 concurrent speculative `queue/try/*` stacks, batch-promotes the furthest green prefix, retries a failed/cancelled attempt once (cancelled jobs alone count for whole rerun), and ejects only a confirmed-red head or conflicting commit (keeping valid downstream entries). Mechanism details: `docs/design/tested-sha-landing.md`.
6. A queued candidate leaves `enqueue/*` and `queue/try/*` only by landing on `main` or by the `promote` workflow ejecting it; you never remove one, not even one you think is yours or dead, because a downstream speculative run may sit atop it and a failed attempt is rerun once first. If `push-queue.mjs --wait` exits with an ejection notice (conflict or red CI), fetch, rebase onto `origin/main`, fix the cause, rerun `preflight.mjs --wait`, and run `push-queue.mjs` again. A human operator who must clear a queued candidate first comments `queue/main release: <reason>` on its commit. Do not repeat step 4 after a later fetch or rebase if `HEAD` did not change.
7. A conflict that changes behavior: resolve it so both sides' intent survives, rerun step 4, and push without asking; name the other lane's commit and how you merged it in your commit message or wrap-up.
8. Check CI on `origin/main` before pushing — judge the latest **completed** `ci` run; a run that is pending, in progress or cancelled is evidence of nothing, so keep looking back to the last run that finished. If that run is red, compare the failing jobs with the area your change touches: overlap means fix it or wait; no overlap means you may push, but when a red job covers your tests, verify them locally yourself. After pushing, watch CI on your commit and diff its failing jobs against the parent's: new failures are yours — fix them, or revert your commit if you cannot fix quickly; an identical failure signature is inherited — report the owning lane in chat, your commit stays. A red that survives several runs unclaimed and blocks deploys falls to the next lane needing a green deploy, or to the owner.
9. Once your work is on `main`, delete every remote branch you pushed for it (`git push origin --delete <branch>`) without asking; this standing approval covers only branches you pushed yourself.
10. Remove your worktree and its local branch once your work is on `main` (`git worktree remove`, then `git branch -d`) without asking — a landed worktree only consumes disk. This covers only worktrees and branches you created.
11. Changes to merge-queue or CI scheduling files (`scripts/ops/{speculative-queue,push-queue,promote-queue,ci-reuse-verified}.mjs`, `.github/workflows/{ci,promote}.yml`) must pass `scripts/ops/merge-queue-invariants.test.mjs` and preserve `green-main` checks alongside verified before/after live efficiency.

## How to work

- User experience comes first. Judge, design and explain every feature from the seat of any Cairn user, never from the owner's own machines or accounts. Five rules: the system carries the complexity — what it can decide it decides, what it can do for the user it does, and what is useless right now does not appear; the same thing looks and works the same everywhere, every press answers, and a second press undoes it; never interrupt what the user is doing; make the common things excellent and keep anything that can lose data out of reach of a stray click; the interface explains itself.
- Product prompts, defaults and gates must suit every Cairn user; the owner's personal workflow preferences belong in his own config, not the product.
- New `CAIRN_*` env vars, settings keys and runner/device fields need a `scripts/product-surface-registry.json` row with the new-user scenario; helper text and permanently disabled controls only ratchet down.
- Repository content is English: code, docs, scripts, tests and commits. Product UI strings in `t()`, translations, matching fixtures and selectors, agent-facing product prompts and `README.zh.md` may be Chinese. Follow the user's language in conversation, and reply to the owner in Chinese: answers, reports, plans, questions and agent wrap-ups he reads.
- Commit format: `<scope>(<ticket>): <subject>`, in English. Put `Closes #N` on its own line when the commit finishes ticket N, or `Part of #N` for one segment.
- Read files in full before editing, and check consumers before moving or renaming paths. Ask before removing intentional functionality or changing intended behavior.
- Do not write code comments; express intent through naming and structure. Only English documentation of a public API or of external behavior the code cannot show is allowed. Delete other legacy comments when touched.
- Use top-level imports only, avoid unexplained `any`, and inline one-line helpers with a single call site. Verify external package APIs against the installed version's types and source.
- Use the established library or SDK when one covers the need; a hand-written replacement needs a stated reason.
- Full local vitest/Playwright runs belong in CI or `~/.agents/mini-test/mini-test`; on this laptop run one explicit test file, or set `CAIRN_LOCAL_HEAVY=1` only as a conscious escape hatch.
- When you fix a defect, name its bug class, search every path the change touches for other instances, and fix them together.
- Product-fix regression tests must fail on the parent source; test deletion, oracle weakening and regression-ledger removal are blocked in `check`.
- Plan gate (`docs/ops/plan-gate.md`, enforced by `scripts/plan-gate.mjs`): small fixes need no plan; any feature, user-visible behavior change, new mechanism, persisted-state change, wire/step protocol change, or concurrency change requires a plan under `docs/design/<slug>.md` (user scenario, numbered scope rows, edge-case table with user-visible behavior, proving test file path, and `Slice/Status` set to `this change` or `later: <ticket or slice>`, out-of-scope list; plus states, transitions, readers, writers and failure paths for state/protocol/concurrency), reviewed by an independent model different from the author's (`Reviewer-Model` != `Author-Model`) with `Verdict: PASS` and matching `Plan-SHA256` recorded in `## Review` and cited via a `Plan: docs/design/<slug>.md` commit trailer. Every `"this change"` proving test must exist at the commit and fail against the parent product source (`scripts/regression-inversion-gate.mjs`). Code review checks the diff row by row against the plan.
- A plan, prototype or report that changes what users see, wait for or pay opens with the newcomer: someone who installed Cairn today and has never heard of its parts. Say where they meet the change and why it is there for them, what they must already know, which accounts, payments and keys it asks of them, where it stores what they give, and where they get stuck or what they see when it fails. Then give why (the user's problem and the data showing it) and a scenario table: one row per situation the user meets, with what they see, what the system does, and the wait and cost. A step only the owner takes (his own accounts, keys, infra) stays an owner action and never ships as a settings field every user sees. Refactors and single-path fixes skip this.
- Decide by your own recommendation and say in chat what you chose and why. Ask the owner for payments, credentials, intended-behavior or design changes, and decisions explicitly routed to him.
- Explain problems, designs, trade-offs and outcomes to the user through concrete scenarios, not internal symbol or protocol dumps. For each point give: a real user scenario ("when you do X..."), why it breaks or blocks in plain words, how the fix works, and what happens in that scenario afterwards; link files for reference instead of reciting field names. Skip this for one-line answers or trivial status updates.
- Keep each change small and self-contained.
- The change that retires a mechanism, path or rule updates or deletes every living document that describes it (`docs/README.md` says which are living), replacing the old text instead of adding a note above it. It also adds the retired name to `scripts/doc-retired-terms.json`, so `scripts/doc-retired-terms-gate.mjs` stops it being copied back.
- Do not commit verification evidence (logs, screenshots, probe output).
