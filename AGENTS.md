# Cairn Development Rules

Before any change under `apps/web/src`, invoke the `design-cairn` skill and run `node scripts/design-rules-for.mjs` on the files you will touch, before reading or editing the code — the printed rule rows are the ones that apply; `apps/web/DESIGN.md` holds the token frontmatter and the which-component table.

## Safety

- This repository is public: never commit secrets, credentials, internal addresses, personal information or quota details.
- Never force push, use `--no-verify`, bypass hooks with `core.hooksPath`, or run `git reset --hard`, `git clean`, `git stash` or `git checkout .`. Never overwrite uncommitted work you did not write.
- Stage only your own changes with explicit paths; never use `git add -A` or `git add .`.
- Commit identity: every agent, on a host or in a Claude Code cloud session, commits as `xiechimon <157263579+xiechimon@users.noreply.github.com>`. Authorized host agents push with his existing user gh login using ordinary git/gh, without an App token; a cloud session pushes with its own session access. Existing `Claude <noreply@anthropic.com>` and bot commits remain accepted; preserve their authors. Git hooks are not installed; run verification explicitly before pushing. Details: `docs/ops/agent-bot-identity.md`.
- Do not run postinstall scripts without explicit user authorization; install dependencies with scripts disabled unless authorized.
- Seams: read the comments in `biome.json` before changing locked imports (`@earendil-works/*`, `@modelcontextprotocol/sdk`, `simple-git`, `isomorphic-git`, `cron-parser`) and consume them through thin bridges. Keep GitOps, MCP and LLM provider access behind `apps/daemon/src/backend/`; the exceptions are the in-server Coordinator runtime, `apps/server/src/coordinator/runtime/`, and the MCP connector client in `apps/server/src/services/mcp-servers.ts`.
- Never kill another lane's processes; inspect the PID, command and working directory before stopping a process you started. Shared ports, heavy slots and worktree rules: `docs/ops/worktrees-and-ports.md`.
- No change may edit what judges it: the eval suite (`eval/**` — task set, scorers and run configuration — is a `humanQueue.evalConfig` path in `packages/shared/merge-gate-paths.json`), and the gate reads the exam from the merge-base checkout at run time.
- Before pushing a change to a security surface, run `/security-review` and fix confirmed findings; name any finding you leave unfixed, with its reason, in the commit message.

Security surfaces (the `credentials`, `machineAndCommandBoundary` and `externalEntryAuth` lists in `packages/shared/merge-gate-paths.json`; `apps/server/test/merge-gate-paths-json.test.ts` fails when this list differs):

- Keys and encryption: `apps/server/src/lib/{secret-box,keys,token-auth,owner-channel,attachments-token}.ts`, `apps/server/src/services/{secrets,credentials,api-keys,oauth,github-connection,github-connection-device,github-device-core}.ts`, `apps/server/src/coordinator/{credentials,codex-login}.ts`

## Ship

Work lands on `main` through the `queue/main` ref, enforced by the `green-main` ruleset: main accepts only commits whose `check`, `pack-smoke` and `e2e-gate` checks are already green, so pushing an untested `HEAD:main` is rejected by GitHub itself. Push to `queue/main` instead (one candidate at a time, only through `scripts/ops/push-queue.mjs`, step 5); the `promote` workflow lands it automatically once its `ci` run is green, or run `node scripts/ops/promote-queue.mjs --wait --enforce` yourself (`docs/design/tested-sha-landing.md`). There is no pull request, merge queue or PR-body format. Production safety lives in the deploy: the shipped product is the Mac desktop app, published by the `desktop-release` workflow on every push whose app sources moved since the last `desktop-v*` tag — it does not gate on `check`/`pack-smoke`/`e2e-gate`. A Claude Code cloud session lands work the same way: it lands work through `scripts/ops/push-queue.mjs` the same way and promotes it, whatever branch its session defaults name.

Work happens in worktrees, never in the primary checkout: a machine-level pre-commit hook there refuses commits, and its tree stays clean so `cairn-autopull` can fast-forward it to `origin/main`.

1. Work in your own worktree on a branch from the latest `origin/main`.
2. Commit any uncommitted changes. Tidy noisy intermediate commits into a few clear ones while they are still unpushed.
3. `git fetch origin main` and rebase onto the latest `origin/main`; resolve conflicts. If the rebase floods add/add conflicts in unrelated files, the clone is shallow: run `git rebase --abort`, `git fetch --quiet --unshallow origin main`, then rebase again.
4. Verify on GitHub runners: `node scripts/ops/preflight.mjs --wait` pushes `HEAD` to your own `refs/heads/preflight/<lane>` and waits for the `ci` run there; the repo is public, so standard runners cost nothing. That green run is the admission ticket — `pnpm prepush` and `pnpm test:changed` stay available for fast local iteration but are optional, and the gate in step 5 enforces only the GitHub evidence. Run `/security-review` when a security surface changed. Run the review inside a subagent (the Agent tool, told to follow `/security-review` and return its findings), not as a slash command in your own turn — a slash command can end your turn with the work uncommitted. Read the subagent's findings, fix confirmed ones, then commit and continue with steps 5 to 8 in the same turn. When the change alters user-facing behavior, walk the touched journeys on a `verify-cairn` live stack before claiming it works — fixture e2e and source review do not prove live behavior; keep the evidence (screenshots, requests, or DB rows). Show the owner the evidence in the wrap-up: screenshots of each touched journey or a live page he can open; a claim he cannot see is an unverified claim. `pnpm test:changed` runs the changed test files and the tests named after changed source files, within a 10-minute budget; CI runs the full suite. Do not run `vitest --changed` locally: a shared package change selects nearly every test. Web e2e runs in CI after the push, not locally; while writing or fixing a spec, run that one spec with `pnpm exec playwright test <spec>`.

   The gate, not the local check: `push-queue.mjs` refuses a head whose `check` + `pack-smoke` + `e2e-gate` contexts are not green on GitHub. Get them for free by pushing `node scripts/ops/preflight.mjs --wait`, which force-pushes `HEAD` to your own `refs/heads/preflight/<lane>` and watches the `ci` run there — the repo is public, so standard runners cost nothing and a docs-only head greens in about a minute. Local `pnpm prepush` and `pnpm test:changed` are optional fast iteration; pre-flight is the admission ticket. A green run on a commit with the same tree counts, so trailer stamping does not invalidate it; any later edit means re-running pre-flight. Mechanics: `docs/design/preflight-ci-verification.md`.
5. Push without force, through the one script that touches `queue/main`: `node scripts/ops/push-queue.mjs`. It applies to every agent and human, whatever tool made the commits (Amp, Claude Code, a Cairn task, your own shell). Never run `git push origin HEAD:queue/main`, `git push origin :refs/heads/queue/main` or `git push origin HEAD:main` by hand, and never write a loop that deletes or recreates `queue/main`. `queue/main` holds one candidate at a time: while the candidate on it has not landed on `main`, the script refuses and prints what it waits on; wait until it lands or is dropped, then push again — `node scripts/ops/push-queue.mjs --wait` does that loop for you: while a candidate is live it rebases your commits onto it, pushes your head to your `preflight/<lane>` ref for green evidence, polls until the candidate lands or is dropped, then pushes the fast-forward (a drop puts you back on `origin/main` instead of stacking you on the dropped commits). The script stamps a `Lane: <host>/<worktree>` trailer on commits that carry no `Amp-Thread-ID` or `Lane`, so drops and refusals name an owner. The `promote` workflow promotes a green candidate automatically; a candidate whose `ci` run has a failed job (cancelled jobs do not count) gets those jobs rerun once, and if they fail again, or the run is cancelled twice, or `main` moved past it, the workflow drops it and comments the reason on the commit — subscribe to your own commit's CI and read that comment. Consecutive commits with the same owner (`Amp-Thread-ID` or `Lane`) stay or go together; commits without an owner drop together. To watch or unblock sooner, `node scripts/ops/promote-queue.mjs --wait --enforce` does the same promotion locally. Mechanism details (guard, drop plan): `docs/design/tested-sha-landing.md`.
6. A candidate leaves `queue/main` only by landing or by the `promote` workflow dropping it; you never remove one, not even one you think is yours or dead, because you cannot tell whose it is and a dropped red candidate is rerun first. If the promoter rejects as `stale`, or your push was refused, wait for the answer and, once `queue/main` is free, fetch, rebase onto the latest `origin/main` and run the script again. A human operator who must clear a live candidate first comments `queue/main release: <reason>` on its commit. Do not repeat step 4 after a later fetch, rebase or rejected push unless conflict resolution or other local edits changed files after it passed.
7. A conflict that changes behavior: resolve it so both sides' intent survives, rerun step 4, and push without asking; name the other lane's commit and how you merged it in your commit message or wrap-up.
8. Check CI on `origin/main` before pushing — judge the latest **completed** `ci` run; a run that is pending, in progress or cancelled is evidence of nothing, so keep looking back to the last run that finished. If that run is red, compare the failing jobs with the area your change touches: overlap means fix it or wait; no overlap means you may push, but when a red job covers your tests, verify them locally yourself. After pushing, watch CI on your commit and diff its failing jobs against the parent's: new failures are yours — fix them, or revert your commit if you cannot fix quickly; an identical failure signature is inherited — report the owning lane in chat, your commit stays. A red that survives several runs unclaimed and blocks deploys falls to the next lane needing a green deploy, or to the owner.
9. Once your work is on `main`, delete every remote branch you pushed for it (`git push origin --delete <branch>`) without asking; this standing approval covers only branches you pushed yourself.
10. Remove your worktree and its local branch once your work is on `main` (`git worktree remove`, then `git branch -d`) without asking — a landed worktree only consumes disk. This covers only worktrees and branches you created.

## How to work

- Product prompts, defaults and gates must suit every Cairn user; the owner's personal workflow preferences belong in his own config, not the product.
- Repository content is English: code, docs, scripts, tests and commits. Product UI strings in `t()`, translations, matching fixtures and selectors, agent-facing product prompts and `README.zh.md` may be Chinese. Follow the user's language in conversation.
- Commit format: `<scope>(<ticket>): <subject>`, in English. Put `Closes #N` on its own line when the commit finishes ticket N, or `Part of #N` for one segment.
- Read files in full before editing, and check consumers before moving or renaming paths. Ask before removing intentional functionality or changing intended behavior.
- Do not write code comments; express intent through naming and structure. Only English documentation of a public API or of external behavior the code cannot show is allowed. Delete other legacy comments when touched.
- Use top-level imports only, avoid unexplained `any`, and inline one-line helpers with a single call site. Verify external package APIs against the installed version's types and source.
- Use the established library or SDK when one covers the need; a hand-written replacement needs a stated reason.
- When you fix a defect, name its bug class, search every path the change touches for other instances, and fix them together.
- Design first for a change to persisted state, a wire or step protocol, or concurrency: write a one-page design (states, transitions, every path that reads or writes the state, the behavior on each failure) before code, with one test per path.
- A plan, prototype or report that changes what users see, wait for or pay opens with the newcomer: someone who installed Cairn today and has never heard of its parts. Say where they meet the change and why it is there for them, what they must already know, which accounts, payments and keys it asks of them, where it stores what they give, and where they get stuck or what they see when it fails. Then give why (the user's problem and the data showing it) and a scenario table: one row per situation the user meets, with what they see, what the system does, and the wait and cost. A step only the owner takes (his own accounts, keys, infra) stays an owner action and never ships as a settings field every user sees. Refactors and single-path fixes skip this.
- Decide by your own recommendation and say in chat what you chose and why. Ask the owner for payments, credentials, intended-behavior or design changes, and decisions explicitly routed to him.
- Explain problems, designs, trade-offs and outcomes to the user through concrete scenarios, not internal symbol or protocol dumps. For each point give: a real user scenario ("when you do X..."), why it breaks or blocks in plain words, how the fix works, and what happens in that scenario afterwards; link files for reference instead of reciting field names. Skip this for one-line answers or trivial status updates.
- Keep each change small and self-contained.
- Do not commit verification evidence (logs, screenshots, probe output).
