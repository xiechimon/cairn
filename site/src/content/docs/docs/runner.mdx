A Runner is the `cairn` daemon on a machine where agents should work. It claims work from your server and runs each thread directly on that host in its own git worktree, so code and credentials stay there. One Runner can be the same machine as the server; you can add more later.

The desktop app already starts and approves its bundled pi Runner; do not install a second CLI for it. The commands below are for npm or extra machines. pi is included in the Runner and does not require a Codex CLI login. [Connect your model in Cairn](/docs/models/). Check that the Runner shows as online under **Settings → Runners**.

<Aside type="tip">
Prefer a machine that stays on, such as a desktop, a home server or a VPS. A laptop sleeps or drops off the network, and work waits until it is back.
</Aside>

## Enroll through the browser

This is the default path, and what the `Add Runner` dialog in the web app shows.

<Steps>

1. On the machine that should do the work, install the CLI:

   ```sh
   npm install -g @xiechimon/cairn-cli@latest
   ```

2. Start it:

   ```sh
   cairn start
   ```

   It prints a link: `Open <url> and approve this machine (expires in 10 minutes).` If the server is not on this machine at `http://127.0.0.1:8787`, add `--server <url>`.

3. Open the link in a browser that is signed in to your Cairn. The `Authorize Runner` page asks you to confirm; press `Authorize`.

4. The Runner shows as online in the web app. It keeps running in the background; you can close the terminal. Its credentials are saved in `~/.cairn/machine.json`, so later starts need no approval.

</Steps>

## Enroll with an API key

For a cloud server with no browser at hand, expand `Running on a cloud server? Register with an API key instead` in the same dialog, create a key under `API keys` (the plaintext shows once), then run:

```sh
cairn start --api-key <cairn_...> --team <teamId>
```

The dialog fills in your team id.

## Everyday commands

```sh
cairn start          # start in the background
cairn stop
cairn restart
cairn status         # local machine and daemon state
cairn logs -f        # follow daemon.log
```

## Keep it running on Linux

Tasks run directly on the Runner host in isolated git worktrees; no container runtime or bubblewrap sandbox is required. On Linux, `cairn start` and `cairn restart` try to run the daemon as a transient systemd user unit (`cairn-daemon-<id>.service`) and print its name. When `systemd-run --user` is unavailable, they print a warning and fall back to a plain background process, which still runs tasks normally.

A transient unit or plain background process ends when you log out or reboot. To keep the Runner up across logouts and reboots, enroll it once as above, stop it with `cairn stop`, and create `~/.config/systemd/user/cairn-daemon.service`. Use `command -v cairn` and `command -v node` for the two paths:

```ini title="~/.config/systemd/user/cairn-daemon.service"
[Unit]
Description=Cairn daemon

[Service]
Environment=PATH=/directory/of/node:/usr/local/bin:/usr/bin:/bin
ExecStart=/path/to/cairn start --foreground
Restart=on-failure

[Install]
WantedBy=default.target
```

```sh
systemctl --user daemon-reload
systemctl --user enable --now cairn-daemon.service
```

## Server and Runner on the same machine

Both packages install a `cairn` command. If you install both globally on one machine, the one installed last owns the name. The clean split is `npx @xiechimon/cairn` for the server and the global `@xiechimon/cairn-cli` for the Runner.

## A Runner on another machine

The server listens on loopback only. For a server on an always-on host and a Runner on another machine, start the server with `HOST` set to that host's LAN address and `CAIRN_TOKEN` set alongside (it refuses a non-loopback address without a token), then start the Runner with `--server http://<host>:8787`. See [configuration.md](https://github.com/xiechimon/cairn/blob/main/docs/configuration.md).
